# GRAF `v2026.08.16.7` — единый вход, безопасное связывание аккаунтов и стабильные названия встреч

## Что изменилось для пользователя

### Один аккаунт — несколько способов входа

- Пользователь может связать вход по email-коду и OAuth с одним аккаунтом GRAF.
- При связывании всегда проверяется владение обоими способами входа.
- Пустой дубликат связывается автоматически после подтверждения.
- Если в обоих аккаунтах уже есть данные, перед объединением показывается понятный
  предварительный экран с тем, что будет сохранено и какой аккаунт останется основным.
- После подтверждения сохраняются встречи, записи и допустимые пользовательские
  связи; исходный аккаунт архивируется, а его старые сессии и доверие устройств
  отзываются.
- В настройках аккаунта видны связанные способы входа. Дополнительный OAuth-способ
  можно удалить после повторного подтверждения, но последний рабочий способ входа
  удалить нельзя.

### Понятное восстановление входа

- Если один email связан с несколькими аккаунтами, система больше не выбирает
  аккаунт наугад и не создаёт ошибочную сессию.
- Пользователь получает объяснение причины и безопасный путь к подтверждённому
  связыванию или объединению.
- Поток одинаково работает в браузере и во встроенном окне GRAF Local.
- Для локального приложения сохранён passwordless-вход по email-коду; production
  OAuth и production cookies не меняются локальным режимом.

### Читаемые названия встреч

- Веб-кабинет и приложение показывают название календарной встречи или проверенное
  имя приложения вместе с датой и временем записи.
- Предыдущая встреча повторяющейся серии больше не получает дату дважды: дата
  передаётся отдельно и отображается один раз.
- Для ручных загрузок API сохраняет исходное имя файла, включая `.wave`, а
  очищенное от расширения имя используется только в визуальном списке.
- Пользовательские и явно заданные названия не заменяются автоматически.

## Безопасность и совместимость

- Объединение аккаунтов требует одноразового подтверждения, CSRF, блокировок строк,
  идемпотентности и узкого RLS-контекста обслуживания.
- Web-приложение не получает общий maintenance-доступ.
- Миграция `0073_account_auth_linking` добавляет только необходимые сущности
  намерения объединения, журнал и архивное состояние исходного аккаунта.
- Сервер совместим с предыдущими клиентами.
- Публичное macOS-обновление использует Developer ID Application/Installer,
  Apple notarization, stapling, Gatekeeper и существующую цепочку Sparkle.

## Эксплуатация и откат

- Production rollout выполняется на exact SHA, указанном в deployment receipt для этого тега.
- Перед миграцией создаётся резервная копия; штатный CD выполняет health checks,
  smoke и guarded rollback.
- При проблеме macOS-обновления сохраняется предыдущий подписанный ZIP и appcast;
  неподписанный downgrade не используется.

## Ограничения

- Production smoke и фактическое состояние внешних сервисов зависят от remote CD
  и фиксируются в deployment receipt после выкладки.
- RLS hardening boundary в локальном CI не выполняется без отдельной probe-базы;
  strict RLS suite при этом прошёл.
