### Почему после загрузки дважды читается сохранённый отказ

На точном JavaScript выпуска `v2026.11.10.4`
(`a50cf9748cab05bff7eb5ce5a0696da18c64ade6`) воспроизведён новый запуск
Chrome с учебным сохранённым отказом. Браузер получил контроллер и библиотеку
CookieConsent из тега; HTML и ответы API были учебными, все запросы
перехвачены внутри отдельной сессии. Рабочий сервер не вызывался.

Первое чтение инициирует callback `onConsent` библиотеки при загрузке
сохранённого выбора. Второе запускает обработчик обычного `pageshow`
(`persisted=false`). Оба вызова относятся к одному учебному отказу;
контроллер принимает результат только от последнего начатого чтения.

| Ответы в порядке начала запросов | Состояние после завершения обоих |
| --- | --- |
| 200, 200 | `necessary_only`, без предупреждения |
| 200, 503 | `unknown`, кнопка «Повторить сохранение отказа» |
| 503, 200 | `necessary_only`, без предупреждения |

В случаях со смешанными ответами первый ответ приходил раньше второго.
Ни в одном случае не отправлялись `grant`, `revoke` или события провайдеру.
Отдельное учебное событие `pageshow` с `persisted=true` вызвало одно новое
чтение: проверка выбора при возврате из кэша браузера — самостоятельный путь.
Настоящий возврат из кэша и синхронизация отзыва между вкладками в этом
проходе не проверялись.

Критерий будущего исправления: обычная загрузка с неизменённым выбором не
должна запускать два конкурирующих чтения. При возврате из кэша и изменении
выбора в другой вкладке нужна свежая проверка; при неподтверждённом состоянии
необязательный сбор остаётся отключённым. Код и настройки не менялись.

### Что показал настоящий возврат кнопкой «Назад»

В отдельном Chrome с локальным HTTP-сервером сравнили точный код выпуска
`v2026.11.10.4` и пробный вариант в памяти. В пробе обычный `pageshow`
не перечитывает публичный выбор, если сохранение нового выбора не идёт.
Путь при возврате из кэша, обработчик другой вкладки и поведение кабинета
оставили без изменений. Использовали библиотеку из выпуска; её запрет
автоматизированных браузеров отключили только в учебной обвязке, как в
штатной браузерной проверке проекта.

| Сценарий | Запросы и результат |
| --- | --- |
| Исходник выпуска, обычная загрузка с сохранённым отказом | Два `read`, ответы 200 и 503. Итог `unknown`, видна кнопка повтора. |
| Пробный вариант, обычная загрузка при том же наборе ответов | Один `read` из `onConsent`, ответ 200. Итог `necessary_only`, кнопки повтора нет; второй ответ не запрашивался. |
| Пробный вариант, единственное чтение возвращает 503 | Один `read`. Итог `unknown`, видна кнопка повтора. Необязательных событий нет. |
| Пробный вариант, настоящее «Назад» с восстановлением документа из кэша | Chrome сообщил `pageshow.persisted=true`; маркер документа не сменился. Возврат к видимости и `pageshow` сделали два `read`. При ответах 200 и 503 итог снова `unknown`, видна кнопка повтора; необязательных событий нет. |
| Пробный вариант, другая вкладка записывает учебный отзыв и новый маркер | В первой вкладке реальное событие `storage` вызвало один новый `read`; выбор сменился с `accepted_all` на `revoked`. Попытка отправки события заблокирована. |

Убрать чтение только на обычном `pageshow` недостаточно: тот же сбой
остаётся при возврате из кэша. Для приёмки нужны оба сценария, остановка
необязательного сбора до подтверждения текущего выбора и отдельная проверка,
что новый отзыв либо смена маркера не могут быть перекрыты поздним старым
ответом. Для проверки вкладок меняли учебное хранилище и ответ сервера;
сохранение отзыва через интерфейс в этой пробе не проверялось.
Управляющие запросы были только `read`. Рабочий сайт, настройки и код
репозитория не менялись; это локальное доказательство для F273, а не
закрытие T106 или рабочая приёмка измерения.

### Одно чтение при возврате и проверка позднего ответа

Во второй локальной пробе при `pagehide.persisted=true` сразу сбрасывали
подтверждённый выбор и запрещали сбор. До `pageshow` обработчики не
начинали чтение из замороженного документа. При настоящем возврате
`pageshow.persisted=true` перечитывал текущее значение. Вне этого интервала
событие другой вкладки по-прежнему самостоятельно инициировало чтение.
Проба собрана в памяти поверх `v2026.11.10.4`; проверка в Chrome
`157.0.8103.40` обращалась только к локальному серверу.

| Проверка | Наблюдение |
| --- | --- |
| Обычная загрузка и настоящий возврат с прежним отказом | По одному `read`; один ответ 200 подтверждает `necessary_only`. При единственном 503 состояние `unknown`, виден повтор, необязательных событий нет. При возврате маркер документа сохраняется. |
| Другой вкладкой меняют согласие, пока ответ на чтение после возврата задержан | До ответа состояние `unknown`, попытка отправки блокируется. Событие `storage` запускает новое чтение и подтверждает `revoked`. Старый ответ с разрешением затем доставлен и разобран; состояние осталось `revoked`. Локальный маршрут принял один контрольный просмотр до ухода со страницы и ни одного дополнительного события. |
| Другая вкладка отзывает согласие, пока документ ещё в кэше | Находясь в кэше, документ запросов не сделал. После возврата Chrome доставил `pageshow`, затем отложенное событие `storage`; оба вызвали чтение. Два ответа 200 дали `revoked`; ответы 200 и 503 оставили `unknown` и кнопку повтора. В обоих случаях маршрут не получил новых событий. |

Последний сценарий важен для приёмки: отложенное событие другой вкладки
отличается от лишнего чтения на `visibilitychange`. Нельзя отбрасывать
`storage` только потому, что страница только что вернулась из кэша: в
проверке с задержанным ответом именно оно доставило сведения о новом отзыве.
В отдельном WebKit `26.6` обычная загрузка прошла с одним чтением, но
переход «Назад» создал новый документ; ветка настоящего восстановления из
кэша этим запуском не принята. Проверка правок в коде, штатный выпуск и
приёмка на рабочем сайте остаются открытыми.

## Авторизованный рабочий отчёт

В существующей сессии браузера `GET /api/v1/product-analytics/reports` вернул
рабочую схему `graf-product-analytics-report-surface-v1`. Обезличенный агрегат
доступен (`aggregate_state=measured`). В отчёте доли согласия R11 указано
`counts_unavailable`, в отчёте стоимости результата R07 —
`report_counts_unavailable`. По контракту это означает отсутствие пригодного
источника счётчиков согласия и конверсий для отчёта. Ответ не устанавливает,
отсутствует ли файл на сервере, не читается ли он или не проходит проверку.

Отдельная проверка метаданных в работающем `rec-api` уточнила причину:
переменные файла и каталога счётчиков не заданы, используется путь по
умолчанию, отдельного монтирования поверх него нет. Файл и его родительский
каталог возвращают `ENOENT` при той же учётной записи и группах, что у
процесса `uvicorn`. В проверяемом контейнере вход отчёта отсутствует; до
разбора файла дело не доходит. SHA-256 модуля отчёта совпал с исходником
`167adbd03ac808d921c4c657c8e2aea95710a80c`; весь образ не сравнивался.

Защищённое чтение и доступность агрегата подтверждены. Для R11 и R07
следующий шаг — получить реальные счётчики за согласованный период из
[источников, предусмотренных для отчёта](../analytics/product-analytics-reports.md#10-что-требует-оператора),
затем подключить их штатно и сверить показания. Проверка не устанавливает,
хранятся ли выгрузки где-либо ещё. Доля согласия, стоимость результата,
допустимые визиты, регистрации, первые результаты и оплаты не подтверждены.
Содержимое счётчиков и секреты не читались, события не отправлялись,
настройки не менялись.

### R11: проверка периода в двух источниках

В опубликованном `v2026.11.10.4` (`a50cf9748cab05bff7eb5ce5a0696da18c64ade6`)
файл `report_surface.py` совпал по SHA-256 с файлом рабочего `rec-api`:
`c43d5f93e972425eb69f8b44f23afff86d0fa965306e883a7dae95ef89348e66`.
По исходнику этого выпуска `report-counts.json` читает отчёт, а заполнять его
должен оператор. Штатный поставщик файла в серверном коде, `infra` и `scripts`
этого исходника не найден. Метрика с неустановленной полнотой и обезличенные
HTTP-сигналы не заменяют число согласившихся визитов.

Изолированная проба на точном исходнике выпуска проверила `build_product_report_surface`
с подставленным чтением двух дневных агрегатов: 100 в заданной неделе и 900
за её пределами. При одном и том же учебном числителе 40 файл без обеих дат
дал опубликованную долю `4 %` (`40/1000`): запрос знаменателя получил обе
границы `None`. С обеими датами тот же код ограничил знаменатель неделей
и дал `40 %` (`40/100`). Рабочая БД и внешние сервисы в пробе не использовались.
Действующий тест выпуска также явно разрешает публиковать долю без периода.

Отсутствие файла в рабочем отчёте сейчас скрывает эту проблему. При приёмке
T099 нужен числитель из фактических событий с согласием и сверка обеих сторон
за один завершённый период. Проверка должна подтвердить, что без известного
общего периода доля не показывается, а данные другого дня не меняют долю
за выбранный период. Ни один из учебных процентов не является измерением ГРАФ.

### R11: что фактически входит в знаменатель

На том же выпуске выполнена отдельная проверка через защищённый HTTP-отчёт
и изолированную PostgreSQL 17. Даты числителя и знаменателя совпадали.
При 100 сигналах просмотра и учебном числителе 40 отчёт показал **40 %**.
После добавления 30 сигналов завершения регистрации и 70 выдач установщика
за тот же день отчёт показал знаменатель 200 и **20 %**. Новых просмотров
страниц и согласившихся событий в проверке не добавляли. Временная проверка
прошла, PostgreSQL и рабочая копия убраны.

Причина: запрос знаменателя не ограничивает тип события. В общей таблице
также есть страницы, для которых ведётся только обезличенный счёт; у них
нет парного сигнала уровня 3. Для T099 нужно отдельно согласовать единицу
счёта, одинаковые даты и охват страниц, фильтр трафика и обработку малых
корзин. Выдачи установщика и шаги регистрации остаются отдельными
показателями. Просмотры и сигналы HTTP сами по себе не дают долю уникальных
посетителей. До сверки фактических источников долю считать неизвестной.

## T106: старое событие после отзыва и нового согласия

На точном исходнике `v2026.11.10.4` (`a50cf9748cab05bff7eb5ce5a0696da18c64ade6`)
проведена новая проверка двух HTTP-клиентов через настоящие маршруты
управления согласием и приёма событий и отдельную PostgreSQL 17. Старый
клиент сохранил запрос с первоначальным маркером версии выбора, как могла
бы сделать открытая вкладка. Второй клиент отозвал согласие и затем дал
новое явное согласие. Внешний транспорт подставлен; рабочие реестры,
провайдеры и пользовательские данные не использовались.

| Попытка | Ответ маршрута | Новых вызовов учебного приёмника |
| --- | --- | ---: |
| Событие с действующим первым согласием | HTTP 202, `delivery.delivered=true` | 1 |
| То же старое событие после принятого отзыва | HTTP 202, `choice_blocked`, `delivered=false`, `retryable=false` | 0 |
| Старое событие после нового явного согласия | HTTP 202, `choice_blocked`, `delivered=false`, `retryable=false` | 0 |
| Событие с новым маркером согласия | HTTP 202, `delivery.delivered=true` | 1 |

В каждом ответе маршрута было `accepted=true`: это приём запроса, а не
доставка. Проверка должна читать `delivery` и подтверждать приём отдельно.
Итог изолированного сценария: 1 успешная проверка, 2 предупреждения среды,
контейнер и временные файлы удалены. Подтверждена граница серверной отправки;
автономный браузерный SDK и рабочая доставка по-прежнему не приняты. T106
остаётся открытой, рабочие настройки и данные не менялись.

| `direct` | 62 | 6 |

### Что именно считает обезличенный агрегат

На исходнике выпуска `v2026.11.10.4`
(`a50cf9748cab05bff7eb5ce5a0696da18c64ade6`) выполнены пять независимых
учебных сценариев: штатный HTTP-маршрут `/transcription` → запись в
изолированной PostgreSQL 17 → чтение штатным фильтром отчёта. В каждом
сценарии три запроса; состояние БД перед следующим сценарием сбрасывалось.

| Учебный сценарий | Что прошло в отчёт |
| --- | --- |
| Три открытия одним клиентом, включая два повторных | `external / direct`: 3 |
| По одному открытию тремя независимыми клиентами | `external / direct`: 3 |
| Три предварительные загрузки с `Sec-Purpose: prefetch`, без открытия страницы пользователем | `external / direct`: 3 |
| Три перехода с другой страницы того же сайта | `external / referral`: 3 |
| Три перехода с другого сайта | `external / referral`: 3 |

Все пять проверок прошли. Это HTTP-сценарии с учебными заголовками,
адресами и клиентами, без рабочего сайта и браузерной доставки событий.
Код выпуска не менялся; штатный запуск удалил временную БД.

Порог три скрывает мелкие группы, но не устраняет повторные открытия и
предварительные загрузки. В `referral` могут попасть внутренние переходы.
Поэтому числа рабочего агрегата выше — нижняя граница *HTTP-сигналов после
фильтра*, а число допустимых посещений людей по ним нельзя оценить ни
сверху, ни снизу. Даже после подтверждения фильтра адресов оператора в
T098 для M01 нужен проверенный источник сессий: повторное открытие не
создаёт новый визит, предварительная загрузка не создаёт визит, внутренний
переход сохраняет исходный канал. Два дня должны быть подтверждены для
одного и того же внешнего источника, а не для категории `referral` в целом.

### Записи источника и атрибуты аккаунта

10 ноября в 12:55 UTC в рабочей PostgreSQL прочитаны только количества
записей за **2–8 ноября UTC**: от `2026-11-02T00:00:00Z` включительно до
`2026-11-09T00:00:00Z` исключительно. Обе таблицы доступны на чтение обычной
роли `rec-api`; для этих двух таблиц ограничение видимости строк не действует.
У роли нет полномочий суперпользователя или обхода такого ограничения.

| Рабочий источник | Поле даты | Записей |
| --- | --- | ---: |
| `public_visit_attributions` — сохранённый источник перехода | `first_seen_at` | 3 |
| `client_acquisition_attributes` — атрибут источника аккаунта | `captured_at` | 0 |

Штатная проверка допустимости записи для уровня профилей атрибуции вернула

идентификаторы, записи пользователей и параметры кампаний не извлекались.
G014 остаётся открытой: нужна подтверждённая связь от допустимого перехода
до нового аккаунта и сверка с отдельным учётом неизвестной атрибуции.

### G014: переход, регистрация и повторный вход

На точном исходнике `v2026.11.10.4` через штатные HTTP-маршруты и временную
PostgreSQL 17 проведены четыре учебные регистрации. Код подтверждения брался
из режима локальной проверки; почта и внешние системы не использовались.

| Первый переход | Что записал сервер | Источник нового аккаунта |
| --- | --- | --- |
| `/download`, учебная метка `utm_medium=organic` | Запись перехода с метками | `linked`, метки и `/download` сохранены |
| `/download`, учебная метка `utm_medium=referral` | Запись перехода с метками | `linked`, метки и `/download` сохранены |
| Руководство о Zoom, переход из поиска Яндекса с `utm_source` и `utm_medium=organic` | Только обезличенный счётчик, категория `referral` | `unknown`, без источника и кампании |
| То же руководство и тот же поисковый реферер без меток | Только обезличенный счётчик, категория `organic` | `unknown`, без источника и кампании |

В каждом сценарии после регистрации проверен повторный вход после перехода
с другой меткой: осталась одна и та же запись связи, включая `unknown`.
Первый прогон дал 2 успешные проверки и один отказ: ожидание `organic` для
помеченного запроса не совпало с кодом. Классификатор выбирает `referral` при
наличии `utm_source` до проверки поискового реферера, если метка не относится
к платным. После добавления контроля без меток итог: 4 успешные проверки,
2 предупреждения среды. Временные данные удалены, код не менялся.

Вывод для органики: по обезличенному просмотру руководства нельзя присвоить
источник зарегистрировавшемуся аккаунту. Метка `utm_medium=organic` сама по
себе не делает помеченный просмотр руководства органическим в агрегате.
G014 остаётся открытой для рабочей приёмки и остальных сценариев. Связь
нельзя восстанавливать догадкой или расширением сбора без отдельного допуска.

### T112: почему первый результат не попадает в учёт

На исходнике опубликованного выпуска `v2026.11.10.4`
(`a50cf9748cab05bff7eb5ce5a0696da18c64ade6`) проверен путь двух событий:
`first_result_viewed` и `first_value_session_completed`. У браузерного
кабинета есть функции сборки этих событий, но вызовов из рабочих маршрутов
выпуска нет. В приложении macOS есть вызовы после открытия результата во
встроенном кабинете. Общий серверный приёмник отклоняет оба имени до записи
в БД: выпуск ещё не подтверждает на сервере, что владелец действительно открыл
готовый непустой результат.

Штатный набор на изолированной PostgreSQL 17 дал **3 успешные проверки**:
два маршрута отклоняют события без доверенного триггера; положительный
контроль `first_recording_completed` принят, а повтор через другой маршрут
помечен как дубликат. В отдельной временной проверке с тем же кодом сервера
обоим событиям передали разрешённые поля готового результата и использовали
учебную авторизованную сессию. Оба сценария прошли: маршруты вернули
`403 product_analytics_trigger_unverified` и
`403 posthog_desktop_trigger_unverified` соответственно, в таблице вех —
**0 строк** для отрицательного сценария. Только в тестовом процессе были
подставлены результаты проверок допуска; транспорт к провайдерам запрещён.
Временная БД и рабочая копия проверки убраны.

Одного включения сбора недостаточно: после допуска T113 нужен серверный
триггер T112 и приёмка обеих продуктовых ветвей. Положительный контроль
проверяет приём события завершения записи, а не обработку самой записи или
просмотр результата. Рабочие первые результаты не измерены, T0 не назначен.

## Регистрации и платежи в рабочем учёте

За **2–8 ноября UTC** в обезличенном агрегате рабочей PostgreSQL найдено
**0 записанных сигналов завершения веб-регистрации**

все способы входа и не устанавливает число новых аккаунтов.

### Какие новые аккаунты охватывает счётчик

На точном коде выпуска `v2026.11.10.4`
(`a50cf9748cab05bff7eb5ce5a0696da18c64ade6`) три штатных сценария прошли
через HTTP и изолированную PostgreSQL 17. В каждом проверили создание
нового аккаунта и сумму записанных сигналов `public_signup_completed`.

| Как создан учебный аккаунт | Новый аккаунт | Сигналы завершения |
| --- | ---: | ---: |
| Форма регистрации, код из письма (`/sign-up/email/verify`) | 1 | 1 |
| Форма входа, новый адрес и код из письма (`/login/email/verify`) | 1 | 0 |
| Вход через Яндекс с учебным ответом провайдера | 1 | 0 |

В сценарии Яндекса дополнительно сохранилась связь с учебной меткой перехода
на `/download`. Так что отсутствие сигнала не означает ни отсутствия нового
аккаунта, ни отсутствия атрибуции. Провайдер и почта не вызывались. Временная
проверка добавляла чтение суммы к существующим тестам; код приложения не
менялся. Итог: **3 проверки прошли**, временная PostgreSQL и рабочая копия убраны.

Для недельного показателя нужен разрешённый агрегат по времени создания
аккаунта: каждый аккаунт один раз, все способы регистрации, служебные и
учебные аккаунты исключены. Подтверждённых внешних, непроверенный статус
аккаунта и неизвестный источник следует различать. Запись атрибуции нужна
для разбивки по источникам, а её отсутствие не должно исключать аккаунт из
проверки. `public_signup_completed` остаётся счётчиком конкретной формы.
