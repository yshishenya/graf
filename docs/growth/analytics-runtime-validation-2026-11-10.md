  пропуска из-за порядка установки Playwright. Оба пропущенных браузерных
  теста прошли после установки Playwright до запуска. Отдельно прошли три
  JS-набора с Chromium: в том числе управление согласием с клавиатуры, отказ,
  повторное чтение, смена редакции и работа между вкладками.
- Дополнительный сквозной сценарий отправил через HTTP четыре учебных запроса
  одной кампании, четыре запроса Googlebot и один внешний запрос в малой
  группе. Приложение само записало сигналы в тестовую PostgreSQL. Защищённый
  отчёт с учебной авторизацией показал четыре сигнала кампании; запросы бота
  и малая группа в отчёт не попали. Доля согласия без числителя не показана.
  Точечный прогон: **3 passed**, включая два браузерных теста выше.
- На плановом исходнике `61ea5112864e46a76959bc1ee89eb3be1a54976f` отдельно

## Следующая приёмка

1. На выделенном тестовом браузере проверить переход от интерфейса отказа до
   подтверждения сервера и чтение после перезагрузки. Серверный цикл отдельно
   прошёл в продолжении ниже; причина надписи в прежнем браузере ещё неизвестна.
2. Открыть авторизованный кабинет Метрики, сверить редакцию согласия и допуск,
   затем проверить путь отдельного учебного события до отчёта. Не менять
   редакцию согласия изолированно, чтобы включить счётчик.
3. Принять рабочий авторизованный продуктовый отчёт и воронку; проверить
   точность классификации в рамках T098 и остальные условия допуска F273/T113.
   Только после приёмки измерения назначить один T0 и переходить к согласованным
   публикациям. Учебные сигналы не входят в цели роста.

## Продолжение 10 ноября: сервер сохранил учебный отказ

На момент продолжения GitHub latest — `v2026.11.10.1`, исходник
`1c581d4555c5c0976e6b24746240181fc7befc4b`. Скачанный с рабочего сайта
контроллер `analytics.js` побайтово совпал с этим исходником. В сравнении
двух исходников выпуска изменений в публичной и продуктовой аналитике нет;
это не подтверждает тождество остальных частей рабочего образа.

В публичном API `/analytics/public-consent` проверен один цикл со случайным
учебным идентификатором, без аккаунта и cookies: `read` → 200 `unknown`,
`revoke` → 200 `revoked`, затем `read` по новому HTTPS-соединению → 200
`known`. Сервер вернул тот же маркер версии выбора, `categories=["necessary"]`
и `copy_version=null`; каждый ответ имел `Cache-Control: no-store`. Это
подтверждает запись и повторное чтение отказа на рабочем сервере. Создана
одна учебная запись отказа; идентификатор и маркер в отчёте не сохранены.
Кнопка и перезагрузка браузера в этом продолжении не проверялись.

Отдельно один запрос с пустым объектом JSON к `/analytics/public-event` получил
403 `consent_revision_mismatch`, `accepted=false`. Рабочий маршрут отверг
запрос до обработки события. В исходнике Compose и образце настроек выпуска
для `TWOBRAIN_PUBLIC_ANALYTICS_CONSENT_COPY_VERSION` указана `2026-10-22.1`;
точный рабочий источник прежней редакции в этом продолжении не читался.

Рабочие флаги, редакция согласия и конфигурация не менялись. Согласие не
выдавалось, событие провайдеру не отправлено. T0 не назначен.

## Проверка интерфейса в отдельном Chrome

В приватном окне рабочая главная загрузила `cookieconsent.umd.js` и
`analytics.js` с HTTP 200. При первой учебной метке с `bot` кнопка
«Настройки cookies» не открыла диалог. Точный исходник библиотеки включает
`hideFromBots` и проверяет `bot` в User-Agent, поэтому этот проход не
показывает дефект интерфейса для обычного посетителя.

Для повтора в приватном окне настроена метка `curl/8.7.1`: классификатор
ГРАФ распознаёт `curl/` как технический признак, а фильтр библиотеки согласия
по этой строке диалог не скрывает. Применение метки к повторному сетевому
запросу и открытие диалога не подтверждены: управление Mac сообщило о
блокировке экрана до завершения повторной проверки. Отказ через интерфейс
не отправлен, повторное чтение после перезагрузки не проверено. Следующий
шаг после разблокировки — сверить User-Agent запроса, открыть настройки,
выбрать «Только необходимые» и проверить подтверждение и чтение по сети.
