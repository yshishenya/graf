# T098 — подготовка отдельного восстановления специального маршрута

Состояние: **подготовлено для операторского ревью; к применению не допущено**.
Этот шаг восстанавливает только специальный маршрут до перехода A–D.
Он не продлевает исключение для rec10444 и не меняет условия выпуска.

## Что именно предлагается изменить

В текущей карте SNI значение `www.amazon.com` ведёт в
`kvn_xray_reality`. По [описи](t098-ingress-observation-2026-11-07.md)
единственное наблюдаемое назначение этого upstream — loopback TCP443,
где получен отказ. На loopback TCP9433 принимает Xray. На
[изолированном стенде](t098-ingress-observation-2026-11-07.md#10-ноября-восстановление-special-проверено-с-настоящим-vlessreality-в-изоляции)
замена только номера порта восстановила настоящий VLESS/REALITY-обмен.

Ровно одна логическая правка для ревью:

```diff
 upstream kvn_xray_reality:
-  loopback TCP443
+  тот же loopback-адрес, TCP9433
```

Это описание правки, а не патч для применения: точный включённый файл,
литеральный адрес и SHA-256 должны быть сняты заново под согласованным
операторским доступом. Применение останавливается, если upstream найден
неоднозначно, назначение уже изменилось, есть другие потребители upstream
с непроверенным влиянием либо меняется что-либо ещё. Публичный bind, карта,
PROXY-протокол, default10444, пять mail SNI→10445 и приёмник8443 остаются
прежними. Настройки Xray и почты в этот пакет не входят.

## Порядок для проверки оператором

| Рубеж | Что должно быть доказано до перехода дальше |
| --- | --- |
| Допуск и исходное состояние | Назначен оператор, согласован способ изменения общего nginx и возврата, приняты исходные DNS/TLS и безопасные ответы пяти mail имён. Необходимую опись Stalwart получить штатным способом. Не править DNS, сертификаты или почту в этом пакете. |
| Входы под блокировкой | Удерживается тот же файл блокировки, что использует `cd-remote.sh` из канонической серверной копии: сверены устройство и inode. Сверены окно обслуживания, занятость блокировки, текущий include, связи upstream, SHA, владелец, режим, слушатели, PID/время старта master и workers. `nginx -T` не выдаётся за дамп активного поколения. |
| Исключение параллельной записи | По исходникам выпуска оба установщика nginx для billing и summary share самостоятельно вызывают reload и не берут общий deploy lock. Оператор отдельно подтверждает, что установщики и другие процессы записи/reload, включая применимые hooks, не будут запущены в этом окне. Одного `flock` для этого недостаточно. |
| Предпросмотр и применение | Сохранена закрытая копия точного файла с метаданными. До записи проверены ожидаемый и обратный diff и отсутствие дрейфа. Только после отдельного допуска, под той же блокировкой: записать согласованный include, сверить его SHA-256 и фактический diff, затем выполнить `nginx -t` с **изменённым рабочим** набором include. Подать один штатный reload только после успеха всех этих проверок. При ошибке до reload вернуть прежние байты и метаданные, сверить исходный SHA и не подавать сигнал nginx. |
| Приёмка загруженного поколения | Тот же master, наблюдаемое новое поколение workers, нет ошибок активации в журнале. Новое независимое соединение проходит настоящий VLESS/REALITY через публичный TCP443, прямой 9433 остаётся рабочим. rec, default, пять mail SNI и 8443 проходят контрольные сравнения по сценарию 8. До окончания наблюдения старые процессы не останавливать принудительно; при оставшихся workers после 15 минут этап не закрывать. |
| Возврат | При провале применения или любой обязательной проверки остановить переход. Под тем же lock вернуть точные прежние байты и метаданные, выполнить `nginx -t`, штатный reload и повторить проверку поколения и исходных маршрутов. Этот возврат восстанавливает и исходный отказ special. Если позже не пройдёт уже A–D, его возврат должен вернуть **исправленное** исходное состояние special, а не старый отказ. |

Источники: [правила выпуска](../agent-guidance/development-process.md#blocked-state-next-actions),
[сценарий 8](../../specs/273-paid-traffic-analytics/quickstart.md),
[разбор опубликованных операторских средств](../../specs/273-paid-traffic-analytics/validation/t098-published-operator-path-review-20261103.md).
Хранить только контрольные суммы и результаты в закрытой квитанции; не переносить
в Git полный вывод nginx, содержимое сертификатных ключей или профили клиентов.

Локальная проверка показала, что `git rev-parse --git-path
twobrain-rec-deploy.lock` в двух рабочих копиях одного Git-репозитория
возвращает два разных файла. Совпадение имени или общего Git-каталога
не гарантирует общей блокировки. На рабочем сервере идентичность файла
блокировки ещё не проверялась.

## Почему одного успешного reload недостаточно

Изолированный nginx 1.28.3, контейнер без сети и опубликованных портов.
Новая конфигурация прошла `nginx -t`. Затем второй учебный процесс занял
новый порт. `nginx -s reload` завершился с кодом 0, однако master записал
`still could not bind()`; PID рабочего процесса не изменился, старый маршрут
продолжил отвечать старым содержимым. Когда учебный порт освободили, reload
создал новый worker и появились оба ожидаемых ответа. При обратном переходе
создано ещё одно поколение, старый ответ вернулся, новый порт закрылся.

Проверены отрицательный случай, успешное применение и возврат; контейнер
удалён. Квитанция и сценарий вне Git:
`.dev/growth/t098-nginx-generation-20261110.{json,py}`. На рабочий сервер
не заходили. Эта проверка не определяет фактическое поколение рабочего nginx,
не подтверждает рабочую почту и не заменяет полную приёмку A–D.
