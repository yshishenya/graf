# T098 — изолированная проверка этапа D

Этап D меняет только доверенный адрес непосредственного посредника для
Uvicorn в `rec-api`. Он выполняется после принятия границы nginx на этапе C.
Здесь проверены форма пересоздания и возврат; рабочего допуска нет.

## Что подтвердили

Выпуск `v2026.11.10.4`, исходник
`a50cf9748cab05bff7eb5ce5a0696da18c64ade6`. Compose 5.3.0 прочитал
точный `infra/docker-compose.yml` этого выпуска (SHA-256
`610bc756230f2762f20c5a59c6887e2b9496d06a69256a8cbd5b5e6fb83445d6`)
и опубликованный пример окружения. С профилем `operations` итоговая схема
содержала 11 служб. При изменении учебного значения в отдельном файле
итоговый JSON изменился ровно в одном поле:
`services.rec-api.environment.FORWARDED_ALLOW_IPS`.

При этом уже заданная переменная оболочки имела приоритет над файлом даже
при пустом значении. В исходнике приложения пустое значение не проходит
проверку точных IP. Поэтому смотреть только на изменённый файл недостаточно.
`validate-production-config.sh` при работающем контейнере вызывает
`Settings()` внутри старого `rec-api`, что тоже не проверяет будущую среду.

В отдельном проекте Docker Compose, без опубликованных портов и с двумя
внутренними сетями, использовали учебные контейнеры `rec-api` и его
зависимость. Публичный `release-images.py validate-override` принял файл
с точным локальным ID образа и `pull_policy: never`. Рабочий
`current-override` и установленный образ ГРАФ не читались.

| Проверка | Результат |
| --- | --- |
| Предпросмотр | Постороннее значение из оболочки и дрейф другого параметра выпуска отличились от разрешённого изменения и были остановлены сравнением. После записи файла старый контейнер всё ещё показывал прежнее значение. |
| Применение | Вызов только для `rec-api` с `--no-deps --no-build --pull never --force-recreate --wait` создал новый исправный контейнер с тем же ID образа. Изменилось ровно одно значение среды. Команда, параметры запуска, монтирования, порты и набор двух сетей совпали; ID и время старта соседней службы не изменились. |
| Штатный возврат | Восстановили прежнее значение и итоговую схему, пересоздали только `rec-api` тем же образом. Он прошёл проверку состояния, соседняя служба не перезапускалась. |
| Отказ проверки состояния | `up --wait` вернул ошибку и оставил новый контейнер в состоянии `unhealthy`. Автоматического возврата не произошло. Явный возврат прежнего окружения и пересоздание тем же образом восстановили исправность; соседняя служба сохранилась. |

Учебный проект и обе сети удалены. Квитанция и два сценария хранятся вне Git:
`.dev/growth/t098-stage-d-20261110.json`,
`.dev/growth/t098-stage-d-render-20261110.py`,
`.dev/growth/t098-stage-d-compose-20261110.py`.

## Что требуется для рабочего этапа

Под тем же серверным lock сохранить точные прежние байты и метаданные
закрытого файла окружения, получить и проверить **рабочий** `current-override`,
сверить фактическое окружение и параметры старого контейнера с ожидаемой схемой.
До пересоздания требуется подтвердить, что меняется только нужное значение,
а оно соответствует непосредственному посреднику, наблюдаемому после этапа C.
Сравнение выполняется внутри закрытого процесса; наружу идут только результаты,
без полного Compose, среды или адреса. Если сравнение не совпало, запуск не делать.

После пересоздания проверить именно новый процесс, наблюдаемый адрес
посредника, прохождение запроса к API, неизменность образа и остальных служб.
При ошибке `--wait` не считать возврат состоявшимся: восстановить прежнее
окружение и снова проверить новый контейнер, запущенный на том же образе.
Учебный сценарий не доказывает правильный рабочий адрес или доверие к нему.
Сохраняются [ворота восстановления специального маршрута](t098-special-operator-preflight-2026-11-10.md)
и [полная приёмка сценария 8](../../specs/273-paid-traffic-analytics/quickstart.md).
На рабочий сервер не заходили, настройки аналитики и службы не меняли.
