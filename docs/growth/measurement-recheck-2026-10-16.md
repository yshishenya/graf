## Хранение: подготовлена оценка, операции не выполнялись

Ограниченные SELECT через существующий операторский путь подтвердили: `events` и `writable_events` — Distributed, физическое хранение — `posthog.sharded_events` с ReplicatedReplacingMergeTree. TTL не определён. Одна настроенная реплика активна, read-only и expired session не обнаружены. Это снимок одной проверенной установки, не доказательство полноты всей инфраструктуры.

В общей таблице 218 событий из двух проектов, из них 46 относятся к основному проекту. Общий счётчик нельзя считать трафиком ГРАФ. На момент проверки строк старше 365 дней — 0 во всех проектах. Это историческая оценка прежнего варианта 365 дней; владелец затем отменил этот срок. Она не служит инструкцией на очистку. Влияние на второй проект не согласовано.

Выполнен только существующий `apply-posthog-event-ttl.sh --dry-run --days 365`. Он напечатал `ALTER TABLE sharded_events MODIFY TTL toDateTime(timestamp) + toIntervalDay(365)`, без подключения к серверу и без изменения данных. Проверенный клиент сервера использует базу `default`, тогда как `sharded_events` существует в `posthog`. Скрипт не передаёт `--database`, его запрос статуса также использует `currentDatabase()`. Поэтому полученный dry-run нельзя применять к этой установке без явного выбора базы и повторной проверки охвата. Команда с полным именем `posthog.sharded_events` также изменила бы срок для обоих проектов; она здесь не выполнялась.

Поиск `retention` в текущих настройках PostHog показал только `Session replay → Data retention`. Это не настройка срока хранения событий. Значение 365 дней через этот элемент не выставлялось.

Воспроизводимые запросы: [measurement-recheck-2026-10-16.sql](measurement-recheck-2026-10-16.sql). Они ограничены временем, объёмом и памятью, имеют `readonly=2`, возвращают только числа и метаданные. Содержимое событий, IP, псевдонимы, имена и ключи не выгружались.

## Следующий ограниченный шаг

1. Решение владельца от 16.10.2026 отменяет прежнюю рекомендацию включить `Discard client IP data`: IP сохраняем для повторного использования в продуктовой аналитике. Выключенное удаление IP само по себе не доказывает корректный IP посетителя в новом server-mediated маршруте.
2. Владелец отменил срок 365 дней: автоматическое удаление по возрасту не требуется; удаление — по отдельному решению или обязательному требованию. TTL/purge не выполнять. Проверить фактический охват таблиц/проектов/реплик и иных фоновых удалений до утверждения соответствия новому режиму.
3. Использовать уже подготовленные `minimal-funnel-queries.sql` F096 для пяти вех и контроля дублей после изолированной проверки доставки. Панель должна явно показывать охват согласившихся пользователей и отсутствие/задержку данных; шаблонные просмотры и сессии не заменяют полезный результат. Сигнал D7 и оплаченный результат остаются отдельными задачами.
4. Принять F289 через штатные условия слияния и выпуска; затем сверить четыре новых поисковых входа с серверными агрегатами. Учёт запросов можно развивать отдельно от выключенной персональной воронки.
