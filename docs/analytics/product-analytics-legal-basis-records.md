# Записи о правовом основании и отзывах

Этот документ для оператора: как записать правовое основание передачи данных
в рекламную платформу, как записать отпадение основания уровня измерения и как
записать отзыв согласия. Без этих записей передача запрещена по умолчанию.

Документ описывает два файла. Оба лежат вне репозитория, содержат только
метаданные и не попадают в git.

## Почему это отдельные файлы, а не флаг

Флаг конфигурации не является правовым основанием. Это прямо записано в
FR-028: техническая настройка не может выдать разрешение, она может только
задержать его. Поэтому основание — это запись с ролью подтвердившего, датой,
областью действия и ссылкой на доказательство. Пока записи нет, передача
запрещена, и это правильное состояние, а не ошибка настройки.

## Файл 1. Основание передачи в рекламную платформу

**Переменная окружения:** `GRAF_PRODUCT_ANALYTICS_ADVERTISING_TRANSFER_STATE_FILE`
**Если не задана:** берется каталог из
`GRAF_PRODUCT_ANALYTICS_ADVERTISING_TRANSFER_STATE_DIR`.

**Заголовок файла, первая содержательная строка:**

```
advertising_transfer_state_version=1
```

Версия обязательна. Файл с другой версией считается нечитаемым, и тогда не
действует ни одно основание.

**Запись об основании:**

```
basis recipient=yandex_metrica purpose=yandex_offline_conversions state=confirmed basis=consent confirmed_by=<роль> confirmed_at=<дата> scope=<область> evidence_ref=<токен>
```

Поля:

| Поле | Что принимается | Что будет, если не так |
|---|---|---|
| `recipient` | только `yandex_metrica` | `recipient_unknown`, основание не действует |
| `purpose` | `yandex_offline_conversions` или `telecom_network_advertising` | `purpose_unknown` |
| `state` | только `confirmed` | `state_not_confirmed` |
| `basis` | только `consent` | `basis_kind_unsupported` |
| `confirmed_by` | роль вида `юзернейм_строчными`, 3-40 знаков, начинается с буквы | `confirmed_by_is_not_a_role_identifier`, персональные имена и адреса не принимаются |
| `confirmed_at` | дата `ГГГГ-ММ-ДД`, не в будущем | `confirmed_at_is_invalid` или `confirmed_at_is_in_the_future` |
| `scope` | для офлайн-конверсий `offline_conversion_transfer_basis`; для рекламы по сетям электросвязи своя область | `scope_is_invalid`, либо `basis_out_of_scope`, если область не та |
| `evidence_ref` | токен из строчных букв, цифр и подчеркиваний | запись отбрасывается |

Ссылка на доказательство — это токен, а не сам документ. Сам документ
хранится там, где положено, а в файле остается только метка, по которой его
найдут.

**Запись об отзыве получателем:**

```
revocation recipient=yandex_metrica purposes=yandex_offline_conversions revoked_at=<дата> delivery_state=confirmed|pending|failed method=<причина> delivered_at=<дата> evidence_ref=<токен>
```

После отзыва любая дальнейшая передача этому получателю запрещена, в том числе
пока доставка отзыва в состоянии `pending` или `failed`. Если написано
`delivery_state=confirmed`, но момента доставки нет, состояние понижается до
`pending`: подтверждение без момента подтверждением не считается.

**Запись об отказе повторной передачи:**

```
revocation_refusal recipient=<получатель> purpose=<цель> ...
```

Такая строка фиксирует, что повторная передача уже отозванных данных была
отклонена по непрозрачной ссылке передачи.

## Файл 2. Отпадение основания уровня измерения

**Переменная окружения:** `GRAF_PRODUCT_ANALYTICS_LEGAL_BASIS_STATE_FILE`
**Если не задана:** каталог
`GRAF_PRODUCT_ANALYTICS_LEGAL_BASIS_STATE_DIR`, а если и он не задан —
`/var/lib/graf-product-analytics-legal-basis`, файл `legal-basis-withdrawals`.

**Заголовок файла:**

```
legal_basis_state_version=1
```

Строки, начинающиеся с `#`, игнорируются — ими можно писать пояснения.

**Запись об отпадении основания:**

```
basis_withdrawal level=<уровень> state=withdrawn withdrawn_at=<дата> reason=<причина> evidence_ref=<токен>
```

| Поле | Что принимается |
|---|---|
| `level` | `anonymous_aggregate`, `attribution_profiles` или `provider_analytics` |
| `state` | только `withdrawn` |
| `withdrawn_at` | дата `ГГГГ-ММ-ДД`, не в будущем |
| `reason` | токен вида `причина_строчными`, 3-80 знаков |
| `evidence_ref` | необязательный токен |

Запись, у которой уровень неизвестен, состояние не `withdrawn`, дата не
разбирается или стоит в будущем, просто не читается. Молчаливое игнорирование
здесь выбрано намеренно: неверно понятая запись не должна останавливать или
разрешать обработку.

**Что происходит после записи.** Обработка уровня запрещается, в отчете
готовности появляется причина `legal_basis_withdrawn`, а разрешение на платный
запуск перестает выдаваться. Срок исполнения удаления или обезличивания
задаётся отдельно применимым обязательным требованием либо отдельным решением:
основание, категории/охват, ответственный и крайний срок фиксируются в случае.
Режим `until_decision` не отсрочивает исполнение. Случай без крайнего срока не
закрывается. Для своих строк проверяется фактический результат; для провайдера
запрос и подтверждённое исполнение учитываются отдельно, пределы контроля
указываются явно. Отправленный запрос не называется подтверждённым удалением.

## Согласие посетителя на рекламную атрибуцию

Отдельно от файлов выше решение посетителя читается из категорий согласия
события. Разрешением считается только явное присутствие категории
`advertising_attribution`. Отсутствие решения, испорченный список или отзыв —
это запрет, а не разрешение.

Для рекламы по сетям электросвязи этого недостаточно: нужно отдельное
предварительное согласие абонента со своей областью. Согласие на измерение его
не заменяет, и попытка подставить одно вместо другого отклоняется как
`subscriber_prior_consent_not_separate`.

## Что проверить после правки файлов

1. Записи читаются: состояние видно в отчете готовности, а не в догадках.
2. Основание действует только в своей области: общая запись не разрешает
   передачу в рекламную платформу.
3. Отзыв останавливает передачу сразу, а не после подтверждения доставки.
4. В файлах нет персональных данных: только роли, даты, токены и причины.

## Категория `network_access_metadata` — целевой реестр F273 T110

Это дополнение требований, не запись действующего основания. Для существующей
БД GRAF (`rec-postgres`, `twobrain_rec`, `public.network_access_metadata`)
регистрируются:

| Поле | Требование |
| --- | --- |
| `category` | ровно `network_access_metadata`, отдельно от уровней 1–3 |
| `storage` / `retention_mode` | `graf_postgres` / `until_decision` |
| `fields` | только id, observed_at, client_ip, surface, traffic_class, address_source, basis_ref; типы/значения — F273 data-model |
| `purposes` | безопасность, исключение своего/служебного трафика, качество измерения; без восстановления связи с человеком/аккаунтом/оплатой |
| `basis_ref` / `basis` | непрозрачная ссылка и конкретное применимое основание в закрытой записи; owner_instruction не заменяет согласие посетителя |
| `confirmed_by_role`, `confirmed_at`, `evidence_ref` | роль, дата, проверяемое подтверждение; не выдумывать задним числом |
| `disclosure_version`, `published_match` | принятая редакция публичного раскрытия и проверка совпадения опубликованного текста |
| `state` | сейчас `pending`; `active` только после проверок, `revoked` прекращает запись до следующей вставки |
| `access` / `audit` | приложение INSERT-only; защищённый операторский read/delete с обязательным metadata-only аудитом до операции; недоступный аудит запрещает её |
| `deletion` | case_ref, основание/решение, закрытый точный selector, owner, deadline, результат/rows_affected; общий IP не доказывает личность |
| `backups` | локальный контур БД GRAF, полный состав и права проверены; повторное применение принятых удалений после restore до доступа |

Пока основание/раскрытие/права/аудит/копии не приняты, writer выключен. Unknown,
отсутствующие поля и недоступная запись закрывают запись, не публичную страницу.
Никакие реальные IP/идентификаторы/селекторы/основания с личными данными в Git
не добавляются. Это не подтверждение, что конфигурация, grants или таблица уже
применены; T110/T111 остаются открытыми.
