# Определения отчётов: GRAF — платный трафик

Feature: `273-paid-traffic-analytics`, задачи T055–T061.

Этот каталог содержит **машиночитаемые определения отчётов**: файлы, по которым
оператор собирает дашборды PostHog и отчёты Яндекс.Метрики. Здесь нет картинок,
скриншотов, ключей, идентификатора счётчика и персональных данных.

Человекочитаемое описание набора, вопросы владельца, оговорки и порядок сверки —
в `docs/analytics/product-analytics-reports.md`.

## Состав

| Файл | Что это |
| --- | --- |
| `catalog.json` | Каталог отчётов: назначение, источник данных, разрезы, владелец, свежесть, обязательные оговорки, что означает пустое значение, правила стоимости результата и процедура сверки кампаний |
| `posthog/dashboards.json` | 14 определений дашбордов PostHog: плитки с запросами, обязательные плитки свежести, полноты и оговорок |
| `yandex/reports.json` | 10 определений отчётов Яндекс.Метрики по тем же разрезам: запрос Reporting API, разрез, цели, оговорки, пустое значение |
| `consistency/sample-campaign-breakdown.json` | Подготовленный набор для сверки разбивки по кампаниям между Метрикой и продуктовой аналитикой (SC-008) с ожидаемым результатом и наборами для отрицательных проверок |
| `runtime-status.json` | Проверенное состояние применения: серверная поверхность R07/R11 уже работает, остальные определения требуют действия оператора; статусы T092/T094/T095 сопровождаются metadata-only receipt-блоком |
| `operator-evidence.schema.json` | Машиночитаемая схема receipts для дашбордов, отката и оповещений; она не допускает live IDs, секреты и status=applied без receipt |

Число отчётов: **14** в PostHog и **10** в Метрике, то есть не меньше восьми,
как требуют спецификации 096 и 093
(`specs/096-product-analytics-provider-rollout/contracts/posthog-provider-runbook.md`,
`specs/096-product-analytics-provider-rollout/contracts/yandex-provider-runbook.md`).
Соответствие минимумам 096 перечислено в `catalog.json` в разделе
`provider_minimum_coverage`.

## Как применять

Применение выполняет **оператор**: подключение к рабочему PostHog и к счётчику
Метрики из репозитория не делается.

Порядок для PostHog:

1. Войти в рабочее пространство аналитики с включённым вторым фактором.
2. Создать дашборд с именем и описанием из `dashboards[].name` и
   `dashboards[].description`.
3. Создать плитки дашборда: тип берётся из `tiles[].insight`, тело запроса — из
   `tiles[].query`. Текстовые плитки ролей `caveats` и `completeness`
   создаются как текстовые карточки с готовым текстом из `tiles[].body`.
4. Убедиться, что на дашборде есть все четыре обязательные роли плиток:
   `primary`, `freshness`, `completeness`, `caveats`.
5. Записать результат: имя дашборда, владелец, состояние, дата.

Порядок для Метрики:

1. Войти в счётчик с включённым вторым фактором.
2. Собрать отчёт в интерфейсе по полю `ui_equivalent` либо выполнить запрос из
   `reporting_api`.
3. Подставить рабочие значения вместо меток `<counter_id>` и
   `<goal_id:имя_цели>`. Рабочие значения в репозиторий не попадают.
4. Сверить имена измерений и метрик с документацией Метрики и тарифом счётчика:
   набор зависит от подключённых возможностей, смысл отчёта при этом не
   меняется.
5. Записать имена сохранённых отчётов, владельца, состояние и дату.

## Что требует оператора

- Применение определений к рабочему PostHog: 14 дашбордов.
- Настройка 10 отчётов Метрики и запись их имён и статусов.
- Ежедневная загрузка выгрузки расхода рекламного кабинета: без неё стоимость
  результата не считается.
- Выгрузка обезличенного агрегата уровня 1 на отчётную поверхность, если
  знаменатель «все визиты» нужен прямо в дашборде. Сегодня уровень 1 живёт в
  PostgreSQL и на поверхность PostHog не выгружается: это отмечено в каждом
  дашборде.
- Первая сверка разбивки по кампаниям между Метрикой и продуктовой аналитикой
  по набору `consistency/sample-campaign-breakdown.json`.
- Подтверждение фильтра внутреннего и служебного трафика до бизнес-выводов по
  абсолютным значениям.

## Сегодняшнее честное состояние

Фактически проверенное состояние зафиксировано в `runtime-status.json`.

- **Серверная отчётная поверхность уже применяет часть определения.**
  `GET /api/v1/product-analytics/reports` возвращает R07 (стоимость результата)
  и R11 (покрытие согласием), их владельцев, источники, оговорки и явные причины
  блокировки. Отсутствующий источник возвращается как «нет данных», а не как 0.
- **Доставка событий в PostHog выключена.** Пустой дашборд сейчас означает
  выключенную доставку, а не отсутствие интереса. Это прямо написано в плитке
  оговорок каждого дашборда и в блоке `data_availability`.
- **Остальные определения не применены к внешним провайдерам.** R01–R06,
  R08–R10 и R12–R14 остаются машиночитаемыми определениями: их применение
  требует оператора, доступа к рабочему PostHog/Метрике и проверки формы запросов.
- **Обезличенный агрегат уровня 1 не выгружается на отчётную поверхность
  PostHog.** Показатели «все визиты» и доля согласия живут в продуктовом
  контуре; серверная поверхность умеет вернуть R11 по своему API.
- **Определения провайдеров не проверены на живом сервисе.** Поля Insights API
  PostHog и имена измерений Reporting API Метрики проверяются оператором при
  применении. Смысл отчётов от этого не меняется.

## Проверки

Структура определений и правила проверяются тестами:

```sh
cd apps/server && PYTHONPATH=src uv run --extra dev pytest -q \
  tests/contract/test_product_analytics_report_catalog.py \
  tests/contract/test_product_analytics_report_dashboards.py \
  tests/contract/test_product_analytics_report_runtime_status.py \
  tests/unit/test_product_analytics_report_cost_per_result.py \
  tests/unit/test_product_analytics_report_gap_not_zero.py \
  tests/unit/test_product_analytics_report_campaign_consistency.py
```

Проверки читают файлы этого каталога и следят за тем, чтобы у каждого отчёта
оставались владелец, оговорки, правило пустого значения и обе поверхности там,
где они объявлены.

## Запрещено в этих файлах

- ключи, токены, рабочий идентификатор счётчика, идентификаторы целей;
- выгрузки событий, строки офлайн-конверсий, номера кликов;
- скриншоты с данными посетителей;
- персональные данные и содержимое встреч.
