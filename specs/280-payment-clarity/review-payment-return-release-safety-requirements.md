Безопасная минимальная коррекция задана достаточно точно в [T045](tasks.md:254) и [уточнении плана](plan.md:228):

- Существующее разрешение для `invoice.status == "pending"` сохраняется вместе со всеми ограничениями соответствующей ветки.
- Дополнительное разрешение для `invoice.status == "manual_resolution"` действует **только** при существующей связанной операции, для которой `_initial_checkout_can_continue(operation)` возвращает `True`: `kind == "initial_checkout"`, `purchase_schema != 2`, `provider_id is None`, состояние из `scheduled / manual_resolution / unknown`, заданный и ещё действующий срок прежнего ключа.
- Проверки владельца, пользователя операции, пространства, действующей сессии, CSRF и доступности оплаты сохраняются. POST проверяет актуальные записи под существующими блокировками; терминальные и несовместимые пары отклоняются.
- GET и POST используют одинаковые условия совместимости. GET остаётся чтением.
- Вызов провайдера повторяет сохранённый запрос с **тем же** `operation.idempotency_key`, суммой, валютой, согласиями и параметрами чека. Новый ключ, новая сумма, новый invoice или operation недопустимы.

**Нельзя просто заменить проверку на `invoice.status in {"pending", "manual_resolution"}`.** Это расширит допуск для операций с `provider_id`, схемы 2 и других типов покупки. Исключение должно быть связано со всем предикатом восстановления старого первоначального оформления.

Исходный дефект подтверждён: [POST guard](../../apps/server/src/twobrain_rec_server/cabinet/web_routes/billing.py:2358) отклоняет `manual_resolution` до проверки допустимости восстановления. При этом [существующий предикат](../../apps/server/src/twobrain_rec_server/cabinet/web_routes/billing.py:531) разрешает именно такую старую операцию. [Тест владельца](../../apps/server/tests/integration/test_web_owner_session_context.py:2784) требует прежний ключ, один вызов провайдера и сохранение единственного invoice/operation. Его финансовые ожидания нужно сохранить.

По **FR-035** это допустимое восстановление прежнего идемпотентного запроса — повторение с той же идентичностью, которое должно возвращать тот же платёж. Оно не разрешает новую покупку. Неизвестный результат остаётся неизвестным; ответ continue не заменяет авторитетное подтверждение оплаты и предоставление доступа.

По **FR-032** есть конкретное препятствие для окончательного PASS. У допустимой старой операции без `provider_id` и схемы 2 текущий `can_refresh_payment` будет ложным. После расширения GET eligibility шаблон попадёт в [ветку продолжения](../../apps/server/src/twobrain_rec_server/cabinet/templates/cabinet/pages/billing_operation_status_content.html:62), где «Продолжить оплату» имеет класс `primary`; пояснение также предлагает продолжение. Это не соответствует требованию о вторичности продолжения и приоритете проверки. При реализации нужно явно проверить и обеспечить FR-032 для этой ветки. Нельзя ради этого разрешать refresh, создающий новый платёж, или показывать неподтверждённое «Оплачено».

Для закрытия T045 необходимы следующие отрицательные проверки через настоящий маршрут и PostgreSQL, с подменённым провайдером:

| Сценарий | Обязательный результат |
|---|---|
| `invoice.manual_resolution` при `purchase_schema == 2`, заданном `provider_id` либо другом `kind` | Нет вызова создания платежа и перехода к провайдеру; GET не предлагает continue |
| Истёкший или отсутствующий срок прежнего ключа | Исключение восстановления не действует; новый ключ не создаётся |
| Терминальный invoice при допустимой старой операции; терминальная operation при `pending` или `manual_resolution` invoice | Нет восстановления, перехода к провайдеру и возврата состояний в `scheduled/pending` |
| `succeeded`, `succeeded_refused`, `succeeded_projected`, `canceled`, `failed`; `reconciliation_gap` и иные состояния вне разрешённого набора | Пара не получает допуск восстановления, даже с сохранённой confirmation URL |
| `invoice.unknown` или иной статус вне `pending/manual_resolution`; отсутствующая, чужая либо несвязанная operation | Нет допуска через новое исключение |
| Чужой `billing_actor_user_id`, другой tenant, пользователь без права управления, недействующая сессия, отсутствующий/неверный CSRF, отключённая оплата | Существующая защита отклоняет запрос до провайдера |
| Подмена суммы, валюты, согласий или параметров покупки через POST/query | Передаётся только исходный сохранённый запрос; противоречащий invoice снимок не отправляется провайдеру |
| Устаревшая форма после завершения платежа; повтор continue после успешного привязывания `provider_id` | Нет нового вызова создания платежа; завершённый платёж не открывается у провайдера |
| GET status/return и поддельные `result`, `reason`, `creation_rejected` в query | Нет вызовов провайдера, финансовых изменений или ложного успеха |

Для отклонённых пар недостаточно проверить `303` и количество строк: нужны **нулевые вызовы провайдера, локальный адрес возврата, неизменные ключ/сумма/согласия и отсутствие новых прав доступа или изменений финансовых резервов**. Положительную проверку восстановления следует распространить на три разрешённых состояния операции и дополнить проверкой точного исходного запроса, одинаковой допустимости GET/POST и безопасного адреса подтверждения.

Нужно сохранить все проверки числа запросов, неизменности GET, отсутствия новой оплаты, резервов бюджета и промокода, безопасных метаданных и достоверности отказа.
