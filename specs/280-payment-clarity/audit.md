заблокированные действия macOS, потерю контекста продления и неверный текст о

обработчика/условия. Она не означает выполненную проверку установленного

### Входы и границы переходов

- `/settings/billing` и `/account/billing` перенаправляют в `/billing`
  (routes:1191–1200). Меню аккаунта: `components/account_navigation.html:8`;
  категория настроек: `cabinet/view_models.py:1692,1704`.
- `/billing/usage` при лимите ведет в `/billing`, при заполненном архиве —
  в `/billing/storage`, встречи или загрузку без аудиоархива. Нельзя показывать
  последний вариант при исчерпанной обработке.
- `public/templates/public/landing.html:270–307` показывает полную цену
  периода, по умолчанию год, и ведет в `/download`; выбор периода здесь не
  переносится в оформление. Это вход знакомства/установки, не готовая оплата.
- `/offer` — документ условий; его содержимое и обязательные раскрытия не
  заменяются кратким экраном покупки. Версия оферты остается частью записи.
- `billing/notifications.py:270–336`: trial, деньги, продление, место, чек,
  приглашения. `entitlements.py:415–428` направляет после success в `/billing`,
  после регистрации чека — в конкретный invoice. Тексты восстановления должны
  соответствовать реальным возможностям страницы назначения.
- В macOS используются те же шаблоны и защищенная навигация. ЮKassa и
  последующее банковское подтверждение разрешены только в существующей цепочке
  оплаты. `DesktopCabinetBillingHandoff.swift` и `/billing/handoff` создают
  обычный браузерный вход; конечная страница — `/billing` (routes:197–349).
- `/billing/checkout/return` ведет к статусу безопасного номера счета либо
  показывает returned в обзоре (routes:3892–3898). Возврат не подтверждает деньги.
- Управление доступно личному владельцу и текущему плательщику согласно
  `_billing_role`/`_can_manage_billing` (routes:1015–1051). Корпоративный owner,
  участник и личный owner с другим billing_owner — разные случаи.

## Предлагаемые поля представления для согласования реализации

Это контракт координации с владельцем шаблонов, а не разрешение менять данные
или денежные правила. Названия можно уточнить до реализации; значения берутся
из существующих серверных источников, не рассчитываются в JavaScript.

| Поле / место | Смысл и ограничение |
| --- | --- |
| `checkout_cycle`, `manual_checkout_url`, `retry_payment_url` | Сохраненный допустимый month/year; retry по исходному invoice, manual по текущей подписке. Явный выбор приоритетен. |
| `checkout_status_url` | Адрес конкретного блокирующего счета вместо общей истории; только после проверки пространства и прав. |
| `receipt_contact_ready`, `receipt_contact_action_url`, `receipt_contact_message` | До подтверждения отличить недостающий контакт от ошибки провайдера. Ссылка только на существующий разрешенный account flow; возвращаемое намерение содержит безопасные параметры, не код/контакт/токен. |
| `invoice.status_url`, `invoice.status_action_label` | История и detail ведут к своей операции; на success не показывается ненужное «продолжить». Не выдавать права текущему owner на чужие платежные данные. |
| `service_status_title`, `service_status_message`, `service_status_kind` | Различить подтверждение денег и предоставление услуги, включая succeeded_refused, elapsed/partial и смену владельца; неизвестный reason нейтрален, внутренний detail не печатается. |
| `renewal_notice`, `renewal_action_url`, `renewal_action_label` | method/contact required, price_changed, pending/unknown, исчерпанные попытки; не обещать штатное списание при блокере. |
| `return_to_work_url` | `/desktop/meetings` для embedded, `/meetings` для браузера; безопасное действие после подтвержденной услуги. |
| `purchase.has_discount`, `checkout_has_discount` | Показать скидку только при ненулевой разнице, из исходных integer money values; строки валюты не разбирать. |
| `purchase_error_action_url`, `purchase_error_action_label` | Ошибка возвращает к подходящему следующему шагу. Пересчет не повторяет списание и не переносит старое согласие. |

Уже есть и должны использоваться: `checkout_quote_id`, `checkout_preview`,
`checkout_period_label`, `checkout_next_attempt_label`, `purchase.purpose`,
`deferred`, `recurring_allowed`, `method_label`, `current_capacity_label`,
`timeline`, `next_label`, `billing_enabled`, роли и `can_continue_payment` /
`can_refresh_payment`. Не создавать параллельную машину состояния оплаты.

## Матрица обязательной повторной проверки

1. Free/Trial → month/year → checkout → подтвержденный результат → встречи;
   отдельно скидка/без скидки, согласия пустые, полная следующая цена на виду.
2. Annual/month действующий клиент → ручная/досрочная оплата, renewal on/off;
   сохранены период, остаток, намерение и разрешение на будущие списания.
3. Storage 5/10/15/500 ГБ, upgrade/deferred/cancel selection, несколько
   оплаченных объемов, бонусный период; сразу видимы важные изменения во времени.
4. Pending/unknown/processing → та же операция из checkout/history/invoice;
   refresh/continue не создают новую оплату. Back, две вкладки, повторный вход.
5. Terminal failed/canceled → повтор с исходным периодом; quote/offer/price
   changed → новый расчет и новое согласие; неверный код можно исправить.
6. Нет verified receipt contact/карты, method/contact required,
   price_changed, исчерпанные попытки, недоступная оплата → конкретный выход.
7. Succeeded/succeeded_refused, owner_changed/workspace_scope_invalid,
   storage_period_elapsed/частичный/полный gap, поздний ответ → правдивые деньги
   и доступ, без «платеж не найден», ложного полного отказа или ложного успеха.
8. Отмена/возобновление: paid-through не теряется, отправленный платеж продолжает
   сверяться, новое регулярное согласие явно; отказ и помощь легко находятся.
9. Браузер и macOS: реальные формы/POST; 320/360/768/1280 CSS px, light/dark,
   клавиатура, 200%, без JS для основных действий; суммы/согласия не спрятаны.
10. Независимые рецензенты перепроверяют исправления; SC-005 с людьми и SC-006
    после выпуска остаются отдельными доказательствами. Согласие агентов не
    доказывает, что каждый человек захочет оплатить.
