## Обязательные критерии для новых доказательств

1. **Годовой вход со страницы скидок.** Создать синтетического годового подписчика; отправить действующий и отдельно неверный/ошибочного формата код через реальную `/billing/discounts/apply` без cycle. После 303, двух обновлений и GET без query выбран year, годовая сумма/будущая сумма правдивы, код доступен для исправления. Отдельно проверить месячный и отсутствующий/неизвестный цикл как fallback month. Поле cycle в форме, если появится, не должно быть единственным основанием при отсутствии его в старой форме.
2. **Две вкладки, непустой устаревший A.** В общей проверенной браузерной сессии открыть A с первым кодом, явно установить новый B в другой вкладке, затем переключить период в A без редактирования. Сохраняется действующий подписанный B, новый период и исходный expiry B; A не стирает B и не получает новый срок. Два обновления и возврат без query подтверждают это. Условия B заново проверяются сервером, а не берутся из старой суммы.
3. **Две вкладки, пустой устаревший A.** Открыть пустой A до применения B; после применения B переключить период в A без правки. Пустая старая форма не удаляет B. Отдельные явные Apply с новым кодом, действительно изменённый непустой ввод и пустой Apply/remove действуют как новая правка/удаление. Эти сценарии нельзя подменить одним тестом общей последовательности в одной вкладке.
4. **Отсутствующий/просроченный B.** При `t+299` неизменённый A сохраняет действующий B и остаток срока; при `t+300`/после срока A не возрождает старый код и получает понятное объяснение. Повреждение/перенос/смена проверенных границ не разрешают наследование. Подсказка `previous_promo_code` не предоставляет права платежа или скидки. Явное Apply после expiry — новое действие с новым сроком, а не автоматическое восстановление.
5. **Почта ещё не подтверждена.** Ошибочный ввод до 48 символов со страницы скидок приводит к checkout с открытым редактируемым полем и понятной ошибкой. Человек может исправить код, переключить период и очистить код. Нет второй hidden-копии `promo_code`, которая конкурировала бы с видимым полем; Enter сохраняет выбранный период. Денежная форма/start отсутствует, прямой start продолжает требовать подтверждённую почту и прежние согласия/права/quote. Доступность предварительной проверки не считается готовностью к оплате.
6. **Общие ограничения.** Все preview/refresh-сценарии используют выдуманные коды, нулевые operation/invoice/redemption и запрет обращений к провайдеру. Согласия остаются пустыми; реальные деньги, пользовательские коды, новые сборщики аналитики и новые зависимости не нужны. DOM приёмка включает Chromium/WebKit, 320/1280, keyboard/Enter, годовую цену и отсутствие горизонтального переполнения.

Критерии 1–5 обязательны для исправленных замечаний. Разумное разделение между HTTP/SQL и настоящими DOM сценариями допустимо, но обход отправки браузерной формы прямым вызовом helper не заменяет проверку формы. Новые результаты и независимые заключения должны называть точный код/хеши; прежний выпуск v2026.09.30.2 не доказывает исправление обновления или новых пограничных случаев.
