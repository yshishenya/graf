1. У каждого из automatic_retry, backfill_inventory, range_playback и
   normalization_cleanup отдельны prerequisites, точный source/time, оператор,
   синтетические входы, действия, ожидаемые факты, срок/условие остановки,

2. automatic_retry доказывает временный отказ и автоматическое восстановление,
   без ручного retry, который мог бы скрыть отсутствие автоматики.
3. backfill_inventory не называется read-only: существующий inventory service
   пишет и делает commit. Процедура ограничивает его выбранными синтетическими
   данными либо отдельно описывает безопасное чтение агрегатов. Пустая выборка
   не считается проверкой backfill.
4. range_playback отдельно проверяет авторизацию, ответы200/206/416,
   действительные Range bytes и браузерную перемотку на синтетическом аудио.

   принятый source и посторонние данные сохраняются. Результат охватывает

   конституции журналов Langfuse/Temporal или обязательных backups.
6. Локальные существующие retry/restart/backfill/Range/deletion tests через
   штатный PostgreSQL runner дают только isolated result. Container builds
   требуют дискового preflight; временные данные проверки очищаются адресно.
7. В evidence отдельный результат pass/fail/not-run каждого сценария с
   source, условиями, временем и безопасными агрегатами; incomplete не pass.

   доказательство цикла. Фраза «по расписанию» сама ничего не доказывает.

### Минимальный недостающий исполнитель

Достаточно **одной операторской команды с конечным сроком жизни и собственным
synthetic run**, без нового публичного API, службы и общих runtime flags.
Её точные owned paths и согласованный design ещё предстоит определить.

1. Скомпоновать существующие create/upload/seed/auth helpers; вести закрытый
   run manifest с позитивной проверкой synthetic organization/workspace/user/
   device/meeting/job/attempt ownership. Отказывать при смешанном/чужом ID,
   существующем неизвестном run и недоказанной изоляции. Для negative auth
   контрольной workspace использовать отдельную synthetic identity.
2. Для retry определить узкую точку **однократного отказа одного своего
   attempt**, которая проходит действующие lease/fencing и обычную durable
   failure запись, не ломает accepted source и сама перестаёт действовать.
   После этого только наблюдать неизменённый обычный worker/reconciler до
   due/retry/ready. Не подменять production-код на fake pipeline и не выдавать
   вызов mock worker за действительный production retry. Если архитектура не
   предоставляет такой точки без изменения runtime, сначала требуется
   отдельный design этого минимального изменения; исполнитель пока blocked.
3. Для backfill подготовить в своей workspace известный набор всех четырёх
   planned actions/не менее одной страницы с продолжением, проверить cursor,
   jobs/outcomes, blocked reasons и неизменность accepted данных. Это запись,
   а не SELECT. Общий пользовательский legacy backlog не является fixture.
4. Удержать только свой auth/session до конечного срока; выполнить настоящие
   raw GET200/206/416 через уже установленный httpx и отдать обычному
   согласованному браузеру окно для воспроизведения/перемотки. Receipt HTTP
   не заменяет browser receipt; browser не заменяет embedded GRAF Dev.
5. Для cleanup создать только свои известные unpublished/late-output
   fixtures и активный контроль, затем наблюдать обычную cleanup и отдельно
   проверить сохранность control/accepted source/canonical winner. После
   этого штатно завершить control и переиспользовать адресную финальную
   smoke cleanup с повторной DB/object/temp residue сверкой.
6. Сохранять четыре раздельных результата/причины с source/time и безопасными
   агрегатами, отдельно auth/final cleanup. При любом exception/interrupt/
   timeout выполнять адресную cleanup в finally; при неполной cleanup
   сохранять закрытую ownership связь до разрешения остатка. Полностью
   описать и проверить путь восстановления после жёсткого завершения, где
   finally не исполнялся. Нет общего restart/stop, общего удаления или
