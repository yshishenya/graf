# Feature Specification: Desktop Billing Actions

**Feature Branch**: `codex/208-desktop-billing-actions`

**Created**: 2026-08-28

**Status**: Draft

**Input**: Пользователь сообщил, что биллинг в установленном macOS-приложении по-прежнему не работает. Диагностика показала: страницы открываются, но действия форм блокируются desktop-навигацией и переводят приложение в состояние «Функция недоступна».

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Завершить действие биллинга в приложении (Priority: P1)

Владелец личного пространства может выполнять доступные ему действия биллинга в GRAF для macOS: рассчитать скидку, начать оплату, проверить или продолжить существующую операцию, управлять промокодом, пробным периодом, автопродлением и способом оплаты. Поддерживаемое действие не должно заменять кабинет экраном «Функция недоступна».

**Why this priority**: Блокировка действия делает весь платёжный путь незавершённым, даже когда страницы, каталог и YooKassa настроены правильно.

**Independent Test**: Для каждого пользовательского действия из действующего billing-интерфейса проверяется, что оно проходит desktop-навигацию. Неизвестные соседние маршруты остаются заблокированными. Для проверки не требуется создавать новый платёж.

**Acceptance Scenarios**:

1. **Given** пользователь открыл выбор тарифа в установленном GRAF, **When** он рассчитывает скидку, **Then** результат показывается в checkout и состояние «Функция недоступна» не появляется.
2. **Given** пользователь подтвердил обязательные условия checkout, **When** он начинает разрешённую тестовую оплату, **Then** GRAF продолжает существующий платёжный поток вместо блокировки маршрута.
3. **Given** пользователю доступно управление существующей подпиской или операцией, **When** он выполняет показанное интерфейсом действие, **Then** запрос обрабатывается штатным billing-потоком и возвращает понятный результат.
4. **Given** ссылка ведёт на неизвестное или неподдерживаемое действие, **When** приложение оценивает переход, **Then** переход остаётся заблокированным.

### Edge Cases

- Безопасный номер операции может меняться, но должен проходить существующую проверку допустимого сегмента пути.
- Query-параметры и fragment не должны расширять набор разрешённых действий.
- Разрешение навигации не отменяет CSRF, авторизацию, tenant-boundary, idempotency или server-side billing gates.
- Действие, которого нет в действующем серверном billing-интерфейсе, не разрешается «на будущее».
- Внешние платёжные и legal-маршруты сохраняют существующие отдельные правила.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Все действия, которые действующий billing-интерфейс показывает пользователю внутри macOS-приложения, MUST проходить desktop-навигацию без состояния «Функция недоступна».
- **FR-002**: Разрешённый набор MUST быть ограничен точным перечнем текущих billing-действий; неизвестные и вложенные соседние действия MUST оставаться заблокированными.
- **FR-003**: Динамические действия над существующей платёжной операцией MUST принимать только безопасный номер операции и только явно поддерживаемое действие.
- **FR-004**: Исправление MUST NOT менять расчёт цены, скидки, промокода, trial, подписки, способа оплаты, idempotency или правила YooKassa.
- **FR-005**: Исправление MUST NOT включать production-магазин, создавать новый платёж, менять подписку или выполнять миграцию production-базы во время проверки.
- **FR-006**: Существующие ограничения для неизвестных same-origin страниц, внешних хостов, небезопасных схем, native capture и локальных диагностик MUST сохраниться.
- **FR-007**: Регрессионная проверка MUST покрывать каждый текущий user-visible billing action и минимум по одному неизвестному sibling-маршруту для статического и динамического действия.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% текущих billing-действий, отображаемых пользователю в macOS-приложении, классифицируются как поддерживаемые.
- **SC-002**: 100% проверенных неизвестных sibling-маршрутов остаются заблокированными.
- **SC-003**: Пользователь может рассчитать скидку и дойти до штатного начала тестовой оплаты без экрана «Функция недоступна».
- **SC-004**: Проверка исправления не создаёт дополнительный платёж и не изменяет существующую подписку.

## Assumptions

- Канонический серверный billing-интерфейс и его user-visible формы являются источником текущего набора действий.
- YooKassa остаётся в test-shop; production shop не включается этой feature.
- Изменение требуется только в macOS desktop policy и её регрессионном контракте; серверные billing handlers уже существуют.
- Фактическое исправление установленного приложения потребует отдельного штатного подписанного macOS-релиза после merge.

## Out of Scope

- Новые тарифы, промокоды, способы оплаты или provider-интеграции.
- Изменение server-side billing semantics, базы данных или production-конфигурации.
- Новый платёж в рамках разработки и focused-проверки.
- Ослабление общих desktop trust boundaries.
