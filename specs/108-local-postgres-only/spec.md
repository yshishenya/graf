# Feature Specification: Локальная разработка только с PostgreSQL

**Feature Branch**: `codex/108-local-postgres-only`  
**Created**: 2026-07-17  
**Status**: Draft  
**Input**: User description: "Перейти с SQLite на локальный PostgreSQL и вычистить всё, что связано с SQLite."

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Предсказуемый локальный запуск (Priority: P1)

Разработчик поднимает изолированное локальное хранилище данных и запускает серверные проверки в среде, которая повторяет свойства рабочего хранилища продукта.

**Why this priority**: Ошибки схемы, блокировок и изоляции должны обнаруживаться до поставки, а не из-за упрощённого локального режима.

**Independent Test**: На чистом компьютере разработчик запускает задокументированный локальный сценарий, получает готовую базу данных и проходит миграции и серверные проверки без доступа к production.

**Acceptance Scenarios**:

1. **Given** чистая локальная среда разработки, **When** разработчик запускает документированный сценарий, **Then** создаётся изолированное локальное хранилище и сервер может применить все миграции.
2. **Given** локальное хранилище уже запущено, **When** разработчик повторно запускает сценарий, **Then** данные не смешиваются с production и результат остаётся предсказуемым.
3. **Given** хранилище недоступно, **When** разработчик запускает проверку, **Then** он получает понятную инструкцию по восстановлению, а не скрытый переход на другой тип хранилища.

---

### User Story 2 — Реалистичные серверные проверки (Priority: P2)

Инженер и CI выполняют серверные тесты только с теми возможностями хранилища, которые реально поддерживает продукт: ограничениями, транзакциями, блокировками и изоляцией доступа.

**Why this priority**: Один и тот же путь данных в разработке и production снижает риск скрытых дефектов миграций и разграничения доступа.

**Independent Test**: Полный серверный набор проверок проходит на выделенном локальном экземпляре, а миграции проверяются на обновление и откат без использования альтернативного встроенного хранилища.

**Acceptance Scenarios**:

1. **Given** запущено локальное изолированное хранилище, **When** запускаются серверные тесты, **Then** каждый тест использует безопасно выделенную область данных и не влияет на соседние запуски.
2. **Given** новая или существующая миграция, **When** проверяется её обновление и откат, **Then** проверка использует локальное хранилище того же семейства, что и production.

---

### User Story 3 — Отсутствие устаревшей альтернативы (Priority: P3)

Сопровождающий проекта не находит в активной конфигурации, зависимостях, исходниках, тестах и инструкциях возможность запустить сервер через SQLite.

**Why this priority**: Поддержка двух несовместимых путей удорожает изменения и маскирует production-ошибки.

**Independent Test**: Автоматическая проверка активных серверных файлов подтверждает отсутствие SQLite-зависимостей и SQLite-конфигурации; локальная документация ведёт только к поддерживаемому пути.

**Acceptance Scenarios**:

1. **Given** актуальная рабочая копия проекта, **When** выполняется серверная проверка зависимостей и конфигурации, **Then** SQLite не может быть выбран как серверное хранилище.
2. **Given** разработчик читает инструкции по локальному запуску и тестам, **When** он следует им, **Then** нигде не предлагается SQLite как допустимый вариант.

### Edge Cases

- Локальный порт занят или контейнер недоступен: сценарий сообщает безопасный способ диагностики и не подключается к неизвестной удалённой базе.
- В окружении задан адрес production-базы: тестовый путь отвергает его до запуска миграций или очистки данных.
- Миграция зависит от возможностей PostgreSQL: локальная проверка исполняет её на PostgreSQL, а не ослабляет требования для совместимости.
- Исторический changelog или evidence описывает прошлое использование SQLite: такая запись сохраняется как правдивый архив и не считается активной инструкцией или рабочим кодом.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Проект MUST предоставлять один документированный локальный путь для запуска изолированного PostgreSQL без учётных данных production.
- **FR-002**: Серверные тесты MUST использовать изолированную локальную PostgreSQL-базу и безопасно предотвращать подключение к production-адресам.
- **FR-003**: Проверки миграций MUST выполнять обновление и откат на PostgreSQL и сохранять возможность повторного запуска на чистой тестовой базе.
- **FR-004**: Активные серверные зависимости, конфигурация, фикстуры, исходники, тесты и инструкции MUST NOT содержать поддержку SQLite или предлагать её как рабочий вариант.
- **FR-005**: Локальный сценарий MUST давать понятную проверку готовности PostgreSQL и инструкции по безопасному восстановлению при сбое.
- **FR-006**: Удаление SQLite-поддержки MUST NOT менять production-данные, production-адреса, секреты или существующую production-схему.
- **FR-007**: Каноническая локальная проверка проекта MUST запускать серверные тесты через поддерживаемый PostgreSQL-путь либо явно подготавливать его перед тестами.
- **FR-008**: Исторические release/evidence-материалы MAY сохранять правдивые описания прошлой SQLite-совместимости, но MUST NOT быть действующими инструкциями для запуска или тестирования.

### Key Entities

- **Локальная база разработки**: изолированный экземпляр PostgreSQL для запуска сервера, миграций и ручной разработки.
- **Тестовая база**: краткоживущая либо отдельно именованная база внутри локального экземпляра, защищённая от production-целей.
- **Проверка готовности**: воспроизводимый сценарий, который подтверждает доступность локальной базы до серверной валидации.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На чистом локальном окружении разработчик получает готовую тестовую базу и запускает серверные проверки за один документированный сценарий без ручного редактирования исходников.
- **SC-002**: 100% серверных тестов, запускаемых канонической локальной проверкой, используют изолированную PostgreSQL-базу.
- **SC-003**: Автоматическая проверка активного серверного пути обнаруживает 0 SQLite-зависимостей, SQLite-URL и SQLite-инструкций.
- **SC-004**: Проверка миграций подтверждает обновление до текущей схемы и откат поддерживаемых ревизий на PostgreSQL без обращения к production-данным.

## Assumptions

- Локальный Docker Engine доступен для разработки; production-инфраструктура и её секреты не используются.
- Production уже работает на PostgreSQL, поэтому эта задача не меняет production-схему и не требует переноса данных.
- Устаревшие исторические артефакты сохраняются как доказательство прошлого состояния, но исключаются из проверки активного пути.
- Feature 097 остаётся отдельной незавершённой веткой; после этой миграции её миграционные проверки будут перебазированы на PostgreSQL отдельным продолжением этой фичи.

## Out of Scope

- Изменение production-базы, production-данных, секретов, ролей или сетевых адресов.
- Удаление или переписывание исторического changelog и зафиксированных evidence-артефактов ради искусственного нулевого текстового совпадения.
- Реализация незавершённых пользовательских сценариев Feature 097.
