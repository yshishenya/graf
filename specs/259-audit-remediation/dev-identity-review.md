## Воспроизведённые дефекты текущего кода

В `scripts/dev-harness.py::_repo_identity` проверены три независимых случая:

| Случай | Ожидается | Наблюдение |
| --- | --- | --- |
| Разные Git-репозитории, одинаковое имя каталога | Разные идентичности | Обе идентичности равны имени каталога `project` |
| `git rev-parse --git-common-dir` завершился ошибкой | Отказ до использования состояния | Использовано имя текущей рабочей копии |
| Git вернул относительный `.git`, процесс запущен из другого каталога | Разрешение относительно `_repo_root()` | `Path.resolve()` использовал каталог процесса |

Воспроизводимая проверка работает только с временными синтетическими каталогами
и подменёнными результатами Git. Она не читает и не меняет живое состояние:

```sh
python3 specs/259-audit-remediation/evidence/dev-identity-probe.py --checkout .
```

На указанной базе три проверяемых поля равны `false`, код возврата `1`.
Это подтверждение дефектов, а не успешная приёмка. Скрипт выводит SHA и булевы
результаты; не выводит домашний каталог, пути состояния, credentials или данные
встреч. Он предназначен для существующего helper `_repo_identity`; при изменении
его интерфейса проверку нужно явно обновить.

## Почему сохранённый патч нельзя просто перенести

Сохранённый вариант нормализует remote и получает новое имя каталога с хешем.
Read-only сравнение двух функций `state_dir()` показало:

- предложенный каталог отличается от действующего;
- действующий каталог содержит `active-manifest.json`;
- предложенный каталог не содержит `active-manifest.json`.

`state_lock(root)` создаёт `promote.lock` внутри выбранного root. Поэтому простая
смена root разделяет и состояние, и блокировки старого/нового контроллеров.
Это вывод из расположения lock и наблюдения двух разных root, а не заявление
о фактически запущенных конкурирующих live-операциях. Такие операции не запускались.

Дополнительно документы F224 расходятся: spec/plan требуют нормализацию remote,
а analysis-canonical-state.md предлагает Git common-dir как основную идентичность.
В обоих документах нет законченной процедуры перехода действующего состояния.
Старое временное исключение для каталогов не содержит конкретной даты окончания.
Автор старого patch не представлен как независимый проверяющий требований.

## Конкретный план следующего этапа

1. Восстановить исходные документы F224 в отдельной рабочей копии, связать
   T001–T008 с #6181–#6188 и пересмотреть старые отметки по новой проверке.
2. Согласовать один контракт: normalized remote для SSH/HTTPS одного GitHub
   репозитория; resolved common-dir только для явно локального репозитория;
   ошибка Git и неоднозначность идентичности заканчиваются отказом. Относительный
   common-dir всегда разрешается относительно каталога Git-команды.
3. Выбрать процедуру перехода живого состояния. До доказанного перехода новый
   контроллер должен обнаруживать прежнее активное состояние и отказывать в
   создании второго стенда. Не переносить и не удалять пользовательские данные
   через обычный `status` или неявный выбор каталога.
4. Закрепить блокировку общей установки `/Applications/GRAF Dev.app` при переходе:
   ни другой root, ни старый контроллер не должны получить независимый live доступ
   к той же установке. Проверить также `recover-schema`, restore и rollback,
   появившиеся после исходного patch.
5. Сохранить текущие защиты production paths, runtime digest, активного журнала
   схемы, подписи и разрешений приложения. Если прежнее состояние временно
   сохраняется, назвать владельца, конкретную дату и проверяемое условие удаления;
   автоматическая очистка в эту задачу не входит.
6. Выполнить review обновлённых требований инфраструктурного этапа, затем

7. После этого — минимальная реализация, отрицательные resolver tests, два
   реальных процесса на синтетических каталогах/locks, прерывание перехода и
   rollback fixtures, авторский review и governance-fast на точном PR SHA.
8. Проверку единственного GRAF Dev проводить после согласования его занятости
   и версии. При текущем наблюдении активен F260 на
   `97bac8580d3f523107a5861036bb4022e52343c6`; это не сборка аудита F259.
