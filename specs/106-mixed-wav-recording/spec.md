# Feature Specification: Чистый единый аудиопоток для записи и транскрибации

**Feature Branch**: `106-mixed-wav-recording`

**Created**: 2026-07-17

**Status**: Implemented in code; acceptance and release gates remain open

**Input**: User description: "Создать новый Spec Kit для полной перестройки записи: один синхронный WAV для MediaScribe, M4A для прослушивания, без legacy dual-track pipeline, с понятным rollback."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Получить чистый текст одной встречи (Priority: P1)

Как пользователь, я хочу после записи получить понятную транскрибацию разговора без повторов и смешения реплик, чтобы пользоваться результатом, а не исправлять последствия технической склейки дорожек.

**Why this priority**: Качество конечного текста — главная ценность записи. Две независимые расшифровки и их последующее объединение уже показали дубли и ошибочные роли.

**Independent Test**: Контрольная запись с поочерёдной речью, одновременной речью, тишиной и системным звуком создаёт один пользовательский transcript, в котором контрольные реплики не дублируются и порядок разговора сохраняется.

**Acceptance Scenarios**:

1. **Given** пользователь начал обычную запись разговора, **When** он нажимает Stop, **Then** система сохраняет одну непрерывную аудиокопию для транскрибации и показывает обычный статус обработки.
2. **Given** в разговоре есть звук собеседника, локальная речь и их наложение, **When** обработка завершается, **Then** transcript отражает один хронологический разговор без склейки двух независимых текстов.
3. **Given** в микрофон попадает тихая акустическая копия системного звука, **When** обработка завершается, **Then** система не создаёт вторую независимую расшифровку этой копии и не выдаёт её как отдельную реплику.

---

### User Story 2 - Прослушать именно записанный разговор (Priority: P1)

Как пользователь, я хочу прослушать готовую запись после встречи, чтобы проверить результат и перейти к нужному моменту разговора.

**Why this priority**: Транскрипт и воспроизведение — единый пользовательский результат; качество одного не должно ухудшать или подменять другое.

**Independent Test**: После контролируемой записи пользователь может воспроизвести готовый аудиофайл, а длительность воспроизведения согласована с длительностью аудиокопии, использованной для транскрибации.

**Acceptance Scenarios**:

1. **Given** запись успешно завершена, **When** пользователь открывает встречу, **Then** доступна отдельная аудиокопия для прослушивания.
2. **Given** валидная M4A-аудиокопия была принята вместе с записью, но позднее недоступна для playback, **When** WAV-аудиокопия цела, **Then** система честно показывает недоступность playback и продолжает отдельную обработку текста.
3. **Given** во время записи пользователь слушает собеседника или подкаст, **When** запись идёт, **Then** приложение не меняет выбранный route и воспринимаемую громкость входящего звука.
4. **Given** новая запись отправляется на сервер, **When** передаётся первый и следующий аудиоартефакт, **Then** пользователь видит монотонный общий прогресс реальной передачи, а не фиксированный скачок по числу файлов.

---

### User Story 3 - Безопасно перейти на новый формат (Priority: P1)

Как владелец продукта, я хочу иметь понятный операторский план возврата на случай, если новая запись действительно окажется нерабочей, но не тратить время на упреждающую проверку старой версии, пока новый путь работает.

**Why this priority**: Запись, приватность и обработка внешним сервисом являются высокорисковыми; ошибка нового пути не должна портить будущие встречи или скрыто менять уже принятые данные.

**Independent Test**: Новый v5-путь проходит синтетический и установленный контрольный набор, а правила contingency-rollback документированы без пользовательского runtime-переключателя; фактическая проверка старого baseline запускается только после подтверждённого сбоя v5.

**Acceptance Scenarios**:

1. **Given** новый формат проходит обязательные контрольные записи, **When** оператор оставляет v5-путь активным, **Then** отдельная установка старого baseline не требуется и пользователь не видит rollback-контрол.
2. **Given** новый v5-путь действительно нарушает quality gate, **When** оператор принимает отдельное решение о contingency-rollback, **Then** проверка и установка выбранного baseline затрагивают только будущие записи, без скрытого runtime-переключателя.
3. **Given** новая запись уже принята для обработки, **When** возникает ошибка или сомнение в качестве, **Then** система не отправляет её повторно скрыто и не подменяет её результат задним числом.
4. **Given** в хранилище есть старые встречи прежнего формата, **When** пользователь открывает их после перехода, **Then** они остаются доступными в пределах их обычного жизненного цикла.

---

### User Story 4 - Не нести старую сложность дальше (Priority: P2)

Как сопровождающий продукт, я хочу, чтобы новые записи не зависели от устаревшей схемы двух входных дорожек, их текстовой склейки и экспериментальной очистки, чтобы дальнейшая поддержка была предсказуемой.

**Why this priority**: Временные обходы вокруг двойной расшифровки создают больше ложных результатов, чем пользы, и усложняют диагностику.

**Independent Test**: Новая запись проходит весь путь без создания, передачи или обработки двух независимых источников для транскрибации; проверка исходного дерева не находит active-path legacy для нового формата.

**Acceptance Scenarios**:

1. **Given** пользователь создаёт новую запись, **When** пакет готов к отправке, **Then** в нормальном пути есть одна аудиокопия для транскрибации и одна для playback.
2. **Given** обработчик получает новую запись, **When** он отправляет её на транскрибацию, **Then** отправляется только одна аудиокопия для текста, а playback-копия не отправляется.
3. **Given** контрольный период завершён успешно, **When** проводится cleanup, **Then** активные legacy dual-track, merge и экспериментальные echo-cleanup пути удалены без удаления исторических данных пользователя.

### Edge Cases

- Одна из исходных сторон молчит весь разговор: тишина сохраняет общую временную шкалу и не превращается в ложный отказ.
- В записи есть gap, смена устройства, обрыв входного звука или нечитаемый файл: система показывает отдельный правдивый degraded/blocked результат и не фабрикует transcript.
- Внешняя обработка могла принять запрос, но не вернула достоверный идентификатор: система не создаёт повторную отправку автоматически.
- Пользователь удаляет встречу до или во время обработки: все созданные аудиоартефакты и результаты участвуют в существующем lifecycle удаления.
- Старый клиент или историческая встреча использует прежний формат: новый путь его не изменяет и не ломает просмотр в пределах retention.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Каждая новая first-party запись MUST создавать ровно одну непрерывную WAV-аудиокопию для транскрибации и одну валидную M4A-аудиокопию для прослушивания; временные, частичные и повреждённые файлы не считаются готовым результатом и не образуют готовый package.
- **FR-002**: WAV-аудиокопия MUST представлять один синхронный разговор из локальной и входящей речи с общей начальной точкой, непрерывной шкалой времени и сохранением тишины, пауз и одновременной речи; для всей версии package применяется один явно версионированный, неизменяемый профиль сведения без скрытого mute или смены источника.
- **FR-003**: M4A-аудиокопия MUST быть получена из той же временной шкалы разговора, что и WAV-аудиокопия; она не должна служить входом для транскрибации и не должна подменять её после завершения записи.
- **FR-004**: Нормальная транскрибация новой записи MUST использовать только одну WAV-аудиокопию и создавать один пользовательский transcript с едиными timestamp и speaker boundaries.
- **FR-005**: Продукт MUST NOT применять AEC, искусственное подавление эха, VAD-вырезание, амплитудные presence-gates или текстовую дедупликацию как скрытую замену качественной записи.
- **FR-006**: Запись MUST сохранять Manual Start/Stop, постоянный видимый индикатор active capture, one-action Stop, выбранный playback route и слышимую пользователю громкость входящего звука; при любом timing/capture/degraded исходе индикатор и безопасное действие Stop остаются доступными до фактического завершения записи. Запись MUST NOT блокироваться только из-за выбранного output route: приложение не меняет маршрут или громкость, а акустическая копия звука колонок остаётся ограничением текущей версии и отдельной будущей фичей.
- **FR-007**: Desktop client MUST отправлять аудио только в GRAF backend и MUST NOT хранить или использовать credentials внешней транскрибации.
- **FR-008**: Для каждой новой записи MUST существовать неизменяемая версия формата и доказуемая связь между её аудиоартефактами, обработкой и результатом; уже принятая запись не может молча сменить режим транскрибации.
- **FR-009**: Переход MUST иметь документированные правила contingency-rollback и критерий остановки нового пути; фактическая проверка и установка baseline выполняются только после подтверждённого quality-сбоя v5, rollback влияет только на будущие записи и не удаляет уже принятые данные.
- **FR-010**: Исторические записи прежнего формата MUST оставаться доступными в пределах их retention, но новые записи MUST NOT создавать, отправлять или обрабатывать legacy dual-track package.
- **FR-011**: Все новые аудиоартефакты, их временные копии, статусы обработки и результаты MUST участвовать в существующих retention, deletion, audit и metadata-only diagnostics правилах.
- **FR-012**: При невалидной аудиокопии, недоступной обработке или неизвестном исходе отправки система MUST показывать отдельный безопасный результат; она MUST NOT автоматически создавать второй внешний job или выдавать ложный готовый transcript.
- **FR-013**: После успешного control period продукт MUST удалить active-path legacy dual-track capture, upload, submission, merge и echo-cleanup код, тесты, документы и user-facing утверждения; compatibility чтение исторических данных остаётся только настолько, насколько необходимо для retention.
- **FR-014**: Видимые состояния active capture, Stop, upload progress, playback/transcript availability и безопасные действия восстановления MUST быть доступны с клавиатуры и иметь однозначные accessibility-метки и обновления состояния; диагностика при этом остаётся metadata-only.
- **FR-015**: Progress отправки новой записи MUST вычисляться из реально переданных байтов всего выбранного package и монотонно отражать передачу до завершения; normal upload MUST иметь наблюдаемое промежуточное состояние между 0% и 100% и MUST NOT использовать фиксированный процент по числу файлов.

### Key Entities *(include if feature involves data)*

- **Каноническая аудиокопия транскрибации**: Непрерывная запись разговора, являющаяся единственным источником для text processing новой встречи.
- **Аудиокопия playback**: Отдельный готовый файл для прослушивания той же встречи, связанный с её временной шкалой, но не используемый для text processing.
- **Версия recording package**: Неизменяемое описание состава и правил конкретной записи, различающее новую и историческую форму данных.
- **Processing revision**: Привязанный к одной принятой аудиокопии жизненный цикл внешней обработки, статусов и результата.
- **Rollback baseline**: Проверенная точка кода и поведения, используемая только для безопасного возврата будущих записей.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% positive controlled recordings создают корректную WAV-аудиокопию для транскрибации и M4A-аудиокопию для playback; 100% заданных повреждённых, частичных и подменённых файлов получают безопасный verdict.
- **SC-002**: В 60-минутной контрольной записи расхождение длительности между canonical WAV, playback и transcript timeline не превышает 100 ms; допустимая container-specific padding фиксируется отдельно и не маскирует drift.
- **SC-003**: В контрольном наборе с локальной речью, входящей речью, overlap, тишиной и музыкой каждая заранее согласованная безопасная тестовая реплика появляется в итоговом transcript не более одного раза и в хронологическом порядке; evidence не содержит её текста.
- **SC-004**: 100% normal new-format MediaScribe submissions содержат ровно одну WAV-аудиокопию для транскрибации и не содержат playback-аудиокопию.
- **SC-005**: Во всех обязательных hardware scenarios active recording не меняет выбранный playback route и показывает изменение входящего уровня не более 1 dB относительно baseline.
- **SC-006**: Все historical recordings из принятого набора остаются открываемыми после включения нового формата, а 100% новых first-party recordings используют только новую версию package.
- **SC-007**: При имитированной невалидности WAV, недоступности processing service, unknown POST outcome и удалении во время обработки система не создаёт скрытую вторую отправку, не публикует ложный transcript и сохраняет правдивый lifecycle status.
- **SC-008**: Если после включения v5 подтверждён quality-сбой, отдельный contingency-rollback возвращает следующую controlled запись на выбранный baseline без потери active capture controls, permission truth или historical data; до такого сбоя rehearsal не является обязательным gate.
- **SC-009**: После завершённого control period source tree, package validation, companion processing и user-facing documentation не содержат active-path dual-track, transcript merge, AEC или echo-cleanup для новой записи.
- **SC-010**: Во всех normal new-format upload сценариях видимый progress монотонно растёт по переданным байтам, имеет хотя бы одно наблюдаемое значение строго между 0% и 100% и не прыгает на фиксированные 50% из-за завершения одного артефакта.
- **SC-011**: Во всех required capture/upload/degraded сценариях keyboard- и assistive-technology-пользователь получает доступное имя/значение состояния active capture, Stop, progress и следующего безопасного действия без раскрытия аудио или transcript content.

## Assumptions

- Первая поставка ограничена macOS system-audio-first recording; другие платформы и virtual routing не входят в этот slice.
- Пользовательский результат важнее сохранения раздельных источников для новых записей; пользователь не выбирает режим обработки, уровни или rollback.
- GRAF сохраняет server-mediated boundary и внешний транскрипционный сервис обрабатывает WAV только после принятия package сервером.
- Документированная rollback-процедура и выбранный baseline достаточно подготовлены для contingency-сценария; их фактическая проверка запускается только после quality-сбоя v5, а новый нормальный package не хранит старые raw dual-track источники как постоянную страховку.
- Исторические записи не мигрируются и не переотправляются без явного отдельного решения; они остаются только в compatibility read path до своего обычного удаления.
- Control period использует только разрешённые owner/test recordings, metadata-only evidence и заранее согласованные quality gates.

## Explicitly Out Of Scope

- Возврат виртуального аудиодрайвера, CoreAudio routing layer или действий с `coreaudiod`.
- AEC, WebRTC/Apple voice processing и другие audio-domain echo-cancellation решения.
- Пользовательская настройка режимов обработки, gain, source balance или rollback.
- Автоматическая повторная обработка существующих записей и скрытая отправка нескольких external jobs.
- LLM-based очистка, текстовая дедупликация или попытка скрыть физическую акустическую утечку после записи.
- Удаление исторических пользовательских встреч вне их существующего deletion/retention lifecycle.
