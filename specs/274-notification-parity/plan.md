# Implementation Plan: Паритет уведомлений GRAF с Krisp

**Branch**: `274-notification-parity` | **Date**: 2026-09-18 | **Spec**: [spec.md](spec.md)
**Input**: Спецификация фичи из `/specs/274-notification-parity/spec.md`
**Research**: [research.md](research.md) — реверс-инжиниринг наблюдаемого Krisp 3.16.8

## Summary

Сегодня все уведомления GRAF показывает система через `UNUserNotificationCenter`:
они подчиняются разрешению macOS и режиму «Не беспокоить», живут несколько
секунд, не несут кнопок действия и не различают «подключиться» и «начать
запись». Наблюдаемый эталон устроен иначе — собственные окна поверх всех окон,
которые GRAF рисует сам.

План заменяет поверхность показа: GRAF получает две собственные панели AppKit —
карточку уведомления (окно 448 точек, карточка 420 точек, скругление 16, тень
`0 1px 8px`, кнопки высотой 40 со скруглением 10) и компактный индикатор записи.
Логика показа переезжает из системного планировщика в собственный согласователь
(`reconcileCard`): окно показа −15 минут и 120 секунд, однократность на событие,
закрытие пользователем запоминается. Системные баннеры остаются дополнительным
каналом и больше не дублируют карточку.

## Technical Context

**Language/Version**: Swift 6 (языковой режим пакета), AppKit + SwiftUI-хост,
macOS 14+
**Primary Dependencies**: AppKit (`NSPanel`, `NSStackView`, `NSButton`),
`UserNotifications` (только для дополнительных системных баннеров), Combine
(подписка на снимок состояния), SwiftPM
**Storage**: файл настроек уведомлений в контейнере приложения
(`DesktopNotificationPreferencesStore`), состояние показа — в памяти процесса
**Testing**: XCTest, `apps/macos/Scripts/run-swift-tests.sh`; новые тесты
`DesktopNotificationCardTests` проверяют правила показа, содержимое, действия,
геометрию и поведение окна
**Risk / Validation Lane**: high-risk-feature — пользовательская поверхность,
рядом с записью и приватностью; полный путь Spec Kit и обязательные
clarify/checklist/analyze
**Release Gate**: no deploy — фича входит в обычный релизный поезд, отдельного
развёртывания не требует; релизная подготовка выполняется после проверок
**Target Platform**: macOS 14+, один экран или несколько, светлое и тёмное
оформление
**Project Type**: desktop-app (macOS-клиент внутри монорепозитория GRAF)
**Performance Goals**: показ карточки без заметной задержки относительно
момента срабатывания; не более одного окна карточки и одного окна индикатора
одновременно; отсутствие постоянного опроса — пересчёт по таймеру до срока и по
изменению состояния
**Constraints**: карточка не забирает клавиатурный фокус
(`canBecomeKey == false`), не перекрывает строку меню, не выходит за рабочую
область экрана, не зависит от разрешения macOS, не использует чужие ресурсы
**Scale/Scope**: один пользователь на Mac; до нескольких встреч в час; два новых
файла поверхности, один изменённый согласователь, один файл тестов

## Constitution Check

*GATE: проверка до Phase 0 и повторно после Phase 1.*

| Принцип | Как соблюдается |
|---|---|
| I. Capture-first, честные состояния | Карточка и индикатор показывают только то, что подтверждено снимком состояния; «Идёт расшифровка» показывается лишь при остановке сессии |
| II. Приватность и согласие | Карточка не раскрывает содержимое встречи, если пользователь отключил показ названий; ссылка открывается только после проверки владельца и актуальности события |
| III. Локальность и офлайн | Карточка работает без сети; для встреч нужен только уже полученный календарный контекст |
| IV. Один контроллер записи | Кнопки карточки отправляют те же команды модели, что и существующие элементы управления; второго контроллера не появляется |
| V. Проверяемость | Правила показа вынесены в чистые функции и покрыты тестами; геометрия измеряется на настоящем окне |
| VI. Простой и надёжный путь | Новый код — небольшой слой AppKit; системные уведомления остаются резервным каналом, а не удаляются |
| VII. Reference-Fidelity | Воспроизводится наблюдаемое поведение и внешний вид эталона; исходный код, ресурсы и бинарники Krisp не переносятся, реализация написана независимо, чужие торговые марки не используются |

Нарушений, требующих обоснования, нет.

## Validation Plan

1. **Модульные проверки**: `swift test --package-path apps/macos --filter
   DesktopNotificationCardTests` — правила окна показа, содержимое карточки,
   безопасность ссылки, однократность закрытия, состояния индикатора, геометрия
   карточки и окна.
2. **Регрессия уведомлений**: существующие `DesktopNotificationControlTests` и
   `DesktopLocalNotificationDeliveryTests` остаются зелёными.
3. **Полный набор macOS-тестов**: `bash apps/macos/Scripts/run-swift-tests.sh`.
4. **Быстрый репозиторный шлюз**: `infra/scripts/ci-local.sh --fast`.
5. **Ручная проверка в единственном приложении** `/Applications/GRAF Dev.app`
   через `infra/scripts/dev-harness.sh` (build → promote → status → smoke):
   карточка встречи, индикатор записи, поведение при выключенных системных
   уведомлениях, тёмное и светлое оформление.
6. **Проверка в PR**: `governance-fast`, `macos-pr`, `pr-metadata` на точном SHA;
   `release-full` — на замороженном кандидате релиза.

**Structure Decision**: поверхность уведомлений остаётся внутри модуля
`TwoBrainRecAppCore` рядом с существующими презентерами; отдельный модуль не
вводится, потому что карточка использует те же модели календаря и состояния
записи, что и текущий презентер, и не должна тянуть новые зависимости.

## Итоги реализации

- Поверхность показа: `DesktopNotificationCardPresenter` (окно 448 точек,
  карточка 420, скругление 16, кнопки 40/10) и
  `DesktopRecordingIndicatorPresenter` (232 точки, состояния записи и
  расшифровки, собственный счётчик длительности).
- Логика: `DesktopNotificationPresenter` получил согласователь карточки
  (срок −15 минут, окно 120 секунд, однократность закрытия), обновление
  индикатора из потока состояния и подавление системного баннера только когда
  карточка действительно показывает то же событие на экране.
- Проверки: 21 тест в `DesktopNotificationCardTests`; полный набор macOS-тестов
  (996 тестов) проходит.
- Шлюз `infra/scripts/ci-local.sh --fast` требует чистого дерева: доказательства
  шлюза фиксируются после одобренного сохранения изменений.
