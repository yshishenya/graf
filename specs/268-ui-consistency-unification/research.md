# Research: единый интерфейс GRAF (фича 268)

## 1. Уведомление об обновлении: сколько индикаторов и где

**Изученные практики (2026)**

- Chrome, Firefox, VS Code: постоянный индикатор один — бейдж на элементе
  оболочки (меню «⋮», гамбургер, шестерёнка активности). Отдельной полосы при
  пассивном состоянии нет; полоса/пункт появляются, когда нужно действие
  («Перезапустить для обновления», «Update available — Restart»).
- Microsoft 365: баннер показывается, только когда обновление нельзя применить
  и оно отложено на дни; частота эскалируется, а не дублируется постоянно.
- Руководства по бейджам (Microsoft InfoBadge, руководства по PWA Badging):
  бейдж — ненавязчивый сигнал, «не дублировать», один бейдж на область,
  появляться/исчезать по реальному состоянию.
- Capgo (обзор стратегий обновления приложений): «использовать наименее
  disruptive паттерн, который ещё работает»; тихое применение для безопасных
  изменений, выбор пользователя — для видимых, принуждение — только для
  критичного.
- macOS/Sparkle: обязательная явная команда «Проверить обновления…» в меню
  приложения; собственного постоянного баннера Sparkle не требует.

**Решение для GRAF**

- Постоянный индикатор ровно один — кнопка в подвале боковой панели
  (`[data-graf-app-update]` в кабинете, локальная плашка в локальном режиме
  без кабинета). Он виден и в рейле (иконка 40×40), поэтому не теряется.
- Верхняя полоса `AppUpdateNotice` показывается только для фаз, требующих
  действия или внимания: `downloading`, `installing`, `readyToInstall`,
  `failed`. При `available`/`deferredForCapture` полосы нет — только индикатор.
- Меню приложения и трей содержат одну явную команду; подписи берутся из одного
  источника и совпадают: «Проверить обновления…» без известной версии,
  «Обновить GRAF до <версия>…» с известной. Пункт трея не является вторым
  постоянным индикатором: он виден только в открытом меню и выполняет действие.
- Состояния, которые сейчас говорят разное об одном событии, сводятся к одному
  словарю фаз (см. контракт).

**Отклонённые варианты**

- Оставить всё как есть (баннер + сайдбар + трей + меню) — дублирование и
  разный текст об одном событии, противоречит практике.
- Убрать индикатор из оболочки и оставить только баннер — на узком окне баннер
  дорог по вертикали и конфликтует с областью heder, а бейдж-паттерн ближе к
  Chrome/VS Code.

## 2. Единая палитра: что источник правды

- Источник — палитра кабинета (`:root`, тёмная тема) и её светлый набор
  (`html[data-theme="light"]` + `prefers-color-scheme: light`).
- Нативное приложение получает динамические цвета (`NSColor(name:)` с
  appearance-провайдером), значения которых совпадают с кабинетом в тёмном и
  светлом вариантах. Системные `NSColor` остаются только там, где элемент по
  смыслу системный (например, материал поповера в AppKit-комбобоксе).
- Локальные палитры (`.detail-page-main`, `.detail-playback`) удаляются; плеер
  использует общий `--surface-2`, текст и границы — общие токены.
- Жёсткие rgba переводятся на `color-mix()` от токенов; белые подложки, которые
  ломают светлую тему, заменяются на `--line-soft`/`--surface-2`.

## 3. Шкала радиусов

Вводится пять значений вместо 17 литералов: `--radius-xs: 6px`,
`--radius-sm: 8px`, `--radius-control: 9px`, `--radius-compact: 10px`,
`--radius-card: 12px`, `--radius-panel: 14px`, `--radius-dialog: 16px`,
`--radius-pill: 999px`. Отображение существующих литералов: 4/5/6 → xs,
7/8 → sm, 9 → control, 10 → compact, 12 → card, 14 → panel, 16 → dialog,
20/999/50% → pill.

## 4. Типографика

- `--font-size-body` приводится к фактическому базовому размеру 14px, поздняя
  правка `body { font-size: 14px }` удаляется (остаётся один источник).
- Компактный режим настроек получает явный `--font-size-body-compact: 13px`
  и применяется только внутри страниц настроек.
- Заголовок страницы один: `--font-size-page-title` (20px, line-height 1.3) для
  списка, карточки встречи, настроек и служебных страниц; единичные клампы
  удаляются.
- Все размеры и заголовки диалогов — через `--font-size-dialog-title`.

## 5. Палитра спикеров и доступность

- `speaker-color-0` (неизвестный) остаётся нейтрально-серым, `speaker-color-4`
  получает собственный синий оттенок; в светлой теме задаются более тёмные
  варианты всех семи цветов, контраст текста ≥ 4,5:1, контраст плашек ≥ 3:1.
- Текст на цветных плашках берётся из токена `--speaker-contrast-text`
  (тёмный в тёмной теме, белый в светлой).

## 6. Идентификаторы состояний автозаписи

- Строковые статусы заменяются перечислением `MeetingDetectionStatus` в
  общей модели (Shared) с готовыми подписями; производитель и потребитель
  используют один тип, поэтому «заблокировано» больше не может отобразиться как
  «включено».
- Существующие тексты сохраняются как значения перечисления; тесты обновляются
  точечно.

## 7. Обрезка подписей навигации

- Замерено: «Поделились со мной» требует 144px при доступных 142px (панель
  240px); «Тариф и оплата» требует 100px при 94px (панель настроек 192px).
- Решение: горизонтальный паддинг пункта 10 → 8px и ширина панели настроек
  192 → 204px. Текст подписей не меняется.
- Блок профиля: имя — не более двух строк, адрес — одна строка с многоточием,
  полный текст в `title`; высота блока перестаёт зависеть от длины данных.

## 8. Страницы вне системы

- История уведомлений переводится на `base.html` + `cabinet_shell` с обычной
  навигацией и профилем; роут уведомлений получает те же данные навигации, что
  и список встреч.
- Страницы удаления получают стандартные компоненты: карточки, заголовки,
  оформленные ссылки; текст отчёта унифицируется по конвенции.

## 9. Тесты и контракты

- Контрактные тесты кабинета проверяют конкретные CSS-значения и тексты: они
  обновляются вместе с изменениями, но не ослабляются (проверка смысла
  сохраняется).
- Новые проверки: отсутствие жёстких цветов вне палитры (по списку селекторов),
  отсутствие «ё» в пользовательских строках, единственный индикатор обновления,
  соответствие радиусов токенам, отсутствие обрезки подписей по замеру,
  контраст палитры спикеров.
