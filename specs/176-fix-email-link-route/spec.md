# Feature Specification: Стабильное подключение email в приложении

**Feature Branch**: `codex/176-fix-email-link-route`

**Created**: 2026-08-20

**Status**: Released in production as `v2026.08.20.2`

**Input**: User description: "При подключении email к своему аккаунту код приходит на почту, но приложение вместо ввода кода показывает ошибку загрузки встреч."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Ввести полученный код без потери экрана (Priority: P1)

Вошедший пользователь открывает настройки аккаунта в macOS-приложении, вводит email и нажимает «Подключить email». После отправки письма приложение оставляет перед ним экран ввода шестизначного кода, чтобы он мог завершить подключение.

**Why this priority**: Сейчас письмо доставляется, но основной пользовательский путь обрывается до ввода кода и подключить email невозможно.

**Independent Test**: В синтетическом аккаунте открыть embedded-настройки, отправить форму подключения email и убедиться, что экран кода остаётся видимым и принимает код без промежуточной ошибки встречи.

**Acceptance Scenarios**:

1. **Given** пользователь вошёл в macOS-приложение и имеет подтверждённую сессию, **When** он отправляет корректный новый email, **Then** приложение показывает экран ввода кода и не заменяет его общей ошибкой загрузки встреч.
2. **Given** экран кода открыт после отправки письма, **When** оболочка приложения синхронизирует своё состояние навигации, **Then** экран не перезагружается как несовместимый адрес и введённые цифры не теряются.
3. **Given** пользователь вводит действующий код, **When** он нажимает «Продолжить», **Then** email подключается по существующим правилам и пользователь возвращается в настройки аккаунта.

---

### User Story 2 - Безопасно повторить или отменить подключение (Priority: P2)

На экране кода пользователь может повторно отправить код или вернуться к изменению email. Эти действия остаются внутри приложения и не создают скрытых повторных переходов.

**Why this priority**: Восстановление после задержанного или ошибочно введённого адреса должно работать без выхода из embedded-пути.

**Independent Test**: На экране кода отдельно проверить повторную отправку и возврат в настройки; каждое действие должно приводить к одному ожидаемому экрану без ошибки встречи.

**Acceptance Scenarios**:

1. **Given** код ещё не введён, **When** пользователь нажимает «Отправить код ещё раз», **Then** создаётся один новый запрос кода и экран ввода остаётся доступным.
2. **Given** пользователь хочет изменить адрес, **When** он выбирает возврат, **Then** открываются embedded-настройки аккаунта, а не web-версия и не список встреч.

---

### User Story 3 - Не сломать web и другие формы приложения (Priority: P2)

Обычная web-версия подключения email и остальные формы настроек продолжают работать как раньше. Исправление применяется к общему классу ошибочного повторного открытия действий, а не к тексту конкретной кнопки.

**Why this priority**: Навигация используется многими формами; локальная заплатка не должна создавать новые повторные отправки или регрессии в соседних сценариях.

**Independent Test**: Проверить web-подключение email и embedded-формы, которые завершаются перенаправлением; успешный ответ должен выполняться один раз, а конечная страница — оставаться доступной.

**Acceptance Scenarios**:

1. **Given** пользователь подключает email в браузере, **When** он проходит отправку и ввод кода, **Then** существующий web-путь работает без изменения адресов и поведения.
2. **Given** embedded-форма завершает действие перенаправлением на обычную страницу, **When** переход заканчивается, **Then** приложение отслеживает конечную страницу, но не воспроизводит само изменяющее действие повторно.

### Edge Cases

- Письмо доставлено медленно, но экран ввода кода уже открыт.
- Пользователь нажимает повторную отправку несколько раз и попадает под существующее ограничение частоты.
- Код неверен, истёк или уже использован; ошибка остаётся на embedded-экране кода.
- Сессия истекает между отправкой письма и проверкой кода.
- Оболочка приложения обновляет представление сразу после ответа на форму.
- Действие завершается обычным перенаправлением; отслеживается только конечная безопасная страница.
- Пользователь возвращается назад или обновляет экран после отправки формы; изменяющее действие не выполняется повторно автоматически.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: После успешного запроса подключения email macOS-приложение MUST оставлять экран ввода кода доступным до явного действия пользователя или терминального результата.
- **FR-002**: Оболочка приложения MUST NOT автоматически воспроизводить изменяющий запрос как обычное открытие страницы.
- **FR-003**: Синхронизация навигации MUST отслеживать безопасную конечную страницу после перенаправления, не сохраняя изменяющее действие как повторно открываемый адрес.
- **FR-004**: Один клик «Подключить email» MUST создавать не более одного запроса отправки кода; исправление MUST NOT дублировать письмо.
- **FR-005**: Экран кода MUST сохранять существующие действия проверки, повторной отправки и возврата внутри embedded-маршрутов.
- **FR-006**: Неверный, истёкший, повторно использованный или временно недоступный код, включая rate-limited и delivery-unavailable состояния, MUST показывать существующую локализованную auth-ошибку, а не общий экран ошибки встречи.
- **FR-007**: Существующие проверки сессии, CSRF, ограничения частоты, одноразовость кода и правила привязки/объединения аккаунтов MUST оставаться без изменений.
- **FR-008**: Email, код, токен сессии и состояние подтверждения MUST NOT попадать в повторно открываемый URL, логи, diagnostics или evidence.
- **FR-009**: Web-путь подключения email MUST сохранить текущее поведение и адреса.
- **FR-010**: Исправление MUST покрывать общий механизм embedded-навигации для изменяющих форм, чтобы соседние POST-only действия не превращались в несовместимые повторные открытия.
- **FR-011**: При ответе сервера 4xx/5xx приложение MUST показывать auth/settings-контекст, когда он доступен, и MUST NOT ошибочно классифицировать такой ответ как сбой списка встреч.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: В 3 из 3 последовательных embedded-проверок пользователь после запроса кода видит экран ввода и может завершить подключение без общей ошибки встречи.
- **SC-002**: Каждый из 3 проверочных запросов подключения создаёт ровно одно письмо и не вызывает автоматический повтор изменяющего действия.
- **SC-003**: В production-like журнале тестового пути отсутствуют повторные открытия адреса отправки кода обычным запросом и ответы `405` для этого пути.
- **SC-004**: Web-подключение email, embedded-проверка кода, повторная отправка, возврат и соседняя форма с перенаправлением проходят автоматические regression checks без изменений существующих security-границ.
- **SC-005**: Пользователь может перейти от нажатия «Подключить email» к началу ввода кода не более чем за 5 секунд после ответа сервера, не считая времени доставки письма.

## Assumptions

- Почтовая доставка работает: production уже подтвердил успешную отправку кода до появления ошибки интерфейса.
- Владельцем изменения является новый регрессионный срез Feature 176; завершённая Feature 175 остаётся историей исходного auth-fix.
- Существующие модели callback-state, привязки identity и объединения аккаунтов переиспользуются без миграции данных.
- Изменение production macOS-бинарника потребует обычного подписанного обновления приложения; серверный код меняется только при необходимости regression coverage или безопасной совместимости.
- Изменение текста общего fallback-экрана, почтового провайдера и логики объединения аккаунтов находится вне scope.
