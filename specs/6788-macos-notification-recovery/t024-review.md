## Причина прежней нестабильности

Старый тест запускал два процесса с одним файлом manifest.
`operation_promote` читает candidate до `state_lock`, а первая публикация
перезаписывает этот файл активной версией. Если второй процесс прочитал файл
после публикации, он законно завершался с idempotent PASS. Если оба успели
прочитать исходную версию, второй получал отказ изменения активной identity.
Ожидание безусловных 1 PASS/1 FAIL и комментарий про stale-parent не отражали
этих двух порядков выполнения. Два PASS сами по себе не доказывали поломку
блокировки.

## Проверенная правка

- Сначала публикуется родитель с SHA `a…a`. До запуска процессов строятся
  два отдельных кандидата `e…e` и `f…f`. Их первые 12 символов и, следовательно,
  manifest IDs различаются; общий parent явно проверяется.
- По одному worker получает собственный файл кандидата. Публикация победителя
  не перезаписывает файл проигравшего: при входе второго в блокировку его
  parent однозначно устарел независимо от времени чтения candidate.
- Ожидается ровно один победитель и ровно одна конкретная ошибка
  `candidate parent manifest is stale; rebuild from current active Dev manifest`.
  Произвольная ошибка lock/IO/validation не засчитывается как правильный отказ.
- Оба worker должны завершиться с кодом 0; результат победителя сопоставляется
  с одним из подготовленных manifest. Активные ID и SHA должны принадлежать
  этому победителю, а parent остаётся исходным общим родителем. Проверка не
  требует заранее выбранного порядка победы.
- `test_repromote_active_manifest_recovers_stopped_runtime_without_self_parent`
  не изменён: отдельная проверка законного idempotent promote, сохранения parent
  и отказа изменённой активной identity остаётся. Допуск двух успешных
  конкурирующих разных кандидатов не добавлен.

Diff затрагивает только тело одного теста и его поясняющий комментарий.
`_promote_worker` и вспомогательные функции сохранены. `git diff --stat --
scripts/dev-harness.py` пустой; production/harness/runtime путь не изменён.
Новых зависимостей, mock-реализации блокировки, sleep или специальных обходов
проверяемого кода не добавлено.

Один запуск процессов проверяет конфликт кандидатов и целостность результата,
но не исчерпывает все варианты планирования потоков ОС. Это прежняя граница
такого теста, а не основание вводить дополнительную инфраструктуру в T024.
