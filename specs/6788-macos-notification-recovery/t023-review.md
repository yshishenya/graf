## Решение

**Новых подтверждённых P1/P2 нет. Требования достаточны; исправление T023
закрывает описанное в combined-code-review.md рассогласование `partial` на
уровне проверенного кода.** Это не объявление runtime PASS или готовности PR.
Повтор тестов объединённого кандидата проводит родитель.

T023 прямо связан с US5/FR011/SC007 и прежним контрактом «partial — доступный
результат с явно указанными ограничениями». Параграф tasks и data-model
документируют минимальное дополнительное поле. Новая продуктовая сущность,
система уведомлений, таблица, миграция или изменение разрешений не требуются.

## Проверенный путь

1. Серверный список получает `summary_progress_state` из существующего
   `summary_progress()` после фильтрации workspace/deletion и решения доступа
   к каждой встрече. Выбор опубликованного результата остаётся в прежних
   selectors и source/media/revision checks. T023 не меняет эти проверки.
2. `build_list_item()` передаёт `summary_status` как исходный `outcome_set.status`
   только при реально выбранном `stored_output`; иначе сохраняет переданное
   проверенное `summary_progress_state`. Это позволяет сохранить общий
   `partial`, даже если отдельная категория summary доступна. Наличие или
   отсутствие отдельных categories не используется для угадывания общего
   результата. Проверены оба production caller: список и `build_review_response`.
3. `MeetingListItem.summary_status: str | None = None` — одно дополнительное
   поле передачи состояния. Оно не хранится в БД, не открывает содержимое и
   не является источником полномочий. Отсутствие поля при создании модели
   допустимо благодаря default `None`; существующие конструкторы не требуют
   миграции. Поле `DesktopSyncReviewState.summary_status` относится к ранее
   рассмотренному переносу F258, а не к новому объёму T023.
4. `_meeting_list_content_readiness()` при `stored_output` + `partial`
   сообщает «итоги доступны частично» с отдельной правдой о расшифровке.
   Полная готовность сохраняет прежнюю подпись; ожидание не превращается в
   готовность. `_meeting_list_compact_status()` учитывает `summary_status ==
   "partial"` как «Готово с ограничениями», сохраняя прежний приоритет ошибок,
   удаления, отправки и состояния аудио. Общий row renderer используется
   обычным и встроенным кабинетом.
5. `renderProcessingProjection()` переводит `partial` в готовый этап с
   подписью «Доступно частично». `available` остаётся «Готово», `generating` —
   активным этапом; failed/unavailable сохраняют прежнюю обработку. Эта
   поправка не меняет видимость содержимого, selected format, polling или
   playback. Она использует прежний `processingSummaryState`, который
   учитывает состояние summary artifact из серверной проекции.
6. `renderProcessingListProjection()` добавляет отдельную подпись частичного
   результата, сохраняя перед ней guards текущей строки, meeting ID и
   generation. При принятом обновлении всего списка используется серверная
   строка; динамическая подпись — прежний запасной путь до такого обновления.
   Выставление textContent не добавляет интерпретацию HTML или источник прав.

Объём минимален: используются существующая проекция, модель ответа и два
существующих места представления. Вводить новый статусный объект или вычислять
`partial` по category states не требуется. Подтверждённого переусложнения в
этих изменениях не найдено.

## Что доказывают подготовленные регрессии

- `test_published_partial_is_visible_but_invalid_pointer_never_substitutes_audio`
  создаёт синтетический принятый `partial`, проверяет processing visibility,
  затем реальный API списка и HTML `/meetings`/`/desktop/meetings`. API сохраняет
  `summary_status=partial`, обе страницы содержат частичную готовность и не
  содержат ложного «Расшифровка и итоги готовы». Существующие проверки чужой
  ревизии, другого формата и invalid source pointer не удалены.
- `test_partial_summary_is_available_with_limits_in_detail_and_list` выполняет
  настоящие тела `renderProcessingProjection` и `renderProcessingListProjection`
  в Node с ограниченными DOM/transport заглушками. Для partial/available
  проверяет состояние этапа и подпись строки; для generating — активный этап.
  Это исполнение функций, а не поиск нужной строки в исходнике. Заглушка
  requestMeetingListRefresh=false намеренно позволяет проверить динамическую
  строку; настоящий серверный путь покрыт отдельной интеграционной регрессией.
- Этот Node-тест не является браузерной приёмкой layout/фокуса и не проверяет
  все networking/epoch guards: они не изменены T023 и остаются в общей проверке.
  Он также не проверяет подпись строки generating; эту более широкую гарантию
  данному тесту не приписываем.
