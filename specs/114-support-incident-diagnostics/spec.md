# Feature Specification: Детальный metadata-only отчёт поддержки

**Feature Branch**: `114-support-incident-diagnostics`

**Created**: 2026-07-21

**Status**: Implemented; validation complete, pending approval/PR

**Input**: User description: «Добавить максимально полезную безопасную информацию в отчёт поддержки: версия, ID записи, этап, проблема и всё необходимое для быстрого разбора; проверить весь поток отправки и создания Issues».

## User Scenarios & Testing

### User Story 1 - Понять инцидент по private Issue (Priority: P1)

Инженер поддержки открывает private GitHub Issue, созданный из отчёта локальной записи, и сразу видит, какая запись и какой запуск затронуты, на каком этапе находится поток, что известно о сервере и локальной копии, почему произошёл сбой и какое действие ожидается дальше.

**Why this priority**: Сейчас в сообщении недостаточно контекста, поэтому поддержке приходится просить пользователя повторить диагностику и вручную сопоставлять несколько попыток.

**Independent Test**: Подать в серверный endpoint фикстуры для неуспешной отправки, конфликта удаления и ошибки доступа и проверить, что private Issue содержит понятную сводку состояния, безопасные корреляционные значения, ограниченный таймлайн и полный безопасный JSON.

**Acceptance Scenarios**:

1. **Given** сервер вернул конфликт или запрет доступа, **When** Issue создаётся, **Then** в его начале указаны канонический этап, код проблемы, причина, следующее действие, локальное состояние и серверная истина.
2. **Given** несколько повторных попыток относятся к одной записи, **When** отчёты принимаются повторно, **Then** Issue находится по CUST/report fingerprint/dedupe key и не создаёт дубликат для того же инцидента.

### User Story 2 - Сформировать правдивый metadata-only отчёт (Priority: P1)

Приложение формирует отчёт, в котором версия клиента и сборки, платформа, безопасные идентификаторы, этап, причина, состояния локальной и серверной копий, время ключевых переходов, попытки отправки, безопасный профиль локального артефакта и серверная корреляция согласованы между собой.

**Why this priority**: Детальный, но правдивый контекст сокращает время диагностики и не должен маскировать удаление, потерю локальной копии или неизвестное серверное состояние.

**Independent Test**: Сгенерировать отчёты для успешной отправки, сетевой ошибки, частичной загрузки, серверного удаления, окончания хранения и отсутствия ответа sync-state; сравнить поля с фикстурой состояния очереди и ответом сервера.

**Acceptance Scenarios**:

1. **Given** серверная запись удалена после предыдущего успешного состояния, **When** создаётся новый отчёт, **Then** он показывает удаление/неизвестность серверной копии, не объявляет запись доставленной и содержит безопасное следующее действие.
2. **Given** этап или причина неизвестны, **When** отчёт формируется, **Then** используются явные значения `unknown`/`not_available`, а не догадки или противоречивые статусы.
3. **Given** старый отчёт версии 1, **When** сервер принимает его во время переходного периода, **Then** он остаётся валидным и получает серверную redaction-метаинформацию без потери совместимости.

### User Story 3 - Передать тот же отчёт при недоступном сервере (Priority: P1)

Пользователь нажимает «Скопировать безопасную сводку», когда отправка не удалась, и получает тот же детальный redacted отчёт, который был бы отправлен на сервер, с локальным report fingerprint для последующего сопоставления.

**Why this priority**: Fallback должен быть полезным каналом поддержки, а не коротким текстом, который теряет причину и историю попыток.

**Independent Test**: Отключить сеть/отклонить запрос, нажать кнопку копирования и проверить, что clipboard содержит bounded JSON/сводку с теми же безопасными полями и без аудио, текста, секретов, путей и необезличенных идентификаторов.

**Acceptance Scenarios**:

1. **Given** сервер не выдал CUST, **When** пользователь копирует отчёт, **Then** в сводке присутствуют report fingerprint и dedupe key, достаточные для ручного поиска после восстановления связи.
2. **Given** clipboard недоступен, **When** копирование не удаётся, **Then** интерфейс сообщает об ошибке без удаления локальной копии и без повторной отправки контента.

### User Story 4 - Найти и отфильтровать повторяющиеся проблемы (Priority: P2)

Поддержка фильтрует private Issues по номеру фичи, приоритету, области, каноническому этапу, коду проблемы и безопасному идентификатору отчёта.

**Why this priority**: Поиск по стабильным значениям позволяет группировать инциденты и видеть регрессии после релиза.

**Independent Test**: Создать несколько фиктивных Issues с разными стадиями и кодами, затем проверить title/labels/body и поиск по CUST, fingerprint и problem code.

**Acceptance Scenarios**:

1. **Given** два отчёта имеют разные коды проблемы, **When** поддержка фильтрует Issues, **Then** каждый код и этап однозначно различимы в title/labels/body.
2. **Given** одна запись повторно отправлена, **When** приходит обновлённый отчёт, **Then** существующий Issue обновляется или связывается по dedupe key вместо создания неуправляемого дубля.

## Edge Cases

- Сервер не отвечает, отвечает без sync-state или возвращает неизвестные поля: отчёт сохраняет локальную правду и явно помечает серверную как `unknown`.
- Серверная запись была доставлена, а затем удалена или заблокирована: более свежая серверная истина имеет приоритет над устаревшим локальным флагом `uploaded`.
- Для записи отсутствуют локальные файлы или не завершена контрольная сумма: указывается безопасный профиль полноты и риск, но не имя файла и не путь.
- У одной записи много retry-записей или затронутых элементов: payload ограничивается детерминированным числом последних событий и безопасных fingerprints.
- Отчёт содержит неизвестный/недопустимый код: сервер сохраняет валидную часть, редактирует опасные поля и сообщает число удалённых полей.
- Запрос создания Issue повторяется после таймаута: dedupe key предотвращает дубликаты и сохраняет последнюю подтверждённую попытку.
- У пользователя нет сети и clipboard недоступен одновременно: локальная копия записи и возможность ручного повторения остаются неизменными.

## Requirements

### Functional Requirements

- **FR-001**: Система MUST формировать версионированный отчёт поддержки с явным `schema_version` и переходной совместимостью с текущим форматом.
- **FR-002**: Система MUST включать безопасные корреляционные значения (CUST при наличии, report fingerprint, dedupe key и ограниченные fingerprints записи/сессии) и MUST исключать raw UUID, имена файлов, локальные пути и содержимое встречи.
- **FR-003**: Система MUST показывать один канонический этап инцидента и отдельно передавать локальное состояние, серверную доступность/удаление, состояние upload/processing и состояние доступа.
- **FR-004**: Система MUST указывать нормализованные `problem_code`, категорию сбоя, безопасную причину, владельца следующего действия и `next_action`; неизвестные значения должны быть явными.
- **FR-005**: Система MUST включать версию приложения/сборки, платформу, архитектуру, локаль, часовой пояс и уже доступные безопасные runtime-статусы без добавления нового permission/logging surface, секретов и персонального контента.
- **FR-006**: Система MUST включать серверную истину из существующего sync-state: безопасные статусы meeting/media/upload/processing/review, deletion/access state, conflict reason/next action и время последней сверки.
- **FR-007**: Система MUST включать ограниченный таймлайн (создание, финализация, попытки, последний ответ сервера, следующий retry, retention) и не более последних пяти безопасных retry-событий.
- **FR-008**: Система MUST включать безопасный профиль локального артефакта: роли дорожек, признаки полноты/контрольной суммы, размеры по bucket и риск потери, без аудиоданных и путей.
- **FR-009**: Сервер MUST применять allowlist/redaction ко всем полям отчёта, сохранять `server_redaction_version`, `redaction_result`, число запрещённых полей и вычислять серверные CUST/dedupe-корреляции.
- **FR-010**: Сервер MUST создавать private Issue с русской структурированной сводкой: корреляции, stage/problem, state matrix, timeline, retry summary, redaction result и полным безопасным JSON; title и labels должны поддерживать фильтрацию по feature 114, приоритету и области.
- **FR-011**: Кнопка «Скопировать безопасную сводку» MUST использовать тот же redacted детальный отчёт, что и отправка, и MUST добавлять локальный fingerprint, если CUST ещё не выдан.
- **FR-012**: Повторная отправка одного инцидента MUST быть идемпотентной по dedupe key и не должна создавать дубликат private Issue.
- **FR-013**: Payload и текст clipboard MUST быть bounded по размеру и количеству элементов; превышение лимита должно обрабатываться безопасным сокращением с признаком truncation.
- **FR-014**: Система MUST сохранять возможность ручной отправки/копирования и локальную копию при любой ошибке сети, redaction или создания Issue.
- **FR-015**: Автотесты MUST проверять запрещённые данные и секреты негативными шаблонами, согласованность canonical stage/problem с серверной истиной, v1 compatibility, idempotency и формирование private Issue.

### Key Entities

- **Support Incident Report**: Версионированное metadata-only представление одного инцидента: корреляции, состояние, причина, таймлайн, retry и redaction-результат.
- **Canonical Incident Stage**: Нормализованный этап жизненного цикла записи/отправки, позволяющий читать инцидент без интерпретации набора разрозненных флагов.
- **Server Truth Snapshot**: Последнее безопасное подтверждение от сервера о meeting, media, upload, processing, review, deletion/access и конфликте.
- **Retry Event**: Ограниченное безопасное событие попытки с временем, режимом, категорией, HTTP/problem code и результатом; без тела запроса.
- **Support Issue Correlation**: Связка CUST, report fingerprint и dedupe key, по которой private Issue создаётся или обновляется идемпотентно.

## Success Criteria

### Measurable Outcomes

- **SC-001**: В 95% тестовых инцидентов инженер поддержки определяет этап, код проблемы, локальное/серверное состояние и следующее действие, читая только начало private Issue, не открывая локальные логи.
- **SC-002**: 100% unit/contract/integration тестов для отчёта и clipboard fallback подтверждают отсутствие аудио, transcript/content, секретов, cookies, токенов, raw UUID, имён файлов и локальных путей.
- **SC-003**: В 100% повторных доставок с одним dedupe key создаётся или обновляется ровно один private Issue; поиск по CUST, report fingerprint и problem code находит нужный инцидент.
- **SC-004**: 100% проверенных сценариев server deletion/access conflict не показывают ложное состояние `delivered`/`server_copy_known=true` и содержат безопасное следующее действие.
- **SC-005**: Формирование bounded отчёта и подготовка clipboard завершаются не более чем за 1 секунду на поддерживаемом Mac и не блокируют stop/finalize захвата.
- **SC-006**: Сервер принимает текущие v1 отчёты и новые v2 отчёты в переходный период; redaction-метаданные присутствуют в 100% принятых отчётов.
- **SC-007**: Структурированный Issue содержит сводку, state matrix, timeline, retry summary и полный безопасный JSON в 100% успешных фикстур создания/обновления.

## Assumptions

- Поддержка использует private GitHub Issues в том же репозитории; публичные Issues и Linear не входят в scope.
- Существующий authenticated sync-state endpoint и текущая очередь upload остаются источниками данных; новый поток сбора аудио/транскрипта не создаётся.
- CUST и server-side issue number выдаются сервером только после успешного запроса; до этого локальный report fingerprint является главным корреляционным значением.
- В отчёт попадают только ограниченные метаданные и fingerprints; универсальное удаление резервных копий, undelete и восстановление записи не входят в feature 114.
- Поддерживаемые macOS версии и существующая локализация сохраняются; новые пользовательские строки должны иметь русскую и английскую локализацию по принятому проектному паттерну.
- Реализация выполняется по текущим product/privacy/deletion gates и не меняет право пользователя удалять локальную копию.
