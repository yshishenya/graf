# Feature Specification: Подключение Яндекс Календаря

**Feature Branch**: `codex/201-yandex-calendar-enable`

**Created**: 2026-08-25

**Status**: Draft

**Input**: User description: "Начать включение календарей с Яндекс Календаря"

## Контекст и границы

GRAF должен начать поэтапно открывать календарные подключения после завершения
общего calendar foundation. Первым провайдером становится Яндекс Календарь.
Подключение предназначено только для чтения выбранных событий и календарного
контекста встреч.

В этой фиче не включаются Google Calendar, Microsoft Exchange, другие CalDAV-
провайдеры, календарные записи/изменения, приглашения, автоматическое
подключение к встречам и автоматический старт записи.

## Сценарии пользователя и проверки

### User Story 1 — Подключить Яндекс Календарь (Priority: P1)

Как владелец рабочей области, я хочу подключить Яндекс Календарь через пароль
приложения, чтобы выбрать календари, из которых GRAF будет читать встречи.

**Почему этот приоритет**: это минимальный пользовательский путь для первого
реально доступного внешнего провайдера.

**Независимая проверка**: на тестовом аккаунте Яндекса пройти подключение в
браузере и embedded macOS, получить каталог календарей и увидеть сохранённый
источник после перезагрузки.

**Сценарии приёмки**:

1. **Дано** активная сессия владельца и валидный пароль приложения, **когда**
   пользователь отправляет форму Яндекс Календаря, **тогда** GRAF проверяет
   доступ и непустой каталог до сохранения источника.
2. **Дано** подключение успешно проверено, **когда** пользователь обновляет
   страницу, **тогда** источник отображается как подключённый, а секрет не
   показывается ни в интерфейсе, ни в ответе.
3. **Дано** пароль неверен, каталог пуст или провайдер недоступен, **когда**
   пользователь отправляет форму, **тогда** источник не создаётся, а UI
   показывает безопасное состояние ошибки.
4. **Дано** подключение Яндекс Календаря успешно сохранено, **когда** ответ
   подключения завершён, **тогда** GRAF сразу запускает первый read-only sync
   источника.

### User Story 2 — Выбрать и синхронизировать календари (Priority: P1)

Как владелец, я хочу выбрать от нуля до двадцати календарей и запустить
синхронизацию, чтобы GRAF использовал только явно выбранные данные.

**Почему этот приоритет**: без выбора и фактического чтения подключение не
даёт продуктовой ценности и может нарушить границу минимально необходимого
доступа.

**Независимая проверка**: выбрать один календарь, дождаться queued → syncing →
успешного состояния, проверить ближайшее событие и затем сохранить нулевой
выбор.

**Сценарии приёмки**:

1. **Дано** каталог содержит доступные календари, **когда** пользователь
   сохраняет выбор, **тогда** сохраняются только переданные ID, а нулевой выбор
   остаётся допустимым и отключает будущие подсказки по этому источнику.
2. **Дано** выбранный календарь, **когда** worker выполняет синхронизацию,
   **тогда** события проходят общий нормализованный контракт и появляются в
   GRAF только в разрешённом временном окне.
3. **Дано** Яндекс возвращает timeout, rate limit, invalid credentials,
   malformed payload или недоступность, **тогда** источник получает безопасное
   состояние ошибки, а ручная запись и загрузка не блокируются.
4. **Дано** у источника Яндекс есть выбранные календари, **когда** после
   предыдущего запуска проходит пять минут, **тогда** GRAF автоматически
   запускает следующий sync без действия пользователя.
5. **Дано** пользователь нажимает «Синхронизировать», **когда** источник
   доступен, **тогда** запрос выполняет sync до ответа и показывает завершённый
   или безопасный ошибочный результат, а не только ставит работу в очередь.

### User Story 3 — Отключить Яндекс безопасно (Priority: P1)

Как владелец, я хочу отключить Яндекс Календарь и понимать результат, чтобы
GRAF перестал читать новые события без потери уже созданных встреч.

**Почему этот приоритет**: отключение и удаление секрета являются обязательной
частью доверенного запуска внешнего провайдера.

**Независимая проверка**: отключить подключённый тестовый источник, обновить
браузер и убедиться, что источник исчез из активных данных, секрет больше не
читается, а ранее связанный контекст встречи сохраняется по правилам GRAF.

**Сценарии приёмки**:

1. **Дано** активный источник, **когда** пользователь подтверждает отключение,
   **тогда** GRAF прекращает новые sync jobs, очищает будущий неиспользованный
   кэш и делает credential envelope непригодным для чтения.
2. **Дано** отключение завершено, **когда** пользователь обновляет страницу,
   **тогда** показывается ровно «Календарь отключён от GRAF.», без инструкции
   по отзыву доступа у Яндекса.
3. **Дано** повторная отправка отключения или queued job после отключения,
   **тогда** операция идемпотентна и завершается fail-closed.

## Краевые случаи

- Яндекс возвращает `401`, `403`, `429`, HTTP 5xx или некорректный XML/ICS.
- Каталог пуст, календарь удалён или стал недоступен между выбором и sync.
- В ответе провайдера есть redirect на другой origin или private destination.
- Пользователь выбирает 21-й календарь, повторно отправляет форму или открывает
  настройки одновременно в браузере и embedded macOS.
- Синхронизация уже идёт, источник отключён или credential encryption key
  недоступен.
- В событии есть private/free-busy, all-day, recurring, cancelled или
  conference data; небезопасные поля не попадают в пользовательскую проекцию.

## Требования

### Функциональные требования

- **FR-001**: GRAF MUST показывать Яндекс Календарь доступным для подключения
  в production только после прохождения полного real E2E gate для браузера и
  embedded macOS. Изолированный development-only режим может показать форму
  локальному тестировщику, но не является certification или production rollout.
- **FR-002**: Подключение MUST использовать серверную проверку read-only CalDAV
  через пароль приложения; пароль и иные секреты MUST оставаться на сервере.
- **FR-003**: GRAF MUST проверить credentials и непустой каталог до создания или
  обновления `CalendarSource`.
- **FR-004**: Ошибка подключения MUST возвращаться только через безопасный код
  причины и MUST не раскрывать секрет, raw provider response или private event
  content.
- **FR-005**: Каталог MUST поддерживать явный выбор от 0 до 20 календарей без
  молчаливого обрезания списка.
- **FR-006**: Sync MUST использовать существующий server-owned maintenance
  worker, tenant/RLS boundary, normalizer и lifecycle. Для `caldav_yandex`
  worker MUST ставить активные источники с выбранными календарями в очередь не
  реже одного раза в пять минут; отдельный внешний scheduler и параллельное
  хранилище не добавляются.
- **FR-007**: Sync MUST читать только выбранные календари в окне от 7 дней до
  текущего момента до 12 месяцев вперёд и корректно обрабатывать pagination,
  отмены/удаления и повторный запуск. Провайдеры с полным одиночным CalDAV
  `calendar-query REPORT` MUST отклонять общие pagination- или delta-курсоры с
  `cursor_invalid`, чтобы существующий sync runner выполнял безопасный полный
  resync, а не молча терял события.
- **FR-008**: Ошибки timeout, invalid credentials, provider unavailable, rate
  limit и malformed payload MUST переводиться в существующие safe states; они
  MUST NOT блокировать ручной Record/Stop, upload или создание встречи.
- **FR-009**: Яндекс-адаптер MUST выполнять только чтение: GRAF не создаёт,
  не меняет и не удаляет события, приглашения или участников у провайдера.
- **FR-010**: Disconnect MUST быть GRAF-side only, идемпотентным и очищать
  credential, будущий неиспользованный кэш, выбор и queued work согласно
  существующему lifecycle contract.
- **FR-011**: Browser и embedded macOS MUST показывать одну серверную истину
  подключения, выбора, sync, ошибки и disconnect.
- **FR-012**: После включения провайдера MUST сохраняться честная маркировка
  pending/syncing/stale/failed/disconnected; callback или каталог сами по себе
  не являются доказательством production launch.

### Сущности

- **CalendarSource**: tenant-scoped подключение Яндекса, состояние connection,
  sync, выбор и метаданные аккаунта.
- **CalendarCredentialEnvelope**: зашифрованный серверный пароль приложения с
  fingerprint и lifecycle/tombstone состоянием.
- **ExternalCalendar**: каталог календарей Яндекса, stable provider ID,
  display label, visibility и selected flag.
- **CalendarEventSnapshot**: нормализованное read-only событие с bounded
  provider metadata и временным окном.
- **Real E2E certification receipt**: metadata-only доказательство сценариев
  browser/embedded, без credentials, event titles, participants или private
  meeting content.

## Критерии успеха

### Измеримые результаты

- **SC-001**: На выделенном тестовом аккаунте 100% сценариев connect → catalog →
  selection → sync → upcoming → reconnect → disconnect проходят в браузере и
  embedded macOS без ручного вмешательства в базу.
- **SC-002**: Все негативные сценарии из матрицы дают безопасное состояние без
  создания источника при неуспешном connect и без блокировки ручной записи.
- **SC-003**: Повторная отправка connect, selection, sync и disconnect не создаёт
  более одного активного источника для одного аккаунта Яндекса и не вызывает
  повторную запись provider-side.
- **SC-004**: 21-й выбранный календарь отклоняется с понятной ошибкой, а 20-й и
  нулевой выбор сохраняются корректно.
- **SC-005**: В production provider card Яндекс становится интерактивной только
  после receipt полного real E2E gate; до этого он остаётся «Скоро».
- **SC-006**: После disconnect ни один новый sync не читает credential, будущий
  неиспользованный cache или disconnected source, а связанный meeting-owned
  context обрабатывается существующей retention policy.
- **SC-007**: После подключения Яндекс первый sync запускается в рамках того же
  пользовательского действия, а ручная кнопка возвращает финальное состояние
  sync; активный выбранный источник обновляется автоматически с интервалом
  пять минут без повторной постановки пользователем.

## Допущения

- У пользователя Яндекса включена поддержка пароля приложения и есть право
  чтения календаря.
- OAuth для Яндекса в эту фичу не добавляется.
- Используются существующие `CalendarSource`, credential envelope, CalDAV
  adapter, worker, sync, lifecycle, UI и fixtures из Feature 168.
- Реальный тестовый аккаунт и production rollout являются отдельными gates;
  секреты не передаются в чат и не коммитятся.
- Локальная проверка может включить отдельный development-only флаг для формы;
  этот флаг не меняет production capability allowlist.
- Полный repository CI и production deploy выполняются только на финальном
  closeout после отдельного подтверждения релиза.
