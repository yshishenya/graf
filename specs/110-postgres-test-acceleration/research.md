# Research: Быстрый и достоверный PostgreSQL test pipeline

## Baseline facts

- The canonical server command is `bash apps/server/scripts/run_local_postgres_tests.sh -q`, called by `infra/scripts/ci-local.sh`.
- A fresh pre-feature collection on the reference worktree reports **1,822
  tests** in 0.62 seconds. It is a minimum historical reference, not a fixed
  final count: every full run must collect its current same-commit node-ID set
  before phase partitioning and prove that the union executes it. The previously
  stopped full run reached 47%; it is not treated as a valid duration baseline
  or a pass/fail result.
- The active path is PostgreSQL-only. No SQLite fixture, driver or fallback may return.
- The pre-feature runner created one disposable main DB and one RLS DB for an
  entire pytest invocation. The function-scoped fixture then dropped and
  recreated `public` both before and after each database test.
- The normal `client` fixture creates all 71 ORM tables, seeds organization/workspace/user/device/registry data, and allocates engines repeatedly. Static inspection identifies more than 580 direct `client` scenarios before parametrization, so the current design executes well over a thousand full schema destructive operations per full run.
- `pytest-xdist` is absent. Passing `-n` today would be incorrect because workers would share the same database and race the destructive reset.

## Decision 1 — Keep one PostgreSQL-only test architecture

**Decision**: Retain PostgreSQL 17 and one canonical runner, but give every
runner invocation its own disposable `postgres:17-alpine` Docker container on
a random loopback port. Strengthen the disposable guard for ordinary, clean,
media-role and RLS targets.

**Rationale**: It is production-faithful and completely separates developer and
production data. A temporary name must be generated by the runner and validated
before create, connect, migrate, truncate or role work; removing the generated
container is stronger and simpler cleanup than operating on a shared local
cluster. A bounded second start attempt handles transient local Docker
readiness without weakening that ownership boundary.

**Alternatives considered**:

- Restore SQLite as a fast lane — rejected: it cannot prove PostgreSQL locking, migration or RLS semantics and violates FR-001.
- Reuse a fixed local test/development database — rejected: interrupted or concurrent runs can retain or destroy unrelated state.
- Use production Compose/credentials — rejected: it violates the local safety boundary.

## Decision 2 — Separate fast client state from clean schema state

**Decision**: Introduce explicit fixture lanes:

| Lane | Intended callers | Reset semantics |
|------|------------------|-----------------|
| `postgres_seeded_database_url` | ordinary `client` API/contract tests | schema prepared once per worker; before every test, bounded table list is truncated with identity restart/cascade and the normal static seed is restored |
| `postgres_clean_database_url` | migrations, RLS and empty-schema assertions | isolated empty disposable database or the existing destructive clean-schema reset |

`client` moves only to the seeded lane. The existing clean path remains explicit instead of silently changing the meaning of migration/empty-schema tests.

**Rationale**: DDL recreation is the dominant avoidable cost. PostgreSQL `TRUNCATE` over the known metadata tables preserves schema while removing test data, including data committed through independent TestClient/application sessions. The runner-owned final trap still removes the entire run state.

**Alternatives considered**:

- Global outer transaction + rollback — rejected: the app creates independent sessions and has more than one hundred explicit commits; forcing all of them onto one savepoint can hide real commit/RLS behaviour.
- Unbounded `TRUNCATE public.*` — rejected: it is not an auditable table inventory and may accidentally include unrelated future objects.
- Create/drop a database per ordinary test — rejected: that repeats the same expensive lifecycle hundreds of times.

## Decision 3 — Parallelize only the independent fast lane

**Decision**: Add `pytest-xdist` as a development dependency. Run normal test
files using a fixed, bounded worker count and `--dist=loadfile`; give every
worker a distinct migrated database. Benchmark one, four, six and eight
workers, then use the fastest stable result as the default. An explicit
environment setting may lower the count for diagnosis. The runner caps the
setting at eight on the 10-CPU reference Docker host, preserving capacity for
PostgreSQL and the operating system.

**Rationale**: xdist documents a stable worker identity and file-level
distribution; keeping one file on one worker preserves module fixtures.
Worker-specific databases mean no worker can reset another worker's data. On
the reference host where Docker exposes 10 CPUs, completed same-collection
runs took 943.49 seconds (one), 264.47 seconds (four), 206.30 seconds (six)
and 193.78 seconds (eight), making eight the fastest verified default.

**Alternatives considered**:

- `-n auto`/logical CPU count — rejected as a default: more processes can slow a database-bound suite and makes the performance promise non-repeatable.
- Shared database with locking around each test — rejected: it serializes the expensive work and risks lock-related false failures.
- Template database per test — rejected: database cloning/connection restrictions are more expensive and complex than bounded truncate. A run-level template may be considered later only after this simpler design is measured.

## Decision 4 — Keep migration/RLS proof serial and cluster-safe

**Decision**: Mark the two modules that create fixed PostgreSQL cluster-global
roles as a strict serial lane: `test_rls_postgres_policies.py` and
`test_playback_normalization_postgres.py`. Run them outside the xdist phase
under an advisory lock in the disposable cluster. Migration and empty-schema
callers use the clean fixture, never the fast baseline fixture.

**Rationale**: PostgreSQL roles are cluster-global, so separate databases do
not isolate the fixed production-like role names. Serial execution plus an
advisory lock protects strict modules inside one run, while separate disposable
containers protect concurrent worktrees without renaming roles or weakening
the RLS proof.

**Alternatives considered**:

- Rename roles by worker — rejected: policy/migration proof intentionally validates production-like exact roles.
- Ignore/skip the RLS modules in full mode — rejected: that reduces coverage and violates FR-004/FR-005.
- Let xdist schedule them normally — rejected: role creation/drop races across workers and worktrees.

## Decision 5 — Fix context regressions truthfully

**Decision**: Before every direct invocation of `run_normalization_job` in affected tests, apply the exact worker `TenantScope` with `context_kind="worker"`. Retain the negative guard test for no context.

**Rationale**: `run_normalization_job` correctly rejects a PostgreSQL session without context. The production worker applies the same context before lookup and execution. The deletion timeout occurs only because its worker exits before reaching the deliberately blocking upload.

**Alternatives considered**:

- Disable `require_database_context` for tests — rejected: it hides the real database boundary.
- Apply request or maintenance context — rejected: neither represents the worker operation and the guard intentionally distinguishes them.
- Increase the timeout — rejected: the timeout is a symptom, not the cause.

## Decision 6 — Measure the full gate without leaking data

**Decision**: The runner reports phase wall times, worker count, collected/outcome/skip/xfail counts, cleanup result and pytest's 20 longest scenarios. The full runner proves the union of its parallel and serial lanes equals the baseline collected node-id set.

**Rationale**: This detects accidental exclusion and makes slowdowns visible while retaining only identifiers and durations; it does not persist database URLs, credentials, test payloads or meeting content.

**Alternatives considered**:

- Claim success from a focused run — rejected: focused checks are developer feedback, not release evidence.
- Save raw pytest output or test database dumps — rejected: unnecessary and can contain sensitive values.
