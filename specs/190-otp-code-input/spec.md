# Feature Specification: Единый ввод одноразового кода

**Feature Branch**: `190-otp-code-input`

**Created**: 2026-08-23

**Status**: Draft

**Input**: User description: "Унифицировать экраны ввода одноразового кода в вебе и macOS: отдельная ячейка для каждой цифры, почти квадратные ячейки, одинаковый вид и поведение во всех сценариях."

## Clarifications

### Session 2026-08-23

- Q: Какие email-code поверхности входят в инвентаризацию? → A: Вход, регистрация, приглашение, web account-link и desktop account-link.
- Q: Должен ли macOS получить отдельный нативный OTP-компонент? → A: Нет, macOS использует тот же server-rendered cabinet WebView и общий CSS/JS.
- Q: Должен ли измениться серверный параметр подтверждения? → A: Нет, все слоты собираются в существующий `code` перед отправкой.

## User Scenarios & Testing

### User Story 1 - Единый экран подтверждения кода (Priority: P1)

Пользователь входит, регистрируется, подключает email к аккаунту, объединяет аккаунты или принимает приглашение и видит один и тот же понятный экран ввода шестизначного кода в браузере и в приложении macOS.

**Why this priority**: Расхождение экранов в чувствительном auth-сценарии создаёт ощущение разных продуктов и повышает риск ошибки при подтверждении аккаунта.

**Independent Test**: Открыть каждый email-code route-flow в браузере и desktop embedded cabinet, сравнить структуру и визуальные параметры шести ячеек; результатом является одинаковый OTP-паттерн во всех поддержанных сценариях.

**Acceptance Scenarios**:

1. **Given** пользователь находится на экране подтверждения email-кода в любом поддержанном сценарии, **When** экран загружен, **Then** отображаются ровно шесть отдельных ячеек одинакового размера, ширина и высота каждой ячейки отличаются не более чем на 2 пикселя.
2. **Given** пользователь открывает один и тот же сценарий в web cabinet и embedded macOS cabinet, **When** сравнивает OTP-поле, **Then** структура, порядок, размеры, интервалы, состояния фокуса и поведение ячеек одинаковы; различаются только route action и контекстный текст сценария.
3. **Given** пользователь вводит цифру, **When** цифра принята, **Then** она отображается только в текущей ячейке, а фокус переходит в следующую свободную ячейку.

### User Story 2 - Надёжный ввод с клавиатуры и вставки (Priority: P1)

Пользователь может ввести код вручную, вставить полный код из письма или использовать автозаполнение одноразового кода, не теряя цифры и не отправляя неполный код.

**Why this priority**: Код часто копируется из письма; корректная вставка и клавиатурная навигация важнее декоративной части изменения.

**Independent Test**: Проверить ручной ввод, удаление, стрелки, Backspace, вставку смешанного текста и автозаполнение на одном экране, затем повторить smoke-проверку на web и desktop вариантах.

**Acceptance Scenarios**:

1. **Given** пустое OTP-поле, **When** пользователь вставляет строку с шестью цифрами и дополнительными символами, **Then** в ячейки попадают только первые шесть цифр в правильном порядке.
2. **Given** заполнены одна или несколько ячеек, **When** пользователь нажимает Backspace, **Then** удаляется текущая цифра или предыдущая цифра при пустой текущей ячейке, а фокус остаётся предсказуемым.
3. **Given** заполнены не все шесть ячеек, **When** пользователь нажимает «Продолжить», **Then** форма не отправляет код как завершённый и сохраняет доступное сообщение/фокус для продолжения ввода.
4. **Given** все шесть ячеек заполнены цифрами, **When** ввод завершён или сработало автозаполнение, **Then** форма отправляется не более одного раза с тем же шестизначным значением.

### User Story 3 - Доступность и адаптивность (Priority: P2)

Пользователь с клавиатурой, экранным диктором или узким окном может понять назначение поля, перейти по всем цифрам и завершить ввод без зависимости от размера экрана.

**Why this priority**: Auth-экран должен оставаться usable в embedded-окне macOS, браузере и на узких viewport, включая состояния ошибки и повторной отправки кода.

**Independent Test**: Пройти OTP-форму только клавиатурой на широком и 390px viewport, проверить доступные имена/описания ячеек, focus ring, ошибку и повторный запрос кода.

**Acceptance Scenarios**:

1. **Given** OTP-форма открыта, **When** пользователь использует Tab и Shift+Tab, **Then** порядок фокуса проходит по шести ячейкам и далее по основному действию без ловушки фокуса.
2. **Given** viewport шириной 390px или меньше, **When** экран отображается, **Then** шесть ячеек остаются отдельными, почти квадратными, не выходят за границы панели и не требуют горизонтальной прокрутки.
3. **Given** код отклонён или истёк, **When** показано состояние ошибки, **Then** ячейки сохраняют тот же размер и структуру, а ошибка доступна пользователю и не маскируется анимацией.

## Edge Cases

- Автозаполнение или вставка содержит пробелы, дефисы, буквы, emoji или более шести цифр: принимаются только цифры, максимум шесть.
- Пользователь пытается отправить форму с неполным кодом: запрос не должен считаться подтверждением и не должен отправляться повторно из-за нескольких событий input.
- Пользователь использует клавиши Backspace, Delete, стрелки, Home/End или вставляет код в середину: фокус и содержимое ячеек остаются последовательными.
- JavaScript недоступен: форма сохраняет безопасный fallback, при котором сервер получает один валидируемый параметр кода без раскрытия внутренних токенов или изменения auth-контракта.
- Экран отображается как обычная web-страница и как desktop embedded cabinet: route-specific пути сохраняются, визуальный OTP-контракт не расходится.
- Включён режим reduced motion: OTP-поведение и focus state остаются функциональными, а декоративная анимация отключается.

## Requirements

### Functional Requirements

- **FR-001**: Все экраны, которые принимают шестизначный email/одноразовый код, MUST использовать единый визуальный контракт из шести отдельных полей по одной цифре.
- **FR-002**: Единый визуальный контракт MUST применяться в login, signup, browser account-link, desktop account-link и share-invitation code flows, если flow отображает ввод кода. Эти потоки используют общий `cabinet/auth/email_code.html`; desktop surface загружает тот же server-rendered cabinet через WebView.
- **FR-003**: Каждая ячейка MUST иметь одинаковую ширину и высоту в рамках одного viewport; целевое соотношение сторон MUST быть 1:1, а допустимое отклонение MUST быть не более 2 пикселей.
- **FR-004**: Между ячейками MUST использоваться один и тот же gap, размеры шрифта, радиус, border, фон, focus ring и состояния заполненности во web и desktop embedded surface.
- **FR-005**: Ввод одной цифры MUST заполнять одну ячейку и перемещать фокус к следующей; ввод нецифровых символов MUST игнорироваться.
- **FR-006**: Вставка и системное автозаполнение MUST распределять цифры последовательно по шести ячейкам, обрезать результат до шести цифр и не создавать дубликатов.
- **FR-007**: Backspace, Delete и навигация стрелками MUST обеспечивать последовательное редактирование кода без перескока фокуса в неожиданный элемент.
- **FR-008**: При полном коде форма MUST передавать существующий серверный параметр `code` как одну строку из шести цифр и MUST запускать автосабмит не более одного раза на заполнение. Отдельные слоты не получают серверных имён; общий параметр собирается перед submit.
- **FR-009**: При неполном коде форма MUST оставаться доступной для исправления и MUST не отправлять неполное значение как подтверждение.
- **FR-010**: Каждая ячейка MUST иметь доступное имя или быть объединена с понятным доступным описанием общего поля; пользователь экранного диктора MUST понимать позицию цифры и общее назначение кода.
- **FR-011**: Компонент MUST сохранять существующие route actions, hidden auth fields, CSRF-поля, error states, resend action и back links каждого flow.
- **FR-012**: Компонент MUST быть адаптивным для desktop, browser и viewport шириной 390px без горизонтального overflow.
- **FR-013**: Компонент MUST иметь видимый keyboard focus, достаточный контраст состояний и корректное поведение при `prefers-reduced-motion: reduce`.
- **FR-014**: Визуальный и поведенческий контракт MUST быть покрыт проверками, которые отдельно подтверждают web route и desktop embedded route, а также их общую структуру. Инвентаризация должна подтверждать, что в исходниках нет второго auth-code шаблона или нативной macOS реализации.

### Key Entities

- **OTP code entry**: пользовательский шестизначный код и шесть видимых позиций его ввода; перед отправкой преобразуется в существующее поле `code`.
- **Email-code flow**: контекст login, signup, account-link или invitation, который задаёт route action и copy, но не меняет визуальный OTP-контракт.

## Success Criteria

### Measurable Outcomes

- **SC-001**: В 100% email-code flow routes, найденных инвентаризацией приложения, присутствует один и тот же набор из шести OTP-ячеек; отдельные прямоугольные code-input варианты отсутствуют.
- **SC-002**: На web и embedded macOS surfaces каждая ячейка имеет соотношение сторон 1:1 с отклонением не более 2 пикселей на широком и 390px viewport.
- **SC-003**: Ручной ввод, вставка шестизначного кода и автосабмит проходят с одним и тем же результатом в web и desktop flow без изменения серверного auth-контракта.
- **SC-004**: Контрактные и focused UI/static checks проходят для всех затронутых auth templates, CSS и JavaScript; fast repository gate не выявляет регрессий в auth-пути.

## Assumptions

- Все email-code экраны в текущем приложении используют общий server-rendered cabinet template; отдельный нативный OTP-компонент macOS не нужен.
- Серверный параметр `code` и все auth/security проверки остаются без изменений; задача касается представления и клиентского распределения цифр.
- Речь идёт о шестизначных email/одноразовых кодах, а не о промокодах, conference passcode или произвольных текстовых кодах.
- Изображение пользователя является визуальным референсом результата, а не инструкцией изменить логотип, тексты auth или security policy.

## Out of Scope

- Изменение длины, срока действия, хранения, rate-limit или серверной проверки кода.
- Переписывание login/signup/account-link маршрутов и embedded navigation policy.
- Изменение промокодов, ссылок на конференции, платежных кодов и других не-auth полей.
