## C1 — ветка несовпадающих деревьев обходит пошаговое доказательство

Место: `scripts/validate-pr-metadata.py:286–287`, размещение нового допуска
после прежнего раннего возврата в строках 263–278. Связь: FR-002/FR-003,
SC-002. Это взаимодействие с существующей веткой, а не утверждение, что сам
ранний возврат впервые добавлен F276.

При `merge_tree != head_tree` код проверяет объединение `merge_parent` с
проверенным head, затем возвращает API base. Новая проверка каждого переноса
не вызывается. Непроверенное содержимое, уже добавленное в промежуточные
перенесённые коммиты, принимается за продвижение основной ветки.

Независимое воспроизведение выполнено в одноразовом Git-репозитории с настоящими
объектами через существующие `snapshot`, `synced_rebase` и `run_trusted`:

1. Взять положительную схему 3+sync→3, API base оставить равным checked base.
2. В каждое из трёх итоговых деревьев добавить один и тот же новый
   `unreviewed.txt`, отсутствующий в исходном PR. Остальные файлы сохранить.
3. Создать три линейных коммита этих деревьев поверх checked base через
   `commit-tree`, последний указать как `merge_commit_sha`.
4. Запустить обычный trusted metadata validator с двумя одинаковыми снимками
   PR и прежним policy checkout.

Фактический результат: конечное дерево **не равно** head tree, посторонний файл
присутствует, но процесс возвращает **0**, печатает **`pr-metadata: OK`** и
создаёт **`trusted-result.json` с `result=pass`** и исходной checked base.
Это доказанный ложный допуск на уровне проверки истории/metadata; полный
производственный выпуск этим опытом не выполнялся и не заявляется.

Нужна узкая коррекция выбора ветки: история переносов после terminal sync
не должна уходить в разрешающий путь для другого вида истории при несовпадении
деревьев. Простое удаление поддержки прежнего squash недопустимо по FR-004.
Добавить отрицательную регрессию ровно на сохранённое постороннее добавление,
требуя ненулевой код и отсутствие PASS-артефакта, затем повторить прежние
положительные случаи squash, продвижения target, rebase и merge. Нынешний
`final-tree` заменяет дерево деревом базы, то есть проверяет потерю содержимого;
он не проверяет описанное сохранение постороннего добавления.

## Остальная проверенная область

- При достижении новой ветки линейность и полнота обоих диапазонов проверяются
  через `predecessor`, исходный диапазон ограничен count+1, синхронизация и каждый
  перенос восстанавливаются через `merge-tree`. Результаты сверяются по порядку;
  ошибка Git приводит к отказу через существующий обработчик.
- Исходные тесты не изменены: добавлены fixture, два положительных случая и
  двенадцать отрицательных. Есть проверка refs, HEAD, байтов индекса, рабочего
  скрипта и отсутствия tracked diff. Код не добавляет checkout/ref/index writes;
  создание недостижимых tree/blob objects разрешено планом.
- Общие проверки `validate-pr-checks.py` по точному источнику, базе, актуальной
  попытке, артефактам и повторному снимку PR не изменены. Это не устраняет C1:
  достоверная привязка CI к исходному PR сама по себе не доказывает содержимое
  пропущенных здесь промежуточных переносов.
- Других подтверждённых блокеров в рассмотренных изменениях не найдено.
