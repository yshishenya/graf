## Первичная оценка до уточнения

**CHK007 пока не подтверждён: 6 отмечено / 1 открыто.** Направление требования правильное: отдельно 250 мс подготовки session и 250 мс записи, общие функции, отсутствие очереди/повторов, отказ измерения без отказа HTML, сохранение внешней отмены. Ровно три caller общего writer — посещение страницы, шаг регистрации, доставка установщика; соседние сценарии явно включены контрактом.

До реализации необходимо уточнить две границы:

1. **Неопределённый commit.** Таймаут во время commit не доказывает отсутствия записи: БД могла завершить commit до потери/отмены ответа. Слова «по таймауту запись пропускается» должны означать отсутствие подтверждённого результата, а не гарантированное отсутствие строки. Нужны явные «результат неизвестен; не повторять» и сохранение этого различия в журнале/приёмке. Требование HTML 200 может сохраняться без ложного утверждения о нулевой записи.
2. **Полная область подготовки и очистки.** Сейчас `async with sessionmaker()` начинается до try/apply_tenant_context. После ошибки выход из context manager может ожидать rollback/close. Нужно явно включить получение/вход session и установку контекста в бюджет подготовки и исключить неограниченное ожидание очистки на пути ответа. Неудавшаяся/отменённая session не должна вновь использоваться downstream. Нельзя размещать timeout context вокруг `yield` DB dependency: это ограничило бы весь обработчик, а не подготовку измерения. Внешняя отмена запроса должна распространяться из подготовки, writer и очистки; локальный timeout не должен поглотить её. Для задач с некооперативной отменой нельзя утверждать строгую стеновую задержку только по asyncio timeout без проверки поведения драйвера.

Эти вопросы переданы основному исполнителю до начала реализации. Они не требуют новой очереди или фонового повтора и не разрешают обойти правовой шлюз. Граница очистки должна сохранять ресурсную дисциплину и не оборачивать всю бизнес-транзакцию регистрации в общий timeout; writer уже вызывается после основного результата и его отказ не должен отменить успешное действие пользователя.

## Разделение отчёта

FR-008 и контракт достаточно определённо требуют отдельные итоги страниц и действий, unknown отдельно. Каталог страниц должен быть явным, действия — существующими регистрационными поверхностями и доставкой установщика; неизвестное значение не подхватывается как page. Канонические external и visits>=3 фильтры до SUM и одинаковое окно сохраняются для каждого итога. Ни общий SUM, ни action count не являются людьми/сессиями/покупками.

На момент чтения SQL ещё прежний, а изменяемая учебная проверка уже ожидает pages/actions/unknown; это незавершённая подготовка, не новый PASS реализации. Тесты не запускались. Нужны отдельные сценарии для малого бакета, technical traffic, page, signup step, installer и неизвестной поверхности, чтобы их нельзя было смешать общей суммой.

## Требуемые проверки будущей реализации

Зависшие подготовка/execute/commit проверяются раздельно; соседние page/registration/installer caller сохраняют результат; выключение и отзыв основания не создают записи; отмена извне не превращается в успешное «пропущено». Нужно проверять освобождение session и отсутствие retry/фоновой записи, неизвестный исход commit и отсутствие использования сломанной session. Для задержки — разумная тестовая погрешность вокруг двух отдельных бюджетов, без обещания общего ответа за 250 мс: подготовка и writer уже допускают суммарно 500 мс плюс остальной путь. Offer-каталог и другие запросы не объявляются автоматически ограниченными этим узким требованием.

## Повторная проверка уточнённых требований

До реализации повторно прочитаны текущий FR-008 и весь `contracts/public-measurement.md`. Оба прежних пробела устранены:

- Таймаут commit прямо обозначает неизвестный результат; повтор запрещён, неизвестность не представляется гарантированным отсутствием строки.
- Подготовка включает создание/вход session и tenant context **до yield**. Timeout прямо не охватывает yield/обработчик страницы. Закрытие/rollback имеет отдельный бюджет 250 мс; session не используется повторно; внешняя отмена не поглощается.

Каждый бюджет отдельный: 250 мс подготовки, 250 мс execute+commit и 250 мс очистки. Это не обещание общего ответа за 250 мс или за 500 мс: очистка и прочая логика имеют собственное время. Основной исполнитель передал подтверждение пользователем бюджетов подготовки/записи. Условие ограниченной очистки также прямо записано в FR-008/контракте. Проверка действительного поведения отмены/драйвера и освобождения соединения остаётся обязательством реализации, а не следует автоматически из синтаксиса timeout.

Предложенный исполнителем способ — создать AsyncSession без открытия соединения, ограничить установку контекста, оставить yield вне timeout и отдельно ограничить close; в общем writer ограничить execute+commit и не перехватывать CancelledError — совместим с уточнённым требованием. Это оценка направления, не независимый review ещё не написанного кода. Нужно проверить именно все три caller, внешнюю отмену, неизвестный commit и отсутствие неограниченного финального ожидания/повторного использования session. При отказе измерения результаты основной регистрации/скачивания не отменяются.

Разделение страниц/действий/unknown остаётся достаточным; текущая незавершённая SQL/учебная правка не объявляется пройденной этим requirements PASS.
