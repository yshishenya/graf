## 1. Метод и ограничения

Проверены проектные правила, конституция, базовое описание продукта, текущий статус, существующая спецификация корпоративной админки, маршруты приложения, модули доступа, обработки, подписок, тарифов, промокодов, диагностики, событий и связанных функций.

Наличие модуля/маршрута подтверждает основу в текущем коде, а не включённость на production. Живые серверы, реальные встречи, реквизиты и записи пользователей не открывались. Проверки браузера и исполнения бизнес-операций относятся к последующей реализации.

Исторические документы могут описывать ещё не принятые или уже изменившиеся этапы; при выводах использованы текущие правила и точки кода. Временная линия User UI при повторной обработке не меняется предлагаемой административной детализацией.

## 4. Важные выводы повторного анализа

1. Глобальная консоль не является снятием workspace-фильтра в существующем /admin: нужны отдельная административная личность, проверка полномочий и журнал.
2. Право суперадминистратора на содержимое всех пользователей — явное требование, а не временный обход. Поддержке аналогичное право автоматически не выдаётся.
3. Новый каталог должен быть связан со всем расчётом доступа. Добавить строку с произвольным кодом сейчас недостаточно: проверяющие функции знают конечный набор тарифов.
4. Личная платёжная ответственность и корпоративное членство различаются. Простое сложение оплат по всем доступным пространствам искажает таблицу пользователей.
5. Ручной подарок — новый источник доступа. Нельзя обозначить его «оплачено» и потерять происхождение.
6. Подарок изменяет не только дату доступности, но и момент будущего продления. Уже отправленный платёж требует сверки до несовместимого изменения.
7. Хранение в существующей модели использует общий предел пакета; новая форма не должна ошибочно прибавлять его повторно.
8. Пауза промокода не отменяет уже оформленный счёт, неизвестный исход не освобождает резерв.
9. Статистика должна измерять полезные действия и стадии, а не число активных записей membership.
10. Диагностический снимок не равен полной истории. Необходимы ограниченная история и устойчивые связи, в том числе до появления серверной встречи.
11. Данные, которые раньше не собирались, нельзя восстановить задним числом или считать отсутствием ошибок.
12. Полные ИИ-журналы и обычная телеметрия подчиняются разным действующим правилам.

## 5. Решения, уточнившие предыдущую концепцию

| Ранее возможная неоднозначность | Однозначное решение комплекта |
|---|---|
| Нужна ли санкция владельца на каждую встречу | Нет для суперадминистратора; основание и аудит обязательны |
| Может ли любой администратор назначать других | Только суперадминистратор |
| Все промо-типы сразу | Процентная скидка на один платёж и подарок дней входят; остальные типы отдельно |
| Смена цены затрагивает всех | По умолчанию только новые покупки; существующие подписки через отдельный переход |
| Немедленный перерасчёт основного тарифа | Не входит; переход со следующего периода либо бесплатное административное повышение |
| Подарочные дни поверх оплаченных | Добавляются после предоставленного непрерывного периода, с согласованным продлением |
| «Дополнительные 20 ГБ» | Пакет общего предела согласно текущей модели; индивидуальная прибавка отдельно |
| Полная телеметрия всегда | Минимальная операционная диагностика отдельно от необязательной аналитики |
| Массовые кнопки | Ограниченный список; единичное удаление/перезапуск доступны, массовое содержимое/удаление не входят |
| Полный текст удалённой встречи | Только фактически сохранённая диагностическая копия отдельным режимом, без восстановления встречи |

## 7. Последовательность реализации

Это рекомендуемая декомпозиция для технического плана, не tasks.md и не зарегистрированные задачи.

1. **Основание доступа:** административная личность, второй фактор, роли/сессии, аудит, проверка глобальных разрешений; не менять текущие пользовательские роли.
2. **Рабочий разбор:** глобальные пользователи/пространства/встречи, полный просмотр и скачивание, безопасный повтор/удаление, лента фактов.
3. **Единый расчёт прав и каталог:** версия тарифа, периодические предложения, миграция текущих прав и новые коды; сначала целостность, затем формы.
4. **Подписки и деньги:** таблица оплат, назначения/компенсации, индивидуальные правила, дата продления, сверка неопределённых операций.
5. **Акции:** версия акции, коды, резервы/бюджет, подарок, запуск/пауза и результаты.
6. **Диагностика и смежные функции:** индекс связей, снимки, обращения, устройства, календарь/общие ссылки/объединение/рефералы.
7. **Метрики и эксплуатация:** каталог событий, охват, расчёт агрегатов, оповещения, зависимости и настройки.
8. **Завершение:** серверное разграничение, финансовые гонки, миграции, браузерная доступность, нагрузка и совместимость старых клиентов.

Для начала технического планирования не требуется додумывать ключевые продуктовые правила: исходные решения записаны. Разработчик обязан конкретизировать схему данных, контракты и атомарность, миграционный порядок и точки проверки прав, а не произвольно менять поведение.

До запуска кода действует полный проектный путь: зарегистрированная фича → specify/clarify → plan → reviewer-owned checklist → tasks → analyze → taskstoissues при разрешённой реализации → implement → converge → проверки/release. Исходный продуктовый комплект дополнен техническими артефактами зарегистрированной фичи; проверки исполнения относятся к реализации.
