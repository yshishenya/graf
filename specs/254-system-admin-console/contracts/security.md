# Граница системного доступа

## Процесс, вход и полномочия

Консоль — отдельный ASGI entrypoint `system_admin/app.py` и Docker service из того же образа/репозитория, на **отдельном origin**, заданном операторским `SYSTEM_ADMIN_PUBLIC_ORIGIN` (например, `https://system-admin.rec.2brain.pro`; это проектный адрес, не утверждение о существующем DNS). Только этот virtual host обслуживает `/system-admin` и `/api/system-admin/v1`. Продуктовый host не проксирует admin API и не получает её credential; необязательная ссылка `/system-admin` на продуктовом host лишь перенаправляет на фиксированный origin без токенов/пользовательских параметров. Обычный `main.py` не получает системный DB credential.

Cookie `__Host-graf_system_session`: Secure, HttpOnly, SameSite=Strict, Path=/, без Domain; только console host. CORS для product origin и credentialed cross-origin отсутствует. Все изменения требуют точного Origin console + CSRF; отклоняются missing/null/чужой Origin, кроме явно описанного server-side CLI. Login/activation также защищены login CSRF. CSP frame-ancestors none. При входе одновременно в продукт и консоль product scripts не читают административные ответы, product requests не несут admin cookie. Обычный API не принимает admin auth, консоль не принимает owner cookie/Bearer/device/legacy auth. Предавторизационная cookie имеет отдельное имя и не открывает прикладной API.

Пароль: 14–128 символов без обрезания/преобразования, hash `hashlib.scrypt` с отдельной 16-byte salt, N=2^17,r=8,p=1, maxmem с запасом; ограничить число параллельных вычислений двумя на процесс, очередь <=10, перегрузка 429. Измерить на целевом CPU, при несовместимости параметров не ослаблять молча. TOTP RFC6238 SHA1, 6 цифр/30s, окно ±1, последний использованный counter обновляется атомарно и не принимается снова. Векторные тесты RFC обязательны. Генерация secrets через `secrets`; TOTP seed шифруется существующей cryptography AES-GCM отдельным операторским ключом с key_id, nonce, AAD principal_id; это credential, не шифрование транскрипта. Ключ отдельно от БД и резервных копий БД. 10 recovery codes, каждый >=128 bit случайности, hash at rest, показ один раз; при использовании обязательная повторная настройка MFA до новой полной сессии, старые sessions отзываются.

Invitation/reset/preauth: обязательные issued_auth_version/credential_version и допустимое состояние principal, hashes tokens, одноразовое потребление под блокировкой; invitation 24 h, password reset 15 min, preauth 5 min; повтор отправки отзывает предыдущий token. Email подтверждён владением приглашением/reset link, но reset не снимает MFA. Rate limits согласно UI, плюс общий серверный предел; распределённые counters в PostgreSQL без нового Redis. Логины canonicalized тем же email normalizer, не произвольным удалением `+suffix`.

Bootstrap CLI `apps/server/scripts/manage_system_admin.py`: только на сервере, без публичного маршрута; init допускается только при отсутствии активных principals, под singleton lock; секреты вводятся через stdin/getpass, не CLI args/logs. Recovery требует операторского доступа к среде, явной цели/причины, сохраняет аудит, повышает auth_version и отзывает sessions; сам не создаёт невидимый бессрочный обход MFA. При потере всех MFA recovery создаёт одноразовое приглашение повторного enrolment, затем обычный вход. Выдача секретной ссылки только оператору в закрытом терминале, не в committed evidence.

Матрица фиксированных ролей из spec нормативна. Permission allowlist: `users.read`, `meetings.metadata`, `content.read`, `audio.listen`, `audio.download`, `content.export`, `diagnostics.content`, `processing.read`, `processing.reprocess`, `billing.read`, `billing.manage`, `catalog.read`, `catalog.draft`, `catalog.publish`, `promotions.read`, `promotions.draft`, `promotions.manage`, `promotions.publish`, `support.read`, `support.manage`, `devices.read`, `sessions.manage`, `integrations.read`, `integrations.manage`, `operations.read`, `operations.manage`, `settings.read`, `settings.manage`, `analytics.read`, `audit.read`, `exports.table`, `deletion.manage`, `fair_use.manage`, `queue.manage`, `notifications.retry`, `admins.manage`. Superadmin получает весь список; только он admins.manage/deletion.manage/fair_use.manage/queue.manage. Прямое назначение неизвестного разрешения отвергается.

Финансовый users.read не раскрывает devices/meetings/login/incident секции: это ограничение роли применяется к каждой проекции и search result.

System admin: users/metadata/processing/devices/support/integrations/operations read, processing.reprocess, support.manage, operations.manage, integrations.manage, notifications.retry, settings.read/manage. Support: users/metadata/processing/devices/support/integrations read и support.manage. Billing manager: users.read только финансовой проекции, billing.read, catalog.read/draft, promotions.read/draft. Analyst: analytics.read. Auditor: audit.read. `exports.table` выдаётся ролям superadmin/system admin/billing manager/analyst/auditor только для уже доступных им наборов. Support без экспортов. Временные grants: system admin/support — только конкретные content.read/audio.listen/audio.download/content.export/diagnostics.content на перечисленные встречи; billing manager — billing.manage/catalog.publish/promotions.manage/promotions.publish на конкретные объекты/проектируемый новый объект, без произвольного глобального wildcard. Ни один grant не выдаёт admins.manage/deletion.manage/fair_use.manage/queue.manage. Изменение собственной роли/grants запрещено; superadmin не может повысить себя вторым назначением.

## PostgreSQL и RLS

Новая схема `system_control` исключает секреты из существующих public default grants. Роль `twobrain_rec_system` — NOSUPERUSER/NOBYPASSRLS/NOINHERIT, без членств, не владелец таблиц. Отдельный engine и новая session на запрос; смешивание с TenantContext запрещено. Настройки контекста задаются транзакционно и восстанавливаются через существующий after_begin pattern; после возврата в pool утечки невозможны. Проверяется настоящий session_user, не только app.* GUC.

`SystemDatabaseContext` несёт admin_session_id, actor_id, permission, reason/operation_id и target. RLS helper проверяет действующую session/assignment в system_control, scope и срок; строка permission сама ничего не разрешает. SECURITY DEFINER helper: отдельный ограниченный owner, фиксированный search_path, schema-qualified таблицы, PUBLIC EXECUTE revoked. User/app/media/maintenance не могут читать credentials/system tables или SET ROLE system.

| Группа таблиц | Разрешённое системное действие |
|---|---|
| user/workspace/membership/device | SELECT безопасных проекций; изменения только конкретным service/command |
| meetings/revisions/processing/media metadata | metadata SELECT; UPDATE только target operation |
| transcript/outcomes/GenerationCall | content permission + case context; financial analyst не получает SELECT |
| OAuth/credentials/payment tokens | Нет SELECT в console; integration service выполняет действие по ID без возврата секрета |
| invoice/payment/refund/paid grants | SELECT billing; запись финансового подтверждения только текущим billing worker/reconciliation |
| catalog/promo/admin grants | Разрешённые действия через narrow policies и domain locks |
| audit_events | INSERT/SELECT по праву, UPDATE/DELETE runtime denied |

Если текущая таблица смешивает metadata и secret/content, использовать column grants/представление с безопасным набором, а не SELECT * с последующей маскировкой. Полная конкретная таблица grants в миграции тестируется по catalog БД. Нельзя расширять `rec_maintenance_allowed` на новую роль.

Консоль записывает durable operation; существующий worker получает operation_id через контролируемый dispatcher, проверяет её фактический actor/scope/состояние и выполняет разрешённый доменный тип. Он не принимает произвольную команду из HTTP, SQL/URL/role из payload. Начало эффекта атомарно отмечается с проверкой актуальных прав; если отзыв уже зафиксирован, новый эффект не начинается. После отправки провайдеру worker завершает обязательную сверку независимо от дальнейшего истечения роли. Maintenance credential не устанавливается в console.

## Контент и аудит

Чтение требует записи audit до выдачи первого байта. Аудит на отдельном append-only пути сохраняет также отказы, не откатываясь вместе с отвергнутой доменной транзакцией. Для мутации audit intent + command фиксируются вместе; outcome дописывается новым событием. Не включать текст/сырой reason с содержимым в обычные логи; причина хранится в защищённом поле аудита, UI предупреждает не вставлять содержимое.

Media ticket срок 60 s, связан с session/purpose/object/revision, не standalone bearer; Range продолжает тот же read session. Recheck перед каждым Range и не реже 1 s/1 MiB при stream; завершить выдачу после отзыва/удаления, уже отправленные байты не отзываются. Никаких публичных redirect на хранилище. CSP default-src self, frame-ancestors none, Referrer-Policy no-referrer, Cache-Control no-store; запрет third-party scripts/session replay. Transcript/AI выводится как текст, preview Markdown через существующий безопасный renderer без raw HTML; URL не запускает административные команды.

Существующие actor_user_id FK не принимают system UUID. В egress/deletion/processing добавляется nullable system_operation_id, ordinary actor остаётся null для system action, system audit сохраняет точного инициатора. Проверка прав перед egress заново: существующий short circuit `access.state=admin` не может авторизовать новый system режим.

Новая политика retention применяется перспективно и сохраняет версию/expiry на записи; ранее установленные сроки не сокращаются молча. Product analytics retention, financial/audit/retained сроки не редактируются этой формой. Контакты/получатели выбираются по operator-configured ID; добавление внешнего получателя остаётся операторским процессом. Settings.manage у system admin ограничен строками его роли; server проверяет key-level policy, superadmin-only настройки не выдаются temporary grant.

Пауза закрывает admission **новых** внешних работ конкретной очереди до expires_at UTC, не завершает активные jobs и не блокирует ingest/capture/локальную запись. Проверка gate атомарна с dispatch claim; уже claimed jobs завершаются. Awaiting задачи показывают причину/ожидаемое снятие, максимум60min, продление — новая step-up операция. Автоматическое снятие по expires_at не зависит от браузера/прав инициатора; при рестарте expired pause не применяется. Нельзя приостановить audit, deletion, payment reconciliation или сохранение принятого аудио.

Секреты, auth TTL/rate limits, DB pools, backup destinations, provider endpoints и глобальная ИИ-конфигурация — только отображение источника/версии без значений секретов; изменение через существующий операторский процесс. Квоты/права — через entitlement/catalog commands. Автоматическое включение продуктовой аналитики запрещено.

## Уточнения после независимого исследования границ

Все reset/revoke/block/credential replacement/emergency recovery повышают auth_version под principal lock, отзывают sessions и **все ранее выданные challenges**, включая preauth/enrolment/reset/invitation, и инвалидируют предыдущий recovery-code набор. Новый challenge выпускается только на новую версию. Consume проверяет версию/статус повторно под тем же lock. У приглашения источник роли — актуальное assignment, не сохранённый текст приглашения. Recovery-code выдаёт только challenge `mfa_enrolment_required`: разрешены enrolment begin/confirm и logout, никакие прикладные API. После подтверждения нового TOTP выдаётся новый набор recovery codes и полная session, старый seed/codes недействительны.

Защита последнего superadmin относится к **назначенному бессрочному действующему principal**, не запрещает временную приостановку его входа для восстановления credential. Служебное recovery состояние `recovery_pending` сохраняет assignment, но не прикладные права. Единственный superadmin может закончить credential recovery через ограниченный challenge или операторскую процедуру; эта процедура не выдаёт session без MFA. Изменением роли/status нельзя удалить последний assignment, даже если он recovery_pending. Bootstrap не считает recovery_pending отсутствием администратора.

Ротация TOTP encryption key: оператор добавляет новый key_id в secret store, новые credentials шифруются новым ключом; существующие переоборачиваются checkpoint-процедурой под version check; старый ключ хранится до счётчика old-key refs=0 и проверенного restore. Недоступный ключ блокирует соответствующий вход и вызывает операционное оповещение, не сбрасывает MFA. Старые backup требуют соответствующего ключа при restore; срок хранения ключа не короче срока этих backup.

**Обязательная RLS-граница поверх существующих PUBLIC policies.** На каждой public relation, к которой system role имеет SELECT/DML, миграция добавляет `AS RESTRICTIVE TO twobrain_rec_system` policy с mandatory system authority для каждого разрешённого действия. Существующие permissive TO PUBLIC политики могут OR-объединяться, но restrictive gate применяется AND. Использовать подходящие USING/WITH CHECK; никакая system-readable таблица не остаётся без этой границы. Вариант изменения всех старых policies TO прежние роли не используется в этой фиче. Проверить system DB login с поддельными request/worker/auth_bootstrap/maintenance GUC, без session и metadata-only: ни content read, ни write не проходит. Без permissive разрешающей политики SELECT тоже не разрешается; additive system permissive + restrictive пара работают вместе.

В `system_control` auth primitives до полной session доступны только через отдельные узкие auth-функции/credential grants для system process, не через общий data access helper, который требует session. Они не читают public content или operations и не возвращают credential через HTTP. Ordinary DB roles не получают их EXECUTE. Системные business queries вне этих auth primitives всегда требуют current authority.

**Доверенный worker канал.** Не выдавать workers SELECT на system_control. Ограниченный NOLOGIN owner функций получает только необходимые SELECT/UPDATE на operations/targets/assignments/sessions, column SELECT/UPDATE-lock на principals.id/status/auth_version (без password_hash), и INSERT audit, без credential доступа. SECURITY DEFINER функции `claim_system_operation(operation_id,target_id)`, `continue_system_operation(operation_id,target_id,attempt_fence,action)`, `record_system_operation_result(...)` имеют fixed search_path, qualified names, PUBLIC EXECUTE revoked. EXECUTE только `twobrain_rec_maintenance`, проверяется session_user и допустимый worker/command тип; app/media/system web role не могут самостоятельно изображать worker claim. Возврат содержит только проверенный typed command, точную цель, domain_ref/fence и safe параметры. Платёжный adapter/существующий worker выполняет доменную работу с его штатными правами, не с admin credential.

Claim берёт principal row lock (такой же, как revoke), затем конкретный operation_target и доменные locks в порядке data-model; проверяет актуальную session/assignment и expected versions. До фактического старта атомарно фиксируются `effect_started_at, authorized_permission, authorized_target, allowed_continuation_actions, domain_ref, attempt_fence`. Для денежных send это связано с durable dispatch claim; для локальных DB effects запись и effect в одной транзакции. Возврат/истечение роли до этой фиксации запрещает start. Неизменяемое разрешение продолжения относится только к уже начатому target, а не всему batch.

Continuation не зависит от старой browser session: helper проверяет настоящий worker login, durable effect-start, точные domain_ref/fence/type и разрешённое действие (`observe`, `reconcile`, `finalize`, `purge` по виду команды). Нельзя менять цель, стартовать новый target или новый внешней эффект под видом continuation. Restart использует тот же доменный ключ, stale fence rejected; результат дописывается идемпотентно. Если storage target не начат, revoke блокирует его, даже когда другой target batch уже исполняется. Пользовательский GUC или forwarded actor ID не создаёт continuation authority.

## Плановые действия

Обычная queued команда требует текущей browser session до старта. Для явного запланированного запуска акции/тарифа и подтверждённого будущего перехода при commit создаётся `scheduled_approval` с actor, authorizing_permission, источником полномочия base assignment либо grant_id/version, assignment_id/version, command/target/parameters hash, execute_at, approval_time и MFA proof time. Это отдельный тип полномочия на конкретное будущее действие, не продолжение уже отправленного эффекта. Natural session expiry не отменяет расписание. В момент запуска helper под principal lock проверяет active principal, действующее неизменённое assignment и все текущие domain/version/consent условия, exact scheduled approval и актуальное permission/scope. Для временного grant проверяются его ID/version, срок и отсутствие отзыва; execute_at должен быть строго раньше grant.expires_at, expiry/revoke/replacement grant отменяет pending approval. После пропущенного срока нельзя исполнить действие на истёкшем grant; revoked/blocked/security-reset отменяет approval, а не обходит запрет. Никакого изменения параметров/цели без нового preview/approval. Worker получает этот exact scheduled target через тот же narrow claim helper, не через пользовательский GUC. Если контекст/цена/согласие изменились, состояние `needs_review`, новый preview обязателен. После недоступности scheduler действие выполняется один раз не раньше execute_at, только если окно акции/предложения ещё открыто и условия актуальны; иначе expired/needs_review.
