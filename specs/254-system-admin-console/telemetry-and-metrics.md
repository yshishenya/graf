# Диагностика приложения и статистика

Нормативное приложение к [спецификации](spec.md), требования FR-061–FR-070, FR-075, FR-079, FR-087–FR-090. Описывает целевой сбор, а не утверждает, что такие данные уже собираются у всех пользователей.

## 1. Четыре отдельных потока

| Поток | Назначение | Содержимое | Получатель | Условие |
|---|---|---|---|---|
| Операционная диагностика | Исправность записи, загрузки, обработки | Только разрешённые технические сведения | Управляемая установка GRAF | Явно опубликованная политика технической диагностики; без подключения нового внешнего поставщика |
| Продуктовые события | Использование, активация, возврат | Событие действия без текста встречи | Внутренний аналитический контур GRAF | Отдельное разрешение на необязательную аналитику; отказ не блокирует запись |
| Аудит | Доказуемость административного доступа/изменений | Кто/что/когда/результат/безопасные связи | Управляемое хранилище аудита | Обязателен для административной операции; не выключается обычной настройкой аналитики |
| Журналы ИИ с содержимым | Полная отладка генерации | Канонический текст, запрос, ответ, проверка | Существующие Generation Call, Langfuse, Temporal по действующим границам | Существующая операторская политика, отдельное право просмотра; без расширения внешних назначений |

Отключение продуктовой аналитики не удаляет финансовые факты и обязательный аудит. Наличие права читать расшифровку не даёт права передавать её внешнему аналитическому поставщику или использовать для обучения.

Внешняя аналитика, если позднее запускается, сохраняет отдельные существующие проверки разрешения, получателя, региона, состава данных и удаления. Этот комплект не разрешает включить её автоматически.

## 2. Обязательная оболочка события

Каждое новое техническое событие включает:

- уникальную идентичность события и версию схемы;
- тип события и источник: приложение / веб / сервер / подтверждённое наблюдение провайдера;
- время события на источнике и время получения сервером;
- номер последовательности и идентичность запуска для клиентских событий;
- категорию среды: production / dev / test и признак служебного трафика;
- версию приложения/сервера, если известна;
- доступные внутренние связи с пользователем, устройством, локальной записью, загрузкой, встречей и попыткой;
- результат: началось / завершено / отказ / ошибка / неизвестный исход;
- безопасный код причины и длительность, если она измерена;
- категорию хранения и версию применённой политики сбора.

До входа нет серверного пользователя; до загрузки нет серверной встречи. Эти поля остаются отсутствующими, а не заполняются вымышленным значением. После подтверждённой связи локальная история привязывается через разрешённый внутренний индекс, не через email в аналитическом событии.

Длительность на устройстве измеряется устойчивым к переводу часов счётчиком. Расхождение календарного времени не меняет порядок событий одного запуска. Точные времена провайдера, если их нет, не вычисляются из времени нашего опроса.

Не следует помещать внутренние ID пользователей/встреч в неограниченные метки инфраструктурных графиков. Индивидуальный поиск выполняется по защищённому индексу, агрегаты используют ограниченные категории.

Сервер устанавливает личность/устройство по действующей авторизации и проверяет принадлежность каждой присланной связи. Идентификатор в теле события не является доказательством владения. До входа допустим только несвязанный ограниченный поток установки без чтения/изменения данных аккаунта; связывание требует подтверждённого входа. Подмена автора, пересылка событий другой встречи и повтор события из другой среды отклоняются.

Клиентские события — утверждения клиента, а не финансовая или серверная истина. Только авторитетное серверное состояние подтверждает оплату, тарифные права, сохранение объекта, публикацию и удаление. Ложное сообщение клиента не меняет эти состояния и не попадает в соответствующий подтверждённый показатель. Даже полученное событие видимого индикатора не заменяет проверку реального интерфейса записи.

## 4. Какие сведения не собирать

В обычных событиях и аудите запрещены: текст расшифровки/итогов, аудио, содержимое сообщений, названия и описания календарных событий, произвольные имена файлов и локальные пути, адреса встреч с параметрами, секреты входа, заголовки авторизации, исходные промокоды, реквизиты карты, буфер обмена, нажатия клавиш, снимки экрана и список всех приложений.

Для поддержки email хранится в карточке пользователя, а не размножается в каждом событии. Доступ к связанному пользователю проверяется при раскрытии детализации. Обезличивание не означает отсутствие риска повторного связывания; права и сроки применяются и к псевдонимным идентификаторам.

Исключение для полного канонического текста в существующих журналах ИИ сохраняется по конституции. Это не разрешение автоматически прикладывать туда другие секреты исполнения или исходное аудио.

## 5. Надёжность доставки и пределы

Исходные ограничения первого выпуска:

- обычная клиентская очередь: максимум 10 МБ, 10 000 событий или 7 суток — удаление по первому достигнутому пределу;
- одно событие: не более 16 КБ; пакет передачи: не более 256 КБ;
- показатели качества/ресурсов: не чаще раза в минуту, кроме смены состояния и терминальной ошибки;
- на запись: максимум 500 детальных обычных событий; дальнейшие повторы суммируются по коду;
- расширенный режим: максимум 24 часа, только выбранное устройство/запись, автоматическое выключение и видимость пользователю; без новых классов содержимого;
- отправка асинхронная с ограниченным отложенным повтором; ручная отправка отчёта пользователя имеет приоритет над периодическими показателями;
- при переполнении первыми удаляются повторяющиеся низкоприоритетные образцы; число отброшенных событий и категорий показывается после восстановления.

Начальная проверяемая нагрузочная цель клиента: не более 20 МБ дополнительной памяти на диагностическую подсистему, средний дополнительный CPU не более 1 процентного пункта на эталонной 60-минутной записи, отсутствие добавленного синхронного ожидания сети в пути записи. Метод сравнения и аппаратный профиль фиксируются до реализации.

Веб-аналитика не повторяет отправку при каждом перерисовывании. Просмотр результата — одно событие на пользователя/встречу/ревизию в пределах сеанса просмотра 30 минут. Серверные деньги и переходы обработки учитываются по своей устойчивой идентичности, не по клиентским кликам.

## 6. Каталог метрик

Общие правила:

- интервал отчёта полуоткрытый: начало включено, конец исключён;
- зона отчёта выбирается явно; по умолчанию Europe/Moscow, хранение исходного времени не переписывается;
- уникальность пользователя соответствует подтверждённой продуктовой личности с учётом связи объединённых аккаунтов;
- тестовый/служебный/административный трафик исключается по умолчанию и включается только явным фильтром;
- исключение неавторизованной аналитики отражается охватом; зарегистрированный аккаунт не считается активным без события;
- статистика числа встреч не удваивается при повторной обработке;
- для p50/p95 применяется ближайший ранг в отсортированном наборе; при менее 20 наблюдениях p95 подписывается «малая выборка»;
- отсутствующее значение не участвует как ноль; показываются число известных и число неизвестных;
- сегодняшние и ещё не завершившие окно наблюдения когорты обозначены предварительными.

| M27 | Конверсия акции в оплату | Уникальные плательщики с хотя бы одной подтверждённой оплатой по счетам этой когорты / уникальные плательщики с созданным допустимым счётом этой когорты; когорта задаётся временем создания счёта в выбранном периоде, окно сверки 72 часа; поздние подтверждения вносят версионированное исправление, не теряются; подарки и число платежей отдельно, две оплаты одного человека не дают 200% |
| M28 | Результат после акции | Первая подтверждённая покупка без скидки в течение 30 дней после льготы / получатели льготы с полным окном; не доказательство причинности |
| M29 | Поддержка | Время до назначения ответственного, первого действия разбора и решения; ожидание пользователя/зависимости отдельно |
| M30 | Удаление | Подтверждённые обязательные классы очистки / подлежащие очистке классы с наступившим сроком; retained observability не ошибка очистки |

Детализация по версии приложения, ОС, типу поддерживаемой цели, тарифу/версии, длительности, ручному/автоматическому запуску, этапу и коду проблемы. Текст встречи не является аналитическим измерением.

У аналитика нет доступа к спискам людей через детализацию. Для его отчётов группы меньше 5 пользователей скрываются/объединяются; режим системной отладки суперадминистратора сохраняет разрешённую индивидуальную детализацию.

## 7. Правила хранения новых данных

| Данные | Срок первого выпуска | Уточнение |
|---|---|---|
| Обычные детальные технические события | 30 дней | Затем удаление деталей, сохранение разрешённых агрегатов |
| Расширенный технический пакет | 14 дней | Режим сбора максимум 24 часа, срок хранения пакета отдельный |
| Снимки и техническая история обращения | 180 дней после закрытия | Для открытого обращения максимум 365 дней без явного пересмотра необходимости; основное описание не должно содержать встречу |
| Исходные продуктовые события | 90 дней | Согласовано с существующим направлением хранения аналитики |
| Продуктовые агрегаты | 13 месяцев | Без обратного списка пользователей; отдельный контроль малых групп |
| Административный аудит | 365 дней минимум | Увеличивается применимой политикой; нельзя удалить через обычную панель |
| Сформированный экспорт таблицы | 24 часа | Повторная авторизация на выдачу; автоматическая очистка |
| ИИ-журналы с содержимым | Действующая политика оператора | Эта фича не сокращает и не отменяет её |
| Платёжные данные | Действующая финансовая политика | Не заменяется общим TTL телеметрии |

При отказе от необязательной аналитики новые продуктовые события прекращаются, ещё не отправленные необязательные события удаляются из очереди. Ранее собранные данные обрабатываются по опубликованным условиям и процедуре удаления. Технические события и аудит продолжаются в собственных границах.

При закрытии аккаунта персонально связанные обычные диагностические/аналитические записи удаляются либо обезличиваются по зарегистрированному жизненному циклу; отдельно отмечаются законные/операционные исключения аудита и финансов, а также существующее сохранение ИИ-журналов. Нельзя заявлять анонимность агрегата, который всё ещё содержит обратный список пользователей.

## 8. Сигналы и исходные пороги

Это начальные настройки для калибровки, а не обещанный SLA.

| Сигнал | Исходный порог | Поведение |
|---|---|---|
| Массовая ошибка этапа | ≥5 разных пользователей и ≥10% ошибок за 15 минут, минимум 20 завершивших окно операций | Один инцидент по этапу/коду/версии, обновление влияния |
| Остановка очереди | Есть ожидающие задачи и нет подтверждённого прогресса 10 минут | Проверить зависимость/worker; не запускать массовые повторы |
| Риск локальной записи | Есть подтверждённый отказ сохранности или сервер не подтвердил копию перед сроком локальной очистки | Приоритетное отдельное событие, без ожидания массового порога |
| Диск | 80% предупреждение, 95% критично либо прогноз исчерпания менее 24 часов при достаточных данных | Указать свободный объём, период прогноза и затронутый класс |
| Платёж без определённого исхода | Более 15 минут после отправки | Очередь сверки; без нового списания |
| Очистка просрочена | Наступил предусмотренный для класса срок + 1 час | Отдельно зависимость, клиент, основное хранилище |
| Необычное скачивание | Более 20 разных встреч одним администратором за час | Уведомить суперадминистраторов и аудит; не объявлять автоматически злоумышленником |
| Backup | Нет успешного запуска за 1,5 согласованного интервала расписания | Отметить отсутствие подтверждения, отдельно последний restore |

Критичность инцидента: P1 — риск данных/массовый отказ/доступ; P2 — частичный отказ с восстановлением; P3 — единичный некритичный сбой. Это операционные приоритеты, не обещание времени ответа.

Уведомление содержит только безопасную сводку, время, число пользователей, этап, версию и защищённую ссылку. Изменение настроенного внешнего получателя требует отдельного разрешения; новый адрес не может получить содержимое встречи. Повторы подавляются в рамках одного инцидента, восстановление отправляется один раз.
