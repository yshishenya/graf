# Implementation Plan: системная консоль GRAF

**Branch:** `codex/254-system-admin-console` · **Дата:** 2026-09-06 · **Spec:** [spec.md](spec.md) · **Umbrella:** [#6708](https://github.com/yshishenya/graf/issues/6708).

## Summary

Отдельная системная консоль на существующем FastAPI/Jinja: независимые административные личности и сессии; глобальный поиск, разрешённый просмотр содержимого и восстановление; единые тарифы/доступ/платежи/акции; связанная диагностика и измеримые показатели. Все FR-001–FR-090 обязательны. Этапы ниже определяют зависимости, а не сокращают объём.

## Technical Context

- Python >=3.13; FastAPI, Pydantic, SQLAlchemy, Alembic, PostgreSQL, Temporal, MinIO и существующий YooKassa-клиент. Swift/macOS для доставки ограниченных событий. Версии зависимостей закреплены существующими lock-файлами; их массовое обновление не входит.
- Серверный HTML, существующие CSS/JS и доступные нативные элементы форм. Отдельный ASGI процесс console из того же образа изолирует системный DB credential; отдельный console origin, host-only cookie и маршруты proxy закреплены security contract. Новая SPA, брокер сообщений, аналитическая SaaS и универсальная система ролей не нужны.
- **Risk / Validation Lane:** high-risk-product: auth, RLS, деньги, удаление, диагностика. В текущей поставке только подготовка документов; исполнение проверяется отдельно перед выпуском.
- **Release Gate:** сейчас no deploy. После реализации — focused проверки, governance-fast на точном SHA PR, quickstart и применимые fast/full/release gates проекта; перед production cd dry-run и отдельное разрешение. Изменения macOS требуют Developer ID, notarization, stapling и Sparkle.
- Целевая среда: Linux/Docker для сервера, браузер для консоли, поддерживаемые проектом macOS/архитектуры клиента. Одна установка, личные и корпоративные пространства.
- Нагрузка SC-006: изолированный стенд 4 vCPU/8 GiB RAM, PostgreSQL на SSD, 10 тыс. пользователей, 100 тыс. встреч, 1 млн событий; 20 административных сессий, 10 минут разогрева, 30 минут измерения. Фиксировать версии, SHA, размеры БД, cold/warm отдельно. p95 списка/поиска <=2 s, карточки <=3 s без медиабайтов. SQL statement_timeout для интерактивной выборки 2 s; ограниченный отдельный пул глобальных отчётов (4 соединения), максимум 2 фоновых тяжёлых отчёта.
- Состояния обновляются опросом каждые 10 s, скрытая вкладка прекращает опрос; это не пользовательская активность сессии. Агрегаты каждые 5 min. SSE/WebSocket не требуется.

## Constitution Check

Проверка до исследования и повторно после проектирования: дизайн совместим с действующей конституцией; исключений не запрошено. Это проверка требований, а не доказательство реализации.

| Обязательство | Решение и проверка |
|---|---|
| Системный звук, видимый индикатор, ручной Stop, локальные always/ask/never | Консоль не запускает запись; клиентские изменения ограничены событиями; AC-030/031 и профильные регрессии |
| Изоляция, отдельные полномочия, без автоматического повышения owner | Независимые principal/session, ограниченный DB-доступ и отрицательная матрица AC-001–007 |
| Секреты MediaScribe только на сервере | В админке статус конфигурации без значений; существующий adapter |
| LiteLLM/Langfuse — единственный существующий путь ИИ | Показываем pinned версии/историю; редактор глобальных prompt/model не создаём |
| Полные GenerationCall/Langfuse/Temporal сохраняются | Отдельный режим retained-диагностики; обычные события и аудит без текста |
| Точная правда удаления | Существующая saga удаления, офлайн-копии/backup/provider/retained отдельно; late-result fencing |
| Минимальное изменение архитектуры | Дополняем текущие модели/сервисы и шаблоны, не переносим платежи/обработку в консоль |
| Проверяемость и независимое ревью | Приёмка, контролируемые данные, reviewer-owned checklists, analyze и задачи; implementation не отмечает чеклисты за ревьюера |

## Архитектура и порядок исполнения

1. **Системный доступ.** Модуль `system_admin/` отделён от `admin/`. Роутер не принимает обычный principal. До проверки сессии допускаются только вход/активация/восстановление. Полномочия выводятся из фиксированной роли + разрешённых ограниченных grant; проверка на сервере каждого чтения и действия. Новые данные не уходят после отзыва.
2. **Аудит и операции.** Транзакция записывает намерение, safe-аудит и устойчивую команду. Фоновый исполнитель проверяет текущие права до начала эффекта, после старта обязательное завершение/сверка не отменяются отзывом. Повтор с тем же ключом возвращает прежнюю операцию. Предпросмотр не меняет доменное состояние.
3. **Глобальные проекции.** Узкие SELECT со списком полей и SQL-фильтрами; нет загрузки всех встреч. Контент запрашивается отдельно, не включён в поиск/листинг/метрики. Разбор привязан к администратору, объектам и причине. Stream/download проходит серверный контроль, без обхода через долгоживущий MinIO URL.
4. **Доменные адаптеры.** Повтор обработки, удаление, календарь, sharing и закрытие аккаунта вызывают существующие сервисы с явным системным разрешением; сохраняются original actor, владелец и worker. Запрещено подделывать пользовательский principal.
5. **Каталог/доступ.** Сначала обобщить контракт каталога на поддерживаемые capabilities, затем версии/предложения и миграция старых назначений, затем административные формы. Все invoice/grant snapshots сохраняются. Каталог общ для веба, клиента, checkout, renewal, promo, quota и уведомлений.
6. **Акции.** Версия условий, отдельные codes и reservations, фиксация лимита/бюджета под блокировкой. Срок/пауза не отменяет обязательства по созданным счетам. Gift использует общий сервис назначения; никакой фиктивной оплаты.
7. **Диагностика/метрики.** Устойчивый ID локальной операции, внутренний индекс связей, ограниченные снимки, каталог событий и SQL-агрегаты. Клиентские сообщения не являются фактами оплаты/удаления/сохранности. События использования соблюдают отдельное разрешение.
8. **Эксплуатация.** Состояния зависимостей берутся из существующих проверок; неизвестное показывается неизвестным. Настройки — фиксированный allowlist, никакого SQL/shell/секретов/редактора внешних адресов.

Детали транзакций, сущностей и границ — [research.md](research.md), [data-model.md](data-model.md), [API](contracts/api.md), [безопасность](contracts/security.md), [миграция](contracts/migration.md). Нормативные экраны и расчёты — [ui-and-operations.md](ui-and-operations.md).

## Project Structure

Существующие точки расширения: `apps/server/src/twobrain_rec_server/{main.py,db/,auth/,admin/,billing/,support/,product_analytics/,observability/,api/,cabinet/}`, `apps/macos/RecApp/Sources/{Diagnostics,Upload}/`.

Новые файлы только по ответственности: `system_admin/{app,auth,permissions,queries,operations,web,schemas,audit}.py`, `system_admin/templates/system_admin/`, `db/models/system_admin.py`; billing дополняется в существующих модулях, новые административные grants и catalogue definitions при необходимости в `billing/admin_grants.py`. Миграции в существующем `db/migrations/versions/`; последовательные номера выбираются по актуальным Alembic heads при реализации, не резервируются фиктивно заранее.

Тесты — существующий pytest в `apps/server/tests/`, native tests в `apps/macos/Shared/Tests/`; сценарии/команды — [quickstart.md](quickstart.md). Отдельный тестовый framework не добавляется.

## Validation Plan

Сначала отрицательная auth/RLS матрица, затем concurrency/replay и денежные инварианты на PostgreSQL; SQLite не доказывает RLS/locking. Синтетические данные покрывают две личные области и корпоративную, обычного owner, разные роли, истёкшие grants, ambiguous платежи, удалённые объекты и два конкурентных действия. Далее доменные регрессии, macOS/offline и веб-доступность, миграция старых snapshots, нагрузка SC-006, 60 min outage SC-009. Каждая проверка связана с [acceptance.md](acceptance.md) и [tasks.md](tasks.md).

Обязательные ревью до реализации перечислены в `checklists/`. Незакрытый пункт — явный gate, а не задача, которую исполнитель может отметить автоматически. Планирование не выполняет платежи, не читает живые записи и не включает аналитику.

## Complexity Tracking

Нарушений конституции и дополнительных платформ нет. Отдельные admin auth/DB boundary нужны из-за глобального доступа; повторное использование обычной сессии нарушило бы FR-001. Системные команды — ограниченный перечень операций поверх существующих сервисов, а не универсальный workflow engine.
