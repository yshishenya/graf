## 3. Блокирующие выводы

### 3.1 FR-011 всё ещё запрещает автоматический eviction

`spec.md:133` (FR-011) прямо говорит: «Автоматический eviction НЕ ДОЛЖЕН включаться». Это противоречит:

- `spec.md:16` — clarify Q2: автоматический eviction включается;
- `spec.md:147` — FR-025: eviction запускается при включённом kill switch;
- `spec.md:153-154` — FR-031/FR-032: пользователь видит состояние и может выключить eviction;
- `spec.md:188` — assumption: eviction включается после выкладки контракта;
- `plan.md:181-193` — целая Phase C автоматического eviction.

`analyze-2026-11-16.md:17` утверждает, что FR-011 исправлен, но в `spec.md` остался старый текст. Это незакрытый CRITICAL-дефект: нельзя одновременно реализовывать Phase C и соблюдать FR-011. Нужно переписать FR-011, привести assumptions и analyze в соответствие и повторно запустить analyze.

### 3.2 Смешение ревизий в playback/custody-доказательстве

`research.md:31` требует `archive_audio/finalized_at` из последней `FINALIZED` сессии «for the exact meeting media revision». При этом playback может обслуживать более старую закреплённую ревизию (`research.md:17`, `contracts/desktop-sync-proof.md:37`). Если custody читается по `meeting.media_revision_id`, а playback — по фактической ревизии, возможна ситуация: playback доказывает старую локальную ревизию, а `archive_audio=true` берётся из более новой ревизии встречи с другой custody-политикой. Это может разрешить удаление WAV, для которого серверная копия не доказана.

`plan.md:78-80` и `data-model.md:65-73` описывают helper по `media_revision_id`, но не фиксируют, какая именно ревизия передаётся из sync-state. `contracts/desktop-sync-proof.md:40` говорит «same media revision», не уточняя local/playback/meeting. Нужно:

- читать custody по той же ревизии, которая проверяется для локального файла, и явно отдавать её идентификатор в ответе;
- добавить тест: meeting revision новее, playback pin — старая ревизия, у старой `archive_audio=false`, у новой `true`; результат обязан быть `keep`.

### 3.3 `object_verified` не проверяет читаемость, хотя FR-002 этого требует

`spec.md:124` (FR-002) требует проверить существование, ожидаемый размер **и доступность для чтения**. `contracts/desktop-sync-proof.md:38`, `data-model.md:19` и `research.md:23` ограничиваются `stat.size == artifact.byte_length`; `research.md:23` прямо говорит, что bounded read probe «may be added later». Это расхождение spec и контракта.

Кроме того, `plan.md:90` предлагает найти `_stored_review_m4a_artifact` без явной передачи уже вычисленной ревизии. Текущий helper принимает `revision` (`cabinet/egress.py:2262-2275`), но plan этого не фиксирует. Нужно передавать одну и ту же разрешённую ревизию в `review_playback_state`, `_stored_review_m4a_artifact` и `stat_object`, а также определить fail-closed проверку читаемости (bounded read/HEAD с явным контрактом) либо изменить FR-002 решением владельца.

### 3.4 Storage status: роли и видимость сумм противоречат друг другу

- `contracts/desktop-storage-status.md:31`: `admin` имеет `access_mode=read_only`, но суммы видны, «если existing billing projection allows it».
- `data-model.md:61`: `access_mode=read_only` **implies** null amounts.
- `plan.md:120`: `access_mode=manage` только personal owner + workspace owner + payer match; иначе `read_only`.
- `spec.md:127` (FR-005): администратор «с правами управления» видит суммы.

Не определено, что происходит с `corporate_owner` из текущего `_billing_role` (`cabinet/web_routes/billing.py:1240-1260`), и какое значение `billing_role` отдавать при неизвестной роли. Дополнительно `contracts/desktop-storage-status.md:40` возвращает 503 при отсутствии DB-сессии, а `spec.md:127` запрещает 5xx при сбое projection; нужно явно разделить «нет DB-сессии» и «projection failure».

### 3.5 Dry run и «no server mutation» противоречат текущему sync-state

`plan.md:154` и `spec.md:132` (FR-010) разрешают существующую серверную expiry-реконсиляцию sync-state. Текущий `get_desktop_recording_sync_state` действительно вызывает `_mark_expired_if_needed` (`ingest/desktop_sync.py:768`, реализация `:627-687`) и мутирует upload session. `security.md CHK010` требует, чтобы dry-run/cleanup/eviction «do not call server mutation». Это не одно и то же: клиент делает GET, но сервер меняет состояние.

Нужно либо явно записать исключение для idempotent expiry reconciliation в security-контракт и тест, либо добавить read-only режим sync-state для dry run. Оставлять формулировку «no server mutation» без исключения нельзя.

### 3.6 Kill switch: default и немедленность не определены

- `plan.md:189`: kill switch «default enabled after contract».
- `research.md:135`: Phase C остаётся «behind the kill switch/default-off until a follow-up», если evidence не чистый.
- `tasks.md:52` (T029): включать Phase C только если production dry run чистый, иначе оставить disabled.
- `spec.md:133` (FR-011): eviction вообще не должен включаться.

Это четыре разных политики. Плюс UX CHK008 требует, чтобы состояние kill switch было видно и действовало без перезапуска; `plan.md:189` даёт env var `GRAF_DISABLE_LOCAL_CACHE_AUTO_EVICTION`, который обычно читается на старте. Нужно выбрать один default, определить источник истины (app setting vs env), поведение при конфликте и тест «выключили — следующий запуск ничего не удалил, перезапуск не нужен».

### 3.7 Receipt не покрывает crash между unlink и записью квитанции

`spec.md:141-142` (FR-019/FR-020) требует durable-квитанцию и идемпотентность. `plan.md:172-173` говорит «durable receipt» и «already missing WAV → success/no-op; receipt appended once», но не описывает:

- что делать, если приложение упало после `unlink`, но до записи receipt;
- как отличить «уже очищено, квитанция есть» от «WAV исчез, квитанции нет»;
- как не создать вторую квитанцию при повторе.

`contracts/cleanup-receipt.schema.json:14-15` разрешает `playbackRevisionFingerprint=null` и `verifiedAt=null`, хотя FR-019 требует фактическую ревизию playback и время проверки. Для ручной очистки эти поля должны быть обязательны. Нужен intent/journal до unlink либо reconcile-правило, а также тест crash/retry.

### 3.8 Текущий sync-state уже отдаёт хеши

`security.md CHK001` требует, чтобы sync-state не содержал hashes. `contracts/desktop-sync-proof.md:63` повторяет «No object key, signed URL, ETag, hash or local path». Но текущий `MediaRevisionSummary` содержит `manifest_sha256` и `track_sha256_by_role` (`api/schemas.py:843-844`), и они уже входят в sync-state (`api/schemas.py:1007-1018`). Существующий no-secret тест не проверяет `sha256` (`tests/contract/test_recording_sync_no_secret_egress.py:7-18`).

Нужно либо ограничить запрет только новыми proof-полями и явно разрешить существующие hash-поля (тогда изменить чеклист/контракт), либо подготовить совместимое удаление/перенос хешей. Молчаливое противоречие недопустимо.

### 3.9 UX copy и accessibility не заданы канонически

`spec.md:145` (FR-023) и `plan.md:175-178` требуют объяснить, что удаляется только WAV, review/manifest остаются, серверная встреча не удаляется, локальное прослушивание сохраняется. Но точных строк, reason-to-copy таблицы и VoiceOver labels нет. `contracts/eligibility-reasons.md:14-46` содержит внутренние коды (`retention_unsafe`, `archive_audio_unknown` и т.п.), а не пользовательские формулировки. Для high-risk deletion UX этого недостаточно.
