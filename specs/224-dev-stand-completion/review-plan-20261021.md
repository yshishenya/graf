## 4313857009: нестандартный путь установки

Ранний отказ `adopt-state`, если выбранный `_dev_app_destination()` отличается
от `DEV_APP_PATH`, соответствует FR-003/004/008/016 и порядку предварительных
проверок в контракте. Проверка должна предшествовать `base.mkdir`, созданию
регистрационной блокировки, взятию operational lock и идемпотентному возврату
существующей привязки. Остановка нестандартного приложения не делает его путь
допустимым. Поиск приложений или данных по диску не требуется.

Сравнивается результат существующего определения пути: отсутствие переменной,
пустая строка и строка из пробелов выбирают `DEV_APP_PATH`; явное каноническое
значение также допустимо. Нестандартный путь не следует разрешать через
`resolve()` или переносить в общий helper новый обходной путь. Общий helper
используется и изолированными тестами; исправление ограничивается принятием.

Для итоговой проверки требуются случаи существующего состояния,
`--expect-empty` и уже зарегистрированного состояния при нестандартном пути.
Отказ должен происходить без создания новой привязки/регистрационных файлов,
без изменения существующих файлов и inode прежнего `promote.lock`, без
вызовов внешних действий. Положительные варианты стандартного пути сохраняются.

## 4313857014: неизвестный runtime_mode

Общий `_load_active` — подходящая точка проверки режима активного указателя.
Единственный writer `_publish_active` вызывается из восстановления схемы,
promote и rollback; фактически публикуются только два значения:

| Запись или результат | Значение | Решение |
|---|---|---|
| `active-manifest.json` | `live` | Допустимо; прочие проверки живого состояния сохраняются. |
| `active-manifest.json` | `metadata-only` | Допустимо для искусственного состояния; не доказывает живую приёмку. |
| `runtime.json` | `compose` | Отдельный формат записи запущенных компонентов; не добавлять в допустимые режимы указателя и не запрещать в runtime record. |
| Диагностический результат build | `live-dry-run` | Не публикуется активным указателем. |
| Результаты операций | `fixture`, `existing-active`, `existing` | Не являются режимами активного указателя. |

Недопустимый или отсутствующий режим должен давать `HarnessError` до загрузки
и использования manifest как активного. Неизвестное значение не подменяется
`metadata-only`. Отсутствие самого указателя по-прежнему возвращает `None`.
`live` без обязательного runtime record при принятии по-прежнему отвергается.

Проверены обращения `_load_active`: adoption, build/build_manifest, adapter
build/promote, retention/prune, promote, status, launch validation, smoke,
rollback и повторные чтения после ожидания/проверки. Их общая проверка не требует
нового слоя или копий валидатора. Часть status recovery-ответов возвращается
раньше чтения active и сохраняет явный заблокированный результат.

Не все чтения JSON проходят через `_load_active`: fixture `reset-data` читает
указатель напрямую, а shared reset уже запрещён отдельно. Поэтому этот проект
не следует описывать как новый универсальный валидатор каждого raw reader.
Чтения указателя в promote/rollback следуют после `_load_active`; adoption
предварительно проверяет безопасный путь manifest, затем вызывает общий reader.

Обязательная матрица: отсутствующее поле, `null`, неизвестная строка, число,
список и объект отвергаются; оба допустимых строковых режима принимаются.
Отказ для сложных JSON-типов должен быть управляемым `HarnessError`, а не
случайным `TypeError` от проверки принадлежности множеству. Нужны прямые случаи
reader и отрицательное принятие состояния с сохранением файлов/lock inode и
отсутствием привязки. Допускаемые контрактом технические lock-файлы adoption
не означают публикацию привязки или изменение исходного состояния.

## 4314313869: origin внешней рабочей копии в launch fixture

Собственная каноническая `_repo_identity` через monkeypatch в launch fixture
соответствует FR-011/016 и CHK011/012. Здесь проверяется синтетический lifecycle,
а не Git remote рабочей копии, из которой запущен pytest. Подмена должна
применяться до создания binding и поддерживать существующий optional root
аргумент. Binding, `_state_ownership`, общий каталог и блокировки продолжают
проверяться настоящим кодом; их целиком подменять ради успеха не следует.

Строгие проверки реального Git остаются в ownership suite: формы origin,
ошибки Git, несколько origin, `insteadOf`, чужой repository, независимые
clones/worktrees и другой cwd. Изменять или ослаблять их для launch fixture
не требуется. Для итогового доказательства нужен launch suite с отсутствующим
либо неподходящим внешним origin в изолированном окружении, без изменения
настоящего origin рабочей копии; после этого — совместный ограниченный набор.
