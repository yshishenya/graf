## Проект устранения трёх P2 PR #7753, до изменения кода

Повторно прочитаны оба checklist (requirements 16/0, infra до этого прохода
28/0), текущий договор, обычный transition и receipt reader, PID/start
helpers, snapshot, lifecycle, публикация и CLI promote/rollback, pending
candidates и прямой prune. Тесты и внешние действия не выполнялись.

Первоначальное ревью пропустило три реальные границы. Новое решение
относится только к проекту их устранения; прежние 378 успешных проверок
не доказывают исправление найденных P2.

1. **Отсутствующий bundle при работающем приложении — проект допустим.**
   Сейчас `app_was_running=True` с `backup=None` создаёт квитанцию,
   которую собственный reader отвергает. До snapshot, записи манифеста,
   квитанции и stop/terminate нужен безопасный отказ. Не завершать процесс
   автоматически и не объявлять его восстанавливаемым без пакета.
   RED/GREEN должен проверять отсутствие новых файлов/изменённых bytes,
   отсутствие stop/install и обычный читаемый status после отказа.
2. **Повторно выданный PID — проект допустим.** Для живого сохранённого PID
   сравнивать сохранённый `controller_start` с наблюдаемым token.
   Совпадение или невозможность доказать token запрещают повтор без записи.
   Доказанное различие означает другой процесс: его не сигналить;
   identity операции обновляется только после всех проверок под тем же lock.
   Нужны случаи совпадения, различия и ошибки/пустого token. Полная цель,
   checkouts и остальные проверки происхождения не ослабляются.
3. **Существующий ready-кандидат — удаление ранней записи необходимо,
   но пока недостаточно для общего обещания сохранности.** Receipt содержит
   полный target, reader не требует его отдельного файла; раннюю запись
   promoted/active можно убрать, оставив обычный ready побайтно. Это
   исправляет обычную ошибку установки до попытки публикации.

**Оставшееся замечание проекта R7/P2:** проверить последовательность
`_publish_active записал target active → запись pointer отказала → receipt
сохранена → повтор получил ошибку install/smoke → успешная компенсация previous
→ следующий штатный prune`. После первой попытки публикации target на диске
уже active. Удаление только ранней записи не возвращает его в ready после
компенсации повторной попытки. `_cleanup_ordinary(keep_extra=target)` защищает
лишь ближайшую очистку; следующий `estimate_or_apply_prune` сохраняет pending
только по `status=ready` и может удалить кандидат. Нужен адресный RED и
минимальное правило восстановления исходных метаданных кандидата либо
сохранения этого pending target после компенсированного повтора. Новая
машина состояний или подсистема не требуется.

### Повторное ревью проекта R7: PASS до реализации

Исполнитель уточнил минимальное решение: receipt закрепляет
`target_record` — полную исходную запись `manifests/<target>.json` либо
`None`, если её не было. Присутствующая запись проходит существующую
валидацию manifest и полное сравнение неизменяемых полей с target.
Ранняя запись promoted target удаляется. При успешной компенсации
исходная запись со всеми status/health/promoted_at либо исходное отсутствие
восстанавливаются с fsync и readback до публикации previous и снятия receipt.
При одинаковом ID previous/target отдельная запись не восстанавливается:
публикация проверенного previous сама возвращает нужный манифест.

**Это решение допустимо и снимает R7 на уровне проекта.** Ошибка записи,
удаления или readback восстановленной записи обязана оставить receipt;
повтор должен оставаться возможным. Текущее содержимое дискового target
при повторе не сравнивается на равенство исходному `target_record`:
неудачная публикация могла законно изменить его. Полнота и целостность
закреплённой записи проверяются в reader до воздействия. Неизвестный старый
формат не превращается автоматически в доказанное исходное состояние.

Минимальная приёмка дополнения: исходная цепочка partial publication →
ошибка повторной установки → компенсация → обычный prune; исходное
отсутствие записи; same-ID; отказ восстановления записи/отсутствия/readback;
а также три случая live token и ранний отказ отсутствующего bundle.
Новый объект, команды, фазы или механизм миграции не требуются.

Все пункты обоих checklist повторно сопоставлены с уточнением. Итог проекта:
**PASS; требования 16/0, инфраструктура 28/0.** CHK023 вновь отмечен по
этому конкретному решению. Новый код, отрицательные проверки и независимое
итоговое ревью ещё нужны; исходное implementation APPROVE не восстановлено.

1. Исходной записи target нет (`target_record=None`, разрешённый путь
   внешнего candidate/первой установки).
2. Target успешно опубликован, но снятие receipt отказало. Указатель уже
   ссылается на target; receipt сохранена, точный повтор разрешён.
3. Повтор получил ошибку установки и восстановил previous runtime/app.
4. `_complete_ordinary` удаляет файл target на строке 2694. Его следующий
   fsync отказывает либо controller завершается до смены active pointer.
5. Receipt остаётся, однако active pointer всё ещё ссылается на удалённый
   manifest. Новый CLI promote и direct transition вызывают `_load_active`
   до восстановления и получают `Cannot read JSON .../manifests/<target>.json`.
   Первая установка имеет тот же разрыв до удаления своего active pointer.

Это не гипотетическая одновременная внешняя запись: состояние создаёт сам
разрешённый recovery. Имеющийся тест restore-sync начинает с pointer=previous,
поэтому не проверяет эту границу после опубликованного target. Матрица
stored/absent + partial publication моделирует отказ pointer-write, при
котором pointer ещё previous, и также не обнаруживает этот путь.

Минимально: сначала долговечно опубликовать и перечитать previous либо
доказать отсутствие active pointer для первой установки; после этого
восстановить target_record/отсутствие и проверить результат; лишь затем
снимать receipt. Все промежуточные исходы должны оставлять pointer читаемым
или отсутствующим. Случай одинакового ID остаётся в существующем исключении.
Нужен RED/GREEN: успешная публикация + отказ receipt-unlink → ошибка
повторной установки → отказ fsync/прерывание при восстановлении отсутствия
target → новый точный повтор. Contract должен отражать новый порядок.

Предыдущее проектное утверждение «target_record до публикации previous»
было ошибочным; это замечание исправляет и собственное прежнее ревью.
CHK023 вновь открыт. После полного перечитывания итог требований 16/0,
инфраструктуры 27/1. Прочие критерии и отдельная живая приёмка не расширяются.
