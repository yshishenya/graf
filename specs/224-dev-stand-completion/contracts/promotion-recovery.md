# F224/T010: восстановление обычного переключения

Проект 26.10.2026; код ещё не изменён. Владелец: T010/#7641.
Область: обычные `promote --live` и `rollback --live` при одинаковой схеме
и совместимых образах хранилищ. `schema-transition.json` и `recover-schema`
сохраняют приоритет; снимки томов и новая машина миграций не добавляются.

## Одна существующая квитанция

Расширяется `rollback-required.json` формата `dev-rollback-required.v1`:
обязательные прежние поля сохраняются, дополнительный объект `operation`
описывает незавершённую обычную операцию. Старую квитанцию без этого объекта
нельзя угадать, автоматически снять или объявить восстанавливаемой повтором.
Некорректные поля, ссылки и пути дают отказ с сохранением исходных материалов.

`operation` содержит вид команды, уникальный технический ID, полный предыдущий
manifest либо null, полный целевой manifest, прежний runtime либо null,
закреплённые controller/previous/target checkouts с полными SHA и digest,
PID текущего контроллера и его start token, снимок прежнего приложения либо
null с digest и прежние признаки запуска.
Путь снимка — только обычный файл-каталог `transactions/previous-*.app`
в принятом state; произвольный путь, ссылка наружу или digest mismatch запрещены.
Это технические локальные метаданные, не секреты или содержимое встреч.

Состояния: квитанции нет → подготовка → квитанция есть → проверка результата
→ долговечная публикация → снятие квитанции → штатная очистка. Отдельные
промежуточные фазы не нужны: после прерывания повторяется та же целевая
операция с полной проверкой, а не угадывается последний исполненный шаг.

## Подготовка до первого воздействия

1. Под прежним `promote.lock` проверить принадлежность, целевой manifest,
   ожидаемый active/parent, чистоту и точные bytes/SHA рабочих копий,
   runtime-definition, образы, подпись и пакет. Совместимость схемы и образов
   хранилищ обязательна. Чужой живой PID и неизвестный runtime запрещены.
2. Сохранить прежнее состояние запуска и готовую копию приложения; проверить
   её digest. Для первой установки отсутствие прежней версии должно быть
   доказано, а не выведено только из отсутствия active pointer.
3. Атомарно с fsync записать квитанцию до первого stop/terminate/install.
   Ошибка этой записи не разрешает воздействия. `_mark_rollback_required`
   при последующих ошибках сохраняет объект `operation`, не затирает его.

## Повтор и общий запрет

Пока квитанция существует, `status` показывает `rollback_required` до чтения
обычного active; даже уже опубликованный target не означает завершение.
Все обычные изменяющие операции и быстрый idempotent return запрещены.
Разрешено только повторить записанные promote/rollback с той же целью,
точным controller и закреплёнными рабочими копиями под прежней блокировкой.
Active допускается только записанный predecessor либо уже записанный target;
чужой parent, новый manifest и изменение bytes дают отказ до воздействия.
Сравниваются все поля полного закреплённого manifest; различаться могут только
`status`, `health` и `promoted_at`. `_same_manifest_identity` для этого
недостаточно: он намеренно не сравнивает часть неизменяемых полей при rebuild.
PID и start token проверяются вместе по существующим `_pid_alive` и
`_process_start_token`; живой чужой контроллер запрещает повтор. Только после
получения прежнего lock и проверки завершения прежнего контроллера новый
процесс долговечно обновляет эти два поля. ID операции, SHA контроллера,
закреплённые checkouts и цель при этом не меняются.

Повтор не требует работающего predecessor. Текущий runtime может быть
остановлен либо принадлежать записанному predecessor/target. Живой процесс
с недоказанной идентичностью не останавливается. Тот же пакет заново
устанавливается, те же образы запускаются и полный текущий smoke проверяет
app/backend/frontend/workers/schema/identity. Успех публикует именно target.
После установки дополнительно выполняется существующий
`_validate_launch_bundle(target, DEV_APP_PATH)`: smoke сам по себе не
подтверждает digest и подпись установленного пакета.
Откат с неуказанным `--manifest-id` при повторе использует записанную цель,
а не новый parent уже изменившегося active.

При обычном пойманном исключении разрешена прежняя компенсация. Она не
потребляет единственную копию приложения и снимает квитанцию только после
проверки восстановленных app/runtime/pointer и прежнего состояния запуска.
Для прежнего пакета обязателен `_validate_launch_bundle(previous, DEV_APP_PATH)`;
подтверждение его bytes/подписи не заменяется чтением plist или одним smoke.
При первой установке проверяется восстановленное отсутствие app/runtime/
pointer; неизвестность оставляет квитанцию. После SIGKILL в компенсации
повтор той же целевой команды по-прежнему возможен.

## Процессы и одна блокировка

Короткие изменяющие команды текущего контроллера наследуют fd уже взятого
`promote.lock` через `pass_fds`: SIGKILL родителя не освобождает право изменения
до фактического окончания команды. Сам файл и inode блокировки не меняются.
Fd доступен только в пределах контекста блокировки; вложенная/чужая блокировка
не подменяет его. После обычного окончания или исключения fd закрывается.
Применимость к настоящим install/Compose/lifecycle scripts проверяется
отдельно; один опыт с Python-процессом не считается их приёмкой.

Долгоживущий backend этот fd не наследует. Переиспользуется существующий
pipe gate `SCHEMA_STARTUP_GATE`: дочерний процесс ждёт один разрешающий байт;
PID, ожидаемая post-exec command и start identity записываются с fsync до него.
EOF при гибели родителя не запускает стек. Обычный startup guard проверяет
квитанцию, точную цель и принадлежность текущему контроллеру. Самостоятельный
startup при незавершённости запрещён. Перед повтором живой записанный backend
останавливается по прежней проверке владения до нового запуска.

Закреплённый старый код не переписывается и его startup guard не обходится.
Для обычной операции после `_checkout_adapter` создаётся экземпляр текущего
`GrafLocalAdapter` с проверенными `root` и `state` закреплённой версии.
Frozen adapter служит проверке исходников/resolver; его изменяющие методы
не вызываются. Это сохраняет пути и точные bytes scripts, но все тела Python
и вложенные вызовы `self` принадлежат текущему классу, без monkeypatch/rebind
старого объекта, globals или frozen module.

Этот путь обязателен для `_snapshot_app`, `_stop_previous`, `_terminate_dev_app`,
`_install_app`, `_start_backend`, `_launch_dev_app`, `_restore_app`,
`_restore_runtime`, `_atomic_swap_dev_app`, `_refresh_dev_app_registration`,
`_ensure_rollback_archive` и последующего `_apply_retention`, включая вложенные
вызовы, файловую компенсацию и очистку. Текущий `_run_command` передаёт held fd
в короткие subprocess; текущий `_start_backend` использует pipe gate.
`_restore_app` копирует backup, не перемещает и не удаляет его до завершения.
Предстартовая проверка текущего контроллера обязательна до разрешающего байта;
затем закреплённый startup script исполняет собственный guard без обхода.
Существующий `_schema_start_authorized` и schema recovery сохраняют свой
приоритет и отдельные проверки. Exact-SHA/bytes/digest/resolver не ослабляются.

## Публикация и очистка

`_publish_active` не удаляет обычную квитанцию автоматически. После успешного
smoke и проверки установленного пакета записываются manifest и pointer с fsync,
затем перечитывается их полное соответствие target по правилу выше. Это точка
подтверждённого долговечного результата. До неё ошибка оставляет квитанцию
и требование восстановления. Только после неё выполняются unlink квитанции
и fsync каталога. Если unlink не выполнен и квитанция осталась, status продолжает
требовать повторной проверки. Если unlink уже выполнен, но fsync каталога
завершился ошибкой, отсутствие квитанции допускает согласованный подтверждённый
target с предупреждением; обещания восстановить имя файла при отказе записи нет.
Очистка при таком предупреждении откладывается. Если после перезапуска
квитанция вновь видна, действует обычный запрет и полный повтор той же команды.
Для успешной компенсации тот же порядок относится к проверенному предыдущему
состоянию, включая доказанное отсутствие при первой установке.
Прерывание после pointer, но до снятия, требует полной повторной проверки;
одного pointer для idempotent PASS недостаточно.

Копия приложения, оба комплекта пакетов и материалы отката не удаляются до
проверенной публикации. `_restore_app` сохраняет исходную копию. Общий
`_apply_retention`, прямой adapter build/prune и cleanup отказывают при
незавершённости; успешная очистка выполняется после снятия квитанции.
Ошибка очистки — предупреждение, без отмены уже подтверждённого результата.
Существующая схема миграции не должна потерять свою квитанцию при изменении
общего `_publish_active` или общих защитных проверок.

## Матрица приёмки

В `tests/governance/test_dev_promotion_transaction.py` настоящие отдельные
процессы и файловая синхронизация; внешний runtime/app подменены маркерами.
Никаких app bundles, Docker, Swift, сети, реальной установки или TCC.

- Обычный успех и SIGKILL до/после stop/install/start/smoke/pointer/cleanup;
  после каждого прерывания — status, сохранность данных и повтор до согласованности.
- Та же матрица для rollback, первой установки и прерванной компенсации.
- Ошибки записи квитанции/manifest/pointer, до unlink и после unlink/до fsync
  каталога: различать видимый marker и согласованный target с предупреждением;
  ни один исход не разрешает преждевременную очистку. Ошибки очистки; чужая цель/PID,
  изменённые bytes, digest и утраченный checkout: ранний отказ и сохранность.
- Совпадающие manifest ID/SHA при изменении digest/app identity/boundary/parent
  отклоняются; прежний PID с другим start token не подтверждает контроллер.
- Закреплённый старый adapter содержит прежние изменяющие методы: ни один
  из них, включая вложенную компенсацию, не исполняется. Проверка установленного
  digest/подписи обязательна для target и восстановленного предыдущего пакета.
- Реальный surviving child удерживает прежний lock после смерти контроллера;
  после его завершения повтор получает тот же inode. До durable runtime record
  startup gate не допускает ни одного действия, после записи retry видит owned PID.
- Все конкурирующие CLI и прямые adapter build/retention/prune, same-active
  return, smoke до/после probe и startup не обходят незавершённость.
- Существующие schema recovery, frozen adapters, ownership и signatures
  проходят прежние проверки. Реальная приёмка T009/T011/T012 остаётся отдельно.
