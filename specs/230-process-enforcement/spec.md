## User Scenarios & Testing *(mandatory)*

### User Story 1 — Однозначная работа с фичей и проверками (Priority: P1)

Разработчик получает свободный номер фичи, явного владельца и контекст; проверка
чужого, изменённого или неполного результата не разрешает слияние.

**Why this priority**: ошибочная идентичность делает все последующие проверки недостоверными.
**Independent Test**: существующие проверки владельцев allocator/context/receipt
подтверждают как разрешённые, так и отклоняемые случаи; точные связи с преемниками записаны.

**Acceptance Scenarios**:
1. **Given** два одновременных запроса, **When** выделяются новые номера,
   **Then** номера различны, собственная ветка не считается внешней коллизией,
   а timeout не создаёт ложную бронь.
2. **Given** фича с главной issue, **When** выбирается контекст,
   **Then** совпадают номер/метка/ветка/владелец/точная версия, без выбора по времени файла.
3. **Given** старый, отменённый, изменённый или неполный результат CI,
   **When** он предъявлен для слияния, **Then** приёмка отклоняет его.

### User Story 2 — Наблюдаемый операторский переход (Priority: P1)

Оператор видит реальные проверки GitHub, границы их доказательств и процедуру
отката до изменения обязательных проверок и очереди слияния.

**Why this priority**: включение защит без проверки может заблокировать весь проект.
**Independent Test**: отчёт связывает реальные события с точными версиями и
различает наблюдение, проверку на искусственных данных и отсутствующий сценарий.

**Acceptance Scenarios**:
1. **Given** существующие защиты репозитория, **When** проводится наблюдение,
   **Then** их состояние до/после одинаково; данные о PR/manual/merge_group
   содержат точную версию, результат, источник и время.
2. **Given** событие merge_group не наблюдалось, **When** готовится отчёт,
   **Then** оно остаётся неподтверждённым; PR или тест на искусственных данных его не заменяет.
3. **Given** план изменения обязательных проверок, **When** его передают оператору,
   **Then** указаны предварительные условия, сохранение прежних настроек,
   точный откат, повторная проверка и отдельное разрешение на применение.

### User Story 3 — Ясные границы вспомогательных агентов (Priority: P2)

Основной агент делегирует исследование без неявного права менять проект, а
исполнитель получает одного владельца и одну рабочую копию с явным списком файлов.

**Why this priority**: общая таблица ролей уже существует, но #6330 требует явных правил передачи работ.
**Independent Test**: по одной краткой процедуре можно принять решение для
исследования, исполнения, пересечения файлов, нового требования и передачи результата.

**Acceptance Scenarios**:
1. **Given** исследователь только для чтения, **When** он получает вопрос,
   **Then** он возвращает вывод, проверенные факты/ссылки и ограничения; не меняет
   файлы, Git, GitHub, приложение, выпуск или развёртывание и не запускает побочные действия.
2. **Given** исполнитель, **When** назначается работа,
   **Then** заданы фича, задачи, единственный владелец/рабочая копия,
   разрешённые файлы и проверки; чужие изменения сохраняются.
3. **Given** два задания с пересекающимися файлами, **When** обнаружен конфликт,
   **Then** пересекающиеся изменения останавливаются до явной передачи владения;
   непересекающаяся разрешённая работа может продолжаться.
4. **Given** результат агента, **When** основная работа продолжается,
   **Then** основной агент сверяет фактические изменения и доказательства,
   а прежние разрешения не расширяются на commit/merge/release/deploy.

### Edge Cases

- Отсутствующие исторические файлы не означают отмену или завершение требования.
- Отмена дубликата имеет причину и точного преемника, а не отметку completed.
- API timeout, неполный ответ, запрет доступа или отсутствие run дают unknown/blocked, не PASS.
- Неизвестный точный SHA или изменившаяся основа делают прежние проверки историческими.
- Новый scope, чужой dirty-файл или неясное владение требуют остановить только затронутую запись.
- Задание read-only не получает право изменять проект ради запуска проверки;
  проверка, способная создавать файлы/данные, требует отдельно назначенного исполнителя.
- Reviewer-owned checklist — отдельное явное исключение к отсутствию записи:
  назначенный reviewer меняет только свой checklist и отчёт; остальной проект остаётся read-only.
- Секреты, личные данные и содержимое встреч не передаются в handoff или evidence.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Сохранить исходные двадцать task IDs и источник каждого требования;
  отменённые дубли отделить от исполняемых задач и не отмечать их выполненными.
- **FR-002**: Переиспользовать действующий collision-safe allocator с общей блокировкой,
  параллельной/повторной проверкой и отказом при ошибке GitHub.
- **FR-003**: Сохранять связь главной issue/метки с фичей, веткой, задачами,
  владельцем и точной версией; явный active pointer обязателен, mtime fallback запрещён.
- **FR-004**: Отклонять stale/cancelled/partial/changed-tree/mismatched-base CI evidence;
  идентичность workflow и requested/start/end версии обязательна.
- **FR-005**: Сохранять Feature ID, главную issue, task IDs, lane, точный SHA и
  Legacy Impact в метаданных PR, не объявляя частичный PR завершением всего объёма.
- **FR-006**: Различать PR/manual/merge_group и соответствующие версии/основу,
  сохранять exact checkout, cancellation и проверенное сопоставление PR.
- **FR-007**: Подготовить наблюдательный rehearsal report и явный rollback contract;
  неподтверждённые реальные сценарии остаются открытыми до фактических доказательств.
- **FR-008**: Не менять обязательные проверки, очередь слияния, правила ветки,
  работающий Dev, production или данные при наблюдении; применение требует отдельного разрешения.
- **FR-009**: Явно определить read-only исследование, пределы записи исполнителя,
  одного владельца/рабочую копию и передачу владения при пересечении файлов.
- **FR-010**: Передавать краткий вывод, точные источники/версии, проверки,
  неопределённость и следующий шаг; не переносить секреты, личный контент или весь диалог.
- **FR-011**: Сохранить независимое владение checklist и обязательные
  specify/clarify/plan/checklist/tasks/analyze/taskstoissues/implement/converge/validation gates;
  новые implementation commits возможны только после проверки и разрешения пользователя.
- **FR-012**: Сохранять стабильные корневые инструкции, один scoped источник
  процедур, переносимый harness без данных GRAF и отдельный owned fragment;
  исключить новый необоснованный legacy и дубли правил.

### Key Entities

- **Исходное требование**: task ID, GitHub issue, текст/хеш источника, актуальное состояние и преемник.
- **Задание агента**: роль, фича/задачи, владелец, рабочая копия, разрешённые файлы, проверки и запреты.
- **Передача результата**: вывод, факты, точная версия, проверки, ограничения, следующий шаг.
- **Наблюдение CI**: событие, run/attempt, workflow, source/target/base SHA, результат и ссылка.
- **Операторский переход**: исходное состояние, предварительные условия, разрешение,
  действие, проверка после действия и обратимое восстановление.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Для всех 20 исходных task IDs существует единственная запись с
  источником и статусом; у всех 12 отменённых дублей указан преемник, без ложных [X].
- **SC-002**: Все профильные проверки действующих allocator/context/receipt
  проходят на зафиксированной версии; каждый пропуск и предел проверки перечислен.
- **SC-003**: Каждое наблюдаемое реальное событие связано с точной версией и
  результатом; отсутствие сценария не выдаётся за успешную проверку.
- **SC-004**: Пять сценариев делегирования — чтение, исполнение, конфликт,
  расширение задачи и приёмка результата — имеют однозначный разрешённый следующий шаг.
- **SC-005**: Снимки защит до/после наблюдения совпадают; применение остаётся
  отдельно разрешаемым операторским действием с проверяемым откатом.
- **SC-006**: Активный срез имеет независимое ревью, ноль неустранённых
  Critical/High findings, актуальные проверки точного PR SHA и принятую связь с issues;
  общая фича не закрывается при недостающем обязательном доказательстве.

## Assumptions

- Продолжается F230/#6314; новый номер не выделяется. Отсутствующий старый план
  восстанавливается из исходных issues и нынешнего кода, без утверждения об оригинальных байтах.
- Принятые F216/F227/F234/F235 — владельцы существующих общих механизмов;
  повторная реализация и новый слой управления агентами не нужны.
- Нынешняя первая реализация ограничена недостающими правилами делегирования US3
  и планировочными артефактами. Остальной объём фичи и операторские ворота сохраняются.
- Наблюдение использует только чтение GitHub API и существующих публичных metadata.
  Если разрешений недостаточно, фиксируется точное ограничение, настройки не меняются.
- Windows/F200 исключена из текущей уборки репозитория.

## Clarifications

### Session 2026-10-16

Повторная проверка по speckit-clarify: новых вопросов пользователю нет — цели и
ограничения заданы исходными issues, текущими правилами проекта и его разрешением
реализовывать актуальное. Это разрешение не распространяется на отдельные commit/merge/release/deploy.

- Восстановление сохраняет исходные требования и номера; отменённые дубли не оживляются.
- Отчёт наблюдения может содержать неподтверждённые сценарии, но их приёмка не считается выполненной.
- Только для чтения означает отсутствие побочных изменений, включая GitHub и локальные данные;
  запись reviewer checklist допустима лишь при явном назначении этого отдельного результата.
- Один владелец/рабочая копия относится к заданию исполнителя. Непересекающиеся
  файлы можно поручать нескольким исполнителям; параллельная запись одного файла запрещена.
