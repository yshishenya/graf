# Контракт T075: внутренний импорт официальных реестров

Статус: требования к реализации, не свидетельство работающего импорта.
Область: FR-087 / T075 / #4930. Реальная финансовая сверка и приёмка магазина
остаются обязательными; полнота файлов сама по себе их не доказывает.

## Исполнитель и доступ — B1

- Единственный вход — внутренняя команда `billing_registry` существующего
  server CLI. По умолчанию она только проверяет; запись требует `--execute`.
  Браузер, desktop, публичный API и обычный worker нового доступа не получают.
- До чтения CSV и каждого обращения к хранилищу применяется существующий
  `require_billing_maintenance_database`: PostgreSQL, реальные `session_user`
  и `current_user` равны `twobrain_rec_maintenance`, `row_security=on`, нет
  superuser/BYPASSRLS, разрешён контекст `billing_reconciliation` / `billing`.
  Переданный URL, имя исполнителя или `SET ROLE` не заменяют эту проверку.
- `shop_id` и `environment` берутся только из серверных Settings. Команда не
  принимает их как параметры доверия. Вход доверен лишь как экспорт,
  предоставленный уполномоченным оператором: CSV не имеет проверяемой подписи.
  Совпадение имени и шапки не доказывает подлинность или режим test/production.
- Общий результат магазина хранится отдельно от tenant-данных: две небольшие
  таблицы `billing_registry_imports` и `billing_registry_gaps`, без workspace.
  Обе имеют ENABLE/FORCE RLS и политику только для указанной реальной роли и
  контекста. Request/обычный worker, Owner/Admin/Member любого workspace не
  могут читать или менять их. Добавить обе в фактический RLS inventory и
  проверить права на отдельной PostgreSQL, включая неверный operation/area.
- `BillingAuditEvent.workspace_id` остаётся обязательным. Ни общий отчёт,
  ни неопознанная строка не записываются в произвольно выбранное workspace.
  Импорт не меняет invoice, entitlement, recurring consent или provider state.

## Поддерживаемый профиль и полнота — B2

Один профиль `yookassa-ru-csv-v1`: русская официальная выгрузка с framing,
разделителем `;`, строгой UTF-8 (допустим начальный BOM). UTF-8 — ограничение
GRAF, а не утверждение о кодировке всех магазинов YooKassa. Неподдерживаемый
профиль требует нового проверенного решения; эвристического fallback нет.

- Имена: `yoomoney-payments-<shop>-YYYY-MM-DD.csv` и аналогичное `refunds`;
  части: `...-part-N.csv`, конечная `...-part-N-last.csv`. Проверить kind,
  shop, дату по имени, виду реестра и шапке документа. Дата — день операций
  Europe/Moscow; контрактный номер не сохранять. Не требовать выдуманный
  столбец `shop_id` или `environment` в каждой строке.
- Payments: обязательны идентификатор, сумма, валюта и время платежа.
  Refunds: идентификатор возврата, исходного платежа, сумма, валюта и время
  возврата. Использовать точные русские имена из официального описания.
  Проверить непустые ограниченные идентификаторы, RUB, положительную точную
  сумму с двумя десятичными знаками и время `dd.MM.yyyy HH:mm:ss` в дне
  отчёта. День платежа определяется подтверждением, возврата — созданием;
  `Invoice.created_at` и локальный `observed_at` их не заменяют.
- Заголовки уникальны; ширина всех строк совпадает. Дополнительные официальные
  поля можно разобрать, но их значения не сохранять и не выводить. В footer
  проверить общее число операций и gross-сумму платежей/возвратов против строк;
  для payments также проверить присутствующие count/gross итоги по типам через
  обязательный `Тип платежа`. Комиссии, НДС, net и обеспечение не являются
  проверяемыми итогами этого профиля: их разбор не означает финансовый PASS.
  Контракт/магазин footer, если присутствуют, не противоречат шапке.
- Уникальность операции проверяется внутри kind по всему набору частей;
  несколько разных возвратов одного платежа допустимы. Одинаковая операция
  в двух частях, повтор номера части, single+multipart, два last и часть после
  last отвергаются. Для multipart требуются все номера 1..N и ровно один last;
  отсутствие номера/last сохраняет неполноту. Непоследняя часть содержит
  10 000 операций, последняя — 1..10 000; один пустой multipart недопустим.
- Оба вида обязательны для каждого дня. Пустоту подтверждает только реально
  присутствующий корректный single CSV с нулевым footer и явным
  `--expect-empty payments|refunds`; отсутствие файла всегда остаётся gap.
  Непустой файл с `--expect-empty` отвергается.
- Ограничения GRAF: не более 64 файлов на день, 16 MiB на файл и 64 MiB на
  весь вход; превышение отклоняется до неограниченного чтения. SFTP, XLSX,
  английский профиль и конвертация кодировок в этот вход не входят.

## Сохранение и восстановление — B3

- Область сериализации: `(environment, shop_id, Moscow date)`, включая разные
  версии профиля. Использовать существующий PostgreSQL transaction advisory
  lock pattern. В одной транзакции сохраняются receipt, gap transitions и
  ссылка на предыдущий принятый receipt. Сбой не оставляет половины результата.
- Receipt неизменяем: последовательный id, scope, profile/config fingerprint,
  SHA-256 фактических байтов каждого файла, part/kind/count, digest набора,
  признак expected-empty, полнота, безопасный код результата, server UTC time,
  фактическая DB identity и проверенная метка оператора. Метка не даёт права.
  Никаких CSV, исходных путей, контрактных номеров, provider object IDs,
  денежных сумм, контактов или свободного текста ошибок в таблицах/выводе.
- Дедупликация: scope + profile/config fingerprint + digest входа. Повтор
  принятых байтов после перезапуска возвращает прежний receipt без новых gaps
  или изменения deadline. Исторический replay не делает старый receipt текущим.
  Первое принятие может быть неполным и обязано сохранить missing gaps.
- Канонизация обоих hashes: UTF-8 JSON с отсортированными ключами и без
  незначащих пробелов. Versioned config fingerprint включает profile/schema
  version, encoding/delimiter/language, обязательные имена полей, правила
  даты/identity/footer/multipart/empty и все пределы объёма. Изменение любого
  правила меняет версию/отпечаток, скрытого validation-параметра нет.
  Digest входа включает scope, config fingerprint, отсортированный список
  expected-empty kinds и отсортированные по `(kind, numeric part index)`
  записи `(kind, part index, last, expected-empty, SHA-256 фактических байтов)`.
  Single имеет index 1/last=true. Пути, owner/operator и порядок argv в hashes
  не входят; одинаковые байты разных частей не становятся одной частью.
- Изменение принятого набора, включая добавление пропущенной части, требует
  `--replace <digest текущего принятого receipt>` и ограниченного reason code.
  После получения lock повторно сравнить digest; устаревшая замена отвергается.
  Отсутствие ожидаемого текущего receipt тоже конфликт. Удалений истории нет.
- Отклонённая попытка при `--execute` сохраняет только безопасный error receipt
  и owned gap, не заменяет последний принятый набор и не закрывает его gaps.
  Неудачное чтение/валидация или потеря БД возвращают ненулевой exit code;
  невозможность сохранить ошибку никогда не выдаётся за успешный импорт.
  Вывод различает последнюю попытку, последний принятый набор и открытые gaps.
- Gap имеет стабильный scope/kind/part/reason key, receipt обнаружения,
  `severity=high`, обязательного именованного `--owner`, detected/checked UTC,
  deadline не позднее 24 часов от обнаружения, containment `report_unverified`
  и состояние `detected|resolved`. Повторная проверка сохраняет исходные owner
  и deadline. Восстановление подтверждает новый принятый набор; только тогда
  gap получает resolution code, actor, time и closing receipt. История
  закрытого gap не переписывается: повторный дефект создаёт новое поколение.
  Произвольного `accepted_risk`/ручного закрытия финансового gap здесь нет.
- Dry-run не пишет. После перезапуска status читает сохранённый результат без
  CSV. Raw CSV никогда не копируется в БД/логи/evidence; исходный экспорт
  остаётся под внешней финансовой политикой оператора, команда его не удаляет.

## Приёмка и границы

В изолированной PostgreSQL проверить реальный CLI → guard → parser → commit →
новый процесс/status, повтор, неполный набор, безопасную замену, конкуренцию,
rollback и сохранение прежнего результата при повреждённом входе. Проверить
реальные права request/worker/maintenance и отсутствие приватных полей в выводе.

`files_complete=true` означает лишь полноту/валидность двух наборов файлов.
До отдельного сравнения их операций с ledger и authenticated provider GET/list
финансовый результат равен `financial_status=not_checked`. Неизвестный provider
ID, несовпадение суммы/даты/магазина и отсутствие операции требуют owned gap;
такую сверку нельзя заменить подсчётом строк или локальным временем invoice.
До доказательства всего T075 задача и #4930 остаются открытыми. T074/T078,
живой test-shop, real-shop canary, выпуск и открытие продаж отдельно.
