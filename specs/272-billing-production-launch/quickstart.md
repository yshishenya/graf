# Как проверить выход на реальные платежи

Короткая инструкция: что уже проверено машинно, что проверяется одной командой, и
что может проверить только владелец продукта.

## 1. Проверено машинно (повторять не нужно)

| Что | Чем подтверждено |
| --- | --- |
| Каталог цен создаётся сам | миграция `0093_billing_catalog_seed` прогнана на чистой базе: две строки, повторный прогон без дублей, откат удаляет только сеяные строки |
| Вход создаёт аккаунт | прогон на настоящей базе: неизвестный адрес получает код, аккаунт появляется только после подтверждения кода, ограничение частоты и аудит целы |
| Обрыв связи с провайдером восстанавливается | тест на настоящей базе: потерянный ответ, поздний вебхук, связывание по метаданным, доступ выдан один раз |
| Зависшая операция больше не блокирует оплату | тест на настоящей базе: до исправления операция уходила в `unknown` и блокировала оплату навсегда, после — отменяется вместе со счётом; негативный контроль на прежней версии кода дал 2 падения из 4 |
| Продление: три попытки заранее и письмо | тесты: расписание −72/−48/−24 часа, свой ключ на каждую попытку, отказ первой и второй попытки сохраняет автопродление, отказ третьей отзывает, письмо содержит дату отключения |
| Досрочная оплата и переход на год | тест сквозного пути: год оплачивается поверх активного месяца, срок продлевается от текущей даты окончания, повтор не создаёт второй платёж |
| Аварийная остановка удалена | поиск по коду, инфраструктуре и тестам не находит упоминаний; доказано, что при выключенном флаге оформления оплаты ни один платёж не создаётся |
| Денежный путь целиком | `apps/server/tests/unit/test_billing_money_path_e2e.py` — идёт в обычной проверке на pull request |

## 2. Проверяется одной командой

```sh
cd apps/server
UV_CACHE_DIR=/tmp/uvcache bash scripts/run_local_postgres_tests.sh --full -q
```

Полная проверка перед развёртыванием:

```sh
infra/scripts/ci-local.sh --full
infra/scripts/cd-remote.sh --dry-run
```

## 3. Что может проверить только владелец продукта

### 3.0 Что уже подтверждено на боевом сервере

Проверено чтением 19 сентября 2026 года, без изменений в боевой среде:

- Боевая база стоит на ревизии `0092_recording_origin_cancel`. После
  развёртывания применится только миграция `0093_billing_catalog_seed`, и она
  ничего не изменит: обе строки каталога уже есть и совпадают с ней.
- В таблице операций нет ни одной операции продления — только пять операций
  первого оформления. Значит, переходить на новый порядок продления не с чего:
  старых записей, которые новый планировщик мог бы не увидеть, нет.
- Лишняя строка `TWOBRAIN_BILLING_EMERGENCY_STOP` в `.env` безвредна: настройки
  читаются с `extra="ignore"`, поэтому служба запустится и с ней. Удалить её
  можно в любой момент.

### 3.1 Переключить магазин на боевой

Магазин — это настройка сервера, а не код. В `/opt/projects/2brain-rec/.env`
пять строк:

| Строка | Сейчас | Нужно |
| --- | --- | --- |
| окружение платежей | `test` | `production` |
| идентификатор магазина | `1436758` | `1430118` |
| секрет API | `./secrets/twobrain_yookassa_test_secret` | `./secrets/twobrain_yookassa_secret` |
| секрет вебхука | `./secrets/twobrain_yookassa_test_webhook_secret` | `./secrets/twobrain_yookassa_webhook_secret` |
| секрет рефералов | `./secrets/twobrain_billing_test_referral_secret` | `./secrets/twobrain_billing_referral_secret` |

Флаги оформления оплаты и наблюдения за провайдером уже включены, коды чека
(система налогообложения 2, ставка НДС 1) уже верные и менять их не нужно.
Оставшуюся строку `TWOBRAIN_BILLING_EMERGENCY_STOP` можно удалить: код её больше
не читает.

Порядок: остановить оформление оплаты → заменить пять строк → `docker compose up -d`
→ установить границу вебхука (ниже) → зарегистрировать в кабинете ЮKassa адрес
`https://rec.2brain.pro:8443/api/v1/billing/providers/yookassa/webhook/production`
→ включить оформление оплаты.

### 3.2 Установить защиту вебхука

```sh
infra/scripts/install-billing-webhook-edge.sh --dry-run
infra/scripts/install-billing-webhook-edge.sh --execute
```

Смотреть на поля `secret_probe_production` и `secret_probe_test`: хотя бы одно
должно быть не `401`. `503` — это успех (секрет принят, уведомление без
метаданных рабочего пространства отложено). `401` на обоих путях означает
расхождение секретов, скрипт сам откатит изменения.

### 3.3 Подписка с автопродлением из тестового магазина

В боевой базе одна подписка с включённым автопродлением и оплатой до 29 сентября
2026 года, а также одна без автопродления с оплатой до 25 сентября. Их способы
оплаты сохранены тестовым магазином, поэтому после переключения списание по ним
не пройдёт: человек получит три письма о неудаче и 29 сентября перейдёт на
бесплатный тариф. Окно первой попытки открывается 26 сентября.

Решите заранее, что с ними делать: отключить автопродление, попросить оплатить
заново в боевом магазине или оставить как есть.

### 3.4 Живая оплата

1. Войдите в кабинет новым адресом — код из письма создаст аккаунт.
2. Откройте тарифы и оплатите 1 000 ₽ за месяц реальной картой.
3. Убедитесь, что доступ выдан, а в кабинете ЮKassa появился чек.

Отдельно, если пользуетесь приложением macOS: оплата внутри приложения — это
цепочка переходов «кабинет → ЮKassa → страница банка → возврат в кабинет».
Проверьте её в том приложении, которым пользуетесь. Два известных ограничения:

- если ваш банк открывает подтверждение в новом окне, окно может не открыться —
  сообщите, это отдельная правка;
- если подтверждение занимает больше 15 минут, цепочка закрывается; это одна
  константа, поправим.

## 4. Что осталось незакрытым

- Реальные платежи не включены: сервер всё ещё указывает на тестовый магазин.
- Шесть подписей ответственных в `docs/runbooks/billing-launch.md` (раздел 5)
  остаются `pending`; по правилам этого руководства они блокируют включение.
  Подписи ставит владелец продукта, агент их не выдумывает.
