# Feature Specification: Восстановление отчётов поддержки

**Feature Branch**: `codex/111-support-incident-recovery`

**Created**: 2026-07-17

**Status**: Draft

**Input**: User description: "Исправить отправку отчётов в поддержку: подробный безопасный отчёт должен попасть на сервер и создать понятный private Issue, а не оставлять пользователя с общим сообщением об ошибке."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Отправить отчёт о неудачной записи (Priority: P1)

Пользователь видит локально сохранённую запись, которую не удалось отправить автоматически, и отправляет безопасный отчёт в поддержку из приложения.

**Why this priority**: Без этого пользователь не может передать команде достаточные сведения для восстановления своей записи и вынужден повторять проблему вручную.

**Independent Test**: На воспроизводимой неудачной записи авторизованный пользователь отправляет отчёт и видит номер принятого обращения; в private Issue есть структурированное описание сбоя.

**Acceptance Scenarios**:

1. **Given** доступную безопасную сводку неудачной записи и рабочую поддержку, **When** пользователь нажимает «Связаться с поддержкой», **Then** сервер принимает отчёт, создаёт или обновляет private Issue и приложение показывает номер обращения.
2. **Given** повтор той же первопричины в том же рабочем пространстве, **When** пользователь отправляет отчёт ещё раз, **Then** поддержка получает один агрегированный Issue с актуальным числом затронутых записей, а не набор неразличимых дублей.

---

### User Story 2 - Понять проблему по обращению (Priority: P2)

Инженер поддержки открывает созданный Issue и получает достаточно контекста, чтобы определить сбой, версию приложения, этап обработки и безопасный корреляционный идентификатор без запроса у пользователя приватных данных.

**Why this priority**: Созданный Issue должен сокращать время диагностики, а не быть пустым сигналом о том, что «что-то не сработало».

**Independent Test**: Проверка сгенерированного Issue подтверждает стабильные разделы с кодом проблемы, категорией, состоянием записи, версиями, безопасными fingerprint-идентификаторами, временной линией и состоянием синхронизации, без запрещённых данных.

**Acceptance Scenarios**:

1. **Given** принятый отчёт, **When** поддержка открывает его Issue, **Then** описание содержит объяснимый код и категорию сбоя, релевантные безопасные диагностические поля и действия для следующей проверки.
2. **Given** отчёт содержит аудио, текст расшифровки, токен, подписанную ссылку, путь на Mac или содержание встречи, **When** он проходит обработку, **Then** сервер не сохраняет и не отправляет эти данные в Issue.

---

### User Story 3 - Получить честный результат при деградации поддержки (Priority: P3)

Пользователь получает понятный результат, если сервер принял отчёт, но Issue пока не синхронизирован, либо если отправить отчёт сейчас невозможно.

**Why this priority**: Текущее общее сообщение «Попробуйте ещё раз» не показывает, был ли отчёт потерян, и не даёт поддержке надёжного пути восстановления.

**Independent Test**: Имитировать недоступность GitHub, ошибку конфигурации и сетевой таймаут; приложение различает сохранённый сервером отчёт, повторяемую временную ошибку и окончательно отклонённый небезопасный отчёт, не обещая несделанного.

**Acceptance Scenarios**:

1. **Given** сервер сохранил безопасный отчёт, но private Issue временно недоступен, **When** пользователь отправляет его, **Then** интерфейс честно сообщает, что обращение принято сервером и ожидает синхронизации, с номером для поддержки.
2. **Given** отчёт нельзя безопасно принять или пользователь не авторизован, **When** отправка завершается ошибкой, **Then** интерфейс называет понятный следующий шаг и предлагает безопасную копию отчёта, не утверждая, что обращение создано.

### Edge Cases

- В production отсутствует, нечитаем или не имеет нужного доступа серверный ключ интеграции с private Issue-трекером.
- Private Issue-трекер отвечает отказом доступа, ограничением частоты или таймаутом после того, как сервер уже принял отчёт.
- Приложение повторно отправляет тот же отчёт после сетевого обрыва или перезапуска.
- Один пользователь отправляет несколько записей с общей первопричиной, а другой — независимую проблему в другом рабочем пространстве.
- В локальной диагностике случайно присутствует запрещённое содержимое или персональные данные.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST принимать от авторизованного desktop-клиента только metadata-only отчёт о неудачной записи и присваивать ему безопасный корреляционный номер до попытки синхронизации с private Issue-трекером.
- **FR-002**: Система MUST создавать или обновлять private Issue для каждого принятого класса проблемы и включать в него стабильное структурированное описание: код и категорию сбоя, этап обработки, безопасные состояния записи, версию клиента и диагностических схем, временные метки, ограниченные fingerprint-идентификаторы и статус синхронизации.
- **FR-003**: Система MUST сохранять и повторно использовать принятый безопасный отчёт при временной недоступности Issue-трекера, не требуя от пользователя повторно собирать диагностику.
- **FR-004**: Desktop-клиент MUST различать: обращение принято и Issue синхронизирован; обращение принято и ожидает синхронизации; обращение не принято. Каждое состояние MUST иметь понятный следующий шаг.
- **FR-005**: Система MUST дедуплицировать одинаковую первопричину только в пределах допустимой области и обновлять число затронутых записей и ограниченный набор безопасных идентификаторов в существующем Issue.
- **FR-006**: Система MUST не помещать в отчёт, серверное хранение, Issue, логи или доказательства raw audio, текст расшифровки, AI-выводы, токены, credentials, подписанные URL, локальные пути, имена людей, email, названия встреч или иное приватное содержимое.
- **FR-007**: Система MUST проверять конфигурационную готовность private Issue-интеграции при запуске, проверять private repository перед синхронизацией и наблюдаемо сообщать оператору о конфигурационной ошибке без раскрытия секрета.
- **FR-008**: Система MUST сохранять идемпотентность повторной отправки и не создавать несколько Issue из-за сетевого обрыва после принятия отчёта.
- **FR-009**: Пользователь MUST иметь доступный способ скопировать безопасный отчёт, когда сервер не может принять его, а интерфейс MUST не ограничиваться неопределённым «Попробуйте ещё раз».

### Key Entities *(include if feature involves data)*

- **Support incident**: Серверное metadata-only обращение с безопасным номером, статусом принятия, статусом синхронизации и ссылкой на private Issue после её появления.
- **Diagnostic report**: Проверенная и отредактированная безопасная сводка технических фактов о неудачной записи.
- **Issue synchronization**: Состояние доставки принятого обращения в private Issue-трекер, причина последней безопасной ошибки и время следующей допустимой попытки.
- **Incident aggregate**: Ограниченная совокупность повторяющихся обращений одной первопричины в одной допустимой области.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: В проверяемом production-пути корректный отчёт о неудачной записи получает серверный номер обращения не более чем за 5 секунд; при доступности Issue-трекера он содержит номер private Issue в том же результате.
- **SC-002**: Каждый созданный private Issue содержит все обязательные безопасные диагностические разделы и не содержит ни одного запрещённого класса данных в автоматизированной проверке.
- **SC-003**: При недоступности Issue-трекера 100% принятых отчётов остаются доступны для повторной синхронизации без повторной отправки пользователем.
- **SC-004**: Во всех проверенных ошибочных сценариях пользовательское сообщение однозначно различает «не принято», «принято и ожидает синхронизации» и «готово».
- **SC-005**: Повторная отправка одного и того же отчёта не создаёт более одного private Issue.

## Assumptions

- Существующий серверный private Issue-трекер остаётся единственным местом, куда доставляются support incidents; desktop-клиент не получает его credentials.
- В существующей authenticated desktop-сессии уже есть достаточный контекст рабочего пространства и устройства для серверной проверки области доступа.
- «Вся необходимая отладочная информация» означает полный набор безопасных metadata-only фактов; приватное содержимое и секреты остаются исключёнными независимо от удобства диагностики.
- Новая архитектура трассировки, внешняя аналитика и отправка аудио или расшифровки не входят в эту фичу.
