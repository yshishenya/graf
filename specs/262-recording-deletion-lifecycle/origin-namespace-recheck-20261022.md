## Результат

В существующем файле были девять случаев: отмена до/после создания,
идемпотентность, конкуренция и оба управляемых порядка блокировки,
RLS отдельной ограниченной роли, неизменность маркеров, ограниченный lookup,
отказ при смене контекста и ограничение частоты с Retry-After.

Обнаружен пробел проверки полного HTTP-пути для одинакового
`local_recording_id` в двух разрешённых контекстах. Добавлен один
параметризованный тест, два случая:

- разные пользователи одного пространства;
- один пользователь в корпоративном и личном пространствах.

Использованы настоящие активные membership и зарегистрированные устройства.
Авторизация, селекторы и блокировки не подменяются. Встреча B создаётся первой;
отмена A возвращает собственный `origin_cancellation` без meeting ID и
сохраняет встречу B без изменения deletion state/epoch. Поздний create A
отклонён с `409 recording_deletion_active`; повтор create B возвращает прежний
ID. Повтор отмены A сохраняет исходное подтверждение. Только явная отмена B
возвращает `meeting_deletion` её встречи и повышает её epoch.

Для второго общего origin обе стороны отменяют создание заранее: PostgreSQL
содержит ровно два разных маркера полных identity, ни одной встречи;
подтверждения различаются и сохраняются при повторе, оба late create отклонены.
Состояние и количество строк проверены непосредственно в PostgreSQL.

Дефекта рабочего кода этими проверками не обнаружено. Это дополнение
покрытия существующего требования, а не исправление воспроизведённого сбоя.
Создание отдельной архитектуры или ещё одного конкурентного набора не нужно.
