## Проверка координации и ограничения сети

- `lifecycleSyncTask`, накопление priority IDs и окончательное исчерпание защищены одной serial queue; ожидание task и HTTP находятся снаружи. Task регистрируется до доступного ему следующего входа в queue. UUID cleanup в `defer` не очищает задачу следующего поколения.
- Отмена одного ожидающего caller не отменяет общий проход. `setDeletionScope` увеличивает generation и очищает priority, visibility, cursors и ссылки на старые задачи под queue; сами `cancel()` вызываются снаружи. Проверки после HTTP и перед save отбрасывают старый результат.
- Public `refreshDeletionScope` при активном lifecycle присоединяется к нему; внутренний `recoverLegacy: false` этой веткой не пользуется, поэтому самоприсоединения нет. Короткие независимые context refresh объединены. Legacy task отдельный и ограниченный; медленная или неуспешная старая запись не задерживает known-owner targeted invalidation.
- У сетевого actor не более двух активных разрешений; очередь ожидающих FIFO. Разрешение охватывает только фактический executor, не вложенный capability/context adapter, decode, callback renewal или весь многошаговый метод. Нет удержания двух разрешений одним вложенным вызовом.
- Отмена ожидающего удаляет и завершает именно его continuation, не уменьшает число занятых слотов. Успешный grant устанавливает `defer release`, затем проверяет cancellation до executor. Если grant и cancellation пересекаются, либо continuation уже отменена и слот не получен, либо слот возвращается через `defer`. Двойного resume/утечки по прочитанному коду не найдено.
- Ошибка executor также возвращает разрешение. Управляемая проверка подтверждает завершение отменённого ожидания **до** освобождения удержанных HTTP, отсутствие его отправки и последующий запрос после ошибок.
- Охват adapter paths: native notification-context, own-origin lifecycle, destructive request, meeting fallback lifecycle, sync-state/reconcile, list purge tasks, ensure purge task, purge ACK. Scope copies сохраняют actor и chained before-request callback. Upload bytes, capture и посторонние API этим actor не ограничиваются.
- `checkingDeletionContext` для deletion/purge проверяет текущие scope/generation непосредственно перед HTTP. `execute` после ожидания разрешения проверяет актуальную native session и authentication fingerprint; затем выполняет acceptance и накопленный before-request guard. Вызовы остаются вне долгой queue/UI блокировки.

## Production путь видимости, открытия и player

App передаёт видимые IDs через `DesktopCabinetWorkspaceView` и все make/update/coordinator связи. Bridge принимает только версию 1, максимум 100 уникальных существующих native row IDs; разрешены текущие list/detail, для detail обязателен matching UUID встречи. Сохраняются проверки active coordinator, main frame, attached WebView, document URL и route policy. Hint не разрешает доступ и не является основанием purge.

JS публикует metadata-only IDs, без файловых путей, токенов и содержимого встреч. Учитываются viewport, clipping ancestors, linked aliases, фильтрация/исчезновение и detail identity. События scroll/resize/visibility и обновления native projection объединяются через requestAnimationFrame; результат ограничен 100. Detach, provisional navigation и termination очищают native hints. Недоказанного изменения authority в этом пути не найдено.

Open передаёт item ID в общий проход и после await заново получает разрешённый playback URL и lifecycle projection. Periodic production caller добавляет текущий managed player ID; видимость добавляется сервисом. `LocalRecordingPlayer` раскрывает только чтение item ID; правила закрытия и освобождения AVPlayer не изменены. Activation/wake/periodic triggers и существующий network reconnect caller просмотрены: reconnect уже сначала ожидает synchronization, затем вызывает общий upload refresh.

## T025: точный смысл ограниченного разброса

Множитель `0.8 + 0.4 * Double(id.uuid.0) / 255` определяется существующим случайным UUID операции. Он не меняется между процессами, не использует Swift Hasher и не требует нового поля/схемы/генератора. Расчётные интервалы: 4–6, 12–18, 24–36 и 48–72 секунд для номинальных 5/15/30/60.

Очередь хранит ISO8601 с секундной точностью, поэтому сохраняется `ceil(now + calculatedDelay)`. К расчётному сроку добавляется от 0 включительно до 1 секунды исключительно вверх; фактический общий верхний предел соответственно строго меньше 7/19/37/73 секунд. Это отдельно от множителя 0,8–1,2: утверждать точный предел 6/18/36/72 для дробных часов было бы неверно. Контракт не задаёт жёсткого потолка 60 секунд; добавленное квантование ограничено, сохраняется при restart и не даёт раннего повтора.

`waiting(until:)` сохраняет максимум существующего срока и серверного Retry-After, также округляя вверх. Accepted/verified не получают retry и не регрессируют. Повторное применение того же состояния не пересчитывает сохранённый deadline. Тесты используют UUID 00/ff/83, обе цели, часы с долями 0/0,25/0,99, все ступени и плато, настоящий ISO8601 и более ранний/поздний серверный срок.
