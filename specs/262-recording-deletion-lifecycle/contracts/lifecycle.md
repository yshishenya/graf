# Контракты жизненного цикла F262

## Команды приложения и WebView

Действия open/send и переход к отчёту используют существующие механизмы. Новый `deleteSelection` принимает version=1, requestId, localIds и meetingIds (всего 1–100, без дублей). Повтор долговечной операции выполняет native executor. Контекст и поколение сессии определяются native, не принимаются от WebView. Результат содержит saved и количества accepted/pending/rejected; timeout bridge означает неизвестный ответ, а не подтверждение сохранения. URL/пути, credentials и произвольный JavaScript не принимаются.

На desktop существует один исполнитель delete в native: JS передаёт подтверждённую команду и получает authoritative projection, не запускает одновременно самостоятельный fetch удаления. Web-only выполняет тот же lifecycle через server route. No-JS форма остаётся рабочей. Неизвестный bridge version не должен незаметно включать legacy local-row merge: показывать понятное требование обновления; web server-delete остаётся доступен отдельно.

Перед удалением desktop проверяет session scope, фиксирует выбранный набор, повторно проверяет capabilities, сохраняет операции и только после этого начинает запросы. Bulk содержит не более 100 текущих допустимых записей; большее число требует нескольких явных выборок. Один пользовательский объект выполняется один раз, даже если пришли local/server aliases.

`projection` содержит неприватные identity aliases, lifecycle generation, состояние и capabilities. Рендерер выбирает одну строку по identity до сортировки/фильтра/счётчиков. Для связанных серверных встреч фильтр и пагинация задаются сервером; native не добавляет их как local-only, если они не пришли в выдаче. Чисто локальные записи фильтруются локально и маркируются как локальные. Selection хранится по identity и переносится на alias, не по DOM-node.

## Серверные операции

### Существующее удаление по meeting_id

Сохранить действующий POST deletion-requests и HTML fallback, добавить явный JSON receipt для новых клиентов через согласованный content negotiation или отдельный typed adapter. Receipt: request_id, meeting_id, phase=accepted, deletion_epoch, report route. HTTP 202 означает только принятие. Повтор после принятия авторизованному lifecycle manager возвращает тот же результат, а не ошибку из обычного content access resolver. Недоступный чужой объект по-прежнему не раскрывается.

Для повторного запроса права на deletion report проверяются отдельно от права читать уже удалённый контент. 401/403/404 не являются доказательством удаления. Неоднозначный ответ разрешается через receipt/report или sync-state исходной собственной записи.

### Новая отмена по origin

Проект маршрута: `POST /api/v1/desktop/recordings/{local_recording_id}/deletion-requests`.

Тело: operation_id, confirmation_boundary. Server/workspace/user/device берутся из аутентифицированной сессии; тело не может задавать другого creator. local_recording_id валидируется по существующим ограничениям ingest. Метод доступен только для origin текущего пользователя, общий manager-delete остаётся по meeting_id.

- В общей с create транзакционной блокировке найти Meeting или cancellation.
- Meeting существует: существующий lifecycle service создаёт/возвращает запрос удаления с проверкой права.
- Cancellation существует: вернуть тот же receipt.
- Ни одного объекта нет: сохранить metadata-only origin cancellation и вернуть принятие без создания Meeting, media revision, календарной привязки и processing job.
- Late create проверяет origin cancellation до побочных эффектов и получает `409 recording_deletion_active`; владелец может запросить безопасный receipt. Отсутствие Meeting не отменяет запрет.
- Серверная идемпотентность задаётся target identity; operation_id служит корреляцией. Неизменность target у operation_id проверяет сохраняемая клиентская операция; сервер не обещает глобальную уникальность correlation ID без отдельного хранения. Каждый запрос независимо авторизует target.
- Применить существующие ограничения частоты destructive запросов, bounded body и лимит 100 операций в batch; cancellation rows доступны только в допустимом scope и не позволяют перечислять чужие origins. Не добавлять публичный endpoint без авторизации.

### Состояние собственных origins

Переиспользовать existing sync-state selector/authorization. Для эффективности добавить bounded batch adapter максимум 100 origins с результатом по каждому: live/deletion_accepted/canceled_before_creation/unknown/denied. Не возвращать title/content для denied/unknown. Для canceled_before_creation вернуть metadata-only receipt без вымышленных meeting_id или revision.

При неизвестном/недоступном состоянии файлы не удаляются. Для отклика на удаление другого устройства visible/open origins проверяются с интервалом до 30 секунд, остальные перед показом/командой и фоновыми страницами. Только один цикл на scope, отмена запросов при смене scope; старые ответы отвергаются по generation. Backoff 5/15/30/60 секунд с jitter, уважать Retry-After; ошибки не снимают tombstone.

Для server-only и доступных встреч другого владельца этот же цикл использует bounded lookup по meeting_id через существующий access/lifecycle resolver, не через owner-origin API. Новый адаптер переиспользует его проверки и выдаёт allowed/deletion_accepted/unavailable в пределах прав. Unavailable/denied закрывают содержимое, но не доказывают удаление и не разрешают purge. Execution scope — аккаунт исполнителя, target creator хранится отдельно.

SC-003 относится к активному приложению. Обычная активная web-вкладка использует существующее обновление detail/list с terminal invalidation; после фокуса/повторной навигации заново проверяет доступ. Гарантия 60 секунд для фоновой/замороженной браузером вкладки не заявляется. Ни один вариант не разрешает новые server media requests после подтверждённого удаления.

### Purge

Существующие list/ack endpoints сохраняются. Клиент рассматривает незавершёнными pending, claimed, failed, unreachable, expired, local_expiry_relied_upon, если ещё хранит связанные данные. Вне зависимости от label сначала проверяет актуальное серверное основание и scope; timeout не разрешает purge.

Разрешён новый монотонный переход terminal failure/expiry → acknowledged с существующими verification reason codes и аудитом. Удаление/недоступность одного известного пути недостаточно: требуется проверка всех управляемых артефактов пакета, производных кэшей и закрытие GRAF playback handles. Сервер получает bounded metadata, не приватные пути.

Для нового approved устройства без своего задания: идемпотентный ensure-task adapter к существующему create_local_purge_tasks для подтверждённо удалённой собственной записи. Unique по deletion request + device + task type. Старое device task не переassignяется и не считается подтверждённым новым устройством.

Эти task/report/ACK маршруты применяются только к receipt `meeting_deletion`. Для `origin_cancellation` Meeting не существует: серверный receipt подтверждает отсутствие созданного контента и запрет late create, native operation хранит проверенный результат очистки текущего Mac и показывает локальный отчёт. Не создавать фиктивные FK или серверный purge report; не заявлять проверку чужих неизвестных локальных копий.

## Пользовательские тексты

| Ситуация | Текст и действие |
|---|---|
| Подтверждение серверной/смешанной выборки | «Удалить N записей?»; «Записи станут недоступны в GRAF. Связанные данные на сервере и подключённых устройствах будут очищены.»; отдельное число записей только на Mac |
| Пределы подтверждения | «Скачанные файлы нельзя отозвать. Резервные копии и отключённые устройства очищаются по своим срокам. Журналы Generation Call, Langfuse и Temporal сохраняются по действующей политике.»; ссылка на подробности |
| Доказанно local-only | «Удалить запись с этого Mac? Она ещё не отправлялась на сервер.» |
| Запрос отправляется | «Удаляем…»; кнопки и открытие недоступны |
| Нет сети, desktop | «Удаление ожидает подключения»; запрос переживает закрытие приложения |
| Ответ потерян | «Проверяем, принято ли удаление»; не «Не удалось удалить» и не «Удалено» |
| Принято | Краткое «Запись удалена из списка» + «Состояние удаления»; без постоянного success-баннера |
| Частичный результат | «Из 5 записей: 3 удалены из списка, для 1 ожидаем подтверждение, 1 удалить не удалось»; повтор только нужных операций |
| Нет прав | «Нет права удалить эту запись»; актуализировать доступ; не очищать файл по этому отказу |
| Сбой локальной очистки | В отчёте «Не удалось очистить данные на этом Mac» + «Повторить»; запись не возвращается |
| Локальная очередь повреждена | «Не удалось подтвердить состояние локальных записей»; восстановление/поддержка, без автоматической отправки |

Без сети обычный браузер сообщает, что запрос не отправлен; не обещает долговечную очередь после закрытия вкладки. После возможной отправки состояние на следующем открытии выясняется с сервера. Отмены после принятия и корзины в этой фиче нет.

## Плеер и уже переданные данные

GRAF-managed local preview использует AVFoundation и opaque session ID; при deletion/access/scope change немедленно прекращает play, закрывает источник, инвалидирует seek/open. Server player получает terminal UI и освобождает audio source. Новые server media requests проходят прежние authorization/deletion gates. Уже скачанные браузером байты или открытый сторонний player физически не отзываются; нельзя заявлять гарантию остановки внешней программы. Для отключённого устройства remote delete неизвестен до связи — отчёт остаётся pending/unverified.
