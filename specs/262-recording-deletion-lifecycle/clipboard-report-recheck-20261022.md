# F262 T005/T018: копирование отчёта после повторного чтения очереди

Дата: 2026-10-22. Основа: `32680690d377871784e49149e677b54da77bac9b`.
Ветка: `codex/262-support-report-lifecycle`.
Дорожка: действующий срез Spec Kit; высокий риск удаления и диагностики.

## Причина и исправление

`TwoBrainRecApp.copySupportIncidentReport` вызывает
`DesktopUploadQueueService.supportIncidentReportText`. Этот метод читал
исходную запись очереди, хотя подтверждение удаления сохраняется отдельно
в `document.deletionOperations`. Временное поле `item.deletionOperation`
не сериализуется. Поэтому при повторном чтении uploaded/processed записи
со старым `deletionState=none` отчёт мог отсутствовать или сообщать старый
этап. Отправка отчёта уже использовала `projectLifecycle`.

Копирование теперь применяет тот же существующий `projectLifecycle` к
основной записи под прежней последовательной блокировкой очереди.
`affectedItems` нужны builder только для количества и безопасных отпечатков
идентичности; их состояние удаления не читается. Новый helper, формат,
сетевой запрос или физическая очистка не добавлены.

## Сходимость и границы

Узкая сверка FR-002/003/004/014/017/018 и плана «одна проекция» не выявила
другой обязательной реализации в исправленном clipboard пути. Текущий код
переиспользует прежние правила server/workspace и manager-delete. Сохранение
accepted состояния, неизвестное состояние и доступ к локальным файлам
проверяются общим профилем, включая предыдущие исправления PR #7711.

Это исправление само по себе не принимает весь индекс «Удаления», серверную
авторизацию отчётов или полную T018/#6893. Полная T005/#6880 требует отдельной
содержательной сверки terminal projection/local open и применимых сценариев.
Исторические installed/VoiceOver результаты не становятся свежей проверкой
новой сборки. Новый выпуск, production, замена общего GRAF Dev, пользовательские
данные и полная приёмка F262 не входят.

Перед слиянием обязательны независимое ревью, проверки процесса и три GitHub
проверки точного SHA и основы через `validate-pr-checks.py`. До содержательной
приёмки задач использовать `Refs`; не закрывать их по одному локальному PASS.

## Повторная проверка доступа после смены аккаунта

Замечание PR #7716 (discussion_r4343401130) выявило отдельную причину:
`projectLifecycle` честно сохраняет accepted deletion, даже когда текущий
аккаунт уже другой. Построение отчёта считало deletion достаточным основанием,
не проверяя `lifecycleAccessAvailable`. Копирование могло раскрыть прежние
служебные сведения; отправка и обновление обращения имели тот же пробел.
Ранний вывод о сходимости выше относился к восстановлению deletion и не
принимал этот путь доступа.

Один существующий сервис теперь проверяет каждый выбранный элемент перед
копированием, отправкой и обновлением: `projectLifecycle` и затем текущий
доступ. Чужой или неизвестный контекст даёт 403 до построения отчёта,
изменения submission и сети. Чужой вторичный элемент запрещает весь набор;
отсутствующий идентификатор больше не пропускается молча. Явный local_unbound
сохраняет локальный доступ. При возвращении исходного аккаунта отчёт снова
доступен. Семантика accepted deletion, включая другого actor управляющего,
не меняется. UI уже обрабатывает исключение до очистки буфера обмена.

Предварительный независимый обзор требований подтвердил достаточность
FR-009/019, ExecutionScope и существующих CHK001/006/008: оба чеклиста 10/10.
В существующий DesktopUploadQueueTests добавлена одна исполняемая проверка
copy/send/sync: смена аккаунта/пространства/сервера, выход, неизвестный owner,
разрешённые owner/local_unbound и чужой secondary, отсутствующий идентификатор и пустой набор. Проверяется отказ без
вызова submitter и без изменения байтов файла очереди. Старые положительные
образцы support явно обозначены local_unbound вместо неявного legacy_unknown.

Исходный код с новой проверкой: 1 XCTest, 98 нарушений ожиданий. Первый
запуск после исправления выявил ошибку самой проверки: XCTAssertNotNil
перехватывал ожидаемое исключение внутри autoclosure. Вызов вынесен перед
assertion; история обоих запусков сохранена. Общий профиль quickstart:
**167 разных XCTest PASS, 0 FAIL, 0 SKIP**, та же команда выбора, что выше.
Повторный запуск той же исправленной проверки на исходном runtime вновь дал
98 нарушений, 0 неожиданных ошибок; после возврата исправления выполнен
новый общий профиль. 96 сочетаний внутри нового теста не считаются отдельными XCTest.

Новый установленный клиент, публикация, production и полная T018 этой
проверкой не принимаются. Итоговое независимое ревью и обязательные проверки
нового PR SHA/основы выполняются отдельно перед слиянием.

## Итог повторного ревью terminal projection и асинхронной отправки

Повторная проверка выявила три дополнительных пробела текущей T005:
ссылка просмотра разрешалась по старым uploaded/processed признакам при
блокирующем lifecycle; общий отчёт мог включать недоступный вторичный
элемент; отправка и её поздний ответ не были привязаны к исходному сеансу.
Прежние выводы выше относятся к предыдущим частям и не принимают эти пробелы.

- Единственный положительный путь `reviewAvailable` теперь требует
  отсутствия `lifecycleBlocksContent`. Настоящий `UploadReviewLink` проверен
  для owner/rejected и denied/queued/sending/resolving/accepted/verified/
  terminalDeleted со старыми processed/access признаками. Origin cancellation
  не выдаётся за подтверждённое удаление серверной встречи.
- Общий `shouldShowNativeSummary` исключает элементы без текущего
  `lifecycleAccessAvailable` до выбора primary, группировки и подсчёта
  доступных кандидатов/attention и affectedItems.
  Законный отчёт владельца об удалении остаётся доступен.
- До построения запроса сохраняется снимок scope, его поколения, отпечатка
  сеанса клиента и общего поколения кабинета. Обязательный контекст запроса
  проверяется до dispatch, после await и внутри последовательной области
  проверки/записи ответа либо ошибки. Смена scope с возвратом также отменяет
  старый ответ. Поколение и барьеры навигации защищены коротким `NSLock`;
  под ним нет диска, JSON, `queue.sync` или `await`. Запись результата не
  заставляет `MainActor` синхронно ждать файловую операцию.
- WebKit перед `fetch` сравнивает origin, actor, workspace и session документа
  с исходным контекстом. Запрос передаёт expected actor/workspace в существующий
  серверный механизм; cookie и CSRF остаются внутри WebKit. После ответа
  заново проверяются контекст и принадлежность WebView. Старый сервер без
  такой проверки заголовков не получает гарантию автоматически.
- Пересекающиеся submit/sync отказывают до сохранения и второго сетевого
  вызова. Временный набор занятых IDs принадлежит существующей очереди,
  добавляется после успешного сохранения и освобождается `defer` на любом
  исходе. Persisted sending не используется как вечная блокировка повтора;
  существующее восстановление прерванной отправки сохранено.

### Решение по задачам и границы

T005/#6880 принята содержательно в области terminal projection/local open,
ссылок просмотра и отчёта. Применимые S01–S06, S27–S29 и S37–S39 сверены
с существующими guards, сохранёнными receipt и текущими регрессиями:
удаление имеет приоритет, unknown/denied не разрешают контент и не доказывают
физическую очистку. Историческая установленная интеграция остаётся историей;
новый код проверен на уровне сервисов, WebKit и PostgreSQL. До закрытия
обязательны новые exact-SHA/base checks PR #7716, защищённое слияние и live
валидатор с подробным комментарием.

Полная T018/#6893, T021/#6896 и вся F262 остаются открытыми. Общий GRAF Dev
не заменялся, выпуск, production, VoiceOver новой сборки и пользовательские
данные не затрагивались. Поддержка non-WebKit платформ этим macOS-срезом
не заявляется. Формат очереди/отчёта и основания очистки сохранены; внутренний
протокол отправки теперь требует контекст, HTTP добавляет expected headers.
