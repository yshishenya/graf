## Решение 1: одна идентичность, несколько независимых фактов

**Decision**: Одна пользовательская запись; серверная встреча и локальные файлы связаны устойчиво. Состояния загрузки, доступа, удаления и очистки остаются отдельными. Представление и допустимые команды вычисляются из этих фактов с приоритетом удаления.

**Rationale**: `.uploaded` описывает только транспорт. Оно не доказывает существование, доступность или возможность воспроизведения. DOM — результат фильтра/пагинации, он не источник жизненного цикла. Расширяем существующую custody projection и очередь, а не создаём параллельный общий framework.

**Alternatives considered**:

| Вариант | Вывод |
|---|---|
| Удалить ещё одну DOM-строку после fetch | Не переживает restart, remote delete и поздние native updates |
| Никогда не показывать uploaded локально | Устраняет симптом, но теряет честное восстановление при незавершённой передаче и не закрывает localPlaybackURL |
| Добавить JavaScript Set удалённых IDs | Нужен как кратковременная проекция, но не заменяет сохранённое состояние и серверный факт |
| Переписать кабинет в SPA / добавить отдельный sync service | Нет необходимости: существующие HTMX, WebKit bridge, очередь и PostgreSQL обеспечивают нужные границы |
| Общая модель идентичности и правил + существующие механизмы | Выбрано: закрывает все входы без переписывания capture/STT/хранилища |

## Решение 2: запрос сначала сохраняется, затем выполняется

**Decision**: Native сохраняет компактную deletion operation до HTTP; JS не исполняет самостоятельный параллельный desktop-delete. Обычный web использует тот же серверный lifecycle API, оставаясь без offline destructive queue.

**Rationale**: Потеря ответа и закрытие процесса не должны терять намерение. Pending intent блокирует upload/play локально; accepted tombstone монотонен. Сетевой отказ не разрешает удалять серверно связанные файлы без подтверждения. Ошибка прав завершает конкретную попытку отказом, но не отменяет ранее подтверждённый tombstone.

**Alternatives considered**: Ожидание сети без сохранения теряет действие; скрытое удаление локального файла до серверного разрешения создаёт потерю данных при отказе; полноценная offline очередь браузера требует дополнительной защиты аккаунтов и не нужна для исправления desktop.

## Решение 3: закрыть неизвестный результат создания на сервере

**Decision**: Добавить узкую отмену по origin identity для собственной записи. Если Meeting уже есть — использовать существующее request_meeting_deletion. Если ещё нет — сохранить минимальный запрет создания для этого identity; последующий create обязан его проверить в той же сериализованной транзакционной области. Таблица содержит только идентификаторы и факт отмены, не новую модель встречи или копии содержимого.

**Rationale**: Между отправленным create и полученным meetingId есть реальная гонка. Ни отсутствие строки, ни sync-state 404 не доказывают, что поздний create не завершится. Новый маркер нужен конкретно для запрета создания ещё не существующего объекта. Для уже созданных встреч источником остаётся существующий Meeting tombstone.

**Alternatives considered**: Повторить идентичный create и затем delete возможно для новых клиентов, если сохранять весь неизменный исходный payload. Текущий клиент строит его заново в createMeeting; для старой записи исходный fingerprint может быть невосстановим. Кроме того, это создаёт пользовательский объект ради удаления и требует сохранять лишние метаданные. Создавать фиктивный Meeting с вымышленной длительностью/ревизией тоже не выбрано. Один узкий metadata-only cancellation marker с общей блокировкой create/cancel лучше закрывает этот случай.

Точный проект контракта — [contracts/lifecycle.md](contracts/lifecycle.md). Для этой фичи допускается одна целевая миграция маркеров отмены и RLS; новые очередь сообщений, микросервис и общая event-sourcing система не нужны.

## Решение 4: согласование ограниченным циклом, очистка отдельно от upload

**Decision**: Использовать существующий upload scheduler, но выделить в нём координацию deletion/purge с независимым запуском: старт, активация, wake, восстановление сети, подтверждённое удаление; в активном подключённом состоянии проверка не реже одного раза в 30 секунд. Один выполняющийся цикл на контекст, повторные триггеры объединяются; purge не ждёт длинной отправки аудио.

**Rationale**: Пользователь не обязан переключать приложение для очистки. Проверка всех доступных локальных origins при первом старте/миграции и последующие ограниченные пакетные проверки ловят remote delete и смену регистрации устройства.

Проверка списка purge задач сама по себе недостаточна: новое device_id могло не получить старое задание. Нужен bounded batch lookup origins через тот же код существующего sync-state, с ответами по каждой записи. Пакеты до 100 элементов, не более двух запросов одновременно; запрашиваются прежде всего открытые/видимые и ожидающие удаления записи. Полный обход локального каталога на каждый таймер не выполняется.

**Alternatives considered**: Постоянный WebSocket и журнал всех серверных событий избыточны при текущем масштабе. Полный N+1 опрос всей истории каждые несколько секунд не выбран. SC-003 относится к доступным в текущем активном представлении/плеере связанным записям; остальные проверяются перед раскрытием/действием и фоновым обходом.

## Решение 5: завершение purge можно подтвердить позже

**Decision**: Для failed/unreachable/expired/local_expiry_relied_upon разрешить только направленный переход в acknowledged по существующему строгому metadata-only подтверждению. ACK должен совпадать с авторизованным устройством, workspace, meeting и текущим deletion request. Сохранить аудит предыдущей ошибки. Повтор acknowledged идемпотентен; понижение состояния запрещено.

Если новое одобренное устройство обнаружило собственную старую копию с доказанным удалением, сервер идемпотентно создаёт/возвращает задание для текущего устройства и существующего удаления. Оно не присваивает себе задание старого устройства. Отчёт показывает факты по каждому устройству; подтверждение нового устройства не выдаётся за проверку недоступного старого.

## Решение 6: GRAF управляет своим плеером

**Decision**: Локальный preview открывать внутри приложения через штатный AVFoundation, с минимальными Play/Pause, позицией, длительностью и закрытием. Серверный плеер сохраняется. Общие правила разрешения команд и инвалидирования сессии действуют для обоих. Не передавать file:// путь или байты в WebView.

**Rationale**: NSWorkspace.open передаёт файл сторонней программе; GRAF не может отозвать уже открытый файловый дескриптор. Нельзя обещать прекращение такого воспроизведения. Встроенный просмотр нужен для контроля удаления, а не для повторения всех функций сложного server player.

## Решение 7: миграция и восстановление — часть функции

**Decision**: Минимальное расширение существующего queue document: единая коллекция deletion operations, включая server-only, с execution scope исполнителя, отдельным target identity и подтверждением удаления. Item получает owner scope и поколение без второй deletion machine. Новые standalone записи получают доверенный local_unbound scope; старые legacy_unknown связываются только через проверенное соответствие. Терминальные deletion markers и незавершённые операции сохраняются при частичном восстановлении; повреждение не запускает автоматическую повторную загрузку.

Queue-файл уже записывается через LocalCustodyFileProtection: сохранить защиту и атомарность, дополнить тестом сбоя записи. До разрушения файлов запись operation/tombstone должна быть долговечной. Повреждённые данные сохраняются в карантине, а идентичность восстанавливается из manifest и сервера; неподтверждённые пакеты не открываются/не отправляются автоматически.

**Rationale**: Исправление обязано убрать уже существующие «призраки» без массового удаления по заголовку и без присвоения чужому workspace.

## Границы уверенности

Существующие исходники и серверные тесты прочитаны; выполняемая проверка исходного filter воспроизводит симптом. Нагрузка, новые API/миграции, межпроцессные гонки и работа установленного GRAF не проверены. Показатели времени — проектные цели, их нужно измерить. Отсутствие контента в старом manifest или доказанного owner scope ведёт в явное восстановление, не в догадку.
