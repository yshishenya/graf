# Quickstart: Feature 200 Windows desktop-приложение GRAF

Этот runbook предназначен для реализации и validation gate Feature 200.
В репозитории уже есть portable CMake contract surface и заготовка MSBuild/
MSIX; этот runbook не превращает их в доказательство готового Windows продукта.
Windows host обязателен для claims о WinUI/WebView2, WASAPI, Media Foundation,
MSIX и hardware.

## 1. Host prerequisites

- Windows 10 22H2 (19045) или поддерживаемый Windows 11; первый claim — x64.
- Visual Studio с C++/WinRT, Windows App SDK stable и Windows SDK без preview API.
- WebView2 Evergreen Runtime; отдельно проверяется сценарий отсутствующего или
  повреждённого runtime.
- PowerShell 7, `msbuild`, `ctest` и стандартные Media Foundation components.
- Для hardware evidence: встроенный/USB/Bluetooth microphone, HDMI/DisplayPort
  или dock render endpoint. RDP проверяется отдельно как ограниченный сценарий.

Не сохранять в evidence реальные meeting audio, transcript, cookies, tokens,
signed URLs, raw device paths или private meeting ids.

## 2. Build and platform-independent checks

```powershell
Push-Location apps/windows
cmake --preset x64-release
cmake --build --preset x64-release
ctest --preset x64-release --output-on-failure
Pop-Location
msbuild apps/windows/GrafWindows.sln /m /p:Configuration=Release /p:Platform=x64
ctest --test-dir apps/windows/out/build/x64/Release --output-on-failure
pwsh -File apps/windows/scripts/validate-audio-contract.ps1 -Synthetic
pwsh -File apps/windows/scripts/validate-webview-boundary.ps1
```

Ожидается: solution собирается без preview SDK, unit/contract tests проходят,
не создаются секретные или content-bearing diagnostics, а bridge policy
останавливает неразрешённые origin/route/command.

Реальные contract/package tests запускаются через CMake/CTest. Пустые тестовые
проекты удалены из `GrafWindows.sln`; сборка solution не заменяет запуск тестов.

Portable CMake/CTest на macOS подтверждает только platform-independent contracts.
Он не заменяет MSBuild/WinUI 3, реальный WebView2 lifecycle, WASAPI capture,
Media Foundation AAC или signed MSIX evidence.

Проверка Constitution 7 (T081/T082): технически готовый manual Start и
автоматический countdown проходят без полей legal-policy/consent и без WebView.
Для каждого оставшегося условия отдельно проверить отказ: microphone privacy,
input, render, normalization, AEC3, storage, AAC, indicator, Stop, active session,
suppression; неизвестный target не запускает запись. После удаления bool-полей
пересобрать все тесты, включая позиционные ReadinessInputs. Реальная запись
частных разговоров для этой проверки не нужна: использовать synthetic fakes.

Фоновая автозапись T081/T082: проверить отдельный индикатор/Stop до старта при
свёрнутом главном окне; отказ создания/показа не запускает capture. В
AutomaticRecordingSmokeTests проверить слежение с `starting`, второй процесс
той же identity, отсутствие 14/15 секунд, разрыв свежести, повторные/старые/
будущие снимки, предел 599/600 секунд без подтверждения, ручной Stop и ручную
запись. Каталог синтетических целей не включать в рабочее приложение; отсутствие
настоящей встречи/каталога явно ограничивает нативную приёмку.

### Нативная регрессия T071: отказ AEC при остановке

На тестовой Windows x64 из консоли Visual Studio с инструментами x64, в
`apps/windows` проверяемого снимка:

```powershell
cmake --preset x64-release
if ($LASTEXITCODE -ne 0) { throw 'CMake configure failed' }
cmake --build --preset x64-release --target NativeCaptureStorageIntegrationTests
if ($LASTEXITCODE -ne 0) { throw 'Native test build failed' }
ctest --preset x64-release -R '^NativeProtectedAecFailureDuringStop$' --no-tests=error --output-junit t071-aec-stop.xml
if ($LASTEXITCODE -ne 0) { throw 'T071 native regression failed' }
```

В отчёте должен быть один прошедший `NativeProtectedAecFailureDuringStop`.
Сохранить точный SHA проверяемых исходников, архитектуру Windows и отчёт.
Тест использует искусственные аудиопакеты и внедрённый отказ AEC, микрофон
не нужен. Он проверяет причину `aec_unavailable` после Stop, сохранение
только проверенного защищённого фрагмента, карантин и отсутствие обычной
отправки. Проверку качества AEC3, реального захвата, установленного MSIX и
60-минутного сценария выполнять отдельно.

## 3. Synthetic audio gate

Продолжение T085: до реального Record проверить единственный стартовый 0x1,
запрет повторного/смешанного флага, ReleaseBuffer failure, неизменность
аудиосостояния при отбрасывании и таймаут без пригодного пакета. Итоговая
безопасная сводка должна различать причины часов каждого источника и
стартовые отбрасывания; её нулевые блоки не являются успешной записью.

Источник synthetic fixture должен генерировать только детерминированные тоны и
шум с известными параметрами: system render reference, microphone near-end,
controlled echo, ±100 ppm clock drift, jitter, packet partition и injected gap.

```powershell
ctest --test-dir apps/windows/out/build/x64/Release -R "Timeline|AudioNormalizer|CaptureFaultState|AEC3|Writer" --output-on-failure
pwsh -File apps/windows/scripts/validate-audio-contract.ps1 -Synthetic
```

Pass criteria:

T085: отдельно пройти `AudioNormalizerTests` с включёнными проверками Release:
общая QPC-шкала, несовпадающие device origins, ±100 ppm с округлением,
441 + 441 и малые переменные пакеты, mapper → normalizer → timeline.
Точные часы не требуют искусственной коррекции из-за разбиения пакетов.
`RecordingAudioTimelineTests` проверяет ±48/49 и разрывы; `CaptureFaultStateTests`
проверяет ошибки меток и native lifecycle. Прохождение моделируемого часа
одних метаданных не является 60-минутной звуковой/ресурсной приёмкой SC-003.

Для WASAPI действуют правила §5 `contracts/windows-desktop-contract.md`:
`GetBuffer.devicePosition` первого кадра точно продолжает размер предыдущего
пакета; расхождение не разрешено объяснять ресемплированием. `IAudioClock`
проверяется отдельно и не заменяет packet QPC/device/count. Отсутствие часов
является отказом инициализации. Прежняя гипотеза 2026-09-07 не является
действующим контрактом.

- два source batch могут иметь разные размеры, но timeline выдаёт только
  contiguous 480-sample frames;
- reference передаётся в AEC3 до microphone frame;
- no dropped/duplicated output frames в 60-minute reference run при ±100 ppm;
- WAV/M4A/timeline duration difference не больше 100 ms;
- integrated RMS dBFS of the canonical 48 kHz mono system-render component,
  measured before final mix over the active synthetic interval, differs from
  the reference by no more than 1 dB;
- processor/timestamp/gap/overflow error не включает raw-microphone fallback;
- только проверенный trusted prefix может быть degraded artifact;
- after warm-up, native process CPU time is no more than 25% of wall time on the
  reference four-core x64 machine, resident memory growth is no more than 128
  MiB, and neither bounded source queue grows without limit.

Для среза микса T071 подать одинаковые подготовленные пары отсчётов
перед записью. Эталон `canonical-mix.v1`: `(0,25; 0,125) → 0,1875`,
`(0,75; 0,75) → 0,75`, `(−0,75; −0,75) → −0,75`; для паузы с
нулевым выходом тестового AEC `(0,5; 0) → 0,25`. Системный компонент
до микса и метка времени не меняются. AEC, вернувший NaN или бесконечность,
не выдаёт этот кадр,
а ранее выданный пригодный блок остаётся доступен. Повторить локальные
тесты шкалы, приватной паузы, отказа и финализации. Проверки здесь
не заменяют установленную и аппаратную приёмку §4.

Диагностика T071: после одного пригодного блока заставить AEC вернуть
ошибку или неконечный последний отсчёт. Диспетчер передаёт финализатору
`aec_unavailable` без подстановки в тестовом финализаторе; новый блок
не выдаётся, запись не получает статус обычного успеха. При подтверждённом
локальном префиксе текст сообщает и причину, и судьбу фрагмента.
Действительные ошибки часов сохраняют `clock_discontinuity`. Для
защищённого пакета сверить код в штатном результате финализации на
Windows; переносимая проверка не доказывает запись в нативное хранилище.

## 4. Hardware capture matrix

На каждой комбинации Windows 10 22H2/Windows 11 и x64 выполнить manual Record,
Pause, Resume, Stop, endpoint unplug/replug, default-device change, sleep/wake и
Audio Service restart. Отдельно проверить microphone privacy denial, exclusive
consumer, protected/DRM render и disk-full fixture.

Записывать только metadata-safe evidence: OS/build, app build, architecture,
source class, format class, state, safe reason code, counters, durations и
redacted endpoint fingerprint. Raw audio остаётся локальным QA input и не
попадает в git/evidence.

Эта матрица выполняется вручную на реальных устройствах. Скрипт
`validate-audio-contract.ps1` запускает только синтетические тесты и проверки
ошибок локального хранения; он не открывает устройства и не принимает список
операционных систем, микрофонов или выходов. Не засчитывать запуск скрипта как
аппаратную приёмку.

Pass criteria: active indicator и one-action Stop остаются видимыми при каждом
fault injection; permission/endpoint/clock/protected/overflow failures не дают
normal-status claim; silent cross-device continuation отсутствует.

### 4.1. Порядок и квитанция T063/T071 для физического x64

1. На физическом ПК войти обычным пользователем в отдельный профиль QA.
   Зафиксировать редакцию и номер сборки Windows, архитектуру самой ОС,
   физический стенд и число логических процессоров эталонной конфигурации.
   Поле `architecture=x64` из сводки GRAF относится к приложению и само
   по себе не исключает эмуляцию. Windows 10 22H2 и поддерживаемые Windows 11
   записывать отдельно; ARM64 не включать в заявление о поддержке.
2. Сверить SHA исходников с квитанцией сборки. Запустить GRAF штатно через
   «Пуск», затем из корня репозитория выполнить под тем же пользователем:

   ```powershell
   .\apps\windows\scripts\validate-package-smoke.ps1 `
     -Package $candidateMsix -ExpectedPackageSha256 $expectedMsixSha256 `
     -VerifyInstalled -RequireRunning
   ```

   `$candidateMsix` — локальная копия установщика, `$expectedMsixSha256` —
   SHA-256 из независимой квитанции сборки. Сохранить версию, SHA-256
   MSIX и запущенного EXE и результат проверки подписи. Доверие к тестовой
   подписи и появление окна не подтверждают публичную установку.
3. На одном и том же пакете выполнить три раздельных прогона. Для смены
   устройств и сбоев использовать отдельные короткие записи, чтобы они не
   искажали измерение непрерывной записи. Вместо встреч и речи реальных
   участников использовать сгенерированные сигналы.

   | Прогон | Что сохранить и сравнить |
   | --- | --- |
   | Физическая непрерывная запись ≥ 60 минут | Классы входа и выхода, длительность записи и дорожек, итоговое состояние, число обработанных и записанных блоков и сбои обоих источников. Снять CPU и рабочий набор процесса GRAF после прогрева и во время прогона: долю CPU считать как прирост процессорного времени, делённый на прошедшее время, а не по нормированному проценту диспетчера задач. Отдельно фиксировать максимум роста памяти. |
   | Эталонный звуковой прогон SC-003 | Входы с известными ±100 ppm, непрерывность кадров, длительности WAV/M4A/timeline (расхождение ≤ 100 мс), RMS канонического системного компонента до смешивания (отклонение ≤ 1 дБ), после прогрева CPU ≤ 25% и рост памяти ≤ 128 МиБ на эталонном четырёхъядерном ПК, поведение обеих очередей. Один счётчик блоков или час одних метаданных не доказывает эти показатели. |
   | Устройства, ошибки и AEC | Для каждого случая §4 указать Windows, классы входа/выхода, фактическое состояние, код отказа, доступность индикатора и Stop. Для AEC раздельно подать сигнал только из динамиков, только у микрофона и оба одновременно. Оценивать остаток эха и сохранение ближнего сигнала в микрофонном компоненте: системный звук в итоговом миксе не является эхом. Самопроверка AEC3 подтверждает подключение библиотеки и порядок обработки, без проверки акустики. |

4. Для каждого запуска записать идентификатор сценария, три хеша (исходники,
   MSIX, EXE), ОС, классы устройств, ожидаемый и фактический результат и
   вердикт `PASS`, `FAIL` или `NOT_RUN`. Отдельно отметить неполученные
   измерения. Безопасную сводку можно приложить для отказа; содержимое
   дорожек, идентификаторы пользователей и системные имена устройств
   оставлять вне отчёта. После замены пакета старый результат сохраняется
   только для прежнего пакета.

Для сравнения с F293/F294 при отключении **фактически активного микрофона**
используйте отдельную короткую запись на каждой платформе для явного выбора
и default при старте; уточнение T126 от 2026-11-12 требует оба варианта. Оставьте устройство
системного вывода неизменным. Подайте различимые искусственные системные
сигналы до и после отключения микрофона; если запись остаётся активной,
завершите её штатным Stop. В локальном результате проверьте отдельно
целостность участка до отключения и наличие сигнала после отключения.
Зафиксируйте переход состояния, доступность Stop, отсутствие автоматического
переключения на другой микрофон, возможность повторного выбора после
завершения и наличие обоих сигналов. Если GRAF сам завершил запись или
в файле нет второго сигнала, продолжение системного звука не подтверждено,
даже если интерфейс показывал ограниченное состояние. Сверить с
требованием F293 и FR-017; записать только результат и счётчики,
без содержимого дорожек.

Скрипт `validate-audio-contract.ps1` и тест
`WindowsHardwareEvidenceSchemaTests` не собирают эту квитанцию. Тест
проверяет константы на искусственном примере; часовой тест нормализации
проверяет метаданные часов. Полный набор измерений SC-003 и физические
прогоны должны быть представлены отдельно. Если стенд не может измерить
компоненты до смешивания или непрерывность кадров, отметить эти измерения
как `NOT_RUN`, даже если итоговая запись воспроизводится.

## 5. WebView2 security and parity gate

```powershell
pwsh -File apps/windows/scripts/validate-webview-boundary.ps1 -Contract
ctest --test-dir apps/windows/out/build/x64/Release -R "WebView|Bridge|Route" --output-on-failure
```

Матрица обязана включать trusted origin/routes, auth expiry, redirect,
cross-frame message, stale nonce, replayed id, malformed JSON, unknown version,
oversized/deep payload, token/file/process command, WebView close/recreate during
recording, missing runtime и repair failure. Для embedded profile menu отдельно
проверяется, что «Закрыть GRAF» отправляет только `request_app_quit` с payload
`{"action":"quit"}`; любой другой action, origin или route не закрывает shell.
Record/local custody должны
оставаться независимыми от результата WebView.

Сравнить с macOS parity matrix: `/desktop/meetings`, detail, settings, auth
recovery, review и deletion-report. Не добавлять Windows-only business UI.

Для T097/SC-009 проверить меню профиля в GRAF Dev и установленном MSIX с
одной версией кабинета. Во всех прогонах диктор сообщает точные подписи
«Вид», «Решение проблем», «Документация» и состояние раскрытия до и после
открытия; для темы — «Светлая», «Темная», «Системная» и ровно один
выбранный вариант. Стрелки и галочка видны, но не входят в имена.
Проверить клавиатурой вход в радиогруппу, смену темы, Escape с возвратом
видимого фокуса к кнопке профиля и повторное открытие с сохранённой темой.
Подписи и отметки не должны обрезаться или требовать горизонтальной
прокрутки. В macOS записать режим навигации и использованные клавиши
(Tab/Option+Tab и команды VoiceOver); результат стенда WebKit этого не
подтверждает.

Пройти четыре сочетания на каждой ОС: обычное, увеличение, повышенная
контрастность, увеличение с контрастностью. На Windows использовать
Narrator, системный масштаб дисплея 200% и контрастную тему Windows.
На macOS использовать VoiceOver, «Увеличить контрастность» и системное
увеличение всего экрана 2× через «Универсальный доступ» → «Масштабирование».
Увеличение macOS проверяет читаемость и работу фокуса, раскладку
в узком окне проверить отдельно; оно не заменяет системные 200% Windows.
Записать версии приложения и кабинета, размеры окна, масштаб,
контрастность, клавиши и наблюдаемую речь. Деревья WebView2/WebKit и
эмуляция масштаба/контрастности страницы — отдельные результаты.
На Windows отдельно запустить точный MSIX при уже включённой
контрастной теме. В отдельном тестовом профиле с открытыми окнами GRAF
перейти от контрастной темы A к теме B, без выключения контраста между
ними, затем выключить контраст. Выбрать A и B с различающимся цветом
хотя бы одной роли и сверить соответствующий цвет окна или кнопки
до и после. Проверить читаемость основной кнопки и «Остановить запись»
в индикаторе, в том числе при наведении и нажатии, а также видимый
фокус и чтение названий Narrator. Во время тестовой записи поставить
фокус на «Остановить запись», сменить палитру, после возврата из
системных настроек подтвердить фокус на той же кнопке и продолжающуюся
запись. Одним клавиатурным действием остановить запись без повторного
поиска кнопки и дождаться штатного завершения. Повторить на системном
масштабе 200%. Записать названия тем, SHA-256 MSIX и результаты до
и после каждой смены.

На Windows записать также режим DPI окна и масштаб его монитора.
Для окна без учёта DPI `GetDpiForWindow` всегда возвращает 96;
это число нельзя использовать для перевода физических границ окна
в логические точки. См. [замер установленного GRAF](validation-2026-11-07-t097-system-dpi.md).

Подменю открывается вправо, когда хватает места, влево, если место есть
только слева, и внутри меню, если по бокам места нет, при мобильной
раскладке или без поддержки всплывающих панелей.

Для T097/T109 отдельно выполнить в точном установленном MSIX настоящий путь
настроек уведомлений, без подставного `webkit` и ответов из browser fixture:

1. В согласованном тестовом аккаунте открыть `/desktop/settings/notifications`,
   дождаться native read и записать исходный выбор «Тихий режим». Не считать
   снимок страницы или поиск обработчика в исходниках выполнением сценария.
2. Изменить «Тихий режим», дождаться подтверждения сохранения, перейти в список
   встреч и вернуться. Повторный native read обязан показать сохранённый выбор.
   После обычного перезапуска приложения проверить его ещё раз в том же scope.
3. Вне записи, при разблокированном экране и без занятой важным сообщением
   карточки нажать «Проверить уведомление»: одна native-карточка, явный результат
   на странице, без начала записи/серверной отправки. Отдельно занятая карточка
   не заменяется проверочной; страница объясняет отказ. Проверить также
   управление с клавиатуры. Вернуть и повторно прочитать исходный выбор.
4. Отдельная синтетическая native-проверка должна удержать старое settings
   сообщение, заменить документ и доставить его с прежним nonce: нет мутации
   или ответа в новый документ; свежий документ может прочитать настройки.
   Не выполнять внедрение сообщений в рабочий аккаунт через консоль браузера.

PASS требует всей цепочки page → WebView2 → AppMain → сохранение → новый read;
mock browser tests и отдельные parser/presenter tests её не заменяют. Для
вывода о паритете тот же пользовательский сценарий проверяется на Mac.

## 6. Local custody and recovery gate

```powershell
pwsh -File apps/windows/scripts/validate-audio-contract.ps1 -CustodyFaults
```

Помощник запускает синтетические тесты, проверки хранения и отдельный
`NativeProtectedAecFailureDuringStop`. Пустая выборка в любом запуске
считается ошибкой. Для приёмки кандидата по-прежнему нужны полный нативный
CTest и отдельный JUnit-отчёт T071 из раздела 3.

Сценарии: offline finalization, process relaunch, network recovery, auth expiry,
partial accepted range, malformed ledger, duplicate Stop, wake recovery и local
purge/deletion truth. Требование — 100 циклов recovery без duplicate meeting или
upload session, когда server truth доступна.

[Нативный прогон 0.1.0.29](validation-2026-11-08-t118-cold-auth-wake.md)
подтвердил 100 повторных открытий уже отправленной записи без новой
загрузки. [Отдельные прогоны](validation-2026-11-08-t118-lost-finalize.md)
проверили потерю ответа после завершения загрузки и новый процесс после
прерывания до публикации результата на диске. Эти прогоны используют
имитацию сервера и покрывают часть SC-005.

Дополнительные регрессии T083: исчерпать автоматические повторы и нажать
«Отправить» для одной записи; прервать проверку аккаунта сетевым отказом и
дождаться планового повтора без перезагрузки кабинета; отдельно проверить
401/403 и несовпадение владельца. Перезапуск между сохранением принятых
диапазонов и итогового статуса не оставляет вечное «Отправляется». Повтор
после нового истечения серверной сессии не использует прежний ключ.

## 7. Automatic recording and accessibility gate

```powershell
ctest --test-dir apps/windows/out/build/x64/Release -R "Automatic|RecordingIndicatorTests" --output-on-failure
pwsh -File apps/windows/scripts/validate-package-smoke.ps1 -UiMatrix
```

Проверить подтверждённое приложение, неизвестное приложение и обычное
воспроизведение медиа; режимы «Всегда», «Спрашивать» и «Никогда» с начальным
значением «Спрашивать». В prompt проверить восьмисекундный отсчёт, действия
«Записать сейчас» и «Не записывать», а также «Запомнить выбор»: настройка
сохраняется только при явном действии, не при истечении таймера. Проверить
автоматическое начало записи после отсчёта, изменение настройки для одного
приложения и для всех подтверждённых приложений, смешанное состояние и отказ
при невыполненных условиях начала записи.

`RecordingIndicatorTests` проверяет модель индикатора, а не доступность
настоящего окна. Отдельно на финальной Windows-сборке проверить управление
клавиатурой, экранный диктор, High Contrast, масштаб 200%, узкое окно и reduced
motion. До этой проверки доступность и поведение нативного prompt не подтверждены.
Для T110 проверять перевод фокуса к карточке и доступ к Stop из двух
состояний: фокус на нативной кнопке оболочки и фокус внутри страницы
кабинета. Отдельно пройти клавиатурой «Перейти к уведомлению» из трея.
Прямой вызов `focus()` не засчитывать за получение F6 из кабинета;
см. [результаты изолированной проверки](validation-2026-11-06-t110-notice-foreground.md#прямой-f6-из-webview2-изолированная-проверка-очереди-окна).
На установленном пакете отдельно проверить, что без доступной карточки
или индикатора, при Shift+F6, удержании F6 или фокусе вне GRAF
нативного перевода фокуса нет. После закрытия или замены карточки либо
смены активного окна отложенный перевод отменяется, даже если фокус уже
вернулся в то же окно GRAF. Повторное явное F6 должно работать для
новой карточки. Для индикатора проверить также исчезновение Stop и
смену сеанса записи до выполнения отложенного перевода.
Явный F6 переводит только фокус и не выполняет действие записи.
Escape внутри явно сфокусированной карточки закрывает только её:
фокус возвращается в исходное окно, если оно ещё доступно и Windows
разрешает возврат. Если пользователь уже переключился в другое окно,
GRAF не забирает фокус. Отдельно проверить, что закрытие карточки не
скрывает индикатор и не лишает пользователя кнопки Stop.

Для T108 на том же точном установленном пакете в отдельном тестовом
профиле провести последовательность с разрешённым тестовым звуком:

1. Начать ручную запись, закрыть главное окно крестиком и повторно открыть
   из трея. Повторить после перехода в состояние записи. Проверить тот же
   сеанс, видимый нативный Stop и отсутствие повторного Start.
2. Скрыть окно, из трея поставить микрофон на паузу и возобновить его.
   Системный сигнал должен сохраняться на всём интервале, микрофонный —
   отсутствовать только на паузе. Открытие окна не создаёт новый сеанс.
3. Нажать нативный Stop, затем выбрать «Закрыть GRAF», пока идёт сохранение.
   Если окно сохранения слишком короткое для наблюдения, отметить шаг
   непроверенным; его не заменяет обычный выход после сохранения.
   После выхода открыть приложение и проверить один доступный результат.
4. Отдельно проверить крестик без активной записи и при недоступном трее:
   если фоновое управление недоступно во время записи, окно должно остаться
   видимым. Стенд с искусственными источниками не заменяет эту проверку
   установленного пакета и работу с физическими устройствами.

### Совместное чтение рабочих и запечатанных файлов обеих версий

`openProtectedCustodyReaders(root, heldPair, cancel)` возвращает фиксированные
2×5 readonly streams по actual ordinal каждой физической slot. Использовать
те же последовательные Release8/Debug3 команды выше. Проверяются разные
сохранённые bytes/версии, reversed wire order, mixed flat/packed и старые roots,

описание и ВСЕ файлы записи; последняя ссылка освобождает их. Неиспользованные
ячейки пусты, каждый успешный stream начинается на cursor0. SEALED сохраняет
exact length/whole SHA/EOF; LIVE использует actual highest из BOTH verified
flat indices либо BOTH current packed closures, без придуманного null stamp.

Одиночная перегрузка использует общий batch: повреждённый sibling отклоняет
даже запрос здорового файла; здоровый LIVE sibling теперь поддерживается.
LIVE target одиночной перегрузки по-прежнему отклоняется. Новые регрессии
проверяют обе LIVE slots, переход finalizing → sealed_normal с lower-only
canonical, разные current/historical bytes, mixed flat/packed, пустой checkpoint,
отказ singleton/trustedPrefix и отсутствие write/repair/slot erase. Независимые
factory открывать последовательно: второй batch не переоткрывает уже удерживаемый
эксклюзивный role. Это расширяет прежнюю ALL-SEALED область успеха, не ослабляя
проверку старой SEALED ссылки. Читаемый checkpoint не доказывает complete-frame
prefix или normal package и не заменяет manifest/formats/phase/trusted prefix, права аккаунта,
интеграцию writer/upload/playback и переход данных. Не удалять старую slot и не
выдавать дополнительный sealed commit ради обхода отказа. T116/T117/T118/T120

| Смена доступа к корню и изменяемому карантину | Отдельный процесс получает отказ DELETE на каждом промежутке смены. Выживший конкурентный дескриптор записи, другой FileId, изменённые байты или состав блокируют мутацию; после успешного снятия усиленных прав обычный доступ снова проходит |
| Нативное воспроизведение и приёмка установленного GRAF | Изолированный NTFS с буквой диска, обычный пользователь, точный исторический исходник и продуктовые пути, проверка сохранности двух имён и отказа нативного rename с заменой. Отдельно: установленный MSIX/EXE и install/update/rollback; восстановление с копии секторов Parallels не принимает потерю питания и другие ФС |

```powershell
& {
    $ErrorActionPreference = 'Stop'
    & .\Test-QaMedia.ps1
    & .\Get-GrafQaState-036.ps1 -Phase Absent -ProfileSid $qaSid -MachineUuid $qaUuid

    function Assert-QaPathAbsent([string]$path) {
        if ($path -cnotmatch '^[A-Za-z]:\\[^\\]+(?:\\[^\\]+)*$') { throw 'QA_STORAGE_PATH' }
        $prefix = [IO.Path]::GetPathRoot($path)
        foreach ($part in $path.Substring($prefix.Length).Split('\')) {
            if ($part -in '.', '..') { throw 'QA_STORAGE_PATH' }
            $parent = $prefix
            $prefix = Join-Path $prefix $part
            try {
                $item = Get-Item -LiteralPath $prefix -Force -ErrorAction Stop
            } catch [System.Management.Automation.ItemNotFoundException] {
                if ($_.CategoryInfo.Category -ne 'ObjectNotFound') { throw }
                if (@(Get-ChildItem -LiteralPath $parent -Filter $part -Force -ErrorAction Stop).Count) {
                    throw 'QA_STORAGE_UNCERTAIN'
                }
                return
            }
            if ($item.Attributes -band [IO.FileAttributes]::ReparsePoint) {
                throw 'QA_STORAGE_REPARSE'
            }
            if ($prefix -ieq $path) { throw 'QA_STORAGE_EXISTS' }
            if (!$item.PSIsContainer) { throw 'QA_STORAGE_ANCESTOR_NOT_DIRECTORY' }
        }
        throw 'QA_STORAGE_PATH'
    }

    $local = [Environment]::GetFolderPath('LocalApplicationData')
    if (!$local) { throw 'QA_STORAGE_PATH' }
    Assert-QaPathAbsent (Join-Path $local 'GRAF\recordings')
    Assert-QaPathAbsent (Join-Path $local 'Packages\com.graf.desktop_jqvfym1syd7bp\LocalCache\Local\GRAF\recordings')
    'QA_RECORDING_ROOTS_ABSENT'
}
```

### T121: Windows-возврат после входа

После независимой проверки [§11.4](contracts/windows-native-web-bridge.md#114-проект-windows-возврата-после-входа-t121--chk022)
и его [чеклиста](checklists/t121-windows-auth-continuation.md) отдельно
проверить:

| Среда | Критерий |
| --- | --- |
| Сервер на изолированном HTTPS и тестовой БД | Действительная B проходит. Cookie A при операции B даёт 409 без цели и без изменения cookie для той же и другой встречи. Задержать подготовку A до B, подтвердить допустимый 409 и успешный явный повтор. Задержать ответ разрешения A и подтвердить отсутствие `Set-Cookie` и на 200, и на ошибках. Отказать при истечении, повреждении, повторе заголовка/имени cookie, отзыве гранта или отсутствии собственной сессии. Сохранить прежние 303 входа и регистрации Mac/браузера в том же профиле. |
| Настоящий WebView2 | Для 303/307 на тот же URL, другой origin и другой порт, 404, фрейма, подресурса, повтора и потери сети сверить счётчики исходного и целевого серверов: ни одного непредусмотренного запроса, ни одного заголовка операции вне допуска. На 200 отклонить `Location`, повтор `Content-Location`, нелокальный или несовпадающий путь. Для позднего завершения email/OAuth A с новой сессией того же либо другого пользователя: ноль выдач reader; для B с доказанным входом и текущей сессией: одна выдача в запросе разрешения, без отдельного GET. Проверить отказ на синтетическом 200 с правильным адресом без запроса к серверу, а также на подмене ответа после настоящего запроса активным service worker. Сохранить обычный вход, оплату и T106. Reader не получает моста. |
| Привязка к входу | На штатных email login/signup и OAuth start подтвердить, что операция связана только с выпущенным сервером challenge/state. Скрестить challenge/state A с nonce B, повторить использованный challenge/state. Задержать ответ A до B; отдельно проверить три несовпадающие пары квитанции и сессии. С auth start отдельно перенаправить запрос через 307 и смену origin: на следующем запросе, в том числе на сервере провайдера, нет заголовка операции. Действительная квитанция при истёкшей подготовке не выдаёт страницу. В обычном входе прежние cookie и ответы не меняются. |
| Между разрешением и показом | Подменить сессию, выполнить logout и сменить аккаунт до одного проверяющего GET; подтвердить отказ без HTML reader. При смене после отправки с B отдельно подтвердить ноль показов устаревшего результата. Проверить совпадение канонического URL, фрагмента, фокуса и истории реальной страницы; Reload и Back не повторяют разрешение и не отправляют заголовок операции. |
| Диагностика | Искусственные контрольные значения заголовка операции, Cookie/Set-Cookie, токена в URI и Content-Location/Location отсутствуют в журналах приложения, прокси и WebView2 при успехе, отказе и ошибке прокси. В материалах только статусы, счётчики и признаки совпадения. |
| Установленный MSIX и Mac Dev | На точных версиях пройти вход с действующим провайдером на испытательной среде, открыть исходную встречу с нужной вкладкой и версией, проверить отсутствие автоперехода после отмены и восстановление обычным повтором. Проверить позицию 0, ненулевую позицию и отсутствие переноса при устаревшей версии. Сохранить только обезличенные результаты. |

Для изолированного HTTPS-прогона T121 включать сетевой домен и
обход worker на том же контроллере до нативной навигации; между
подтверждениями и перед запуском заново сверять текущую попытку.
В обоих контролях подмены страница посылает отдельный безвредный
сигнал исполнения: без защиты сигнал должен прийти, с защитой
не должен. Скрытое окно и совпавшее тело после загрузки не
заменяют эту проверку. При отмене, замене, ошибке, тайм-ауте или
позднем ответе команды не запускать и не повторять навигацию
без защиты. Перед повторным использованием дождаться отключения
обхода и сетевого домена; если сброс не подтверждён, закрыть
этот контроллер. Проверить восстановление и независимый reader.
CDP в этой пробе только управляет режимом: без сетевых подписок,
чтения cookies и тел, трасс и отладочного порта. Тестовый допуск
по точному сертификату внутри одноразового стенда, если он нужен,
не засчитывается как проверка доверия установленного MSIX.

## T104: нативная подсказка панели записи

1. На искусственных событиях прогнать четыре сочетания «Предлагать запись»
   и «Предлагать подключиться», linked/unlinked, секунду до и момент начала,
   отложенный due и момент окончания. Проверить отсутствие/повреждение
   необязательных полей, чужой и сокращённый снимки, запись в процессе,
   несколько событий и детерминированный порядок. С искусственными
   монотонными часами проверить возраст запроса 59.999 с и 60 с, отсутствие
   метки, время раньше запроса и поздний ответ. Проверить переход
   свежий ответ → зависание или временный сбой → новый принятый ответ:
   подсказка отзывается, карточка F277 сохраняет свой срок и правила
   удержания. Отдельно сверить тихий режим, закрытие и повторное подключение.
2. В точном Windows MSIX и согласованном GRAF Dev проверить одну встречу
   и пересечение двух: выбор каждой встречи, явный отказ от связи,
   закрытие и обычную ручную запись. Проверить Tab/Shift+Tab/Enter,
   Narrator, высокий контраст и 200%, сохранение фокуса при обновлении
   списка. Отдельно проверить Stop и неизменность уведомления F277.
3. Между показом и нажатием, во время обновления и перед допуском звука
   сменить пользователя/пространство, передвинуть или отменить событие,
   выключить настройку, заблокировать ОС, завершить встречу, включить
   запись другим способом и повторить старое нажатие. Не должно быть
   второго старта или эффекта старой кнопки.
4. На тестовом сервере проверить реальные решения automatic/user_selected/
   user_declined, их применение только к той же локальной записи, Stop
   до ответа, повтор запроса после обрыва и перезапуск до отправки.
   Проверить, что событие и решение не попадают в журналы. Запись,
   сохранение и отправка проверяются раздельно; ID или включённая кнопка
   сами по себе не доказывают успешное связывание.

Проверка B1 в переносимых `ContractFixtures`: точные маршрут, ключ и
JSON для каждого решения, отсутствие UUID события для автоматического
выбора и отказа, повтор с теми же байтами, неправильные UUID/время/пары
решения и события, ответ формы действующего сервера с дробными
секундами, отсутствующая зона, дубли, граница 8192/8193 байта,
неподходящий ответ, отсутствие изменения
старого тела `/api/v1/meetings` и добавление только UUID попытки при
наличии. Обычные и защищённые строки дают одинаковый контракт. Эти
тесты не подтверждают отправку HTTP или работу установленной панели.

Первый уровень B2a — `CalendarMatchEnvelopeTests`: три вида решения,
точная привязка к каждому из четырёх полей, ограничение размера, неверная
пара решения и события, обрезанный конверт и успешная расшифровка Windows
с заведомо неверной внутренней контрольной суммой. Переносимый прогон
проверяет вход и пределы; вызовы DPAPI проверяются в Windows.

Проверка B2a выполняется только на Windows с отдельным частным каталогом
и искусственными идентификаторами, без доступа к рабочим записям:

1. Сохранить по одному решению каждого вида. Открыть журнал из нового
   процесса в том же профиле и сверить вид решения и наличие UUID события.
2. Повторить тот же выбор и сверить исходный конверт побайтно. Попытаться
   записать другое решение для того же UUID, включая одновременную
   публикацию из двух процессов: первый успешный выбор не меняется.
3. С теми же байтами изменить по очереди origin, actor, workspace и UUID
   записи. Подложить обрезанный и слишком большой конверт, ссылку вместо
   файла и каталога, а также имитировать отказ доступа. Эти исходы нельзя
   принять за пустое состояние. Отдельно проверить настоящий отсутствующий
   файл в безопасном каталоге.
4. Сверить, что тест не изменил очередь, защищённые пакеты и установленный
   GRAF. Эти проверки не принимают запись через панель, загрузку,
   удаление журнала или откат приложения при ожидающем решении.

Отдельно воспроизвести отказ подготовки каталога и отказ сброса
каталога журнала сразу после перемещения файла. В первом случае
журнал недоступен: чтение отсутствующего решения допустимо только
после успешной подготовки каталога. Во втором случае запись не
подтверждена, файл остаётся; повтор с искусственным отказом сброса не
выдаёт успех, а после восстановления сброса то же решение
подтверждается без замены исходного конверта. Чтение для использования
при этом же сбое не выдаёт подтверждённого решения.

Для допуска B2b использовать отдельную цель CTest
`NativeCalendarRecordAdmission` в существующем стенде защищённой записи.
Стенд работает с настоящими резервированием и журналом в уникальной
временной папке, подставляет только ответы авторизации и готовность
звуковых устройств, не читает микрофон и не обращается к рабочему серверу.
Проверить положительный случай выбора встречи и отказа, затем конфликт и
неподтверждённую публикацию (ноль запусков устройств), Stop при удержанном
сохранении, отмену после запуска устройств до допуска пакетов и отдельную
обычную запись без журнала. Этот тест не нажимает кнопку панели.
Продуктовая сборка B2b сохраняет существующие маршруты: новая кнопка
подключается только вместе с отправкой, когда испытание на отдельном
сервере показывает, что выбор или отказ дошёл до создания той же встречи,
а повтор запроса после разрыва не заменил решение автоматическим.

##### T104/B2c.1: подтверждение после потери ответа

На отдельной тестовой БД создать запись с явным отказом, потерять
ответ создания и сверить её с тем же токеном устройства. Запрос без
`include_calendar_match_receipt` сохраняет прежнюю форму ответа; запрос
с `include_calendar_match_receipt=true` возвращает только
`attempt_id` и `state=declined_by_user`, с `Cache-Control: no-store`.
Повторить с выбранным событием (`matched_user`). Проверить принятую
попытку после TTL, непринятую просроченную попытку, другой UUID попытки
или записи, смену устройства/аккаунта, несовпадение ревизии и удаление.
Отдельно убедиться, что поле не раскрывает сведения события и не
зависит от истечения сессии загрузки. Успешная сверка здесь не принимает
кнопку или установленный MSIX.


##### T104/B2c.2: строгое создание и повтор

В отдельной тестовой БД использовать явные выбор и отказ: создание
подтверждает тот же исход через B2c.1. Повторить исходное тело после TTL
и изменения карточки: тот же UUID встречи без второго применения.
Изменённое тело, другая ревизия, неподтверждённая существующая встреча
и активное удаление отклоняются без перепривязки. Для нового создания
проверить чужую, просроченную, неизвестную и автоматическую попытки,
другое время старта и сбой после записи ревизии и потребления попытки,
до коммита. Из новой сессии проверить отсутствие встречи, ревизии,
обработки, календарной связи, аудита и квитанции; попытка осталась
непотреблённой, а память процесса не сохранила новую встречу или аудит.
В двух транзакциях отозвать устройство после авторизации, пока запрос
ждёт блокировку источника: создание и повтор должны отказать.
В локальном маршрутизаторе без строгого маршрута запрос отклоняется до
ingest; обычное создание по-прежнему работает. Отдельная приёмка клиента
должна подтвердить отсутствие запасного POST при откате и сохранение
локального звука.


##### T104/B2c.3: защищённая метка при потере журнала

В синтетическом корне проверить сохранённую метку до начала захвата
для выбора и отказа, прежний путь для обычной записи и автоматического
сопоставления, штатное завершение и восстановление проверенного
`sealedNormal`. После обрыва до появления каталога, на незапечатанном
пакете и после восстановления `sealedDegraded` первая метка остаётся
закрытой. Проверить, что UUID встречи из квитанции удаления не
открывает отправку. При совпадающих квитанции и задании проверить
отдельную запись намерения, отказ для другого сервера и локального
запроса, удаление пакета, повтор после обрыва до записи результата
и подтверждение после холодного открытия. С журналом, без него
и при его повреждении обычная
автоматическая и ручная отправка дают ноль выбранных записей. Сверить
с обычным сохранением без календаря, неизменностью прав владельца
и удаления, отклонением неправильного статуса/владельца в v4 и чтением
старым исходником. Отдельно на точном установленном MSIX и
совместимом пакете отката проверить прерывание до удаления пакета и
после него, но до сохранения подтверждения: очередь открывается,
локальный обход закрыт, то же задание завершается с подтверждением.
Откат к 0.1.0.18 для профиля с таким намерением не принимать.
Эта проверка не включает настоящий микрофон или сервер и не
подтверждает отправку по новому маршруту.

##### T104/B2c.4: Windows сверяет точную квитанцию

Подать в разбор искусственные полные ответы B2c.1: оба явных решения,
сверка после истечения сессии загрузки, точный 404 записи и чужой 404.
Проверить ответ с другой записью, любой из двух несовпадающих проекций
ревизии, другой встречей или попыткой, обратным исходом, отозванным
доступом, удалением и несовместимым конфликтом. При точной квитанции
проверить оба разрешённых кода временной недоступности загрузки;
`meeting_unavailable`, отсутствие или подмена причины при
`dependency_unavailable`, отсутствие или неизвестное состояние
конфликта должны дать «не доказано». Неполное тело, дубли
ключей (в том числе после декодирования), отсутствующая или пустая
квитанция, превышение лимита, отмена и транспортный сбой не подтверждают
решение. Проверить отсутствие UUID встречи в результате отказа.
Это проверка формата и разбора; отдельная приёмка всё ещё должна
подтвердить точный адрес/сессию, запрет запасного POST, совместимый
откат и штатный путь из установленного приложения.

##### T104/B2c.5: привязанный GET сверки в Windows

На искусственном транспорте зафиксировать один точный GET без тела
и ключа повтора, сохранение токена и идентификаторов устройства,
пространства и ожидаемого актёра. Проверить точные 200 и 404, ответ
старого маршрута, редирект, отказ аккаунта и потерю транспорта.
При отсутствующем или несовпадающем origin, устройстве, владельце,
пространстве или снимке токена, недопустимых ID, подстановке в URI
или заголовки, автоматическом исходе, отмене или истёкшем сроке до
запроса число вызовов равно нулю. При отмене или опоздании после
вызова не принимать ни точную квитанцию, ни точный 404. Отдельно
проверить фактический код WinHTTP на подменённой границе ОС:
точный метод, заголовки и запрет перенаправлений; корректный полный
ответ больше 64 КиБ; чистый EOF на границе 2 МиБ; отказ для лишнего
байта или сбоя чтения после корректного префикса (как для 200, так
и для 404). Подключение к очереди, настоящий серверный повтор и
приёмка установленного пакета остаются отдельными.

##### T104/B2c.6: устройство из подтверждённой сессии

На отдельной тестовой БД получить `auth/me` с единственной
доверенной привязкой при `AuthSession.device_id=NULL`: вернулся UUID
связанного устройства, а не запрошенного в заголовке; ответ `no-store`. Проверить сессию без привязки даже с зарегистрированным
устройством, старые заголовки без сессии, чужое пространство и отказ
отозванной или заблокированной сессии. В Windows проверить точное поле,
совместимость со старым ответом, `null`, неправильный тип/UUID и список
устройств без доказательства. Проверить, что подтверждённый снимок
доставляет ID до защищённого транспорта, а запрос B2c.5 не отправляется
без доказательства или при несовпадении с явным устройством. Старый
путь загрузки не получает новый заголовок. Удержать результат
`auth/me` токена A с устройством до принятия его Windows, сменить
токен на B того же владельца и пространства, затем доставить результат
A. До подтверждения B нет календарного запроса. Ответ B без поля
даёт обычную идентичность, но B2c.5 по-прежнему делает ноль запросов. Эти проверки не включают панель и
не заменяют приёмку установленного MSIX.

##### T104/B2c.7: исходный строгий запрос после перезапуска

На искусственной записи проверить оба явных решения. Из исходных
времени начала и конца, длительности, смещения часового пояса и
попытки сформировать тело штатным формирователем; отсутствие
шкалы времени, неправильный UUID, неверный срок и автоматическое
решение отклонить. В другом процессе с тем же профилем получить
точные тело, ключ, UUID и срок; просроченный пакет также читается
для сверки. Повторное сохранение тех же данных не меняет файл.
Одновременно предложить два разных пакета: пригоден только
неизменённый победитель. Подменить отдельно origin, владельца,
пространство, запись, устройство, ревизию, решение и событие.
Отсутствие исходного решения, порча любого файла и сбой подтверждения
публикации не дают запроса. Сбой не разрешает заменить пакет;
повторное чтение после восстановления подтверждает ровно исходные
данные. Сверить, что прежний файл решения побайтно не изменился.
Для одной записи и области поменять местами два конверта и убедиться,
что ни один не читается в чужой роли. Проверить неизвестную версию
с корректным дайджестом, усечение, неверный дайджест и превышение
границ длины конверта и полей. Проверить отказ для ссылки и файла,
не соответствующего правилам частного каталога.
Проверки не вызывают сеть и не открывают отправку или панель.

##### T104/B2c.8: метка обязательного исходного пакета

В защищённом хранилище подтвердить исходный пакет журнала, но не
сохранять копию очереди. Перечитать очередь: исходная метка не даёт
запроса. При новом владельце хранилища принять только сохранённый пакет
без нового решения, отказать при попытке заменить его. Сохранить
очередь штатным подтверждением поколения, закрыть и открыть хранилище:
пакет доступен только для новой закрытой метки и точной области.
Сменить устройство, пользователя, пространство, ожидаемое поколение;
проверить отмену, неподтверждённую публикацию, потерю или порчу журнала
после сохранения очереди. Ни один такой отказ не выдаёт запрос или
не меняет метку обратно. Подтвердить неизменность записи и отказ
обычной ручной и автоматической отправки, сохранение проекции локального
просмотра и владельца удаления, отказ при серверном удалении и
недопустимые формы строки v4. Реальный сетевой повтор и совместимый
установленный откат проверяются отдельно.
В отдельной проверке отозвать право сразу после успешной операции
журнала: подготовка не возвращает копию и оставляет исходную метку,
чтение не возвращает тело/ключ. Имитировать отказ очереди до публикации
и неопределённое подтверждение после публикации: текущий владелец
не выдаёт пакет, а холодное чтение старого и нового поколения
отличает закрытое состояние от ровно исходного пакета.


##### T104/B2c.9: отправка исходной попытки и отдельное подтверждение

Проверить порядок GET → один строгий POST → GET, одинаковую область
всех запросов и побайтовое совпадение тела и ключа с журналом. Покрыть
потерю ответа POST, исключение транспорта, 2xx без квитанции,
отказ старого маршрутизатора, неверное устройство или исходный ключ,
существующую подтверждённую запись, известную встречу при 404, неизвестный
404 и истечение UTC-срока. Вызов после отмены не выполняет сеть;
отмена/истечение срока после первого GET не допускают POST, а после
POST не допускают чтение или выдачу устаревшего подтверждения.
Проверить, что POST и оба GET получают один исходный предельный срок,
а не новый бюджет. Отдельно управляемыми часами: после точного 404
довести UTC до границы во время подготовки WinHTTP и убедиться, что
`WinHttpSendRequest` не получил POST; если POST начат вовремя,
довести UTC до границы после него и принять точную квитанцию до
исчерпания монотонного срока. Только она возвращает UUID встречи.
Прогон с подменой только сетевого обмена не заменяет живую связку с
владельцем хранилища и установленную проверку.


##### T104/B2c.10: фиксация квитанции без обычной отправки

Из исходной закрытой строки подтвердить правильный UUID встречи.
Отказать при другой области/устройстве/поколении, другом решении,
подмене исходного пакета, отсутствии журнала, неподтверждённом
ответе, отмене после чтения и удалении по записи или по тому же UUID
встречи. При точной квитанции и неизменном журнале отдельно проверить
`sealedDegraded`, отсутствующий пакет и повреждённые метаданные: кандидат
не выдаётся, сохранённая строка остаётся без UUID. На NTFS проверить отказ до публикации и потерю подтверждения
после публикации: холодное чтение различает старую закрытую строку
без UUID и новую закрытую строку с ровно исходным UUID. Проверить v4,
запрет обычной ручной/автоматической отправки, право локального
просмотра/удаления и невозможность повторно подготовить исходный POST
из подтверждённой строки. Тесты используют искусственный пакет;
установленная приёмка, живое удаление обоих журналов и загрузка аудио
остаются самостоятельными.

##### T104/B2c.11: защита от смены ревизии между сверкой и загрузкой

В изолированной базе создать встречу строгим POST, получить квитанцию
и UUID ревизии, затем заменить актуальную ревизию. Передать исходный UUID
в отдельный POST сеанса. Ожидать отказ без появления сеанса или события его
создания. Для актуальной ревизии сверить UUID ответа и повтор с тем же
ключом. Чужая попытка, другое устройство или отсутствие UUID дают отказ.
Без полного списка размеров, при нулевом размере или дублирующейся
роли сеанс не создаётся.
Проверить оба порядка захвата блокировки встречи и отказ для прежнего
сеанса без закреплённой ревизии. Повтор с тем же ключом проверить
при чужой ревизии, чужом устройстве, истекшем или завершённом сеансе:
отказ без возврата или замены сеанса, изменения встречи и аудита.
Отдельно отозвать сессию или доверенную привязку после входной
авторизации, пока запрос ждёт блокировку встречи. Проверить обе
ветки — создание и возврат существующего сеанса: обе отказывают
без изменения загрузки, встречи и события создания. Подменить устройство
заголовком чужой привязанной сессии, назначить новой ревизии имя
начальной и оборвать транзакцию после записи аудита, до коммита.
Не должно остаться сеанса или события в БД либо в памяти. Старый маршрут
должен сохранить существующий контракт. При 404 нового маршрута
проверить отсутствие отката к старому. На клиенте подставить чужой UUID
встречи, ревизии или сеанса в ответ GET, неподходящие размеры или роли
и потерянный ответ POST: до точного подтверждения нет запроса
диапазонов, передачи байтов, завершения или запасного POST встречи.

Для строгого GET отдельно проверить отсутствие БД, отсутствие строки при
наличии подходящей записи в памяти, пустой UUID ревизии в самой строке,
подмену UUID встречи/ревизии/сеанса, чужое устройство, отозванный
доступ, истечение, завершение и начавшееся удаление. Положительный
ответ содержит только закреплённые поля, с `Cache-Control: no-store`;
ошибки не подставляют старое значение и не изменяют хранилище.
Отдельно подставить подлинные квитанцию и сеанс от другой записи того же
владельца с совпадающими размерами: ни одного запроса. Строка срока
должна представлять допустимую дату и время с часовым поясом; сравнение
с текущим временем остаётся на сервере.

##### T104/B2c.12: проверка клиентского допуска к сеансу

С подставной сетью воспроизвести принятый сервером POST с потерянным
ответом. Следующая попытка обязана отправить те же путь, тело и
ключ. Только ответ строгого GET для UUID из ответа POST разрешает
вернуть этот UUID. Подставить старый сервер, чужой UUID, неверный
размер, смену токена и отмену между запросами. Проверить точный
порядок и отсутствие обычного POST, запросов диапазонов и байтов.

##### T104/B2c.13: проверка части после отзыва допуска

На одноразовой БД подтвердить, что обычный сеанс с теми же ключом,
ревизией и устройством нельзя выдать за календарный. Создать
строгий сеанс и принять контрольную часть. После смены ревизии или
отзыва доступа повтор и новая часть должны получить отказ. Для
гонки изменить ревизию во время пробного PUT: сервер не фиксирует
часть и очищает объект или оставляет точный адрес в журнале очистки.

Повтор строгого POST с точной меткой возвращает тот же сеанс; с другой
ненулевой меткой или NULL — отказ без изменения БД. Строгий GET с
NULL отказывает. Сохранённый в памяти сеанс без строки БД отказывает
до любого доступа к объектному хранилищу. Проверить отзыв допуска во
время ожидания блокировки при быстром повторе принятой части:
ответ — отказ, принятая часть сохраняется. После календарной очистки
сверить сохранность метки холодным чтением БД. Обычный сеанс с NULL
проходит штатную отправку после миграции.

##### T104/B2c.14: завершение после отзыва допуска

На одноразовой PostgreSQL загрузить части строгого сеанса. Отозвать
допуск после начала сборки дорожки и отдельно при записи DEGRADED.
Ожидать отказ без изменений принятой ревизии, состояния или аудита;
сохранить исходные части и удалить только пробные объекты.
Для двух завершений одного сеанса проверить разные ключи составных
объектов; поздний отказ одной попытки не повреждает принятую.
Повторить обычную загрузку и штатный путь DEGRADED без метки.

Для B2c.14a загрузить по одной части на дорожку; отозвать
допуск между первоначальной сверкой и поздней блокировкой
отдельно в успешной ветке и DEGRADED. Проверить сохранность
частей, отсутствие нового аудита и положительный контроль.
Временно строгий сеанс с двумя частями одной дорожки должен
получить отказ до I/O без изменений; обычная загрузка проходит.

Для B2c.14a также дать сеансу истечь после начального допуска:
сам запрос завершения не выставляет EXPIRED и не пишет аудит.
Принять вторую часть параллельным запросом до блокировок DEGRADED:
новая часть остаётся принятой, завершение возвращает отказ, статус
и аудит завершения не меняются.

**Матрица B2c.13/B2c.14b перед включением строгого маршрута.**
На одноразовых PostgreSQL и точном здоровом MinIO из compose без версий
использовать искусственные данные, настоящий клиент и холодные сверки из
отдельного соединения. Сценарии с очисткой выполнить дважды: через фоновый
очиститель и полное удаление встречи. Проверять строки журнала и владельцев,
ListParts, точный ключ и отсутствие версий; одного статуса HTTP недостаточно.

Проверка ролей MinIO: на одноразовом экземпляре применить правила
`rec-minio-init` дважды, затем выполнить прежний установщик с теми же
учётными записями. Обычные API и media должны сохранить свой обычный I/O,
но получить отказ на запись, удаление и multipart-операции в обоих
защищённых семействах. Проверить действие политики после прежнего
установщика. На пустом стенде вызвать отказ базовой привязки API:
установщик завершается ошибкой и не публикует маркер готовности.
На существующем томе прежний маркер может остаться; проверять код
выхода актуального установщика и действующие права отдельно.
Восстановление снимка IAM проверяется отдельно.
Для отдельных тестовых учётных записей вывести политики командой
`python3 infra/scripts/strict-upload-minio-policy.py` с аргументами
`writer --epoch <выделенное-поколение>`, `cleaner` и `discovery`.
Команда только выводит JSON. Она не выделяет поколение, не устанавливает
учётные данные и не включает строгий путь. Подтвердить, что отдельные
пользователи имеют ровно свои политики, без широких групп или старых
привязок. Повторить тесты с настоящими выделенными клиентами записи,
очистки и поиска, старым поколением и обычным ключом как отрицательным
контролем. Не считать проверку прав подтверждением общего тома,
эксплуатационного допуска или полного отката.

| Сценарий | Наблюдаемый результат |
| --- | --- |
| Кэш без строки, отозванный допуск, удаление выиграло гонку до регистрации либо COMMIT намерения неизвестен | Ноль чтений и записей в хранилище от текущего запроса; нет принятой строки |
| Очиститель забрал намерение до отправки либо ключ после подтверждённого Complete | В первом случае нет записи в хранилище; во втором позднее принятие запрещено даже после операторского повтора |
| Create задержан до пустого списка и HEAD 404 либо потерян ответ о фиксации ID | Ни одного UploadPart или Complete; второго ID нет. При неизвестном Create запись не закрывается от пустого списка. При потерянном COMMIT ID отдельная сверка отличает известный ID от неизвестного, а исходный запрос не продолжает передачу |
| Нормальная запись и запрет скрытых повторов | Отдельное соединение видит зафиксированную строку до I/O. Очиститель не захватывает запись только пока писатель держит её блокировку; в промежутке между транзакциями очиститель может выиграть. На стороне MinIO подсчитать один Create, по одному UploadPart на номер и один Complete, включая сбой ответа; посредник и SDK запросы не повторяют |
| Запоздалый UploadPart/Complete после разрыва PostgreSQL | При Complete-first остановить его после проверки ID внутри MinIO; при Abort-first остановить Complete до захвата блокировки ID и дать Abort закончиться. В обоих случаях проверить разрешённый точный DELETE. Старый запрос не восстанавливает `settled`. После подтверждения нет действующего ID, частей или объекта на уровне API; это не проверка физического стирания. При неопределённости журнал действует, полное удаление не выдаёт успех |
| Срок попытки и ответ Complete | Зависание на соединении, чтении и блокировке освобождает строку не позже настроенного срока транзакции; следующего запроса от исходной попытки нет. Поздний ответ обрабатывается очисткой, без ложного `settled`. `HTTP 200` с XML-ошибкой не принимается. Проверить и самую большую поддерживаемую дорожку: поток ограничен по памяти, результат не теряет и не дублирует байты |
| Потеря ответа Abort, DELETE, повтор и последний просроченный `deleting` | Нет ложного `purged`; повтор работает только с тем же ключом и ID. После исчерпания попыток строка доступна оператору, повтор не возвращает право принятия |
| Поздний отказ допуска и неизвестный COMMIT принятия | При отказе нет новой принятой строки и связанных изменений встречи/аудита. При неизвестном COMMIT принудительно проверить оба исхода: принятый владелец с доступным объектом либо откат с журналом; сам запрос не удаляет и не пересоздаёт объект |
| Конкурентный победитель или занятый ключ | Попытки имеют разные ключи. Отдельно потерять успешный ответ Complete и ответ 412. При 412 оба очистителя сохраняют чужой объект побайтно; замена между HEAD и DELETE также не приводит к удалению чужого объекта. Если защита не доказана, обязательство остаётся открытым |
| Неизвестная конфигурация, версии, неоднозначный список или недостаточные полномочия | Не допускается запись или ложная очистка; нерешённая строка доступна оператору. Основная роль API и очиститель не могут перечислять multipart-сеансы. Отдельная роль поиска не может читать, записывать или удалять объект и отменять ID; операторский вход отвергает широкий поиск и не принимает пустой список как подтверждение очистки |
| Свежесть ключа и неисправные метаданные | На закреплённом MinIO создать занятый ключ с потерянными или противоречивыми метаданными. При старом поколении, неоднозначной выдаче нового поколения, невосстановимом журнале эксплуатации или невозможности доказать свежесть продукт не отправляет Complete и не сохраняет `settled`. Отдельно проверить отказ старых и обычных ролей на обоих семействах ключей, даже при ошибке чтения |
| Обновление и откат | Оба совместимых очистителя готовы до включения писателя. При откате писатели остановлены или ограждены, ранее выданный строгий сеанс нельзя продолжить старым писателем; незавершённые записи остаются у совместимых очистителей. Принятые вложенные ключи читаются, обрабатываются и удаляются при полном удалении, очистке временных данных и истечении срока хранения; после восстановления старой копии БД повторившийся номер попадает в новый ключ. Старые учётные данные, уже выданный строгий сеанс и прежний установщик правил не возвращают право записи. До сообщения об очистке сверить обязательства, отсутствующие в копии. Старый очиститель с новым незавершённым журналом — отрицательный контроль |
| Неполная сверка после восстановления | Создать живой multipart, восстановить снимок БД до регистрации его обязательства, оставить этот multipart в MinIO и намеренно не завершить сверку. Даже при пустом журнале обычная очистка не выдаёт `active_purge_complete`, операторская — `converged`; признак `recovery_unknown` переживает перезапуск. Повторить без известной встречи: блокировка действует в области восстановленного хранилища. |
| Обычная загрузка и B2c.14a | Обычная многочастная загрузка, повтор и DEGRADED ведут себя как прежде. Строгая одночастная дорожка проходит B2c.14a; временный отказ многочастного строгого пути сохраняется до приёмки B2c.14b |

**Установка блокировки до восстановления (проверка на отдельном стенде).**

1. На хосте развёртывания, из того же checkout, который использует
   `cd-remote.sh`, открыть отдельную оболочку и взять замок:

   ```sh
   exec 9>>"$(git rev-parse --git-path twobrain-rec-deploy.lock)"
   /usr/bin/flock -n 9 || exit 1
   ```

   Сохранять эту оболочку и дескриптор 9 до завершения всей операции.
   Не заменять файл замка. Только после захвата остановить писателей,
   очистителей и выдачу результатов. В журнале
   эксплуатации вне снимков зафиксировать область, прежний и свежий UUID
   операции. Использовать каталог оператора вне снимков БД и MinIO,
   недоступный для записи сервисам. Файл `<state>.lock` подготовить один раз
   и не заменять; сервисы должны видеть тот же файл блокировки. Подключать
   только общий каталог в режиме чтения: отдельное монтирование файла
   состояния может удержать прежний файл после атомарной замены.
2. Из этой же оболочки выполнить в установленном на хосте окружении
   Python с серверным пакетом GRAF:

   ```sh
   python apps/server/scripts/mark_storage_recovery_unknown.py \
     --deployment-lock-fd 9 --file "$state" --scope "$scope" \
     --previous-id "$previous_uuid" --recovery-id "$new_uuid"
   ```

   `state` — абсолютный путь к файлу в том же томе, который видят сервисы.
   Обычный `docker run` не передаёт дескриптор хоста. Наличие Python
   с пакетом GRAF и доступ оператора к тому надо проверить на отдельном
   стенде до использования этой процедуры. `--previous-id` пропускается только при
   создании первого файла состояния. При отказе восстановление не начинать.
   После неоднозначного сбоя повторить с теми же UUID и областью; не выдавать
   второй UUID только ради повтора записи.
3. После `storage_recovery=recovery_unknown` восстановить стенд. Привязать
   каждый проверяемый сервис к той же области, файлу и новому UUID. Проверить
   отказ со старым UUID и с новым UUID при несверенном состоянии, в том числе
   после перезапуска. Команда сама не останавливает сервисы, не выполняет
   сверку и не выдаёт разрешение на возобновление операций. Снятие блокировки
   требует отдельного подтверждения сверки и сохранения обязательств.
   Держать тот же замок при записи во внешний журнал, изменении
   эксплуатационных настроек и восстановлении. Закрыть дескриптор
   (`exec 9>&-`) только после фиксации состояния и проверки, что работа
   сервисов в нём безопасна; при неполной сверке оставить потребителей
   остановленными.

В выпускном Compose API, обработчик записей, обработчик воспроизведения и
фоновая очистка получают `twobrain-rec-storage-recovery` только для чтения
по пути `/run/graf-storage-recovery`; имя файла — `state.json`. При проверке
использовать одноразовую копию тома. Оператор заранее подготавливает внешний
том: при его отсутствии Compose останавливается, не создавая пустую замену.
Писать в том может только отдельный запуск оператора. Не включать этот том
в восстановление снимков БД или
MinIO и не удалять его при замене контейнеров. Для активации задать одинаковые
`TWOBRAIN_STRICT_STORAGE_SCOPE` и `TWOBRAIN_STRICT_STORAGE_RECOVERY_ID` из
журнала эксплуатации. Пустой том без явных настроек ничего не подтверждает.
Только для ещё не активированной области оператор может явно разрешить
прежний режим через `TWOBRAIN_STRICT_STORAGE_RECOVERY_ALLOW_LEGACY=true` и
пустой том. При активации удалить эту настройку из эксплуатационной
конфигурации всех хостов, включая резервные, пересоздать контейнеры всех
четырёх сервисов и сверить их фактические настройки. После появления
`state.json.lock` неполные
настройки или потеря файла состояния не разрешают подтверждать очистку
даже с оставшимся разрешением прежнего режима. Сверить
это на всех четырёх сервисах, включая обычное развёртывание и откат,
прежде чем включать строгую запись.

Запуск и изменение привязки восстановления сериализовать тем же
эксплуатационным замком, что и развёртывание. Перед заменой контейнеров
`cd-remote-runtime.sh` проверяет внешний том на закреплённом образе
кандидата. Разрешены только проверенный прежний режим на пустом томе или
подтверждённый текущий UUID без разрешения прежнего режима. В неизвестном
состоянии обычное развёртывание останавливается до замены контейнеров.
Автоматический откат с возвратом прежнего кода разрешён только если до
развёртывания и при отказе подтверждён прежний режим. В активированной
области при сбое не понижать схему и не запускать старые образы: нужен
совместимый выпуск, прошедший проверку с текущей схемой и привязкой.
Незавершённую попытку обычный запуск отклоняет до смены исходников.
Сохранить `no-rollback.json`, прежние и кандидатские образы и связанные
выпускные записи. Не подставлять результат вручную: существование
`result.json` само по себе не подтверждает состояние сервисов.
На одноразовом стенде под тем же замком, из checkout неудавшегося
выпуска и с привязкой хранилища из журнала, проверить исходную точку:

```sh
python3 infra/scripts/release-images.py check-forward-baseline \
  --failed-attempt "$failed_attempt" --failed-sha "$failed_sha"
```

Результат — только прочитанная ревизия БД. Проверка должна отказать,
если ещё работает потребитель или разовая операция Compose, если
изменились попытка, исходники, образы или привязка хранилища либо
фактическая ревизия не совпадает ни с одной из записанных. Успех
этой проверки пока не разрешает перезапуск или смену исходников.
Подменить PostgreSQL и MinIO по отдельности на одноразовом стенде,
сохранив Docker-образы и номер схемы: оба случая должны дать отказ.
Сверить также отказ при отсутствующем или несверенном внешнем томе.
Побайтовое восстановление может сохранить системные идентификаторы,
поэтому его всегда фиксировать как новую операцию во внешнем журнале.
Для уже собранного образа исправления с точным SHA и идентификатором
`sha256:…` под тем же замком дополнительно выполнить:

```sh
python3 infra/scripts/release-images.py check-forward-candidate \
  --failed-attempt "$failed_attempt" --failed-sha "$failed_sha" \
  --source-sha "$candidate_sha" --image "$candidate_image"
```

Образ с другой схемой, неподтверждённым исходным SHA или без поддержки
чтения внешнего тома должен получить отказ. Эта команда только проверяет
совместимость и не переводит среду на исправленный выпуск.
Перед подготовкой под общим замком оператор сверяет область и UUID с
внешним журналом, ID PostgreSQL, MinIO и Temporal — с исходной
инфраструктурой, и подтверждает, что прежние операции Docker больше
не могут создать или запустить контейнер. Пустой список работающих
потребителей сам по себе этого не подтверждает. Запись оператора
хранится вне checkout и содержит только `schema_version: 1`,
`attempt_id`, `seal_sha256` (SHA-256 файла `no-rollback.json`),
`binding_sha256` (отпечаток сверенной области и UUID),
`snapshot_sha256` (отпечаток свидетельств запуска и снимка остановки),
`docker_operations_quiesced` и объект `infrastructure` с тремя
парами имя службы → полный ID контейнера. Предложение для одноразового
стенда можно получить командой:

```sh
python3 infra/scripts/release-images.py check-forward-stop \
  --deployment-lock-fd 9 --failed-attempt "$failed_attempt" --failed-sha "$failed_sha"
```

Предложение всегда содержит `docker_operations_quiesced: false`.
Сверить его с внешним журналом и отдельно доказать завершение всех
запросов запуска. Только после этого оператор сохраняет свой экземпляр
с `docker_operations_quiesced: true`. При потере замка выполнить
новую сверку: не использовать прежнюю операторскую запись.

```sh
python3 infra/scripts/release-images.py record-forward-stop \
  --deployment-lock-fd 9 --failed-attempt "$failed_attempt" --failed-sha "$failed_sha" \
  --operator-record "$reconciled_operator_record"
```

Помощник проверяет привязку записи и фактическое состояние, но сам
не доказывает завершение неизвестной операции Docker. При отсутствии
намерения, работающем потребителе или неподтверждённой сверке квитанция
не создаётся. В `forward-stops/` сохраняются только отпечаток
операторской записи и технические сведения о сверенной среде;
`forward-stop.json` указывает на текущую квитанцию. При изменении
снимка выполнить новую сверку. Новая квитанция ссылается на прежнюю,
не заменяя её. Кандидат, подготовленный по прежней квитанции,
должен пройти новую подготовку с новым ID попытки.
После записи изменить время запуска остановленного контейнера или
заменить ID зависимости: последующая подготовка либо принятие кандидата
должны отказать. Квитанция не запускает сервисы.

На одноразовом стенде с уже подтверждённым кандидатом и квитанцией
остановки проверить запись подготовки под тем же замком:

```sh
python3 infra/scripts/release-images.py stage-forward \
  --deployment-lock-fd 9 --failed-attempt "$failed_attempt" --failed-sha "$failed_sha" \
  --source-sha "$candidate_sha" --image "$candidate_image" --runtime-image "$runtime_image" \
  --attempt-id "$new_attempt" --candidate-id "$candidate_id" \
  --decision-digest "$decision_digest" --full-digest "$full_digest"
```

Проверить, что новая папка содержит только запись `forward-stage.json`,
а `active.json` и записи неудавшейся попытки не изменились. При другом
образе, изменённой конфигурации Compose, чужом или занятом замке
подготовка должна отказать. Этот шаг не создаёт резервную копию
и не допускает запуск сервисов.

Под тем же замком, после подготовки, на одноразовом стенде создать
свежую копию в новом абсолютном каталоге:

```sh
python3 infra/scripts/release-images.py backup-forward \
  --deployment-lock-fd 9 --attempt-id "$new_attempt" \
  --backup-directory "$new_backup_directory"
```

Сверить неизменность `active.json`, наличие приватной описи
`minio-inventory.jsonl` и связанной квитанции `forward-backup.json`.
Для искусственного объекта проверить, что опись хранит исходные ключ,
размер, SHA-256, тип содержимого и метку `Graf-Upload-Attempt`.
Подменить копию байтами того же размера до финальной сверки: квитанция
не должна появиться. Неверная конфигурация, незавершённые загрузки,
версионирование бакета, сбой сверки, старый каталог или замена контейнера
должны дать отказ. Квитанция подтверждает создание и проверку копии,
но ещё не разрешает запуск сервисов.

На отдельном одноразовом стенде с проектом Compose `twobrain-rec`
выполнить защищённую репетицию. Подстановка другого проекта через
`COMPOSE_PROJECT_NAME` не меняет цели восстановления:

```sh
RESTORE_BACKUP_REFERENCE="$new_backup_directory" \
  ./infra/scripts/rehearse-rec-restore.sh --execute --forward-attempt "$new_attempt"
```

Каталог задаётся каноническим абсолютным путём из букв ASCII, цифр,
точки, дефиса, подчёркивания и косой черты. Нужен результат
`object_restore_mode=verified-forward-manifest` вместе с
`restore_rehearsal_result=pass` и `cleanup_result=pass`. Режим
`legacy-file-mirror` не подтверждает восстановление меток.
В режиме T104 проверить отказ при отсутствующей описи, чужом ID,
неверных байтах в файле и подмене метки. На искусственном защищённом
ключе подтвердить чтение штатным читателем с исходным ID и SHA-256,
отказ с чужим ID и отсутствие выходного файла при отказе. Отдельно
проверить пустой бакет. Репетиция создаёт отдельные временные цели
и не меняет `active.json`.
Перед первым включением на резервном хосте отдельно сверить факт
активации по внешнему журналу. Пустой том не доказывает, что область
никогда не активировалась.

#### Управляемый запуск исправления T104

Перед разработкой запуска на одноразовом стенде проверить выпускной
допуск из чистой локальной `master`, совпадающей с `origin/master`:

```sh
TWOBRAIN_DEPLOY_HOST="$isolated_host" TWOBRAIN_DEPLOY_PATH="$isolated_checkout" \
  ./infra/scripts/cd-remote.sh --forward-preflight "$failed_attempt" "$new_attempt" \
  "$new_backup_directory" --candidate "$decision_json" --evidence "$full_ci_json"
```

Успех — `forward_preflight_result=pass`. Команда проверяет решение `go`
и полный прогон CI для того же SHA. Под общей блокировкой на стенде она
сверяет квитанцию остановки, архив, образы, схему и привязку хранилища.
До и после сравнить HEAD, `active.json` и записи обеих попыток.
Этот допуск предназначен для исходного checkout неудавшегося выпуска
до начала принятия нового кандидата. Если началась запись принятия
или изменился активный указатель, нужен отдельный сценарий повтора.
Проверка может запускать короткие контейнеры для чтения схемы и тома,
но не запускает рабочие службы и не разрешает публикацию. Перед будущим
запуском проверки надо выполнить снова под непрерывно удерживаемой
блокировкой.

Команду запуска проверять на одноразовом стенде с искусственными
записями, штатными ролями и собственным HTTPS-адресом. Выполнить из
чистой локальной `master`, совпадающей с `origin/master`:

```sh
TWOBRAIN_DEPLOY_HOST="$isolated_host" TWOBRAIN_DEPLOY_PATH="$isolated_checkout" \
  ./infra/scripts/cd-remote.sh --forward-execute "$failed_attempt" "$new_attempt" \
  "$new_backup_directory" "$remote_public_approval" "$public_approval_sha256" \
  "$remote_decision_json" "$remote_full_ci_json" --candidate "$decision_json" --evidence "$full_ci_json"
```

Файлы на стенде задаются абсолютными путями. Решение и Full CI должны
совпадать с локальными файлами по точным байтам. Замок удерживается до
конца запуска и записи подтверждения. Успех — `forward_execute_result=pass`
и две записи: `result.json` и `forward-result-confirmed.json`.

Если ответ потерян, сначала дождаться освобождения замка. Потеря SSH сама
по себе не доказывает остановку удалённого процесса. Для проверки
записанного результата выполнить ту же команду с `--forward-confirm`
вместо `--forward-execute`. Если `master` продвинулся, использовать чистую
локальную копию на SHA активной попытки и явно указать `--branch master`.
Удалённая копия тоже должна оставаться на SHA попытки. Подтверждение
сверяет те же файлы допуска, ID и время старта контейнеров, роли, схему,
хранилище и опубликованные файлы. Оно не меняет исходники, не запускает
службы и не повторяет загрузку. Успех — `forward_confirm_result=pass`.

Если подтвердить результат нельзя (например, API уже перезапустился),
остановить потребителей, проверить прекращение операций Docker и MinIO
и получить новое предложение `check-forward-stop`. Только после этой
сверки оператор подтверждает `abandon_unconfirmed_result` и остальные
условия предложения. `record-forward-stop` привязывает квитанцию к SHA-256
исходного результата и наблюдаемой остановке. Результат сохраняется,
подтверждение больше недоступно; разрешена подготовка нового кандидата
по обычным правилам. Квитанция не разрешает принять заменённые контейнеры
PostgreSQL, MinIO или Temporal. Уже подтверждённый результат этим
способом не списывается: для следующего обычного выпуска допустим
штатный перезапуск тех же контейнеров после повторной проверки их
состояния, образов, схемы и хранилища.

Для проверки уже открытого канала macOS оператор готовит отдельную
запись к решению о восстановлении. Поля: `schema_version: 1`, `source_sha`,
`candidate_id`, `decision_digest`, `origin` (точный HTTPS-адрес),
`version` (версия действующего macOS-выпуска без `v`), `pkg_sha256`,
`pkg_bytes`, `appcast_sha256`, `archive_sha256`, `archive_bytes`.
Контрольные суммы трёх файлов берутся из проверенных материалов уже
утверждённой публикации. Нельзя подставлять хеши текущего ответа
сервера как ожидаемые. Сам файл связывается с выпускной командой
по SHA-256 точных байтов. Запись не разрешает публиковать новый пакет.
Проверить отказ при несовпадении решения, перенаправлении на другой
адрес, зависшем ответе и подмене PKG или ZIP файлом такого же размера.

После публичной проверки запустить штатную синтетическую загрузку через
тот же утверждённый HTTPS-адрес. Проверить, что запись о запуске создаётся
до первого обращения к API и повтор под тем же ID отклоняется. Настройка
запущенного API должна подтверждать тот же HTTPS-адрес до создания
сессии. Очистка проверяет точную связь встречи, завершённого сеанса и
ревизии; пустой результат очистки не считается успехом. После очистки
повторно проверить очереди и API. Ошибка загрузки, неподтверждённая
очистка и превышение времени оставляют попытку незавершённой; для
сверки остаётся безопасный `run_id` из `forward-smoke-intent.json`.
Обрыв после принятия загрузки должен удержать запрет на новый кандидат,
пока прежние операции не завершились и остатки не сверены. Сценарий не
подтверждает завершение обработки или транскрибации.

Для прерванного теста получить новое предложение `check-forward-stop`
и выполнить операторскую сверку, описанную выше. Для прерванной загрузки
предложение также содержит `storage_writes_quiesced: false`. Отдельно
подтвердить по операционным сведениям MinIO, что уже принятые PUT
завершились, нет незавершённых составных записей и хранилище остаётся
без версионирования. Пустой список объектов этого не доказывает.
Если подтвердить нельзя, оставить значение `false` и остановиться.
Под тем же замком записать квитанцию `record-forward-stop`, затем на
одноразовом стенде вызвать:

```sh
python3 infra/scripts/release-images.py reconcile-forward-smoke \
  --deployment-lock-fd 9 --failed-attempt "$failed_attempt" --failed-sha "$failed_sha"
```

Команда использует только точный `run_id` из журнала. Временный
`graf-cleanup-<run_id>-<отпечаток остановки>` запускает штатную очистку
под проверенной ролью обслуживания на закреплённом образе. Он не запускает API, обработчики
или миграции и использует уже существующие сети и том. Файл тестовой
записи и ключ сессии в API лежат в частной памяти контейнера и исчезают
при остановке. Результат очистки требует пустой тестовой области в
PostgreSQL и MinIO. Намерения записи в PostgreSQL остаются, пока MinIO
не подтвердит пустую область этого запуска. Квитанция не означает,
что загрузка или выпуск успешны.

Проверить обрыв после принятой загрузки, тайм-аут служебного контейнера,
чужой `run_id`, остатки и повтор после успешной квитанции. При тайм-ауте
не запускать очистку снова с прежней квитанцией: подтвердить окончание
прежних операций, сверить именованный служебный контейнер по ID, образу и
меткам и получить новую квитанцию. Успешный повтор только читает и
проверяет записанный результат. Если прежний контейнер остался, не
удалять по совпадению имени: сначала подтвердить, что это одноразовый
контейнер данной попытки и прежняя операция завершилась.

| Сценарий | Наблюдаемый результат |
| --- | --- |
| Обычный повтор; неверный SHA, `go`, Full CI, архив, попытка, внешний журнал или замок | Никакой смены активной попытки и никакого запуска |
| Только печать запрета отката без доказательства начала; есть намерение, но исход запуска неизвестен | Первая ситуация не даёт допуск к автоматическому переходу. Во второй можно остановить и сверить службы; один и тот же запуск не повторяется |
| Обрыв после смены `active.json`, но до первой записи намерения | Тот же подтверждённый кандидат сверяет идентичные записи и прежние ID зависимостей. При целостном журнале без намерения это первый запуск. Чужой кандидат, намерение или неизвестное состояние дают отказ |
| Несовместимая схема, изменённые ID инфраструктуры, секреты или образы | Отказ до запуска; прежние записи, PostgreSQL, MinIO, Temporal и установщик остаются на месте |

## T125: восстановление главного окна между запусками

Используйте отдельный обычный профиль Windows и установленный подписанный
кандидат. Сначала выполните проверку точного MSIX и EXE из §8, запишите версию,
архитектуру и SHA сборки. Для сравнения на Mac запишите `GRAFSourceSHA`:
этот сценарий происходит из F293; старые результаты T097 его не доказывают.

1. На чистом профиле без сохранённого размещения запустите GRAF. Проверьте
   обычное окно по центру доступной рабочей области: 1080×620 логических
   точек или меньше, если экран не вмещает этот размер.
2. Переместите и измените размер окна; завершите приложение через
   «Закрыть GRAF», дождитесь завершения процесса и откройте его через
   меню «Пуск». Повторите с другим размером и положением. При неизменных
   экране и масштабе четыре границы совпадают с допуском в один физический
   пиксель. На Mac повторите перемещение и перезапуск на том же экране.
3. Повторите на втором экране, по возможности расположенном слева или выше
   основного. Сначала перезапустите с обоими экранами. Затем при закрытом
   приложении отключите второй экран и запустите снова. Окно центрируется
   на основном экране и целиком помещается в его рабочей области.
4. При закрытом приложении смените масштаб сохранённого экрана со 100% на
   200%. После запуска размер в логических точках тот же, если помещается;
   иначе окно ограничено рабочей областью. Заголовок и нативные элементы
   управления доступны с клавиатуры, панель задач не перекрывает окно.
   Отдельно измените рабочую область, например положение или видимость
   панели задач, и повторите запуск. Сверьте DPI awareness HWND:
   96 DPI сам по себе не отличает 100% от DPI-unaware окна.
5. После сохранения нормального прямоугольника разверните и сверните окно,
   затем завершите GRAF через трей. Проверьте обычную геометрию после запуска.
   Повторите после скрытия крестиком и открытия из трея; затем выполните
   отдельный новый запуск. Перемещение с клавиатуры также должно
   сохраниться. Возврат из трея сам по себе не подтверждает
   сохранение между процессами. Приёмку записи и Quit выполняйте по T108.
6. В том же отдельном профиле проверьте запуск с повреждённым значением
   размещения: испытательная оснастка должна менять только значение T125
   и сохранить исходное для возврата. В нативном испытании хранилища отдельно
   воспроизведите отказ чтения и отказ записи; в обоих случаях окно
   остаётся управляемым, а отказ записи не заменяет сохранённое значение.
   Повторите проверку базового запуска
   в состоянии без WebView2. Ожидается доступное обычное окно с начальным
   размещением, без сброса данных кабинета, записи или других настроек.

Запишите размеры рабочих областей, масштаб, результат по каждому шагу и
фактический запуск нового процесса. Упрощённый одноэкранный прогон в VM
оставляет шаги 3–4 открытыми; переносимый расчёт геометрии или запуск EXE
вне пакета не заменяет установленную приёмку.

## T126: потеря выбранного микрофона

Уточнение 2026-11-12: каждый положительный сценарий и порядок гонок ниже
выполнить отдельно с явным выбором и с фактически активным микрофоном,
разрешённым по умолчанию при старте. Сохранить все прежние проверки,
численные пределы и отрицательные сценарии; новый допуск не относится
к незавершённому `starting`. Подтверждать прежний endpoint/worker текущей
сессии. Смена default и ошибка перечисления не являются отключением;
после reconnect микрофон этой сессии не возобновляется.

Сначала воспроизведите исходный отказ на искусственных данных. В проверке
контроллера и звуковой шкалы чередуйте события микрофона, вывода и Stop;
используйте границы `B = S + 719` и `B = S + 960`, где `S` — первый
общий системный отсчёт. Подайте 1 440 системных отсчётов с различимым
значением по индексу и проверьте до кодирования все позиции
`[S, S + 1 440)`: три блока с PTS `S`, `S + 480` и `S + 960`,
без потери, перестановки или повтора. В обычной записи подайте
отличимый ненулевой микрофон до `B`; проверьте ожидаемый вклад на
`[S, B)` и ровно нулевой на `[B, S + 1 440)`, включая результат
AEC с искусственным ненулевым хвостом. Проверьте прежний вес
системного источника в миксе. В WAV и M4A сверяйте длительность и
различимые сигналы; допуск синхронизации файлов — SC-003 (≤ 100 мс).

| Вариант | Критерий |
| --- | --- |
| Подтверждённая потеря фактически активного микрофона в активной записи: явный выбор и default при старте — два отдельных прогона | Одна сессия, явное ограничение, видимый индикатор и Stop, оба системных сигнала присутствуют. Повтор события, повторное подключение и смена устройства по умолчанию не открывают новый микрофон. |
| Смена default без потери прежнего активного входа; ошибка/пустой результат перечисления без доказательства | Не устанавливают microphone-loss/EOS или degraded-продолжение. Не подменяют захваченный вход. Если обычный capture health независимо обнаружил отказ, действует штатное прерывание, а не новый T126 допуск. Раздельно проверить отказ свежего GetState, отсутствующий endpoint без native removal, DISABLED и противоречивое состояние. |
| Потеря раньше Resume | Отложенный и READY Resume отклонены, поздний результат ничего не меняет, OPEN сохраняется до Stop. Ни один скрытый пакет не возвращается. |
| Resume принят раньше потери | Уже принятый CLOSE с прежним T0 не переписывается; отдельно проверить отказ его сохранения с сохранением OPEN по T120. Отсчёты после `B` остаются нулевыми. |
| Stop принят раньше потери | Позднее уведомление не начинает продолжение и не меняет принятый Stop. Ровно один финализатор и одна граница каждого входа, прежний предел Stop. |
| Чужое или устаревшее событие, смена default, потеря системного источника, сбой часов, AEC или хранилища | Чужое событие не меняет запись. | Сохранение и перезапуск | При штатном Stop после подтверждённой потери получен `sealed_degraded` с причиной недоступности микрофона и проверенными системными кадрами после события. После холодного запуска открыть его через защищённое чтение, увидеть ограничение и проверить отказ автоматической и ручной отправки. ## T116 — штатный FFmpeg и измерение памяти

Основание: решение владельца 2026-11-16 и [контракт §5.1](contracts/windows-protected-local-custody.md).
Это критерии будущей проверки, не отчёт о выполнении. T116/T118 остаются открыты.

1. На закреплённой Windows x64 сборке записать source/recipe/DLL hashes,
   архитектуру, параметры LGPL-конфигурации, состав MSIX и фактически загруженные
   app-local модули. Отклонить чужую/отсутствующую/неверной архитектуры DLL,
   GPL/nonfree сборку, внешний executable и поиск библиотеки через случайный PATH.
2. На прежних коротких и обычных искусственных PCM fixtures проверить полный
   decode до EOF через существующий Windows reader, длительность, частоты,
   амплитуду, начало/конец и выбранные fixed windows. Не снижать прежние допуски,
   не обрезать неудачный участок и не объявлять успех по одному файлу/кодированию.
   Проверить protected logical read/seek/hash/upload/playback и restart.
3. Выполнить отдельно 10- и 60-минутные искусственные записи с постоянными
   параметрами потока. Для каждой сохранить длительность, число samples, время
   finalization/Stop, исходный/пиковый/конечный Private Bytes и Working Set всего
   процесса, метод и частоту измерения, отдельно peak счётчика owned GRAF buffers.
   Последний не превышает 64 MiB, включая одновременные candidate/IO буферы;
   отсутствие whole-recording accumulation проверяется путём данных и
   последовательными измерениями. Память процесса не выдавать за чистые
   выделения FFmpeg или за доказательство затирания внутренних копий.
4. При encoder/IO/out-of-memory/cancel/shutdown fault проверить штатное
   освобождение library contexts/packets/frames на всех выходах, затирание
   собственных plaintext buffers, сохранность последнего validated prefix и
   отсутствие normal claim/новых открытых файлов. После повторных полных
   циклов объекты прежнего encoder не должны оставаться живыми; подтвердить
   lifecycle instrumentation и измерениями, а не снижением рабочего набора ОС.
5. Свежий installed MSIX должен пройти запись → Stop → restart → playback →
   upload/recovery и удаление по прежним T117/T118. Отдельно сохраняются
   настоящие microphone/system audio, физическая x64/60min/AEC матрица и T097 UI.
   Непроверенная архитектура/сценарий остаётся NOT_RUN.

Допустимое ограничение: общий расход процесса может превышать 64 MiB; FFmpeg
