# T117 / #7445 — воспроизведение дефекта в нативных путях GRAF

Текущий код выдаёт обычного владельца уже перенесённого хранилища с
подлинным, но изменяемым карантином. После выхода исторический reader
сообщает отказ, однако его попытка замены убирает sentinel со старого
имени. Следующее холодное открытие GRAF отказывает. Это исходная
регрессия, которую предстоит исправить. Данные пользователя в прогоне
не используются.

## Условия и границы

Windows 11 ARM64 в Parallels; два нативных исполняемых файла MSVC x64
Debug. Исторический reader использует реальный код очереди на
`99b00a579c24b50e320465b69d9a296038bc544d`; в текущем тесте только
диагностическая обвязка добавлена к
`NativeCaptureStorageIntegrationTests.cpp` вне рабочего дерева.
Она вызывает `ProtectedCustodyMigration::open` и существующие точки
инъекции, не заменяя реализацию хранилища. Положительный контроль
исторического reader: обычный искусственный реестр с одной записью
прочитан, enqueue принят, вызван один writer.

Сгенерированные профили создавались на выделенном диске E:, отдельном
128 MiB fixed VHD/GPT/NTFS. Для стенда использован повышенный процесс;
проверка обычного пользователя остаётся открытой. В двух прогонах gap
дочерний процесс остановлен после настоящего переименования и
`FlushFileBuffers` исходника, до попытки создать sentinel. Для формы
старого дефекта тест снимает `READONLY` только с искусственного
карантина, оставляя прежние байты. Это воспроизведение формы профиля,
а не прогон установки и обновления исторического MSIX.

| Состояние | Наблюдение |
| --- | --- |
| Оригинал на прежнем имени; форма изменяемого карантина | После подготовительного отказа flush обычный повтор отказывает без переноса: owner=0, error=13, root flush=0, снимок содержимого прежний |
| Оригинал перенесён, sentinel отсутствует, карантин изменяемый | Два исторических процесса отказали, снимок прежний. GRAF отказал: owner=0, error=13, root flush=0, оригинал прежний |
| Тот же разрыв, виден `READONLY`; отказ сброса подготовлен в тесте | Два исторических процесса отказали, снимок прежний. GRAF не дошёл до точки инъекции отказа: root flush=0, sentinel создан, owner=1, оригинал прежний. Это пробел порядка вызовов; видимый атрибут здесь не моделирует потерю питания |
| Завершённый профиль; подлинная пара, карантин изменяемый | Холодное открытие приняло профиль без root flush. Два отдельных исторических процесса вернули отказ без writer; sentinel исчез со старого имени, хеш оригинала прежний. Следующее холодное открытие отказало: error=6; содержимое после этого отказа не изменилось |

Код выхода **86** означает воспроизведение ожидаемого дефекта. Оба
проекта собраны, запуск завершён штатно с точки зрения стенда. Диск
отключён и временный каталог Windows удалён. Рабочий GRAF 0.1.0.18
остался тем же процессом, хеш установленного EXE до и после совпал.
Запись, сеть, рабочий профиль, ключи и настройки GRAF не использованы.

## Проверка смены дескрипторов

Дополнительная нативная проба на одном искусственном файле в Windows
подтвердила причину конфликтов доступа. Усиленное открытие корня или
файла одновременно с прежним `FILE_SHARE_READ` возвращает 32.
Промежуточный дескриптор чтения с разрешением совместного чтения и
записи, но без совместного удаления, позволяет последовательно снять
прежний доступ и открыть усиленный; попытка открыть с `DELETE`
возвращает 32. На файле дескриптор с чтением и записью только атрибутов
открылся, но `FlushFileBuffers` вернул 5; записывающий дескриптор
успешно поставил атрибут и выполнил сброс. На родителе точная маска GRAF
успешно выполнила сброс. Обычные открытия проходят после снятия
усиленных прав. Это проверка Win32 на искусственных объектах, а не
готовый протокол GRAF; во время смены требуется повторная проверка
подлинности и проверка конкуренции в продуктовых путях.

## Очередь перенесена, пакет ожидает переноса

Второй нативный прогон из того же снимка Windows подтвердил отдельный
путь до первой записи пакета. Тест перехватывает только создание
защищённого каталога сгенерированного пакета и один вызов сброса на
корневом каталоге. В подготовительной попытке штатный GRAF перенёс
очередь, записал пару маркеров и дошёл до первого создания каталога
пакета. В этой точке тест вернул `ERROR_WRITE_FAULT`; пакет остался
на старом формате. Проверены одинаковые байты обоих маркеров и
неизменный оригинал очереди.

Повторная попытка выполнялась в двух отдельных профилях: в одном
карантин остался `READONLY`, в другом атрибут снят только с
искусственного маркера. Обычное открытие владельца отказало
(`error=13`, `native=0`) и не изменило снимок. Координатор переноса
в обоих случаях открыл хранилище (`owner=1`), создал каталог пакета
и изменил снимок пакета; вызовов root flush не было, так что
подготовленная инъекция отказа сброса не сработала. Оригинал очереди
и оба маркера сохранили байты. В изменяемом случае карантин остался
изменяемым. Код 86 обозначает воспроизведение пропуска проверки,
а не успешную приёмку.

Этот результат касается ветки с ожидающим пакетом до создания его
защищённого каталога. Отдельный сценарий с уже установленным package
fence и отказы исправленного кода ещё предстоит проверить. Диск NTFS
отключён, временный каталог удалён, установленный EXE и работающий
процесс GRAF 0.1.0.18 совпали до и после. Повышенный тестовый процесс
не считается приёмкой обычного пользователя.

## Установленный GRAF 0.1.0.18 — контроль после открытия пользователем

В рабочей Windows 11 пользователь открыл приложение через «Пуск».
Пакет `com.graf.desktop` 0.1.0.18 со статусом `Ok`; процесс отвечает,
SHA-256 запущенного EXE совпал с указанным выше. В окне видна страница
«Мои встречи» с данными; справа кнопка «Начать запись» недоступна и
показано «Защищённое локальное хранилище недоступно. Записи не изменены».
Это подтверждает загрузку кабинета в установленном приложении и
сохранившийся отказ записи в этом профиле.

Обычный процесс вне пакета прочитал только атрибуты трёх заранее
известных служебных имён. В прямом каталоге очереди видны старое имя
реестра и `.quarantine`, оба — обычные файлы без атрибута `READONLY`;
`.quarantine.stage` не наблюдался. В стандартном каталоге перенаправления
MSIX соответствующая папка приложения не наблюдалась. Эта сверка
устанавливает только видимые атрибуты: подлинность пары, права записи
и точный код отказа рабочего приложения не установлены. Сходство с
одной формой синтетического воспроизведения не устанавливает её как
причину отказа.

Содержимое служебных файлов, записей и ключей не читалось; ничего
не исправлялось в рабочем профиле, захват и отправка не запускались.
T117/T118 и приёмка записи остаются открытыми.

## T117 — повтор после перемещения очереди и до защитного файла на старом имени

В `ProtectedCustodyQueueMigration::openImpl` новый сброс подтверждает
уже видимый `READONLY` только для незавершённой очереди: оригинал уже
перемещён, защитного файла на старом имени ещё нет, обе записи
bootstrap подтверждают тот же перенос очереди. Сначала проверяются
подлинные файлы и полный состав; затем сбрасывается удерживаемый
каталог на NTFS. После снятия временного доступа проверяются история,
снимок и отсутствие старого имени. Новое имя создаётся исключительно
с `CREATE_NEW`; поздно появившаяся копия не принимается и не меняется.

Нативная регрессия `NativeProtectedQueueGatePublication`:
Windows 11 ARM64 в Parallels, MSVC x64 Debug, искусственная очередь
и пакет в отдельном временном каталоге NTFS. В итоговом прогоне
тестовый поток олицетворял текущего пользователя с ограниченным
токеном (`TOKEN_EFFECTIVE_ADMIN=0`), сам запускатель имел повышенный
токен. Точки отказа подменяли только выбранный файловый вызов.

| Проверка | Результат |
| --- | --- |
| Отказ создания файла на старом имени после настоящего переноса | Исходник остался на новом месте; на старом имени ничего нет |
| Отказ повторного сброса | Нет владельца, старое имя не создано, снимок совпал |
| Поздно появившийся файл с точными байтами защитного файла | Отказ с `ERROR_ALREADY_EXISTS`, исходник и поздний файл сохранены |
| Успешный повтор | Проверены оригинальные байты, оба защитных имени и следующий холодный запуск |
| Контроль обычной публикации и конкурентного доступа | Все пять ранее существовавших случаев прошли |

### Итоговый снимок: появление файла до первого чтения и после сброса

После независимого ревью GRAF запоминает отсутствие старого имени уже
при первоначальном перечислении корня. Все проверки маркеров
сохраняют это условие до успешного `CREATE_NEW`. Тесты вставляют точную
копию защитных байтов с теми же закрытыми правами отдельно до первого
чтения старого имени и после успешного сброса каталога. В обоих случаях
отказ `ERROR_ALREADY_EXISTS`; соответственно ноль и один вызов сброса,
файл и все остальные байты сохранены. Повтор без конкурента и следующее
холодное открытие прошли. Независимое ревью исходников закрыло оба
замечания; область решения ограничена этим состоянием миграции.

Тест вернул 0. Хеши итогового манифеста (230 входов),
EXE и журнала соответственно:

- `d41f9e01146d62a43b82f53f47fe63a8c599acd69020df3a283164611b42f0d1`
- `a7f64f27035e96b8787a38c548ff8d1c49eb8ace6756d10e089cb4768d3290ce`
- `eae5b6268fc8699c79772395138cd6d27ee5e97822e86bc651bf78471d9115ee`

Переносимые тесты итогового снимка: 48/48. Рабочий процесс GRAF и
хеш установленной версии сохранены; временные сборки удалены,
микрофон, сеть и рабочее хранилище в тесте не использовались.

### Холодное открытие после завершённого переноса очереди

Изменяемый карантин принимался после проверки содержимого. Старый
читатель затем мог убрать защитный файл со старого имени, хотя сам
сообщал об отказе. Теперь при открытии GRAF удерживает оба защитных
файла, сверяет байты и идентификатор карантина после смены режима
доступа, добавляет только `READONLY` и сбрасывает тот же дескриптор.
Для уже защищённого карантина на NTFS холодное открытие подтверждает
сброс каталога заново. После отказа GRAF не открывает хранилище через
другую ветку координатора. После снятия временных прав GRAF повторно
проверяет историю переноса, состав каталога и отсутствие файлов,
которые уже были удалены.

Нативная сборка MSVC x64 Debug в Windows 11 ARM64 / Parallels,
искусственные данные на NTFS. Тест `NativeProtectedQueueGatePublication`
прошёл под ограниченным эффективным токеном (`TOKEN_EFFECTIVE_ADMIN=0`):

- Изменяемый карантин получил `READONLY`, его байты сохранились,
  обычный читатель смог открыть каталог.
- Отказ сброса через записывающий дескриптор вернул `ERROR_WRITE_FAULT`
  (29) без допуска и без изменения содержимого; видимый атрибут не
  снят. Следующий запуск с отказом сброса каталога тоже не допущен.
  Чистый повтор после успешного сброса открыл хранилище.
- Появление неизвестного служебного файла после начального прохода
  проверки каталога остановило допуск. Точная копия реестра, уже
  удалённого при наличии двух подтверждений, также остановила допуск
  (`ERROR_ALREADY_EXISTS`, 183). Оба файла оставлены на месте;
  остальное содержимое не изменилось.

Два отдельных процесса с историческим читателем из
`99b00a579c24b50e320465b69d9a296038bc544d` проверены под основным
токеном запускателя. Положительный контроль прочитал старую очередь и
вызвал writer один раз. Для защищённого профиля оба запуска отказали
без writer. Для карантина, sentinel и оригинала совпали идентификаторы,
число ссылок и атрибуты; совпали и хеши всех файлов. Следующее обычное
открытие прошло. Оба тестовых процесса завершились с кодом 0.

- SHA-256 манифеста 385 входов: `72e9a314c96dd3d94d8f131a1b2f15b9128ce664f52c691ee8be49d76d8057ed`.
