`GRAF`: `90a33ea2677032141cf2eb453471f0920cf2129b3a1b696bf97b95092b149213`.

`EmbeddedCabinetSupportIncidentBridge.requestScript`. Установленный

## T083: сервер забывает первый ключ после второй отправки

На `3dfeaff5a6774ab12be781547e4a300f9ce2a46c` проверен действующий
`submit_support_incident` с новым PostgreSQL, доступным только через
локальный сокет, и имитацией GitHub. Все проверенные серверные входы
совпали с Git до и после прогона. Файлы службы отчётов и её модели
также совпали с проверенной ссылкой `origin/master`
`2c82da9062faa572c3b247e82bdd2d98fc65d733`.

Один автор, устройство и пространство отправили один безопасный отчёт
v2 с двумя разными ключами. Каждый запрос прошёл в отдельной транзакции.

| Шаг | Счётчик записей | Действие в имитации GitHub |
| --- | ---: | --- |
| Первый запрос A | 1 | Создано обращение |
| Немедленный повтор A | 1 | Запросов нет |
| Новый запрос B | 2 | Обновлено то же обращение |
| Поздний повтор A | **3 вместо 2** | **Повторное обновление** |

Номер CUST оставался прежним; нового обращения в этой пробе не
появилось. Причина наблюдаемого поведения: поиск повтора использует
только `last_idempotency_key_fingerprint` строки инцидента, а запрос B
перезаписывает это поле. Это отдельный отказ от уже воспроизведённых
дублей создания после потери ответа или двух одновременных sync.
Тест не выполнял HTTP-запросов к рабочему серверу или GitHub.
Временная база остановлена и удалена.

| Артефакт | SHA-256 |
| --- | --- |
| Проба `probe.py` | `deea9b026af10c495470b36e105f4150ce04dc78761ce4a3336447571d308ab2` |
| Квитанция `result.json` | `d9680b03f4aca9f30f7eb241292966e9f245041065b9b4453b3aa917aa1e9787` |

**Критерий для отдельной серверной задачи F114.** На том же сценарии
последний A возвращает прежний CUST и счётчик 2; обращение и счётчик
не меняются, запросов к GitHub нет. Ключ того же автора, устройства
и пространства с другим отчётом даёт конфликт даже после B. Чужая
область не узнаёт, существовал ли A. Проект общего контракта должен
явно описать, сколько сервер гарантирует помнить принятый ключ и как
клиент проверяет ранее выданный CUST за пределами этого срока.
Приёмка F114 также сохраняет Mac v1/v2, проверяет Windows v3 и
единственное создание при одновременном sync и потере ответа.
Исправление в клиентской T083 не заменяет этот серверный критерий.
