# F200 / T121: ответ от уже закрытой страницы общей встречи

Задача [T121 / #7933](https://github.com/yshishenya/graf/issues/7933),
контракт Windows §11 и сценарии quickstart. Код зафиксирован на
`972af4762e7afc1a5a1c8d9025aec1eb6ce7127e`; текущий master
`2ca0465aa1721be293cd9b479d8f9d75b8854bfa` входит в историю этой ветки.
Производственный код в рабочей копии не менялся.

На Windows 11 ARM64 собран отдельный MSVC x64 тест с настоящим WebView2
и локальным HTTPS. Сценарий: собственный кабинет → публичная общая
встреча → снова собственный кабинет. Все три документа прошли
сопоставление GET, HTML 200 и завершения навигации. В отдельной копии
исходников задержали доставку завершившегося чтения cookie публичной
страницы, не меняя проверки поколения документа, URL и нативных прав.

один раз. Остались два допустимых чтения сессии кабинета, без выхода,
сброса сессии или смены поколения и nonce нового документа. Публичный
читатель не получил bridge или публикацию локальных записей; семь
поддельных запросов не вызвали нативных действий.

профиль удалён. Все данные, включая сертификат и сессии, искусственные;
сертификат использован только в тестовой среде WebView2. Рабочий GRAF

### Проверка текущей политики Windows

Коммит `f5d61539fc0fbcdd4a05f7416054fa1ac8e2ea57` с основным T121 —
предок текущего `3dfeaff5a6774ab12be781547e4a300f9ce2a46c`.
Скомпилирован текущий `WebViewRoutePolicy.cpp` из рабочей копии
(SHA-256 `30960154b03fee964faadd03d809c64d02f32b7be5534d73648beb4321b63ce8`).
Один тест собственной встречи и по четыре варианта адресной и публичной
ссылок: позиции 0 и 275 мс с версией и без. Все девять маршрутов
разрешены для перехода. У собственной встречи допуск моста сохранился,
у публичного reader отсутствовал, а все четыре адресных варианта были
допущены к мосту вопреки уточнённому контракту. Все четыре варианта
без версии также перенесли позицию. Варианты с версией сохранили позицию
как требуется. Это вывод политики до загрузки документа: выдача nonce,
локальные записи и выполнение нативной команды в пробе не проверялись.

Связанные вызовы показывают, почему одного изменения классификации мало:
сейчас признак публичного reader одновременно выбирает показ без моста,
серверный возврат входа и запрет скачивания. Для адресного reader нужен
тот же безопасный показ с прежним адресным возвратом и отдельным
разрешением серверного вложения. Тестовая сборка удалена; продуктовые
исходники не менялись.

Повторное ревью подтвердило требования к правам reader, внешней активации
и скрытию окна. По оставшимся замечаниям контракт разделяет устаревшую
цепочку навигации и новую цепочку с оставшимся cookie того же ресурса:
без подтверждённого свежего начала возврат не принимается. Правило о
версии распространено на готовый URL, запрос продолжения и редирект.
Эти изменения ещё не проверены в WebView2; подтверждение обычного
успешного входа и безопасного повтора остаётся обязательным.

### Серверный возврат: источник неподтверждённой позиции

Отдельная проверка вызвала два действующих серверных обработчика на

### Что связано с нативными полномочиями адресного просмотра

Независимый просмотр исходников подтвердил два пути: адресная встреча
классифицируется как собственная карточка, а навигация к нативным
настройкам отдельно сообщает о действии в AppMain. Перевод адресного
просмотра в режим без моста требует закрыть оба пути. Сверка собственной
сессии может использовать уже действующее чтение cookie публичной
страницы после доказанного ответа; она не должна выдавать мост.

Для сохранения паритета отдельно проверить прежние доступные способы
экспорта: аудио приходит как серверное вложение, текст сейчас
скачивается из формы через Blob. Нужен отдельный допуск подтверждённого
серверного вложения в T123 с отзывом при смене документа, аккаунта или
запроса. Способ доставки текста и проверка на настоящем WebView2 ещё
не приняты. Смена классификации без этого разорвёт рабочий экспорт.

Проверка существующих путей не нашла готового билета, который можно
переиспользовать для этой выдачи без нового постоянного состояния.
Первый кандидат для нативной пробы — обычный POST формы в отдельный
фрейм того же origin. Сервер может применить действующую проверку
CSRF из поля формы и прежнюю проверку прав/ревизий, затем вернуть
вложение в том же запросе. JSON API остаётся прежним. POST в верхнем
документе служит сравнением: отказ без вложения может заменить reader.

До выбора реализации надо наблюдать на настоящем WebView2, можно ли
связать точный запрос формы с `DownloadStarting` и его одноразовой
меткой. Проверить 200 с вложением, 409 без вложения, редирект и
запоздалое A после B на том же маршруте. Верхний документ, право
скачивания и обработка ошибки должны остаться действующими только для
текущей попытки. Если наблюдаемые события не позволяют доказать связь,
допуск по совпадению адреса запрещён. Общий запрет встраивания кабинета
ослаблять нельзя.

### Адресная встреча: независимое воспроизведение и повтор v5

Независимый просмотр кандидата v3 выявил три расхождения высокого
риска. Явный `next` без версии обходил обработку. Ручная перемотка
до `loadedmetadata` перезаписывалась старой позицией (3,1 → 1,5 с).
После выбора другой вкладки через `replaceState` повтор той же
ссылки игнорировался; «Назад» на исходный адрес без фрагмента
оставляло прежнюю вкладку. В обеих средах переход также переносил
фокус с выбранного элемента на расшифровку.

Кандидат v5 проверен в Chromium и WebKit на действующих шаблонах
входа, регистрации и её формы email. В каждой среде 54 случая:
явный и унаследованный фрагменты и их приоритет, позиция 0 и 1500,
нет версии, одна версия и дубликат; сверены фактически отрисованные
поля и ссылки, включая действующие действия Яндекс/VK. На исходнике
24 случая из 54 не соответствовали ожиданию в каждой среде,
на v5 — 0 из 54. Сценарии проверяют HTML и передачу `next`, не
вход у внешнего провайдера.

С искусственным WAV поздняя загрузка метаданных после снятия
позиции больше не перематывает запись (1,5 → 0 с по сравнению с
исходником). Отдельная управляемая проба в обеих средах подтвердила
сохранение ручной позиции 3,1 с, клавиатурную шкалу (10 с),
восстановление вкладки и повторный переход на 1,5 с. Переходы
истории с изменением только query показывают одно сообщение об
устаревшей версии и убирают его после возврата; ссылка на новое

«Открыть в GRAF» и «Войти» до события `hashchange`. Оба передали
`15000` и на исходнике, и с пробным сбросом, в обоих движках.
После события пробный сброс больше не переносил позицию. Это
управляемая проверка порядка вызовов, а не результат ручного клика
в таком промежутке. Для постоянной правки требуется проверка текущего
адреса в момент передачи ссылки или применения ожидания. См.
[проект отдельного среза](t121-public-pending-seek-proposal.md).

### Публичная встреча: оба порядка событий на настоящем WAV

В отдельном браузерном опыте кандидат сверяет живой фрагмент при
формировании перехода и при `loadedmetadata`, а позднее событие
`hashchange` не повторяет уже применённую команду. Проверены Chromium
и WebKit, четыре цели из исходной позиции 15000 мс: итоги, запись
без позиции, явные 7000 и 0. Во всех 8 случаях для каждого из двух
порядков три ссылки передали ожидаемые вкладку, позицию, версию
и действие; проигрыватель остался на паузе.

Для раннего порядка фрагмент менялся в перехватывающем обработчике
настоящего `loadedmetadata` (`isTrusted=true`, `readyState>=1`);
счётчик `hashchange` в этот момент был 0. Затем он достиг 1.
Сеттер фактического `currentTime` не вызывался для итогов и записи
без позиции, вызывался ровно один раз для 7 и 0 секунд. Для позднего
порядка менялся фрагмент, ссылки проверялись сразу, затем отдавался WAV
и сверялось фактическое время. Изменения пока подставлялись только
в перехваченный браузерный ответ; исходник пакета не проверялся.

### Публичная встреча: повтор того же таймкода до уведомления браузера

Независимое ревью предыдущей правки нашло ещё один порядок: адрес
