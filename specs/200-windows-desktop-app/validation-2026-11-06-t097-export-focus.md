# T097 / SC-009 — клавиатура после отмены экспорта

Проверка сценария из [quickstart §11](quickstart.md#11-итоговая-приёмка-двух-платформ-2026-09-27).
Windows 11 ARM64 в Parallels, сборка 26300.9711, MSVC x64.
Исходник `972af4762e7afc1a5a1c8d9025aec1eb6ce7127e`, десять файлов
`RecApp/Web` совпадают с [входами MSIX 0.1.0.23](validation-2026-11-06-package-023.md).
Исполняемый файл стенда не является установленным приложением.

В отдельном окне настоящий `WebView2Host::attach` открыл искусственную
страницу кабинета по локальному HTTPS. Сначала подтверждены системный
фокус и доставка Escape исходному элементу. Страница создала один
искусственный TXT через `blob:`; открылась настоящая системная панель
сохранения. Отдельный ограниченный по времени наблюдатель подтвердил
принадлежность диалога стенду и один раз вызвал «Отмена». WebView2 вернул
`Interrupted / UserCanceled` для этой загрузки. После закрытия диалога
без щелчка или программного возврата фокуса тот же элемент получил
второй Escape через системное сообщение выбранному окну.

Первая сборка стенда не скомпилировалась из-за недостающих заголовков
самого теста. Предварительный запуск проверил окно и доставку Escape,
но не доказал отмену загрузки и выбор элемента. Эти пробелы выявлены
независимым ревью и устранены в итоговом прогоне. Перед созданием
WebView2 проверены настройки переопределения в процессе и реестре;
для отдельной папки стенда и профиля проверены права текущего
пользователя/SYSTEM и отсутствие точек перенаправления.

Итог: **PASS для отмены и возврата фокуса в изолированном окне**.
Браузер и сервер штатно завершились, выход 0. Временные файлы и
искусственный ключ удалены. Пакет, процесс и EXE рабочего GRAF 0.1.0.18

## Что фактически показывает диалог Windows

фильтром и исходным именем, что и GRAF. Во всех четырёх замерах

## Поле и результат сохранения могут различаться

Стенд с десятью точными файлами WebView2 из входов MSIX 0.1.0.23

### Следующая отказная проверка системного диалога

В исходнике `WebView2Host.cpp` обработчик DownloadStarting резервирует
слот диалога пустой функцией. `cancelDialog()` освобождает слот, но
не закрывает уже открытый `GetSaveFileNameW`. После возврата из диалога
проверяется поколение страницы; при отказе текущего документа
(`fail()`) поколение само по себе не меняется. Это наблюдение по коду,
а не подтверждённый результат работы диалога.

На изолированном настоящем WebView2 нужны два отдельных прогона:
открыть системный диалог с синтетическим файлом, затем (1) перейти
на другой разрешённый документ или (2) отозвать готовность текущего
документа без смены поколения. В обоих случаях подтвердить, что
событие отзыва действительно обработано во время модального окна,
диалог закрывается, файл не появляется, а завершение старого экспорта
не меняет фокус или состояние нового документа. Контроль Save/Cancel
на неизменном документе должен оставаться успешным.

### Переключение в другое приложение при открытом диалоге

В Windows ARM64 Parallels проверен тот же x64-код `WebView2Host.*` в
изолированном WinUI/WebView2. Отдельный процесс стенда получил активное окно

не доказывает перехват фокуса. Проверка с раздельными сигналами подготовлена.

### Позднее переключение: возврат только внутри активного GRAF

На 2026-11-07 отдельно перепроверен живой эталон: запущенный
`/Applications/GRAF Dev.app`, версия `0.0.0-dev`, macOS 27.2 arm64,
EXE SHA-256 `90a33ea2677032141cf2eb453471f0920cf2129b3a1b696bf97b95092b149213`.

не вводились данные; это подтверждение эталона, не приёмка Mac UI.

Проверен вариант только в стенде: `IFileSaveDialog::Show(nullptr)` в
потоке интерфейса GRAF, кабинет временно недоступен для ввода. Обработчик
смотрит на скрытие точного окна диалога. Если оно ещё впереди, разрешает
ввод в кабинет и вызывает `SetActiveWindow`. Если пользователь уже
перешёл в другое приложение, не активирует кабинет.
[Документация SetActiveWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setactivewindow)
ограничивает перевод окна на передний план активным приложением.

Первый вариант дополнительно вызывал `SetFocus` для прежнего дочернего
окна. Windows x64/Parallels: обычные Save/Cancel с Escape, фоновый переход,
позднее переключение после `WM_CLOSE`, переход при активном кабинете,
отзыв без смены поколения и отказ записи с повтором прошли. При позднем
переключении независимые события не зафиксировали промежуточной
активации GRAF; внешний процесс сохранил фокус поля, отозванный экспорт
не создал файл. Повтор позднего прогона с тем же EXE прошёл.
Манифест `e53be31e977bea3cc4a6dc6444a6bad3a9958234ddf7c2b5e598635d92b77bf7`,
EXE `4428ec38536e18347fef8138bc3fc5a954f118368469b5e9d4e77c7f0af32983`,
повтор позднего прогона `8ec0603ae4c94b63a32f81ee4da0ce9882d58256fc1081a2678e1050b181f324`.
Независимое ревью отклонило прямой `SetFocus` для продукта: он сам может
активировать окно или его родителя, а проверка фокуса перед вызовом
не удерживает его. Системная связь владельца с диалогом в этом
варианте тоже отсутствует.

Без прямого `SetFocus` обычные Save/Cancel сохранили исходное
нативное окно и клавишу Escape в исходном DOM-элементе. Отзыв без
смены поколения тоже прошёл. Но при управляемой передаче активности
другому процессу **после** последней проверки и **перед**
`SetActiveWindow` Windows зарегистрировала промежуточную активацию
кабинета. Манифест
`0d6cd7d9c56dcb0acfc23a4c77a3110b445dd0c3ea7daa64304c61e3484116c9`,

Различающий контроль, тот же EXE для двух вариантов: в обоих
кабинет был снова доступен, а окно второго процесса и его поле получили
фокус в той же точке, пока диалог ещё существовал. При пропуске
`SetActiveWindow` второй процесс сохранил фокус без промежуточной
активации; отозванная загрузка не создала файл. При вызове
`SetActiveWindow` с тем же предварительным состоянием снова было

и Escape прошло. EXE
`86c492744b57d65c265605f8445e56d79541a249e9d80d3adff8a1e7e92e0141`,
манифест `c5379bfc88eda38be777134245867ae4580005057f35c9b798f5632c59747110`,
без вызова `a3f22239c50f718816273bff7faf43cdb5096533f9645695d59d1da8ef530ede`,
с вызовом `203199765922c52ea566abb436d666953d91f50ff29dde9378e8270518cfe65e`.
В этом порядке вызов не является надёжным способом сохранить чужой
фокус. Ни один вариант из этого опыта не внесён в код продукта.

Современный [FileSavePicker из Windows App SDK](https://github.com/microsoft/WindowsAppSDK/blob/5c22efb69bcce7da50e2efd1c279a88ede76a37b/dev/Interop/StoragePickers/FileSavePicker.cpp)
использует тот же COM-диалог с нативным владельцем на фоновом потоке.
В просмотренном исходнике отмена проверяется до входа в `Show`,
а [возврат клавиатуры](https://github.com/microsoft/WindowsAppSDK/blob/eb11b094d05c4a230d707fbb1455cafab78791fa/dev/Interop/StoragePickers/PickerCommon.cpp#L147)
выполняется отдельным `SetFocus`. Поэтому замена API сама по себе
не подтверждает ни закрытие открытого окна при отзыве, ни защиту от
перехвата фокуса. Следующий различающий прогон: оставить настоящий
HWND владельца и перенести COM-диалог в выделенный поток, где можно
точно отменять свой диалог; отдельно подтвердить обычную клавиатуру,
отзыв и отсутствие даже краткой активации после позднего переключения.
Исправление общего экспорта и установленный GRAF 0.1.0.18 этим
экспериментом не менялись. T097 остаётся открыта.

### T123 — права на сброс выбранного каталога NTFS

### T123 — нативный прототип восстановления и предел защиты версии на NTFS

В рабочей копии поверх
`3dfeaff5a6774ab12be781547e4a300f9ce2a46c` проверен отдельный нативный
путь, который не вызывается из панели экспорта. Перед перемещением
исходника он фиксирует закрытое намерение с идентификаторами каталогов
и файлов, длинами, SHA-256 и проверяемыми свойствами. При восстановлении
одного File ID недостаточно: изменение байтов при прежней длине и
восстановленном времени записи оставляет резерв и намерение на месте.
Разрешение относится к одной подготовке, поэтому позднее подтверждение
A не расходует подтверждение B и не меняет ни A, ни B. Служебные имена
нельзя выбрать для замены; проверяется настоящее имя открытого файла,
включая отказ при выборе существующего короткого имени 8.3.

Цель `NativeExportSaveCommitTests` собрана штатным CMake/Ninja, MSVC
Release x64, в Windows 11 ARM64 под Parallels. Контрольные суммы 230
входов проверены до и после. CTest: 1/1; внутри этой цели прошли
отмена, успешная операция, принудительная остановка после записи
намерения, переноса исходника, публикации и удаления резерва, а также
повторное прерывание восстановления. Позднее чужое имя, повреждённое
намерение, перезапись опубликованного файла или резерва с тем же File
ID не разрешают уборку. Прежние тесты нового файла, создания папки,
повторного выбора и отзыва разрешения в той же цели прошли.
При сравнении опубликованной версии учтены два допустимых времени
создания: нового объекта до переноса и предыдущего объекта под
тем же именем ([поведение NTFS при повторном использовании имени](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fltkernel/nf-fltkernel-fltgettunneledname)).
В отдельном сценарии конечное имя временно занял другой файл с
отличным временем создания. После его удаления при обратном переносе
исходника NTFS действительно подставила это время. Дополнительная
проверка после переноса сохранила возвращённые байты, намерение и
временный файл (`EXPORT_REPLACEMENT_RESTORE_TUNNELING=RETAINED`).

Отдельная синтетическая проба показала, что дескриптор с
`DELETE | FILE_READ_DATA | FILE_READ_ATTRIBUTES` и `FILE_SHARE_READ`
блокирует конкурентное открытие основного потока для записи (ошибка 32),
но разрешает открытие с `FILE_WRITE_ATTRIBUTES` и создание
дополнительного именованного потока. Последний сценарий также проверен
в продуктовой функции: поток появился после подготовки, повторная
проверка отклонила фиксацию, сохранила исходник и убрала намерение.
Это проверка обнаружения изменения, а не доказательство исключения
изменения между проверкой и переносом или удалением.
[Документация Microsoft по потокам NTFS](https://learn.microsoft.com/en-us/windows/win32/fileio/file-streams)
подтверждает, что режимы совместного доступа и оппортунистические
блокировки действуют на отдельный поток. Условие неизменности всей
версии из контракта T123 этим способом не выполняется.

### 2026-11-08 — ввод длинного адреса и запоздалый переход

На локальном NTFS созданы две искусственные соседние папки: полный
путь первой — 259 символов, путь второй совпадает с первым до последнего
символа и имеет длину 260. Исходник панели из 0.1.0.34 при вводе через
нативный EDIT обрезал второй адрес до первого. После «Открыть» →
«Сохранить» обработчик получил путь к первой папке. Стенд проверяет
выбранное место; он не записывает файл экспорта.

Отдельная проба Shell показала: при 259 символах полученный
`SIGDN_FILESYSPATH` совпал с запросом; при 260 и 331 обычный и
относительный разбор вернули успех с несовпадающим путём. Разбор с
явным префиксом длинного пути вернул `0x80070057`. Поэтому проверка
именно поля адреса не поднимает предел выбора папки в ExplorerBrowser.

Исправленный вариант сохраняет введённый адрес и объясняет отказ.
В ходе перехода запоминается исходный текст до разбора адреса.
Пользовательский черновик отличается от подтверждённой папки —
сохранение и создание папки требуют сначала открыть введённый адрес.
Опоздавший результат прежнего перехода не стирает новый адрес.

Проверено на Windows 11 ARM64 в Parallels, MSVC x64, `/W4 /WX`, в
отдельном рабочем столе, без переключения рабочего стола ввода:

- Вставка всех 260 символов; отказ от Save до «Открыть»; после
  «Открыть» адрес не изменился, Save выключена, вызовов сохранения 0.
- Удержание завершения старого перехода до ввода длинного адреса и
  команды Enter: после старого результата сохранились новый текст и
  сообщение об отказе, Save оставалась выключенной. Допустимый адрес
  снова открывается по Enter.
- Изменение текста внутри вызова разбора Shell: поздний результат
  не подменил адрес, сохранение не вызвано; после допустимого
  адреса обработчик один раз получил именно ожидаемую папку.
- Временный каталог Windows удалён. Окно и процесс рабочей
  версии 0.1.0.18 продолжают отвечать; установка, рабочие записи и
  хранилище не использовались в тесте.
