# T117: нативная проверка публикации защитного файла

Исследование Windows 11 ARM64 / NTFS в Parallels. Все операции выполнялись
в отдельных временных каталогах с искусственными байтами. Исходники
приложения, установленный GRAF и его профиль не участвовали.
Исходная регрессия: [исторический читатель очереди](validation-2026-11-06-t117-historical-queue.md).

Создание и публикация проверены через нативный Windows API:

- Записать файл на временное имя с `DELETE_ON_CLOSE`, включить
  `FILE_ATTRIBUTE_READONLY`, выполнить `FlushFileBuffers` через
  исходный дескриптор с правом записи. Снять удаление при закрытии
  на том же дескрипторе, выполнить rename **без замены** на постоянное имя,
  затем ещё раз выполнить flush. Атрибут и точные байты сохранились.
- Rename без замены на занятое имя отказал с
  `STATUS_OBJECT_NAME_COLLISION` (`0xC0000035`).
- `FileRenameInformationEx` с флагами замены и POSIX при открытом
  аутентифицируемом файле назначения с `FILE_SHARE_READ` отказал с
  `STATUS_SHARING_VIOLATION` (`0xC0000043`). Для этого пути нельзя
  ослаблять текущую блокировку: API выбирает цель по имени, а не сравнивает
  её `FileId` атомарно перед заменой. Нативная проверка также показала,
  что readonly на **исходном** sentinel не защищает от старого
  `MoveFileExW` при изменяемом карантине.

Затем пять дочерних процессов остановлены через `TerminateProcess` без
выхода из областей дескрипторов:

| Точка остановки | Что увидел следующий процесс |
| --- | --- |
| До первого flush временного файла | Временного и постоянного файла нет |
| После первого flush, до снятия удаления при закрытии | Временного и постоянного файла нет |
| После снятия удаления при закрытии, до rename | Полный readonly временный файл; постоянного нет |
| После успешного rename, до второго flush | Постоянный readonly файл; временного нет |
| После второго flush | Постоянный readonly файл; временного нет |

Исходный тестовый реестр сохранился во всех пяти случаях. В третьем
сценарии новый процесс удалил только точную ожидаемую временную копию
через проверенный дескриптор, не снимая readonly. В отрицательном
контроле несовпадающий временный файл остался на месте. В приложении
эта проверка должна сравнивать байты и контекст зафиксированного
зашифрованного блока intent; совпадение имени не доказывает происхождение.
Это аварийное завершение процесса, **не** потеря питания: наличие имени
после rename до второго flush не доказывает его запись на накопитель.

Границы проверяемого решения для новых переносов: только выделенное
временное имя, `CREATE_NEW` и публикация без замены после flush.
При штатном прерывании известную временную копию можно заново подготовить;
неизвестный или неполный файл сохраняется для диагностики. После
публикации необходимо доказать, что постоянное имя, под которым старый
читатель ищет защиту, зафиксировано до переноса исходного реестра.
Изменение уже существующего изменяемого карантина остаётся отдельным
путём; тест не разрешает его подмену, открытие очереди или выпуск.

## Запись имени и удержание каталога

Отдельная проба повторила режим блокировки каталога из GRAF. Относительный
rename без замены в том же каталоге (нативное простое имя,
`RootDirectory=null`) прошёл под текущей блокировкой. Открытие второго
дескриптора каталога с правом записи после взятия существующей блокировки
отказало с Win32 32.

Затем каталог **сразу** открыт с теми же запретами совместной записи и
удаления, но с дополнительным правом `FILE_ADD_FILE` у удерживаемого
дескриптора. Второй дескриптор на запись по-прежнему получил Win32 32;
штатные перечисление каталога, rename и `FlushFileBuffers` на уже
удерживаемом каталоге прошли. Постоянное имя и readonly перечитаны.
[Правила Microsoft для сброса каталога](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/0de7dc40-9627-437e-a4df-c4696cdc3d02)
дают основание использовать flush каталога для записи **привязки имени**
после уже подтверждённой записи самого файла. Они не позволяют считать
flush каталога подтверждением изменения атрибутов ранее существовавшего
файла.

Перед реализацией нужно проверить область такого дескриптора в GRAF:
взятие прав в начале узкой фазы переноса, сохранение блокировки,
повторная проверка identity и отсутствие конфликтов с обычными
читателями. Не добавлять право к общему открытию корня как побочный
эффект. Результаты Windows: `FlushRoot.ps1`
`060c683499f8b453efcb66a43ea441a088b9eb494b46608432abbd840e545c27`;
`flush-root.json`
`fe113866473608214fd09b32c1fed54d861b39c7cfa6faccb12ca845e59220d8`.

Повторены все пять остановок с этим режимом каталога, относительным
rename и прежним запретом совместной записи/удаления. После остановки
сразу за rename новый процесс открыл readonly-файл, проверил точные
ожидаемые байты, зафиксировал привязку имени через свой удерживаемый
дескриптор каталога и снова проверил наличие исходника. Снимки временных
файлов и отрицательный контроль совпали с первым прогоном. Это новый
успешный flush на повторе, а не вывод о результате предыдущего.

## Условия для проверки в коде GRAF

Подготовку нового карантина следует отделить от переключения очереди.
Подготовка получает дополнительное право только на конечный каталог,
сохраняет обычные исключения совместного доступа и не передаёт этот
дескриптор обычному владельцу. В ней допустимы только проверка контекста
переноса, выпуск нового защитного файла, запись его имени и чтение
результата. До подтверждения публикации не переименовывать исходный
реестр и не публиковать защищённое состояние очереди.

Один из вариантов передачи: завершить фазу подготовки без выдачи
полномочий, затем заново получить обычные дескрипторы, повторно проверить
всю цепочку и связать её с результатом подготовки (идентичности тома,
корня и файла, точные байты, контекст и исходный реестр). Несовпадение
между фазами означает отказ без переноса исходника. Нельзя просто закрыть
один дескриптор и продолжить работу по старым результатам проверки пути.
Проверить этот вариант с реальными независимыми открытиями GRAF,
включая отсутствие несовместимого дескриптора после получения обычного
владельца. Старые изменяемые карантины, уже начатые переносы и
неизвестные артефакты остаются отдельными отрицательными ветками до
независимой проверки полного плана.

Проверено на NTFS в Windows ARM64, на искусственных файлах: после закрытия
дескрипторов подготовки обычное открытие принимает неизменённый набор.
Отдельное обычное открытие каталога совместимо во всех пяти случаях;
дескриптор подготовки к этому моменту уже закрыт. Объект с теми же байтами,
но другим идентификатором отклонён отдельно для корня, карантина и исходного
реестра. Изменение байтов реестра при неизменном идентификаторе тоже
отклонено. Все исходные файлы остались на месте; тестовый каталог удалён.
Это проверка возможности повторного связывания тома и идентификаторов,
без операций миграции GRAF и без подтверждения установленного пакета.

- `IdentityProbe.cs`:
  `288aa53ae666f4291d4901864d1ce99b736c52af612da54fa5e74f62f79ae658`;
  `Identity.ps1`:
  `133cea28f28091b0c233b794b3da41d0c8fb59b8e88cdcf7c23a3ddbc36d7a5d`;
  `identity-result.json`:
  `cae2abe0c1746035d406321fc3d025acc45c0d98d9d1bbcd5e58b70cacc1aa40`.

## Нативная подготовка самим GRAF

Отдельная диагностическая сборка MSVC x64 на Windows 11 ARM64:
исходники GRAF `972af4762e7afc1a5a1c8d9025aec1eb6ce7127e` без изменений.
В копии теста `NativeCaptureStorageIntegrationTests` перехвачено только
первое точное открытие конечного каталога во время
`ProtectedCustodyQueueMigration::prepare`. Контроль использует исходные
права. Опыт добавляет `FILE_ADD_FILE` без изменения `FILE_SHARE_READ`.

В обоих случаях подготовка прошла, нативный код открыл конечный каталог
ровно один раз. При добавленном праве `FlushFileBuffers` на удерживаемом
дескрипторе успешен; отдельные чтение и запись с обычным режимом
совместного доступа получили Win32 32. До завершения подготовительной
фазы исходный реестр по прежнему имени сохранил точный SHA-256,
карантин и сохранённый оригинал отсутствовали. После освобождения
всех дескрипторов обычный перенос GRAF завершился в обеих пробах,
сохранив оригинал с тем же SHA-256. Само опубликование readonly-карантина
в эту сборку не входило.

Проверены 224 входа; временный каталог Windows удалён, SHA-256
установленного EXE до и после одинаков. Исходный манифест:
`68364efb58dfa8ee7438938ea73077540e256e6748094e94041d21c290dbda7d`;
тестовая правка:
`9d26945e712bac3423f1667b756ce4f3a884362fb4a1207fec4c0f9a6406445c`;
вывод `pair.log`:
`4431a234af1ddf53acf255f2c764254d87426add9776d3b0e8750af7aaa727d0`;
`result.json`:
`d21503d6390ef2e4a13bce2147709174621428c50aa802178b670a35009eb5ba`.

Второй опыт прошёл через `ProtectedCustodyMigration::open` целиком,
включая перенос искусственного пакета. В контроле конечный каталог
открывается трижды: обычная попытка, поиск защищённой истории и перенос
старой очереди. На трёх новых профилях временное право отдельно добавлено
при каждом из этих открытий, при тех же запретах совместного доступа.
Все четыре случая завершились, сохранили точные байты исходного реестра
и прошли обычный холодный запуск без изменений файлов. Только при праве
на **третьем** открытии независимый обычный читатель получил Win32 32
после успешного возврата владельца. Тем самым подтверждён конкретный
побочный эффект, если просто добавить право к существующему пути
переноса: каталог с этим правом переживает миграцию.

Манифест 224 входов:
`9b1939cc2caf72cfe25c07f7db63a510ccdb444236f6c298310c213fefa5a0b4`;
тестовая правка:
`f9de79f372ef1d386703703479926572df138d43d2cdb5b8decd6ef176947bc0`;
`pair.log`:
`47a03f203f0634d10e67900c70bca9b5fd172567fd3c348cae8b7926069732d5`;
`result.json`:
`b7c34c6640b9b1a693148c52cd07d31755c36932cd37c94adfdd0f8602f8adf7`.
MSVC x64: настройка, сборка и сценарий завершились с кодом 0.
Тестовый каталог удалён. Установленный EXE 0.1.0.18 не изменился.

Вывод для плана: временное право допустимо только у закрытого
работника переноса; прямое присвоение его корня обычному владельцу
недопустимо. Оставить непрерывное исключение до фиксации нового
карантина, переноса реестра и подтверждения защищённого состояния
очереди. Вариант для независимой проверки — снять право после этого,
но до продолжения пакетного переноса или обычного допуска: открыть
обычный корень заново с проверкой тома и FileId, сохранить удерживаемые
дескрипторы ролей и контекст проверки отсутствий, перепроверить все
обязательные имена, данные и защищённые пары. Повторить обнаруженный
запрет на открытие как отрицательный контроль и доказать обычное
открытие при живом владельце после исправления. Этот вывод не
разрешает переименовать старый реестр при неподтверждённом карантине
или чинить уже существующий изменяемый карантин.

Отдельный контроль на NTFS проверил, чего **не** даёт такой дескриптор.
При удержании родителя обычный `MoveFileExW` вернул 32 даже без
блокировки конечного каталога, но прямой нативный rename в том же
контроле прошёл. Пока удерживался конечный каталог, открытие для
нативного rename получило 32. В промежутке между его закрытием и
повторным открытием нативный rename с удерживаемыми дочерним
каталогом, файлом роли и дескриптором атрибутов был отклонён
(`STATUS_ACCESS_DENIED`); новый обычный дескриптор и ещё один читатель
получили прежний FileId. Создание и удаление постороннего дочернего
каталога прошло **и при удерживаемом сильном дескрипторе, и в
промежутке**. Поэтому режим совместного доступа сам по себе не
фиксирует состав каталога; проверки удерживаемых объектов, полного
состава и ранее обнаруженного нарушения нельзя заменить проверкой
FileId. Это один сценарий нативного rename, а не доказательство
универсального запрета внешних изменений.

`RebindGapNative.ps1`:
`464aaebc05fe5d4808ba1a94a5ac14f0c1b14643433b601994f10d1cde72bafd`;
`rebind-gap-native.json`:
`574043807db584c6f7433dfcb65e2c4cde8868f80e4be86a4fc05ffc5a4cb73b`.
Тестовый каталог удалён.

Следующая проба использовала самостоятельный дочерний процесс на
точной границе смены дескриптора. До смены промежуточный дескриптор
успешно открыт с `FILE_LIST_DIRECTORY` и совместной записью, без
совместного удаления. После закрытия усиленного дескриптора дочерний
процесс получил Win32 32 уже на DELETE-open; нативный rename в
контроле без промежуточного дескриптора прошёл. Другой процесс создал
временный и сохраняющийся каталоги. Чужой пишущий дескриптор удерживался
на момент обычного открытия, которое отказало с Win32 32. После закрытия
чужого дескриптора обычное открытие получило исходный FileId, и при
живом обычном дескрипторе второй читатель открыл тот же каталог.
Это нативная проверка границы, не прогон будущего кода GRAF; отказ
из-за выжившего или ранее обнаруженного child предстоит проверить
на настоящем worker. Тестовый каталог удалён.

## Отдельный контроль ранее изменяемого файла

Искусственный файл переведён в readonly без явного flush. Повторное
открытие с `FILE_WRITE_DATA` или `FILE_APPEND_DATA` отклонено (Win32 5).
Дескриптор с `FILE_WRITE_ATTRIBUTES` открылся, но оба вызова сброса
отклонены: `FlushFileBuffers` вернул 5, `NtFlushBuffersFileEx` вернул
`STATUS_ACCESS_DENIED`. Добавление `FILE_FLAG_WRITE_THROUGH` к этому
дескриптору не изменило результаты сброса. Повторная установка ровно
тех же атрибутов с этим флагом вернула успех без изменения `ChangeTime`;
видимый readonly и байты остались прежними. Положительный контроль на
изменяемом файле прошёл для обоих API. В [документации Microsoft о
write-through](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew#caching-behavior)
речь идёт о метаданных, изменённых самой операцией; успешное повторение
без видимого изменения не принимается за новый подтверждённый flush.
Потеря питания не имитировалась, тестовый каталог удалён.

`0e08a45f43e2e5e394cc1244b481d836834a4e8e9172b388edd32756d6f717bd`;
`readonly-flush-matrix.json`:
`2a488d8f02f26434549f616fedc1247c282093a7671f35e414160894aff7798d`.

## RED: порядок перед переносом исходника в коде GRAF

Сборка MSVC x64 из `972af4762e7afc1a5a1c8d9025aec1eb6ce7127e` на
Windows 11 ARM64. Только в копии теста добавлены две проверки реального
`ProtectedCustodyMigration::open` на сгенерированном v3 профиле.
Перехватываются нативный rename точного файла исходной очереди и
`FlushFileBuffers` точного корня профиля. Для отрицательной ветки только
сброс корня должен возвращать `ERROR_WRITE_FAULT`. Тест оставляет
исходные production файлы неизменными.

- В контроле перед настоящим rename карантин не readonly, сброс корня
  не вызван. GRAF завершил перенос; исходные байты подтверждены в

## T117: варианты для существующего изменяемого карантина

Пробы NTFS в основной Windows 11 ARM64, только собственные искусственные
файлы. Источник `t117-legacy-repair.eBCInT5s`, гостевые временные каталоги
удалены. Потеря питания и установленный перенос не проверялись.

- На дескрипторе чтения и записи атрибутов Windows приняла изменение
  `READONLY` для изменяемого файла и изменение `ARCHIVE` у уже защищённого
  файла (33 → 1 → 33, защита не снималась). Точный FileId и байты сохранились,
  исторический вызов `MoveFileExW` получил 5 и до закрытия, и после.
  Однако `FlushFileBuffers` вернул 5, а наблюдаемые результаты были теми же
  с `FILE_FLAG_WRITE_THROUGH` и без него. Документация
  [CreateFileW](https://learn.microsoft.com/windows/win32/api/fileapi/nf-fileapi-createfilew#caching-behavior)
  описывает сброс изменений, вызванных запросом. Из пробы нельзя заключить,
  что новый `ARCHIVE` подтверждает запись ранее неподтверждённого
  `READONLY`. Параллельное открытие только на запись атрибутов также прошло.
- Нативная замена подготовленным файлом работает без блокировки прежнего
  объекта или с `FILE_SHARE_DELETE`. При действующем `FILE_SHARE_READ`
  она вернула `STATUS_SHARING_VIOLATION`. Дополнительная проба с корнем,
  открытым с `FILE_ADD_FILE`, важна: старый `MoveFileExW` получил 32,
  однако нативная замена под тем же корнем с разрешённым удалением прошла,
  сохранив старый дескриптор валидным. Видимое имя при этом сменило FileId.
  Это соответствует [описанию Windows](https://learn.microsoft.com/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information);
  такой дескриптор не доказывает сохранение проверенной привязки имени.
  Нельзя ослаблять блокировку ради замены. Первую версию наблюдателя
  остановил конфликт прав его повторного открытия; в r2 изменён только
  режим совместного доступа повторного чтения наблюдателя.

Обе идеи остаются вне продукта. Повторная успешная установка атрибута или
удачный запуск после неё не заменяют проверки сохранности. Для отказов на

## Подтверждённое изменение метаданных уже readonly-файла на NTFS

В Windows на искусственном файле воспроизведено состояние «readonly
виден после отдельной попытки, подтверждённого flush нет». Дескриптор
`GENERIC_READ | FILE_WRITE_ATTRIBUTES` открыт с `FILE_FLAG_WRITE_THROUGH`;
`FileModeInformation=34` подтверждает наличие бита `FILE_WRITE_THROUGH`.
Повторное присвоение тех же атрибутов не изменило `ChangeTime`. Реальное
снятие и возврат только вспомогательного атрибута `ARCHIVE` изменили
`ChangeTime` на обеих операциях. `READONLY` сохранялся на каждой границе;
явный `FlushFileBuffers` на дескрипторе с правом изменения только атрибутов
по-прежнему вернул 5. Байты и идентификатор файла совпали, замена через
`MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)` вернула 5. Положительный
контроль той же замены изменяемого файла прошёл.

В отдельной проверке четыре процесса Windows последовательно оставили
`READONLY` без `ARCHIVE`, проверили отказ замены, вернули `ARCHIVE` и
независимо перечитали итог. Все четыре подтвердили идентичность файла;
байты цели и отдельного источника замены оставались прежними. Windows
не перезагружалась, кэш и физический носитель не проверялись. Это
подтверждает повторный старт процесса после промежуточного состояния,
без утверждения о сохранности после потери питания. Путь GRAF, рабочий
профиль и установленные пакеты не использовались; оба временных каталога
Windows удалены.

[Документация Microsoft по CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew#caching-behavior)
связывает write-through с реально изменёнными метаданными NTFS. Для
прикладного протокола нужен независимый тест носителя, где исходный
baseline устойчив, незаписанное изменение теряется в отрицательном
контроле, явный flush даёт положительный контроль, а обе ступени
кандидата проверяются по отдельности. Проверить отказ до подтверждения,
сохранность FileId/байтов/обоих маркеров и повторный запуск без снятия
readonly. Остановка приложения в работающей Windows и обычная
перезагрузка не заменяют этот тест. Наличие свойства у искусственного
файла не разрешает изменение рабочего профиля и не закрывает T117.

### T117: может ли запрет удаления защитить тот же файл — 2026-11-07

на чтение токена тоже показал `TokenElevation=1`. Это не объясняет
