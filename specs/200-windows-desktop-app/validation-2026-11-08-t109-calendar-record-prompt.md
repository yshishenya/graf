кабинета с искусственными данными. В Chromium 153.0.8010.12 и WebKit

нативной оболочки установленного пакета.

## Подтверждённое расхождение

1. В обоих движках при подключении скрипта из `WebView2Host.cpp` общий
   шаблон показывает «Подсказки в Windows». Переключатель «Предлагать
   запись» доступен. Выключение отправляет
   `POST /desktop/settings/integrations/calendar/preferences` с
   `record_prompt_enabled=false`. Mac без маркера делает тот же POST.
   Перехваченный запрос получил искусственный ответ «Сохранено».
   Рабочая учётная запись и серверная БД в проверке не участвовали.
2. Реальный обработчик `calendar_settings_preferences` сохраняет эту
   настройку для текущего пользователя и пространства. API выдаёт
   отдельные `record_prompt_state` и `record_prompt_due_at`.
   Поэтому изменение из Windows может изменить поведение Mac с тем же
   пользователем и пространством.
3. Переносимая проверка с фактическими
   `DesktopApiClient::decodeCalendarReminders` и
   `MeetingReminderModel::candidate` использовала одно событие без
   ссылки, с длительностью один час, выключенной записью и
   минутным смещением уведомления. Выбор кандидата:

   | «Предлагать подключиться» | «Предлагать запись» | −30 с | +30 с | +61 с |
   |---|---|---|---|---|
   | выкл. | выкл. | нет | нет | нет |
   | выкл. | вкл. | нет | нет | нет |
   | вкл. | выкл. | есть | есть | нет |
   | вкл. | вкл. | есть | есть | нет |

   Декодер читает только `join_prompt_state`; действующий presenter для
   кандидата без ссылки предлагает «Начать запись». Сама карточка
   Windows в этой проверке не запускалась, захват не выполнялся.
4. В эталонном Mac уведомление F277 тоже выбирается по настройке
   подключения. Отдельно главное окно вызывает
   `DesktopCalendarReminderService.activePrompt` и показывает результат
   в панели записи. Там запись учитывает собственную настройку и
   действует во время встречи независимо от ссылки. Когда встречи
   пересекаются, можно выбрать событие или начать запись без привязки.
   Вызов записи следует за явным нажатием и использует обычный путь
   ручной записи. Речь идёт о двух разных поверхностях.

## Что принять в Windows

- Независимо проверить четыре сочетания переключателей и границы до
  начала, в момент начала и при окончании встречи. При выключенном
  подключении и включённой записи отдельная подсказка о записи
  сохраняется. Выключение записи убирает эту отдельную подсказку; не
  меняет настройку или поведение отдельного уведомления F277.
- Проверить события со ссылкой и без неё, две пересекающиеся встречи,
  выбор события и запись без привязки. Подключение по проверенной
  нативной ссылке остаётся в границах T119. Общая серверная настройка
  и общая страница продолжают использовать один контракт.
- Проверить закрытие, исчезновение просроченной подсказки, смену
  пользователя или пространства, недоступность актуального календаря,
  активную запись и повторное нажатие. Устаревшая кнопка не запускает
  запись. Проверить переход по Tab, активацию с клавиатуры и чтение
  названий вариантов. Сравнить результат с новым GRAF Dev и точным
  установленным Windows MSIX.

запроса измеряет по монотонным часам. На границе 60 с кандидатов нет.

не меняют действующие решения карточки F277. Сокращённый снимок для
повтора карточки не имеет права вернуть подсказку записи.

настроек, неопределённые или ошибочные поля, linked/unlinked, границы
начала, отложенного срока и конца, порядок при пересечении, активную
запись, истечение срока запроса, поздний ответ, восстановление после
сбоя и смену пространства. Независимое ревью исходников не выявило
блокирующих замечаний. Полная переносимая Release сборка и CTest 48/48

## T104/B1 — календарное решение в контракте Windows

Независимый проектный допуск CRW001–003, действующая T104/#7281.
Windows строит запросы существующего API для automatic, user_selected и
user_declined, отвергает неверные UUID/пары решения и события и извлекает
UUID попытки/срок из ограниченного ответа того же типа. В запросе
создания встречи поле calendar_match_attempt_id необязательно; без
него проверенные прежние тела побайтно совпадают. Обычный и защищённый
типы строк используют один контракт. Сетевой вызов ещё не подключён.

Первый прогон регрессии выявил потерю времени жизни ключей строгого
JSON-разбора; после удержания разбора до чтения ответ принят. По
независимому ревью чтение даты переведено на представление без
обычной строки; дата проверяется тем же разбором, что календарь.
Окончательное состояние проверено:

- macOS: Release, 48/48 переносимых тестов;
- Windows 11 ARM64 в Parallels: MSVC 2022 Release x64, ContractFixtures
  1/1; точные SHA-256 трёх файлов совпали с локальным деревом.
  Временная копия и сборка Windows удалены;
- существующие модели сервера: три допустимых решения, три неверные
  пары, дата ответа с дробными секундами и необязательная попытка
  создания встречи — PASS без БД. Интеграционный прогон серверного
  API остановился на подготовке фикстуры: нет настроенной отдельной
  тестовой PostgreSQL. Это не проверка живого сервера.

Срез B2: v4 очередь и состав защищённого пакета имеют строгие
проверки, поэтому добавление поля или файла внутрь них не считается

### T104/B2b — допуск записи после сохранения выбора

Рабочая копия F200, базовый SHA
`3dfeaff5a6774ab12be781547e4a300f9ce2a46c`, без нового коммита.
Первая интеграция на Windows обнаружила конфликт с защищённым
хранилищем: его владелец удерживает родительские каталоги с
`FILE_SHARE_READ`. В отдельном тестовом каталоге Win32 вернул
32 при повторном открытии для записи и 5 при попытке сброса буферов
через дескриптор чтения. Исправление сохраняет ограничения владельца:
рабочий поток подтверждает каталог журнала до открытия владельца и
после этого сбрасывает только удерживаемый каталог журнала.

В рабочем маршруте подготовки решение связывается с принятым
резервированием, аккаунтом, рабочим пространством и UUID записи.
Сбой или конфликт журнала не разрешает открыть файл записи или
запустить устройства. Stop при сохранении и отзыв аккаунта до допуска
пакетов не возобновляют попытку. Обычная запись остаётся доступной
по прежним правилам, даже если каталог журнала не удалось подтвердить.

каталоги, искусственные записи и ответы авторизации:

`RecordingIndicatorTests` — 3/3 до дополнения об отзыве аккаунта
внутри фабрики допуска. Отдельный тест журнала подтвердил повтор
неоконченной подготовки, конкурентную публикацию, холодное чтение,
конфликт, отсутствие и недоступность. SHA-256 журнала в обеих
сборочных копиях совпал:
`021ec7dc92b0afd6963a5257a41e918a7db7164990df72dddd513bff2a448b21`.

### 2026-11-09 — T104/B2c.14b: более простой кандидат без маркера MinIO

MinIO SDK 7.2.20 включает `Retry(total=5)`; urllib3 2.7.0 может
повторить PUT после ошибки чтения и ряда ответов 5xx. В локальной пробе
с искусственным таймаутом чтения (без сокетов) один вызов SDK отправил
два одинаковых PUT по одному ключу, затем вернул успех. Это
подтверждение повтора в клиенте, а не наблюдение позднего PUT в MinIO.

В исходниках MinIO `RELEASE.2025-05-24T17-08-30Z` обработка тела
начинается до блокировки ключа на публикации. Успех повторного PUT
не исключает завершение первого уже после DELETE. Для составной
записи отдельной проверки требуют публикация конечного ключа и судьба
незавершённых частей; успех Complete не подтверждает последнюю.

Поправка к предыдущему кандидату: уникальный ключ на вызов GRAF не
доказывает единственность отправки. До реализации нужно либо исключить
непрозрачные повторы записи на строгом маршруте и доказать свойства
одной отправки, либо получить явное подтверждение завершения всех
отправленных операций. Потеря ответа всё равно оставляет неопределённый
исход. Ни один очиститель не закрывает обязательство по этому ключу
по успешному повтору, HEAD 404 или DELETE. Положительный контроль —
успешная публикация без неопределённых отправок; отрицательный —
потеря ответа, скрытый повтор или его запрет, поздняя запись после
первой уборки и сохранение обязательства в обоих путях очистки.

CHK005/CHK008 остаются открытыми. Продуктовый код и чеклист не менялись.

### 2026-11-09 — B2c.14b: проверка границ повторов и позднего PUT

Локальная HTTP-проба использовала закреплённые версии MinIO SDK 7.2.20
и urllib3 2.7.0, только искусственные байты и адрес loopback.
При `PoolManager(retries=False)` и `num_parallel_uploads=1` результат:

| Ответ или отказ | Наблюдение на принимающей стороне |
| --- | --- |
| Обычный успех | Один PUT |
| Таймаут чтения, 503, 307 | По одному PUT; на адрес перенаправления запрос не ушёл |
| Составной объект из двух частей | Один Create, два разных UploadPart, один Complete |
| Таймаут чтения первого UploadPart | Один Create, один UploadPart, один Abort; Complete не вызывался |
| Искусственный S3 XML `RetryHead` на PUT | Два PUT по одному ключу и успешный ответ второго: повтор внутри SDK, независимо от настройки urllib3 |
| Тот же `RetryHead` с ограничителем отправок на одну попытку | Один PUT; второй вызов с теми же методом, путём и параметрами отклонён до сети, итоговый отказ |

Это доказательство поведения клиента, а не гарантии по реальным
незавершённым multipart-частям. Ошибка в записи или Abort не доказывают
ни исчезновение частей, ни невозможность позднего сохранения. Успех
повторной отправки SDK не является положительным доказательством.

Отдельный эксперимент с реальными PostgreSQL 17 и MinIO
`RELEASE.2025-05-24T17-08-30Z` (локальный образ
`sha256:460b46057cbcf8d01c2f7ceae9209290334b75dc1912235b10ad9bd35de056db`):
в одноразовой БД зафиксирована строка `unresolved`. Пишущая транзакция
взяла её `FOR UPDATE`. Локальный прокси принял подписанный PUT и
удержал его до передачи в MinIO. После `pg_terminate_backend` другая
транзакция получила блокировку и прочитала `unresolved`. Наблюдатель
выполнил HEAD (404), DELETE (успех) и повторный HEAD (404). Только
затем прокси пропустил PUT: MinIO вернул 200, точный объект из девяти
искусственных байтов появился, долговечная строка осталась
`unresolved`. Поздний объект удалили отдельно и подтвердили отсутствие.

Результат повторился **в двух случаях**: клиент дождался ответа 200
после потери транзакции и клиент уже получил таймаут, когда PUT
попал в MinIO. В обоих случаях прокси принял один PUT. Для опыта не
использовались продуктовые таблицы, продуктовые очистители или
задержка внутри самого MinIO. Контейнеры и их временные тома удалены.

Следствие для плана: потеря PostgreSQL-блокировки не является
свидетельством окончания внешнего I/O; так же не годится 404 или DELETE.
Нужны доказуемая граница отправки, отдельный долговечный исход записи и
отдельный допуск к принятию ключа. CHK005/CHK008 остаются открыты до
независимой проверки уточнённых требований. Продуктовый код не менялся.

| До отправки | Строгая часть и составная дорожка используют новый точный ключ с различимым форматом защищённой попытки. Существующие принятые части, на которые ссылается B2c.14a, не получают новую запись. При неизвестном COMMIT сам запрос ничего не удаляет: состоявшийся COMMIT оставляет принятого владельца с читаемым объектом, откат — запись очистки. |
| Очистка | Подтверждённый захват навсегда исключает принятие; операторский повтор не возвращает `pending`. При неизвестном исходе нет `purged`, `superseded`, `complete` или `server_purged`. Новый механизм не заявляет автоматическое подтверждение удаления там, где его невозможно доказать. |

#### Проверка двух исходов потерянного COMMIT

В отдельном PostgreSQL 17 с двумя искусственными таблицами одна
транзакция добавляла владельца ключа и удаляла его запись журнала.
Локальный прокси протокола PostgreSQL в первом прогоне дождался
`CommandComplete(COMMIT)`, но оборвал соединение до передачи ответа
клиенту. Во втором прогоне оборвал соединение, не передав сам
`COMMIT`. Клиент в обоих случаях получил одинаковый
`ConnectionDoesNotExistError`.

Холодная сверка другим подключением: после первого прогона владелец
есть, записи журнала нет; после второго владельца нет, запись журнала
сохранена. Это проверка поведения СУБД и способа воспроизвести оба
исхода; вызовы GRAF и проверка доступности объекта в этих двух прогонах
не выполнялись. Временный контейнер и его том удалены.

##### B2c.14b — пробы конкурентного завершения и потерянного Create

Использован отдельный MinIO того же образа, один пул, бакет без версий,
MinIO SDK 7.2.20, искусственные байты. Это пробы границ хранилища,
а не прохождение обоих очистителей GRAF. Действующие настройки сервера
и права API не менялись.

- Условие `If-None-Match: *` передано настоящим подписанным заголовком
  Complete, не через `metadata`. На занятом ключе получен
  `PreconditionFailed`, исходный объект сохранился.
- 48 запусков Complete одновременно с цепочкой Abort → DELETE:
  17 Complete успели успешно, 31 получили `NoSuchUpload`. После обеих
  операций в каждом запуске HEAD не находил объект, список не находил
  multipart по точному ключу, повтор Complete прежнего ID возвращал
  `NoSuchUpload`. Порядок прибытия менялся; паузу внутри MinIO не вводили.
- В дополнительной пробе передача подписанного UploadPart разделена
  пополам. MinIO вернул `100 Continue`; клиент отправил первые 4 МиБ,
  дождался Abort → DELETE на другом соединении, затем отправил остальные
  4 МиБ. Поздний запрос вернул `403 AccessDenied` (не `NoSuchUpload`);
  независимые ListParts и HEAD подтвердили соответственно
  `NoSuchUpload` и `NoSuchKey`. Тот же подписанный запрос без Abort
  успешно добавлял вторую часть. Ошибку позднего запроса саму по себе
  доказательством очистки не считать.
- Перехват скрывал от писателя реальный успешный ответ единственного
  Create. Писатель получил таймаут; на его сетевом клиенте не было
  UploadPart, Complete или повторного Create. Отдельный наблюдатель нашёл
  одну пустую попытку, отменил её по найденному ID и подтвердил
  сохранность соседней попытки. Это проверка уже состоявшегося Create;
  пустой список до запоздалого Create не доказывает его отсутствие.

Исходники [Complete и Abort в точной ревизии MinIO](https://github.com/minio/minio/blob/ecde75f9112f8410cb6cacb4b76193f1475b587e/cmd/erasure-multipart.go#L1093)
подтверждают, почему существенен заголовок: с условием Complete захватывает
блокировку ключа до проверки ID; без него блокировка берётся позже.
Пробы не доказывают уничтожение байтов на диске и не заменяют
проверку конфигурации MinIO на выпускном стенде. Контейнеры удалены.

**Предложение к обновлению плана и повторному ревью.** Сузить предыдущий
вариант: для строгих пробных ключей использовать один явно управляемый
multipart ID, включая маленькие части, чтобы исключить скрытый прямой
PUT, который Abort не может остановить. Не менять обычный маршрут.

1. Зарегистрировать точный ключ под Meeting и свежим `deletion_epoch`.
   Подтвердить COMMIT и отпустить Meeting до I/O. До Create устойчиво
   отметить, что отправка может произойти. Если Create или COMMIT ID
   неопределён, текущая операция прекращается без передачи медиа.
   Ни при каких условиях не выдавать второй ID для того же ключа.
2. Перед UploadPart заново прочитать подтверждённый ID под блокировкой
   журнала и проверить, что очиститель ключ не забирал. Писать части
   последовательно, по одному запросу на номер, с подписанным условием
   на Complete. Отключить повторы и редиректы, включая скрытый повтор
   SDK. Подтвердить итог `settled` только при успешном доказанном
   завершении. После освобождения блокировки проверить текущий допуск
   и `pending + settled`; один COMMIT принимает владельца и удаляет
   журнал. Неопределённый COMMIT не даёт права удалять, переотмечать
   объект или создавать журнал заново.
3. Очистители сначала фиксируют необратимый захват. Для известного
   ID требуется точечный Abort, проверка ID и одиночный DELETE с
   последующим HEAD. Не выдавать эти проверки за доказательство
   завершённого I/O при неизвестном результате. Для потерянного
   Create отдельный операторский путь ищет только точный ключ из
   журнала и применяет Abort по найденному ID; основной API не получает
   разрешение List по бакету. Если ID не найден и поздний Create
   возможен, сохранить `terminal_unknown`. Отдельно проверить, кто
   выполняет операторское действие и как возвращает проверяемый
   результат, без доступа пользователя к служебным ключам. Истечение
   последнего захвата должно попасть в операторскую очередь.
4. Сначала выпустить поддержку чтения и очистки нового формата без
   выдачи строгих попыток; включать писателя только после подтверждения
   версии обоих очистителей и прав хранилища. При откате выключить
   писателя, сохранить совместимый очиститель и не возвращать прежний
   очиститель, пока жив хотя бы один новый ключ или журнал. Префикс
   и новый класс журнала не заменяют это условие: старый путь полного
   удаления собирает ключи из всех незакрытых строк, даже если класс
   незнаком, затем может создать строку `object_store`.

Для ревью остаются конкретные проверки: встроить сценарии в
настоящий путь GRAF (включая оба исхода COMMIT и оба очистителя),
проверить поздний Create после пустого списка и операторский повтор,
подтвердить путь чтения обработчика и порядок выпуска/отката.
CHK005/CHK008 и T104 остаются открытыми.

**Запоздалый Create после пустого списка — воспроизведено.** Локальный
HTTP-посредник принял единственный подписанный Create, но передал его
MinIO только после того, как наблюдатель получил HEAD 404, выполнил
DELETE, снова получил HEAD 404 и пустой список по точному ключу.
MinIO затем успешно создал ID, а посредник оборвал ответ. У ID было
ноль частей; объект так и не появился. Операторский Abort найденного
ID убрал попытку. Это прямое подтверждение, что отсутствие ID в списке
до разрешения исхода Create не позволяет закрывать запись журнала,
даже когда повторной передачи данных не было.

**Потребитель нового ключа — подтверждён на границе подготовки файла.**
Функция GRAF `processing.submit._stage_artifact` через настоящий
`MinioStorage` и неизменённую политику роли обработчика загрузила
синтетический объект с форматом
`media-revisions/<revision>/attempts/<attempt>/tracks/media`.
Проверены точная длина и контрольная сумма; неверная сумма вернула
`storage_object_digest_mismatch`, без частичного выходного файла.
Контрольный суффикс после `tracks/media` дал S3 `AccessDenied`,
который GRAF штатно преобразовал в недоступность хранилища;
частичного файла также нет. Первый прогон ожидал исключение S3 напрямую;
повтор проверил фактическое преобразование ошибки. БД, полная
обработка ревизии и отправка MediaScribe этим опытом не проверялись.

##### Независимое ревью и проверка отката через настоящий GRAF

Повторное консультативное ревью Turing
(`01a1c21d-c067-7e70-b446-9da6243d02dd`) разделило три случая:

- **Потерянный Create.** Пустой список по точному ключу не разрешает
  закрыть журнал: поздний Create воспроизведён выше, а [точный List
  в закреплённом MinIO](https://github.com/minio/minio/blob/ecde75f9112f8410cb6cacb4b76193f1475b587e/cmd/erasure-multipart.go#L269-L298)
  читает один доступный диск. Без подтверждённого ID писатель не
  передаёт ни одного байта, не создаёт второй ID и сохраняет
  неопределённость. Отдельный оператор может найти и отменить ровно
  одну попытку по сохранённому месту хранения и точному ключу.
  Разрешение на список бакета не выдаётся основной роли API.
- **Неизвестный Complete для известного ID.** В закреплённом MinIO
  [Abort и Complete сериализованы по ID](https://github.com/minio/minio/blob/ecde75f9112f8410cb6cacb4b76193f1475b587e/cmd/erasure-server-pool.go#L1922-L1991),
  а [одиночный DELETE — по точному ключу](https://github.com/minio/minio/blob/ecde75f9112f8410cb6cacb4b76193f1475b587e/cmd/erasure-server-pool.go#L1121-L1137).
  Для подтверждения на уровне API требуются подтверждённый Abort,
  ListParts с `NoSuchUpload`, точный подтверждённый DELETE и HEAD 404
  при проверенном здоровом бакете без версий. Успех Abort сам по себе
  недостаточен: отсутствующий ID может дать 204, а ошибки удаления
  отдельных дисков не возвращаются клиенту. При неизвестном состоянии
  хранилища или истории версий обязательство остаётся в журнале.
  Ни один ответ очистки не даёт писателю права поставить `settled`
  или принять ключ.
- **Откат.** Сначала остановить выдачу новых попыток и дождаться
  завершения писателей либо отозвать их допуск. Незавершённые
  журналы обслуживают только совместимые очистители и операторский
  повтор. Для принятого объекта отсутствие журнала ожидаемо:
  отдельно проверить чтение, обработку и удаление по сохранённой
  ссылке при откате. Смена версии не меняет владельца ключа.

Две пробы проведены через настоящий API GRAF на изолированных
PostgreSQL и MinIO с синтетическими данными. Текущий
`deletion/service.py` совпадает с HEAD
`3dfeaff5a6774ab12be781547e4a300f9ce2a46c`.

| Устойчивая запись перед удалением | Результат прежнего очистителя |
| --- | --- |
| Принятая дорожка с вложенным ключом `media-revisions/<revision>/attempts/<attempt>/tracks/<role>` | Прочитал сохранённую ссылку и удалил точный объект. Холодная сверка: объект отсутствует, журнал `purged`, встреча `active_purge_complete`. |
| Новый класс журнала, `pending + unresolved`, в MinIO живой multipart с одной частью, конечного объекта нет | Создал вторую строку `object_store=purged` и пометил встречу `active_purge_complete`. Исходная строка осталась `pending`, а ListParts по-прежнему возвращал часть. Новый класс журнала не защищает от прежнего пути полного удаления. |

Обе проверки прошли после исправления обращения к реальному
`MinioStorage.put_stream` в оснастке. Это доказывает два конкретных
исхода старого кода, но не является приёмкой нового очистителя или
полного отката. Временные контейнеры и синтетические данные удалены.
CHK005/CHK008 не отмечены: это проверка проекта решения, а не
независимая приёмка окончательных требований или реализации.
