# T088: название приложения в общем списке сеансов

Проверка текущей ветки F200 на
`3dfeaff5a6774ab12be781547e4a300f9ce2a46c` с изменениями рабочей копии.
В Mac `DesktopCabinetConfiguration.applicationNameForUserAgent`
добавляет `GRAFDesktop/<версия>`. В текущем Windows WebView2 задан
общий `X-GRAF-Client: desktop`, без метки приложения в User-Agent.
Сервер создаёт устройство входа по ограниченной подсказке из
User-Agent, а общий кабинет читает сохранённые platform и version.

На искусственных данных вызваны реальные `client_metadata`,
`account_session_view` и `account_device_view`. Результаты:

| Вход для проверки | Подпись сеанса | Подпись устройства |
| --- | --- | --- |
| Метка GRAF macOS | GRAF для macOS | Mac |
| Стандартный User-Agent Edge на Windows | Edge на Windows | Браузер |
| Windows с меткой GRAF macOS | GRAF для macOS | Mac |
| Устройство уже сохранено с platform windows | Неизвестный вход | Устройство |
| Браузерный режим со вставленной меткой приложения | Edge на Windows | Браузер |

Все пять проверок прошли, ещё 17 существующих тестов разбора метки
и представления настроек прошли. Проверка не выполняла запросы к
базе, рабочему серверу, провайдерам входа или в установленный GRAF.
Она подтверждает расчёт подписи на данных указанного вида; заголовки
реального входа в пакете и сам экран ещё нужно проверить.

| Материал | SHA-256 |
| --- | --- |
| Текущий Windows WebView2Host.cpp | `fb1e480cc0a9065c16d36aaf66e6bf387c1b6a9d14baf066dd5a25d53277a736` |
| Серверный auth/sessions.py | `c94996ff2a4be814f43f502d7bc2f3fc925909311686d437aad32d7c9f528aab` |

Исправление требует согласования общего контракта. Копирование
метки Mac в Windows и одно лишь переименование уже сохранённой
платформы не дают нужного результата. Код приложения и сервера
не менялся; задача T088 остаётся открытой.

## Проверка заголовков в реальном WebView2

Два отдельных x64 запуска в Windows 11 ARM64 / Parallels, WebView2
`157.0.4341.42`, SDK `1.0.4129.50`. У каждого прогона два
локальных HTTP-адреса, отдельный пустой профиль и искусственный заголовок.
Проверяющий сервер записывал только метод, наличие маркера и значение
`Sec-Fetch-Dest` из фактически полученного запроса.

- На первом адресе перехватчик `Document` срабатывал и для верхнего
  GET/POST, и для вложенного GET. До отправки `Sec-Fetch-Dest` в
  перехватчике отсутствовал во всех этих случаях. На принимающей стороне
  верхний запрос содержал `document`, вложенный — `iframe`. Тестовая
  метка появилась в обоих, поэтому один фильтр `Document` недостаточен
  для выбора сеанса на стороне GRAF.
- Во втором прогоне получатель `localhost` не получил маркер при
  переходе с `127.0.0.1` через 302 GET и 307 POST без перехвата
  второго адреса, а также через 308 POST с явным удалением заголовка.
  Оба POST сохранили метод. Это наблюдение для данной версии движка и
  локального стенда, а не обещание для всех провайдеров и версий.
- Оба запуска завершились с кодом 0; их локальные сборки и профили
  удалены. Рабочий GRAF, браузерный вход, сеть провайдеров и доверие
  к сертификатам не использовались. Встроенный сервер пробы не реализует
  вход GRAF и не заменяет проверку конечного маршрута по HTTPS.

SHA-256 журналов: первый прогон
`1b5113690992512b0ffb6df2288cc926c9233bab94752ad45a21646fce291630`,
прогон 302/307/308
`a2bc2070395b567a3c770609582bf04cf497016889507d17b4f25999fd506651`.

Для проекта контракта остаётся вариант: метка отправляется только на
точный маршрут входа GRAF, а сервер использует её для подписи лишь при
полученном `Sec-Fetch-Dest: document`. Он должен игнорировать метку
при `iframe`, отсутствии или неоднозначном значении и никогда не
использовать её для разрешения входа. Назначение полей описано в
[проекте Fetch Metadata](https://www.w3.org/TR/fetch-metadata/#sec-fetch-dest-header).

### HTTPS: возврат от условного провайдера и отправка формы

На WebView2 `157.0.4341.42` два одноразовых локальных HTTPS-сервера
имитировали GRAF и провайдера на разных адресах и портах. Перехватчик
добавлял пробную метку только на точных методах и путях из проекта
контракта. На каждом сервере измерялся полученный запрос.

| Запрос | Метод | Метка | Назначение |
| --- | --- | --- | --- |
| Начало входа GRAF | GET | нет | document |
| Внешний адрес условного провайдера | GET | нет | document |
| Возврат на точный адрес GRAF | GET | Windows | document |
| Подтверждение email в основном окне | POST | Windows | document |
| Та же форма внутри фрейма | POST | Windows | iframe |
| Подтверждение регистрации GRAF | POST | Windows | document |
| Перенаправление 307 POST на второй адрес | POST | нет | document |
| Соседний маршрут с похожим именем | POST | нет | document |

В перехватчике `Sec-Fetch-Dest` отсутствовал на всех трёх проверенных
путях, включая оба контекста подтверждения email. Подтверждённая граница —
проверять назначение при получении запроса сервером.

Отрицательный контроль: временный сертификат отвергнут, HTTP до первого
сервера не дошёл. Для остального теста исключение ограничено контрольной
суммой сертификата и двумя адресами внутри тестового WebView2. Кэш
исключений очищен, оба сервера остановлены, тестовый профиль, ключ и
сборка удалены. Хранилища доверия Windows не менялись. Рабочий GRAF
`0.1.0.18` остался в том же отвечающем процессе. Проба не выполняла
настоящий вход, не обращалась к рабочему серверу или к Яндексу/VK.

### HTTPS: переход с уже помеченного запроса

На том же WebView2 `157.0.4341.42` три помеченных POST прошли
перенаправления. Новый получатель не увидел метку. В каждой цепочке
обратный GET на разрешённый маршрут получил её только после нового
явного добавления перехватчиком; на входе в перехватчик её не было.

| Ответ на POST | Следующий запрос | Метка | Метка на разрешённом возврате |
| --- | --- | --- | --- |
| 302 | GET, соседний путь того же адреса | нет | добавлена заново |
| 307 | POST, другой порт | нет | добавлена заново |
| 308 | POST, другой адрес | нет | добавлена заново |

Хранилище доверия не менялось. Это проверка передачи поля в конкретном

### Независимая проверка серверной границы

Найдены два существенных риска проекта. В `create_login_device`
явно переданные метаданные обходят вычисление с `browser_only`;
нынешний платёжный вызов их не передаёт, но новая реализация должна
сохранить браузерную подпись при любом способе вызова. Обычная
регистрация позволяет клиенту менять `platform`, `client_version`
и передавать `device_public_id` с началом `login:`. Поэтому эти
поля не могут назначать подпись приложения.

Проект контракта уточнён: отдельное серверное значение только для
отображения, приоритет браузерной оплаты, отклонение повторов обоих
заголовков и отдельное согласование серверного среза по CHK022.
Реализация, схема и рабочий сервер не менялись.

Повторное независимое ревью: **0 критических, 0 высоких,
2 средних** замечания к требованиям. Уточнены оба места: только
ASCII-цифры в версии, а при смене пространства — копирование только
проверенного серверного значения с устройства исходного сеанса
(иначе `NULL`). Добавлены отрицательные сценарии в quickstart.
Это не отметка о закрытии чеклиста и не согласование изменения схемы.

Отдельная проверка `browser_only` выполнила без изменений тела
`client_metadata` и `create_login_device` из текущего `auth/sessions.py`
(SHA-256 `c94996ff2a4be814f43f502d7bc2f3fc925909311686d437aad32d7c9f528aab`).
Вместо базы и модели использованы пустой приёмник записи и объект
с теми же полями. Из четырёх вызовов два контрольных сохранили
ожидаемые подписи Mac и браузера. В двух отрицательных случаях
явно переданные метаданные Mac/Windows обошли `browser_only=True`.
Текущий платёжный вызов передаёт только User-Agent и `browser_only`,
поэтому результат показывает пробел помощника, а не ошибочную
подпись при действующей оплате. Для будущего серверного среза это
отдельная регрессия: браузерная подпись при обоих явных вариантах.

### Граница отдельной серверной задачи

По текущему исходнику целевой владелец серверного среза — F6794
«Актуальные входы в аккаунт»: результат виден в общем списке входов.
F6795 остаётся эталоном сохранения и отзыва сеанса. T088 принимает
нативный сценарий после поставки общего контракта. Проверка путей
записи показала три разные границы:

- Новый вход: `auth/sessions.py:create_login_device` вызывают email
  и провайдеры; платёжная ветка тоже вызывает его с `browser_only`.
  Версия Windows допустима только после успешного входа на
  разрешённом маршруте и только как подпись.
- Повторное назначение рабочего пространства:
  `auth/workspace_onboarding.py:activate_workspace_session` уже
  проверяет исходное устройство и переносит только пару
  `(platform, client_version)`. Новый признак должен копироваться из
  проверенного исходного устройства, а при его отсутствии — оставаться
  `NULL`; текущий HTTP-запрос не является источником.
- Обычная регистрация устройства: `api/auth.py:register_device`
  обновляет указанную пару из данных клиента. Она не должна создавать,
  перезаписывать или переносить признак нативного входа.

Критерий общей задачи: в одном списке видны правильные подписи
для Windows, Mac и браузера; подпись Windows переживает смену
пространства, а неверные или повторные заголовки, регистрация
устройства и платёжный вход её не назначают. Миграция добавляет
необязательное поле без изменения старых строк; прежний код после
добавления поля продолжает читать и обслуживать входы. Срок и отзыв
сеанса одинаковы с подписью и без неё. Это предложение по владельцу
и проверкам; схема, статусы задач и рабочий сервер не менялись.
