# F200/T119 — ссылка Телемоста без идентификатора встречи

Локальная проверка изменений поверх `972af4762e7afc1a5a1c8d9025aec1eb6ce7127e`.
Владелец — существующая задача [T119 / #7540](https://github.com/yshishenya/graf/issues/7540).
Действующие FR-002/005/006 и §10 контракта моста: валидный HTTPS без
поддерживаемого пути нативного приложения открывается в браузере. Это
исправление существующего маршрута по эталону Mac. Правила выбора сервера,
права на запуск и форматы данных не меняются.

На синтетической ссылке `https://telemost.yandex.ru/j/` Mac выбирал браузер,
Windows — связь с приложением Телемоста. Ошибка повторялась, когда после
`/j/` шли только косые черты, в том числе закодированные, или когда после
пустого пути оставались параметры и фрагмент. Windows теперь требует
содержимое пути после префикса, отличное от косых черт. HTTPS остаётся
допустимым, поэтому используется существующая ветка открытия в браузере.
Это не проверка существования встречи у провайдера.

## Точная проверка Windows-обработчика и границы аргумента

Изолированный MSVC x64 на Windows 11 ARM64, в сеансе текущего
пользователя. Скомпилированы текущие `CalendarMeetingOpener` и
`CalendarNativeLauncher` поверх той же базы, без замены вызовов WinRT.
`QueryUriSupportAsync` для синтетической ссылки Телемоста, схем Zoom и
Teams дал `available`. Реальная отмена applicability вернула
`cancelled` после завершения запроса. Для пустого `/j/` нативный запрос
не создаётся. Обычный HTTPS по метаданным Windows назначен браузеру,
отдельный пользовательский класс Телемоста указывает на существующий
`YandexTelemost.exe`; перечисление [FindAppUriHandlersAsync](https://learn.microsoft.com/en-us/uwp/api/windows.system.launcher.findappurihandlersasync?view=winrt-26100)
вернуло ноль пакетных обработчиков синтетической HTTPS-цели.
Документация не обещает перечислять обычные Win32 приложения. Поэтому
`available` для HTTPS не доказывает передачу Телемосту.

В следующем опыте [ShellExecuteExW с SEE_MASK_CLASSKEY](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-shellexecuteinfow)
вызвал только собственный тестовый EXE. Использован уникальный
непостоянный ключ вне `Software\\Classes`, команда формы
`--conf-url="%1"`, фиктивный HTTPS-адрес. Подтверждены три результата:

- Корректно закодированная ссылка передана в одном аргументе без
  изменения параметров и фрагмента.
- Буквальная кавычка, которую текущий валидатор HTTPS и
  `Windows.Foundation.Uri.AbsoluteUri` сохранили, в опытном пути
  превратила часть адреса в отдельный аргумент. Это дефект предложенной
  прямой передачи, а не доказанный запуск произвольной команды из
  установленного GRAF: его путь не вызывался.
- В опытном запуске кодирование буквальных `"`, `\\` и пробела как
  `%22`, `%5C`, `%20` вернуло точную передачу одним аргументом;
  имеющийся `%2F` и фрагмент остались прежними.

Реальные Телемост, Zoom, Teams и браузер не запускались; тестовый EXE
не обращался к сети, микрофону и камере. Каждый временный ключ удалён;
обработчики и настройки по умолчанию не менялись. Рабочий GRAF 0.1.0.18
после проб отвечает, EXE имеет тот же SHA-256
`20a7544617b3008cc6706f94b769d0ad3e66b3e3ec146e30768b3a795bb1f17b`.

Путь с явным классом в продукт не принят. Отдельно остаются
проверка неизменности и идентичности получателя при dispatch (предыдущий
опыт A→B показал, что read-only HKEY не замораживает команду), безопасное
кодирование в точке передачи, проверка реакции реального клиента на
контрольной цели и текущие fences авторизации/документа/отмены.
Это также не доказывает «Подключиться и начать запись» и не закрывает T119.

## Кодирование HTTPS на общей границе Windows

Перед передачей Windows в части ссылки после имени узла буквальные кавычка,
обратная косая черта и пробел кодируются как `%22`, `%5C` и `%20`.
Существующие escape-последовательности, параметры и фрагмент сохраняются.
Уже нормализованная ссылка повторно принимается без изменения; предел 8192
байта проверяется и после кодирования. Политика допустимых узлов и выбор
обработчика остались прежними.

На Windows 11 ARM64 собраны и запущены три теста MSVC x64. До изменения
новые проверки нормализации и передачи через браузерную границу падали;
после изменения прошли все три теста, включая 141 общий пример адресов.
`NativeCalendarLauncherTests` использовал настоящий `Windows.Foundation.Uri`
и тестовую замену конечного вызова запуска. Подтверждена точная передача в
обоих режимах; внешнее приложение тест не запускал. Переносимый тест с
Xcode SDK на macOS также воспроизвёл падение до исправления и прошёл после
него. Независимая проверка исходников не выявила блокирующих замечаний.

### Ранний клик в кабинете Windows

Новый тест исполняет общий `calendar-series.js` вместе с нативным
обработчиком WebView2. До исправления тест упал: клик до установки моста
открыл браузерный путь при обычном User-Agent Windows. Общий скрипт теперь
распознаёт уже отрисованный признак встроенного кабинета и ждёт мост.
В Chromium и WebKit проверены клик без моста, до рукопожатия, при
недоступной команде и после готовности. До готовности нет открытия окна,
запросов `join-target` и нативных сообщений; после готовности отправляется
одно нативное сообщение. Для самостоятельного браузера проверен прежний
путь открытия вкладки. Тест прошёл на синтетической и на реально
отрисованной разметке календаря. Приёмка установленного MSIX и фактического
получателя ссылки встречи остаётся открытой.
