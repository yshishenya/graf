# Windows Feature 200 — валидация сведения с master от 2026-09-17

Документ фиксирует проверки после сведения ветки `codex/200-windows-desktop-app`
с master (коммит сведения `4b25d6cd2`). Предыдущая валидация от 2026-09-06
остаётся в `validation-2026-09-06.md` и не переписывается.

Во всех записях ниже нет реального аудио, расшифровок, токенов, cookie и
приватных путей. Использованы только синтетические кадры, имена устройств и
локальные каталоги виртуальной машины.

Полосы и артефакты пересобираются по мере правок, поэтому таблица первого прогона
ниже описывает не текущее состояние. Актуальные номера прогонов находятся в
разделах с датой 2026-09-18: там указаны и число пройденных тестов, и отпечатки
того пакета, который проверялся последним.

## T086 — порог короткой записи F6796

Реализовано в Windows полностью, по образцу macOS
`applyShortRecordingPolicy(stopReason:)`:

- `Contracts/WindowsDesktopContracts.h` — константы порога, причина остановки
  `RecordingStopReason` (`userRequested`, `meetingEnded`, `interruption`) и
  предикат `isShortRecording`.
- `Recording/V5LocalRecordingWriter.*` — манифест получает
  `"capture_status":"blocked"` и маркер `"short_recording_discarded":true`,
  добавлен предикат `keepablePackage()`.
- `Upload/DesktopUploadQueueService.*` — `discardShortRecording`,
  `isShortRecordingMarked` и `sweepDiscardedShortRecordings`.
- `Capture/WindowsCaptureSessionController.*` — финализатор получает причину
  остановки; отброшенная короткая запись завершает сессию состоянием `blocked`
  без ошибки захвата.
- `Shell/RecordingNoticePresenter.*` — пассивное окно, не забирающее фокус,
  одно уведомление за раз, само закрывается через 6 секунд.
- `AppMain.cpp` — обычная остановка даёт `userRequested`, закрытие приложения и
  сбой дают `interruption`, поэтому фрагмент сохраняется.

### Единица измерения порога

Порог выражен в канонических 10-мс кадрах (480 отсчётов), то есть ровно
3 000 кадров на 30 секунд. Первая версия константы считала порог в сырых
отсчётах (1 440 000) и отвергала бы любую запись; дефект нашла новая проверка
`ShortRecordingThresholdTests` на границе 29,99 с / 30,00 с и был исправлен до
записи evidence. Константа теперь выводится из
`kCanonicalFrameRate / kCanonicalSamplesPerFrame`, а не пишется руками.

### Что именно проверено

| Проверка | Результат |
| --- | --- |
| 2 999 кадров (29,99 с), обычная остановка | запись отброшена, манифест `blocked`, маркер на месте |
| 3 000 кадров (30,00 с), обычная остановка | запись сохранена, маркера нет |
| 100 кадров, прерывание | фрагмент сохранён |
| 100 кадров, сбой захвата | фрагмент сохранён, ошибка не превращается в отбрасывание |
| нулевая длительность | отбрасывание запрещено |
| повторный `finalize` | решение не меняется |
| удаление отброшенной записи из очереди | строка очереди и все байты удалены |
| подметание после сбоя | помеченный каталог удалён, непомеченный не тронут |
| каталог с вложенным каталогом | отказ `unsafePath`, ничего не удалено |
| путь вне корня хранения | отказ `unsafePath` |
| пассивное уведомление | одно за раз, заменяется, само истекает через 6 с |

Отдельно проверено, что решение об отбрасывании принимается до проверки
структурной полноты пакета: `normalPackage()` намеренно остаётся прежним
(«структурно целый, без сбоя захвата»), а новое решение опирается на
`keepablePackage()` и на явную проверку маркера в финализаторе.

## T092 — закрыто: упакованное приложение не доходило до точки входа

Первоначальное наблюдение: установка и регистрация проходили, но при активации
процесс жил ~54 мс и завершался с кодом 0, не дойдя до `wWinMain`. Матрица
экспериментов на одном и том же стенде:

| Эксперимент | Наблюдение |
| --- | --- |
| Распакованный `out\x64\Release\GrafWindowsApp.exe` | запускается, `MainWindowTitle = "GRAF"`, живёт дольше 12 с (pid 12852) |
| Журнал `Microsoft-Windows-AppModel-Runtime/Admin` | `Created Desktop AppX container`, затем `Created process 7520 ... [LaunchProcess]`, контейнер уничтожен через 54 мс |
| `IApplicationActivationManager::ActivateApplication` | `HRESULT` = 0, PID выдан; ожидание процесса заканчивается, `GetExitCodeProcess` = 0 |
| Точка входа с различающимися кодами выхода (61/91/92/93) и записью трассы | код выхода 0, файл трассы не создан ни в одном из четырёх мест — `wWinMain` не вызывается |
| Тот же установленный exe, скопированный из `Program Files\WindowsApps` в обычный каталог и запущенный без идентичности пакета | доходит до `wWinMain` и возвращает 91 (единственный экземпляр уже держит мьютекс) |
| Стороннее x64-приложение из пакета на том же стенде (`Microsoft.MSIXPackagingTool`) | запускается и живёт дольше 15 с |

Вывод из матрицы: двоичный файл исправен, под идентичностью пакета процесс
снимается раньше точки входа C++, отчётов WER и ошибок AppX нет.

### Причина

`RecApp/GrafWindowsApp.vcxproj` задавал `<WindowsPackageType>None</WindowsPackageType>`,
то есть приложение собиралось как **распакованное** для Windows App SDK. В таком
режиме в образ вкомпоновывается загрузчик рантайма: `dumpbin /dependents`
показывал импорт `Microsoft.WindowsAppRuntime.Bootstrap.dll`, а в объектных файлах
лежал `MddBootstrapAutoInitializer.obj`. Загрузчик запускается из статического
инициализатора, то есть **до** `wWinMain`, и внутри пакета он не может разрешить
рантайм: процесс завершается раньше точки входа. Именно это и наблюдалось — код 0,
отсутствие трассы, 54 мс жизни.

Проверено на том же коде: тот же exe, запущенный вне пакета, до точки входа
доходит, потому что там загрузчик работает штатно. Одинаковый двоичный файл в
двух режимах даёт разное поведение — это и было решающей уликой.

### Исправление

- `RecApp/GrafWindowsApp.vcxproj`: `WindowsPackageType` берётся из свойства
  `GrafWindowsPackageType`, если оно задано, иначе остаётся `None`. Отдельный
  `AppxManifest` подключается только для режима `MSIX`, потому что этого требует
  `_ValidateWindowsPackageType` из `Microsoft.Windows.SDK.BuildTools.MSIX`.
- `Installer/GrafWindows.Package.wapproj`: ссылка на проект приложения передаёт
  `AdditionalProperties=GrafWindowsPackageType=MSIX`.

Так одна проектная единица даёт две полосы: распакованная сборка для проверок
(`None`, с загрузчиком) и полезная нагрузка пакета (`MSIX`, без загрузчика).

| Проверка | Результат |
| --- | --- |
| `dumpbin /dependents` для собранной полезной нагрузки пакета | импорта `Microsoft.WindowsAppRuntime.Bootstrap.dll` нет |
| Установка | `INSTALL_OK`, `STATUS: Ok` |
| Запуск из установленного пакета | процесс создан, окно `GRAF` живо все 20 с наблюдения, процесс не завершается |

Дополнительно проверено, что из пакета приложение доходит не только до окна, но и
до рабочей инициализации: процесс запущен из

- Пакет: `GrafWindows.Package_0.1.0.0_x64.msix`, 1 616 021 байт, SHA-256

- Полезная нагрузка пакета `GrafWindowsApp.exe`, 1 579 008 байт, SHA-256
  `D3E17E08FC896183358B2A00F447F28B9BD355EABAAC773033F739BEE940D65E`.
- Распакованная сборка `out\x64\Release\GrafWindowsApp.exe`, 1 576 960 байт,

Две сборки законно различаются: вариант пакета не содержит загрузчика. Совпадение

ожидается; вместо него проверяется отсутствие импорта загрузчика.

Известный остаток: в полезную нагрузку пакета попадает неиспользуемая
`Microsoft.WindowsAppRuntime.Bootstrap.dll` (394 040 байт). Она берётся из каталога
вывода приложения: свойства Windows App SDK объявляют её копирование в
`build\native\WindowsAppSDK-Nuget-Native.C.props` при условии
`AppxPackage != true`. Включение `AppxPackage=true` для режима `MSIX` проверено
(`msbuild -getProperty:AppxPackage`: в режиме `MSIX` значение `true`, по умолчанию
`false`), но копирование оно не прекращает, поэтому изменение отменено как
недоказанное. На работу это не влияет: полезная нагрузка файл не импортирует
(`dumpbin /dependents`), приложение из пакета запускается. Уборка требует
отдельного разбора условий копирования и не входит в закрытие T070.

## T083 — исправление R4: классы конфликтов вместо слепого повтора

Расхождение: любой конфликт состояния синхронизации возвращался как отказ
сервера, а очередь превращала его в автоматический повтор — восемь попыток по
расписанию. Сервер при этом прямо сообщает в проекции `custody`, что ещё может
дать автоматическая попытка, а macOS переводит такие элементы в ручной режим.

Правка: Windows читает `custody.retry_class` и действует по нему.

| Класс от сервера | Состояние строки очереди | Смысл |
| --- | --- | --- |
| `paused_until_user_action` | `needsAuth` | нужен вход; восстановление входа возвращает строку в работу |
| `paused_until_admin_action` | `blocked` | автоматические попытки остановлены, нужен администратор |
| `not_retryable` | `blocked` | автоматические попытки остановлены, нужно исправление на компьютере |
| `terminal` | `quarantined` | отправить уже нельзя |
| пусто или `automatic` | `retry` | прежнее поведение: попытка по расписанию |

`blocked` — новое состояние очереди: оно не выбирается автоматическим облётом,
но его можно перевести в работу явным действием владельца («Отправить»), как это
делает macOS через ручной режим. Номер состояния в реестре — шестой, прежние
значения не сдвинулись; диапазон при чтении расширен, поэтому старые реестры
читаются без изменений.

| Проверка | Результат |
| --- | --- |

### T083 R6 — время и заголовок записи (2026-09-18)

Расхождение R6: тело `POST /api/v1/meetings` содержало пять полей, а macOS
отправляет одиннадцать. Windows не отправлял `title`, `title_source`,

сервер ставил встрече общее имя и время загрузки, а не время записи. Причина
была не в транспорте: время начала и окончания записи не сохранялось нигде —
писатель пакета знал только длительность, а отметки захвата велись по
монотонным часам и в пакет не попадали.

Правка: время записи сохраняется в пакете и отправляется серверу.

| Место | Что сделано |
| --- | --- |
| `V5LocalRecordingWriter` | момент первого принятого кадра становится началом записи, финализация закрывает конец; смещение часового пояса берётся на момент начала, а не «сейчас» |
| Манифест пакета | добавлены `started_at_ms`, `stopped_at_ms`, `display_timezone_offset_minutes` |
| Читатель пакета | поля необязательные: пакет прежней сборки читается и просто не сообщает время. Невозможная пара (конец раньше начала) или смещение вне ±14 часов отбрасываются |
| `DesktopApiClient` | заголовок `Meeting - ГГГГ-ММ-ДД ЧЧ:ММ` по местному времени начала, источник `generic`; отдельно `formatUtcInstant` даёт `started_at`/`ended_at` в виде `ГГГГ-ММ-ДДTЧЧ:ММ:ССZ` |

`DesktopUploadClient.swift:358` кодирует даты как ISO-8601, а необязательные
поля Codable при `nil` не попадают в тело, поэтому отсутствие поля — то же
поведение, что у macOS. Сервер принимает ровно эти поля (`api/schemas.py:804`,
`extra="forbid"`), источник `generic` разрешён (`api/schemas.py:91`), а политика
заголовка отбрасывает только управляющие символы и текст, похожий на ссылку,
почту или токен (`domain/metadata_text.py:6`), то есть сгенерированное имя
проходит.

тело манифеста не разбирает, а только сверяет `sha256` дорожки `manifest` с
объявленным (`ingest/finalize.py:505`) и проверяет роли дорожек и их параметры
(`ingest/manifest.py`). Расхождение состава полей манифеста записано в

| --- | --- |

Снимок не является полномочием сам по себе. Он принимается, только если содержит
корректные UUID пользователя и пространства и совпадает с рабочим пространством,

проверки, когда пространство ещё неизвестно.

`setAuthSessionToken` — единственное место, где меняется токен, и он отменяет
запланированную отправку, отменяет незавершённую проверку аккаунта, увеличивает
поколение входа и очищает подтверждённый аккаунт до того, как любая отправка
сможет начаться. Если сессию отозвали на сервере, запросы получат 401/403 и
строка перейдёт в состояние «нужен вход» — отдельный опрос `/auth/me` для этого
не нужен.

### T083 R8 — ворота, область и чтение жизненного цикла удаления (2026-09-18)

Первая часть расхождения R8 из `parity-matrix.md` закрыта: у Windows-клиента

### T083 R1 — мост удаления из кабинета: разбор запроса и ворота (2026-09-18, шаг 1)

macOS принимает выбор пользователя в `EmbeddedCabinetDeletionSelection.parse` и
пропускает его дальше по странице и по составу выбора. Пока на Windows этого не
было, кабинет не мог попросить приложение удалить локальную запись — и, что
важнее, страница встречи удаляла её веб-формой, а не через приложение.

| `RecApp/Web/WebView2Host.h/.cpp` | приказ `delete_selection`, ворота `deletionSelectionFrom`, `completeDeletionSelection`, слушатель `graf:delete-selection` в скрипте моста |
| `Tests/GrafWindowsContractTests/RecordingDeletionBridgeTests.cpp` | новые: шесть наборов проверок разбора, ворот и ответа |
| `Tests/GrafWindowsContractTests/WebView2HostLifecycleTests.cpp` | ворота удаления проверены без браузера: страница, строка, чужак на странице встречи |
| `RecApp/GrafWindowsApp.vcxproj` | новый файл добавлен в проект приложения |
| `apps/windows/CMakeLists.txt` | новый тест добавлен в портируемую полосу |

Что решено и почему именно так:

- **Принимается только то, что принимает macOS.** Версия 1, действие
  `deleteSelection`, идентификатор запроса в форме UUID, две непустые в сумме
  группы, не больше 100 целей, без повторов внутри группы, встречи — только
  UUID, локальные строки — только те, которые приложение само предлагает
  удалять. Незнакомые лишние поля игнорируются: так же ведёт себя словарь в
  macOS. Идентификатор запроса уходит обратно в скрипт страницы, поэтому он
  проверяется как идентификатор, а не как строка.
- **Одна плохая цель отменяет весь выбор.** Удалить «остальное» значило бы
  удалить не то, что выбрал человек.
- **Цель локальной записи — каталог, который знает сервер.** Кабинет присылает
  идентификатор строки, которую показал; серверу нужен каталог пакета. Это
  разные значения, и подставлять одно вместо другого нельзя: сервер не нашёл бы
  запись.
- **Ворота страницы повторяют macOS.** Список встреч принимает любой выбор;
  страница встречи — только саму эту встречу или одни локальные копии; общая
  встреча (`/shared-meetings/...`) — тоже одна встреча. Прочие страницы не
  являются поверхностью удаления, даже если сообщение пришло с верным мостом.
- **Ответ приходит только на ту страницу, которая спросила.** Запрос несёт
  отметку документа, и ответ не выполняется, если документ успел смениться:
  иначе медленное удаление всплыло бы на другой странице.
- **Мост не выставляется раньше времени.** Сценарий страницы объявляет версию 1
  и обработчик `grafLocalRecording` только тогда, когда у приложения есть
  обработчик выбора. Сейчас его нет, поэтому страница по-прежнему не считает
  удаление доступным через приложение, и удаление встречи идёт прежним,
  работающим путём. Это не осторожность ради осторожности: включённый мост
  заставляет страницу встречи отказаться от веб-формы, и включить его без
  исполнителя значило бы сломать удаление, а не починить.

Найденная ошибка: ворота сначала требовали вид маршрута «одна встреча», а список
встреч на Windows — это отдельный вид. С таким воротами список отверг бы любой
выбор, то есть удаление из списка не работало бы вовсе. Ошибку поймала новая
проверка, а не сборка. Заодно решение перестало зависеть от скрытого состояния
хоста: страница передаётся в ворота явно, поэтому проверяется без браузера.

### T083 R1 — исполнитель удаления из кабинета (2026-09-18, шаг 2)

Теперь у моста есть вызывающий, поэтому ворота протокола и обратный вызов

| `Tests/GrafWindowsContractTests/DesktopDeletionProtocolTests.cpp` | чтение `meeting_id` у отмены копии и отказ на отрицательный `deletion_epoch` |
| `Tests/GrafWindowsContractTests/WebView2HostLifecycleTests.cpp` | ворота и вывод целей по тем же строкам |

Почему проход устроен в три фазы. Реестр очереди пишется только из потока
владельца окна: так устроены очередь восстановления и все прежние вызовы, и
второго писателя у файла быть не должно. Поэтому удаление разделено на «сохранить
выбор» (поток владельца), «отправить сохранённое» (рабочий поток, без доступа к
реестру) и «записать ответы» (снова поток владельца). Это то же разделение, что у
macOS даёт последовательная очередь; здесь оно выражено явно, потому что очередь
на Windows не сериализована сама.

Что решено и почему:

- **Сначала ворота, потом изменение.** Перед первой отправкой читается контекст
  уведомлений, и без объявленной поддержки (`recording_deletion_protocol_version`
  = 1) ни один запрос не уходит: старый сервер игнорирует заголовки области, а
  нечитаемая квитанция пришла бы уже после удаления. macOS отвечает на эти же
  ответы `recording_deletion_update_required`, а на контекст другого аккаунта —
  `recording_scope_changed`. Одно чтение решает судьбу всего ограниченного
  прохода: это расхождение с macOS, который читает контекст на каждый запрос.
- **Сохранено — это про реестр, а не про удаление.** `saved=true` означает, что
  запросы durable; кабинет видит это и ни в каком случае не читает молчание как
  удаление. Повторный выбор уже принятой записи снова даёт `saved=true`: запрос
  уже лежит в реестре, и говорить «не сохранилось» было бы неправдой.
- **Попытка считается тогда, когда она состоялась.** Счётчик попыток растёт при
  записи ответа, а не при планировании: иначе сбой сети сжёг бы расписание
  повторных попыток у всех запросов сразу, включая те, что не отправлялись.
- **Общий сбой останавливает проход, отказ одной цели — нет.** Продолжают проход
  только два ответа про саму цель: `403 deletion_forbidden` и `404
  meeting_not_found`. Сеть, истёкшая сессия, ограничение частоты, обновление
  сервера и нечитаемый ответ говорят одно и то же обо всех запросах аккаунта.
- **Копия без сервера удаляется локально.** Запись, о которой сервер никогда не
  слышал, не получает запроса вовсе: она удаляется на месте, и кабинету
  сообщается результат удаления, а не отправки.
- **Сервер может назвать встречу в ответе про копию.** Ответ `meeting_deletion` с
  идентификатором локальной копии подтверждает просьбу об этой копии (то же
  правило в `RecordingDeletionReceipt.matches` у macOS), и строка узнаёт встречу
  из того же ответа вместо нового запроса.

Найденные ошибки:

- **Нечитаемый `meeting_id` у отмены копии.** Разбор квитанции возвращался сразу
  после `local_recording_id`, поэтому встреча из ответа не читалась никогда, и

Что именно теперь хранится и почему:

- **Отметка времени у каждой строки и у документа.** Раньше строка не несла
  времени вовсе: строка, застывшая неделю назад, была неотличима от той, что

- **Имя запроса выводится, а не придумывается.** `operation_id` — это версия 4 по
  форме, но значение выведено из цели и аккаунта, потому что сервер обращается с
  ним как с именем запроса. Повтор после перезапуска — та же операция, и удалить
  дважды по ней нельзя. Случайное имя означало бы, что повтор после сбоя
  выглядит для сервера новым запросом.
- **Один запрос на цель и аккаунт.** Повторный запрос той же цели тем же
  аккаунтом не создаёт вторую запись, а возвращает имя существующей; та же цель
  другим аккаунтом — другой запрос, и квитанция одного никогда не подтверждает
  запрос другого.
- **Принятие только с квитанцией.** Перейти в `accepted` нельзя «просто так»:
  объявить эту фазу вызывающему запрещено, а `acceptDeletion` требует квитанцию,
  которая назвала именно эту цель, и для каждой цели — свою форму квитанции
  (`origin_cancellation` для локальной записи, `meeting_deletion` для встречи).
  Ответ про другую запись не подтверждает эту.
- **Монотонность.** Принятое удаление может стать только подтверждённым, и
  `verified` — конечное состояние. Поздний сбой или поздний отказ не возвращают
  запись в список: сервер её уже удалил. Ожидание — это задержка `5/15/30/60`
  секунд по числу попыток, а не отказ.
- **Один адрес сервера.** В записи хранится происхождение сервера, и принимается
  только `https`, либо `http` для сервера на этом же компьютере. Смена адреса не
  переносит чужой запрос на другой сервер.
- **Старые реестры читаются.** Файл `v2` по-прежнему загружается и обновляется при
  первой же записи: в очереди лежат записи, которых больше нигде нет. Отказ от
  чтения потерял бы незавершённую отправку пользователя.
- **Подделка не проходит.** Загрузчик отвергает реестр, где операция объявлена
  принятой без квитанции, а испорченный файл уходит в карантин, как и раньше.

поэтому строки `local-purge-tasks` появляются в выпуске, а не остаются
вырезанными компоновщиком.

| `RecApp/AppMain.cpp` | `startLocalPurgePass` (список и адресный запрос задачи в рабочем потоке), `prepareLocalPurgeAnswers` (удаление и подготовка ответов на потоке владельца), отправка подтверждений в рабочем потоке, `utcNowIso`; проход раз в минуту и сразу после принятого удаления |
| `Tests/GrafWindowsCoreTests/DesktopDeletionLedgerTests.cpp` | семь наборов: сопоставление по встрече, удаление только завершённых копий, подтверждение доказанного удаления, честный отказ по непроверяемому типу, запрос задачи по подтверждённому удалению, отказ на нечитаемом реестре, повторная попытка после неудачи, сохранение доказательства между запусками |

Что решено и почему:

- **Задачу связывает только встреча от сервера.** Строка сопоставляется по
  `meeting_id`, который вернул сам сервер. Задача без встречи не совпадает ни с
  чем, а не со всем: иначе очистка одной встречи уносила бы чужие записи.
- **Удаляется только то, что сервер уже считает своим.** Пригодна к удалению
  строка в состоянии `uploaded`. Копия, отправка которой не завершилась,
  остаётся: это уничтожило бы незавершённую отправку, а не очистило буфер.
- **То же безопасное удаление, другое доказательство.** Файлы уходят тем же
  путём, что и подтверждённое пользователем удаление (проверка каталога внутри
  хранилища, отсутствие второго владельца пути, запись намерения в реестр до
  операции ОС, перенос в Корзину). Отличается только доказательство:
  `serverRequestedPurge` не может прийти из меню, потому что пользователь эту
  копию не подтверждал.
- **Непроверяемый тип не трогает файлы.** `purge_local_exports` и
  `confirm_local_expiry` — не работа этого клиента, и он отвечает
  `failed` / `local_purge_unverified` вместо выдуманного успеха. Это то же
  правило, по которому в порт не попали фиктивные подтверждения удаления.
- **Доказательство записывается до ответа.** Доказанное удаление попадает в
  реестр (`purge_acknowledgements`) раньше, чем уходит подтверждение: потерянный
  ответ не превращает выполненную очистку в неудачу, когда сервер спросит снова.
  Записываются только доказанные удаления: неудача не замораживается, иначе
  локальную копию нельзя было бы удалить после того, как отправка завершится.
  Список ограничен тем же пределом, что и список задач сервера (200).
- **Достижимые состояния проверки.** Windows различает `deleted` (все копии
  встречи удалены), `failed` (часть копий осталась) и `unverified` (тип задачи
  или отсутствие строк). `tombstoned` и `cryptographicallyUnrecoverable` в порт
  не переносятся: строку Windows удаляет вместе с копией, а шифрования локальных
  буферов, недоступность которого надо доказывать, в объёме Feature 200 нет.
- **Расхождение с macOS.** macOS отвечает от терминальной строки, которую

### T083 R5 — состояние удаления в кабинете (2026-09-18, часть 2)

Вторая часть R5: кабинет видит не только строки, но и удаления в работе. До этого

сохранённого запроса и уведомление о скрытых записях не появлялись никогда —
полей просто не приходило.

| `RecApp/Web/WebView2Host.h/.cpp` | `setLocalRecordings(rows, operations, recoveryRequired)`; строка получила `localDeletionPending` и `deletionIsLocalOnly`; в сообщении появились `operations` и `recoveryRequired`, а в сценарии — вызов `update(rows, operations, recoveryRequired)`, как в macOS |
| `RecApp/Upload/DesktopUploadQueueService.h/.cpp` | публичные `localDeletionPending(item)` и `pendingLocalDeletionIds()` |
| `RecApp/AppMain.cpp` | заполнение признаков строки, сборка списка удалений, `finishPendingLocalDeletions` в обычном проходе восстановления, фаза удаления в ключе отображения |

Что решено и почему:

- **Страница получает тот же вызов, что и в macOS.** `update(rows, operations,
  recoveryRequired)` — это контракт кабинета (`cabinet.js:447`), и без двух
  последних аргументов он молчит о сохранённом запросе. Приложение уже хранило
  фазы удаления в реестре; теперь их видно и пользователю.
- **Фазы не переводятся.** Имена `queued`, `sending`, `resolving`, `accepted`,
  `verified`, `rejected` совпадают у реестра и у страницы. Одно написание означает,
  что приложение и страница не могут разойтись в том, в каком состоянии удаление.
- **Причины ожидания переводятся, потому что это словарь страницы**: `rate_limit`
  → `rateLimit`, `server_update` → `serverUpdate`. Незнакомая причина передаётся
  как есть: страница тогда печатает фазу, а не состояние, которого ей не называли.
- **Цель — в форме перечисления, которую присылает macOS** (`target.meeting._0`,
  `target.ownOrigin._0`): страница читает именно её. Ссылка на отчёт об удалении
  появляется только тогда, когда встречу назвала квитанция; у локальной копии
  квитанция называет копию, а не встречу, поэтому ссылки не будет.
- **Обещание в диалоге равно поведению.** `deletionIsLocalOnly` выводится из
  `hasServerIdentity` — того же правила, по которому исполнитель решает, нужен ли
  серверный запрос. Поэтому «Эти записи ещё не отправлялись на сервер» — не
  отдельная догадка страницы, а то же знание приложения.
- **`localDeletionPending` без доведения до конца был бы неправдой.** Страница
  печатает для такой строки «очистка файлов ещё не завершена. Повторим попытку
  автоматически», а до этого приложение ничего не повторяло: отметка
  `local_delete_pending` оставалась навсегда, если процесс умирал между записью
  намерения и операцией «Корзины». Теперь такой проход есть, и записанное
  намерение — это и есть подтверждение пользователя.
- **`recoveryRequired` всегда `false` и это правда.** macOS скрывает строки, доступ
  к жизненному циклу которых недоступен, и объясняет это уведомлением. Windows
  показывает строку с её причиной («Нужен исходный аккаунт записи»), то есть ничего
  не скрыто, и уведомление о скрытых записях было бы ложью.

Найденная ошибка проверки (не сборки): строки сценария моста и ключи JSON лежат в
сборке в кодировке UTF-16, потому что содержат русский текст. Поиск по ASCII-виду
исполняемого файла показывал `localDeletionPending`, `deletionIsLocalOnly`,
`recoveryRequired` и даже `local_recordings` как отсутствующие. Скрипт проверки в
ВМ теперь ищет обе кодировки и печатает, где строка найдена.

### T083 R11 — тема кабинета решает оформление окон (2026-09-18)

Кабинет хранит тему как пользовательскую настройку: сервер отдаёт её в
`<html data-theme="dark|light">` (`templates/cabinet/base.html:2`), а страница
настроек меняет её на месте (`settings-autosave.js:174`). macOS узнаёт её через
обработчик `grafAppAppearance` и выставляет `NSApplication.appearance`. Windows до
сих пор держал `ElementTheme::Dark` в четырёх местах, поэтому выбор «светлая» в

### T083 R2 — страницы настроек отвечают кабинету (2026-09-18)

Страницы настроек кабинета разговаривают с приложением так, как это устроено в
macOS: `window.webkit.messageHandlers.<handler>.postMessage(...)` возвращает
обещание, а ответ приходит телом `{version: 1, ...}` (`cabinet.js`,
`nativeSettingsQueue`). В WebView2 такого моста нет, поэтому на Windows обе
страницы молчали: «Настройки автозаписи» показывали «Не удалось загрузить
настройки этого Mac» через пятнадцать секунд ожидания, а страница уведомлений —
то же самое.

| Файл | Изменение |
| --- | --- |
| `RecApp/Web/NativeSettingsBridge.h/.cpp` | маршруты страниц, словарь действий и правил, тело ответа, тело отказа и сценарий-переходник, который выставляет `window.webkit.messageHandlers` |
| `RecApp/Web/WebView2Host.h/.cpp` | `setNativeSettingsHandler`, рукопожатие `connect(nonce)` при загрузке страницы настроек, `refreshNativeSettings`, разбор запроса и отправка ответа `native_reply` |
| `RecApp/AppMain.cpp` | ответ по правилам автозаписи из того же хранилища, которым пользуется нативное окно настроек; страница уведомлений получает правду о платформе |
| `RecApp/MeetingDetection/AutomaticRecordingPolicy.h/.cpp` | `automaticRecordingPreferenceToken` и обратный разбор: одно слово и в реестре, и на странице |
| `Tests/GrafWindowsContractTests/NativeSettingsBridgeTests.cpp` | маршруты, словарь, тело ответа, экранирование, отказ, состав сценария |

Что решено и почему:

- **Одно хранилище, две поверхности.** Правило автозаписи читается и пишется
  через `AutomaticRecordingPolicy` — то же хранилище, что и у нативного окна
  настроек. Поэтому нативная страница и страница кабинета не могут разойтись в
  том, какое правило у приложения; после сохранения из кабинета нативная
  страница обновляется, а после изменения в нативном окне кабинет получает
  `refresh()`.
- **Словарь правил общий.** В реестре и в списке страницы одни и те же три слова
  (`always`, `ask`, `never`); страница отказывается от всего остального, поэтому
  перевод «на лету» был бы вторым словарём и вторым источником ошибок.
- **Страница отвечает только за свой маршрут.** Запрос принимается, только если
  документ на экране — это `/desktop/settings/recording` или
  `/desktop/settings/notifications` без запроса и фрагмента, и обработчик
  совпадает со страницей: страница записи не может ответить за страницу
  уведомлений. Значение рукопожатия меняется на каждый документ, и запрос со
  старым значением не получает ответа.
- **Мост ставится только там, где есть кому ответить.** Без обработчика сценарий
  не устанавливается вовсе: страница, которая нашла обработчик, ждёт ответа
  пятнадцать секунд и сообщает об ошибке, которую устроило приложение.
- **Уведомления — правда, а не заглушка.** В Windows у приложения нет местных
  напоминаний о встречах: обратная связь о записи живёт в самом приложении и не
  зависит от разрешений системы (`Shell/RecordingNoticePresenter.h`). Поэтому
  страница получает `canEdit: false`, нулевые настройки и причину, и показывает
  свои элементы выключенными вместо обещания напоминаний, которых не будет.
  Изменение отклоняется с причиной, а не сохраняется в никуда.
- **Строка про «этот Mac» на этих страницах больше не показывается.** Она
  оставалась в тексте ошибки, который печатался ровно потому, что моста не было.

Что осталось и почему:

- `/desktop/settings/meeting-detection` по-прежнему открывает нативное окно
  определения встреч, а не страницу кабинета. Сервер такой страницы не отдаёт:
  в `cabinet/web_routes/settings.py` есть `/desktop/settings/recording`,
  `/notifications`, `/summaries`, `/workspace`, `/account`, но не
  `meeting-detection`. macOS разрешает этот адрес как документ кабинета и получил
  бы ответ сервера об отсутствующей странице; у Windows для определения встреч
  есть работающая нативная страница, и показывать вместо неё пустующую было бы
  шагом назад. Расхождение остаётся осознанным и записано в матрицу паритета.
- Страница уведомлений остаётся только для чтения, пока в Windows не появятся
  местные напоминания о встречах; это отдельная работа, а не паритет оформления.

Проверки:

### T083 R10 — срок сессии, названный сервером (2026-09-18)

Сервер продлевает сессию, пока отвечает на запрос с заголовком `X-Auth-Session`,
и называет новый срок в `X-GRAF-Auth-Expires-At`. macOS читает этот заголовок и
переписывает им срок своей сессионной cookie (`DesktopCabinetSessionBridge.swift`
`renewalExpiry`/`renewalCookies`). Windows заголовок не читал: сессия в кабинете
истекала по прежнему сроку, хотя вызовы приложения продолжали работать.

| Файл | Изменение |
| --- | --- |
| `RecApp/Upload/DesktopHttpTransport.h/.cpp` | чтение заголовка тем же правилом, что в macOS (только цифры), `DesktopTransportResult::authExpiresAt`, `DesktopDeletionResponse::authExpiresAt` |
| `RecApp/Upload/DesktopUploadRecoveryScheduler.h/.cpp` | `setSessionExpiryHandler`; срок передаётся на поток владельца из `apply`, рядом с паузой `Retry-After` |
| `RecApp/Web/WebView2Host.h/.cpp` | `extendAuthCookieExpiry` и правило `authCookieShouldBeExtended`; срок ставится на cookie `__Host-twobrain_rec_owner_session` |
| `RecApp/AppMain.cpp` | срок доходит от полёта до кабинета |
| `Tests/GrafWindowsContractTests/WebView2HostLifecycleTests.cpp` | три отказа: чужое значение cookie, пустой токен, срок в прошлом |

Что решено и почему:

- **Заголовок читается как в macOS.** Только цифры и не длиннее девятнадцати
  знаков; украшенное или локализованное значение сроком не считается. Значение
  разбирается в секунды эпохи без плавающей точки, поэтому срок не «плывёт».
- **Срок ставится на ту же cookie, которой пользуется кабинет.**
  `__Host-twobrain_rec_owner_session` — та cookie, из которой приложение берёт
  токен сессии; переписывание её срока и есть то, что делает macOS.
- **Три отказа перед переписыванием.** Нет токена — нечего продлевать; значение
  cookie уже другое — это другая сессия; срок в прошлом — он бы укоротил сессию,
  которую сервер только что продлил. Последнее важно: без этой проверки старый
  ответ мог бы откатить уже продлённую сессию назад.
- **Срок не хранится в реестре.** macOS тоже нигде его не сохраняет: он живёт в
  cookie, потому что именно cookie решает, когда кабинет попросит вход. Место в
  реестре очереди, о котором говорила матрица, оказалось не нужным.
- **Ошибка переписывания не показывается пользователю.** Не удалось поставить
  срок — сессия приложения цела, и тревожить пользователя нечем.

### T083 R9 — отпечаток сервера в строке реестра (2026-09-18)

macOS хранит в строке очереди отпечаток того, что сказал сервер
(`ServerTruthFingerprint`): идентификатор принятой медиаревизии, идентификатор
сессии загрузки, состояние встречи и обработки. Windows запоминал только
идентификатор встречи, поэтому после перезапуска приложение не могло сказать,
что сервер говорил о строке, не спросив его заново.

| Файл | Изменение |
| --- | --- |
| `RecApp/Upload/DesktopUploadQueueService.h/.cpp` | в строке реестра появились `media_revision_id`, `upload_session_id`, `server_status`, `processing_status`, `media_revision_status`; чтение проверяет каждое значение, запись добавляет их в строку, а `reconcile` принимает отпечаток целиком |
| `RecApp/Upload/DesktopHttpTransport.cpp` | разбор `sync-state` читает `media_revision.media_revision_id` и `.status`, `upload_session.session_id`, `meeting.status` и `processing.status` |
| `Tests/GrafWindowsCoreTests/DesktopUploadQueueV2Tests.cpp` | круг «запись → перезапуск → чтение» и отказ записывать непригодное значение |

Что решено и почему:

- **Поля объявлены последними.** Существующие позиционные инициализаторы в
  тестах и фикстурах сохраняют смысл, а старые реестры читаются как прежде:
  отсутствующее поле — это обычное состояние строки, которую сервер ещё не
  принял, а не ошибка.
- **Отпечаток принимается как есть, но каждое значение проверяется.**
  Идентификаторы — только буквы, цифры, дефис и подчёркивание; состояния —
  только строчные имена. Негодное значение не попадает в файл, а прежнее
  значение строки остаётся: реестр не должен портиться из-за одного ответа.
- **Снимок заменяется новым, а не дополняется.** Он описывает то, что сервер
  держит сейчас; устаревшая копия заставила бы реестр ссылаться на ревизию или
  сессию, которых у сервера уже нет.
- **Конфликт и срок хранения в строку не переносятся.** macOS держит в строке
  `syncConflictState` из семнадцати значений и `RetentionDecision`. Windows ведёт

| Обе палитры живьём | в одном запуске при светлой системе окно сначала нарисовалось светлыми значениями набора (до чтения темы страницы), а после рукопожатия перешло на тёмные — значит, применяются обе половины набора, а не только тёмная |
| Снимки | вне репозитория (`~/Documents/graf-vm-drop/`): содержимое кабинета в репозиторий не сохраняется |

Что решено и почему:

- **У оболочки теперь две палитры, а не одна.** Прежнее решение «собственные цвета
  остаются тёмными» было основано на неверном чтении macOS: у macOS
  `DesktopMeetingShellChrome.shellBackgroundColor` — динамический цвет
  `DesktopDesignTokens.background`, и светлая половина у токенов есть. Кабинет
  тоже отдаёт светлую тему (`html[data-theme="light"]`), поэтому окно обязано её
  поддерживать, иначе оно остаётся тёмным на светлой странице.
- **Светлая тема кабинета по умолчанию не включается.** Пока в кабинете выбрана
  тёмная тема (а по умолчанию там тёмная), окно остаётся тёмным — ровно как
  кабинет. Светлые значения применяются, когда кабинет объявит светлую тему или
  когда тема «системная» и система светлая.
- **Тема читается у страницы, а не ждётся объявлением.** Объявление через мост
  требует одноразового значения, которое выдаётся при рукопожатии, поэтому первое
  объявление всегда опаздывает. Чтение `data-theme` после рукопожатия даёт верную
  тему на первой же отрисовке, а объявление остаётся для смены темы на месте.
- **`prefers-color-scheme` внутри кабинета совпадает с окном.** Тема «системная»
  в кабинете решается медиазапросом внутри WebView2, а он по умолчанию не следует
  настройке окна; теперь окно задаёт её явно, и обе половины согласованы.
- **Высокая контрастность Windows остаётся за системой.** При ней кнопки не
  получают собственный рецепт: системные краски делают неактивную кнопку
  отличимой от активной, а свои — нет.

### Найденная ошибка: приложение не видело запрет доступа к микрофону

Первая живая проверка выглядела так: запись начиналась, появлялся системный
запрос «Let GRAF access your microphone?», после ответа «No» запись падала с

упакованным программам и остаётся «Allow» независимо от ответа в системном
запросе. У упакованного приложения согласие лежит под именем семейства пакетов

первым.

| Что | Как |
| --- | --- |
| Порядок ключей согласия | `RecApp/Shell/MicrophoneConsentKey.{h,cpp}`, проверка семейства пакетов, затем `NonPackaged`, затем общий ключ |
| Проверка в приложении | `currentPackageFamilyName()` через `GetCurrentPackageFamilyName`, перебор суффиксов в порядке из модуля |
| Потерянный код отказа | `CaptureWorkerError::accessDenied` для `E_ACCESSDENIED` в `Activate`, `Initialize`, `Start` |
| Причина отказа по источнику | `RecApp/Capture/CaptureReasonMapping.{h,cpp}`: отказ в доступе к микрофону — это `microphonePermissionDenied`, а не «устройство отключилось» |

| Срок запуска источника | Истёк срок — причина называет источник, который не поднялся (`renderEndpointUnavailable` или `microphoneEndpointUnavailable`) |

## Раунд 27 — отказ любого источника ограничивает запись (паритет с macOS)

До этого раунда отказ микрофона ограничивал запись, а отказ системного звука
обрывал её. В macOS `CaptureSessionController.markDegraded(source:recoveryAction:)`
помечает сессию ограниченной для любого источника, а
`CaptureControlViewCore.degradedSourceRecovery` называет человеку тот, который
отказал: «Микрофон», «Системный звук», «Тракт удаления эха». На Windows сделано
то же.

Правило, по которому решается судьба записи:

| Положение | Что решает | Итог |
| --- | --- | --- |
| Источник отказал на ходу, второй пишет | второй источник дал звук | запись продолжается ограниченной, причина называет отказавший источник |
| Источник отказал, второй ещё поднимается | второй не отказал | запись продолжается: второму дают договорить |
| Истёк срок запуска | живёт только тот, кто успел дать звук | если звук дал хотя бы один — ограниченная запись, если ни один — отказ |
| Отказали оба | — | запись обрывается: писать нечем |

Причина ограничения больше не сводится к «источник пропал»: `endpointInvalidated`
и истёкший срок запуска превращаются в `microphoneEndpointUnavailable` или
`renderEndpointUnavailable`, и человек читает «Системный звук недоступен.
Проверьте устройство воспроизведения в параметрах Windows» вместо общей фразы.
Полоса записи в этом случае показывает «Только микрофон», а панель — «Системный
звук недоступен: запись продолжается с микрофоном».

Проверки: `CaptureFaultStateTests.cpp` — новый сценарий «отказ системного звука
на ходу» (микрофон продолжает писать, запись сохраняется с
`degradedReason=renderEndpointUnavailable` и `reason=none`), обновлённый сценарий
истёкшего срока запуска (микрофон жив — ограниченная запись вместо обрыва) и
`RecordingOutcomeTextTests.cpp` — текст и признак `isRenderOnlyReason`.
Портируемая полоса 30/30, полоса приложения и полоса пакета пройдены, пакет
`sha256=34F9C6D9A68D195883E9A91E0D8520F8E61F4C3C7F219D9ECA3F40CE05FFA2C1`
установлен.

Живая проверка в ВМ: запись по-прежнему не начинается, и это правильный итог —
в ВМ нет рабочего микрофона, а системный звук на молчащем устройстве не даёт
пакетов, то есть оба источника нерабочие. Панель при этом честно показывает
«Разрешите доступ к микрофону в настройках Windows»: переустановка пакета с
полным удалением сбрасывает согласие на микрофон, и приложение это замечает.
Ограниченная запись с живым источником проверена модульными сценариями; живое
подтверждение требует физического компьютера (T071).

## Раунд 32 — прогресс отправки в строке локальной записи (T083, остаток R5)

Последним расхождением R5 оставался `progressPercent`: macOS считает его из
принятых сервером байт и веса дорожек локального пакета, а Windows это поле не
отправлял, поэтому кабинет не мог показать «Отправляется · N %».

Сделано то же самое:

- `DesktopUploadQueueService::uploadProgressPercent` — чистая функция: сумма
  принятых байт по дорожкам против суммы веса дорожек, ограничение сверху сотней
  процентов, отсутствие значения при неизвестном весе;
- `packageTrackBytes` читает вес дорожек локального пакета (`manifest`, `media`,
  `playback`) тем же разбором, которым пользуется отправка;
- строка локальной записи несёт `progressPercent` только когда он измерим:
  кабинет ждёт число или отсутствие поля, а ноль процентов выглядел бы как
  «ничего не отправлено»;
- проверка в `DesktopUploadQueueV2Tests.cpp`: половина, полный, превышенный и
  неизвестный прогресс.

Портируемая полоса 30/30, полоса приложения, полоса пакета; пакет
`sha256=17FBC6CFC20009C7CF09E647BF740AB1EAA9F081424D7CF4BDDD04DA43E84B59`
установлен и открывает кабинет без изменений в списке встреч.

Что остаётся в T083: живая проверка отправки и входа требует настоящего аккаунта,
поэтому строка с прогрессом проверена модульно; конфликт и срок хранения в
реестре остаются осознанным расхождением с macOS.

### Почему приглашения и не должно было быть

Определитель Windows требует, чтобы **проверенный** процесс держал одновременно
**активный поток воспроизведения и активный поток захвата**. В одиночной комнате
Телемосту нечего воспроизводить: участник один. Значит, потока воспроизведения
нет, и приложение не считается встречей — даже несмотря на подпись, версию и
активный микрофон. Это и есть обещанная защита от ложных срабатываний, и она
сработала вживую, а не только в модульном тесте.

Обратная сторона того же правила: чтобы получить **положительный** случай, в
комнату должен говорить кто-то ещё — тогда у приложения появится поток
воспроизведения. В этой машине это возможно двумя путями: второе устройство в
той же комнате либо веб-клиент. Веб-клиент с микрофоном отправил бы звук из
этой комнаты на сторонний сервис, поэтому без отдельного разрешения владельца я
этого не делаю.

## Раунд 43 — найдена и исправлена мёртвая ветка моста

Живая проверка страницы уведомлений показала не то, что ожидалось, и это
оказался настоящий дефект, а не мелочь оформления.

### Что было

Страница настроек уведомлений в кабинете показывала «**Не удалось загрузить
настройки этого Мака**» и предлагала повтор. Журнал моста объяснил причину
одной строкой:

```
739140687 validation-rejected native_settings
```

Приложение **отбрасывало** запрос страницы, а не отвечало на него. Причина
нашлась в списке разрешённых команд моста (`WebViewBridge::isAllowedWebCommand`):
в нём были только `request_app_quit`, `local_recording` и `app_appearance`, а
оболочка кабинета отправляет ещё две — `native_settings` (страницы настроек) и
`delete_selection` (удаление записи из кабинета). Обе команды доходили до
проверки и отбрасывались.

Последствия были не косметические:

- страницы настроек кабинета (запись и уведомления) **не работали вовсе** — вместо
  честного ответа показывалась ложная ошибка загрузки;
- выбранное в кабинете удаление записи **не доходило до приложения** — то есть
  T087 был не «не проверен живьём», а сломан на живом пути.

### Что исправлено

В список разрешённых команд добавлены `native_settings` и `delete_selection`;
разбор полей у обеих команд остаётся строгим и живёт в обработчиках (имя
обработчика, маршрут документа, идентификатор запроса, ровно пять полей у
удаления), поэтому конверт по-прежнему пропускает только право команды дойти до
приложения. Проверки расширены: `WebViewBridgeEnvelopeTests.cpp` теперь требует,
чтобы обе команды проходили, и по-прежнему отвергает похожие по имени
(`native_settings_purge`).

## Раунд 45 — почему локальную запись в этой машине создать не удаётся

Попытка получить запись длиннее порога, чтобы проверить на ней удаление, упёрлась
в честный отказ самого приложения.

### Что происходило

1. Панель во время записи показывала «Остановка записи», уровни шли, запись
   длилась 45 секунд — и по остановке **пакета не появилось** (каталогов записей
   по-прежнему 13, файл очереди не менялся, время записи 01:03:31).
2. Первый заход вдобавок упёрся в системный запрос Windows «Let GRAF access your
   microphone?»: приложение ждало ответа, поэтому звук в запись не попадал.
3. После ответа «Yes» и второй записи на 45 секунд (с работающим звуком в машине,
   чтобы устройство воспроизведения не простаивало) панель сказала прямо:

   > **Не удалось сохранить запись**
   > Системный звук недоступен. Проверьте устройство воспроизведения в параметрах
   > Windows.

   Сразу под этим — «Микрофон и системный звук готовы», то есть проверка готовности
   снова проходит.

### Что это значит

Захват системного звука в этой виртуальной машине во время записи **не работает**,
и приложение ведёт себя правильно: оно не сохраняет пустую запись, а говорит, что
именно проверить. Пустой канонический звук не доходит до порога короткой записи
(T086, F6796), поэтому пакет и не создаётся — это то же правило, что подтвердилось
в прошлом раунде, только теперь видна его причина.

Граница честная, но не абсолютная, и это важно сказать точно. В этой же машине
**раньше** записи сохранялись: два пакета от 17:10 и 17:12 лежат с
`capture_status: "normal"` и длительностью 9880 и 9600 мс, то есть среда в принципе
работает. Отдельно проверено и отброшено объяснение «звук в машине простаивал»:
третий заход шёл на 45 секунд **без** постороннего звука и дал тот же отказ. Значит,
дело не в простое устройства и не в моей подсказке звуком, а в текущем состоянии
захвата, которое в этом круге восстановить не удалось.

Причину можно будет назвать точно только на физическом x64 — это ровно тот случай,
который владелец отложил как гейт T071.
