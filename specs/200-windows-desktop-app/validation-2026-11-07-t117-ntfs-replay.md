# T117 / CHK005 — проверка повторного сброса карантина на NTFS

Проверка файловой системы для [T117 / #7445](https://github.com/yshishenya/graf/issues/7445).
Результат: в Windows на изолированных копиях секторов NTFS успешный
`FlushFileBuffers` на родительском каталоге сохранил уже видимый атрибут
`READONLY` существующего файла после повторного подключения. Повторная
запись атрибутов файла для этого варианта не потребовалась. Это новый
кандидат на проверку в GRAF для
[CHK005](checklists/t117-legacy-queue-gate-immutability.md).

## Метод

Windows 11 ARM64 в Parallels, отдельный фиксированный VHD 128 MiB,
GPT/NTFS. Сценарий сверяет происхождение и размер только что подключённого
диска, отсутствие системной/загрузочной роли и границы раздела до
форматирования. Исходник пробы C# собран в x64. Для установки стенда
использована учётная запись с повышенными правами. Ни приложение, ни
путь его хранилища в стенде не используются.

Файл с искусственными байтами записан и явно сброшен. Проба проверяет
его имя, номер и поколение записи в MFT (таблице файлов NTFS), контроль
границ секторов и исходные атрибуты в чтении блоков устройства без
буферизации. Только после этого атрибут `READONLY` ставится через
обычный записывающий дескриптор. До сброса API Windows показывает
`READONLY`, а запись на томе всё ещё показывает исходный `ARCHIVE`.
В первой серии это различие воспроизведено пять раз для каждого
из трёх вариантов: обычная запись атрибута, явный сброс файла и два
изменения `ARCHIVE` с `WRITE_THROUGH`. Явный сброс файла отразился в
самой записи MFT во всех пяти случаях. Два изменения `ARCHIVE` не
были видны в MFT, что ещё не означало потерю данных журнала NTFS.

В итоговом прогоне дополнительно копируются все блоки именно этого VHD,
пока исходный том ещё подключён и до штатного отключения. Для каждого
варианта проверяется та же запись файла внутри готовой копии **до**
подключения копии. После отключения исходного VHD семь копий
подключаются по одной. При чтении проверяются исходные идентификатор
файла, одна ссылка и байты. Затем все дескрипторы цели закрываются,
и нативный вызов `MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)`
пытается заменить её искусственным файлом. При отказе сверяются оба
имени, обе строки и идентификатор цели; при успешном контроле —
новые байты цели и исчезновение имени источника.

## Итог двух повторов на новых VHD

| Действие перед копированием блоков | Атрибут в копии MFT до подключения | Атрибут после подключения | Код замены |
| --- | --- | --- | --- |
| Видимый `READONLY` без явного сброса | 32 | 32 | 0, замена прошла |
| Явный сброс того же записывающего дескриптора | 33 | 33 | 5, оба файла прежние |
| Снять и вернуть `ARCHIVE` без `WRITE_THROUGH` | 32 | 32 | 0, замена прошла |
| Повторить тот же набор атрибутов с `WRITE_THROUGH` | 32 | 32 | 0, замена прошла |
| Только снять `ARCHIVE` с `WRITE_THROUGH`, сохраняя `READONLY` | 32 | 1 | 5, оба файла прежние |
| Снять и вернуть `ARCHIVE` с `WRITE_THROUGH`, сохраняя `READONLY` | 32 | 33 | 5, оба файла прежние |
| Явно сбросить родительский каталог, без повторного изменения атрибутов файла | 32 | 33 | 5, оба файла прежние |

32 = `ARCHIVE`; 1 = `READONLY`; 33 = оба атрибута.
В последней строке целевой файл был открыт с правом чтения и
записи атрибутов, но после открытия атрибуты файла не менялись.
Дескриптор родителя получил `READ_CONTROL | FILE_READ_ATTRIBUTES |
FILE_LIST_DIRECTORY | FILE_ADD_FILE`, `FILE_SHARE_READ`,
`OPEN_EXISTING`, `FILE_FLAG_BACKUP_SEMANTICS |
FILE_FLAG_OPEN_REPARSE_POINT`. Это та же маска, которую текущий
закрытый путь GRAF использует для сброса привязки нового имени в
[ProtectedCustodyFiles.cpp](../../apps/windows/RecApp/Storage/ProtectedCustodyFiles.cpp#L324).
Третий прогон добавил тот же сценарий при дескрипторе файла только
с `GENERIC_READ` и `FILE_SHARE_READ`: MFT 32 до подключения, 33 после,
код замены 5, оба файла прежние. Остальные семь результатов совпали.

Вариант со сбросом каталога предпочтительнее для следующего точного
прогона: он не требует промежуточного изменения `ARCHIVE` и не требует
снимать `READONLY`. Для ранее изменяемой цели по-прежнему требуется
проверка подлинности и успешный сброс на том же дескрипторе, который
ставит защиту. При повторе после неоднозначной остановки одного чтения
атрибута недостаточно. Для продукта нужно привязать успешный сброс к
тому же удерживаемому каталогу и проверенному файлу, повторно проверить
идентичности, содержимое, исходные имена, историю и наблюдавшиеся
отсутствия, затем снять лишнее право до выдачи владельца. Отказ сброса,
конфликт, подмена или отмена не дают допуск.

Это не проверка потери питания: чтение всех блоков работающего тестового
устройства не является атомарным снимком и не проверяет физический
контроллер или его кэш. Наблюдаемая разница между исходными секторами
и повторно подключённой копией согласуется с восстановлением из журнала
NTFS. Гарантия записи дочернего файла по одному сбросу каталога на любой
ФС из [документации FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers)
не следует. Для GRAF остаются условия конкретной поддерживаемой ФС,
штатный путь под обычной учётной записью, защищённые сгенерированные
профили, исторический reader, точный MSIX и отдельная проверка потери
питания. CHK003–006 и T117 остаются открытыми; исходники GRAF и чеклист
не менялись.

## Независимая сверка с кодом GRAF

- Для завершённого профиля узкая точка — после холодной проверки,
  до возврата владельца из
  [`ProtectedCustodyStoreOwner::open`](../../apps/windows/RecApp/Storage/ProtectedCustodyMetadata.cpp#L3722).
  Обычная проверка `validate` используется и при очистке на уже
  открытом владельце, поэтому добавлять туда запись или сброс нельзя.
  Исправление только в вызывающем координаторе пропустит прямые вызовы
  открытия владельца. Удерживаемые карантин и sentinel надо сохранить
  до завершения сброса и контрольного чтения.
- Для незавершённого переноса точка — после полной сверки истории,
  Birth, очереди и исходника в
  [`ProtectedCustodyQueueMigration::openImpl`](../../apps/windows/RecApp/Storage/ProtectedCustodyMetadata.cpp#L2842),
  до снятия временного доступа и до переноса оригинала либо
  публикации sentinel. Текущий сброс под `!moved` пропускает
  разрыв после переноса оригинала.
- После сброса использовать существующую схему
  [снятия права](../../apps/windows/RecApp/Storage/ProtectedCustodyFiles.cpp#L803)
  с удержанием от удаления. Перед возвратом владельца повторить
  проверку маркеров, корня, истории и полного состава. Новый
  формат не требуется, если допуск основывается только на сбросе
  в текущей попытке. При следующем холодном допуске повторить проверку.
- Для продуктового теста нужен отдельный NTFS-том с буквой диска:
  папка подключения пробы не подходит под проверки путей GRAF.
  Подлинные старые профили, отказ сброса, конкурентный дескриптор,
  пропавший sentinel, неизменность обычного чтения и открытие
  независимого читателя при живом владельце остаются обязательными.
  Действующая проверка тома допускает локальный диск с постоянными
  ACL; вывод пробы не распространяется на иные файловые системы.
