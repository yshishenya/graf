# T116 — повторная нативная проверка хранения на текущем исходнике

Исходник `972af4762e7afc1a5a1c8d9025aec1eb6ce7127e`, Windows 11 в
Parallels, MSVC x64 Debug. Проверяется предшествующий этап T116/#7444.
Свежий план T117 для нового карантина получил 6/6 в независимом
[чек-листе требований](checklists/t117-fresh-queue-publication-design-review.md).
Это не разрешение пропустить порядок T116 → T117 → T118 и не приёмка
существующего изменяемого карантина.

## Разделение двух проверок пути

В исходном `NativeProtectedStartOwnerUnfinishedRestart` режимы 0–3 дошли
до своих конечных проверок. В режиме 4 native startup вернул
`unsafePath=3`, `native=0`, `generation=0` до выдачи владельца.
Старые тестовые данные задавали `directoryId=generated-alias`, а путь
указывал на каталог другой строки. Путь также приводился к верхнему регистру
целиком. Текущая `validateQueuePackages` требует, чтобы полный путь
совпадал с `trustedRoot / directoryId`; `unsafePath` не допускает
переход в обходную ветку миграции. Отказ на этом входе ожидаем по
контракту и не воспроизводит пропуск межпользовательской проверки.

Для проверки двух разных границ нужен допустимый путь второй строки,
который через отличающийся только регистром ID разрешается в тот же
объект NTFS. Обычное открытие тогда не должно давать другому владельцу
доступ к записи; пакет, очередь и содержимое корня должны остаться
неизменными. Прежний несовпадающий путь отдельно должен дать
`unsafePath`, без готовности к записи, публикации очереди или
обращения к транспорту. Это уточнение теста, не изменение правил
продукта или критериев задачи.

Рабочий профиль приложения и установленный GRAF не использованы для этих
прогонов. Запуск через Parallels CLI использует текущую учётную запись
гостя; отдельная проба того же способа запуска показала активную роль
Administrator. Этот результат не закрывает приёмку под стандартным
пользователем. Причина ошибки хранилища установленного 0.1.0.18 ими
не определена.
