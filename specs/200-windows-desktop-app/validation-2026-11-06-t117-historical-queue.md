# T117: откат на реальный исторический читатель очереди

Статус: воспроизведён блокер возврата к новой версии после отката. T117,
исключение старого читателя, установленная приёмка и выпуск остаются открыты.

Сравнение на Windows 11 ARM64 в Parallels, оба тестовых процесса x64 (MSVC).
Исторический `DesktopUploadQueueService::load/enqueue` собран без правок из
`99b00a579c24b50e320465b69d9a296038bc544d`. Текущий нативный код переноса —
из `972af4762e7afc1a5a1c8d9025aec1eb6ce7127e`. Добавлены только временная
тестовая точка входа и перехват успешного `NtSetInformationFile` для одного
искусственного пути. Старый читатель использует настоящий путь карантина
на диске; его штатная точка сохранения считает попытки записи в памяти.
Каждый запуск старого читателя — новый процесс. После прерывания проверены
хеши файлов и повторный запуск текущего переноса. Ни рабочий профиль GRAF,
ни микрофон, ни сеть в проверке не использовались.

| Состояние | Исторический читатель | Текущий читатель / файлы |
| --- | --- | --- |
| Старый реестр до переноса | Прочитал 1 строку, принял новую строку, 1 вызов точки сохранения | Файлы не изменились |
| Контроль: прежнего имени и карантина нет | Открыл пустую очередь, принял новую строку, 1 вызов точки сохранения | Файлы не изменились |
| Сразу после нативного rename и успешного flush, до создания sentinel | Дважды отказал, 0 вызовов точки сохранения | Все хеши совпали после обоих запусков; текущая версия завершила перенос, создала sentinel и сохранила исходный реестр |
| После полного переноса и закрытия всех дескрипторов новой версии | Дважды отказал, 0 вызовов точки сохранения | Первый запуск старого кода убрал sentinel, заменив карантин теми же байтами. Исходный реестр сохранился; новый запуск завершился `ioFailed` (6), ничего больше не изменив |

Причина: старый путь карантина делает `std::filesystem::rename(old, quarantine)`.
MSVC использует [MoveFileExW с заменой существующего файла](https://github.com/microsoft/STL/blob/main/stl/src/filesystem.cpp).
Отдельный нативный тест на временной паре файлов подтвердил: с обычным
файлом назначения переименование проходит и убирает старое имя; с
`FILE_ATTRIBUTE_READONLY` у файла назначения Win32 вернул
`ERROR_ACCESS_DENIED` (5), оба имени остались. Это проверка механизма,
не проверка исправленной реализации GRAF.

Ещё два коротких нативных прогона: `CREATE_NEW | FILE_ATTRIBUTE_READONLY`
выдал новый дескриптор с правом записи; запись, `FlushFileBuffers` и
повторное чтение с атрибутом прошли. Для существующего изменяемого файла
`FileBasicInfo` меняет атрибут через дескриптор с `FILE_WRITE_ATTRIBUTES`,
но в таком режиме `FlushFileBuffers` вернул 5. Дескриптор с
`GENERIC_READ | GENERIC_WRITE`, полученный **до** смены атрибута, позволил
поставить атрибут и выполнить flush. Повторно открыть этот уже readonly
файл с `GENERIC_WRITE` Windows отказалась (5). Прогоны ничего не меняли
в установке GRAF.

## Повтор: причинная проверка с настоящим зашифрованным карантином

Новый искусственный профиль перенесён штатным текущим нативным кодом.
После закрытия всех дескрипторов тест добавил `FILE_ATTRIBUTE_READONLY`
к настоящему файлу `.quarantine` через `SetFileAttributesW`. Код приложения
и байты файлов не менялись. Это проверка действия атрибута, не проверка
его штатной установки GRAF и не имитация потери питания.

- Два отдельных запуска исходного старого читателя отказали, не приняв
  строку и не вызвав сохранение. Оба маркера и исходный реестр сохранили
  имена и хеши.
- Следующий холодный запуск нового читателя принял то же защищённое
  хранилище. Снимки файлов до старых запусков, после них и после нового
  запуска совпали.
- Отрицательный контроль: тест удалил только sentinel в искусственном
  профиле. Старый читатель снова отказал; новый вернул `ioFailed` (6),
  не создал ни sentinel, ни пустую очередь. Снимок не изменился.
- Снова пройден прерванный нативный rename/flush до sentinel; оба старых
  запуска сохранили файлы, новый завершил перенос.

Выход 0, временный каталог Windows удалён. Установленный GRAF 0.1.0.18
сохранил тот же EXE; отдельно подтверждён один отвечающий процесс именно
этого пакета. Хеши SHA-256 повторного прогона:

- Входы `dd5aaab7200414ba517370f1ec0c37d45465d3e708a21958584fc050d73d94c3`;
  тестовое дополнение `b3b0909e0b0838c06de306b6355b293e1647f6e155e89d6413ce690e4808f67f`.
- Старый EXE `965b81235d79e496202224e1dff09b0c7167411ad08f3aea60f938aabcbbc401`;
  текущий тестовый EXE `34da73286e86ea46233c076dd3b3bf51d15cc9965adfeb0eb4d933a1981f26d4`.
- `pair.err` `899cda9644aecacee930c1543677e4a85dbf393754231599b8b7004794c1c617`;
  `result.json` `5e8404aef7500ff24b3390af7b934e02a5bff2bb00c9dfea2a2629a7b4a7a66d`.

[Независимый разбор плана](checklists/t117-legacy-queue-gate-immutability-review.md)
отдельно сохраняет открытым случай «атрибут виден, flush отказал».
Успешный повторный запуск процесса с уже видимым атрибутом подтверждает
текущее поведение Win32, но не подтверждает сохранение метаданных при
потере питания. Изменения продукта и установленную приёмку этот
исследовательский прогон не заменяет.

### Оба пакета и исходники на одном автономном носителе

В Parallels образ назначен существующему `cdrom2` машины

### Предварительная проверка входов сборки в QA 117

Обнаружение файлов не гарантирует успешную сборку; имя и обычный профиль
для проверки установленного пакета по-прежнему сверяются отдельно.

заменяет `Get-GrafQaState-038.ps1`.
