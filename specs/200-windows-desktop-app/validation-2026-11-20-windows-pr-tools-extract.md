# Windows PR lane: зависание на tools-extract — 2026-11-20

Этот файл фиксирует наблюдения по полосе `windows-pr` для head
`6558eb767c5586185418d1993cc2bab8383d4958` (PR #8130) и по более раннему
head `7ab13a09da186b95af0ed628ed51fc81e3edec76`.

## Что произошло

Шаг `Build Windows x64 test targets` не завершился ни за 60, ни за 120 минут:
job был отменён по лимиту, а полоса так и не дошла до CMake-сборки и CTest.

Строки `FFmpeg stage terminal name=tools-extract exit=...` нет: процесс

На head `f431b0fb` при лимите 60 минут картина та же: остановка на
`tools-extract` (job `135728538874`).

## Почему это важно

- CMake-сборка и CTest ни разу не выполнялись, поэтому полоса не подтверждает
  и не опровергает код Windows-приложения.
- Двухчасовое ожидание не даёт никакой диагностики: нет ни вывода `tar`, ни
  кода возврата, ни размера распакованного каталога.
- Изменение лимита с 60 до 120 минут проблему не решило и не является
  доказательством.

## Что уже проверено

- Все четыре зависимости скачиваются, их размер и SHA-256 совпадают с пинами.
- `FFmpegToolsExtractionTests.ps1` проходит: распаковка малого USTAR/xz
  работает, `network_requests=0`, PATH shadow игнорируется.
- Шаг использует системный `%SystemRoot%\System32\tar.exe` для
  `msys2-base.tar.xz`; распаковка `make`/`diffutils` идёт уже MSYS2-тарболом.

## Что не проверено

- Причина зависания: поведение bsdtar на `.tar.xz`, ожидание stdin,
  блокировка файла антивирусом, поведение `WaitForExit()` при асинхронном
  чтении потоков или что-то ещё. Без Windows-хоста это не устанавливается.
- Полный прогон `windows-pr` с CTest и T124.

## Следующий шаг

Отдельная задача: ограничить каждый шаг bootstrap по времени, добавить в
журнал безопасные метаданные (длительность, код возврата, размер и хвост
stderr), воспроизвести распаковку на Windows-хосте и только после этого
считать полосу рабочей.

## Ограничение этапов — 2026-11-22

Шаги bootstrap теперь ограничены по времени в `build-graf-ffmpeg.ps1`:
`tools-extract` — 900 с, распаковка пакетов и исходников — 600 с, сборка
FFmpeg — 3600 с, остальные шаги — 1800 с. Пока шаг выполняется, каждые 30 с
печатается `FFmpeg stage progress`, поэтому зависание видно в журнале. При
превышении лимита процесс завершается, пишутся логи и
`<stage>.terminal.json` с `timeout=true`, а job падает с понятной причиной
вместо двухчасового ожидания. Нормальный успешный путь не меняется:
`FFmpeg stage started` и `FFmpeg stage terminal ... exit=0` сохраняются.

Это ограничивает ущерб, но не доказывает причину зависания; задача #8146
остаётся открытой до прогона на Windows-хосте.

## Проверенные и отклонённые гипотезы — 2026-11-22

Прогон с закрытым stdin и исключением каталога сборки из проверки Defender
(job для head `f43c3c15a`) дал те же показатели: `cpu_ms=16`, `memory_mb=5`,
`stdout=0`, `stderr=0`, таймаут 900 с, `defender_exclusion=applied`.
Значит, ожидание stdin и сканирование Defender эту блокировку не объясняют.

Следующий шаг по задаче #8146: если на раннере есть `7-Zip`, распаковка идёт
через него (сначала `.tar.xz`, затем `.tar`), иначе используется прежний
`System32\tar.exe`. Архив и его SHA не меняются, оба пути проверяются
пределами времени и теми же логами.
