Штатный рабочий контекст не формируется из произвольного запроса пользователя к финансовой таблице: нормализация создаёт job из workspace и meeting (`normalization/service.py:887–890`), подбор работы формирует TenantScope из сохранённых полей job (`normalization/pickup.py:426–430`), activity устанавливает этот worker-контекст и читает задачу с явным равенством job.workspace_id, после чего проверяет meeting/media revision/profile/validation identity (`normalization/worker.py:305–321`). Для случая (3) настройка отсутствующего workspace действует в текущей транзакции чтения; для (4) прежний rec_maintenance_allowed требует отдельную обслуживающую роль. ## Дополнительное ревью совместимости прежних финансовых испытаний

После обнаруженных GitHub fast ошибок старых имитаторов сессии перечитан отдельный diff `tests/unit/test_billing_entitlements.py` и `tests/unit/test_renewal_charge.py`. **PASS исходного кода дополнения; блокирующих замечаний нет.** Изменены только импорт SimpleNamespace и метод execute у двух существующих помощников. Выполнение исправленного набора GitHub fast этим выводом не подтверждается.

Оба execute проверяют одну выбранную колонку с именем capacity_snapshot_bytes или plan_snapshot и делегируют прежнему scalar(query). Объект, возвращённый scalar, помещается в результат first() без преобразования самого значения: отсутствие строки остаётся None; существующая строка/ORM-объект с NULL-полем остаётся объектом с соответствующим полем None. Значит, различие отсутствующей строки и NULL не схлопывается. Это ограниченная имитация именованной строки SQLAlchemy для двух текущих запросов; effective_paid_storage использует только именованное поле и проверку наличия объекта, поэтому выбранная форма результата ему соответствует.

Прежние маршруты scalar и порядок получения финансовых объектов не изменены: _FakeDb возвращает сохранённый счёт для invoice JOIN и отсутствие бонусного журнала; FakeDb возвращает отсутствие bonus/base invoice/storage grants для прежних сценариев, а прочие запросы продолжают читать свою прежнюю последовательность. Унаследованные PlanningDb/PagedDb используют тот же полиморфный scalar; новые execute не вводят расходования финансовых ответов вне прежней логики.

Проверки согласия и текущих полномочий, защиты от повторного предоставления/платежа, неизвестного ответа провайдера, повторов с тем же ключом, временных окон, цены, статуса чека и запрета личной подписки для связанной области не удалены и не ослаблены: ни один test body, assertion или исходный financial scenario в этом дополнении не изменён. Отдельные испытания bonus NULL и причинная PostgreSQL-матрица F287 остаются на месте.
