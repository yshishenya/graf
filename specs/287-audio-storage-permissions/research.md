# Research

## Decision

Использовать PostgreSQL SELECT на уровне конкретных столбцов и минимальные проекции SQLAlchemy. Текущий `effective_paid_storage` требует чтения четырёх таблиц; исправление лишь первой переносит отказ на следующий запрос. Существующие RLS-политики уже ограничивают все четыре таблицы текущей рабочей областью.

## Rationale

- `normalization.service._reserve_playback_storage` вызывает общий расчёт только для действующего trial/personal.
- Расчёт использует ledger → storage grants → invoice/base grants → historical journal; чтение целого ORM ledger/invoice требует ненужных полей.
- `.execute(select(snapshot)).first()` сохраняет различие отсутствующей строки и NULL-снимка бонуса. Предикаты/порядок и все вызывающие пути остаются прежними.
- Существующая настройка отзывает табличные права, но отдельные права столбцов требуется отзывать отдельно. Для четырёх финансовых таблиц очищаем все прежние права столбцов перед точным назначением, затем проверяем фактический набор.
- Нынешний PostgreSQL seed подготовки не создавал платную подписку, поэтому не доходил до проблемного вызова.

## Alternatives considered

- SELECT четырёх таблиц целиком: отклонено, открывает ненужные контакты/идентификаторы платежей.
- Повышенная роль, BYPASSRLS, членство, SECURITY DEFINER: отклонено, нарушает существующие границы.
- Использовать кэш `subscription.capacity_bytes`: отклонено, может расходиться с действующими/будущими правами.
- Новая служба/система восстановления: не нужна, существующий повтор задачи достаточен после исправления прав.
