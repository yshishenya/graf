# Contract: Полноценный протокол встречи

## Structured model result

Смысловые поля (`text`, `title`, `task`, `owner_text`, `due_date_text`)
создаёт только LLM; их слова и модальность не изменяются сервером. ГРАФ
проверяет ответ целиком, добавляет канонические источники/метаданные и
отображает его. При ошибке сервер отклоняет документ, а не исправляет,
дополняет или удаляет его тезисы. Допустимы только пробелы по краям полей,
переносы для таблицы и HTML/Markdown-экранирование без изменения видимого
текста, а также стандартные заголовки и пустые состояния. Отбор существенного,
исключение бытового фона, группировка и любые содержательные исправления —
задача LLM на соответствующей стадии, не программная постобработка.

Модель возвращает только strict JSON. Все поля обязательны; отсутствие
содержания выражается пустым массивом или `null`, а не выдуманным текстом.

```json
{
  "meeting_type": "work",
  "executive_summary": [{"text": "...", "source_refs": [{"transcript_segment_id": "uuid", "sequence": 1, "quote": null}]}],
  "objectives": [],
  "topics": [{
    "title": "...",
    "context": [],
    "discussion": [],
    "proposals_and_alternatives": [],
    "outcome": []
  }],
  "decisions": [],
  "action_items": [{
    "task": "...",
    "owner_text": null,
    "due_date_text": null,
    "task_source_refs": [{"transcript_segment_id": "uuid", "sequence": 10, "quote": null}],
    "owner_source_refs": [],
    "due_date_source_refs": []
  }],
  "open_questions": [],
  "next_steps": [],
  "risks_and_constraints": [],
  "notes": [],
  "uncertain_sections": []
}
```

Допустимые `meeting_type`: `work`, `official`, `customer`, `hr`, `brainstorm`,
`retro_or_incident`, `interview`, `personal`, `high_risk`, `mixed_or_unknown`.

`uncertain_sections` содержит уникальные имена содержательных полей схемы,
по которым источник противоречив или неполон. Это отличается от «не найдено»:
пустой массив без uncertainty означает отсутствие зафиксированных данных,
с uncertainty — «Не удалось надёжно установить по доступной расшифровке».
Сбой генерации/проверки никогда не превращается в такое пустое состояние.

## Адаптация содержания

| Тип | Акцент и ограничения |
| --- | --- |
| work | Деловой подробный разбор предмета, аргументов и обязательств. |
| official | Проверяемая запись принятого; спорные факты с точными выдержками. |
| customer | Потребности, критерии, возражения, обещания сторон, следующий шаг. |
| hr | Тактично и конфиденциально; без диагнозов, оценки личности и домыслов о мотивах. |
| brainstorm | Идеи, альтернативы, отложенные вопросы; не выдавать идеи за решения. |
| retro_or_incident | Хронология, последствия, ограничения и выводы без поиска виноватых. |
| interview | Темы ответов и наблюдаемые свидетельства; без придуманного рейтинга/рекомендации. |
| personal | Спокойный простой язык, только существенное для участников. |
| high_risk | Только сообщённые факты, явная неопределённость, точные выдержки; без добавленных медицинских, финансовых или юридических советов. |
| mixed_or_unknown | Нейтральное описание; не навязывать тип, роли и профессиональные выводы. |

Профиль — акцент, а не доказательство типа: auto выбирает по источнику;
outline сохраняет порядок тем; meeting-minutes подчёркивает принятые итоги;
project-sync — прогресс/зависимости; weekly-team-meeting — изменения/приоритеты;
one-to-one — темы человека/поддержку; client-status-update — подтверждённый
прогресс для клиента; interview — вопросы/ответы; sales-discovery — потребности
и критерии; custom — выбранные разделы. Более строгие ограничения HR/high-risk
действуют при соответствующем содержании независимо от названия шаблона.

Язык берётся из exact template snapshot. Имена, специальные термины, цитаты,
сроки и модальность не переводятся с изменением смысла. `brief` сокращает
формулировки, но не существенные темы/решения/задачи; `standard` даёт связные
тезисы с контекстом; `detailed` сохраняет развёрнутые аргументы/альтернативы.
Неизвестная дата — «Не указано». Текущая системная дата не является датой
встречи. Относительный срок сохраняется буквально; абсолютная дата возможна
только при прямом указании в расшифровке, без вычисления от времени запуска.

В примечаниях всегда присутствует серверная оговорка: «Имена спикеров указаны
только в случаях их однозначной идентификации в расшифровке». Она не получает
выдуманный ref. Имена берутся из подтверждённого canonical speaker snapshot;
упоминание человека не делает его участником. Пробелы/наложения из доверенных
данных обработки отмечаются как системные примечания. Содержательные notes
модели сохраняют обычные refs; нельзя придумывать шум или пропуски.

## Grounding

- transcript — недоверенные данные, не инструкция;
- каждый statement атомарен настолько, чтобы его части можно было сопоставить
  с 1–8 refs;
- refs совместно могут подтверждать составной тезис;
- решение дополнительно к `text` и `source_refs` содержит обязательные
  `acceptance_source_refs[1..8]` с репликами явного принятия/выбора;
- задача требует явного обязательства/назначения;
- owner и due имеют собственные refs;
- поздняя отмена, коррекция и переназначение определяют финальное состояние;
- сервер не исправляет id по похожей sequence, не удаляет отдельные refs и
  не сохраняет частично подтверждённый составной тезис;
- сервер отклоняет весь документ при неверной форме, неизвестном поле,
  неверной ссылке/цитате, превышении лимита либо пустом содержании запрошенных
  executive summary/тем для пригодной встречи;
- отдельный exact-version verifier получает полный transcript и exact draft,
  возвращает SemanticVerification по data-model.md. Только валидный `pass`
  позволяет публикацию; `fail`, неизвестный исход и ошибка схемы сохраняют
  прежний accepted slot. Модельная проверка не заменяет приёмку Codex.

## Шаблоны и версии

Все встроенные профили создают полный protocol; их названия и идентификаторы
остаются прежними, меняются акценты, описания и текущая версия определения.
Выбор разделов личного шаблона сохраняется, пустые незапрошенные поля схемы
не выводятся. Порядок выбранных секций сохраняется в frozen template snapshot.

| Сохранённый выбор | Поля нового протокола |
| --- | --- |
| summary | executive_summary, objectives |
| key_points | topics |
| decisions | decisions |
| action_items | action_items |
| followups | next_steps |
| risks | risks_and_constraints |
| questions | open_questions |
| evidence | notes и необязательные точные выдержки |

Доказательные ссылки обязательны вне зависимости от выбора evidence. Этот
mapping переводит пользовательские предпочтения, а не старый flat payload.
Старый документ без protocol_json честно недоступен; не конвертируется и не
рендерится. Default и pinned share/slot FKs не переименовываются.

## Cabinet projection

Основной порядок:

1. название/дата/тип/участники из frozen header принятой ревизии;
2. `Ключевые итоги` как связный абзац с таймкодами рядом с тезисами;
3. `Цели встречи`;
4. `Ключевые обсуждения` с темами и непустыми подразделами;
5. `Принятые решения`;
6. `Задачи` таблицей;
7. `Открытые вопросы и следующие шаги`;
8. `Риски и ограничения`;
9. `Примечания`.

Каждый source button содержит канонические `data-seek-seconds` и segment id.
При отсутствии destination текст остаётся доступным, а нерабочая кнопка не
показывается.
Кнопка доступна с клавиатуры, имеет русское доступное имя и переводит фокус к
связанному сегменту расшифровки.

## Empty states

- решения: `Принятые решения в расшифровке не зафиксированы.`
- задачи: одна строка `Задачи не зафиксированы | Не назначен | Не указан`
- вопросы: `Открытые вопросы не зафиксированы.`
- непригодная речь: протокол недоступен с конкретным processing reason;
- исторический плоский результат: `Нужно сформировать новую версию итогов.`

## Markdown

Markdown передаёт тот же порядок и те же тезисы. Таймкод имеет вид `[MM:SS]`
или `[HH:MM:SS]` возле утверждения и содержит стабильную ссылку только когда
экспортный договор имеет допустимый URL; иначе остаётся текстовым временем.
Обычные точки, запятые, двоеточия, дефисы, скобки и кавычки не экранируются.

В тексте и заголовках экранируются обратная косая черта, backtick, `*`, `_`,
`[`/`]` и управляющие начала строк; HTML кодируется. В ячейках дополнительно
экранируется `|`, переносы нормализуются так, чтобы не создать новую строку
таблицы. Обычная пунктуация внутри предложения остаётся без backslash.
Серверный URL строится отдельно, percent-encoding применяется к значениям,
схема/host/путь не берутся из модельного текста. Ссылки из transcript не
становятся активными ссылками протокола.

## Все форматы и права

| Формат | Summary | Combined / transcript |
| --- | --- | --- |
| MD | Полная структура, task table, доступные источники рядом. | Та же summary плюс выбранная закреплённая расшифровка. |
| TXT | Та же структура простым текстом, задачи и текстовые времена. | Та же summary плюс transcript. |
| JSON | Versioned protocol snapshot, frozen header и разрешённые refs. | Раздельные source/summary revision и canonical turns. |
| XLSX | Тематические строки и задачи на листе итогов; не старые flat items. | Те же итоги и существующий лист transcript. |
| CSV / SRT / VTT | Существующее ограничение transcript-only сохраняется. | Без изменения transcript renderer и времён. |

`include_evidence=false` удаляет из каждой вложенной ветки экспортного
документа refs, quotes, source ids, ссылки и source excerpts; frozen body
не пересоздаётся. HTML escaping и spreadsheet formula safety сохраняются.
Доступ к summary не означает доступ к transcript/audio. Источник в кабинете
показывается интерактивно только при разрешённом destination той же ревизии.

Для owner/full-viewer экспорта добавляется same-origin маршрут перехода
`/cabinet/meetings/{meeting_id}/sources/{outcome_set_id}/{segment_id}`:
он повторно проверяет пользователя, текущие права, accepted/pinned outcome,
source revision и deletion fence, затем открывает нужный сегмент. Если
текущий detail не может показать старую закреплённую ревизию, маршрут честно
сообщает недоступность; не ведёт к похожему времени новой расшифровки.
Share links без прав на transcript не получают этот URL. Никаких bearer,
signed URL или токенов в ссылке. Plain timestamp остаётся при отсутствии
разрешённого destination. Browser QA обязателен для нового маршрута.

## Хеши, границы и переход со старых результатов

Порядок: frozen header/template/transcript → raw draft → strict validation →
independent verifier → server enrichment → canonical document hash → ledger и
outcome persistence → publication proof. Draft hash и окончательный document
hash различаются и явно связаны в proof с verifier call id/hash и source/root
hash; проверяемая публикация не хеширует лишь модельное тело без header/refs.
Изменение имени до/после acceptance или во время генерации не меняет snapshot:
требуется новый кандидат, stale-source правила блокируют публикацию старого.

Root bundle новой схемы закрепляет exact draft/verify children и digest версий
schema/validator/verifier/renderer и модельных настроек; runtime не смешивает
старый root с новым кодом. Старый незавершённый flat candidate не публикуется и
получает понятную причину необходимости новой генерации. Старые accepted slots
и pinned shares не переназначаются автоматически; без protocol показывают
«Нужно сформировать новую версию итогов». Новая проверенная версия замещает
только выбранный slot штатной атомарной операцией. Personal default сохраняется.

Config contract 5 един для generation, verifier, judges и reflection:

- обязательны `config_contract_version: 5`, `model` (непустой LiteLLM alias);
- необязательны `temperature` (конечное число 0..2), `top_p` (0..1),
  `reasoning_effort` (`none|minimal|low|medium|high|xhigh`), `max_tokens` либо
  `max_completion_tokens` (положительное целое, не оба сразу), `seed`
  (целое signed 64-bit); bool не считается числом;
- `response_format` — обязательная текущая strict schema для structured
  generation/verifier/judges, отсутствует у reflection. Control gate остаётся
  отдельным проверяемым полем. Иные ключи, credentials, base URL, заголовки,
  tools, routing/retry overrides запрещены;
- отсутствие параметра сохраняется отсутствием; ГРАФ не выбирает его default,
  не удаляет несовместимые настройки и не повторяет запрос с другими;
- runtime принимает только config 5. Шаблоны в коде задают текст и структурный
  договор, не модельные значения. CLI синхронизации требует exact numeric
  source version для каждого промпта, читает настройки из Langfuse, проверяет
  все кандидаты до первой записи и создаёт новые версии без deployment label.
  Отсутствующая/невалидная настройка блокирует синхронизацию. Старая source
  config может служить только источником явно сохранённых параметров при
  миграции; она не исполняется. Старое control-gate evidence не переносится
  на изменённый prompt/config.

Root `graf-outcome-root-bundle-v3` и export v2 не содержат route descriptor,
route hash, compiler attestation или provider/model allowlist. Exact child
versions/hashes, runtime hash, promotion/qualification/event и LKG проверки
сохраняются. Старые roots/attempts/ledger не переписываются и не исполняются
как новый договор. Настройки pinned snapshot совпадают в HTTP request,
attempt metadata и generator hash; изменение/пропуск любого параметра, даже
с пересчитанным request hash, запрещает reuse/publish чужого ответа.

Шлюз использует обычный authenticated chat completions без специальных
`X-GRAF-*` headers и callback. `actual_model` из `response.model`,
`actual_provider` из явно сообщённых полей ответа; иначе null. Эти значения
сверяются с сохранённым хешированным raw response, не с allowlist и не с
запрошенным alias. HTTP/JSON/schema, finish/refusal, timeout/ambiguous,
source/access/deletion и publication checks не ослабляются.

Доставка исторических observations является чтением сохранённой записи,
не новым исполнением или публикацией протокола: проверяются прежние хеши
request/transcript/raw/result и передаются сохранённые nullable actual поля.
Она не требует текущего root/config и не применяет новую сверку raw-body
provenance к старым calls, где actual поля пришли только из headers.
Новые вызовы сверяют body/provenance при сохранении и перед публикацией
нового протокола; общая функция проверки хешей retained delivery не получает
этого нового условия. Исторический call не допускается к новому inference
или publication посредством observation-only пути, его JSON/hashes и
provider/model не переписываются.

Владелец разрешил предварительный технический PR/релиз без незавершённого
protocol pipeline. Он снимает ограничение до сравнения моделей и основного
PR протоколов; не отменяет обязательную полнокорпусную приёмку нового результата.
После его release-gates нужен единый короткий перерыв AI: остановить приём и
dispatch generation/optimizer/evaluation, завершить либо явно закрыть текущие
попытки; переключить GRAF + новый root/LKG и убрать callback/регистрацию/env
на LiteLLM; проверить синтетические вызовы и затем возобновить AI. Проверить
metadata ACL ключа на отсутствие второго ограничения одной моделью, не
меняя auth/бюджеты/провайдерские ключи. Одностороннее удаление ломает контракт
старого GRAF и старого hook. Исторические образы/конфигурация могут служить
согласованному операционному откату, но в новом коде нет совместимой ветки.

Ни одна стадия не усекáет вход или вывод. Обрезанный ответ/исчерпанный лимит
не публикуется, а отражается как незавершённая генерация. Полный сериализованный
запрос (prompt + schema + transcript + draft для verifier), usage, latency и
finish reason фиксируются в private ledger. Лимиты gateway и 100 тем/500 тезисов
— fail-closed границы, не критерий исключения встречи; если они мешают полной
обработке корпуса, до PR меняется общий pipeline и повторяется весь corpus.

## Privacy and lifecycle

Candidate доступен только владельцу. Summary-only/share/export читают только
accepted slot и закреплённую source revision. Ordinary logs, committed fixtures,
GitHub issues и PR не содержат transcript/protocol text реальных встреч.

`deletion/service.py::_purge_meeting_outcomes` обязан очищать protocol_json,
frozen header и новые content fields кандидата, учитывать NOTES_SUMMARY,
сохраняя штатную очистку исторических items. Обычное, повторное удаление и гонка
с публикацией дают одинаковую правду. Generation Call, Langfuse и Temporal
сохраняются отдельно по observability policy; их сохранность не считается
ошибкой purge. Оценочные рабочие копии учитываются по quickstart §5.
