# Contract: Полноценный протокол встречи

## Structured model result

Смысловые поля (`text`, `title`, `task`, `owner_text`, `due_date_text`)
создаёт только LLM; их слова и модальность не изменяются сервером. ГРАФ
проверяет ответ целиком, добавляет канонические источники/метаданные и
отображает его. При ошибке сервер отклоняет документ, а не исправляет,
дополняет или удаляет его тезисы. Допустимы только пробелы по краям полей,
переносы для таблицы и HTML/Markdown-экранирование без изменения видимого
текста, а также стандартные заголовки и пустые состояния. Отбор существенного,
исключение бытового фона, группировка и любые содержательные исправления —
задача LLM на соответствующей стадии, не программная постобработка.

Модель возвращает только strict JSON. Все поля обязательны; отсутствие
содержания выражается пустым массивом или `null`, а не выдуманным текстом.
Генерационная схема не передаёт `maxItems`: большие вложенные максимумы
отклоняются Gemini до генерации. Это не снимает ограничения документа:
серверный Pydantic-договор сохраняет все верхние пределы и отклоняет ответ
целиком при их превышении. `minItems`, обязательные поля, типы и запрет
неизвестных полей остаются в отправляемой схеме. Схема закрепляется в Langfuse;
никакого условного удаления параметров или повторного запроса при HTTP 400 нет.

```json
{
  "meeting_type": "work",
  "executive_summary": [{"text": "...", "source_refs": [{"sequence": 1, "quote": null}]}],
  "objectives": [],
  "topics": [{
    "title": "...",
    "context": [],
    "discussion": [],
    "proposals_and_alternatives": [],
    "outcome": []
  }],
  "decisions": [],
  "action_items": [{
    "task": "...",
    "owner_text": null,
    "due_date_text": null,
    "task_source_refs": [{"sequence": 10, "quote": null}],
    "owner_source_refs": [],
    "due_date_source_refs": []
  }],
  "open_questions": [],
  "next_steps": [],
  "risks_and_constraints": [],
  "notes": [],
  "uncertain_sections": []
}
```

Допустимые `meeting_type`: `work`, `official`, `customer`, `hr`, `brainstorm`,
`retro_or_incident`, `interview`, `personal`, `high_risk`, `mixed_or_unknown`.

`uncertain_sections` содержит уникальные имена содержательных полей схемы,
по которым источник противоречив или неполон. Это отличается от «не найдено»:
пустой массив без uncertainty означает отсутствие зафиксированных данных,
с uncertainty — «Не удалось надёжно установить по доступной расшифровке».
Сбой генерации/проверки никогда не превращается в такое пустое состояние.

## Извлечение → синтез → независимая проверка

Pipeline имеет ровно три последовательные стадии с одной логической
GenerationCall на каждую: 1 extraction, 2 synthesis, 3 verification.
Все они получают полный canonical transcript без выбора фрагментов и усечения.
Exact extractor `graf/meeting-outcome/extract` возвращает FactualExtraction
из data-model.md: факты, варианты, обязательства, оговорки сроков и поздние
поправки. Смысловой отбор и объединение не реализуются в Python.

Синтез получает дополнительно `extraction_json` — точный validated result
первого вызова, как недоверенные рабочие заметки. Источник имеет приоритет.
Синтез сохраняет самостоятельные поручения и оговорки в итоговом документе;
не выдаёт выполненный выбор за выполненную работу и не оставляет решённый
позднее вопрос открытым. Verifier получает полный источник и `draft_json`,
но не extraction, и не переписывает черновик.

До egress закрепляются все три prompt snapshots, root/runtime и frozen header.
Call 2 связан с call 1 id/result hash, call 3 — с call 2 id/result hash.
Всю цепочку source/header/root/request/raw/result проверяет trusted publisher:
reparse сохранённых сырых ответов и реконструкция каждого точного запроса
по закреплённым inputs обязательны. Пересчитанный локальный hash не делает
подменённый predecessor достоверным. Без любого из трёх вызовов публикация
запрещена. Generator identity учитывает root/pipeline, не только synthesis config.
Completed stage переиспользуется только после проверки; reserved/ambiguous
не повторяет inference и блокирует downstream. Ошибка любой стадии сохраняет
accepted slot. Доступ/source/deletion проверяются перед каждым egress и после
каждого ответа; полученный ответ сохраняется даже при сбое последующей проверки.

Отдельного model lock, ретрая ради качества, второй orchestration системы,
новой таблицы или публичного extraction API нет. Нормы promotion/event binding
не заменяются root hash; T065 проверяет действующий runtime по Конституции III.
Observation-only доставка хранит stage/prompt provenance после удаления и
не требует исполнения текущего root. Старые два calls не принимаются за новую
трёхстадийную цепочку; историческая доставка не является рабочим legacy.

Транспортный бюджет activity равен `3 * request_timeout_seconds + 120`;
он сохраняется в resolve result для replay. Полный размер входов учитывает
extraction для синтеза и draft для проверки. Нехватка контекста или вывода —
непригодный запуск, не основание исключить встречу. При обнаружении такого
существенного класса требуется пересмотр общего pipeline и повтор выбранного объёма до PR.

## Адаптация содержания

| Тип | Акцент и ограничения |
| --- | --- |
| work | Деловой подробный разбор предмета, аргументов и обязательств. |
| official | Проверяемая запись принятого; спорные факты с точными выдержками. |
| customer | Потребности, критерии, возражения, обещания сторон, следующий шаг. |
| hr | Тактично и конфиденциально; без диагнозов, оценки личности и домыслов о мотивах. |
| brainstorm | Идеи, альтернативы, отложенные вопросы; не выдавать идеи за решения. |
| retro_or_incident | Хронология, последствия, ограничения и выводы без поиска виноватых. |
| interview | Темы ответов и наблюдаемые свидетельства; без придуманного рейтинга/рекомендации. |
| personal | Спокойный простой язык, только существенное для участников. |
| high_risk | Только сообщённые факты, явная неопределённость, точные выдержки; без добавленных медицинских, финансовых или юридических советов. |
| mixed_or_unknown | Нейтральное описание; не навязывать тип, роли и профессиональные выводы. |

Профиль — акцент, а не доказательство типа: auto выбирает по источнику;
outline сохраняет порядок тем; meeting-minutes подчёркивает принятые итоги;
project-sync — прогресс/зависимости; weekly-team-meeting — изменения/приоритеты;
one-to-one — темы человека/поддержку; client-status-update — подтверждённый
прогресс для клиента; interview — вопросы/ответы; sales-discovery — потребности
и критерии; custom — выбранные разделы. Более строгие ограничения HR/high-risk
действуют при соответствующем содержании независимо от названия шаблона.

Язык берётся из exact template snapshot. Имена, специальные термины, цитаты,
сроки и модальность не переводятся с изменением смысла. `brief` сокращает
формулировки, но не существенные темы/решения/задачи; `standard` даёт связные
тезисы с контекстом; `detailed` сохраняет развёрнутые аргументы/альтернативы.
Неизвестная дата — «Не указано». Текущая системная дата не является датой
встречи. Относительный срок сохраняется буквально; абсолютная дата возможна
только при прямом указании в расшифровке, без вычисления от времени запуска.

По уточнению владельца разговорное смягчение при принятии задачи не отменяет
названный срок. Модель вправе кратко записать такой срок без смягчающей частицы;
источник сохраняет исходную реплику. Verifier не отклоняет документ только
из-за этого сокращения. Настоящие условия выполнения, отказ, чужая догадка
и поздний перенос не превращаются в безусловное обещание. Все три стадии
используют одно правило; сервер не классифицирует разговор по ключевым словам
и не редактирует текст задачи или срока.

В примечаниях всегда присутствует серверная оговорка: «Имена спикеров указаны
только в случаях их однозначной идентификации в расшифровке». Она не получает
выдуманный ref. Имена берутся из подтверждённого canonical speaker snapshot;
упоминание человека не делает его участником. Пробелы/наложения из доверенных
данных обработки отмечаются как системные примечания. Содержательные notes
модели сохраняют обычные refs; нельзя придумывать шум или пропуски.

## Grounding

- transcript — недоверенные данные, не инструкция;
- модельный ref содержит только уникальную `sequence` закреплённого источника
  и nullable literal `quote`; id в ответе запрещён, fallback к прежней паре нет;
- до проверки refs сервер проверяет уникальность всех canonical id и sequence;
  неизвестная sequence, bool/float вместо int, дубликат, неверная цитата или
  дополнительное поле отклоняют весь ответ;
- повтор sequence запрещён внутри одного массива refs; в разных массивах
  один и тот же фрагмент может подтверждать разные утверждения и поля;
- sequence не является индексом массива и не действует вне source revision/hash;
  полный lossless input, UUID, provenance и durable raw/validated calls сохраняются;
- после verifier только existing enrichment добавляет canonical id/time;
  publisher реконструирует обогащение из pinned source и сравнивает весь документ;
- каждый statement атомарен настолько, чтобы его части можно было сопоставить
  с 1–8 refs;
- refs совместно могут подтверждать составной тезис;
- решение дополнительно к `text` и `source_refs` содержит обязательные
  `acceptance_source_refs[1..8]` с репликами явного принятия/выбора;
- задача требует явного обязательства/назначения;
- owner и due имеют собственные refs;
- поздняя отмена, коррекция и переназначение определяют финальное состояние;
- сервер не ищет похожую sequence или цитату, не удаляет отдельные refs и
  не сохраняет частично подтверждённый составной тезис;
- сервер отклоняет весь документ при неверной форме, неизвестном поле,
  неверной ссылке/цитате, превышении лимита либо пустом содержании запрошенных
  executive summary/тем для пригодной встречи;
- отдельный exact-version verifier получает полный transcript и exact draft,
  возвращает SemanticVerification по data-model.md. Только валидный `pass`
  позволяет публикацию; `fail`, неизвестный исход и ошибка схемы сохраняют
  прежний accepted slot. Модельная проверка не заменяет приёмку Codex.

## Шаблоны и версии

Все встроенные профили создают полный protocol; их названия и идентификаторы
остаются прежними, меняются акценты, описания и текущая версия определения.
Выбор разделов личного шаблона сохраняется, пустые незапрошенные поля схемы
не выводятся. Порядок выбранных секций сохраняется в frozen template snapshot.

| Сохранённый выбор | Поля нового протокола |
| --- | --- |
| summary | executive_summary, objectives |
| key_points | topics |
| decisions | decisions |
| action_items | action_items |
| followups | next_steps |
| risks | risks_and_constraints |
| questions | open_questions |
| evidence | notes и необязательные точные выдержки |

Доказательные ссылки обязательны вне зависимости от выбора evidence. Этот
mapping переводит пользовательские предпочтения, а не старый flat payload.
Старый документ без protocol_json честно недоступен; не конвертируется и не
рендерится. Default и pinned share/slot FKs не переименовываются.

## Cabinet projection

Основной порядок:

1. название/дата/тип/участники из frozen header принятой ревизии;
2. `Ключевые итоги` как связный абзац с таймкодами рядом с тезисами;
3. `Цели встречи`;
4. `Ключевые обсуждения` с темами и непустыми подразделами;
5. `Принятые решения`;
6. `Задачи` таблицей;
7. `Открытые вопросы и следующие шаги`;
8. `Риски и ограничения`;
9. `Примечания`.

Каждый source button содержит канонические `data-seek-seconds` и segment id.
При отсутствии destination текст остаётся доступным, а нерабочая кнопка не
показывается.
Кнопка доступна с клавиатуры, имеет русское доступное имя и переводит фокус к
связанному сегменту расшифровки.

## Empty states

- решения: `Принятые решения в расшифровке не зафиксированы.`
- задачи: одна строка `Задачи не зафиксированы | Не назначен | Не указан`
- вопросы: `Открытые вопросы не зафиксированы.`
- непригодная речь: протокол недоступен с конкретным processing reason;
- исторический плоский результат: `Нужно сформировать новую версию итогов.`

## Markdown

Markdown передаёт тот же порядок и те же тезисы. Таймкод имеет вид `[MM:SS]`
или `[HH:MM:SS]` возле утверждения и содержит стабильную ссылку только когда
экспортный договор имеет допустимый URL; иначе остаётся текстовым временем.
Обычные точки, запятые, двоеточия, дефисы, скобки и кавычки не экранируются.

В тексте и заголовках экранируются обратная косая черта, backtick, `*`, `_`,
`[`/`]` и управляющие начала строк; HTML кодируется. В ячейках дополнительно
экранируется `|`, переносы нормализуются так, чтобы не создать новую строку
таблицы. Обычная пунктуация внутри предложения остаётся без backslash.
Серверный URL строится отдельно, percent-encoding применяется к значениям,
схема/host/путь не берутся из модельного текста. Ссылки из transcript не
становятся активными ссылками протокола.

## Все форматы и права

| Формат | Summary | Combined / transcript |
| --- | --- | --- |
| MD | Полная структура, task table, доступные источники рядом. | Та же summary плюс выбранная закреплённая расшифровка. |
| TXT | Та же структура простым текстом, задачи и текстовые времена. | Та же summary плюс transcript. |
| JSON | Versioned protocol snapshot, frozen header и разрешённые refs. | Раздельные source/summary revision и canonical turns. |
| XLSX | Тематические строки и задачи на листе итогов; не старые flat items. | Те же итоги и существующий лист transcript. |
| CSV / SRT / VTT | Существующее ограничение transcript-only сохраняется. | Без изменения transcript renderer и времён. |

`include_evidence=false` удаляет из каждой вложенной ветки экспортного
документа refs, quotes, source ids, ссылки и source excerpts; frozen body
не пересоздаётся. HTML escaping и spreadsheet formula safety сохраняются.
Доступ к summary не означает доступ к transcript/audio. Источник в кабинете
показывается интерактивно только при разрешённом destination той же ревизии.

Для owner/full-viewer экспорта добавляется same-origin маршрут перехода
`/cabinet/meetings/{meeting_id}/sources/{outcome_set_id}/{segment_id}`:
он повторно проверяет пользователя, текущие права, accepted/pinned outcome,
source revision и deletion fence, затем открывает нужный сегмент. Если
текущий detail не может показать старую закреплённую ревизию, маршрут честно
сообщает недоступность; не ведёт к похожему времени новой расшифровки.
Share links без прав на transcript не получают этот URL. Никаких bearer,
signed URL или токенов в ссылке. Plain timestamp остаётся при отсутствии
разрешённого destination. Browser QA обязателен для нового маршрута.

## Хеши, границы и переход со старых результатов

Порядок: frozen header/template/transcript → raw draft → strict validation →
independent verifier → server enrichment → canonical document hash → ledger и
outcome persistence → publication proof. Draft hash и окончательный document
hash различаются и явно связаны в proof с verifier call id/hash и source/root
hash; проверяемая публикация не хеширует лишь модельное тело без header/refs.
Изменение имени до/после acceptance или во время генерации не меняет snapshot:
требуется новый кандидат, stale-source правила блокируют публикацию старого.

Root bundle новой схемы закрепляет exact draft/verify children и digest версий
schema/validator/verifier/renderer и модельных настроек; runtime не смешивает
старый root с новым кодом. Старый незавершённый flat candidate не публикуется и
получает понятную причину необходимости новой генерации. Старые accepted slots
и pinned shares не переназначаются автоматически; без protocol показывают
«Нужно сформировать новую версию итогов». Новая проверенная версия замещает
только выбранный slot штатной атомарной операцией. Personal default сохраняется.

Config contract 5 един для generation, verifier, judges и reflection:

- обязательны `config_contract_version: 5`, `model` (непустой LiteLLM alias);
- необязательны `temperature` (конечное число 0..2), `top_p` (0..1),
  `reasoning_effort` (`none|minimal|low|medium|high|xhigh`), `max_tokens` либо
  `max_completion_tokens` (положительное целое, не оба сразу), `seed`
  (целое signed 64-bit); bool не считается числом;
- `response_format` — обязательная текущая strict schema для structured
  generation/verifier/judges, отсутствует у reflection. Control gate остаётся
  отдельным проверяемым полем. Иные ключи, credentials, base URL, заголовки,
  tools, routing/retry overrides запрещены;
- отсутствие параметра сохраняется отсутствием; ГРАФ не выбирает его default,
  не удаляет несовместимые настройки и не повторяет запрос с другими;
- runtime принимает только config 5. Шаблоны в коде задают текст и структурный
  договор, не модельные значения. CLI синхронизации требует exact numeric
  source version для каждого промпта, читает настройки из Langfuse, проверяет
  все кандидаты до первой записи и создаёт новые версии без deployment label.
  Отсутствующая/невалидная настройка блокирует синхронизацию. Старая source
  config может служить только источником явно сохранённых параметров при
  миграции; она не исполняется. Старое control-gate evidence не переносится
  на изменённый prompt/config.

Root `graf-outcome-root-bundle-v3` и export v2 не содержат route descriptor,
route hash, compiler attestation или provider/model allowlist. Exact child
versions/hashes и runtime hash сохраняются. Promotion/qualification/event
и полноценная LKG authority — обязательный целевой договор, но T065 выявил
отсутствующую реализацию (D239-P01, research.md); их сохранность нельзя
считать проверенным фактом. Старые roots/attempts/ledger не переписываются и не исполняются
как новый договор. Настройки pinned snapshot совпадают в HTTP request,
attempt metadata и generator hash; изменение/пропуск любого параметра, даже
с пересчитанным request hash, запрещает reuse/publish чужого ответа.

Шлюз использует обычный authenticated chat completions без специальных
`X-GRAF-*` headers и callback. `actual_model` из `response.model`,
`actual_provider` из явно сообщённых полей ответа; иначе null. Эти значения
сверяются с сохранённым хешированным raw response, не с allowlist и не с
запрошенным alias. HTTP/JSON/schema, finish/refusal, timeout/ambiguous,
source/access/deletion и publication checks не ослабляются.

Доставка исторических observations является чтением сохранённой записи,
не новым исполнением или публикацией протокола: проверяются прежние хеши
request/transcript/raw/result и передаются сохранённые nullable actual поля.
Она не требует текущего root/config и не применяет новую сверку raw-body
provenance к старым calls, где actual поля пришли только из headers.
Новые вызовы сверяют body/provenance при сохранении и перед публикацией
нового протокола; общая функция проверки хешей retained delivery не получает
этого нового условия. Исторический call не допускается к новому inference
или publication посредством observation-only пути, его JSON/hashes и
provider/model не переписываются.

Актуальная граница — проверенный PR без merge/release/deploy и без изменения
production labels/LiteLLM. Прежнее разрешение на предварительный выпуск было
ошибочно истолковано и отменено уточнением владельца. Ни технический PR #6661,
ни синтетический smoke не заменяют реальную приёмку протоколов по FR-028.
Следующий порядок — инструкция для отдельной задачи общего выпуска, не
разрешение исполнять его здесь. После её release-gates нужен согласованный
короткий перерыв AI: остановить приём и
dispatch generation/optimizer/evaluation, завершить либо явно закрыть текущие
попытки; переключить GRAF + новый root/LKG и убрать callback/регистрацию/env
на LiteLLM; проверить синтетические вызовы и затем возобновить AI. Проверить
metadata ACL ключа на отсутствие второго ограничения одной моделью, не
меняя auth/бюджеты/провайдерские ключи. Одностороннее удаление ломает контракт
старого GRAF и старого hook. Исторические образы/конфигурация могут служить
согласованному операционному откату, но в новом коде нет совместимой ветки.

Корневой набор квалифицируется под фактический объединённый runtime общего
выпуска: `runtime_contract_hash` включает исходники генерации, проверки и
отображения. Слияние других фич может изменить этот хеш. Перед активацией
оператор пересчитывает его на замороженном кандидате, сравнивает с выбранным
root и при различии создаёт и проверяет новый exact root. Старый root нельзя
просто продвинуть по названию фичи или результату проверки другой ветки.
Несовместимость должна остановить AI, а не включить старый формат.

Ни одна стадия не усекáет вход или вывод. Обрезанный ответ/исчерпанный лимит
не публикуется, а отражается как незавершённая генерация. Полный сериализованный
запрос (prompt + schema + transcript + draft для verifier), usage, latency и
finish reason фиксируются в private ledger. Лимиты gateway и 100 тем/500 тезисов
— fail-closed границы, не критерий исключения встречи; если они мешают полной
обработке выборки, до PR меняется общий pipeline и повторяется весь выбранный объём.

## Допуск корневого комплекта F239 и dev

Это отдельный закрытый договор F239 по Конституции III. Он не заявляет
соответствие будущим схемам F183/194/195/200 и не переносит их calibration,
canonical-artifact или dispatch архитектуру. Ссылки на операторские артефакты
имеют ровно `artifact_id`, `schema_version`, `artifact_version`, `hash`.
ID адресует строку `PromptRootPromotion`, тип схемы — конкретное поле этой
строки; неизвестный тип/версия отклоняется. Хеш — SHA-256 canonical JSON;
загрузчик проверяет и использует одно прочитанное тело, без повторного чтения
после проверки. Целостность не заменяет право создавать операторские записи.

Полные тела хранятся в одной операторской таблице, а не универсальном реестре:

- `Activation`: версия схемы, runtime hash, точная упорядоченная тройка ролей
  extraction/synthesis/verification и разрешённые для каждой роли имена prompts.
  Модельные настройки здесь отсутствуют. Activation создаётся до root;
  root закрепляет полное тело и его hash. Все имена children и их exact
  version/hash/config находятся в root export.
- `CandidateRoot`: имя и numeric version root, полные typed bindings на root
  export и Activation. Экспорт содержит полные тексты/configs всех children.
- `Qualification`: CandidateRoot, полный окончательный metadata-only отчёт
  оценки и его hash, контрольные проверки, проверка приватности, имя/время
  разрешения оператора, ожидаемое исходное состояние и операционный откат.
  Отчёт связывает run/root/runtime, полную инвентаризацию, пригодные и
  исключённые meeting/source IDs, output hashes и все 14 критериев FR-029.
  Пропущенный, failed, ambiguous либо неполный элемент не допускает PASS;
  причины исключения проверяются действующим evaluator. Контрольные сценарии
  включают разговорное принятие срока и настоящий отказ/условие. Тексты,
  имена участников и содержательные review notes в отчёт не включаются.
- `PromotionEvent`: ID операции, оператор/время, Qualification binding,
  ожидаемое исходное состояние, CandidateRoot цели и фактического read-back,
  `result=pass`. Цель и read-back должны совпасть полностью. Qualification и
  Event находятся вне уже хешированных root/Activation; цикла нет.
- `ProductionAuthority`: вид `production`, CandidateRoot и успешный Event
  binding. Каждый loader повторно проверяет все связанные тела и их равенство.
- `EvaluationAuthority`: вид `evaluation`, exact root/Activation, run id,
  точные имена изолированных БД/очереди и `publication_sink=evaluation_only`.
  Она не содержит Event и никогда не заменяет ProductionAuthority.

EvaluationAuthority создаётся **до первого вызова**, без Qualification и без
операторской строки. Полный export/Activation с хешами хранится в неизменяемом
run-owned снимке изолированного контура оценки; attempt/calls закрепляют этот
снимок. Evaluation loader перечитывает именно его, проверяет изоляцию и все
хеши, не обращается к production-журналу или LKG. После оценки операторская
строка связывается с ним по project/root name/numeric version/export hash/
activation hash/runtime hash, а не по ещё не существовавшему ID строки.

Qualification создаётся только операторским путём, который непосредственно
вызывает существующий `finalize_run` с доступом к изолированному run и
read-only источнику. Приём произвольного JSON с PASS, даже с пересчитанными
хешами, запрещён. Финализатор повторяет полную инвентаризацию, сверяет каждую
review с текущим source, конкретным output и полной цепочкой calls, используя
общую publication validation без публикации. Неполные, чужие, изменённые
или failed/ambiguous результаты отклоняются. Контрольные прогоны проверяются
тем же способом; переданный CLI boolean не заменяет эти проверки.

Окончательный metadata-only отчёт имеет закрытую версионированную схему:
`schema_version`, `run_id`, `project_id`, `root_name`, `root_version`,
`root_export_hash`, `activation_hash`, `runtime_hash`, `cutoff_at`,
`inventory[]` (meeting_id/source_hash/selection_status), `reviews[]`
(meeting_id/source_hash/candidate_id/output_hash, точные три call_id и
validated_result_hash, 14 verdicts по фиксированным ключам FR-029),
`exclusions[]` (meeting_id/source_hash/reason), `controls[]`
(case_id/candidate_id/source_hash/output_hash/call bindings/verdict),
`privacy` (checked_at/reviewer/verdict), `complete`, `errors`.
Обязательные controls: informal_commitment, conditional_commitment,
refused_commitment, third_party_guess, later_correction, prompt_injection,
unknown_owner_and_due. Контрольные cases — общие синтетические сценарии,
не копии частных встреч. Каждый control требует `pass`; все reviews требуют
14 pass; `errors` пуст, `complete=true`, reviewed/excluded вместе без повторов
покрывают заявленный объём приёмки. Полный режим покрывает весь cutoff inventory;
`representative` требует ровно три закреплённые реальные встречи (одна ≥3600
секунд) и те же семь controls. Полный inventory не обрезается; невыбранные
встречи учитываются как `not_evaluated`, не как исключения или PASS. Manifest
выборки и его hash связаны с EvaluationAuthority до первого egress, источники
и exact root/runtime не заменяются задним числом. `complete` означает завершение
этого заявленного объёма, а не проверку всех встреч. Exact project/root/version/export/activation/
runtime отчёта равны CandidateRoot. Приватность проверяет Codex по процедуре
quickstart; приватные заметки не включаются. Только проверенный финализатором
отчёт сохраняется полным в операторской строке и переживает очистку временных
заметок. Дополнительная подпись, новый реестр и сервис для этого не нужны.

Приёмка по указанию владельца от 2026-09-07 оценивает существенные ошибки.
Стиль, повторы, необязательные подробности и отсутствие дублирования однозначного
контекста имени/предмета не являются причиной `fail`. Неверное утверждение,
неподтверждённое решение/задача/исполнитель/срок, пропуск, меняющий результат или
следующее действие, и неверные источники остаются блокирующими. Сервер не
редактирует слова или ссылки, а проверка schema/sequence/quote/revision не меняется.

`PromptRootPromotion` принадлежит операторскому maintenance-пути: worker и
HTTP-пользователь имеют только чтение, обычные workspace admins не получают
прав записи. Полные подготовленные root/Activation/Qualification неизменяемы
после создания; Event записывается ровно один раз. Ограничения БД запрещают
перезапись финализированных тел и обеспечивают не более одной незавершённой
операции и одной `is_current` строки на Langfuse project/root. Привязка проекта
проверяется оператором по настроенным credentials без сохранения ключей в
журнале. Текущая строка и её полный export являются единственным LKG;
runtime не записывает LKG и не использует прежний MinIO `last-known-good.json`.

Один root writer использует PostgreSQL advisory lock на project/root/label.
Он проверяет текущий numeric root и квалификацию, долговечно сохраняет начало
операции перед единственным `update_prompt`, затем проверяет exact read-back.
Event и смена `is_current` фиксируются одной транзакцией. Повтор завершённой
операции возвращает её Event и не двигает метку снова, даже после другого
выпуска. Сбой после возможной отправки даёт `reconciliation_required`:
никакого слепого повторного update. Другой writer не начинает переключение,
пока состояние не разобрано оператором. При отмене уже начатый сетевой поток
дожидается завершения до освобождения lock. Read-back target сам по себе
не доказывает авторство операции и не создаёт Event автоматически после
неоднозначного исхода. Подтверждение защиты production label и единственного
владельца mutation credential — обязательные отдельные операторские сведения
с методом, временем и результатами проверки; CLI boolean не является evidence.

Первое включение явно имеет `initial_activation`: предыдущего допуска в
журнале нет; ожидаемая внешняя метка и её numeric version фиксируются без
выдуманного прошлого Event. Нужны тот же полный отчёт и отдельное разрешение
оператора. Операционный безопасный выход первого включения — отключить новую
AI-генерацию, сохранив запись, расшифровку и ранее принятые данные; это не
обещание отката на старый root и не рабочая legacy-ветвь. Последующие операции
могут ссылаться только на реальный прежний допуск, совместимый с runtime,
либо на такую же явную остановку AI. Настоящее первое включение и любые
перемещения `production` выполняет отдельная задача выпуска, не этот PR.

Runtime закрепляет допуск на attempt до первого egress. Каждая GenerationCall
содержит полное `execution_authority_json/hash` отдельно от запроса LiteLLM;
authority не отправляется модели и не становится HTTP-заголовком. До каждой
стадии, reuse и publication production-цепочка перечитывается из операторского
журнала, evaluation-цепочка — из run-owned снимка, описанного выше.
Смена текущего допуска не меняет уже закреплённый совместимый комплект.
Отсутствующая/подменённая связь блокирует исполнение. Недоступный Langfuse или
постороннее перемещение метки не заменяет допуск: разрешён только проверенный
LKG журнала с совместимым runtime; иначе AI ждёт, запись/расшифровка продолжаются.

`dev` — только удобный selector root перед всем изолированным прогоном. После
первого разрешения он сохраняет numeric root/Activation и не перечитывается
для следующих встреч или при повторе. Полная проверка БД/очереди/источника
остаётся в общем исполнителе. Тестовый authority и результат не могут изменить
production журнал/LKG, accepted slots прода или метку `production`.

Продвижение и откат отдельных children, в том числе control prompts,
оптимизатором удаляются. Оптимизатор создаёт только непомеченные кандидаты;
их включение требует нового полного root и того же допуска. Исторические
observations и callbacks завершённых histories не запускают новый inference
и не авторизуют публикацию. Журнал и call authority сохраняются по политике
наблюдаемости, не удаляются при удалении встречи. Новых сервисов, секретов
провайдера, списков моделей и правил LiteLLM нет.

## Приватность пользовательского документа

Candidate доступен только владельцу. Summary-only/share/export читают только
accepted slot и закреплённую source revision. Ordinary logs, committed fixtures,
GitHub issues и PR не содержат transcript/protocol text реальных встреч.

`deletion/service.py::_purge_meeting_outcomes` обязан очищать protocol_json,
frozen header и новые content fields кандидата, учитывать NOTES_SUMMARY,
сохраняя штатную очистку исторических items. Обычное, повторное удаление и гонка
с публикацией дают одинаковую правду. Generation Call, Langfuse и Temporal
сохраняются отдельно по observability policy; их сохранность не считается
ошибкой purge. Оценочные рабочие копии учитываются по quickstart §5.
