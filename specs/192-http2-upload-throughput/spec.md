# Feature Specification: Быстрая загрузка файлов через production edge

**Feature Branch**: `codex/192-http2-upload-throughput`

**Created**: 2026-08-23

**Status**: Draft

**Input**: Сохранить подтверждённое ускорение загрузки файлов в репозиторной конфигурации, не меняя существующую серверную архитектуру загрузки.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Быстрая загрузка записи (Priority: P1)

Пользователь с быстрым интернет-соединением загружает большую запись в GRAF и не сталкивается с искусственным ограничением скорости со стороны production edge.

**Why this priority**: Медленная передача увеличивает ожидание почти в 12 раз и задерживает весь последующий цикл обработки встречи.

**Independent Test**: Загрузить через реальный встроенный клиент файл около 40 МБ по ранее воспроизведённому каналу с задержкой около 165 мс и сравнить время передачи с зафиксированным baseline.

**Acceptance Scenarios**:

1. **Given** production-путь загрузки и канал с RTT около 165 мс, **When** пользователь загружает файл около 40 МБ через основной протокол клиента, **Then** чистая передача завершается не дольше 15 секунд и не ниже 30 Mbit/s.
2. **Given** существующая серверная обработка загрузки, **When** ускорение включено, **Then** запрос по-прежнему проходит через GRAF API, а сохранение объекта, запись в БД и финализация продолжают работать без изменения контракта.
3. **Given** повторная установка edge-конфигурации из репозитория, **When** установочный скрипт применяет source-of-truth, **Then** подтверждённая настройка пропускной способности не теряется.

### Edge Cases

- Настройка должна оставаться ограниченной 2 МБ дополнительной preread-памяти на один активный HTTP/2 request stream и не вводить неограниченное буферирование тела запроса.
- При ошибке проверки конфигурации или reload должен сохраняться существующий автоматический rollback установочного сценария.
- Клиенты, использующие альтернативный поддерживаемый протокол, не должны терять совместимость.
- Улучшение не должно ослаблять лимит размера файла, аутентификацию, авторизацию или серверную валидацию загрузки.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Репозиторный source-of-truth production edge MUST сохранять подтверждённую настройку, устраняющую ограничение скорости основного протокола загрузки на соединениях с высоким RTT.
- **FR-002**: Установочный сценарий MUST повторно применять ускоренную конфигурацию без ручного hotfix после каждой установки или восстановления edge.
- **FR-003**: Загрузка MUST оставаться server-mediated через существующий GRAF API с неизменными проверками доступа, лимитом размера и финализацией.
- **FR-004**: Решение MUST иметь ограниченный и явно зафиксированный верхний предел 2 МБ дополнительной preread-памяти на активный HTTP/2 request stream.
- **FR-005**: Существующие проверки конфигурации, reload и автоматический rollback MUST оставаться действующими.
- **FR-006**: Изменение MUST быть отражено в журнале операций проекта.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Реальная загрузка файла около 40 МБ через встроенный клиент на измеренном канале с RTT около 165 мс передаёт тело запроса не дольше 15 секунд и со скоростью не ниже 30 Mbit/s.
- **SC-002**: Полное время реальной загрузки файла около 40 МБ улучшается не менее чем в 8 раз относительно зафиксированного baseline 97,6 секунды на том же production-маршруте.
- **SC-003**: После применения source-of-truth health и readiness остаются успешными, а загрузка завершается штатным ответом без изменения API-контракта.
- **SC-004**: Повторный dry-run установочного сценария подтверждает использование репозиторной edge-конфигурации и сохранение штатных проверок и rollback.

## Assumptions

- Production-диагностика уже локализовала причину в слишком малом окне чтения тела запроса основного протокола, а не в провайдере, VPN, диске, объектном хранилище или БД.
- Подтверждённый bounded размер окна — 2 МБ на активный поток, что даёт достаточный запас для измеренного bandwidth-delay product без архитектурной перестройки.
- Прямые загрузки в MinIO, presigned URLs, новые CORS-правила, собственный chunk scheduler и изменение API-контракта находятся вне scope.
- Production hotfix уже прошёл синтаксическую проверку, reload без рестарта master-процесса, health/readiness и реальную загрузку через встроенный клиент.
