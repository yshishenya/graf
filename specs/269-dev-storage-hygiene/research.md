# Research: Гигиена дискового пространства Dev-стенда и ускорение CI

**Feature**: 269-dev-storage-hygiene | **Date**: 2026-09-16

## R1. Политика хранения локальных артефактов

- **Decision**: Хранить набор артефактов только для: (а) активного манифеста — его приложение (`GRAF Dev.app`), нужное для будущего отката поколения «активный → его родитель»; (б) родительского (целевого для отката) манифеста — архив образов `runtime-images.tar` плюс приложение. Каталог сборки `build/` удаляется сразу после успешной сборки — он не участвует ни в promote, ни в rollback (проверено: promote/rollback читают только app bundle через `_checked_app_bundle`, `GRAF_DEV_BUILD_DIR` используется исключительно сборщиком).
- **Rationale**: В `promote`/`rollback` приложение устанавливается из артефактов *целевого* манифеста. Активный набор на диске нужен как будущий целевой для отката; освобождать его нельзя. Один `tar` (~1.7 ГБ) + два app bundle (~46 МБ) дают стабильный потолок вместо линейного роста.
- **Alternatives considered**: (1) Хранить N последних — линейный рост, отклонено пользователем. (2) Совсем без архивов — требует менять контракт F229 «восстановление только из immutable образов» и допускать пересборку вместо точного ID; отклонено. (3) Сжатие архива — экономия ~0.7–1 ГБ, но добавляет CPU/время в сборку и распаковку в `rehydrate`; отклонено пользователем при выборе «один несжатый архив».

## R2. Момент создания архива

- **Decision**: Архив создаётся в `promote --live` для нового целевого отката (прежнего активного манифеста), а не в `build`. При каждом успешном promote архив целевого перезаписывается/создаётся, архив прежнего целевого удаляется. `build` больше не пишет `runtime-images.tar` вовсе.
- **Rationale**: Образы прежнего активного манифеста гарантированно присутствуют в Docker в момент promote (контейнеры только что работали). Это исключает ситуацию «build сделал 1.7 ГБ архив для кандидата, который никогда не будет продвинут».
- **Alternatives considered**: Ленивый архив по запросу `rehydrate` — к моменту запроса образы уже могут быть потеряны, восстановление невозможно. Архив в `build` — текущее поведение, источник утечки.

## R3. Освобождение образов и тегов удалённых кандидатов

- **Decision**: Для каждого манифеста, покидающего политику хранения, снимаются теги `graf-dev-immutable:<manifest>-*` через `docker image rm <tag>`; образ удаляется, если на него нет других ссылок. Активный и целевой манифесты не затрагиваются. Глобальные `docker system prune` / `image prune -a` не вызываются.
- **Rationale**: Сейчас накоплено 1080 immutable-тегов; теги удерживают слои. Точечное снятие безопасно и сохраняет активные образы проверяемыми (`docker image inspect` по digest).
- **Alternatives considered**: Глобальная чистка Docker — риск удалить образы активного стенда; отклонено. Оставлять теги — рост продолжается.

## R4. Жизненный цикл снапшотов перехода схемы

- **Decision**: Каталог `schema-transactions/<operation>` удаляется в момент перехода журнала в фазу `complete` или `recovered` (единая точка — `_schema_phase`). Незавершённые фазы сохраняют снапшоты. Операция `prune` удаляет каталоги, не совпадающие с operation_id незавершённого журнала.
- **Rationale**: Снапшоты нужны только для восстановления незавершённого перехода (2.2 ГБ накоплено после завершённых). Единая точка гарантирует отсутствие пропусков на обоих путях завершения (`operation_promote` и `_schema_resume`).
- **Alternatives considered**: Хранить последний завершённый снапшот для аудита — не требуется; журнал сохраняет метаданные, а холодные копии не являются evidence.

## R5. Очистка остаточных копий приложения

- **Decision**: Операция `prune` под общим state lock удаляет `transactions/previous-*.app`. Поскольку lock исключает одновременную операцию, любая найденная копия — остаток прерванного процесса.
- **Rationale**: Существующий код удаляет копию после успеха; утечка возникает только при убитом процессе (найдено 2 копии, 43 МБ).
- **Alternatives considered**: TTL по времени — сложнее и не нужен при наличии блокировки.

## R6. Swift-кэш в GitHub Actions

- **Decision**: В `macos-pr.yml` и `release-full.yml` (job `macos-full`) добавить `actions/cache@v4`:
  - пути: `apps/macos/.build`, `~/.cache/org.swift.swiftpm`, `~/Library/Caches/org.swift.swiftpm`;
  - ключ: `swift-${{ runner.os }}-${{ runner.arch }}-spm6.0.3-${{ hashFiles('apps/macos/Package.resolved') }}-v1`;
  - `restore-keys`: префикс без хэша `Package.resolved`.
  - Промах кэша не меняет шаги: те же `swift build`, `run-swift-tests.sh`, `ContractValidation`.
- **Rationale**: Единственная внешняя зависимость — Sparkle (pinned в `Package.resolved`), остальное — собственный код. Стандартная практика GitHub для SwiftPM: кэшировать `.build` и глобальные кэши пакетов; инвалидация по `Package.resolved` и версии инструмента. Версия Swift закреплена в workflow (`6.0.3`), поэтому входит в ключ. `v1` в ключе — ручной сброс при изменении состава кэша.
- **Alternatives considered**: Кэшировать только `.build/checkouts` и `repositories` — ускоряет только разрешение зависимостей, не компиляцию (основная стоимость). `--cache-path` — кэширует только module cache. Без кэша — текущее состояние.

## R7. Привязка доказательств к продуктам сборки

- **Decision**: В `ci-local.sh` заменить `--artifact macos-build=<весь .build>` на явные продукты: `macos-products` — список `apps/macos/.build/debug/TwoBrainRecApp`, `ContractValidation`, `MeetingMuteTruthRuntimeProof`, `WebRTCAEC3Validation`, `LeakageValidation` (файлы, если существуют) и `TwoBrainRecMacOSPackageTests.xctest` (бандл). Для каждого существующего пути добавляется отдельный `--artifact` с именем вида `macos-product-<name>`.
- **Rationale**: Доказательство должно привязываться к тому, что реально собрано и проверено. Полный `.build` содержит промежуточные объектные файлы, `ModuleCache`, `index`, а также посторонние локальные каталоги (`installer-cache`, `notary`), которые не являются результатом CI и создают шум в диджестах. Чтение 1.7 ГБ заменяется на ~100 МБ.
- **Alternatives considered**: Хэшировать только `ContractValidation` (узко); хэшировать `Package.resolved` (не подтверждает сборку); оставить весь `.build` (медленно и шумно).

## R8. Новая операция `prune` и наблюдаемость

- **Decision**: Добавить подкоманду `prune [--dry-run] [--json]` в `scripts/dev-harness.py`; под общим lock она: проверяет отсутствие незавершённого перехода схемы и `rollback-required.json`; удаляет артефакты вне политики; снимает теги/образы; удаляет снапшоты завершённых переходов; удаляет остаточные копии приложения; печатает JSON-квитанцию (`removed`, `bytes_freed`, `kept`, `status`, `partial_reasons`). Ошибки Docker переводят квитанцию в `partial`, но не отменяют удаление файлов. `status` дополняется блоком `retention` (active, rollback_target, суммарные байты артефактов — без вызовов Docker).
- **Rationale**: Требования FR-009/FR-010 и наблюдаемость SC-006; dry-run обязателен для безопасной эксплуатации. Lock уже существует и сериализует операции.
- **Alternatives considered**: Только автоматическая уборка без команды — оператор не сможет разобрать инцидент или освободить место без новой сборки. Отдельный скрипт — дублирование контрактов и проверок.

## R9. Автоматическая уборка без изменения контракта manifest

- **Decision**: Схема манифеста (`infra/dev/manifest.schema.json`) и формат `runtime-images.tar` не меняются. Меняется только *набор* хранимых каталогов и момент записи архива. `rehydrate` продолжает работать для целевого манифеста; для манифеста вне политики возвращает явную ошибку «immutable Dev image archive is unavailable; rebuild a new candidate».
- **Rationale**: Минимизирует риск для F229-контрактов и существующих тестов; обратная совместимость с ранее записанными манифестами.
- **Alternatives considered**: Добавлять в манифест поле `archive_state` — лишнее состояние, которое может рассинхронизироваться.
