## Technical Context

**Language/Version**: Python >=3.12 (сервер; локальное окружение 3.13), Bash 3.2+ (штатные скрипты).
**Primary Dependencies**: stdlib, существующие pytest/uv; новых зависимостей нет.
**Storage**: только временный изолированный PostgreSQL из штатного runner.
**Testing**: существующий test_ci_cd_contract.py и оба календарных файла.
**Risk / Validation Lane**: active-spec-slice с полными воротами significant-feature;
общий выбор и исполнение проверок затрагивает несколько модулей, использует Docker/Postgres.
**Release Gate**: без deploy; перед merge три обязательных exact-SHA PR checks;
перед отдельным выпуском frozen release-full и разрешение пользователя.
**Target Platform**: macOS/Linux, штатные локальные CI команды.
**Project Type**: внутренние скрипты проверки репозитория.
**Performance Goals**: не добавлять повторный запуск полного calendar integration;
существующий serial_performance порог обязателен, новых обещаний ускорения нет.
**Constraints**: общий Dev не менять; не копировать зависимости; малые проверки
используют уже установленное окружение и образ Postgres, при завершении cleanup.
**Scale/Scope**: одна дополнительная группа, три изменяемых файла кода/тестов.

## Phase1 / Design

1. `scripts/ci-behavior-tests.py`: добавить calendar-auto-context для календарного
   каталога, API, модели, миграции0021 и самих mapped tests. Группы кабинета
   ограничить их областью: прежнее shared условие не должно выбрать новый календарь.
2. Список tests/covered_tests — объединение без повторов, прежняя проверка
   существования/AST/containment сохраняется для каждой выбранной цели.
3. При наличии calendar integration `execute` вызывает существующий
   `run_local_postgres_tests.sh --focused` без partitioned: одна последовательная
   pytest выборка, один JUnit, реальные миграции/RLS, required performance gate.
   PYTEST_ADDOPTS сбрасывается; addopts пуст; пропуски/деселекция файлов проверяются
   прежним check_execution. Без календаря прежний Python/Node путь сохраняется.
4. `infra/scripts/ci-local.sh`: полные behavior targets исключаются из changed_tests;
   наличие целого calendar integration в них покрывает отдельный performance этап.
   Остальные unit/component/static gates не отменяются.
5. JSON environment отражает PostgreSQL/Docker только для календарной выборки;
   coverage остаётся partial, changed_paths и diff_available сохраняются.

## Самостоятельная US3 / #6907 — 2026-10-23

Lane: active Spec Kit slice, CI tooling с изолированным Docker/PostgreSQL;
продуктовые данные и deployment не затрагиваются. Constitution check до Phase0:
PASS — используются существующие локальные runner/fixtures и обычные PR gates,
не меняются доступ/RLS, миграции продукта или правила выпуска.

Исследование текущих callers: все режимы runner завершаются через один trap
cleanup, включая setup/collection/phase failure, SIGINT/SIGTERM. CI вызывает
runner как отдельный процесс и получает его итоговый код. 85 contract-проверок
PASS и два настоящих PG-прогона 68/68 PASS обнаруженную ошибку не покрывают:
`docker rm` внутри cleanup подавляется и выдаётся ложное подтверждение удаления.
Отдельный управляемый контроль на настоящем скрипте воспроизвёл это поведение.

Минимальное исправление: в существующем cleanup проверить исход удаления
собственного контейнера. Только успешная команда печатает прежний removed;
ошибка печатает failed, делает успешный общий результат неуспешным и сохраняет
уже существующий ненулевой код. Не добавлять повторный runner, удаление по
префиксу, новые зависимости или общий менеджер контейнеров.
Второй вызов удаления находится в повторной подготовке PostgreSQL: при отказе
нельзя сбрасывать container_started и продолжать подготовку. Остановить запуск,
сохранив владение контейнером для общего cleanup; не скрывать ошибку удаления.

Проверки до/после: закрепить управляемый отказ Docker в существующем
`test_local_postgres_test_runner.py`, включая исходный success/failure/signal;
полный runner contract, включая subprocess-проверки plugin; те же два реальных изолированных
PG-прогона workers1/2 после исправления, сбор case IDs из штатных JSONL,
одинаковая выборка, ровно одно исполнение, strict/performance/parallel,
обязательный порог скорости и отсутствие своих контейнеров после завершения.
Файлы: runner, его существующий contract, текущие документы F263 и fragment.

До реализации: новый reviewer-owned runner checklist, независимый обзор всех
применимых checklist, analyze и live сверка существующей #6907. Исторические
задачи и исходные описания не переписываются; T006–T008 пока открыты.
US2 и её утраченный baseline не принимаются по новому набору US3. Два запуска
не являются измеренной медианой; полный CI/релиз остаются отдельными этапами.

Constitution check после Phase1: PASS — исправляется правдивость результата
существующего тестового процесса; изоляция, секреты, worker-БД, product/release
гейты сохранены. Перед merge обязательны три точных GitHub checks и общий
валидатор SHA/основы. Для closeout применим штатный live validator после merge.
