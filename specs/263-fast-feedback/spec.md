## User Scenarios & Testing

### User Story 1 — Читать применимые требования (Priority: P1)

Разработчик читает целые релевантные разделы с зависимостями и сохраняет все
ограничения. Независимая приёмка: известная область, пересечение областей,
неизвестная область и изменение принципа; при неопределённости чтение расширяется.

### User Story 2 — Не создавать ненужные встречи в тесте (Priority: P1)

В четырёх исходно согласованных тестах одна эквивалентная готовая встреча
заменяет пять, без удаления assertions, аудио и отрицательных контрольных данных.
Независимая приёмка: одинаковый набор, три до и три после при одном worker,
условия и медианы. Оригинальные node IDs пока неизвестны, работа не принята.

### User Story 3 — Запускать каждую выбранную проверку один раз (Priority: P1)

Разработчик получает настоящую выборку pytest и непересекающееся разбиение;
strict имеет приоритет. PostgreSQL, миграции, RLS и отдельные worker-БД сохраняются.
Независимая приёмка: ошибки, пустота, cleanup, два независимых запуска,
отдельные измерения workers=1/2. Похожие результаты F211 — материал сверки.

### User Story 4 — Выбирать проверки поведения календаря (Priority: P1)

Изменение реализации календаря выбирает уже существующие проверки контракта
и интеграции, даже когда сами тесты не менялись.

**Why this priority**: сейчас изменение matching.py не выбирает эти проверки
через общую карту поведения; пользователь получает неполную целевую проверку.

**Independent Test**: реальный `--plan` выбирает оба файла для matching/API/model;
`--focused` исполняет оба файла с изолированным PostgreSQL. В смешанном `--fast`
каждый целый файл принадлежит одному этапу, отдельный performance этап не дублирует
уже исполненный целиком integration-файл; порог скорости календаря обязателен.

**Acceptance Scenarios**:

1. При изменении matching/API/model выбираются оба существующих файла проверки.
2. При смешанном изменении календаря и кабинета выборка объединяется без дублей;
   unit/changed/component проверки сохраняются, затронутый тест не исполняется дважды.
3. Удалённый, пустой, синтаксически неверный или выходящий через symlink за репозиторий
   обязательный файл вызывает ошибку до запуска. Пропуск или исключение выбранного
   файла при pytest не дают PASS; ненулевой код runner передаётся наружу.
4. При rename учитываются оба пути. Неизвестные и общие пути остаются в отчёте;
   отсутствующая база сравнения не превращается в полное покрытие.
5. Изменение только кабинета не добавляет календарь, PostgreSQL или Docker.

### Edge Cases

Дубли путей; удаление/переименование mapped source/test; смешанные группы;
covered целым файлом или каталогом; отсутствующий Node/runtime/Docker;
pytest filters/skips; недоступный diff; ошибка обязательной проверки скорости.

## Requirements

### Functional Requirements

Нумерация ниже реконструирована по диапазонам ссылок issues; текст оригинала
не восстановлен и за оригинал не выдаётся.

- **FR-001**: чтение сохраняет все применимые требования и общие gates.
- **FR-002**: выбираются целые разделы и их зависимости, а не случайные строки.
- **FR-003**: пересекающиеся/неизвестные области расширяют чтение.
- **FR-004**: изменение принципа требует конституции; исторические ссылки сохраняются.
- **FR-005**: упрощение fixtures ограничено четырьмя исходными тестами.
- **FR-006**: ready-встреча, аудио, assertions и отрицательные объекты эквивалентны.
- **FR-007**: измерения подготовки данных отделены от эффекта числа workers.
- **FR-008**: настоящая выборка subprocess исполняется ровно один раз.
- **FR-009**: разбиение непересекающееся, strict имеет приоритет, workers ограничены.
- **FR-010**: настоящие PostgreSQL/миграции/RLS и worker-БД сохраняются.
- **FR-011**: ошибки/пустота/cleanup не дают ложного PASS; нужны два независимых запуска.
- **FR-012**: matching/API/model календаря добавляют существующие contract/integration
  проверки поведения к остальным выбранным проверкам.
- **FR-013**: объединение без дублей; отсутствующий/непригодный mapped test — ошибка.
- **FR-014**: unknown/shared/rename и недоступный diff честно отражены;
  частичная карта не является полным CI и не отменяет unit/component/release gates.
- **FR-015**: независимое ревью, analyze, целевые проверки, converge и точный SHA CI
  подтверждаются отдельно; новые commit/merge/release требуют соответствующих разрешений.
- **FR-016**: validation содержит факты и пробелы, а changelog — только фактический результат.

### Key Entities

Изменённый путь; группа существующих проверок; набор неповторяющихся файлов;
запись выбранных/уже покрытых файлов; результат фактического исполнения.
Пользовательские данные и модель продукта не меняются.

## Success Criteria

### Measurable Outcomes

- **SC-001**: четыре сценария чтения сохраняют все применимые gates, объём чтения измерен.
- **SC-002**: одинаковые четыре исходных теста сохраняют проверки, медианы трёх
  запусков до/после при одном worker записаны; неизвестный исходный набор не принимается.
- **SC-003**: исходная выборка равна непересекающемуся объединению групп;
  два независимых запуска успешны, workers1/2 измерены отдельно, ошибочные случаи отказаны.
- **SC-004**: каждый matching/API/model выбирает оба обязательных файла, смешанный
  набор не содержит повторов; все отрицательные сценарии US4 отказаны;
  фактический запуск обоих календарных файлов проходит с обязательным порогом скорости.

## Уточнение US1 — повторное чтение, 2026-10-16

Критических вопросов для этой ограниченной части нет: обязательное первое
полное чтение документов из AGENTS.md сохраняется. Оптимизируется только
повторное чтение уже полностью прочитанного документа в том же диалоге при
подтверждённом неизменном содержимом. Сохранённая память, краткий пересказ,
результат другого агента или другого диалога полного чтения не заменяют.

FR-001–004 и SC-001 для US1 уточняются так:

- Известная область: после первого полного чтения можно использовать его
  результат, если путь и SHA-256 всех использованных документов совпадают.
  Применимые инструкции, контракты и зависимости читаются целыми разделами.
- Пересечение областей: добавить все инструкции и зависимости новой области;
  прежнее чтение нельзя считать достаточным только по совпадению имени файла.
- Неизвестная область или сомнение в полноте прошлого чтения: полностью
  перечитать конституцию, PRD, текущий статус и product-gates; определить область
  до изменений. Нет подтверждённого хеша — нет повторного использования.
- Изменение принципа: полностью перечитать те же четыре документа и выполнить
  отдельный путь изменения конституции; повторное использование не применяется.
- Изменённый, отсутствующий или нечитаемый документ нельзя объявлять
  прочитанным по старому хешу. Изменённый обязательный документ читается полностью.
- После сжатия истории до пересказа или потери полного содержания чтение
  повторяется. Совпадение хеша не доказывает сохранение требований в контексте.
- Выбор активной фичи, ветки и точного SHA по существующим правилам не меняется.
- Ссылки и содержимое исходных документов не меняются. Для четырёх сценариев
  записываются фактические байты чтения и список сохранённых ограничений;
  экономия относится только к повторному чтению, а не к первому входу в проект.

US1 не зависит от утраченных четырёх тестов US2: данные, исполнение тестов и
продукт не меняются. Перед T003 нужны самостоятельные требования, план,
независимый контрольный список, analyze и сверка существующей #6905. T001/T002,
US2/US3 и общая приёмка остаются открытыми. Локальная проверка US1 не означает
принятие её PR, слияние или закрытие issue.
