# Feature Specification: Надёжное хранение ключа обновлений

**Feature Branch**: `codex/109-release-signing-key-custody`

**Created**: 2026-07-17

**Status**: Draft

**Input**: User description: "Исправить всё и сделать безопасное, всегда доступное хранение ключа подписи обновлений."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Восстановить штатные обновления (Priority: P1)

Владелец GRAF получает один проверенный пакет восстановления, если исторический
секрет подписи утрачен, а после его установки следующие версии приходят через
обычную команду «Проверить обновления» в приложении.

**Why this priority**: Без этого пользователь с уже установленной версией не
может получить исправления безопасным и предсказуемым способом.

**Independent Test**: Установить пакет восстановления на контролируемый Mac,
затем установить следующую версию через приложение без повторной ручной
установки.

**Acceptance Scenarios**:

1. **Given** установленный GRAF доверяет утраченному историческому ключу,
   **When** владелец запускает утверждённый пакет восстановления,
   **Then** приложение сохраняет прежнюю идентичность и начинает доверять
   новому управляемому ключу.
2. **Given** пакет восстановления уже установлен, **When** выходит следующая
   подписанная версия, **Then** приложение находит, проверяет и устанавливает
   её через обычный in-app путь.

---

### User Story 2 - Выпуск без единой точки потери (Priority: P1)

Оператор релиза может подготовить подписанное обновление, даже если один из
разрешённых защищённых путей хранения ключа временно недоступен, и до начала
выпуска получает понятное подтверждение, что выбранный подписант соответствует
доверенному ключу приложения.

**Why this priority**: Один случайный Keychain или локальный файл уже привёл к
невозможности обновления. Повторение этого состояния блокирует безопасность и
доставку исправлений.

**Independent Test**: Проверить оба разрешённых пути хранения по отдельности;
каждый должен подготовить одинаково проверяемый тестовый артефакт без раскрытия
секретного материала.

**Acceptance Scenarios**:

1. **Given** основной защищённый путь доступен, **When** оператор начинает
   выпуск, **Then** система подтверждает соответствие ключа до создания
   публичного каталога обновлений.
2. **Given** основной путь недоступен, а резервный доступен, **When** оператор
   начинает выпуск, **Then** выпуск может безопасно продолжиться без создания
   нового несовместимого ключа.
3. **Given** ни один разрешённый путь не доступен или ключ не совпадает,
   **When** оператор начинает выпуск, **Then** подготовка останавливается до
   публикации архива или каталога обновлений.

---

### User Story 3 - Безопасное управление и проверяемый откат (Priority: P2)

Владелец может проверить состояние хранения ключа и безопасно остановить
неудачный rollout, не публикуя секреты, не подменяя ключ в обычном обновлении
и не оставляя каталог, указывающий на отсутствующий архив.

**Why this priority**: Надёжная доступность не должна ослаблять проверку
подлинности или раскрывать ключ через логи и ручные обходы.

**Independent Test**: Запустить проверку готовности, имитировать отсутствие и
несовпадение ключа, затем подтвердить, что публичный каталог и предыдущая
версия остаются неизменными.

**Acceptance Scenarios**:

1. **Given** ключ или доступ к нему неверен, **When** запускается проверка
   готовности, **Then** результат объясняет безопасный путь восстановления без
   вывода секрета, локального пути или содержимого записи.
2. **Given** выпуск уже подготовлен, **When** проверка перед публикацией не
   проходит, **Then** старый публичный каталог остаётся активным.
3. **Given** требуется отменить опубликованный rollout, **When** владелец
   выполняет утверждённую процедуру, **Then** каталог возвращается к последнему
   проверенному состоянию, а установленным клиентам предлагается только более
   новая исправляющая версия, а не небезопасное понижение.

### Edge Cases

- Исторический приватный ключ невозможно восстановить из публичного ключа или
  из установленного приложения; для такого случая обязателен один ручной
  пакет восстановления, а не подмена ключа в обычном обновлении.
- Один из защищённых путей может быть временно недоступен, но другой не должен
  автоматически копировать секрет в репозиторий, логи, публичный host или
  приложение.
- Секретный материал может отсутствовать, быть повреждённым или не
  соответствовать публичному ключу; во всех случаях выпуск останавливается до
  публикации.
- Одновременные попытки выпуска не должны привести к двум каталогам или
  нарушению последовательности версий.
- Пакет восстановления не должен менять идентичность приложения, разрешения
  macOS или поведение записи.
- Attestation от другой версии, другого tag, отменённого job или неизвестной
  schema не подтверждает channel readiness.
- Подозрение на компрометацию нового ключа требует нового manual bootstrap;
  оно не даёт права продолжить обычную публикацию старым ключом.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система выпуска MUST хранить один действующий секрет подписи в
  двух независимых защищённых каналах с ограниченным доступом; ни один канал
  не может быть репозиторием, публичным host, приложением или диагностикой.
- **FR-002**: Система MUST проверять перед созданием артефактов, что выбранный
  подписант соответствует доверенному публичному ключу приложения и
  неизменной идентичности GRAF.
- **FR-003**: Система MUST останавливаться до создания публичного каталога
  обновлений, если ключ отсутствует, повреждён, не совпадает или доступ к нему
  не подтверждён.
- **FR-004**: Система MUST предоставлять безопасную проверку готовности обоих
  каналов, возвращающую только статус и безопасный идентификатор ключа, без
  секретов, путей, содержимого Keychain или командной строки с секретом.
- **FR-005**: Система MUST поддерживать один утверждённый ручной пакет
  восстановления для исторически утратившего ключа канала, после которого
  обычные обновления используют новый управляемый ключ.
- **FR-006**: Система MUST запрещать незаметную замену ключа или адреса
  каталога внутри обычного in-app обновления; такие изменения допускаются
  только через явно отмеченный пакет восстановления и отдельную проверку.
- **FR-007**: Система MUST сохранять порядок публикации: сначала проверяемые
  версионные артефакты и контрольные суммы, затем публичный каталог обновлений.
- **FR-008**: Система MUST ограничивать доступ к облачному каналу подписи
  утверждённым release-контекстом, последовательной версией и ручным
  подтверждением владельца перед доступом к секрету.
- **FR-009**: Система MUST документировать процедуру восстановления, ротации,
  остановки rollout и проверки двух последовательных in-app обновлений без
  указания реальных секретов или локальных путей.
- **FR-010**: Система MUST сохранять текущие гарантии: bundle id
  `pro.2brain.graf`, имя GRAF, безопасный HTTPS-каталог, подпись обновлений,
  отсрочку установки во время записи и отсутствие изменения TCC-разрешений.
- **FR-011**: Система MUST иметь версионируемую публичную запись активного
  доверия с состоянием, поколением доверия, публичным ключом и безопасным
  идентификатором; неизвестная схема, неактивное состояние, неверная длина
  публичного ключа или несовпадение записи с приложением MUST блокировать
  выпуск. Эта запись MUST NOT содержать приватный материал, секретный путь,
  credential-bearing URL или содержимое защищённого хранилища.
- **FR-012**: «Независимые защищённые каналы» MUST означать разные
  independently revocable control planes: потеря, удаление, блокировка или
  компрометация учётной записи/устройства одного канала не может одновременно
  удалить или изменить другой. Две копии в одном локальном файле, одной
  учётной записи или одном неразделённом backup-контуре не считаются двумя
  каналами.
- **FR-013**: Безопасный идентификатор ключа MUST быть детерминированным
  `sha256:` + lowercase SHA-256 от ровно 32 декодированных байтов публичного
  Ed25519-ключа. Все channel/app/manifest проверки MUST сравнивать именно этот
  идентификатор и исходный публичный ключ до подписи.
- **FR-014**: Создание, импорт, экспорт только для первоначального
  защищённого переноса и активация нового поколения MUST быть явной
  owner-approved процедурой. Приватный материал MAY существовать лишь в
  защищённом Keychain, защищённом облачном secret и краткоживущем файле
  ограниченных прав внутри доверенного job; он MUST быть удалён при завершении
  job и никогда не может быть выведен, закэширован, приложен к release или
  сохранён в shell history.
- **FR-015**: Нормальная readiness-проверка MUST требовать две свежие
  безопасные attestations равного `keyId`; состояние ровно одного доступного
  канала MUST быть `degraded`, а нуля или несовпадения — `unavailable`. Выпуск
  в `degraded` состоянии допускается только после явного owner approval и
  повторной проверки выбранного ключа, приложения, архива и provenance; это
  не считается штатной готовностью. Attestation MUST быть создана для
  конкретного candidate tag/workflow run и не может быть reused для другой
  версии или release attempt.
- **FR-016**: Облачный signing workflow MUST быть только вручную запускаемым
  из защищённой default-branch конфигурации, проверять exact утверждённый tag
  и его provenance, иметь least repository permissions, требовать protected
  environment approval для доступа к секрету и MUST NOT иметь trigger,
  предоставляющий секрет untrusted pull request, fork или произвольному ref.
  Любой внешний GitHub Action в таком workflow MUST быть закреплён immutable
  full commit SHA; встроенные runner/`gh` возможности предпочтительны, если
  позволяют не добавлять внешний Action.
- **FR-017**: До подписи workflow MUST проверить, что draft archive и русские
  release notes принадлежат запрошенной версии, содержат ожидаемый GRAF.app,
  identity и публичный ключ; публиковать он MAY только inspectable draft
  artifacts. Прямой доступ workflow к public download host и замена live
  appcast запрещены.
- **FR-018**: Система MUST сериализовать попытки выпуска для одной stable feed:
  конкурентные заявки не могут одновременно заменить staging/draft/live
  appcast. Отказ или отмена одной заявки MUST оставить последнюю проверенную
  public feed неизменной.
- **FR-019**: При подозрении на компрометацию активного Sparkle private key
  владелец MUST немедленно остановить обычный rollout, не использовать этот
  ключ для следующего release и выполнить новую явно ручную trust migration.
  Клиенты на скомпрометированном поколении не могут получить замену verifier
  через старый appcast; требования к новой bootstrap package и последующим
  двум in-app proof применяются снова.
- **FR-020**: Система MUST документировать и проверять failure path для
  неустановленного/частично доставленного bootstrap package, client на старой
  trust line и недоступных draft/public artifacts. Никакой такой failure path
  не может включать выключение проверки подписи, автозамену verifier или
  небезопасный downgrade.
- **FR-021**: Владелец MUST запускать metadata-only readiness drill обеих
  каналов перед каждым production release, не реже одного раза в 90 календарных
  дней и сразу после изменения control plane. Drill MUST фиксировать только
  дату, generation, безопасный `keyId` и channel state; он не может сохранять
  secret, идентичность владельца или локальный secret path.
- **FR-022**: Каждый versioned ZIP/package, принятый для public publication,
  MUST иметь SHA-256 checksum. Владелец MUST сверить checksum локального
  проверенного артефакта с asset/draft и с повторно скачанным public-host
  артефактом до замены live appcast.
- **FR-023**: Manual bootstrap MUST иметь явную user-facing маркировку
  одноразовой trust migration, указывать исходное и целевое поколения в
  metadata-only release evidence и доставляться только как ручной package.
  Он MUST NOT быть item обычного Sparkle appcast и не может использовать shared
  normal staging workflow для обхода FR-006.

### Key Entities *(include if feature involves data)*

- **Запись владения ключом**: Публично проверяемое описание действующего
  ключа, его безопасного идентификатора, статуса и версии доверия; не содержит
  секретного материала.
- **Канал подписи**: Защищённое место, из которого ограниченный release-процесс
  может выполнить подпись, не раскрывая приватный ключ в приложении или
  публичных системах.
- **Пакет восстановления**: Один вручную устанавливаемый выпуск, который
  переводит клиент с утратившей ключ линии доверия на новую управляемую линию.
- **Запрос выпуска**: Проверяемое намерение подготовить конкретную версию с
  известной исходной ревизией и пользовательскими заметками.
- **Безопасная attestation**: Связанный с одной версией/job metadata-only
  результат, содержащий channel state и `keyId`, но не секрет или путь.
- **Штатная/аварийная готовность**: `ready` означает подтверждены оба канала;
  `degraded` — ровно один с явным owner approval для единичного выпуска;
  `unavailable` блокирует выпуск.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: После одного ручного пакета восстановления контролируемый Mac
  успешно выполняет две последовательные in-app установки более новых версий
  без повторной ручной установки и без потери ранее выданных разрешений.
- **SC-002**: Для 100% проверенных попыток выпуска с отсутствующим или
  несовпадающим ключом публичный каталог и существующие версионные архивы не
  меняются.
- **SC-003**: Проверка готовности подтверждает оба независимых защищённых
  канала и их общий безопасный идентификатор до выпуска; отсутствие одного
  канала отображается как блокирующее или аварийное состояние, а не как успех.
- **SC-004**: Автоматическая проверка и ручной review не находят приватных
  ключей, seed-значений, секретных путей или значений секретов в отслеживаемых
  файлах, опубликованных артефактах и release-логах.
- **SC-005**: 100% подписанных артефактов, принятых для публикации, проходят
  проверку соответствия версии, идентичности приложения, содержимого архива,
  подписи и публичного каталога до изменения публичного каталога.
- **SC-006**: Матрица проверки охватывает как минимум absent, malformed,
  mismatched, inaccessible, stale и wrong-release attestation/secret случаи;
  каждый случай останавливается до signed draft artifact или изменения live
  appcast согласно своему этапу.
- **SC-007**: В 100% проверок корректного candidate `keyId` в manifest,
  GRAF.app, Keychain attestation и protected workflow attestation одинаков и
  вычислен по FR-013; ни один output не содержит private bytes или путь к ним.
- **SC-008**: При двух конкурентных release attempts существует не более одной
  активной заявки на stable feed, а после отмены/ошибки второй заявки текущий
  public appcast и уже проверенные versioned artifacts остаются доступны.
- **SC-009**: Перед activation нового trust generation проверены возможность
  protected GitHub environment approval, доступность owner-only app-signing
  identity и отсутствие secret authority у public-host оператора; при любом
  непрохождении activation не начинается.

## Assumptions

- Исторический секрет, которому доверяет установленный GRAF `2026.07.17.10`,
  недоступен; криптографически корректный путь к нему не предполагает попытки
  восстановления из публичных данных.
- Пользователь принимает одну ручную установку пакета восстановления как
  неизбежную миграцию доверия; после неё нормой остаётся обновление из
  приложения.
- GitHub environment и его approved reviewers доступны как отдельный от macOS
  Keychain control plane; конкретные владельцы и правила approval задаются до
  activation, но их identities и secret details не попадают в Git.
- Текущая owner-only app-signing identity остаётся доступной для bootstrap и
  сохраняет проверяемую continuity с установленным GRAF; Developer ID/
  notarization остаются отдельной будущей миграцией.
- Канал остаётся контролируемым owner-only до отдельной утверждённой миграции
  на Developer ID и notarization.
- Действующая идентичность приложения и разрешения macOS сохраняются, если
  это подтверждается установленной проверкой continuity.
- Граница фичи включает только custody и delivery обновлений; она не меняет
  захват аудио, транскрибацию, серверную обработку или исторические данные.

## Out of Scope

- Восстановление утраченного исторического приватного ключа из публичного
  ключа, установленного приложения или appcast.
- Публичная Developer ID/notarized дистрибуция и миграция code-signing
  identity.
- Автоматическая установка обновлений без действия пользователя.
- Изменение записи, аудиопайплайна, MediaScribe или незакрытых физических
  acceptance-gates feature 106.
