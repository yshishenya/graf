# Feature Specification: Видимый прогресс загрузки записи

**Feature Branch**: `128-upload-progress-visibility`

**Created**: 2026-07-25

**Status**: Ready

**Input**: User description: "Показать пользователю прогресс загрузки локальной записи и отличить медленную отправку от зависшей без изменения custody semantics"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Понять, что запись отправляется (Priority: P1)

Пользователь после остановки записи видит в нативном локальном списке не только
слово «загрузка», но и текущий прогресс отправки. Он может понять, что процесс
идёт, не открывая служебный инспектор и не предпринимая лишних действий.

**Почему этот приоритет**: Большая запись может отправляться долго. Без
прогресса пользователь не отличает нормальную медленную отправку от зависшего
состояния и может преждевременно закрыть приложение или повторить действие.

**Независимая проверка**: На синтетической записи с состояниями отправки 0%,
25%, 75% и 100% открыть локальный список и проверить, что видны состояние,
процент и индикатор прогресса, а завершение не объявляется до подтверждённого
состояния записи.

**Сценарии приёмки**:

1. **Дано**: запись находится в активном состоянии `uploading` и сервер
   подтвердил долю байтов, **когда** пользователь смотрит локальный список,
   **тогда** строка показывает понятный текст отправки, линейный индикатор и
   процент от 0 до 100.
2. **Дано**: сервер подтвердил все байты, но финализация ещё не завершена,
   **когда** пользователь смотрит строку, **тогда** она показывает завершение
   отправки/проверки, но не «Готово к просмотру».
3. **Дано**: запись уже перешла в `uploaded`, **когда** пользователь смотрит
   строку, **тогда** отображается существующее состояние готовности без
   отдельного прогресс-бара.

---

### User Story 2 - Сохранить спокойный и доступный custody-flow (Priority: P1)

Пользователь получает прогресс как объяснение автоматической работы приложения,
а не как новую задачу очереди. Доступные технологии и локализованный текст
сообщают то же состояние, что и визуальная строка.

**Почему этот приоритет**: Upload/custody — доверительная граница записи.
Прогресс не должен превращаться в ручной retry, раскрывать транспортные детали
или создавать ложное обещание сохранности на сервере.

**Независимая проверка**: Пройти синтетические uploading, queued, retrying,
blocked и uploaded состояния мышью и VoiceOver; проверить, что действия
очереди не добавились, а доступное описание совпадает с видимым состоянием.

**Сценарии приёмки**:

1. **Дано**: запись не отправляется прямо сейчас (`queued`, `retrying`,
   `blocked` или сохранена только локально), **когда** пользователь смотрит
   локальный список, **тогда** показывается существующая bounded custody-копия
   без stale-прогресса и без кнопок ручной повторной отправки.
2. **Дано**: VoiceOver фокусируется на uploading-строке, **когда** состояние
   обновляется, **тогда** доступная метка сообщает состояние и текущий процент,
   не раскрывая путь файла, идентификатор встречи или содержимое записи.
3. **Дано**: значение прогресса отсутствует, равно нулю или некорректно,
   **когда** строка строится, **тогда** интерфейс не показывает NaN/отрицательный
   процент и не объявляет загрузку завершённой.

### Edge Cases

- При 0% виден активный, но ещё не начавший передавать байты процесс; пустая
  полоса не должна выглядеть как ошибка.
- При 100% принятых байтов финализация остаётся отдельным состоянием; нельзя
  показывать `Готово к просмотру` до существующего `uploaded`.
- При быстром изменении прогресса значение не должно регрессировать в UI из-за
  устаревшего snapshot.
- При нескольких локальных записях каждая видимая строка получает свой
  прогресс; агрегирование очереди и порядок строк не меняются.
- При отсутствии total bytes или server progress строка сохраняет честный
  текст состояния без выдуманного процента.
- В режиме без настроенного кабинета локальный список сохраняет текущую
  локальную модель и не превращается в серверный список.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Нативная строка локальной записи MUST показывать линейный прогресс
  и процент только для текущего активного состояния `uploading` с доступным
  измеримым прогрессом.
- **FR-002**: Отображаемый процент MUST быть ограничен диапазоном 0–100 и
  вычисляться из существующего принятого объёма относительно существующего
  общего объёма записи; новый источник байтов не вводится.
- **FR-003**: Прогресс MUST сопровождаться текстом состояния и MUST NOT быть
  единственным способом сообщить, что запись отправляется.
- **FR-004**: При принятых 100% байтов, но незавершённой финализации, UI MUST
  показывать bounded состояние завершения отправки/проверки и MUST NOT называть
  запись готовой к просмотру.
- **FR-005**: После существующего состояния `uploaded` UI MUST сохранить текущее
  состояние готовности и MUST NOT показывать активный прогресс-бар.
- **FR-006**: Для `queued`, `retrying`, `blocked`, локально сохранённой и иных
  неактивных custody-состояний UI MUST сохранять существующий текст и MUST NOT
  показывать устаревший активный прогресс.
- **FR-007**: Прогресс MUST обновляться вместе с текущим queue snapshot и MUST
  сохранять monotonic truth внутри одной отправки, не создавая собственный
  таймер или сетевой опрос.
- **FR-008**: UI MUST NOT добавлять пользователю ручные retry/stop/verify controls,
  новые transport labels, storage paths или server upload identifiers.
- **FR-009**: VoiceOver и другие assistive technologies MUST получать текстовое
  состояние и процент для активной отправки, а при отсутствии измерения —
  bounded состояние без процента.
- **FR-010**: Состояние прогресса MUST корректно отображаться при нескольких
  видимых локальных записях без изменения порядка, группировки или лимита строк.
- **FR-011**: Реализация MUST сохранить существующие server-mediated egress,
  custody ownership, automatic retry, retention, deletion, local-purge и
  fail-closed policy.
- **FR-012**: Визуальный и доступный текст MUST быть локализационно безопасным,
  не раскрывать private meeting content и проходить clean-room UI gate.

### Key Entities

- **Прогресс отправки записи**: производное значение от принятого сервером
  объёма и общего upload-объёма; действует только внутри текущего queue
  snapshot и не является отдельным lifecycle state.
- **Локальная строка записи**: существующая нативная строка, которая показывает
  локальное custody-состояние и теперь может показать его измеряемую отправку.
- **Custody-состояние**: существующая authoritative projection, отделяющая
  активную отправку, финализацию, готовность, retry и blocked states.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: В 100% синтетических активных uploading-состояний с доступным
  progress snapshot пользователь видит состояние, линейный индикатор и процент
  в первой видимой строке локального списка без открытия инспектора.
- **SC-002**: В 100% сценариев с 100% принятых байтов до перехода в `uploaded`
  интерфейс не сообщает «готово к просмотру» и не создаёт ложное completion
  состояние.
- **SC-003**: В 100% проверенных uploading-состояний VoiceOver получает
  локализованное текстовое описание с актуальным процентом; при отсутствии
  измерения процент отсутствует, а состояние остаётся понятным.
- **SC-004**: Focused macOS projection/UI tests и полный repository gate проходят
  без изменения существующих custody, retry, deletion, egress и capture
  контрактов.
- **SC-005**: В committed code, tests и evidence не появляются raw audio,
  transcript text, private meeting content, local paths, credentials, signed
  URLs или server upload identifiers.

## Assumptions

- Queue item уже содержит безопасный `progressFraction`, полученный из
  существующего upload snapshot; новый серверный API и новая модель данных не
  нужны.
- Порог «зависло» не определяется этой правкой: stalled/retry semantics
  остаются в существующей custody projection и copy.
- В первую версию входит per-row progress в нативном локальном списке; общий
  ETA, скорость, история попыток и ручное управление очередью остаются вне
  scope.
- Browser/WebView meeting list и server-mediated upload path не меняются.

## Out of Scope

- Изменение upload protocol, chunking, accepted-byte truth, server endpoints,
  retries, retention, deletion, local purge или MediaScribe boundary.
- Новый глобальный progress HUD, уведомления, ETA, скорость или ручные retry и
  cancel controls.
- Исправление P1 production owner-journey evidence: для него по-прежнему нужна
  отдельная свежая запись с reviewable audio и действующая auth-сессия.
