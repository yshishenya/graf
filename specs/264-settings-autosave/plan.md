# Implementation Plan: Понятные настройки с автосохранением

**Branch**: `264-settings-autosave` | **Date**: 2026-09-13 | **Spec**: [spec.md](spec.md)

## Summary

Один механизм сохранения поверх существующих форм и маршрутов; общие строки и группы вместо отдельных систем оформления. Удалить длинные пояснения, ручные Save/Reset для обычных настроек и конкурирующие обработчики. Существующие локальные хранилища и API форматов остаются владельцами своих данных.

## Technical Context

- Python/FastAPI/Jinja, обычные JavaScript/CSS; SwiftUI/AppKit для резервного окна Mac.
- Существующие PostgreSQL-модели и локальные предпочтения. Миграции и новые зависимости не планируются.
- Проверки: pytest, существующие браузерные проверки Node и Swift tests, GRAF Dev.
- Lane: high-risk reference-fidelity UX; clarify/checklist/analyze обязательны.
- Release gate: no deploy в этом запросе; после разрешённого коммита governance-fast на точном SHA; перед выпуском release-full и отдельные release gates.
- Область: 7 разделов + меню темы + редактор форматов + резервные локальные настройки; веб и встроенный кабинет.
- Цель: немедленная реакция элементов; текстовая пауза 500 мс; один запрос на ресурс; без перезагрузки и постоянных черновиков браузера.

## Constitution Check

До исследования: полномочия ограничены представлением/сохранением существующих настроек. Захват, трёхзначные правила, Stop, разрешения, приватность, удаление, оплата и AI-процесс неизменны. Источник — наблюдаемый интерфейс KRISP, самостоятельный код, без извлечённых ресурсов.

После проектирования: FR-004/007/008/009 сохраняют эти границы. Назначенный пользователем агент завершил проверку требований: checklists/ux.md и security.md PASS, результат в review.md. Продуктовый код начинается после analyze и taskstoissues (T002).

## Implementation

1. Поведенческие проверки для общей очереди сохранений: последний ввод, IME, ошибки, редирект, версионность, переход и закрытие.
2. В cabinet.js заменить initSettingsFormState и отдельный обработчик уведомлений одним управлением обычными формами. Тема получает только предпросмотр, запись идёт общим путём. Calendar selection/preferences переходят на тот же путь; connect/sync/disconnect остаются отдельными.
3. Существующие маршруты сохраняют POST/CSRF/валидацию. Для автосохранения возвращают явное подтверждение нормализованных значений и текущей области вместо распознавания успеха по произвольному HTML. Для прежнего клиента сохранить ответ-редирект. Не отправлять всю устаревшую форму аккаунта при изменении одного поля.
4. Общая очередь идентифицируется владельцем/областью/ресурсом, включая обе точки темы. Ожидание ограничено 15 секундами; после неподтверждённой записи перечитать ресурс, не повторять вслепую. Для заменяемых неделимых групп без версии проверить исходное состояние под блокировкой; новые таблицы не нужны. UI обновляет только подтверждённую часть, не затирает последующий ввод. Ошибка/конфликт сохраняют ввод, предлагают повтор/перечитывание. При внешней смене владельца отменить очередь и не применять старый ответ; сервер переиспользует _validate_tenant_scope и X-Graf-Expected-Actor / X-Graf-Expected-Workspace для проверки ожидаемого контекста до записи; метаданные страницы дают текущую область. Переход/Escape/закрытие редактора завершают очередь либо предлагают остаться/уйти без сохранения, не запирая невалидный черновик. Штатную защиту закрытия embedded окна проверить через существующие EmbeddedCabinetWebView/контроллер окна; DOM beforeunload сам по себе не доказывает её на Mac.
5. Формат новых итогов и редактирование существующего личного формата используют тот же протокол состояний. Создание происходит явно; пустой черновик автоматически не создаётся. Для редактирования сохранить expected_version, валидацию всего формата и доступ владельца; не пересоздавать диалог после ответа и не запускать генерацию итогов.
6. В primitives.html переиспользовать/дополнить существующие макросы строки, переключателя, флажка и статуса; все семь страниц используют один CSS-блок. Удалить старые противоречащие правила, не добавлять ещё один хвост переопределений.
7. Резервные SwiftUI-настройки используют существующие stores/bridge, с теми же правилами текста и ошибок. Не объединять разные владельцы хранения ради одинакового внешнего вида.
