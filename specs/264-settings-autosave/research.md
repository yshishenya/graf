# Research: F264

Дата: 2026-09-13. Исходный SHA: `5e599a5b743f3983a9ba6ebfe0ed7f234a317c55`.

## Наблюдения кода

- Настройки сервером рендерятся одинаково для веба и embedded. Уже есть settings-page, settings-section, settings-control-row, ui.switch/checkbox; переиспользовать.
- initSettingsFormState в cabinet.js хранит начальное FormData и выводит «Есть несохранённые изменения». Он пересекается с отдельными обработчиками темы, календаря и уведомлений.
- initAccountPreferences содержит два разных сохранения: меню темы и ручное сохранение страницы с переходом window.location.assign. Проверка успеха меню недостаточно конкретна: HTTP OK без /login не подтверждает сохранённое значение.
- Обработчик data-notification-settings в конце cabinet.js автоматически отправляет форму, но сохраняет Save/Reset и блокирует checkbox на запрос. Версия и 409 — действующий контракт; сохранить.
- calendar-selection-form и calendar-preferences-form требуют ручного submit. Фоновое обновление calendar:baseline может обновлять формы; должно учитывать ожидающие изменения.
- _save_account_preferences умеет принимать отдельные поля. Не отправлять незатронутые theme/locale/timezone вместе со старым значением.
- _save_notification_preferences блокирует владельца и проверяет версию. Нового generic settings API не требуется.
- Локальные правила записи и уведомлений уже автоматически пишутся через существующий мост. Унифицировать состояния, не переносить их на сервер.
- Личный формат итогов редактируется существующим диалогом с Save. Новый формат должен создаваться кнопкой «Создать», существующий — сохраняться автоматически после валидного изменения.

## Решения

Общая очередь на существующий ресурс + один ожидающий последний снимок. Пауза текста 500 мс, change для готового выбора. Явное подтверждение ответа. Неподтверждённое состояние сохраняет черновик в памяти страницы и показывает повтор, не пишет приватные значения в localStorage. Смена области инвалидирует очередь. Запросы не повторяются бесконечно.

Для no-JS: поля обычных настроек недоступны, одна короткая причина. Старые явные операции продолжают существовать. Это сознательное следствие требования об отсутствии ручного Save, которое проверяется отдельно.

## Reuse / ограничения

F260 и существующие примитивы дают основную структуру. Незавершённые изменения combobox из других веток не импортируются без отдельного анализа совместимости: фильтрация никогда не должна сохранять запрос как значение. Текущие параметры KRISP не менялись ради исследования; сохранение предпочтений KRISP не проверялось. Видимое отсутствие Save подтверждено на просмотренных страницах.
