# F136: оценка различения переходов по navigationType

Дата: 2026-10-18. Независимый reviewer: `review_f290_infra`.
Режим: high-risk-product. Только оценка предлагаемого решения, без изменения кода.

## Решение

**Предложенный классификатор недостаточен.** Нельзя считать любую action с
типом, отличным от `.other`, новым переходом и безусловно инвалидировать
активный `WKNavigation`: это повторно нарушит проверенный POST → 303 → GET.
Предложение ещё не реализовано; этот вывод не является новой находкой кода.
Прежний P2 и Request Changes сохраняются.

## Прямое доказательство

В сохранённом `F136-redirect-identity-diagnostic-20261017.log`, строки 279–283:

```text
action type=1 method=POST active=nil
start nav=A
action type=1 method=GET active=A
server_redirect nav=A
finish current=false nav=A active=nil
```

Идентификаторы объектов здесь заменены буквами только для понятности;
в исходном журнале у start/redirect/finish один ObjectIdentifier.
`1` соответствует `.formSubmitted`. Таким образом, redirected GET имеет
тот же тип, что и исходная форма. Инвалидация в policy callback GET уничтожит
identity A до подтверждающего redirect callback. Нельзя восстанавливать уже
инвалидированную A из следующего callback: это вернёт исходную проблему старых
callbacks и создаст вторую ветку правил восстановления identity.

## Ограничения публичного API

Повторно прочитаны SDK headers `WKNavigationAction.h:38–125` и
`WKNavigationDelegate.h:102–135`. У `WKNavigationAction` есть request,
navigationType, sourceFrame и targetFrame, но нет связанного `WKNavigation`.
`.other` означает иной повод перехода, а не подтверждённое HTTP-перенаправление.
Инициированный кодом страницы новый переход также нельзя исключить из этой
категории. Ни метод GET, ни совпадение URL не устраняют неоднозначность.

Свойство `isContentRuleListRedirect` в macOS 26 относится к перенаправлению
правилом фильтрации контента; оно не является общим признаком server HTTP
redirect и недоступно на всей минимальной платформе macOS 14.
`modifierFlags`/`buttonNumber` не являются обещанием уникального нового
перехода и не покрывают клавиатуру, скрипты и продолжение формы.

Публичные redirect/start/finish callbacks уже содержат WKNavigation, но
подтверждение A само по себе не устанавливает принадлежность более поздней
неоднозначной action B к A. Именно этого не хватает текущему исправлению.
Задержка на один цикл MainActor или таймер не заменяют такую связь.

## Минимальная безопасная основа решения

1. Для переходов, которые действительно запускает код GRAF через load/go/
   reload, явно передавать происхождение «новый переход», инвалидировать
   предыдущую identity и связывать новое поколение с возвращённым WKNavigation.
   Лучше выразить происхождение отдельным именованным параметром, а не
   неочевидным смыслом `navigationType == nil`.
2. Не разрешать redirect callback A очищать глобальный pending нового
   поколения B. Состояние продолжения активной A и состояние нового ожидающего
   перехода должны иметь раздельное владение; один URL не является владельцем.
3. Не объявлять `.other`, `.formSubmitted`, GET или одинаковый URL достаточным
   доказательством продолжения A. Поддержку неопределённой action нельзя
   принять по двум зелёным тестам POST, оставив тот же сбой для GET-формы или
   JavaScript-перехода.

Это необходимые условия минимального решения, а не готовый полный алгоритм.
По рассмотренным публичным данным универсальный классификатор policy action
ещё не доказан. Отдельный счётчик поколений полезен только при обоснованном
назначении владельца action; сам по себе он не устраняет неоднозначность.

Следующий небольшой опыт должен зафиксировать только синтетические сведения:
порядок policy/start/redirect/commit/finish и sourceFrame/targetFrame requests
для настоящего POST303, GET-формы и JavaScript navigation при ещё активном A.
Если source/target frame даёт различие, сначала проверить его границы; не
принимать наблюдаемую разницу за обещанную API identity. Отдельно проверить
307/308, где перенаправление может сохранить POST: правило «POST всегда новый»
тоже не является общим решением.

Если без дополнительного доказанного происхождения публичный API не позволяет
различить события, нужно либо узко документировать поддерживаемый контракт и
не закрывать остальные требования, либо изменить момент/механизм публикации
границы так, чтобы неоднозначный callback не мог разрушить новую action.
Расширенная перехватывающая JavaScript-подсистема или перезапуск исходного
POST не являются минимальным оправданным исправлением этого среза.

## Обязательная приёмка реализации

- Обе независимые красные пробы: pending новой формы не завершается старым
  redirect/finish; прежний logout не меняет boundary нового login.
- Старые redirect/failure и redirect/cancel не завершают новый переход.
- Подтверждённые старые identities не восстанавливаются после invalidation.
- Настоящий POST303 завершается, исходный POST отправлен ровно один раз.
- GET-форма и `.other` новое действие проверяются отдельно от redirect.
- Обычные POST200/error/cancel, 401/reselection, history controls, billing и
  download остаются в текущей проверке.
