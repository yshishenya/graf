## Решение по находке

**Прежний P2 снимается как блокер продукта: достижимый пользовательский сбой
не подтверждён.** Он не считается исправленным изменением кода: код с момента
находки не менялся. Результат собственных двух синтетических FAIL сохраняется
в доказательствах вместе с ограничением их применимости.

После проверки настоящего WebKit и настоящего Coordinator GRAF я не требую
нового алгоритма классификации action или обхода только ради вручную заданной
последовательности. В текущем срезе новых подтверждённых блокирующих находок
не осталось. Итоговое принятие проверки среза ожидает текущего полного набора
и сверки хешей; его результат на момент этого решения ещё не получен.

## Почему решение изменено

Первоначальная проба передавала реальным методам Coordinator callbacks,
вручную созданные и упорядоченные самим тестом: start A, принятие B, затем
redirect A и finish A, без нативного fail/cancel A. Она доказала поведение
методов на этой последовательности, но не доказала, что WebKit так вызывает
их при двух формах. Объект WKNavigation от loadHTMLString и action из другого
синтетического WebView не образуют одну реально выполненную сетевую цепочку.

В наблюдаемом native lifecycle у новой формы есть собственная identity.
Предыдущая provisional A завершается fail до policy B; её terminal callback
передаётся контроллеру, который очищает active A. Поздний callback уже
завершённой A не может пройти сравнение с active B. В настоящий redirect
активной A identity сохраняется, поэтому очищение pending относится к
продолжению A. Это объясняет наблюдаемые реальные цепочки без классификатора
по navigationType/методу. Отдельное присваивание native identity тестом до
событий WebKit исключало существенную стадию отмены старой A.

Это не доказательство отсутствия любых гонок на любой версии WebKit и не
публичное обещание точного порядка callback для всех возможных действий.
Но для блокирующей ошибки нужен достижимый путь, причинная связь либо
доказанное нарушение контракта. После адресной проверки такой путь не
показан. Необоснованно сохранять статус P2 только потому, что произвольный
ручной вызов методов даёт нежелательный результат.

## Новый постоянный тест GRAF

Прочитан `testSessionBoundaryNewFormSupersedesPendingFormWithoutRemount` и весь
его путь через `checkSessionBoundary`, listener и `SessionBoundaryRequests`.
Тест использует существующий SwiftUI fixture с настоящими route/state bindings
и `.id(sessionBoundaryID)`, настоящий WKWebView и настоящий Coordinator.
Ручных вызовов start/redirect/finish нет.

1. Загружается исходная settings-страница; controller подтверждает завершение.
2. Первая явная форма отправляется на тот же URL; listener удерживает ответ.
   Проверены loading и неизменная граница сеанса.
3. В том же документе явно отправляется вторая форма с теми же полями.
4. При получении второго POST listener пытается ответить старой A через
   303 на `/login`, а B получает200 и документ результата.
5. Проверяются ровно два POST (два явных действия), единственный исходный GET,
   ноль новых sessionBoundaryID, прежний WebView, завершённый loading,
   ожидаемый stable route и видимый элемент результата после SwiftUI reconciliation.

Это содержательная регрессия настоящего пересечения двух форм. Два POST
не противоречат однократности: тест явно инициировал два действия пользователя.
В этом fixture одни и те же поля формы задают одинаковое тело; listener
не проверяет побайтовое равенство полного HTTP body и такого доказательства
я не заявляю.

Адресный журнал подтверждает **1 PASS / 0 FAIL / 0 unexpected, 0.515 секунды**.
Прежний standalone native пакет повторён одним запуском: **5 PASS / 0 FAIL**,
0.693 секунды. Он по-прежнему показывает `fail A` до policy B, без redirect
или finish A после принятия B.

## Что тест не доказывает

`old_response_send=written` означает успешное завершение записи в NWConnection,
а не получение WebKit. Вызов send начинается до ответа B, но его completion
не ожидается XCTest и в адресном журнале напечатан после результата теста.
Поэтому тест не называется доказательством «полученного позднего redirect A»
или проверки произвольного периода после finish B. Его доказательство —
успешная вторая форма через настоящий lifecycle при удержанном ответе первой.
Это соответствует названию теста и достаточно для проверки заявленного overlap.

Новый тест не устраняет ограничение одной проверенной среды macOS26.6.2.
OAuth, настоящие аккаунты, installed GRAF Dev, выпуск и production не проверены.
Статус остальных открытых задач всей F136 не меняется.

## Границы принятия среза

Текущий product diff сохраняет identity check terminal callbacks и не
воскрешает invalidated navigation; `didStart` меняет владельца identity.
`didFailProvisionalNavigation` проходит через `navigationDidFail`, который
очищает active/pending, затем завершает auth navigation. Существующий тест
same-URL stale finish остаётся полезным защитным инвариантом и проходит.
Новый настоящей-сетью тест проверяет дополнительный достижимый сценарий.

Принимается решение **не вводить** предположительные правила
`.other=redirect`, `non-.other=new` или `POST=new`: новые native трассы
показывают их ошибочность. Нет необходимости править требования для их обхода.

До общего вывода нужны текущий full Swift result, сведения о SKIP и их
причинах, контрольные суммы текущих файлов и журналов. Самостоятельный повтор
оконных тестов параллельно основному исполнителю не выполнялся.
