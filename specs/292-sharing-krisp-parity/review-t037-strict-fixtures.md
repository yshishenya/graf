## Основания по пунктам

  падают с `fair_use_operator_declaration_rejected`; следующие два
  параметра HTTP refund — на точных ожиданиях pending, после них девять
  сценариев — на неизвестном синтетическом receipt в подставном провайдере.
  Итого 13 failed / 668 passed. Локальный исходный порядок отдельно
  воспроизведён: 3 failed / 1 passed за 4.64s, pending равны 2 и 3
  вместо 1, затем KeyError. В исходниках `test_billing_rls.py:99–166`
  нет требуемых деклараций при прямой вставке; проверка app-role
  `:768–800` намеренно оставляет событие pending и не убирает его.
  `test_provider_refund_observation.py:142–543` также не содержит
  завершающей очистки после ошибки. Его точные pending-утверждения
  находятся в `:478–506`. Читатель очереди в
  `billing/webhook_reconciliation.py:597–622` правильно выбирает события
  всех пространств; подставной провайдер следующего набора в
  `test_provider_refund_observation.py:609–618` знает только собственные ID.
  Запрет заменять неизвестный receipt ответом 404 и запрет ослаблять
  pending прямо зафиксированы в анализе T037.

- **CHK002 — PASS.** Анализ T037 и задача T037 ограничивают код двумя
  тестовыми модулями. `declare_operator` в
  `test_billing_fair_use_operator.py:58–61` использует `set_config(..., true)`,
  то есть декларация ограничена текущей транзакцией. Существующий trigger
  `0113_fair_use_operator_history.py:94–108` сначала требует декларацию,
  затем отвергает capability вне server_processing/storage через
  `RAISE EXCEPTION 'fair_use_transition_rejected'`: это P0001, а не
  ошибочно ожидаемый CHECK23514. Существующие отрицательные operator-тесты
  уже используют точную пару P0001/сообщение. Требование T037 сохраняет
  trigger и эти отрицательные сценарии. Область вызовов
  `_seed_reconciliation_probe` проверена: два activity-теста, оба должны
  получить finally по собственному event ID, в том числе при исключении.
  Для первого HTTP refund-теста finally ограничен его собственным
  синтетическим workspace; существующий `refund_queue_case:829–839`
  уже реализует именно такую узкую завершающую очистку. Глобальная очистка,
  ограничение рабочей очереди одним пространством, изменение финансовых
  строк и ослабление утверждений явно запрещены. Будущий обзор кода должен
  проверить фактические границы try/finally, включая ошибку после создания
  события и до заключительных утверждений.
