# Проверка порядка сохранения календарного продления T034

19.10.2026. Область: FR-011/014/024/025/039, задача T034 / #7663. Lane: active Spec Kit slice / high-risk-product. Это проверка исправления, не закрытие всей F278 или календарной приемки T026.

## Причина

На выпущенном `f9ed447e878581f7ec49003d5ab10864426071db` настоящий планировщик в изолированной PostgreSQL получил SQLSTATE23503 по `fk_billing_invoices_operation_id_billing_operations`. После штатной начальной выдачи доступа подписка personal/month и согласие были корректны. Ограниченный перехват INSERT увидел audit, затем invoice; parent operation до ошибки не вставлялась. Единственный прикладной caller в worker фиксирует планирование до отдельной отправки провайдеру.

Минимальная правка сохраняет operation через flush до добавления invoice. Она не добавляет commit, не меняет схемы/цены/права/согласие и не отправляет оплату. При откате вся новая тройка остается частью той же транзакции.

## Воспроизводимая регрессия

Файл: `apps/server/tests/integration/test_billing_renewal_planner_postgres.py`.

- Обычные `create_engine/create_sessionmaker`, настоящий PostgreSQL, миграции и ограниченная maintenance-роль: без superuser, BYPASSRLS и владения таблицей; row_security=on.
- Начальный синтетический успех проходит штатный apply_confirmed_purchase. Нет ручной подгонки срока или вставки операции продления вместо планировщика.
- До T0 планировщик ничего не возвращает; в T0 создается одна связанная operation/invoice/audit. Другая сессия до caller commit не видит ни одной новой строки. После commit видит все три; повтор возвращает прежний ID без дублей.
- Caller rollback удаляет всю новую тройку. Начальные финансовые строки, grant, срок, цена, согласие и сохраненный способ совпадают по всем полям; повторное планирование успешно с прежним детерминированным ID.
- Unknown текущей попытки блокирует новое окно. Общая очередь проверяется в границах своего workspace без удаления других фикстур.
- Оба httpx send явно запрещены до I/O; нет секретов провайдера, API-платежей или почтовых отправок. Synthetic email использует .invalid, ключ метода создан только в tmp_path.

Изменения после прогона восстановлены, одноразовые контейнеры удалены. Это локальная диагностика на сервере, не авторитетный release-full.

## Границы доказательства

Независимые требования: новый checklist 6/0; все действующие чеклисты в затронутой области 92/0; analyze CRITICAL0/HIGH0. Это отдельный допуск требований. Результат ревью кода и проверки точного SHA записываются в PR; полный выпуск и выкладка еще обязательны.

У первого исторического S-прогона отсутствует сохраненная трасса БД; Alembic отключал его счетчик ошибок. Он остановился до POST продления, но не считается отдельным абсолютным доказательством причины. T026 требует отдельного настоящего тестового API и расписания. Temporal, webhook, естественное письмо нового чека T032, ручная доступность/понятность и банковское зачисление возвратов этим тестом не подтверждены.
