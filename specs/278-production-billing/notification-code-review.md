- Причина рассогласования подтверждена исходниками: `maintenance_worker` запускает существующий `run_billing_notification_reconciler`, а прежний Compose не предоставлял этой службе почтовые настройки, ключ и сеть. - Compose добавляет maintenance только существующий Postal secret и существующую сеть. DB роль `twobrain_rec_maintenance`, прежние secrets, непривилегированный пользователь, дополнительная приватная группа, read-only filesystem, `cap_drop: ALL`, `no-new-privileges` и отсутствие опубликованных портов сохранены. - `verify_billing_notification_runtime run` выполняется с candidate image override перед `runtime_mutated=1` и остановкой служб. Команда контейнера заменена на `python -c`; процесс worker не запускается. После запуска выполняется `exec` во всех трёх фактических службах. Старые backup/image identity/DB identity/rollback проверки не удалены.
- Probe вызывает настоящий загрузчик настроек, `PostalEmailLoginClient.from_settings` и открывает TCP-соединение с timeout 5 секунд. `from_settings` читает непустой ключ, но не отправляет запрос. HTTP POST/send, SQL или вызов финансового применения в probe отсутствуют. Это не проверка действительности ключа, TLS/HTTP/API-доступа, принятия письма или получения адресатом.
- При выключенной почте и включённом checkout либо provider observation проверка блокирует развёртывание. `disabled` возвращается только при выключенных почте, checkout и observation. При включённой почте отсутствие ключа, ошибка конфигурации/соединения или неуспех любого из трёх процессов дают отказ.
- stdout дочернего процесса захвачен, stderr подавлен. Внешний вывод ограничен фиксированными reason/result и именем службы из фиксированного списка. Исключения настроек, содержимое ключей, пути, адреса и payload не выводятся. Регрессия подставляет чувствительные синтетические строки в оба потока и проверяет отсутствие их в результате.
- Денежные суммы, права, согласие, бюджет и event identity этим diff не меняются. Исторические failed строки автоматически не сбрасываются: существующий reconciler выбирает только `pending`/`retry`. Новый механизм возврата очереди или создания событий не добавлен.

## Повторное независимое ревью реализации

Проверены текущие рабочие изменения поверх `1ecaeb8f72c506f5e0bf0b8afd64b34a15e23ecc`. **Новых конкретных блокеров в T032 не найдено.**

1. **NTF-C01 устранён.** Maintenance передаёт существующий bootstrap workspace; regression сравнивает его с API/processing. Probe regression теперь использует настоящий `Settings` через `_production_settings`: валидная production-конфигурация проходит, отсутствие bootstrap workspace даёт bounded configuration failure. Валидатор production не ослаблен.
2. **Повтор после неизвестного исхода устранён.** Отправитель заново берёт существующую строку под `FOR UPDATE`, допускает только pending/retry, фиксирует failed + `postal_outcome_unknown` + attempts до вызова отправки и завершает транзакцию. Внешняя отправка выполняется без удержания DB lock. Другой отправитель после блокировки видит failed и пропускает строку. После прекращения процесса до/во время отправки или до записи успеха исход сохраняется неопределённым и автоматически не повторяется. Даже остановка до фактического POST требует ручной сверки — намеренный отказ от автоматического риска дубликата.
3. **Безопасные повторы ограничены.** Только `EmailLoginDeliveryError` с `outcome_unknown=False` и `retryable=True` возвращает строку в retry, пока attempts < 5. Неизвестный исход, generic exception и nonretryable error остаются failed. Attempts увеличивается один раз на захват, event_id, workspace, recipient и delivery key сохраняются. Успешный ответ переводит захваченную failed/unknown строку в delivered и очищает last_error_code; это означает принятие Postal по существующему клиентскому контракту, а не получение письма адресатом.
4. **Чувствительные исключения не публикуются.** Оба warning отправителя/цикла теперь содержат фиксированный текст без `exc_info`; неизвестный результат сохраняет фиксированный код. Регрессия подставляет синтетический секретный текст в исключения и проверяет его отсутствие в логе. Передача адресата остаётся существующей verified identity, тексты и внешние провайдеры не меняются.
5. **Финансовые и исторические границы сохранены.** Новая логика изменяет только состояние/attempts/ошибку/время доставки существующей очереди. Тест проверяет неизменные paid_through, capacity, выключенное recurring и израсходованный/зарезервированный бюджет. Старые failed, delivered и suppressed строки не выбираются для отправки. Runtime/историческая очередь в ходе ревью не изменялись; операторское повторение девяти писем по-прежнему отдельный будущий шаг со сверкой.

Подменён только внешний транспорт; внутри send проверяется уже зафиксированное состояние через отдельную DB-сессию.
