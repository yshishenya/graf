# Quickstart: проверка готовности аналитики

Руководство по проверке на живом стенде. Описывает, что запустить и что должно
получиться, без деталей реализации.

## Что нужно заранее

- Локальный сервер продукта поднят и отвечает на публичные страницы.
- Приложение `/Applications/GRAF Dev.app` собрано через существующий
  `infra/scripts/dev-harness.sh` — для сценариев с активацией.
- Доступ к базе продукта для проверки сохранённых записей.
- Для инфраструктурных сценариев — доступ к серверу аналитики.

## Команды проверки

```sh
# Модульные и контрактные тесты измерения
cd apps/server && python -m pytest tests/unit/test_public_analytics.py \
  tests/contract/test_public_analytics_contract.py -q

# Тесты агрегата, атрибуции и хранения
cd apps/server && python -m pytest tests/unit -k "aggregate or acquisition or retention" -q

# Сквозные серверные сценарии
cd apps/server && python -m pytest tests/integration -k "analytics" -q

# Браузерные сценарии согласия и меток
cd apps/server/tests/browser && node --test ./*.cjs

# Контракты приложения
cd apps/macos && swift test --filter ProductActivationAnalyticsContractTests

# Проверка страниц
infra/scripts/validate-product-analytics-provider-pages.sh
```

## Сценарий 1 — обезличенный счёт видит всех

**Шаги:** открыть публичную страницу в чистом профиле браузера, не давая
никакого согласия. Повторить для каждой публичной страницы.

**Ожидаемо:** каждый визит попал в обезличенный агрегат. В сохранённых записях
нет адреса устройства, идентификатора сессии, строки пользовательского агента и
отпечатка устройства. Проверка выполняется разбором записей, а не чтением кода.

**Требования:** FR-009 … FR-013, SC-001, SC-002.

## Сценарий 2 — метки кампании переживают переходы

**Шаги:** открыть лендинг с метками кампании, перейти на страницу загрузки,
нажать скачивание.

**Ожидаемо:** оба шага несут ту же кампанию, объявление и ключевое слово.
Постоянная cookie слежения не появилась. В агрегате метки сохранены
нормализованными.

**Требования:** FR-014, FR-019, SC-005.

## Сценарий 3 — регистрация переносит кампанию

**Шаги:** прийти на сайт с метками, перейти к регистрации, завершить её. Затем
посмотреть запись о клиенте.

**Ожидаемо:** у записи о клиенте есть атрибут привлечения с исходной кампанией,
применённым правилом последнего непрямого источника и уровнем надёжности
`linked`.

**Требования:** FR-015, FR-017, SC-005.

## Сценарий 4 — воронка активации

**Шаги:** прийти с метками, скачать установщик, открыть приложение, подключить
аккаунт, сделать первую запись, посмотреть результат.

**Ожидаемо:** в воронке видны все шаги, каждый несёт исходную кампанию.
Повторное прохождение того же шага не удваивает счёт. Шаг, который не удалось
связать, помечен `unknown`, а не `direct`.

**Дополнительная браузерная ветвь:** новый внешний учебный аккаунт с
разрешённым источником загружает синтетический файл, дожидается обработки
и открывает непустой результат. До обработки, при одном GET/предзагрузке,
при ошибке и у пустого результата активация не появляется. Новый файл
старого разговора подходит; мигрированный старый результат и служебный
аккаунт исключены из новых внешних активаций. Выполнить повтор из второго
процесса, после перезапуска, перезагрузки страницы и со второго устройства:
все вместе дают одну первую активацию аккаунта. Доказанный pre-send сбой
допускает безопасный повтор; неоднозначная передача отмечается отдельно.
Никакого создания рабочего аккаунта или загрузки частных встреч это
описание не разрешает: сценарий исполняется на согласованном стенде.

**T113, изолированная матрица:** проверить оба HTTP ingress и server-auth
против одной admission boundary: body с чужим псевдонимом, отсутствие principal,
первый запуск без install key, аккаунт и чужой результат. Два процесса и два
устройства конкурируют за account+event; после restart и reload остаются одна
строка и два независимых delivery states. Другой аккаунт/другая веха не блокируются.
Отказ commit не оставляет принятой вехи или отправки; доступный продукт сохранён.

Для каждого получателя: доказанный технический сбой до входа в транспорт
даёт pre_send_retry и один безопасный повтор. Выключатель/неизвестное основание
не разрешают отправку, отзыв отменяет соответствующее намерение; transport timeout/5xx и авария после remote accept до local commit дают
ambiguous без повторной отправки. Одновременный worker не получает право второй
попытки; успех одного получателя не повторяется из-за сбоя другого. HTTP2xx —
submitted; confirmed требует точного отдельного readback. Отзыв между admission
и доставкой останавливает соответствующий side effect. Нечитаемое основание,
выключенная аналитика/получатель и отсутствующая БД не используют fallback.
Проверить предел16KiB, unknown поля, пять строк на аккаунт и bounded scan20/60с.

На учебной GRAF DB проверить until_decision, права, account/category deletion
всех четырёх локальных категорий (ledger/aggregate/visit/acquisition), полное
удаление acquisition bridge без удаления identity, отдельные purge-results,
rollback completion и отказ позднего writer после блокировки identity,
полный withdrawal coverage даже при пустых таблицах и точные survivors,

restore старой копии с pending/dispatching/submitted и удалениями после её точки.
До свежей reconciliation/retention/restore-проверки всё восстановленное
неподтверждённое quarantined/ambiguous и writer закрыт. Пропуск после копии —
unknown, не искусственная история; второй счёт/повтор передачи запрещён.
При непокрытом интервале admission затронутых account+event остаётся закрытым
до подтверждённой сверки: unknown не разрешает повторное INSERT утраченной вехи.
Проверить добавление relation к полному backup/inventory и отказ partial receipt.
Runtime не включать по результату unit-теста или одного provider HTTP2xx.

**Требования:** FR-021 … FR-025, SC-006, SC-007.

## Сценарий 5 — отказ соблюдается

**Шаги:** дать необязательное согласие, затем отозвать его. Пройти по сайту.
Закрыть и открыть браузер, вернуться на сайт.

**Ожидаемо:** после отзыва не отправляется ни одного необязательного события.
В последующих визитах отказ по-прежнему соблюдается. Обезличенный счёт при этом
продолжает работать.

**Требования:** FR-001 … FR-007, SC-003, SC-004.

## Сценарий 6 — деградация измерения

**Частичная деградация на живом сервере:** остановить контейнеры аналитики
на изолированном стенде. Открыть публичную страницу. Дождаться срабатывания
локальных правил. Повторить с управляемой нагрузкой на сервер.

**Ожидаемо:** внешнее оповещение пришло не позднее 15 минут. Публичная страница
и продукт продолжили работать. Измерение отключилось управляемо. Отдельный
всплеск нагрузки при достаточном запасе диска и бюджете аналитики не отключил
измерение; защита общего диска ниже 20% проверяется отдельно и имеет приоритет.

**Полная недоступность цели — отдельная проверка:** наблюдатель и timer работают
на существующем `astraglobal`, а не на целевом стенде. Отключить только
согласованную изолированную цель/подставленный проверочный адрес, не рабочий GRAF.
Проверки GET/TLS/HTTP/JSON идут раз в 60 секунд с timeout 10 секунд; после двух
неуспехов прямой Telegram-путь должен доставить `target_unreachable` ≤15 минут
от начала непрерывного отказа. Целевая машина не исполняет отправитель и не
участвует в доставке. Подтвердить время начала, независимый host, фактическую
доставку, отсутствие ложного PASS при timeout/ошибке канала и восстановление.
При полной потере целевого сервера продукт недоступен — этот сценарий не должен
показывать «продукт продолжил работать». Реальная учебная отправка только после
конкретного разрешения владельца; до receipt T119 открыта.

На изолированном стенде дополнительно проверить: (1) общий filesystem при
свободном месте 19% и 9%, (2) одновременное превышение бюджета аналитики и
порога общего диска, (3) разные filesystem с тревогой только продукта,
(4) неизвестный замер/бюджет. Использовать управляемые сигналы/ограниченный
временный том; не заполнять рабочий диск. Сопоставить идентичность filesystem,
сумму классов и бюджет с `contracts/operations.md`: один ресурс не удваивается,
совместные причины сохранены, защитное действие одно, продукт доступен,
история не удаляется, автоматического возобновления нет. При достаточном
запасе отдельно проверить всплеск без отключения. Проверить ровно 20%/10%,
19,9%/9,9%, бюджет −1/равно/+1, повтор инцидента после перезапуска guard,
ошибку применения с успешным повтором, dry-run и выключенную автоматику.
Старый/будущий/неполный замер, pending/expired бюджет, неучтённый том и
пересечение путей не дают готовности. Отдельные полные архивные копии и
staging/failed файлы входят в расход; ёмкость всего диска в сумму не входит.
Исчезновение тревоги не снимает защиту: проверить отказ неподтверждённого
ручного восстановления и разрешённый путь из runbook. Метаданные результата
содержат показатели/пороги/действие, без адресов посетителей и секретных путей.

Для нагрузочной части использовать только профиль `contracts/operations.md`
§Нагрузка сайта: полный минутный baseline/классификацию, 5/20/15 минут,
5×R, отсутствие повторов и отдельную пометку инженерного 1→5→1 запроса/с,
если R неизвестен/нулевой. Отчёт содержит входную/достигнутую частоты,
статусы/ошибки и задержки по фазам, доступность и guard каждые 15 секунд,
восстановление очереди и метаданные ёмкости. Неполный/сорванный прогон не PASS.
Проверка точного p95 и профиля не заменяет выполнение испытания T097.

**Требования:** FR-030 … FR-032, SC-009, SC-012.

## Сценарий 7 — хранение и восстановление

**Шаги:** проверить наличие свежей резервной копии и результат последней
проверки восстановления. Проверить явный режим хранения и установленные TTL/таймеры.

**Ожидаемо:** локальное хранилище и права соответствуют FR-052, последний запуск
успешен, полный набор проверен, пригодных наборов минимум 2, сохраняются последние
7. Неполные наборы и локальный `.offsite` не увеличивают счёт и не вытесняют хорошие.
Внешнего хранилища не требуется. Возраст от окончания копии неотрицателен и
меньше 26 часов; неизвестное время, будущее, ровно 26 часов, больший возраст и
failed после прежнего pass блокируют готовность. Проверка
восстановления выполнена не позднее 30 дней назад и зафиксирована. На учебном
наборе категории в режиме `until_decision` переживают прежние 365/1095 дней;
90-дневная атрибуция после окна не применяется к новой конверсии. Отдельное
учебное решение об удалении исполнено с охватом, сроком и результатом.
Проверены восстановление из старой копии, неизвестный режим и нехватка места:
ни один не возвращает возрастную очистку и не открывает готовность. Raw IP,
секреты и содержимое встреч не выводятся в доказательства. До включения IP
приняты место, основание, раскрытие, доступ, аудит и удаление по FR-061.
Состояние готовности заблокировано, если копии нет или проверка устарела.
Восстановление читает согласованный полный PostHog; tar/hash недостаточно.
Учебный сценарий потери всех локальных копий честно возвращает отсутствие
восстанавливаемой истории, без повреждения рабочих данных. Это сценарий приёмки;
рабочего результата ещё нет.

**Требования:** FR-033 … FR-036, SC-010, SC-011, SC-013.

**Первый узкий срез GRAF backup T110/T113:** исполнить настоящий helper на
временном каталоге с подставным Docker. Успех проверяет 0700/0600 и очистку
уникального контейнерного staging. Два запуска не используют общий dump;
существующие каталог/файл/ссылка отклоняются, сохраняя содержимое и права.
Отказы dump/copy/mirror/cleanup не дают PASS; неполная копия закрыта.
Исполнить оба контейнерных shell-блока на учебных данных и проверить реальные
права файлов, а не только наличие `umask` в тексте. Dry-run не создаёт файлов.
Профиль: `apps/server/.venv/bin/python -m pytest -q apps/server/tests/integration/test_deployment_backup_restore_rehearsal.py`.
После независимого ревью отдельно проверить исправление прав прежних копий:
полный охват, нет открытых файлов/каталогов, содержимое/владельцы сохранены;
необычные объекты не обходить. Рабочий helper не устанавливать обходом выпуска.
Полный сценарий 7, T110/T113 и включение аналитики этим профилем не принимаются.

## Полная проверка перед снятием блокировки

Перед запуском платного трафика дополнительно требуется:

1. Все сценарии выше пройдены и результаты записаны.
2. Обязательные проверки GitHub прошли на точном SHA pull request.
3. Записи об одобрении зафиксированы, включая правовое подтверждение.
4. Путь отката отработан на живом сценарии, а не только описан.
5. Тексты согласия на сайте, в коде и в документах совпадают.

Снятие блокировки платного запуска выполняется отдельным выпускным решением и не
входит в эту фичу.


## Сценарий 8 — доверенная цепочка адреса и схемы, T098

Все данные учебные; никаких рассылок, оплат или изменений аккаунтов.
Полный путь: public443 stream → dedicated PROXY/TLS receiver → Docker peer
→ настоящий Uvicorn/API → writer → PostgreSQL → отчёт. Стенд, начинающийся
после общего stream, не подтверждает этот путь. Файлы и переходные стадии —
`plan.md` §Полный вход T098; существующая задача T098, issue #7698.

Сначала профильный middleware test, затем изолированный полный стенд:

```sh
python3 infra/scripts/check-graf-sni-ingress.py
```

Это запланированная команда реализации: до появления исполняемого файла
не выдавать её за выполненную. Она обязана запускать собственный временный
nginx без чтения/изменения рабочей конфигурации, использовать только учебные
данные, выдавать безопасный JSON и завершать только свои процессы.
Реальная сеть/Docker и рабочая приёмка — отдельные проверки.

| Проверка | Ожидаемый результат |
| --- | --- |
| Полный effective nginx include graph и listener membership | Все файлы прочитаны, хеши совпадают; новые внутренние сокеты имеют точные loopback binds без wildcard/reuseport/конфликтов, исходные public binds сохранены, неожиданного PROXY на shared10444 нет |
| Public443 IPv4/IPv6; IPv4/IPv6 dedicated loopback receiver | Оба семейства проверены отдельно; отсутствие публичного IPv6 явно зафиксировано как недоступный путь, а не PASS IPv6 |
| Доверенный peer и очищенные XFF/XFP/X-Real-IP | Восстановлены посетитель и HTTPS; входные поддельные заголовки полностью заменены |
| Public PROXY prefix; dedicated TLS без envelope; PROXY UNKNOWN | Не достигают API с придуманным/пустым адресом; UNKNOWN отклонён 400 до API |
| Недоверенный peer; пустое/неправильное доверие | Поддельные заголовки игнорируются, доверие не расширено; неизвестная конфигурация блокирует приёмку |

| Новые PP sockets извне/из обеих рабочих Docker-сетей | Недоступны; host-network контейнеры и локальные недоверенные пользователи перечислены и не имеют доступа к доверенному входу |

| Effective timeout/buffer/half-close/keepalive; ресурсы | Прежние параметры согласованы; новые значения не ухудшают прежние сроки и двунаправленный поток. При нагрузке ниже каждый worker использует <70% worker_connections и soft FD limit, прирост p95 времени до первого байта <10 мс |
| Долгое/простаивающее соединение, upload, WebSocket и разрыв upstream | Двунаправленные данные/допустимые таймауты сохранены; ошибка не затрагивает другие соединения |

| Direct TLS8443 | Прежний сертификат/listener/allowlist/POST-only и 404 прочих путей сохранены; только безопасные отказы, без настоящей/поддельной оплаты |
| Журналы и получатели | Нет нового сохранения visitor IP в HTTP/stream/error/application logs или внешних получателях; `$remote_addr` не заменён через realip, relay access_log off |
| Настоящий writer → хранилище → отчёт | Учебный внешний запрос учитывается ровно один раз; оператор не учитывается. Корзины 1–2 подавлены до суммирования, контрольный порог 3 раскрывается по полному ключу без идентификаторов |

Ресурсная проба: одинаковые baseline/candidate на одном узле, с одной версией
nginx, сертификатом, числом workers и лимитами. После десяти прогревочных
запросов на каждый маршрут держать 100 завершивших TLS соединений не менее
30 секунд: поровну default/special, HTTP keep-alive без закрытия со стороны
клиента. Раз в секунду снимать все FD и socket FD каждого worker отдельно,
включая дренирующие поколения; максимум socket FD / worker_connections и
всех FD / soft FD limit должен быть <0,70 для каждого процесса на всех пробах.
Socket FD включает listeners и upstream и служит консервативной верхней
оценкой занятых nginx connections, а не суммой по узлу. Неполные /proc-данные
или неизвестный лимит дают INCOMPLETE, сумма по workers не скрывает перегрузку.

Задержка: по 500 новых TLS/HTTP соединений для baseline и candidate в отдельных
окнах не менее 60 секунд, поровну по двум прежним маршрутам, одинаковое
чередование и открытый темп 8 запросов/с. Время измеряется monotonic от начала
TCP connect до первого байта HTTP-ответа, включая TLS. p95 — nearest-rank:
отсортированное значение с индексом ceil(0,95×N)-1; сравнить candidate p95
минус baseline p95 отдельно для каждого маршрута. Все 500 запросов обязаны
успеть в окно с HTTP 200 и ожидаемым учебным телом; timeout/пропуск/ошибка
делает прогон FAIL. Эту сетевую пробу выполнять только изолированно.
Настоящие соседи/special проверяются безопасными штатными сценариями отдельно;
учебный HTTPS backend не принимает протокол special.

Числа 100/70%/10 мс/15 минут — инженерные пределы этой приёмки, выбранные
исполнителем 27.10 для ограниченного органического старта. Они не заменяют
полный нагрузочный T097 и не разрешают прерывать чужие рабочие соединения.
Если исходный остаток ресурса меньше, переход блокируется до отдельного
согласованного изменения ёмкости. Измерять оба тракта на одном узле.

До применения: закрытая серверная копия 0700/0600, одинаковые хеши входов
между audit и применением, `nginx -t`, existing deploy/config lock. Применение
и возврат — стадиями по plan; disk config/reload exit0 не заменяют probes
обслуживающей генерации. Точный Uvicorn peer применяется отдельной стадией

автоматически; рабочая запись требует своих T110/T118/T119 и других ворот.

В доказательствах — source SHA, версия nginx/Uvicorn, тип сети, числа,
HTTP-схемы и результаты сравнений; без raw IP/их хешей, dump секретов,

PR/Full/CD, рабочая приёмка и коммерческий результат — отдельные состояния.
