# F273/T113: L6 через предварительный отзыв допуска

Проект на source `71fffe15c3d86630e8a7e22105df997c96b806d7`.
Принцип принят независимо: **SCOPED L6 ARCHITECTURE PASS, I1/I2=0**,
[отчёт](t113-platform-trust-review-20261031.md#повторная-проверка-i1i2-scoped-l6-architecture-pass).
Принимается ограниченный архитектурный договор; полный L6/J1 остаётся HOLD
до фактического охвата установки. Проверенный proposal SHA256:
`043ef40de08f7d2c6f95cf5116fd7192ac824cfd13efafc77ba2da4ec8dde289`.
Это проект, не код/установка и не полный J1 PASS. Сохраняются fixed T0,
полный initial/backup/restore, L1–L5, native locks, закрытые roots/UID1003,
ресурсы и оба unconditional HOLD. API не получает root или чтение секретов.

## Причина и выбранный механизм

Непривилегированный API сейчас не может заново прочитать весь root-only
scheduler/config inventory. Root receipt с digest/возрастом этого не решает.
Вместо нового watcher/service — обязательный предварительный отзыв ready
для каждого **фактически поддержанного автоматического mutator** платформы.
Существующие read_ready и SH/EX fence уже дают общий admission boundary.
Ordinary verify и полный оператор по-прежнему читают current generation
с достаточными правами; автоматического возврата ready после обновления нет.

Для APT-клиентов кандидат — fixed DPkg::Pre-Invoke в локальной конфигурации,
вызывающий отдельный revoke-only режим существующего root bootstrap.
Режим пользуется закреплённым stdlib-кодом ActivationFence.revoke,
не готовит uv/зависимости и не запускает продукт/DB/backup/recovery.
Он не принимает путь, SQL, expected digest, pass-file или новое T0 от caller.
Конфигурация фиксированной установки и trusted source проверяются до действия.

Порядок revoke-only: NB существующий deployment flock → filesystem EX с
существующим конечным пределом → durable revoke/fsync/readback → release.
EX дожидается обычного освобождения активных SH. Это не доказательство
завершения SQL после смерти клиента: его advisory xact-lock может жить дольше. Ошибка,
busy, timeout, подмена inode или неопределённый fsync не дают exit0;
поддержанный mutator обязан остановиться до первого опасного изменения.
Hook не получает APT/dpkg locks повторно: ими уже может владеть его caller.
NB deployment исключает взаимное ожидание с полным оператором, который
держит deployment и неблокирующим образом получает native locks.

После exit0 все следующие API admission видят revoked под прежним SH;
обычные SH закончены, но crash/unknown SQL этим не объявляются settled.
Для эффекта, которому нужен DB settlement, обязательны прежний DB EX (273,3)
и поддержанный drain/полный оператор либо HOLD; простой hook его не разрешает.
APT может продолжить только эффект, принятый без такого требования,
продукт не останавливается из-за обычного analytics HOLD. Failed/no-op update
тоже оставляет revoked; это допустимый лишний отказ аналитики, не новый T0.
После изменений только полный verifier под native locks/EX заново принимает
current generation и прежние data/lifecycle/resource/access proofs для той же
initial. Hook никогда не пишет ready и не обещает отменить уже начатое изменение.

## Конечная область и незакрытые условия

Это **не утверждение**, что одного DPkg hook достаточно всей установке.
До допуска требуется конечная карта каждого actual автоматического entry:
effective argv/env/APT_CONFIG/admindir → полный порядок hooks → первый опасный
эффект. Hook должен быть неустранимым в принятой модели и предшествовать этому
эффекту; ранние APT::Install::Pre-Invoke/иные delegates классифицируются отдельно.
Прямой dpkg, самостоятельный Snap, deferred needrestart/reboot/D-Bus, изменения
cron/units/config вне этого пути либо имеют доказанный harmless vendor role,
либо свой поддержанный предварительный отзыв/native exclusion, либо дают HOLD.
Не добавлять произвольные хуки на все службы ради предполагаемого охвата.
Прежнее исключение ручных параллельных root-действий не расширяется на jobs.

Без независимой текущей проверки всего этого набора L6 остаётся DESIGN HOLD.
После снятия native locks API полагается на доказанную полноту prechange
invalidation, а не на скрытый root readback или периодический stale receipt.
Пропущенный mutator — реальный пробел, не допустимое уменьшение цели.

Сохранённые точные исходники apt 2.8.3 подтверждают только локальную часть:
dpkgpm.cc 1540–1558 вызывает RunScripts(DPkg::Pre-Invoke) до Pre-Install-Pkgs
и возвращает false при отказе. RunScripts/outer callers и фактический порядок
всех entries этим excerpt ещё не доказаны. Source receipt SHA256:
3404b797b2ac9976ff2def0102ac48b4173da5790e72443936517b95020f6fa0.

Требуемые проверки будущей реализации: event удерживает SH → revoke ждёт →
event COMMIT → revoke durable → mutator starts → новый event rejected;
busy/unknown outcome не запускают mutator; повторный hook не меняет T0;
APT/GRAF lock inversion завершается HOLD без deadlock; отсутствующий/обойдённый
hook и каждый неподдержанный внешний executor не дают generation PASS.
Нативное APT-поведение проверяется на пустой временной базе, без рабочего
dpkg configure/установки. Влияние ошибок hook на штатные security updates
нужно явно принять: постоянный отказ не должен маскироваться как успех или
приводить к самовольному отключению обновлений.

## Уточнение I1/I2: непрерывное окно и предел SQL

Prechange revoke закрывает **новые activation admission**, а не все записи
продукта и не всю PostgreSQL. Умерший клиент мог оставить COMMIT в сервере;
filesystem EX не заменяет DB EX и полный product drain. Actual restore,
schema/data replacement и любой иной эффект с требованием DB settlement
не поддерживаются одним этим hook. При unknown SQL следующий verifier
не возвращает ready по одной файловой EX: он использует прежний DB EX/
сверку фактических исходов и остальные полные proofs. Hook не получает
универсальное право останавливать продукт или игнорировать транзакции.

Для синхронного APT допустима только следующая **доказанная для конкретного
entry** непрерывная последовательность (не общий вывод обо всех клиентах):

1. Caller уже держит тот native lock набора L1, который конфликтует с любым
   ready writer. Этот lock сохраняется через hook, всё опасное тело и последний
   опасный Post-Invoke; исход/освобождение установлены полным caller trace.
2. Hook получает deployment NB. Если готовый verifier уже держит deployment,
   hook немедленно отказывает; caller не начинает опасное тело. Если APT уже
   держит native lock, verifier не может получить полный native набор и
   возвращает HOLD **до ready**, а не ждёт hook. Взаимного ожидания нет.
3. Hook получает filesystem EX, durable revoke/fsync/readback; обычные
   SH закрыты. При crash SQL действует предел I1 выше. Только после exit0
   hook освобождает свои locks, и caller продолжает поддержанное тело.
4. Caller всё это время сохраняет конфликтующий native lock. Каждый initial/
   backup/verify/resume/иной writer ready обязан держать полный набор L1
   до последней durable attempt; нет отдельного раннего writer ready. Поэтому
   verifier не может вклиниться между revoke и последним опасным эффектом.
5. После доказанного последнего опасного эффекта и settlement caller отпускает
   lock. Лишь новый полный verifier получает весь набор, принимает current
   generation/DB outcome и прежние proofs и пишет ready для той же initial/T0.

Если caller отпустил lock до позднего опасного действия, этой ветви **нет**.
Отложенный delegate либо доказан harmless, либо на своём фактическом входе
должен повторить защищённый revoke и иметь собственную непрерывную сериализацию
со всеми ready writers до последнего эффекта, либо вся установка остаётся HOLD.
Повторить revoke заранее, подождать таймер/увидеть пустой list-jobs недостаточно.
Не утверждать отсутствие pending действия по одному current snapshot. Полный
J1 остаётся запрещающим gate, пока все actual deferred entries не классифицированы.

## Ошибка hook и обновления безопасности

Hook при busy/timeout/unknown fsync возвращает nonzero без опасного продолжения;
ошибка не превращается в exit0 ради зелёного статуса. Он выдаёт один фиксированный
metadata-only код в существующий журнал, без command/env/путей/секретов. APT
таймеры остаются включены; следующая штатная попытка повторяет весь admission,
не дописывает PASS и не начинает новый T0. Постоянный отказ требует действия
действующего оператора по журналу: устранить недоступность/конкурирующую
операцию и повторить штатное обновление с тем же проверяемым revoke. Отключение
security updates, обход hook, принудительный ready и бесконечный быстрый retry
не являются восстановлением. До установки обязательна проверка на фактическом
entry: hook failure виден оператору и существующему наблюдению, даже если
apt.systemd.daily подавляет вывод или возвращает итоговый exit0. Один статус
systemd здесь не принимается; точную привязку к журналу/существующему guard
ещё нужно доказать, а не объявить уже установленной.
