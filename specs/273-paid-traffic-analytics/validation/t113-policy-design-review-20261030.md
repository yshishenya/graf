## Первоначальные замечания и их закрытие до реализации

### P2-01: происхождение shell-переменных — устранено в проекте

Предложение, строка 10: «только escaped $$ преобразуется в $,
неразрешённые $VAR/${VAR} в сравниваемых командах запрещены».
После указанного преобразования текущий entrypoint `rec-minio-init`
содержит `$MINIO_ROOT_USER`, `$TWOBRAIN_MINIO_BUCKET` и другие разрешённые
shell-переменные; entrypoint `rec-temporal` содержит `$(cat ...)`.
Это существующие элементы доверенной команды, а не подстановка окружения
оператора. Проверка после unescape либо отвергнет штатную установку, либо
потребует неописанного исключения. Правило также должно исключать повторный
разбор списка argv через shlex: многострочный shell-script является одним
аргументом после `-c`.

Минимальное уточнение: проверять исходную строку штатно разобранной Compose
модели **до** unescape; каждый допускаемый знак `$` должен происходить из
пары `$$` в закреплённом source. Неэкранированная Compose-интерполяция даёт
HOLD. Затем заменить пары один раз, без shell expansion, eval и подстановок
окружения. Списки Entrypoint/Cmd сохранять поэлементно; строковую команду
разбирать один раз до получения argv. Не разбивать содержимое отдельного
аргумента `sh -c` или `bash -c`.

Добавить положительное доказательство точного argv для обоих существующих
entrypoint и отрицательный случай с исходным неэкранированным `$VAR`/`${VAR}`.
Сопоставить результат со штатным Compose/Docker на собственных временных
ресурсах, включая поведение выбранных флагов `config --no-interpolate`.
Это также закрывает неопределённость, на какой стадии Compose оставляет `$$`.

**Проверка исправленной редакции:** пункт 2 теперь требует сначала проверить
отсутствие одиночного `$` после удаления пар `$$`, затем выполнить однократный
unescape. Готовые списки argv сохраняются по элементам. В дополнении явно
обязательны оба точных многострочных entrypoint через собственный Compose create
без запуска init, с последующим inspect. Алгоритм определён; исполнение этих
положительных и отрицательных проверок остаётся обязательным после кода.

### P2-02: единый фактический источник logical secret — устранено в проекте

Предложение, строка 13, требует защищённого реального Source и закрытого
списка destination, но не связывает Source между потребителями одного
top-level secret. Например, `twobrain_postgres_password` используется
`rec-postgres`, `rec-temporal`, `rec-migrate` и `rec-db-runtime-bootstrap`.
Разные защищённые обычные файлы с правильными правами под одним logical secret
могут пройти описанные локальные проверки. Часть потребителей не проходит
`_runtime_settings`, потому что это инфраструктура или остановленный
initializer. Метка config-hash и правильный destination такого расхождения
не доказывают. Для буквального `secrets.<name>.file` предложение также не
определяет обязательное равенство с объявленным файлом.

Минимальное уточнение: построить закрытое соответствие
`secret name → canonical actual Source + dev/ino` и требовать его одинаковости
у всех фактически присутствующих потребителей этого имени, независимо от
running/exited. Для буквального статического file сначала вычислить ожидаемый
путь относительно канонического `root/infra` и сравнить с actual Source.
Для предусмотренного `${...:-...}` допускается фактический путь установки,
полученный из mount metadata, без чтения окружения оператора; при этом правило
единственного источника на имя и прежние проверки canonical/ancestry/ACL/
regular-single-link обязательны. Неподдержанный вид source-декларации — HOLD.
Привязку и её идентичность включить в private digest; при завершении проверки
снова подтвердить метаданные/идентичность удержанных файлов и текущих путей.
Содержимое ненастроенного секрета читать и выводить не требуется.

Добавить отрицательный случай: один secret name у двух служб с разными
защищёнными файлами, включая остановленный initializer; положительный — один
файл у разных destinations/служб. Отдельно проверить неверный static file.
Имена разных optional secrets вправе разделять один канонический пустой
placeholder: правило устанавливает единственность источника **на имя**,
а не запрещает разрешённое совместное использование одного файла.

**Проверка исправленной редакции:** дополнение теперь задаёт единый registry
на logical secret, канонический Source и полную `_settings_file_identity`,
сверку всех присутствующих потребителей и повтор всего registry в конце.
Статический file привязан к исходной декларации. Динамический file допускается
только как цельное `${NAME:-DEFAULT}` из доверенного source, без окружения
оператора и без неявного расширения шаблонов. Добавлены отрицательные случаи
разных файлов, замены inode и несовпадения статического пути. Общий placeholder
разных logical secrets разрешён с сохранением прежней закрытой матрицы Settings.
Алгоритм определён; фактическое покрытие должно подтвердить финальное ревью кода.

### Дополнительное уточнение пустого argv до кода

После первого заключения исполнитель предоставил
`.dev/growth/t113-policy-empty-argv-20261030.json`. Результат четырёх собственных
Compose create показывает наследование image Cmd при `command: []`,
`command: ""`, `entrypoint: []` и сочетании пустых entrypoint/command для
проверенного образа с Entrypoint=null. Поэтому первоначальное упрощение
«[] очищает Cmd» не может служить алгоритмом сравнения с actual Config.

Последний раздел исправленного предложения определяет последовательность
Engine merge: source entrypoint с сохранением None/[]; source argv команды;
при пустом entrypoint пустой command наследует image Cmd; только None
entrypoint наследует image Entrypoint. Непустой явно заданный entrypoint
оставляет отсутствующий/пустой command пустым. Различие None/[] сохраняется
до вычисления результата, и только окончательные пустые argv нормализуются
для сравнения. Это устраняет неверное допущение до кода, не меняя действующие
образы, Docker или продукт. Алгоритм определён и принят.

Прочитанный JSON относится к образу с пустым Entrypoint. В нём нет отдельного
доказательства образа с непустыми Entrypoint и Cmd; этот вариант и override
service command прямо обязательны в будущей причинной матрице реализации.
Ревьюер native-пробу не запускал; сведения о собственной очистке получены от
исполнителя, не из этого ограниченного JSON. Дополнение не расширяет scope и
не является проверкой готового кода.
