### F1 — неполный ответ API становится available и delivered

Новый `probe_telegram_channel` проверяет подстроку `"ok":true`, а не корректный
JSON и булевый результат (`alert-analytics-degradation.sh:516/525`).
Переиспользуемый `deliver_telegram` делает то же на строке445. Поэтому
неполный JSON, HTML/ошибочный ответ с этой строкой и противоречивый JSON
могут открывать канал и публиковать delivered receipt.

Независимый фактический прогон observer/sender через curl/logger stubs,
возвращающие для Telegram HTTP200 и обрезанное тело `{"ok":true`:

1. При здоровой цели — exit0, `channel_status=available`, `result=ready`.
2. После двух отказов цели — `delivery=delivered`, `notified_outage=true`,
   хотя целый подтверждённый ответ API не получен. Повтор затем подавлялся бы
   как уже доставленный по существующему состоянию.

Это нарушает принятую границу unknown/incomplete и правдивость доставки.
Нужно строго разобрать JSON-объект и требовать булевое `ok is True` для
канального probe и доставки в общем транспортном пути. Нового Telegram
транспорта не требуется. Отрицательные проверки должны включать хотя бы
обрезанный ответ для channel и send, с отсутствием ложного receipt.
Переиспользование старого transport не делает этот исход допустимым в T119.

### F2 — assert отключает закрытую схему и допускает вывод лишних полей

`check-graf-availability.sh:47–55` выполняет все проверки закрытой схемы через
Python `assert`. При допустимом для интерпретатора `PYTHONOPTIMIZE=1` они
удаляются, после чего `state.update(loaded)` сохраняет и печатает произвольные
лишние поля. Служба не фиксирует этот режим, поэтому защита формата не должна
зависеть от optimization. Даже без утверждения, что production сейчас запускает
Python с оптимизацией, локальный проверяемый путь допускает её обход.

Независимо: создан обычный healthy state, в него добавлено только поле
`unexpected=synthetic-private-sentinel`; выполнен реальный observer с
`PYTHONOPTIMIZE=1`. Результат — exit0/ready, неизвестное поле и sentinel вышли
в stdout и снова попали в state. Принятые строгие метаданные должны отвергать
unknown, не переносить его в доказательства. Минимальное исправление —
явные проверки с безопасным отказом/исключением вместо assert и проверка
обоих режимов Python; нового хранилища/планирования не нужно.

Удалены тело ответа из журнала и неиспользуемый redactor. Прочитаны все
применения нового helper, включая существующий локальный channel режим.

Независимо выполнены9 вариантов тела Telegram на фактических observer/sender
через stubs: обрезанный JSON, строковое true, число1, null, false, массив,

цели и delivered после порога. Stderr пуст; logger stubs не получили тело
ответа. Это синтетическое доказательство разбора, не настоящий Telegram receipt.

F2: вместо assert применены явные проверки точных типов, допустимых диапазонов,
закрытого набора ключей и значений до state.update. Независимо повторён
unknown-field sentinel в режимах PYTHONOPTIMIZE=0 и1: оба дают state_invalid,
ненулевой код, sentinel не появляется в stdout/stderr. Никаких assert в
защитной схеме больше нет.

Дополнительно самостоятельно пройден связный сценарий с отдельными запусками:
healthy → первый отказ/degraded → второй отказ и failed delivery → успешный
повтор доставки → подавление одинаковой тревоги → failed recovery notification
→ успешный повтор recovery/ready. Проверены mode0600 файла, занятая flock
(unknown/probe_already_running) и stale status при180секундах. Новый observer
не читает guard/backup/retention целевой машины и не обещает доступность
продукта при полном отказе; код service/timer прочитан, установка не выполнена.

Все собственные пробы использовали автоматически удалённые временные каталоги,
