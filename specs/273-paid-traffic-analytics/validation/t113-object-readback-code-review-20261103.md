## Исправленный P1/R1 — автоматическое HTTP-декодирование

Первоначальное место: `infra/scripts/rec-object-verify.py:185`, вызов
`response.stream(1024 * 1024)` без явного `decode_content=False`.
В текущей версии этот аргумент явно равен False.

В закреплённом urllib3 2.7.0 `HTTPResponse` по умолчанию имеет
`decode_content=True`; `stream(..., decode_content=None)` наследует это
поведение. Minio 7.2.20 `get_object` задаёт `preload_content=False`, но не
отключает декодирование Content-Encoding при выполнении HTTP-запроса.
Следовательно, объект с `Content-Encoding: gzip` может хешироваться после
распаковки. Проверка должна сравнить каждый сохранённый байт объекта, а не
его представление после HTTP-преобразования.

Собственная причинная проверка использовала настоящий `urllib3.HTTPResponse`
этой версии, стандартный gzip и учебный Client только для списка/HEAD:

- Исходный файл —54байта; отличающееся gzip-содержимое объекта — тоже54байта.
- Полный перечень и HEAD сообщают54байта и стабильные метаданные.
- GET возвращает именно другое gzip-содержимое с Content-Encoding:gzip.
- Первоначальный `verify()` распаковывал поток и возвращал строки, равные
  исходному манифесту: **checker_accepts=True при stored_bytes_differ=True**.

Это не предположение о повреждении рабочих копий: показан воспроизводимый
ложный положительный результат алгоритма на допустимом HTTP-поведении.
Равенство длин специально сохраняет все существующие проверки размеров.
Тест не подключался к MinIO или серверу, не читал реальные данные/секреты.

Основной агент внёс минимальное исправление — чтение raw entity bytes через
`response.stream(..., decode_content=False)`. Сравнение размеров и SHA256 осталось прежним. Добавлена
и прочитана регрессия с настоящим HTTPResponse/Content-Encoding; fake Response
теперь требует явно переданный decode_content=False. Разные сохранённые
байты той же длины не получают PASS.
Собственная повторная проверка с настоящим HTTPResponse подтвердила обе
стороны: источник23байта против другого raw gzip-объекта23байта отклонён;
исходный raw gzip-файл, в точности равный объекту23байта, принят даже при
Content-Encoding:gzip. Это исключает исправление путём простого запрета
всех gzip-заголовков. Перенос полного activation_operator не потребовался.
Настоящий SDK/MinIO прогон остаётся отдельным обязательным этапом.

## Прочитанные защитные пути и пределы оценки

- Host snapshot не импортирует SDK на уровне модуля; новые зависимости
  загружаются только для verify. Файл эталона создаётся O_EXCL/0600,
  записывается с flush/fsync и перечитывается.
- Обход открывает компоненты и дочерние объекты через no-follow FD, отклоняет
  ссылки/необычные файлы/hardlink/неверные права, проверяет источник до/после.
  Точное множество и SHA256 исходных файлов сравниваются с эталоном.
- Полное SDK-перечисление выполняется до/после; missing/extra/duplicate,
  размеры, версии, lifecycle/object lock и HEAD охвачены отказами в коде.
  Сами etag не используются вместо SHA256 содержимого.
- Ответ GET закрывается и release_conn вызывается вложенным finally,
  в том числе при исключении close. Успех после ошибки pool.clear не выдаётся.
  SDK-текст исключений не печатается; main возвращает фиксированный отказ.
- Последняя узкая дельта main задаёт region=us-east-1. Прочитаны методы
  Minio7.2.20 `_get_region`/`_execute`/`_handle_redirect_response`: при явном
  region кэш региона не заполняется, условие скрытого RetryHead не выполняется.
  Фактическая совместимость региона с учебным/рабочим MinIO ещё требует native
  проверки; неверный регион не должен получать fallback или PASS.
- HTTP timeout и отсутствие retry заданы; main устанавливает общий alarm
  и монотонный предел. Это не доказательство будущего parent/container stop
  и cleanup: их ещё должна реализовать и проверить shell-интеграция.
- SDK-сверка намеренно сравнивает с host-эталоном только files, не tree,
  из-за разных device IDs bind mount. **Обязателен будущий host source-check
  против полного первоначального tree до PASS**, как предусмотрено проектом.
  Без него одинаковые байты не докажут неизменность исходной файловой цели.
- Это не приёмка неизменности private manifest/родителей во всей будущей
  обвязке, фактических image/mount/user/group/secret-access, удержания общего
  deploy lock, завершения принадлежащего попытке контейнера или удаления
  корзины/БД/staging. Эти границы проверяются после интеграции.

## Локальные проверки

Собственный запуск профильного модуля с отключёнными bytecode/cache:

```text
PYTHONDONTWRITEBYTECODE=1 <существующий Python3.13 venv> -m pytest -q
  -p no:cacheprovider apps/server/tests/unit/test_rec_object_verify.py
Первоначально:33 passed, 2 warnings in0.21s; exit0
После исправления:34 passed, 2 warnings in0.62s; exit0
```

Предупреждения — прежние PytestAssertRewriteWarning и Starlette/httpx
deprecation. Minio7.2.20 и urllib3 2.7.0 проверены в использованной среде.
Первоначальный Content-Encoding пример выполнен независимо от модуля
и показал пробел33 зелёных тестов. После исправления повторный модуль
и две собственные raw-byte проверки завершились ожидаемыми результатами.
Они выполнены на checker7015db72 после raw-byte правки. Последующая дельта
0f6c351b добавляет только явный region/comment в main и независимо просмотрена;
34 unit-теста не выданы за проверку сетевого запуска main или image.

Набор содержит полезные missing/extra/duplicate, page-error, same-size,
short/long, source drift, специальные файлы, права, пустую корзину,
create-only snapshot и cleanup HTTP response. Это преимущественно подставной
Client/Response: он не заменяет настоящее SDK/MinIO-перечисление страниц,
проверки заголовков/таймаутов и native bind semantics. Его HEAD-failure
срабатывает также внутри fake listing; отдельные стадии следует причинно
различить в последующей приёмке, а не считать одним тестом все пути HEAD.
