## Требования первого локального периода

Прежняя находка проекта с поздним COMMIT закрыта в принятых требованиях:
filesystem SH дополняется PostgreSQL transaction advisory SH lock(273,3)
до конца COMMIT/ROLLBACK; actual restore требует filesystem EX → durable
revoke → ограниченный EX DB drain и отдельный полный product maintenance/drain
всех пишущих API/workers/transactions, включая late DELETE/account closure.
Обычный analytics HOLD сохраняет продукт и обязательные удаления.

local_only принимает одну account+event через общий admission, оба получателя
not_requested, внешних вызовов0 и последующего replay нет. Readiness находится
вне восстанавливаемой DB, сохраняет started_at и bindings. Первый старт
проверяется полной доверенной maintenance-ролью и историей закрытого writer;
count0 или нынешний флаг недостаточны. Потеря state/unknown gap закрывают
admission и не создают новый период. until_decision/точные удаления/основание/
раскрытие/ресурсная защита, полный GRAF backup и свежесть0≤age<26h, restore≤30дней,
минимум пригодных комплектов и last-attempt failure остаются обязательными.

## Узкий гейт безопасности репетиции и P2

Исходные четыре требования уже следуют из operations и quickstart:
изолированные create-only DB/bucket с очисткой только своих целей; уникальный
закрытый staging; проверка отсутствия своих DB/bucket/staging до PASS;
выбор полного пригодного GRAF комплекта вместо nginx-edge/ссылки/неполной копии.
Это условия существующего T113, без новой категории/получателя/сервиса.

| Риск | Действующее проверяемое основание | Вывод для исправления |
|---|---|---|
| Сигнал после успешного create, до owned=1 | operations: изоляция и проверенная очистка DB/objects/staging до PASS; infra CHK008/009; requirements RQ06/09/10/13 | Успешно созданная цель должна быть зарегистрирована как своя до выхода; команда с ошибкой не даёт владения. |
| Ошибка create при предсуществующей чужой цели | create-only и запрет удаления чужих данных; security CHK004/013/014; quickstart conflict case | Отсрочка сигнала не должна ставить owned=1 при failed/unknown create. |
| Унаследованный SIGINT ignore или сигнал между Popen и установкой forward handler | тот же отказ без ложного PASS и удержание общего lock до завершения работы/очистки | Установка обработчиков до Popen и pending stop до появления child устраняют потерю запроса остановки; child не должен наследовать SIG_IGN для INT. |
| Параллельная выкладка во время очистки | общая deployment-блокировка и cleanup-before-PASS | Передача того же flock FD и ожидание child сохраняются. Новая независимая блокировка не требуется. |

**PASS требований до кода,117/0.** Минимальная отсрочка завершения только на
интервале create→успешное owned=1 реализует уже принятое условие очистки.
Обработчик в этом интервале запоминает termination_requested; после определения
статуса создания обычный exit-trap возвращается, pending stop завершает запуск
неуспехом через cleanup. Не нужно игнорировать сигнал полностью, назначать
владение до успешного create, повторять create или удалять цель по одному факту
её существования. Ошибка/неопределённость создающей команды не является
подтверждённым владением; чужая цель сохраняется.

Supervisor устанавливает forward handlers до Popen, пока child отсутствует
сохраняет pending signal и после появления child передаёт остановку ему.
Это узкое закрытие окна запуска/унаследованного SIGINT ignore; прежние lock FD,
wait и ненулевой итог остановки сохраняются. Нового продуктового решения
или изменения spec/plan/tasks для этих исправлений не требуется.

## Собственное причинное red-воспроизведение P2

На указанном исходном helper использованы только TemporaryDirectory и
существующая учебная fixture с подставными Docker/MinIO. Учебная createdb или
mc mb сначала создаёт маркер своей цели, затем ждёт разрешения вернуть exit0.
Reviewer посылает HUP/INT/TERM Python-supervisor и разрешает завершение create.
Это проверяет именно промежуток успешное создание→owned assignment.
Ни Docker daemon, ни сеть, ни серверы не использовались. Учебные процессы
завершены, TemporaryDirectory удалены; рабочие данные не создавались.

| Ресурс | Сигнал | Итог процесса | Осталась DB | Остался bucket | Остался staging | Ложный PASS |
|---|---|---:|---|---|---|---|
| DB | HUP | 1 | да | нет | нет | нет |
| DB | INT | 1 | нет | да | нет | нет |
| DB | TERM | 1 | да | нет | нет | нет |
| bucket | HUP | 1 | нет | да | нет | нет |
| bucket | INT | 0 | нет | нет | нет | **да, запрос остановки потерян** |
| bucket | TERM | 1 | нет | да | нет | нет |

Для HUP/TERM утечка именно созданной цели воспроизведена в обоих местах.
INT нельзя объявить корректно обработанным: один прогон продолжил работу
до создания bucket с поздним выходом, другой вернул PASS. Эти результаты
показывают дополнительное окно/унаследованную обработку INT, а не разрешение
считать INT успешной остановкой. Поэтому обязательная регрессия должна
однозначно подтвердить фактический запрос/доставку stop, а не только отсутствие
ошибки от os.kill. Одна прежняя зелёная mirror-stop проба create-окно не покрывает.

Дополнительно reviewer повторил оба INT-сценария с явно заданным
унаследованным SIG_IGN перед запуском supervisor. Для этой пробы helper
прочитан через git show указанного source SHA и записан только во временную
область, поэтому последующие правки основной рабочей копии её не меняют.
После Popen контроллер восстановил свой прежний обработчик, послал INT
именно supervisor в точке create-ожидания и разрешил exit0 команды.
В обоих случаях запрос остановки потерян:

```json
{"resource":"database","inherited_sigint":"SIG_IGN","signal":"SIGINT","exit":0,"database_remaining":false,"bucket_remaining":false,"pass":true}
{"resource":"bucket","inherited_sigint":"SIG_IGN","signal":"SIGINT","exit":0,"database_remaining":false,"bucket_remaining":false,"pass":true}
```

Это самостоятельное подтверждение необходимости устанавливать forward
handlers до Popen; одних shell trap и отсрочки owned assignment недостаточно.
Доставка INT supervisor подтверждена os.kill; проверенный нынешний supervisor
переадресует INT, но уже запущенный shell сохранил унаследованный SIG_IGN.
Отчёт не принимает такую потерю stop за корректный успех.

## Обязательная приёмка реализации после этого гейта

- Причинно остановить каждый из двух create в подтверждённой точке ожидания:
  HUP/INT/TERM × DB/bucket × successful/failed create. При успехе созданная цель
  удалена и отсутствие прочитано обратно; при failed create foreign target
  сохранён. Во всех остановленных сценариях итог ненулевой и PASS отсутствует.
- Подтвердить удержание той же блокировки до завершения команды и очистки;
  сохранить обычную конкуренцию и supervisor TERM/KILL проверки.
- Проверить сигнал до появления child, отсутствие унаследованного SIGINT ignore,
  обычный успех, restore/mirror/drop/readback отказы, закрытые права и staging.
- Выполнить текущий объединённый профиль, независимое code review, scoped
  analyze/converge и точные PR/выпускные проверки основным исполнителем.

Предыдущее независимое code review проверило собственные TERM/KILL пробы
на mirror и41 профильный тест(2 предупреждения,32.19с,exit0). Оно закрыло
раннюю потерю lock после смерти supervisor, но не охватывало create-окно.
