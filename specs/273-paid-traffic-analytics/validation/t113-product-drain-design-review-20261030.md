## Минимальные обязательные уточнения

### D1. Таблица наличия и конечных состояний контейнеров

Проект строки32–48 сочетает «пять фиксированных writers», «неполный набор —
HOLD» и отрицательную проверку только running/restarting/paused. В реальном
Compose **rec-prompt-optimization-worker и rec-maintenance имеют профиль
operations**, поэтому могут штатно вообще не иметь контейнера. Неопределено,
какое отсутствие допустимо. Кроме того, status dead/removing/created сейчас
не исключён отрицательной проверкой и может ошибочно быть принят как остановка.

До кода достаточно одной явной матрицы:

- обязательные runtime службы должны присутствовать в ожидаемом количестве;
  отсутствие необязательной operations-службы допустимо только по заранее
  проверенной конфигурации/инвентарю и не ведёт к её созданию;
- для существующего writer после stop допустим только известный завершённый
  status `exited` с `Running=false`, `Restarting=false`, `Paused=false`;
  stop не обязан давать exit0, в отличие от успешной миграции/инициализации;
- migrate/bootstrap/minio-init должны иметь подтверждённое успешное
  завершение по принятому runtime inventory (либо явно допустимое отсутствие,
  если это действительно разрешено проверенным путём установки);
- `created/dead/removing`, неизвестный status, дубли/смена container ID,
  отсутствие обязательной службы, неизвестная project/network membership
  дают HOLD, а не «не running значит безопасно»; `created` для заведомо
  никогда не запускавшейся optional operations-службы можно явно отнести
  к отсутствующим writers, проверив PID0/все state flags, без её запуска;
- инфраструктурные postgres/minio/temporal сохраняются работающими с проверенной
  identity. Набор ID и membership повторно сверяется после stop.

Не нужна универсальная политика всех Docker-состояний: достаточно таблицы
этих существующих служб. Нужно добавить причинные проверки optional absent,
required absent, dead/removing, допустимый optional-created и запрещённый
required-created, failed initializer, duplicate/replaced ID.

### D2. Один точный предел для всего DB-шагa

В строках60–79 непонятно, начинается ли общий30с DB budget до ALTER или только
при ожидании advisory lock; «owner close» также не соответствует удерживаемому
owner-соединению в postgres, которое используется и для финальной проверки.
Если ALTER/identity и последняя проверка вне deadline, суммарный шаг может
превысить обещанный предел, хотя каждая отдельная часть успела.

Минимальное уточнение: один монотонный deadline создаётся при входе в DB drain
до первого identity SQL/ALTER; все owner/source execute, ожидания try-lock,
metadata и финальная identity/fence проверка получают только остаток. SQL
statement/command limits остаются верхними пределами и при меньшем остатке
сокращаются внешним deadline. Не выполняется ещё одна30с попытка. Удалить
«owner close» из описания: owner в postgres не относится к source PID и
сохраняется для подтверждения closed/OID; открытые source/owner connections
были подготовлены до мутации, их последующее закрытие принадлежит caller.

Timeout после отправленного ALTER означает unknown/HOLD независимо от того,
подтвердит ли отдельная последующая диагностика false. Следующий шаг не
выполняется и прежняя готовность не возвращается. Cleanup не обязан завершиться
за этот deadline ценой отпускания EX до разрешения DB task.

### D3. Владелец subprocess при отмене/таймауте

Проект требует ограниченный subprocess и удержание EX до разрешения DB task,
но не задаёт, что происходит с уже запущенным `docker compose stop` при
CancelledError/TimeoutError. Отмена ожидания `communicate()` не останавливает
клиентский процесс и уже принятую daemon-операцию. Нельзя оставить дочерний
процесс работать после возврата helper и считать освобождение context безопасным.

До кода закрепить конкретный узкий lifecycle: helper владеет своим child,
при отмене/таймауте прекращает только собственный CLI child при необходимости,
обязательно дожидается/reap его, не запускает stop повторно и не делает
start/restart/kill контейнеров. Успех после отмены не возвращается; состояние
операции daemon остаётся unknown/HOLD, пока владеющий верхний оператор его
не урегулирует. Отдельная отмена cleanup не должна отпускать EX раньше
завершения владельца ресурса. Это не запрос общего background-task framework;
достаточны локальный try/finally и проверенный владелец ожидания.

Для SQL остаётся уже заданная обязанность caller владеть connections и EX до
закрытия/разрешения отменённого DB task. В этом узком helper нельзя обещать
доказанную реализацию ещё не созданного верхнего initial/full restore operator.
Добавить причинный случай cancel/timeout после настоящего spawn: child не
осиротел, не произошло автоматического start и PASS отсутствует.

## Что уже достаточно и не требует расширения

- Deployment lock → существующий filesystem EX → durable revoke → stop
  writers → pre-open maintenance/owner → подтверждённый ALLOW_CONNECTIONS=false
  → session EX273,3 → все остальные PID/prepared → финальная identity/revoked.
- Session advisory lock подходит для удержания через metadata autocommit и
  последующий READ ONLY REPEATABLE READ экспорт. SH xact locks не подменены
  файловой блокировкой; SQL EX не отпускается helper до экспорта.
- Остановка API закрывает продуктовый ingress; отдельная правка nginx не нужна.
  PostgreSQL datallowconn=false закрывает новые source-подключения, включая
  owner; ранее открытая maintenance-сессия сохраняется.
- Проверка всех PID данного OID без фильтра по ролям/запросам и всех prepared
  transactions, pg_stat_clear_snapshot, отсутствие query text/private rows
  достаточны выбранной границе. Не надо добавлять terminate-backend/drop-force.
- Нет автоматического открытия БД/продукта, ready writer, нового T0,
  full actual restore/swap/resume CLI или снятия unconditional blocker.
- Граница доверенного host-оператора сохраняется; отдельный ОС-процесс не нужен.
  Отменённая полная прежняя marketing history до T0 не возвращается.
