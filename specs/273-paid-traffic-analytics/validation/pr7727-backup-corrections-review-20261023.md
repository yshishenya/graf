## Общая группа чтения состояния

Фактический Bash-блок runbook:745–781 требует явно выбранный для API
`TWOBRAIN_RUNTIME_SECRET_GID`, без молчаливой подстановки. Его regex и
верхняя граница совпадают с текущим `validate_runtime_secret_group` в
`infra/scripts/cd-remote-runtime.sh:125–130`; заново проверять членство
оператора в этом блоке не нужно, поскольку он принимает уже выбранную и
проверенную штатным развёртыванием группу.

Перед изменением проверяются все три файла: обычные файлы, не symlink.
Временный файл создаётся mktemp, старые строки только этой переменной
удаляются awk, одно выбранное значение добавляется, остальные параметры
сохраняются. `install -o root -g root -m0600` сохраняет закрытую установку.
Ошибки не разрешают дальнейший запуск; временный файл убирается trap.
При частичном отказе требуется исправить конфигурацию и повторить блок;
атомарная транзакция сразу трёх файлов не обещается и для этой границы не нужна.

Три env-примера теперь направляют к этому блоку. Ранние команды запуска
runtime-guard/timer убраны из вводного примера и заменены обязательным
переходом к подготовке; shell-переменная перед systemctl больше не выдаётся
за окружение службы. Все три существующих service читают нужные env-файлы.
API уже получает выбранную группу и существующие read-only bind, включая
retention. Архивный каталог не открывается API.

Тест исполняет извлечённый фактический Bash-блок, подменяя только три
абсолютных пути на временные и install на проверяемый stub. Проверены
нестандартная4321, повтор, смена на5432, ровно одна строка, сохранность
постороннего параметра и0600; отсутствующая переменная,0,123,01001,
2147483648,bad отклоняются без изменения трёх файлов. Stub проверяет
root/root/0600 аргументы, но не доказывает настоящее Linux ownership или
доступ процесса API — это остаётся операторской приёмкой.

## Очистка только собственного staging

`staging_owned=0` инициализирован до обработчика отказа. После lock и
проверки коллизии владение появляется только вслед за успешным mkdir.
`fail_backup` удаляет только точно этот процитированный target_dir;
родительский каталог, final или история не передаются rm. Ошибка удаления
записывается через существующий log_event с
`backup_staging_cleanup_failed`; исходный ненулевой отказ, failed state
и вызов alert сохраняются.

После успешного завершения Python publication владение снимается до
verified_sets/rotation. При отказе Python после rename, до снятия флага,
обработчик обращается лишь к уже отсутствующему старому staging; final
сохраняется. Это отдельно проверяется настоящим выполнением publication
с последующим искусственным ненулевым результатом, а не проверкой строки.

Исполняемые сценарии подтверждают: первый архив уже опубликован в staging,
второй записывает байты и только затем отказывает; собственный staging
исчезает, чужой `.foreign.incomplete/keep` и восемь исторических complete
наборов сохраняются; коллизия incomplete/final до mkdir не запускает
архивирование; отказ после rename оставляет final/.complete; отказ rm
оставляет staging, даёт критическую запись, failed state/alert и не PASS.
Существующая проверка ротации сохраняет незавершённый и повреждённый
исторические наборы. Массовой очистки каталога или удаления истории нет.

## Префикс настроенного проекта

Bash discovery:325 и Python verified_sets:102 заменяют ровно первое
`graf-posthog_` на `${project}_`, как существующий posthog-storage.py.
В обоих путях преобразуются шаблоны, не исходный файл. Исходный inventory
копируется побайтно; marker сохраняет digest этих исходных байтов.
Проверки project, текущего полного volume set, manifest, архивов и
нераспознанных labelled/mounted томов остаются.

Прежний ошибочный project-positive теперь использует настоящие имена
`replacement-project_*`; проверка полного успешного набора одновременно
проходит discovery и verified_sets. Старые наборы остаются, не считаются
текущими; inventory.txt и marker digest сверяются с raw исходником.
Отдельный old-only-negative передаёт новый project при одних старых томах
и требует ненулевой результат, отсутствие PASS и нового complete marker.
Дополнительные общие сценарии сохраняют отказы неполного/нераспознанного
inventory, недостаточного доказательства и ротации. Восстановление
согласованного PostHog не подменяется проверкой архивных байтов.
