## Доказанная причина

`product_analytics/router.py:197–236` выбирает максимум 20 ledger IDs, для которых хотя бы у одного получателя pending/pre_send_retry либо обнаружен stale dispatching. Порядок сейчас: stale первыми → accepted_at → id. После этого для каждого ID последовательно рассматриваются PostHog и Яндекс.

`milestones.py:413–455` возвращает technical_pre_send в pre_send_retry, basis_unavailable/provider_disabled в pending. Accepted_at при этих переходах остаётся прежним. Поэтому 20 самых старых строк с уже submitted PostHog и постоянно заблокированным Яндексом остаются первыми при каждом проходе. Новая 21-я строка с допустимым pending PostHog вообще не попадает в выбранные IDs. Независимые состояния/слоты провайдеров не помогают, потому что голодание происходит раньше claim, на общем подборе строк.

Существующий `test_scan_bound_and_no_hidden_backfill` проверяет 23 PostHog-only строки, которые после успеха полностью покидают подбор. Он не воспроизводит старые строки, остающиеся пригодными для подбора у другого получателя. Существующие проверки pre-send retry и независимости провайдеров не проверяют продвижение за лимит 20.

## Почему достаточно updated_at

| Место | Существующее поведение | Следствие |
| --- | --- | --- |
| `admit_account_milestone`, milestones.py:315–328 | accepted_at и updated_at получают одно серверное UTC now при INSERT. Повтор не переписывает их. | Новые решения получают исходное место по времени; уникальность/первый payload неизменны. |
| `claim_milestone_delivery`, :357–405 | Успешный claim записывает dispatching, новый attempt_id/attempted_at и updated_at=now. | Рассмотренная разрешённая попытка перемещается за давно ожидающие строки уже до транспорта. |
| `finish_milestone_delivery`, :408–455 | Любой разрешённый outcome обновляет updated_at только при совпадении dispatching и attempt_id. Это включает pending/pre_send_retry outcomes. | Постоянно заблокированная старая строка после рассмотрения перестаёт занимать начало следующего прохода. Неверный/поздний finish не продвигает её фиктивно. |
| `quarantine_milestone_deliveries`, :458–505 | Stale dispatching и restore quarantine переходят в ambiguous с updated_at=now. | Stale сначала освобождает recipient slot; эта попытка не повторяется. Если второй получатель всё ещё pending, строка далее участвует в обычной ротации. |
| Неуспешный claim | Нет записи updated_at при занятом advisory lock/наличии другого dispatching либо неподходящем состоянии. | Не нужен искусственный touch: попытки не было. Действующий получатель занят; после finish/quarantine подбор продолжится. При недоступной БД обещать прогресс нельзя. |

Минимальный новый порядок:

```text
ORDER BY CASE WHEN stale THEN 0 ELSE 1 END,
         updated_at ASC,
         accepted_at ASC,
         id ASC
LIMIT 20
```

Условие отбора, лимит 20, порядок обработки PostHog/Яндекс, закрытый enum outcome, условный finish и commit до сети остаются прежними. `accepted_at` не менять: это факт первого принятия, не позиция очереди. Не обновлять время всем выбранным строкам до claim, не отменять pending и не пересылать submitted/ambiguous для устранения голодания.

updated_at общий для двух получателей: это справедливая ротация **строк**, не обещание отдельной равной доли каждого провайдера. Успешный/заблокированный outcome любого получателя сдвигает строку целиком, но в уже выбранном проходе рассматриваются оба получателя. Это устраняет описанное R05 без двух отдельных очередей. Для конечного набора строк при доступных БД/worker и завершающихся попытках ранее ожидающие строки получают ход. Абсолютное время доставки при непрерывном превышении пропускной способности этим не гарантируется.

## Минимальная содержательная проверка в изолированной PostgreSQL

Добавить regression рядом с `test_scan_bound_and_no_hidden_backfill` в существующем `apps/server/tests/contract/test_activation_milestone_delivery.py`, используя реальную PostgreSQL и имеющиеся fake transports/isolated receipts, без рабочего провайдера:

1. Создать 20 старых уникальных ledger решений: PostHog submitted, Яндекс pending. Создать 21-ю более новую строку: PostHog pending, Яндекс not_requested. Явно задать accepted_at/updated_at так, чтобы все 20 были старше 21-й; не полагаться на порядок UUID или sleep.
2. Для старых Яндекс-попыток дать доказанный отказ до транспорта. Параметры: provider_disabled, basis_unavailable и technical_pre_send. Предпочтительно пройти настоящий `_deliver_claim` со scoped gate/secret stand-in, как в нынешних тестах; если исход моделируется, отдельно доказать, что transport не вызывался. PostHog transport возвращает synthetic 200.
3. Первый проход выбирает ровно 20 старых строк; транспорт не вызван. Их updated_at продвинулось, состояния Яндекса остаются pending либо pre_send_retry по исходу; PostHog остаётся submitted.
4. **Второй последовательный проход обязан захватить 21-ю строку**, отправить её PostHog ровно один раз и оставить submitted, не confirmed. Проверить UUID отправленного события и отсутствие Яндекс-транспорта. Старый порядок accepted_at этот шаг стабильно провалит.
5. Повторить третий проход: для 21-й второй PostHog-запрос отсутствует; old pending/retry не потеряны и не отменены. Количество ledger решений, event_id, accepted_at и safe_payload всех строк прежние; not_requested не стал pending. Возвращаемый размер каждого прохода ≤20.

Одна 21-я строка — достаточная граница для самого дефекта. Не нужно строить большой нагрузочный стенд. Для проверки общего shared updated_at полезен зеркальный параметр (старые PostHog pre-send retry, Яндекс новой строки доступен), если это не удваивает бессодержательные проверки текущего кода. Существенная проверка — достижение нового получателя за пределом старых 20, а не буквальная проверка текста ORDER BY.

**Уточнение по предложению исполнителя, принято до изменения кода.** Вариант из 23 новых строк, обеих requested providers и шести параметров blocked_provider × три причины равноценно и содержательно покрывает R05 в обе стороны. Настоящие `_deliver_claim/claim/finish` сохраняются; basis/disabled моделируются лишь существующим scoped readiness resolver, technical_pre_send — отсутствующим отдельным synthetic keyfile только заблокированного провайдера. Здоровый использует свой рабочий synthetic key, HTTP остаётся fake. После двух проходов здоровый должен иметь **23 уникальных отправленных UUID без повторов**; исходная сортировка оставляет только20. После снятия причины/создания synthetic key ещё два прохода доставляют все23 второму получателю. Дополнительно проверить прежние event_id/accepted_at/safe_payload и отсутствие confirmed. Важны явный порядок дат и отсутствие случайной зависимости от UUID; тест не должен требовать реальной секунды sleep. Этот ограниченный набор из шести сценариев принят; дополнительный зеркальный21-сценарий одновременно не нужен.

Дополнительно сохранить/выполнить существующие профильные DB-проверки конкурентных worker, единственного recipient slot, отсутствия SQL locks во время сети, stale quarantine, late finish, удаления и отсутствия resend ambiguous. Узкое дополнение stale-case: stale строка с более новым updated_at должна попасть перед обычной более старой pending и стать ambiguous без повторной передачи; второй provider при этом может продвигаться. Это проверяет, что новое поле не вытеснило первичный stale priority.

## Конкурентность и пределы

- Два worker могут прочитать один снимок IDs. Выборка сама не выдаёт право отправки; advisory transaction lock, persisted dispatching slot и attempt owner остаются обязательными. Не добавлять row locks на всю выборку или удержание locks во время HTTP.
- Обновление времени между SELECT и claim может дать повторное рассмотрение одной pending строки другим worker после доказанного pre-send отказа; это уже разрешённый повтор той же ledger вехи. Изменение порядка не разрешает повтор неизвестной передачи. Для текущего дефекта достаточно гарантировать продвижение последовательных завершённых проходов; строгий round-robin всех параллельных снимков не требуется.
- Stale приоритет сохраняется для освобождения глобальных recipient slots. Большой конечный stale набор разбирается порциями по 20. Нельзя выбирать только по updated_at и оставить свежую незавершённую dispatching блокировать провайдера навсегда.
- updated_at non-null уже в модели/миграции; оба admission timestamps и последующие обновления задаёт сервер. Нарушенные/будущие даты из ручных операций и существенный рассинхрон часов требуют честной неизвестности, но новая система часов для этого исправления не нужна.
- Существующие индексы — `(provider_state, accepted_at)`; добавление updated_at в ORDER BY может потребовать сортировки подходящих строк. LIMIT20 ограничивает результат, а не абсолютное число прочитанных SQL-строк. Не обещать постоянную стоимость подбора. Миграция/новый индекс без измеренной причины здесь не обязательны; при сомнении достаточно отдельного изолированного EXPLAIN на реалистичном размере, не теста рабочего узла.
- Изменение updated_at не подменяет время события/первого принятия, не меняет provenance и не подтверждает readback. Старые запреты restore/admission, оснований и удаления сохраняются. T113 и коммерческие критерии не закрываются этим исправлением.
