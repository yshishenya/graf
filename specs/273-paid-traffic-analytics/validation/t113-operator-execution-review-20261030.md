# T113: независимое ревью исполнения доверенного оператора

30.10.2026. Проверяющий `/root/f273_release_boundary`, исполнитель `/root`.
Основа `3a3076da88aef5e998b5f640f53e2efb4d4e7356`, ветка
`codex/f273-local-period-20261029`, полоса `high-risk-product`.

## Решение

**SCOPED PASS проекта: один доверенный host-оператор в отдельной временной
среде Python 3.13, собранной из точного исходного SHA и существующего
`apps/server/uv.lock`; существующие replay-функции получают только пониженные
сессии.** Отдельный процесс сверки не требуется принятым уточнением R2.
Готовность этого пути к рабочему запуску ещё не доказана: до product drain
нужна проверка временной среды и прямой достижимости PostgreSQL с host.
Ошибка такой проверки запрещает остановку продукта и восстановление.

Это выбор одного пути реализации, не разрешение нового произвольного
snapshot/pass CLI, не приёмка actual restore или включения аналитики.
Существующий `restore_replay.py` CLI остаётся только для учебных UUID-источников;
его regexp и параметры не ослабляются для рабочей БД.

## Прочитанные основания и граница привилегий

Полностью прочитаны проект R2/R3 с последующим решением B/T0, текущий
`restore_replay.py`, Dockerfile, необходимые зависимости упаковки, разделы
«Первый локальный период T113» и «Приёмка первого локального периода T113»,
скрипт/JSON/журнал новой PostgreSQL 17 пробы, сохранённый отчёт о ней и весь
requirements checklist. Прежнее полное чтение остальных требований применяется
в рамках разрешённого владельцем исключения F273; не заявляется новое полное
чтение PRD или всей истории статуса. Новое ревью не возвращает требование всей
маркетинговой истории до T0.

Принятое уточнение R2 §3 буквально говорит:

> Для replay/readback этот же оператор открывает отдельное owner-соединение и
> СРАЗУ выполняет SET SESSION AUTHORIZATION twobrain_rec_maintenance до чтения
> строк. […] Самим replay-функциям owner password/owner engine не передаются.

Это конкретизирует первоначальную фразу проекта «Owner password остаётся
только в уже привилегированном host-пути, не в reconciliation-процессе»:
привилегии остаются в доверенном операторе, функции сверки не получают пароль,
owner URL/engine или фабрику повторного owner-подключения. R2 не требует
отдельного ОС-процесса и не обещает изоляцию от злонамеренного кода внутри
доверенного оператора. Вводить такую новую обязанность через ревью нельзя.

**`SET SESSION AUTHORIZATION` не является необратимым снижением привилегий.**
При первоначальной аутентификации superuser PostgreSQL допускает возврат к
исходной авторизации через RESET. Отдельный процесс, получивший тот же backend,
сам по себе этого не исправляет. Низкоуровневый объект драйвера также не следует
считать очищенной от секретов песочницей: он может сохранять сведения исходного
подключения. Здесь проверяется доверенная граница вызовов и выполняемого SQL,
а не защита от произвольной интроспекции/вредоносной функции. Пароль не должен
передаваться отдельным параметром, через доступный replay engine URL/factory,
выводиться в журнал или передаваться обычному приложению.

Новая native-проба подтверждает текущие session/current_user после снижения,
атомарный откат/фиксацию двух rename, сохранение ALLOW_CONNECTIONS=false и
CONNECTION LIMIT 0, отказ обычного входа. **7/7 PASS** и cleanup своего кластера
следуют из прочитанных результатов исполнителя. Проба не проверяет RESET,
полные role flags/RLS и весь restore; отчёт исполнителя теперь честно это
ограничивает. Ревьюер ничего не запускал.

## Один конкретный порядок исполнения

1. **Подготовка до остановки продукта.** На host создаётся отдельный временный
   каталог/venv, принадлежащий оператору. `uv` использует точный проверенный
   source SHA, Python 3.13 из `.python-version` и frozen `apps/server/uv.lock`,
   только объявленные runtime-зависимости, без dev/default groups и правки lock.
   Project `.venv`, системные пакеты и существующие окружения не меняются.
   Если 3.13 отсутствует, его штатная подготовка выполняется до drain в
   управляемом временном назначении. Ошибка установки/импорта даёт HOLD.
   Источник установки должен быть закреплённым и недоступным для параллельной
   правки во время запуска; editable-импорт из движущегося checkout не подходит.

2. **Проверка среды и адреса.** Оператор подтверждает фактический путь импорта,
   исходный SHA, хеши lock/package, единственный packaged Alembic head и версии
   зависимостей. Из Docker inspect проверенного PostgreSQL-контейнера получает
   адрес только существующей private Docker network и перед использованием
   подтверждает неизменность container ID/cluster ID. Linux host подключается
   asyncpg прямо к этому адресу, без нового опубликованного порта, proxy или
   изменения HBA. Наличие `uv` и `docker exec psql` само по себе такую связь не
   доказывает; предварительный безопасный вход и проверка identity обязательны.
   Используются существующие проверенные credentials, не произвольный CLI URL.
   Source/image binding работающих служб независимо сверяется штатным inspect:
   host-среда не выдаётся за работающий образ приложения.

3. **Один доверенный оператор.** Он владеет deployment lock и затем постоянным
   filesystem EX, durably отзывает readiness, закрывает ingress и останавливает
   все пять служб, проверяет migrate/bootstrap/неизвестные экземпляры. Заранее
   открывает настоящую maintenance-сессию источника. Через существующий
   `docker exec psql` owner-путь в `postgres` подтверждает identity и фиксирует
   ALLOW_CONNECTIONS=false; maintenance держит EX advisory `(273,3)` и после
   drain всех чужих PID/prepared transactions делает READ ONLY REPEATABLE READ
   экспорт через прежние `database_context/closure_snapshot/replay_accounts`.
   Не вводятся новые grants/роль, terminate/drop-force или неизвестный ACK.

4. **Цель и приватный bootstrap.** CREATE новой UUID-цели сразу с CONNECTION
   LIMIT 0, owner pg_restore и полный существующий verifier сохраняются.
   Для replay приватная функция доверенного оператора открывает отдельное
   owner-соединение; первым прикладным SQL выполняет SET SESSION AUTHORIZATION
   maintenance, до чтения строк. Затем проверяет session/current_user,
   NOSUPERUSER/NOBYPASSRLS/NOCREATEDB/NOCREATEROLE/NOINHERIT, row_security,
   cluster/name/OID/revision и точные прежние policy/права. Неверная роль или
   неизвестный результат закрывают соединение и оставляют HOLD.

5. **Узкая передача сессии.** Для уже пониженного asyncpg-соединения создаётся
   отдельный SQLAlchemy AsyncEngine с `NullPool`, credential-free URL и
   `async_creator`, замыкающим только это уже открытое соединение. Он отдаёт
   его ровно один раз и отказывает при повторном checkout; не содержит owner
   URL/password или фабрики нового owner-входа. AsyncSession этого engine
   передаётся существующим функциям сверки/карантина/точных удалений. Передача
   сессии, привязанной к исходному owner engine, нарушила бы явное R2.
   Проверка контекста повторяется внутри транзакции, как в текущем helper;
   операторский/bootstrap код не импортирует main/router/worker/providers.

6. **Свежая проверка после COMMIT.** Оператор закрывает первую сессию и её
   одноразовый engine; отдельным приватным bootstrap открывает новое физическое
   owner-соединение, снова немедленно снижает авторизацию и повторяет identity/
   context. Только новая пониженная сессия делает readback. Отключение или
   неоднозначность после попытки COMMIT означает unknown, не rollback/PASS.
   При swap все source/target-сессии закрыты; обе rename выполняются одной
   owner-транзакцией в postgres. После swap требуется ещё новый пониженный
   вход для проверки новой identity при всё ещё нулевом лимите.

7. **Завершение.** Прежние условия run-token/digests, 0700/0600,
   O_EXCL/O_NOFOLLOW/UID/nlink и fsync сохраняются. Ошибка оставляет закрытые
   принадлежащие запуску цели/материалы и HOLD для canonical resume. Только
   полное проверенное завершение разрешает очистку собственной retired DB,
   возврат обычного лимита и запуск продукта с отозванной аналитикой. Временная
   среда после законченной проверки очищается штатно с проверкой владения;
   активные материалы восстановления не удаляются. Initial receipt и T0
   от этих действий не создаются повторно и не сбрасываются.

Подготовка среды целиком предшествует общему stop budget. Принятые connect5с,
statement25с/command30с, drain30с/stop120с и metadata autocommit SELECT с
pg_stat_clear_snapshot сохраняются; новый timeout дочернего процесса не
продлевает общий предел. Ни сеть установки, ни пакетный менеджер не вызываются
внутри остановленного продуктового периода.

## Почему выбран host-путь

Исполнитель сообщил read-only сведения host: Python3.12.3, `uv` есть,
SQLAlchemy/asyncpg и project venv отсутствуют. Сам ревьюер host не проверял.
Текущий pyproject/uv.lock требуют >=3.13; запуск существующим 3.12 неприемлем.
Lock содержит asyncpg0.31.0 и SQLAlchemy2.0.51, совпадающие с constraints образа.
Временная frozen-среда использует уже заявленные зависимости; новый пакет,
постоянная служба или общий протокол обмена не нужны.

Одноразовый доверенный app-image оператор технически возможен, но для этого
среза добавляет передачу host locks/каталогов/секретов, UID и управление child
при остановке всех runtime-служб. Он не даёт необратимости авторизации и не
выбран запасным автоматическим путём. Psql↔SQLAlchemy bridge, новая HBA/роль,
временный CONNECTION LIMIT1 и произвольный owner engine в replay не нужны.
Если прямой host-вход не подтверждён, этот проект остаётся HOLD до отдельного
уточнения; реализация не должна молча вводить один из этих обходов.

## Следующая независимая проверка и доказательства

До написания initial verifier и полного actual restore исполнитель должен
описать конкретный алгоритм этих двух операций и пройти обязательную
независимую проверку до кода. Текущий выбор способа исполнения эту проверку
не заменяет; 117/0 прежнего общего списка не является приёмкой нового кода.
Реализация после неё должна доказать:

- Предварительная установка/импорт точной версии, совпавшие SHA/lock/runtime
  binding и прямой host-вход без новых сетевых публикаций; отказ до drain
  при Python3.12, изменившемся исходнике, неверной identity или недоступной сети.
- Первое SQL до чтения строк и точные role/RLS проверки для replay, свежего
  readback и чтения после swap; отсутствие owner engine/URL/password/factory
  среди параметров и credential-free URL передаваемой сессии.
- Непустые учебные случаи карантина/удалений; сбой до COMMIT и неизвестность
  после COMMIT; отдельные физические соединения и одноразовый checkout.
- Полный product drain, late COMMIT/unknown writers/prepared transactions,
  соблюдение общего timeout и удержание locks до разрешения/закрытия сессий.
- Отказ/откат atomic swap на поздней сессии, canonical resume и сохранение T0;
  корректная очистка только своих завершённых ресурсов без ложного PASS.

Перечитан весь requirements checklist: **16 `[x]` /0 `[ ]`**, отметки не менялись.
Результат относится к согласованному способу исполнения. Initial verifier,
actual restore/rollback, рабочий T0, включение writer, T112/T113 целиком,
PR/CI/выпуск и коммерческие AC01–AC06 остаются открытыми.
