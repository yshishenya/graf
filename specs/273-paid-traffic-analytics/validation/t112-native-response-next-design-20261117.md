## Решение

**TEST DESIGN PASS, P1=0/P2=0 для одного следующего normal-случая, без fault и без global tracing. EXECUTION HOLD до конкретной реализации и отдельного implementation review.** Выбран не повтор one-GET пробника и не полный профиль87, а одна параметризация исходного `test_real_commit_acknowledgement_and_idle_return_keep_pair_and_foreign_generation[False]` с сохранёнными setup/relay/assertions и редкими прямыми отметками в тестовой копии. В ней уже есть один GET и два последовательных POST; дополнительных HTTP/SQL операций не добавлять.

**Один точный вопрос:** проходит ли неизменённая обычная native-цепочка GET с двумя HTML-подтверждениями → первый COMMIT и его полный ответ → ранняя очистка/F/B → второй явный POST с полным `accepted` и неизменными двумя durable строками, если глобальная трассировка отсутствует; если нет, какая из этих конкретных границ первой не достигнута?

Это проверка прохождения и локализация первой недостигнутой границы. Даже успех не установит причину исторического repeated `unavailable` и не докажет, что причиной прежних отказов была трассировка. Fault/M1 — отдельный следующий вопрос после чтения normal-результата; этот проект не назначает его автоматически.

## Почему сначала normal, а не оба случая

Текущий исходник integration:996–1290 прочитан целиком, включая callback commit, independent observer, ранние assertions, F/B, repeated POST и finally. Также прочитаны relay в budget:102–190, настоящий guard и принятые design/checkout review. Для normal и fault предпосылки GET одинаковы, но fault добавляет задержку COMMIT и независимое окно M1. Последние V4-параметризации остановились ещё на GET:1159; normal POST2 и fault M1 не достигнуты. Положительный отдельный GET не гарантирует их прохождения в полном native-setup.

Поэтому минимальный следующий случай — **normal False один раз**. Он проверяет HTML и реальный ответ без намеренного сетевого отказа, сохраняет первую COMMIT/return-границу и достигает именно прежнего normal POST2. Включение True сейчас добавило бы вторую причину и второй набор исходов раньше проверки normal-предпосылки. Отсутствие M1 в False — ожидаемое «не применимо», а не успешная проверка или отказ fault.

## Минимальный измерительный механизм

Не использовать `sys.settrace`, `sys.setprofile`, `sys.monitoring`, line/opcode/exception tracing, подмену asyncio/SQLAlchemy/native driver или polling собственных стеков. Не переносить V4 целиком и не устанавливать семь обёрток раннего GET. Нужны только следующие ограниченные тестовые добавления.

1. **Проверяемая тестовая копия.** Сохранённый исходный integration и runtime остаются неизменны. Подготовить отдельный инертный диагностический файл, основанный на точной копии текущего integration-модуля с хешем `1a326735...`, и затем временно разместить его в `apps/server/` для адресного выбора только указанного теста `[False]`. Полная копия сохраняет исходные imports/globals и fixture linkage; другие тесты из неё не выбираются. Изменять только тело данного теста для явных диагностических вызовов и добавить его локальные помощники. Никакого выполнения извлечённых строк через exec или автоматического подбора мест вставки по одному номеру строки. Проверить полный diff и AST: после удаления перечисленных диагностических добавлений и строго заданного обратного преобразования двух вызовов POST и аргумента app у ASGITransport исходные выражения, assertions, awaits, callback conditions и их порядок должны буквально соответствовать принятому native-тесту. Нормализатор не вправе удалять произвольные statements/arguments/assertions. Нужные imports/вход диагностической fixture также показываются в diff.
2. **Редкие прямые отметки сценария.** Снять status после естественного GET; число HTML-proof получать только из результата уже вызываемого `_proofs`, через прозрачную обёртку этой функции только в диагностическом модуле. Исходная функция вызывается ровно один раз на исходный вызов и возвращает тот же объект; входной HTML/результаты не удерживаются. Если исходный short-circuit не вызвал `_proofs`, число `None`, а не0. Сохранить исходные assert/status/proof extraction. Затем отметить: первый POST enter/return/raise; прохождение исходных ранних assertions до снятия gate; прохождение B/F до и после штатного gate.set; начало и результат второго явного POST; прохождение его исходного JSON assertion и equality durable rows. Исходный код JSON/DB проверок не заменять диагностическими bool.
3. **Прозрачная граница POST/ASGI.** Только два существующих `client.post` в копии делегируются через малую async-обёртку, вызывающую исходный bound method ровно один раз с прежними args/kwargs. Она сохраняет объект response, исходное исключение/отмену и сбрасывает request-local ContextVar в finally. В конкретном тестовом `ASGITransport(app=app)` оборачивается только этот app: исходные scope/receive и каждое message передаются неизменными и ровно один раз. Обёртка send отдельно отмечает attempted перед await и completed после его возврата; отдельно app return/raise. Никаких глобальных monkeypatch `httpx` или чтения HTTP body/headers/path/query. Не вызывать response.json/text для диагностики. Все прежние assert/json обращения остаются в самом native-тесте.
4. **Терминальные данные вне буфера.** Максимум48 подробных строк плюс фиксированные summaries GET/POST1/early-cleanup/B/POST2 и отдельный final snapshot, которые обновляются независимо от заполнения records. Счётчики attempted/completed start/body, terminal-body completion, app return/raise и post return/raise — по порядковому номеру запроса. Значения — только фиксированные имена стадий, число, bool, None, type/module исключения. Сроки брать из фактических `scope.state.result_view_deadline/result_view_cleanup_deadline` для соответствующего POST, используя тот же loop.time; неизвестные сроки оставить None. Не подставлять сроки POST1 к POST2, не создавать новый дедлайн от времени наблюдателя. Никаких frames/tracebacks/task/owner/DBAPI/строк/токенов в сохранённом выводе.
5. **Снимок до спасательной очистки.** Добавить синхронный снимок первым действием исходного scenario finally, до `armed=False`, watchdog.cancel, gate.set, task.cancel, ручных db.close/dispose. Взятые transient ссылки сразу превращать в числовые/bool признаки и не хранить. Поля: последний достигнутый этап; entered; snapshot_error только как type; количества исходных markers/returns и checkout offsets; target gate/held/done; `.done()`/`.cancelling()` уже известных post/observer/DB task; actual work/hard remaining или None; watchdog_fired; test assertion/exception type. Не выполнять там новые SQL/HTTP, не сканировать стеки. Снимок после естественного выхода из внутреннего AsyncClient не объявлять снимком до всех автоматических context-manager cleanup: это точка **до исходного явного scenario finally**. Ошибка POST дополнительно снимается его обёрткой непосредственно до распространения. Выводить JSON только после исходной очистки; ошибка диагностики не должна превращать исходную ошибку в успех.

В normal исходные public Engine/Session/pool callbacks уже собирают нужные commit/after_commit/reset/checkin/invalidate и checkout-корреляцию; новых listeners и запросов для их повторного получения не нужно. Детальный внутренний guard trace не входит в этот проект. Если внешние границы покажут его недостигнутый ответ, следующий более узкий разбор выбирается по этому результату, а не добавляется заранее.

## Критерии и остановка

| Первая проверяемая граница | Критерий | При невыполнении |
| --- | --- | --- |
| GET/HTML | Исходный HTTP200 и ровно2 proof из реального HTML; pool checkedout0, pair snapshot пуст | Остановиться до POST; это ещё не normal POST2 и не fault M1 |
| Первый normal POST | Исходные accepted/private-no-store, ровно1 новая operation, writes2/commits1; complete ASGI start и terminal body, исходный post возвращён | Остановиться на POST1; app return либо send attempted без completed body не заменяют полный ответ |
| Ранняя очистка/T/F/B | Все исходные assertions внутри hard deadline, commit/after_commit/reset/checkin; очищены owner/Session/keys/tasks; target idle/locks0; foreign здоров, B получает точное прежнее normal поколение и остаётся здоров после gate.set | Не переходить к POST2 и не принимать результат, достигнутый только finally/watchdog/dispose |
| Второй явный POST | Один исходный POST2; отдельный обычный request budget; completed ASGI start200/terminal body, app вернулся, исходный post вернулся; исходный JSON `accepted`, полные saved rows неизменны, provider_calls0, pool checkedout0 | Зафиксировать последнюю достигнутую и первую недостигнутую границы и исключение; нет третьего POST, retry, new proof/GET или ожидания до зелёного |
| Чистота наблюдения | Один выбранный False, source pins совпали, исходные assertions/сроки не менялись, нет недоказанных пропусков, cleanup подтверждена | HOLD; ошибка прибора не объявляется дефектом продукта |

ASGI completed значит успешный возврат исходного send: ровно один завершённый start и завершённое terminal body с more_body=false. Одно `app_return` или `post_leave` без этого недостаточно. Также полная ASGI-передача не заменяет исходные JSON/durable assertions. HTTPX `AssertionError` по response_complete — отдельный transport outcome; нельзя синтезировать unavailable или принять такой исход как корректный normal response. POST2 счётчики отделены от первого запроса и от первоначальных commit markers; уже исправленная checkout-корреляция сохраняется.

Прежние ограничения неизменны: guard2s/work1.5s/cleanup0.5s **на каждый исходный запрос**, SQL<=128, lock<=250ms, statement<=500ms, body/proof/response caps; native pool_size2/max_overflow0/pre_ping; два sequential warm соединения; прежние _real_app/http_period, relay и пустой Context() независимого observer. Ни задержки, ни lock order, ни F/B, ни после-COMMIT cleanup не заменяются. Watchdog3s остаётся только исходным выходом из неуспешного теста и обязан быть false при успехе; это не дополнительный бюджет запроса. Живые здоровые F/B sockets не считаются утечкой target.

После любого исхода — сохранить первичный журнал, безопасную квитанцию, source/probe/выборки hashes и доказательство удаления только своего контейнера и временного файла. При dropped>0 и отсутствующей существенной границе нельзя заявлять полную причинную цепочку; фиксированные summaries не теряются при cap. Не запускать ещё один normal, fault,87 или runtime fix автоматически. Успешный normal означает лишь проход normal-цепочки в этом опыте, unknown repeated HOLD остаётся до объяснения прежнего симптома.

## Fault/M1: отдельная граница, сейчас не назначена

После normal-результата новый gate должен явно решить, нужен ли один True. При его будущем проектировании сохраняется **весь** принятый causal M1: exact target COMMIT-enter один раз, target task не cancelling/POST pending; target server→client chunk реально удержан закрытым per-stream gate; target after_commit отсутствует; отдельная сессия видит две durable строки, backend ещё существует idle/no xact/locks0; F того же request pool здоров при закрытом target gate. Всё это — до исходного `min(work_deadline-.1, now+.9)` и до отмены. Недостигнутый `response_held` или истёкшее окно не являются unknown-COMMIT PASS и не разрешают сдвиг окна.

Только после такой M1 fault может проверять полный unavailable, invalidate→checkin(None), завершённое старое поколение/backend/relay до открытия gate, безопасные новые B/F и отдельный POST2 reconciliation без переписывания пары. Поздний snapshot после gate.set/teardown не заменяет M1. Нынешний GET и будущий normal сами этого не докажут. Прозрачная request ContextVar не охватывает independent observer/relay с Context(); явные метки в этих местах потребуют отдельного точного кода и review, без глобальной трассировки.

## Что требуется до исполнения

Сначала подготовить конкретный инертный diagnostic module и малый selfcheck без HTTP/БД: прозрачность original call/return/exception/cancel identity и ContextVar reset; attempted/completed send и app return/raise; proof-count wrapper без дополнительного парсинга; фиксированные summaries при переполнении; snapshot не падает на частично заполненном target и None deadlines; исходные assertions/awaits/order сохранены по AST/diff. Selfcheck не является HTTP/PG-приёмкой.

Затем **отдельный независимый implementation review точных файлов/хешей**, включая новый способ сборки/загрузки копии, нормальную параметризацию False, отсутствие автозапуска True/87, cleanup и отсутствие payload в отчёте. Старые early-proof/V4 PASS на новый модуль не переносятся. Только после такого PASS можно назначить collect-only с ровно одним node и container_not_started и один native normal запуск. Путь root-level копии потребует явного `-p tests.conftest`; не добавлять одновременно `tests/` к выбору, сохраняя проверенное ограничение регистрации conftest. Нового запуска в этом отчёте нет.
