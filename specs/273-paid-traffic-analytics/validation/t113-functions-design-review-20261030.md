# F273/T113: независимый проект сверки пользовательских функций PostgreSQL

Дата: 30.10.2026. Проверяющий: `f273_release_boundary`.
Основа: `91fb51b226710755b1866ee0a7360a40017ec78d`, ветка
`codex/f273-local-period-20261029`, F273/T113/#7804, `high-risk-product`.
Проверка до изменения кода; исходное рабочее дерево было чистым.

## Решение

**SCOPED DESIGN / ANALYZE PASS. P1=0, P2=0** для уточнённого алгоритма ниже.
Это разрешение реализовать узкую сверку routines в существующей T113 и
предъявить конечный код и тесты на отдельную независимую проверку.
Реализация и полный T113 этим решением не принимаются.

Полностью прочитана конечная редакция
`.dev/growth/t113-functions-precode-20261030.md`, SHA-256
`c072d9a4448a7f2b8b5caf4b8aefbcc4bb88a02c4b1e9f6067e708d4ff1348af`.
В ней до кода согласованы две существенные границы: пользовательские routines
не скрываются фильтром системной схемы; существующие read-only транзакции не
называются общей RR-транзакцией всего preflight. Неустранённых блокирующих
неопределённостей в принятом узком алгоритме не осталось.

## Обоснование и согласование с требованиями

`local_retention_database_catalog` сейчас сверяет четыре категории,
relations/extensions и семь точных trigger functions. Новый standalone routine
вне этих семи не меняет его доказательство. Это известный остаток T113,
зафиксированный в `tasks.md` и предыдущем независимом retention-проекте.
Его устранение согласуется с FR-036/038/050: сохранение без возрастной очистки,
сверка установленного кода с закреплённым источником и отказ от заявления о
готовности при неизвестной конфигурации. Проверка остаётся только чтением;
FR-032 не получает новую зависимость продукта от аналитики.

Прочитан весь действующий полный алгоритм T113 (473 строки), SHA-256
`5d1e069f3fe18f31a21c72c9b0abc41614ff8bfc00c3269f27b1f3cb596738ec`.
Его раздел local retention требует реальные functions/jobs проверки,
существующий источник с пониженными правами, повторную сверку и общий отказ
до полноты verifier. Новый этап закрывает только routine-часть этого остатка;
полный executable catalog и installed jobs не объявляются выполненными.

Новая фича, роль, grants, сервис, таблица, SQL-парсер миграций или caller-supplied
эталон не требуются. Константа, полученная из собственной чистой native PG17
штатных миграций, проще нового разбора всех SQL literals. Текущая source schema
либо schema.sql из её собственной копии не принимается как независимый эталон.

## Минимальный принятый алгоритм

1. В существующем `local_retention.py` закрепляется ожидаемый digest
   отсортированного полного пользовательского routine descriptor. Он создаётся
   из чистой собственной PG17 с текущими штатными Alembic-миграциями этого
   дерева и не меняется по данным проверяемого сервера. CLI, environment,
   receipt или вызывающий код не передают новый expected/PASS.
2. Отбираются все `p.oid >= 16384` независимо от схемы, в том числе
   `pg_catalog`, и любые routines неслужебных схем. Только встроенные системные
   routines с OID ниже этой границы исключаются. Ограничения `rec_*`, `public`
   или полного исключения `pg_catalog` нет. Имена/сигнатуры/OID проверяемого
   источника не используются для молчаливого расширения разрешённого множества.
3. Сначала читается и проверяется kind полного выбранного множества. Текущий
   эталон разрешает только `prokind=f`; procedure/window/aggregate/неизвестный
   kind дают HOLD **до** `pg_get_functiondef`. Проба, которая сначала вызывает
   deparser на aggregate, не является принятой последовательностью исполнения.
4. Descriptor включает namespace/name/identity arguments, полный
   `pg_catalog.pg_get_functiondef`, owner/language и заявленные return/security/
   config/argument/default/cost/parallel/volatility/strict/leakproof/retset
   свойства. Полный deparser text покрывает штатные определения, отдельные поля
   покрывают невыводимые из него свойства. Нулевой support и отсутствие
   `probin`/`prosqlbody` в текущем эталоне должны оставаться явными проверенными
   состояниями, а не причиной проигнорировать появившееся значение. Случайные
   OID пользовательских типов не становятся способом считать разные объекты
   одинаковыми. Исходный SQL не исполняется для сравнения.
5. Применяется одна и та же сортировка и JSON-сериализация descriptor при
   получении константы и чтении источника. Строго проверяется
   `SHOW search_path = '"$user", public'`; иной путь даёт HOLD. Source не получает
   SET search_path ради успешного совпадения. Все обращения к системным
   каталогам и deparser квалифицированы через `pg_catalog`. На текущем эталоне
   support=0 и обе nullable-структуры отсутствуют; произвольное разрешение новых
   языков/типов/поддерживающих функций не добавляется.
6. Сохраняются прежние семь точных trigger checks и проверка policy/relations/
   extensions. Общий routine hash не заменяет table/type/columns/args/WHEN/
   enable/constraint/transition и literal-body проверки триггеров.
7. Дополнительно требуется отсутствие пользовательских event triggers,
   неизвестных languages, FDW и foreign servers. Эти проверки выполняют
   реальные фиксированные запросы каталога, не проверяют только имена
   известных планировщиков и не объявляют отсутствие внешнего host cron.
8. Источник — прежнее удержанное физическое соединение и его read-only
   транзакция; нового подключения/повышения прав/RESET протокола нет. RR
   сохраняется в уже принятом `_backup_lifecycle`. `_runtime_databases`
   использует свои прежние read-only транзакции до снижения прав и при
   финальной повторной сверке; весь preflight одним RR здесь не объявляется.
   Native owner и reduced должны получить один digest. Отказ чтения,
   повреждение каталога, timeout, отмена либо изменение перед выходом дают HOLD.
9. В существующий общий proof входит вычисленный digest, наружу не выводятся
   тела функций/SQL/строки/идентификаторы клиентов или необработанные ошибки БД.
   Получение эталона на диске ограничено стандартными определениями миграций
   собственной учебной БД; определения рабочего сервера не сохраняются.

## Прочитанная учебная проба, без приёмки реализации

Полностью прочитан `probe-routines-20261030.py`. Он использует существующий
`postgres_isolated_cluster_database_url.__wrapped__`, принимает только loopback
и собственное имя учебной БД. Прочитан fixture: он создаёт новый кластер PG17,
а `prepare_schema` выполняет настоящий Alembic upgrade head, а не create_all.
В finally fixture удаляет принадлежащий ему контейнер.

Из JSON независимо прочитан descriptor всех 31 routines и пересчитан
`sha256(json.dumps(rows, sort_keys=True).encode())`. Получено
`f587419462003e7aa9116c51191c23ad7a885867bf880885386a068a7f0f8550`,
что совпало с записанным digest. Все 31 routine имеют kind=f, owner
`twobrain_rec`, схему public; языки sql/plpgsql. Лог сообщает
`owned_native_cluster_cleanup=pass`. Сам проверяющий кластер не создавал,
не подключался к БД и пробу не запускал.

Эта проба подтверждает получение выбранного descriptor на чистом кластере,
но не принятие ещё отсутствующего runtime-кода. В пробе deparser уже вызывается
до Python all(kind=f); такой порядок достаточен только для известного чистого
baseline. Реализация обязана применять предварительный kind guard из пункта3.

## Обязательная проверка следующего кода

- Причинный RED старого reader: добавить standalone SQL-функцию с DELETE
  учебной аналитической таблицы, не вызывать её; прежний каталог принимает
  изменённую схему. Новый reader должен отказать, а после undo вернуть тот же
  baseline. Данные ради этого сценария удалять не требуется.
- Чистая PG17 текущих миграций совпадает с закреплённым digest; понижение
  source-сессии не меняет доказательство. Ошибочный expected даёт отказ,
  а runtime не создаёт новый expected из изменённого источника.
- Обратимые extra routine/overload/другая схема/`pg_catalog`, изменение
  standalone body/security/config/owner/defaults/arguments/parallel и
  search_path drift дают HOLD. Процедура и aggregate отвергаются до deparser.
- Event trigger, неизвестный язык, FDW/foreign server дают HOLD. Отдельная
  проверка порядка запросов подтверждает, что unsupported kind не попал в
  pg_get_functiondef. Изменение каталога между первой и последней проверкой
  не принимается как прежний proof.
- Прежние literal/trigger/relation/policy/extension, source lifecycle,
  four-category replay и coherent backup проверки сохраняются. Native cleanup,
  конечные хеши и отдельное независимое code-review нужны до принятия кода.
