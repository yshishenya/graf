# T112 — серверный приём: проект продолжения

Дата:16.11.2026. Основа:a3ff5b8709dc5da61f4751c4eb3145eb84d9fc9e.
Полоса:high-risk-product, существующие T112/#7698 и T113/#7804.
Это рабочий проект для независимой оценки, не разрешение нового сбора.

## Обнаруженное различие проекций

GET использует общий get_cabinet_meeting_review с выбранными
summary_format и source_result_id. Нынешний observer посылает POST только
на pathname/result-viewed и теряет оба параметра. Если POST прочитает
проекцию по умолчанию, она может отличаться от показанного текста.

Нужна передача только этих двух существующих параметров на собственный
canonical POST URL и повторная серверная валидация. Остальные query,
fragment и proof в URL не передаются. Подтверждение по-прежнему только
в JSON; оно связывает фактические result/outcome/version/digest. Выбор
параметра не даёт полномочий: чужая/устаревшая проекция должна отказать.

## Общая граница вместо второго хранилища

Предложено переиспользовать ProductAnalyticsIngestService и
admit_account_milestone. Общий контекст транзакции/проверок получателей
для HTTP и server-auth не создаёт нового ledger. Настоящие
trigger_unverified для обычного JSON и activation_recovery_unverified
сохраняются. Доверенное начало периода не берётся из клиента, settings
или текущего времени: у T113 ещё нет принятого runtime verifier.

Положительный изолированный тест может подставить общую границу с fixture
started_at; это прямо допускает §5 договора result-visibility. Такая
подстановка не разрешает production, local_only, restore или рабочий T0.
Фиктивный положительный период или флаг trusted в код не добавляются.

## Предлагаемый защищённый путь

1. Один обработчик обоих canonical POST использует прежние
   PrincipalDependency/WebTenantDependency/WebCSRFDependency. Тело читается
   потоком до2KiB, только точное JSON-поле proof; ответ private/no-store.
2. Общий admission получает положенные filesystem/DB fences T113 и
   проверенный started_at. До этого измерение остаётся закрытым.
3. На отдельной2s транзакции после shared identity lock читаются заново
   действующие auth session/device, workspace/membership, затем прежние
   meeting/source/deletion fences. Lock≤250ms, statement≤500ms, без retry.
4. После guards общий get_cabinet_meeting_review заново выбирает разрешённую
   проекцию с двумя допустимыми параметрами. load_result_view_bindings и
   verify_result_view_proof связывают её с текущим владельцем/сессией/источником.
5. Expired даёт renewed только при полном совпадении свежего binding, без
   записи вех. Valid использует прежние построители result/value; каждый
   INSERT проходит свежий общий gate и правила получателей.
6. Два admit_account_milestone выполняются в одной транзакции, commit один.
   Accepted возвращается только после подтверждённого commit либо прежнего
   идемпотентного решения; ошибка/неизвестный commit — unavailable/no retry.
7. Render выдаёт proof только для той же свежей разрешённой проекции.
   При закрытой готовности возвращается пустая карта; просмотр сохраняется.
   Чужой, устаревший или изменённый результат разрешения не получает.

## Предел проекта

Контент и вёрстка не меняются. Новых таблиц/миграций/зависимостей/получателей
нет. Свободно трактовать отсутствие реализации T113 как passed запрещено.
Пока независимый reviewer не подтвердит конкретную общую границу и порядок
locks, зависящий server-admission код не начинается. Отдельно допустима
проверка/исправление потери двух существующих параметров, если reviewer
подтвердит её соответствие текущим требованиям.

FR-021: выбранный показанный текст и свежий владелец/версия; FR-025:
совместное устойчивое решение; SC-006: общая семантика browser/desktop.
Остаток уже покрыт открытыми T112/T113, дубль задачи не создаётся.
