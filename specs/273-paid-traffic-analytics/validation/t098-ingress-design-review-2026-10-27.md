## Решение

**Условно принят протокольный кандидат для продолжения T098; рабочее применение
и полная приёмка T098 заблокированы.** На установленном nginx 1.24.0 разумный
кандидат состоит из штатных директив, отдельного TLS-порта ГРАФ и двух внутренних
stream relay для прежних маршрутов. Безусловное утверждение «не влияет на
соседей» доказательствами пока не поддерживается.

Предпочтителен уточнённый вариант v2:

1. Публичный stream443 продолжает принимать обычный TLS, без входного
   `listen ... proxy_protocol`; на исходящих соединениях включается
   `proxy_protocol on`.
2. Точное SNI `rec.2brain.pro` направляется в отдельный loopback TLS-порт
   ГРАФ с `listen ... ssl ... proxy_protocol`. Два прежних rec-listener10444
   заменяются новым портом. Старый rec10444 не сохраняется без доказанного
   потребителя и отдельной совместимой границы.
3. В двух proxy locations именно этого TLS-сервера XFF и X-Real-IP заменяются
   `$proxy_protocol_addr`, XFP — константой `https`. Пустой адрес, включая
   `PROXY UNKNOWN`, не достигает API. `real_ip_header`/`set_real_ip_from`
   здесь не добавляются.
4. Прежние default10444 и special443 направляются через два отдельных
   loopback stream-listener, принимающих PROXY envelope и передающих прежним
   адресатам TLS-поток без envelope. Прежние HTTP/Xray-конфиги и socket-флаги
   shared10444 не меняются.
5. Отдельный публичный8443 платежей остаётся прежним прямым TLS listener;
   доверие Uvicorn к непосредственному Docker peer принимается отдельно
   после проверки всей цепочки.

Это принятие устройства протокола, а не разрешение пропустить обновление
T098 plan/scenario, reviewer/analyze/issue sync, испытания и выпускные ворота.
Исходный вариант с HTTP realip требует отдельного решения по журналам и
не является предпочтительным минимальным исправлением.

## Доверие, обход и журналирование

PROXY protocol не аутентифицирует отправителя. У v2 доверие основано на
проверенном входном сокете, его точной loopback-привязке и недостижимости
со стороны недоверенных контейнеров/внешней сети. Нельзя объявить доверенным
любой адрес в envelope или заменить эту проверку добавлением широкого CIDR.
Локальный администратор/root остаётся доверенным участником, как в прежнем
network review. Для недоверенных host-network контейнеров либо локальных
пользователей такая граница недостаточна: они должны быть явно инвентаризированы.

Нужны проверенные правила: public443 не принимает пользовательский envelope;
dedicated rec-port не принимает обычный TLS без envelope и не передаёт пустой
адрес; клиентские XFF/XFP/X-Real-IP полностью заменяются; недоверенные container
paths не получают доверие Uvicorn через тот же принятый peer. На relay исходящий
PROXY должен быть явно выключен, иначе унаследованное `on` снова отправит
envelope старому серверу. Входные и исходящие socket-параметры — разные вещи.

Сохранение rec на10444 создаёт отдельный обход: неизвестный/пустой SNI идёт
в default10444, после TLS HTTP Host может выбрать rec vhost. Loopback-порт
сам по себе не делает этот маршрут внутренним. Удаление двух rec listeners
лучше, если внутренний потребитель не найден. Но после удаления ещё надо
проверить все оставшиеся default/catch-all/proxy targets10444: они не должны
передавать `Host: rec.2brain.pro` в API ГРАФ. Нельзя чинить это глобальным
запретом неизвестного SNI, нарушая прежние соседние маршруты. Для ГРАФ следует
явно описать совместимость: допустим ли прежний доступ без правильного SNI.

Исходная realip-схема имеет самостоятельный побочный эффект: она меняет
`$remote_addr`. В rec-конфиге `access_log` задан без отдельного формата, значит
используется combined, включающий `$remote_addr`; error messages также могут
содержать адрес. Это может начать сохранять настоящий visitor IP вместе с
URI/реферером/User-Agent, хотя T110 writer выключен. Нельзя выдавать это за
принятую семипольную категорию FR-061, ограниченную таблицей GRAF PostgreSQL.
Устаревшее подтверждение общей юридической модели не закрывает новый поток IP.
Основание вывода —
[HTTP realip](https://nginx.org/en/docs/http/ngx_http_realip_module.html) и
[HTTP access log](https://nginx.org/en/docs/http/ngx_http_log_module.html#access_log),
а не самостоятельное новое юридическое заключение reviewer.

Прямое использование `$proxy_protocol_addr` в двух proxy locations сохраняет
транспортный `$remote_addr` nginx и уменьшает этот эффект. Это штатная схема из
[официального руководства PROXY protocol](https://docs.nginx.com/nginx/admin-guide/load-balancer/using-proxy-protocol/).
В репозитории Uvicorn уже запускается с `--no-access-log`; штатный
`request_logging_middleware` не пишет client address. Тем не менее будущий
полный audit должен проверить унаследованные log_format/realip/другие получатели
и фактический лог нового пути: только просмотр двух исходных директив не
доказывает все действующие конфигурации. Новые relay не должны заводить журнал
`$proxy_protocol_addr`. Сохранение старого transport log не объявляется проверкой
всей прежней политики журналов или T110.

## Что действительно доказывает прототип v2

Прототип изолированно подтверждает сохранение source/https, перезапись трёх
пользовательских заголовков, перенос IPv6 visitor в PROXY envelope через IPv4
внутренний hop, получение ожидаемого ответа двух старых TLS targets и noSNI
default. Проверены отказ при public PROXY prefix, отказ dedicated listener
без envelope,400 на `PROXY UNKNOWN`, отсутствие rec на default target.

Названия `default_tls_bytes_preserved`/`special_tls_bytes_preserved` в JSON
обозначают успешный TLS-запрос и совпавшее тело ответа. Сравнения всех байтов
на входе/выходе нет; настоящий Xray/другой special backend в стенде заменён
простым HTTPS return. Проверка fallback Host rec совпадает с уже выполненным
default-запросом, поэтому13 отметок не означают13 независимых сетевых сценариев.
Это не недостаток базовой гипотезы, но важная граница силы доказательства.

Не проверены новый IPv6 receiving socket rec-port, два внешних выхода,
оператор/публичные маркеры, реальный Docker/Uvicorn/API writer/reader,
HTTP2/ALPN/WebSocket/долгие загрузки, лимиты/таймауты живых соседей,
workers/reload/rollback и8443. Отсутствие этих проверок не превращается в PASS
из-за зелёного числа13/13.

## Применение и возврат

Нужны полный `nginx -t`, тот же хеш входных файлов между audit/применением,
штатный reload и доказательство новой рабочей генерации. Дисковый снимок или
exit0 reload не заменяют живые probes. Старые соединения могут обслуживаться
старой генерацией: это ожидаемое поведение
[graceful reload nginx](https://nginx.org/en/docs/control.html). Дождаться
наблюдаемого завершения старых workers, не обрывать чужие длительные сессии
ради зелёной проверки; таймаут наблюдения оставляет эту приёмку открытой.

Общий map, исходящий PP mode, оба relay и dedicated receiver должны применяться
согласованным набором под существующей deploy/config блокировкой. При возврате
важно восстановить весь согласованный старый набор; нельзя вернуть только
receiver либо только PP mode. Новые relay нельзя убирать, пока draining
старой поколения ещё может в них подключиться: проверяется взаимодействие
поколений при apply и rollback, а не только конечный конфиг. То же относится
к прежнему rec10444: старый stream worker может ещё не открыть upstream в
момент reload, и прежний TLS receiver нельзя убрать раньше его дренирования.
Временная совместимость old/new receivers и снятие legacy rec — отдельные
стадии; пока старый обход существует, итоговая доверенная граница не принята.
Точный порядок и временный сохраняемый набор сокетов должен быть испытан
изолированно.

Резервная копия исходной конфигурации — в проверенном закрытом серверном
хранилище с правами/сверкой, без публикации ключей или копирования полного
nginx dump в Git. Возврат проверяет прежние маршруты,8443 и неизвестные
SNI, а не только rec health. Операция Uvicorn/env/API остаётся отдельной
согласованной стадией и не включает автоматически аналитику, оплату или IP writer.
