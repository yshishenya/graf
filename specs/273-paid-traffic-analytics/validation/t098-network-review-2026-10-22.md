# T098 — независимое ревью изолированного nginx/Docker стенда

Дата: 22.10.2026. Полоса: `high-risk-product`; FR-013/FR-062, существующая T098.
HEAD чтения: `ac25ad3d86e0810924e3328a8b1a2017891071a9`.

**Результат: FAIL полной изолированной матрицы matrix-7.** На стенде с двумя
обычными NAT bridge-сетями не прошли восстановление адресов/схемы (0/3), оба
HTTPS slash-перенаправления (0/2), классификация записи и исключение оператора
из отчёта. Все 25 учебных landing-запросов стали external. Проверка recreate
не завершилась: новый API оставался running, но не стал готов для проверки.
Очистка тестовых ресурсов подтверждена. Рабочее доверие посреднику принимать
нельзя; причина неуспеха и безопасный повторный прогон остаются открытыми.

## Основание и границы

Независимо прочитаны актуальные runner, boot, sanitizer, безопасные разборы
nginx, полный token audit nginx, завершённые matrix-5/matrix-6/matrix-7, требования plan §Уточнение T098 и сценарий 8
quickstart. Использовано разрешение владельца на ограниченное повторное чтение
F273 из `f273-scoped-reading-authorization-2026-10-22.json`; семь хешей этого
документа и семь хешей кандидата из `t098-review-snapshot-2026-10-22.json`
совпали с локальными файлами. Полное повторное чтение всех документов и новый
прогон pytest не заявляются. Результаты местных config/middleware tests и их
независимого ревью остаются отдельными доказательствами.

Reviewer не запускал стенд, production-запросы, Docker/SSH или команды изменения
служб. Проверен код предоставленного испытателя и сохранённые безопасные
результаты. Изменён только этот отчёт; checklist, код, spec/plan/tasks, Git/GitHub,
рабочие настройки, измерение, запись IP, оплаты и сообщения не изменялись.

## Устройство испытания

Актуальный runner создаёт две отдельные одноразовые обычные Linux NAT bridge-сети;
по сообщению исполнителя рабочие сети также ordinary bridge, internal=false,
ipv6=false. Предыдущий matrix-6 имел internal back-сеть и не равен новой топологии.
Runner не публикует PostgreSQL наружу и хранит его данные в tmpfs. API использует
существующий образ, кандидата через read-only mount и штатный Uvicorn с
`--proxy-headers`, без CLI-перекрытия `FORWARDED_ALLOW_IPS`. Порт API опубликован
только на host-loopback. Отдельный nginx с host network слушает адрес собственного
тестового bridge на высоком порту, перезаписывает XFF адресом соединения и XFP
значением HTTPS. Тестовые соседи находятся в обеих сетях.

Операторский адрес задаётся отдельно от транспортного посредника. Поддельный
служебный маркер внешних посетителей не должен менять их классификацию.
Маршрут `/_t098` добавляет только диагностический ответ о схеме/адресе;
landing, writer, SQL-хранилище и reader отчёта берутся из приложения.
Boot готовит таблицы одноразовой БД и входит в исходный lifespan приложения.
Отключение `public_analytics_enabled` не подменяет анонимный агрегат:
фактическая запись наблюдается отдельно. В matrix-7 она присутствует, но
классификация неверна для ожидаемой матрицы.

Администратор хоста с root/Docker-правами считается доверенным оператором.
Стенд не моделирует враждебного администратора и не изменяет production API/nginx.
Это проверка данного Linux/IPv4 bridge-пути; IPv6 и иные топологии ею не доказаны.

| Настоящий reader отчёта | FAIL | Вернул 25 посещений external вместо ожидаемых 10, поэтому операторский трафик не исключён. |

| Удаление временных ресурсов | PASS предоставленного лога | `isolated_network_cleanup=verified_complete`; проверены коды удаления и отсутствие уникальной метки контейнеров/сетей. |

Matrix-7 прямо содержит `all_pass: false`: шесть true, семь false и один
обязательный recreate-кейс не завершён. Нельзя принять полную матрицу по числу
успешных HTTP-запросов или по наличию external в отчёте. Все 25 landing-запросов
выполнены, но часть должна быть операторской; отчёт завышает внешний результат.

Рабочая гипотеза — фактический непосредственный peer/маршрут при двух обычных
сетях отличается от заданного тестом front gateway. Это **не установленная
причина**: нужен безопасный результат сравнения фактического peer со списком
конкретных ожидаемых посредников. Нельзя решать неуспех wildcard, CIDR всей
сети либо включением общего gateway в INTERNAL_HOSTS.

Matrix-6 завершился с 13 true, но recreate не прошёл и topology была другой
(internal back). Тогда запись дала 10 external + по 5 internal/support/test,
а отчёт — 10 external. Этот прежний частичный результат сохраняется как
диагностическая история, не как PASS рабочей топологии. Matrix-5 также не
прошёл writer/report и recreate; его старый `cleanup=complete` не был достаточен.

В актуальном runner исправлены точный canonical `Location`, отсутствие цикла,
проверка удаления ресурсов и порядок `create → connect обе сети → start`.
Последнее исключает запуск API до подключения тестовой БД; оно само не
доказывает готовность нового API или правильный выбор доверенного peer.

## Разбор nginx

Прочитан новый `t098-nginx-token-audit.py` и безопасный результат
`t098-nginx-token-audit-2026-10-22.json`. В нём успешный `nginx -T`, 30 загруженных
и 30 токенизированных файлов, один целевой файл vhost, разрешённый include graph,
ноль найденных `real_ip_*` во всём наборе. В трёх proxy-location целевого файла
все три XFF равны `$remote_addr`, все три XFP — `https`; в двух целевых
зависимостях этих заголовков нет.

Переход к `shlex` устраняет прежнюю зависимость `real_ip_*` от первого слова
строки. В актуальном scanner имена XFF/XFP также приведены к lowercase;
замечание о возможности пропустить иное написание регистра снято для этого
варианта scanner. Безопасный JSON фиксирует отдельный снимок конфигурации;
его нельзя молча считать результатом запуска любой более поздней редакции
scanner без сохранённой привязки выполнения. Старые sanitizer/JSON сохранены
только как история, их построчный вывод больше не нужен как главное основание.

**Загруженное состояние активных workers всё ещё не доказано.** В token audit
`all_config_files_predate_oldest_worker: false`. Это не доказательство, что nginx
работает неверно, но временная сверка не подтверждает равенство активного и
дискового снимков. Нужна отдельная проверка фактического пути при штатной
production-приёмке. `nginx -T` не читает память worker-процессов.

Тестовый nginx задаётся runner и не подменяет принятие рабочего nginx.
Самоподписанный сертификат стенда используется с отключённой проверкой доверия;
это проверяет транспорт XFP/Location в одноразовой сети, но не публичный
сертификат, имя узла или production TLS.

## Открытые действия перед приёмкой

- [ ] Установить безопасную причину неверного восстановления адреса/схемы
  при двух ordinary NAT bridges и неготовности API при recreate. Завершить
  всю матрицу с `all_pass: true` и проверенной очисткой.
- [ ] Связать успешный прогон с фактически смонтированным кандидатом,
  runner/boot и конфигурацией тестового nginx. Актуальный runner предусматривает
  source tree/runner/boot hashes и image IDs, но matrix-7 до финального блока
  не дошёл. Поэтому их печать ещё не является доказанным результатом.
  Независимо рассчитанный локальный source tree SHA:
  `309506fae1d2cd013b1d99bb96a702ef0887902c8197d93c3e24b7bf02c287a3`.
- [ ] Сохранить image IDs API/nginx/PostgreSQL, версии Uvicorn/Docker и
  фактическую топологию вместе с завершённым успешным прогоном.
- [ ] Отдельно принять фактическую загруженную production-цепочку во время
  штатного выпуска. Token audit диска не подтверждает активные workers.
- [ ] Пройти независимые проверки, convergence и точные SHA PR/CI, затем
  production-приёмку и выпуск по правилам проекта. До этого рабочему gateway
  не доверять по одному факту успешного стенда.

Недопустимые/пустые значения trust проверяются локальным config/middleware
набором и не заявляются новым сетевым испытанием. Общий gateway по-прежнему
нельзя включать в INTERNAL_HOSTS. T098 не открывает IP writer/T110 и не
подтверждает готовность всех показателей к коммерческим выводам.
