## Что изменилось после неуспеха matrix-7

Прежний **FAIL matrix-7 остаётся действительным результатом того запуска**:
при двух обычных NAT bridge-сетях не прошли восстановление адресов/схемы,
два HTTPS slash-перенаправления и классификация; все 25 посещений попали в
external, recreate не завершился. Matrix-6 до этого дал 13 true, но имел другую
топологию с internal back-сетью и тоже не завершил recreate.

Matrix-11 не скрывает этот неуспех, а проверяет исправленное устройство стенда:

- Фактический непосредственный peer сначала установлен через host-loopback
  запрос без forwarded-заголовков. Он совпал с gateway back-сети, а не с
  предполагавшимся front gateway. Это объясняет прежнее несовпадение доверия
  в проверяемом стенде; конкретный рабочий gateway этим не принимается.
- Затем API перезапущен с **одним фактически установленным точным peer** через
  штатный `FORWARDED_ALLOW_IPS`. Wildcard/CIDR и включения gateway в
  `INTERNAL_HOSTS` нет; адрес оператора задаётся независимо.
- Используется `create → connect обе сети → start`; запуск не предшествует
  подключению к одноразовой БД. Ожидание готовности ограничено 90 секундами.
  В matrix-11 фактические старты заняли примерно 23 секунды; прежние короткие
  ожидания не доказывали поломку работающего процесса.
- Для recreate заменены **обе** сети API; PostgreSQL переподключён к новой
  back-сети. Сохранён прежний точный trust; после старта новый неизвестный
  gateway не получил доверие автоматически.

Это изменения испытателя и выбора учебного peer, не включение доверия в
production и не новый parser forwarded-заголовков в приложении.

## Устройство принятого изолированного испытания

Две отдельные обычные Linux NAT bridge-сети соответствуют описанному типу
рабочей топологии; IPv6 не проверялся. API публикует порт только на host-loopback,
PostgreSQL не имеет опубликованного host-порта, его данные в tmpfs. Source
монтируется read-only. Отдельный nginx с host network слушает только адрес
собственного тестового bridge на высоком порту. Он перезаписывает XFF адресом
соединения и XFP значением HTTPS; соседи находятся в каждой из двух сетей.

Существующий API-образ используется как среда зависимостей. Через `PYTHONPATH`
подключены кандидат и boot; настоящий Uvicorn запускается с `--proxy-headers`
без CLI-перекрытия trust. Boot создаёт таблицы одноразовой БД, входит в исходный
lifespan и добавляет только маршрут `/_t098` для ответа об адресе и схеме.
Landing, классификатор, aggregate writer и report reader взяты из приложения.
Внешняя публичная аналитика отключена в boot; фактическая работа независимого
анонимного агрегата доказана отдельно чтением БД и отчёта.

Администратор хоста с root/Docker-правами считается доверенным оператором.
Стенд проверяет соседние обычные контейнеры данного Linux bridge-пути;
он не моделирует враждебного администратора или все возможные сетевые режимы.

## nginx и фактическая рабочая транспортная граница

Token audit показывает успешный `nginx -T`, 30/30 токенизированных файлов,
разрешённый include graph, ноль `real_ip_*`, три правильных XFF и три правильных
XFP в целевом файле, без этих заголовков в двух его зависимостях. Scanner
использует shlex и сравнивает имена заголовков без учёта регистра; прежние
построчные/регистровые пропуски устранены для этого разбора.

**Активная рабочая конфигурация этим не подтверждена:**
`all_config_files_predate_oldest_worker: false`. Дисковые файлы и память active
workers не доказаны равными. Это не доказательство неверной конфигурации, но
не позволяет принять её без отдельной рабочей проверки.

Безопасный `t098-peer-readonly-2026-10-22.json` фиксирует один новый established
host→API TCP peer при успешном health-запросе. Он не loopback, относится к gateway
одной из рабочих сетей и не входит в текущий разрешённый Uvicorn loopback-набор.
Это подтверждает транспортную причину, по которой существующая настройка не
принимает forwarded-заголовки на данном host→container переходе. Снимок не
устанавливает адрес посетителя, браузерное происхождение либо безопасность
всех production-путей; raw адреса не экспортированы.

Сертификат изолированного nginx самоподписанный, проверка доверия сертификату
в испытателе отключена. Это допустимо для внутренней проверки XFP/Location,
но не проверяет публичный сертификат, имя узла или production TLS.
