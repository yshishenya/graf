## P2-D01 — финальный разбор ответа может создать новую ошибку наблюдения

На observer:100 выполняется `response.json().get("status")` без защиты. Невалидный JSON выбросит ValueError/JSONDecodeError, валидный JSON другого типа — AttributeError. Код находится в finally после `return response`, поэтому эта новая ошибка заменит возврат исходного HTTP-ответа и traceback будет указывать на observer, а не на первоначальный неверный ответ. Tracer/ContextVar к этому моменту уже восстановлены, но семантика диагностического вызова изменится.

Известный исторический ответ `{status:unavailable}` является корректным JSON-объектом и **сам по себе этот дефект не вызывает**. Также при исключении original_post переменная response остаётся None и данный JSON-разбор не выполняется; маскирование этой конкретной исходной ошибки не утверждается. Пробел касается достоверного сохранения неожиданного завершённого HTTP-исхода — его наблюдатель не должен превращать в собственную ошибку.

Минимальная допустимая правка только временного plugin: получить status в невыбрасывающей ошибки ветви, проверить что decoded body является dict, брать только whitelist строку; при ошибке разбора оставить status=None либо фиксированный metadata marker ошибки разбора, без тела/текста исключения. Original response должен вернуться неизменным, original exception должен продолжить распространение. Не заменять ошибочный ответ на accepted/unavailable и не выполнять повторный POST. Native/selected code/сроки/ожидания тестов не менять.

Для этого небольшого исправления не требуется новый интеграционный прогон до повторного статического чтения. Исполнитель сохраняет единственный планируемый диагностический профиль для принятой версии observer. Здесь plugin не редактировался и отрицательный опыт не запускался; находка следует из прямого исполнения выражения finally при недопустимом JSON-формате.

## Пределы допустимого будущего вывода

После устранения P2-D01 и статической сверки observer можно допустить ровно один ранее предложенный общий87 с trace только на POST2 fault. Его следует отделить от обычной приёмки: sys.settrace устанавливается на весь поток Python и получает входы в функции до фильтра selected, поэтому он добавляет временные расходы даже при отключённых line/opcode событиях. Исходные2s/work1.5s/cleanup0.5s сохраняются. Отказ только под trace не доказывает, что первоначальный untraced отказ имел ту же причину.

Selected trace записывает исключения/вызовы и `_refuse`, но не охватывает всякий молчаливый возврат false/None и не пишет результаты `result_view_proof_age`/`verify_result_view_proof` напрямую. Вложенный verify может завершиться без исключения. Поэтому unavailable без captured исходной ошибки нельзя объяснять отсутствием ошибки; это предел выбранного ограниченного наблюдения, не требование расширять plugin до общего профайлера.

Если dropped>0, журнал не считается полной цепочкой; если второй POST принят или исходный отказ не воспроизведён, результат остаётся «причина неизвестна». Зафиксированные ожидаемые исключения первого COMMIT к POST2 не переносятся: active включается только для POST2. После законченного опыта observer снять, сохранить его hash/малую копию и метаданные результата; не запускать циклы повторения ради PASS. Runtime fix без установленной причины этим ревью не допускается.
