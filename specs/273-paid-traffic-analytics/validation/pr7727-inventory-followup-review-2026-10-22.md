## 4345130412: полнота входа и общая готовность

Замечание обосновано: `runtime_guard_blockers` правильно проверяет freshness,
формат inventory и `capacity_input_verified`, но затем добавляет ту же причину
из одного `capacity_ready != true`. Capacity evaluator считает ready из
полноты, принятия бюджета и отсутствия причин защиты. Поэтому pending budget
или реальная защита диска не доказывают неполноту входа.

Критерии для будущего исправления:

- При полном свежем input и непринятом бюджете остаётся budget blocker,
  без ложного `capacity_input_unverified`.
- При полном input и активной защите сохраняется защита/latch;
  полнота не становится ложной.
- Неверный/отсутствующий/устаревший input по-прежнему блокируется своей причиной.
- Удаление ложного input blocker не должно открыть готовность при
  `capacity_ready=false`. Если специфические причины не объясняют это
  состояние, требуется отдельная причина общей неготовности/недостоверности
  guard, а не подмена смысла input. Согласованный здоровый ready=true проходит.
- Проверить Python reader вместе с уже исправленным shell sibling consumer.
  Матрица включает полные input+pending budget, защиту, отсутствующий input,
  healthy и противоречивое ready=false при остальных якобы здоровых полях.

## 4345130420: самодекларированный restore receipt

Замечание обосновано для обоих consumers. В Python `_consistent_restore_proof`
и shell `consistent_restore_proof` синтаксически полный receipt может сам
объявить только postgres/clickhouse, любые64-значные hashes и все pass.
Consumers не знают, что в текущем reviewed runtime присутствуют ещё объекты,
Redis, broker/coordination/proxy. Непустой допустимый список и равенство
`storage_classes == verified_classes` не подтверждают полноту комплекта.

Существующий T117 backup-state не предоставляет независимую связку выбранного
комплекта, полного generated runtime и классов. Writer полноценного холодного
T118 с собственным нативным чтением пока отсутствует. Нельзя дописывать marker
вручную или добавлять рядом новый самоподтверждающий flag.

**Рекомендованный минимальный промежуточный путь — закрытый отказ в обоих
consumers до реализации полноценного доверенного T118 verifier.** Даже полный
по синтаксису v2 receipt не должен открывать readiness; сохранить наблюдаемый
`restore_verification_failed`. Это честный временный статус незавершённой T118,
а не её реализация. Не требуется новая служба, файл ожидаемых классов или
ручной переключатель доверия.

Для этого промежуточного исправления проверить:

- postgres/clickhouse subset не проходит;
- все восемь допустимых классов с правильно выглядящими hashes и pass
  также не проходят без настоящего независимого binding;
- неизвестные/повторные классы, отсутствующие поля, v1, старое/будущее время
  не проходят;
- Python readiness и shell alert показывают отказ одинаково;
- прежние тесты «здоровой эксплуатации» не должны утверждать, что выдуманный
  fixture является рабочим доказательством восстановления. Другие проверки
  метрик/причин должны оставаться независимыми от невыполненной T118.

### Минимальный полный контракт будущей T118

Доверенный verifier должен сначала сам получить и проверить полный runtime
inventory и manifest выбранного сохраняемого комплекта, вывести присутствующие
классы из них, проверить соответствие текущему принятому runtime и выполнить
принятые нативные сверки/собственное чтение PostHog/очистку. Только после этого
он публикует короткую защищённую metadata-attestation со связкой:

1. Identity конкретной проверенной точки и hashes её manifest/runtime/config.
2. Версия/отпечаток принятого inventory и доказанный полный набор классов.
3. Результаты каждого присутствующего класса и общего чтения/очистки.
4. Время окончания и применимость к текущему reviewed runtime.

API читает только безопасную короткую аттестацию; доступ к архивам, secret files
или закрытому generated runtime ему не нужен. Короткий receipt не должен сам
превращать произвольные hashes в доверенный binding.

**Не сравнивать restore manifest с последней ежедневной копией:** законная
проверка восстановления действует менее30суток; выпуск новой совместимой копии
сам по себе не отменяет её. Привязка относится к конкретной проверенной точке
и полноте/совместимости reviewed runtime. Реальный drift требует новой оценки,
но очередная compatible backup не является drift автоматически.
