# T113: атомарная смена имени БД и среда оператора

30.10.2026. Полоса: изолированная техническая проверка существующего T113.
Проверены свойства PostgreSQL 17 в собственном временном кластере с вымышленными
ролями и UUID-именами. Рабочий сервер и его данные не использовались.

## Подтверждённые свойства

1. Ошибка второй `ALTER DATABASE ... RENAME` из-за занятого имени откатывает
   первую; исходное соответствие имён и OID сохраняется.
2. Поздняя открытая сессия целевой БД запрещает переключение и откатывает
   обе операции именования.
3. Две операции переименования успешно фиксируются одной транзакцией;
   штатное имя получает OID восстановленной цели.
4. Прежняя БД после смены имени сохраняет `ALLOW_CONNECTIONS=false`.
5. Восстановленная БД сохраняет `CONNECTION LIMIT 0`.
6. Обычная роль после переключения не может открыть в ней соединение.
7. Владелец подключается к цели с лимитом 0 и выполняет
   `SET SESSION AUTHORIZATION` на роль обслуживания для чтения результата.
   Проба проверяет `session_user/current_user`; она не доказывает необратимость
   снижения привилегий или изоляцию процесса от первоначального владельца.

Итог: **7/7 PASS**, собственный контейнер/кластер удалён с проверкой метки
владения. Скрипт, JSON и журнал находятся в закрытом ignored `.dev/growth/`:
`probe-postgres-cutover-20261030.{py,json,log}`.

Первый запуск завершился `TimeoutError` при лимите команды 5 секунд в случае
поздней сессии: PostgreSQL сам ожидает примерно 5 секунд перед отказом. Очистка
прошла. Повтор с лимитом команды 15 секунд подтвердил все семь свойств.
Это изменение условий пробы; рабочие ограничения и настройки не менялись.

## Что остаётся открытым

Этот результат проверяет только транзакционную смену имён. Он не доказывает
полный product drain, проверку копии, удалений, восстановление данных,
непрерывность периода, resume/rollback или доверенную готовность аналитики.
T0 ещё не задан; безусловный recovery blocker остаётся. T113/#7804 и
коммерческие AC01–AC06 не закрываются этой пробой.

## Безопасная проверка среды на рабочем сервере

До остановки продукта проверен более простой способ исполнения:
один доверенный оператор на сервере с временным окружением Python3.13 из
существующего frozen `apps/server/uv.lock`. Этот выбор получил отдельное
[независимое заключение](t113-operator-execution-review-20261030.md).
Его положительная оценка не заменяет проверку конкретного алгоритма до кода.

На `2brain.dev` прочитаны только технические метаданные и выполнены SELECT;
службы, данные, права и сеть не менялись. Исходная версия
`976f310f9fff09b96a1e6fcec99cb43f4bb706ae`, SHA-256 lock
`c7bba4a373661487b1c13ac931f3d2c1ad0ade7c28b12dd1b8c21316b40ca52d`.
Собственная среда создана отдельно от project `.venv` и после пробы удалена.
Итог JSON: **9/9 PASS**, очистка временного окружения PASS:

1. Исходный SHA и lock совпали с ожидаемыми перед подготовкой.
2. Отдельное окружение из frozen lock подготовлено.
3. Его интерпретатор действительно Python3.13.
4. Подключение к PostgreSQL через адрес существующей частной сети Docker
   прошло с действующей аутентификацией; новый порт не публиковался.
5. После `SET SESSION AUTHORIZATION` проверены session/current_user,
   row_security, NOSUPERUSER/NOBYPASSRLS/NOINHERIT.
6. SELECT через SQLAlchemy engine с URL без credentials и одноразовым
   async_creator выполнился в этом пониженном контексте.
7. Повторный checkout соединения явно отклонён.
8. Текущая revision и идентификатор кластера доступны для проверки.
9. Исходный SHA и lock не изменились к концу пробы.

Пароль оставался на сервере, не передавался в аргументах команд/engine URL
и не выводился; на Mac вернулся только краткий результат. Скрипт и JSON
в закрытом ignored `.dev/growth/probe-host-operator-runtime-20261030.{py,json}`.
Проба использовала нынешний checkout, проверив его до/после; она не доказывает
будущую неизменность исходников во время actual restore. Поддерживаемый
оператор должен использовать закреплённый недоступный параллельной правке
исходник и отдельно сверять рабочие image/source bindings.

Ни обратимость RESET, ни частичный список role flags не скрываются:
для настоящего replay остаются все точные проверки `database_context`,
схемы/политик/прав, новые физические входы readback и конечный независимый
анализ алгоритма initial/full restore. Рабочий T0 и admission не менялись.
