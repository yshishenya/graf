## Проверка исправления прежнего P2-1

В `result_view_text_blocks(review, owner=...)` введены проверки владельца
в фактическом извлечении блоков. Количество кандидатов ограничивается прежним
`_TOTAL_ROWS`; длина строки проверяется до UTF-8 кодирования, затем проверяются
размер поля в байтах и суммарные байты по прежним `_FIELD_BYTES` / `_TOTAL_BYTES`.
Старый review не считается автоматически ограниченным новым SQL snapshot.
Переполнение вызывает `owner._refuse()`, сохраняя постоянный отказ.

`matching_render_bindings` использует это ограниченное извлечение и проверку
после каждого digest. Свежие bindings также получают проверки до/после digest.
Valid POST теперь выполняет явный цикл с `owner.checkpoint()` до и после
полного verifier вместо неограниченного синхронного `next(...)`. Проверки
подписания и renewal в сервисе сохраняются. Повторного срока, второй Session
или повторного admission при TTL race не добавлено.

Просмотрен причинный исходный RED
`/private/tmp/graf-t112-http-sync-budget-red-20261116.log`: четыре отказавших
сценария соответствуют прежним неограниченным циклам и большому старому review.
В текущем журнале
`/private/tmp/graf-t112-http-sync-size-final-20261116.log` три проверки раннего
синхронного исчерпания времени проходят: следующий кандидат не обрабатывается,
новых записей нет, pool и задачи очищены. Задержка в актуальной проверке
рассчитывается до исходного work deadline плюс 30 ms, сохраняя резерв cleanup;
она не продлевает запрос и не пытается успешно ответить после hard deadline.

Это обоснованное исправление замечания о продолжении следующих кандидатов.
Сам факт проверки до/после не делает произвольную единственную синхронную
операцию прерываемой; поэтому пределы данных до кодирования также необходимы.
Рецензент не запускал тесты и не переносит отдельные GREEN на весь HTTP-срез.

## Сохранение выбора блоков

По исходнику сохранены прежние ключи, порядок и текст для допустимых данных:

- transcript использует прежние turns либо segments и их исходные индексы;
- protocol сохраняет порядок секций, объединение open_questions / next_steps,
  частей topics и notes, а также прежнюю классификацию summary/action_items/outcome;
- plain outcome по-прежнему нумерует только элементы с truthy `item.text`.
  Пробельный truthy текст занимает прежний индекс, затем отбрасывается `strip`,
  поэтому ключи последующих непустых элементов не сдвигаются;
- owner=None сохраняет прежнее извлечение для render / обычных callers;
  ограниченный отказ не переписывает продуктовый review и HTML.

Во время чтения обнаружен конфликт имени `rows`: счётчик был перезаписан
списком строк protocol, после чего `rows += 1` с owner приводил к TypeError.
В текущей редакции счётчик уже называется `candidate_count`; конфликт устранён.
Это не текущее открытое замечание. Для защиты найденной регрессии полезен
прямой случай непустого protocol с owner, поскольку существующие unit-примеры
protocol вызывают extractor без owner. Его отсутствие не заменяется рассказом
о том, что plain transcript проходит.

## Гипотеза очистки: не повторять отмену уже отменяемой задачи

Текущее изменение `_run_result_view_operation` вызывает `child.cancel()` только
если `child.cancelling() == 0`. Оно соответствует механизму наблюдаемого сбоя:
повторная отмена может прервать уже начатую SQLAlchemy invalidation. Установленный
SQLAlchemy выполняет graceful terminate через shield и повторно выбрасывает
CancelledError; поэтому повторное внешнее вмешательство в эту фазу существенно.

Область изменения остаётся узкой: перечень задач строится из прежних точных
leases / transaction ownership, сохраняются terminate initializing generation,
join дочерних задач, проверки пустого владельца и ContextVar reset.
Чужой pool не сбрасывается, `engine.dispose()` не добавлен.

`Task.cancelling()` — счётчик запросов отмены, а не универсальное доказательство
текущего состояния очистки. Условие само по себе не доказывает, что все
необходимые задачи уже завершаются, что новый shield-child не останется жить
или что cleanup уложится в резерв. Нужны фактические проверки завершения,
lease / transaction / driver / pool и чужого подключения. Рассмотренные три
синхронных сценария дают полезное положительное доказательство этой гипотезы,
но не заменяют повтор прежней PG-матрицы pre-ping / close / rollback / handoff
после изменения общей функции POST и GET.

Журнал `graf-t112-http-sync-cleanup-20261116.log` завершился 15 PASS / 2 FAIL,
включая valid_verifier без завершённого HTTP-ответа. Более поздний точечный
журнал содержит 7 PASS / 46 deselected. Исторические FAIL не скрываются;
изменённая постановка синхронной задержки описана выше. Ни один из этих
журналов не является полным текущим GREEN HTTP-профиля.

## P2-2 — near-total тест принимает неизвестную причину отсутствия proof

**Место:**
`apps/server/tests/contract/test_result_view_http_integration.py:869–876`
в текущем `test_http_inspection_renewal_and_pair_keep_original_size_limits`.

Для `hour_near_total`, когда подписей нет, тест меняет `allowed` на False и
принимает отказ, проверяя только raw_bytes в допустимом диапазоне,
`owner.budget.failed` и SQL<=128. Но `_result_session_context` устанавливает
`owner.failed = owner.budget.failed = True` при любом Exception. Поэтому
посторонний RuntimeError, ошибка выбора результата или будущая регрессия
extractor также может сделать этот случай зелёным. Печать `over_work` не
является assertion и не удостоверяет причину первого отказа.

Отказ по исходному сроку при большом допустимом по размеру входе сам по себе
разрешён: размер и время — независимые ограничения. Однако проверка, заявляющая
такой переход, должна причинно доказывать именно истечение work budget,
сохранение исходного cleanup deadline, нулевой набор записей и отсутствие
оставшихся задач/подключений. Иначе текущий GREEN не отличает допустимый
отказ по времени от скрытой ошибки реализации.

**Что исправить:** на тестовом пути наблюдать причину первого отказа в момент
её возникновения либо детерминированно подставить только часы / границу времени
и независимо проверить размерный путь. Не добавлять рабочие журналы содержимого
и не менять privacy. Простого общего флага после sanitizer и позднего сравнения
часов после render недостаточно. Полный обычный 60-минутный положительный
пример должен продолжать выдавать proof / renewed / accepted без уменьшения
данных и повышения caps.

В текущем точечном журнале near-total сообщает bytes8335873, SQL73,
`over_work=True` и отказ. Это согласуется с гипотезой о времени, но его
причинность не закреплена тестом. Положительные три фазы для этого размера
не были доказаны: журнал содержит только одну inspection-фазу.
