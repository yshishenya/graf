## Решение до изменения настроек

**BLOCK применения предложенного доверия как приёмки T098.** Сначала требуется
read-only проверка полного пути `публичный443 → SNI ingress → TLS10444 →
nginx → Docker → Uvicorn`. Проверенные соседние Docker-пути полезны, но
присутствующий перед nginx дополнительный ingress не был воспроизведён
в принятом изолированном стенде. Ни reload, ни точный Docker peer сами по себе
не доказывают происхождение адреса посетителя.

В репозитории `infra/nginx/rec.2brain.pro.conf:33–34` принимает TLS на
loopback10444 без `proxy_protocol`; XFF заменяется `$remote_addr`.
`infra/nginx/graf-summary-share-limit.conf:1–3` прямо поясняет, что существующий
SNI ingress приходит через loopback и не доказывает индивидуальные адреса.
Если рабочий ingress действительно теряет исходный адрес, nginx передаст
loopback как XFF; включение доверия к Docker peer не вернёт утраченные данные.
Нужно подтвердить эту причинную цепочку по действующей topology, а не считать
её уже доказанным новым наблюдением reviewer в production.

Релиз `v2026.10.27.1` и успешный Full40491725053 указаны основным исполнителем.
Прочитанный текущий runtime receipt связывает Git/image/runtime с точным HEAD
и healthy API. Это не доказательство рабочей адресной границы, активной nginx
конфигурации или приёмки T098; сам GitHub run в этом ревью не запрашивался.

## Минимальные доказательства до мутации

1. Показать безопасную карту всех hop: кто слушает443, как выбран SNI target,
   чем передан исходный адрес в10444 и какой адрес становится `$remote_addr`.
   Проверить реальную загруженную конфигурацию каждого задействованного
   процесса и локальные границы доступа. Два контролируемых внешних выхода
   и оператор должны сравниваться внутри закрытого процесса; наружу только
   результаты совпадений/различий и числа, без адресов или их хешей.
2. Если исходный адрес на этом участке не передаётся, текущий минимальный
   env-only план недостаточен. Уточнить существующий T098 plan/scenario для
   фактического ingress, пройти независимое ревью затронутого решения до
   изменения конфигурации. Новый Feature ID не требуется. Изменение общего
   SNI-пути не распространять на соседние сервисы молча.
3. Сохранить правильную очистку пользовательских XFF/XFP на принятой границе.
   Не заменять потерянный адрес пользовательским заголовком, CIDR сети,
   wildcard, patch middleware или добавлением посредника в INTERNAL_HOSTS.
   Синтаксическая допустимость точного IP не подтверждает его происхождение.
4. После принятия полного пути: повторный полный token-audit и `nginx -t`,
   одинаковый хеш файлов между аудитом/применением, штатный reload и успешное
   появление новой рабочей генерации. Дождаться окончания старой генерации;
   подтвердить, что загруженные входы не менялись, и выполнить реальные
   public запросы. Старый false timing не превращать в PASS только по exit0reload.
5. До recreate связать image/source/Compose/настройки с опубликованной версией,
   подготовить ограниченное окно API и возврат только изменённого env. Отдельно
   сравнить все действующие флаги до/после; аналитика, воспроизведение/dispatch,
   биллинг, auth и внешние получатели не меняются по умолчаниям caller.

## Безопасная проверка оператора и отчёта

Настоящий `classify_public_traffic` принимает `x-graf-traffic-class` только
когда восстановленный `client_host` уже входит `product_analytics_internal_hosts`.
Без маркера такой адрес получает `internal`; публичный query marker игнорируется.
Одного служебного заголовка с внешнего IP недостаточно. curl/wget/обычный
python User-Agent получает `automated`: исключение такого запроса не докажет
операторскую классификацию.

Проверка оператора требует принятого фактического операторского адреса и
отдельного доказательства его происхождения через публичный443. Сравнение с
закрытым INTERNAL_HOSTS выполняется в памяти; сохраняются только булевы признаки
`operator_address_matches`, `proxy_not_operator`, классы и итоговые счётчики.
Не сохранять raw IP, персональный хеш IP, cookies, headers или полный inspect.
Если нужного operator entry нет, это отдельное изменение конфигурации; нельзя
молчаливо добавить его в операцию, разрешённую только для FORWARDED_ALLOW_IPS.
При потере адреса в ingress этот тест **BLOCK**, а не подмена127.0.0.1/gateway.

После принятия всей цепочки провести ограниченный batch: два контролируемых
внешних выхода и оператор, нормальный неботовый User-Agent, без секретов
и аккаунтных действий. Внешний запрос с поддельным support/test маркером
остаётся external; операторские internal/support/test исключены отчётом.
Прочитать настоящие aggregate bucket и штатный reader; код счёта независим
от выключенных необязательных provider flags, включать их для теста не нужно.

Отчётный порог —3 запроса по полной корзине. Один записанный external запрос
может законно отсутствовать в отчёте; нельзя принять его отсутствие за
неуспех writer или операторское исключение. Для полного доказательства
reader нужен batch, достигающий порога, с учётом каждого запроса ровно один раз.
Сохранять безопасный итог batch и общий campaign label проверки, не индивидуальные
идентификаторы запросов; не удалять рабочие строки ради красивого результата,
учебный batch не выдавать за органический рост. При одновременном реальном
трафике сырая разность глобальных totals не является доказательством batch.

Финальная приёмка дополнительно требует публичные HTTPS canonical/slash URL
transcription и Zoom без follow-redirects, валидный TLS, повтор spoofing обоих
соседей после recreate и подтверждение, что внешний client address действительно
восстановлен. Сам по себе HTTPS307 даёт только доказательство схемы.
У Uvicorn используемый один trust-набор обслуживает XFF и XFP вместе:
env-only включение не является отдельным переключателем «только HTTPS».
Если нужен меньший срез исправления схемы, его нужно описать/проверить отдельно
в T098 и не объявлять исправлением visitor/operator классификации.
