## Решение

**Конкретного допустимого полного пути A–D только средствами опубликованного
v2026.11.01.3 не установлено. HOLD рабочего исполнения и выпуска сохраняется.**

Это вывод из исходников указанной версии и применимых ограничений, а не
следствие одного отсутствующего convenience script. Уже опубликованные
средства дают полезную часть для D — закрепление существующих image IDs.
Они не выполняют безопасный A–C для нынешних трёх направлений и не устраняют
несовместимость опубликованных nginx-шаблонов с текущей конфигурацией.

Базовые команды nginx/Compose технически способны выполнять операции,
но наличие этих программ не является готовым проверенным операторским
набором. Ручное создание актуального набора не превращает его в содержимое
старого опубликованного кандидата и требует отдельной проверки применимого
пути/границ. Запрет не объявляется бессрочной технической невозможностью:
его конечные отсутствующие условия перечислены ниже.

## Почему опубликованный набор не выполняет A–C

Published routing SHA256
`a3b9e9c7a4bcda31d1fbece250dd6193b4666a2c57b9dca37f3f3c2a169af35e`:

- rec направляется на10445; этот порт логически принадлежит нынешнему Stalwart;
- отдельные relay10446/default и10447/special;
- прежний трёхмаршрутный map не переиспользуется, пять mail SNI отсутствуют;
- при исходящем public PROXY on почтовый маршрут нельзя просто оставить
  прежним прямым TLS backend без снятия envelope;
- published rec также принимает10445 и имеет прежний server error destination,
  тогда как принятый проект03.11 требует10446 и отдельную PP error-log защиту.

В A необходим новый совместимый принимающий набор **до** переключения public,
при сохранённом старом rec10444. Edge installer вместо этого сразу заменяет
итоговый rec-файл: он не устанавливает transitional набор и не сохраняет
его до последнего потенциального позднего ClientHello. В B нужны общий
map/PROXY cutover и наблюдение прежних stream workers. В C нужны снятие
rec10444 и завершение последнего старого поколения с доказательством отсутствия
Host-обхода. Ни один проверенный published caller не реализует эти действия
и их безопасный обратный порядок.

Принятый локальный новый кандидат rec10446/one-relay10447 решает новую
топологию и имеет scoped review/изолированные доказательства. Он отличается
от e447. Его перенос через ручное копирование или запуск edge installer из
подменённого repo-source не является использованием неизменённого старого
кандидата. Переименование файлов/вызова не устраняет различие поведения.

## Частичная возможность D — полезна, но недостаточна

Published `release-images.py:397–413`:

1. при отсутствии active state возвращает None — не создаёт доказательство
   текущего image автоматически;
2. требует terminal result завершённой попытки, не pending recovery;
3. требует sourceSHA release record == текущий HEAD;
4. `verify` сверяет running containers с записанными точными image IDs;
5. `validate-override` разрешает только service→image sha256 и pull_policy=never.

В этих условиях существующий helper может дать pinned override для
ограниченного D того же rec-api image. Но сам helper **не** выбирает и не
доказывает доверенный Docker peer, не меняет env, не выполняет recreate,
не сравнивает effective Compose до/после и не откатывает env. Конкретная
последовательность D должна пройти своё предварительное ревью под lock,
без build/pull/dependencies/других флагов. В этом ревью она не исполнялась.

Полный runtime caller не заменяет такой узкий путь: опубликованные
строки1214–1229 останавливают API/processing/maintenance, поднимают API,
migration/MinIO/Temporal/processing/maintenance и меняют dispatch-переменные.
Прямое выставление release-gate env не является разрешением обхода caller.

Даже идеально выполненный D при старом входе443→10444 сохраняет прежнюю
потерю источника: доверие непосредственному Docker peer не восстанавливает
адрес, не переданный предыдущим SNI hop. Поэтому делать D первым ради
«закрытия retirement» не обосновано.

## Применимые правила и предел истёкшего исключения

Прочитаны действующие T098 plan/scenario8 и:

- `development-process.md:157–192`: expiry строго позже текущей датыUTC,
  expired_exceptions=0; при истечении `block merge/release and create/execute
  retirement task`;
- `release-and-validation.md:175–192,348–408,591–611,675–690`: точный
  SHA/candidate/Full/dry-run и рабочие ворота; даже incident skip-local-ci
  не отменяет candidate/SHA/production gates;
- `plan.md`: закрытая согласованная операторская конфигурация после ревью
  include graph, под существующим lock; обоим edge installers запрещено
  работать во время перехода; A–D/rollback и реальные поколения обязательны;
- spec Legacy Impact: всё ещё retain-with-exception, expiry2026-11-03,
  removal trigger — наблюдаемое завершение поколений и отсутствие Host rec
  через shared10444, не наличие нового файла или локального PASS.

Требование исполнять retirement позволяет продолжать существующую задачу:
чтение, проект, локальную реализацию, изолированную проверку, подготовку
точного операторского набора. Оно не делает опубликованный старый набор
совместимым и не создаёт неописанный emergency/expiry bypass.

В правилах не найден конкретный уже разрешённый способ провести новый
неопубликованный ingress-кандидат в production при действующем expired gate.
Отсюда не следует, что любой частный nginx config обязательно требует нового
образа приложения. Следует более узкое: готовая применимая операторская
последовательность и её законный выпускной/операционный допуск в предъявленных
материалах отсутствуют; считать их существующими от имени reviewer нельзя.

## Конечные отсутствующие условия

1. **Настоящий успешный исходный baseline.** Снять текущие отказы соседей в их
   собственном основании/границах, проверить настоящий Stalwart и действующий
   VLESS/REALITY разрешённым клиентом. Наличие процесса/другого порта/HTTPS
   fixture не принимается. Новый вопрос владельцу о почте не нужен: уже
   ожидающее согласование остаётся у основного исполнителя.
2. **Точный актуальный операторский набор A–C и возврата.** Он должен сохранять
   нынешний map/все3upstream/5mail SNI,10445, точные binds, новый rec10446/
   strip10447, оба принимающих набора до дренирования. Нужны конкретные
   входы/хеши/команды/lock/закрытая копия/границы остановки и independent review;
   опубликованные callers этого набора не дают.
3. **Подтверждённый применимый допуск именно этому набору.** При новом
   кандидате — обычные проверки его точного источника и законный путь
   publication/production; при узкой конфигурационной retirement-операции —
   конкретное предварительно рассмотренное основание и последовательность,
   которая сохраняет действующие ворота. Пока такого принятого пути нет,
   expired gate не обходится и merge/release/применение остаются HOLD.
4. **Отдельный D на неизменённом установленном образе.** Успешный current-
   override, действительный release record/source/image, проверенный peer,
   разрешённый ограниченный recreate rec-api, сравнение всех effective
   настроек и проверенный возврат без других служб/флагов.
5. **Реальная полная приёмка после предварительных ворот.** Actual apply/
   rollback/lateHello/drain/сети/семейства/журналы/8443/writer→DB→reader по
   scenario8, после чего правдивое завершение старого пути. Локальный
   scoped PASS и будущий merge не заменяют этого доказательства.

Это конечный перечень условий, а не предложение продлить исключение,
назначить фиктивный remove, создать обходную feature или подменить
рабочую доступность новой формулировкой. Если любой этап возвращает старый
путь/оставляет старые поколения, retirement не завершён, T098 остаётся открытой.
