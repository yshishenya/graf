# Независимое ревью исправления provider-smoke F273/T118

Дата: 23.10.2026. Проверяющий: `/root/f273_smoke_requirements_reviewer`.
Ветка: `codex/273-provider-smoke-recheck`.
Основа проверки: `1c5148dbe5c1c3d19ae69d713b99cc8227458cb6` и текущий diff
ровно двух назначенных файлов. Режим: существующий высокорисковый срез F273,
проверка локального синтетического сценария. Выпуск и production не входят.

## Решение

**Узкий PASS, обязательных замечаний нет.** Исправление доказывает блокировку
перед подстановкой, оба положительных синтетических транспорта внутри неё и
возврат настоящей блокировки после выхода. Новых флагов/зависимостей/fallback
и изменений рабочих ворот нет. Это не готовность всей T118: доверенный
проверяющий согласованного восстановления, реальный комплект, native/PostHog
чтение, установка и рабочая приёмка остаются открытыми.

Требования и их границы проверены в отдельном
[requirements review](provider-smoke-requirements-review-20261023.md).
Перед этой проверкой заново прочитан весь изменённый smoke и весь test-файл,
их diff, общий provider_delivery_gate; применимые consumer/client paths и
типизированный helper сопоставлены с уже прочитанными исходниками. Требования
используются после сверки неизменности; источник проверки — конкретные bytes,
не сообщение исполнителя о PASS.

## Разбор реализации

- `check_restore_blocked` читает настоящий operations consumer, требует
  `restore_verification_failed` и от обоих клиентов получает `live_safe_blocked`
  с `analytics_operations_not_ready`. До patch оба счётчика равны нулю.
- `unittest.mock.patch` ограничен контекстом, заменяет только
  `provider_readiness.collect_analytics_operations_evidence`. Замыкание вызывает
  заранее импортированный настоящий collector, затем `dataclasses.replace`
  меняет только `restore_consistent`. Рекурсии и замены всех остальных полей нет.
- Оба клиента используют синтетические функции транспорта, проверяющие форму
  URL/body и возвращающие учебный ответ; реальные адреса/секреты не нужны.
  Внутри контекста требуются оба конечных положительных статуса.
- После контекста повторяется тот же отрицательный сценарий; конечный счётчик
  ровно `posthog=1,yandex=1`. Поэтому ни ранний/поздний вызов, ни отсутствие
  положительной отправки, ни лишняя отправка не скрываются PASS.
- Новые metadata-only строки явно говорят
  `provider_transport_evidence=synthetic_test_process_only` и
  `restore_gate=blocked_before_and_after_transport_test`; существующие
  `product_rollout=blocked` и `campaign_launch=blocked` сохраняются.
- Новый test действительно исполняет встроенный Python в дочернем процессе
  с запретом `socket.connect/getaddrinfo`, вместо проверки только строк Bash.
  В окончательном варианте PYTHONPATH задан двумя абсолютными путями проекта,
  поэтому смена cwd на корень не ломает импорт `tests.fixtures`.

Промежуточный вариант нового test без собственного PYTHONPATH независимо
воспроизвёл `ModuleNotFoundError: No module named 'tests.fixtures'` при обычном
запуске из apps/server с `PYTHONPATH=src`. Исполнитель самостоятельно добавил
env до окончания ревью. Окончательный вариант в том же окружении PASS;
этого замечания в текущих bytes больше нет.

## Собственные проверки без сети

Встроенный Python извлекался из реального файла; дочерний процесс запускался
под проектной `.venv`, с запретом socket connect/DNS/sendto и вложенного запуска
процессов. Для каждого прогона время ограничивалось 45 секундами. Все учебные
state-файлы находились во временных каталогах; их удаление после группы проверено.
Изменённые отрицательные варианты существовали только в памяти процесса,
репозиторные файлы для них не менялись.

| Проверка | Результат |
| --- | --- |
| Точный встроенный Python | exit0, оба новых marker и product/campaign blocked |
| В подстановке restore_consistent=False | ожидаемый exit1; положительный путь не проходит без свидетельства |
| Настоящий consumer искусственно принимает самодекларацию до patch | ожидаемый exit1 `restore evidence accepted` |
| Patch намеренно оставлен активным после положительного блока | ожидаемый exit1 `restore evidence accepted` |
| Добавлен счёт вызова до положительного блока | ожидаемый exit1 `blocked transport called` |
| Добавлен лишний счёт вызова после положительного блока | ожидаемый exit1 `unexpected transport calls` |
| Убраны записанные approvals | ожидаемый exit1; patch не обходит одобрения |
| Убрано рекламное согласие | ожидаемый exit1 `restore gate`; проверяется настоящий transfer gate |
| Ёмкость capacity_ready=false | ожидаемый exit1; patch не обходит capacity |
| Окончательная новая test-функция из apps/server, PYTHONPATH=src | PASS |
| `bash -n` и `git diff --check` двух файлов | PASS |

Итого: девять независимых вариантов встроенного сценария (один положительный,
восемь ожидаемых отказов), прямой запуск окончательной новой test-функции и
две статические проверки. Сводные pytest исполнителя здесь не присваиваются
проверяющему: широкий профиль и полный shell-сценарий выполняет основная задача.
В этом ревью Docker, SSH, настоящий провайдер и рабочие данные не вызывались.
