## Результат и границы

Исправить существующий `infra/scripts/rehearse-rec-restore.sh`: после
копирования в собственную новую корзину прочитать её точное множество ключей
и каждый байт, сравнить размеры и SHA256 с выбранным исходным деревом.
PASS возможен только после этой сверки, прежней проверки БД и подтверждённой
очистки всех собственных временных целей. Иной путь проверки восстановления
или обход штатного выпуска не вводится.

Это проверка восстановления наблюдаемого комплекта. Она не доказывает, что
исходное копирование было полным/согласованным с историческим продуктом.
Общий activation operator, replay удалений, готовность аналитики и T0 не входят.
Рабочие БД и корзина не восстанавливаются поверх существующих данных;
продукт не останавливается. Исходные 40 комплектов сохраняются.

## Минимальные требования

1. O1: источник — явно выбранный canonical каталог, без символических ссылок
   в обходе и подмен родителей. Чтение через удержанные directory FD,
   O_NOFOLLOW/O_NONBLOCK; только обычные файлы с одной жёсткой ссылкой,
   каталоги0700/файлы0600 и ожидаемый UID. Ошибка доступа или обхода — FAIL.
   Файлы, каталоги и корень сверяются до/после; добавление, удаление или замена
   источника исключают PASS. Время доступа не используется как признак подмены.
2. O2: закрытый манифест содержит точное множество относительных
   ключей, размер и SHA256 каждого файла. Ключи не исполняются в shell;
   пустые/абсолютные/неканонические ключи и коллизии отклоняются.
   Пустой комплект допустим только при точном пустом перечне новой корзины.
3. O3: нативное перечисление новой корзины полное, включая все страницы.
   Пропуск, лишний/повторный ключ, неизвестный тип или размер — FAIL.
   Каждый объект читается потоково до конца; ожидаемый размер ограничивает
   чтение, SHA256 сравнивается независимо от ETag. Укороченный/лишний поток
   и изменение одинаковой длины отклоняются. HEAD до/после и повторное полное
   перечисление исключают наблюдаемое изменение цели во время проверки.
4. O4: у временной корзины нет versioning, lifecycle или object lock.
   Ошибка проверки конфигурации — FAIL. Source-манифест до копирования и после
   readback должен совпасть. Одной проверки сумм уже восстановленных файлов
   или успешного mirror недостаточно.
5. O5: общая deploy-блокировка удерживается до завершения readback и cleanup.
   Коллизия create-only цели сохраняет чужую цель. Проверка не удаляет и
   не меняет исходник/рабочую корзину. Отказ или неполный cleanup не даёт PASS
   и запрещает переход ко второй копии до разбора остатка.
6. O6: новый процесс чтения имеет конечные HTTP timeout без скрытых retry и
   общий монотонный предел600с. Успех не выдаётся после предела. При сигнале
   или timeout дочерний процесс и принадлежащий попытке контейнер должны
   завершиться до удаления корзины; неизвестное завершение — FAIL с остатком
   для разбора. Проверяемая очистка имеет отдельный предел60с; превышение
   не подменяется успешным выводом. Это не вводит безусловный kill чужих процессов.
7. O7: секреты передаются только прежними read-only secret mounts. Содержимое
   объектов, ключи, отдельные хеши и сырые исключения не попадают в stdout,
   Git или сохраняемый отчёт. Разрешены итог, постоянный код причины,
   количество объектов/байт и общий digest. Временный частный журнал очищается.
8. O8: источник/цель читаются только внутри существующего доверенного узла.
   Нового пакета, внешнего сервиса, учётной записи или выгрузки на Mac нет.
   Образ берётся из действующего закреплённого release override и запускается
   с `--pull never`. При неизвестном image/SDK/secret access — отказ, без fallback.

## Выбранный подход и зависимости

Эталон снимается до mirror стандартной библиотекой host Python. Он записывается
create-only в собственный0700 staging как0600 файл без раскрытия в журнале;
ошибка записи/чтения, ссылка, неверный владелец/режим или изменение манифеста
запрещают PASS. После mirror этот файл монтируется в проверяющий контейнер
только для чтения. Контейнер заново читает исходник и сравнивает его с
первоначальным эталоном до/после GET; при cleanup эталон удаляется вместе
с собственным staging. Сравнение metadata учитывает семантику native bind
mount; её нужно подтвердить учебным контейнером, не предполагать совпадение.

Потоковый readback через уже установленный MinIO SDK в существующем серверном
образе. API/worker не запускаются: отдельный одноразовый процесс с read-only
монтированием нового проверяющего файла, источника и прежних secret files,
в существующей частной сети. Никакой .env внутри контейнера, новых полномочий
Docker или входа в работающий API. UID/GID оператора обеспечивают чтение
закрытых копий; фактические права secret files проверяются до запуска.

Для перечисления/чтения переиспользовать проверенный алгоритм `_file_manifest`
и `_object_manifest` из текущего проекта как основу узкого общего проверяющего,
а не вызывать внутренний `_rehearsal_resources` вне его предусловий. Нельзя
переносить весь activation_operator или считать его прошлое ревью приёмкой
нового выделенного файла. Точные библиотечные версии, Python entrypoint,
права image и release-images/current-override проверяются на свежей основе
и в учебном контейнере до рабочего применения.

Альтернативы: второй mc mirror обратно в host staging увеличивает расход
примерно на размер объектов и требует дополнительной защиты имён/владения;
поэтому не выбран. Запуск docker/mc на каждый объект создаёт множество
контейнеров; не выбран. ETag/размер без чтения не доказывают равенство байтов.

Сначала оценить возможность выделить уже существующий алгоритм без изменения
непринятого большого оператора. Если это требует нового общего механизма
вместо узкой проверки, вернуть проект на ревью; код не расширять автоматически.

- Один профильный модуль unit-тестов для выделенного алгоритма, настоящий
  учебный MinIO для независимого SDK smoke; существующие snapshot/backup
  тесты проверяют совместимость. Одна owned changelog запись, Spec Kit ссылки.
- Callers: `rehearse-restore-scheduled.sh` и workflow cadence сохраняют прежние
  аргументы/результат. Прежние script/verifier/SQL/Compose нельзя смешивать
  с изменёнными версиями большой плановой ветки. Их регрессии обязательны.

## Приёмка реализации и рабочей операции

Положительные случаи: точный непустой комплект, допустимые ключи с Unicode
и пробелами, обычный файл нулевой длины, пустой источник и точная пустая
новая корзина. После совпадения байтов, прежней сверки БД и полного cleanup
каждый допускает PASS. Пустые каталоги исходника не являются S3-объектами;
источник с пустым файлом требует соответствующий объект нулевой длины.

Отрицательные случаи: missing/extra/duplicate, same-size corruption,
неполное перечисление, failed HEAD/GET, короткий/длинный поток, source drift,
symlink/hardlink/FIFO, ошибка доступа, неканонический ключ, пустой источник
при непустой корзине, timeout и сигнал, неизвестный исход контейнера,
ошибка cleanup/чужая коллизия. Каждый причинно исключает PASS и сохраняет
чужие ресурсы. Отдельно доказать освобождение ответа/соединения на ошибках.

После независимых требований/checklist/analyze и сверки существующего #7804:
узкий код со свежей master → профильные проверки → независимое code review
и convergence → exact-SHA PR gates → обычный общий выпуск. Этот документ
не является разрешением ставить helper на сервер в обход выпуска.

Перед реальным восстановлением: свежие canonical две ссылки, исходные суммы,
точный установленный набор script/verifier/SQL/Compose/SDK image, отсутствие
активного владельца deploy lock, здоровые PG/MinIO. По одной копии; cleanup
и здоровье продукта до второй. Расход включает новую корзину, временные
DB/WAL, существующий metadata staging, журналы и inode; отсутствие второго
полного object staging не отменяет расчёт. Неизвестный расход — HOLD.

Результаты по каждой копии записываются отдельно. Удаление38 требует отдельного
окончательного решения после доказательств и свежей проверки набора/ссылок
под общей блокировкой. Полные F273/T113/T116 и трафик не закрываются.
