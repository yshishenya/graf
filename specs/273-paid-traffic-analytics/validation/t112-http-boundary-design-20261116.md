исправления H1 из `t112-http-preflight-20261116.md`, не приёмка реализации.
Рабочий сбор закрыт, T112/T113 и коммерческие критерии остаются открытыми.

## Область и порядок

Сначала реализовать и причинно проверить внешнюю границу обоих будущих POST,
затем подключить общий service/выдачу/renewal и реальные detail callers.
Это зависимость полного HTTP пути; отдельная граница не объявляется T112.

Переиспользовать установленный снаружи HTTP middleware
`ProductAnalyticsIngressGuard`. Его прежние три API пути и ограничения
сохраняются. Для `/meetings/{component}/result-viewed` и
`/desktop/meetings/{component}/result-viewed` добавлена отдельная узкая ветвь.
Компонент — один непустой сегмент: неканоническая запись UUID также попадает
под ограничение до штатного разбора UUID маршрутизатором.
Она окружает всё ASGI приложение: зависимости, обработчик, закрытие сессий,
`session_renewal_middleware` и завершение ответа. Штатное продление сессии
сохраняется; его отдельная запись не подменяет атомарный ledger commit.

До зависимостей отвергать non-JSON, слишком большую объявленную длину,
реальное тело свыше 2048 bytes, неоднозначный JSON и всё кроме единственного
ASCII `proof` длиной не более1536 bytes. Читать stream только до предела;
принятые bytes передавать дальше через ограниченный receive. Не читать
форму, не отражать содержимое в ошибке, не сохранять его в журнал.

Один абсолютный монотонный срок устанавливается до чтения тела. Внутренняя
работа ограничена 1,5s с остатком до общего2s для отмены/закрытия; будущие
service/SQL используют этот же срок, а не получают новые независимые2s.
Собственный ответ буферизуется ограниченно до возврата всего внутреннего
ASGI вызова: accepted/proof нельзя отдать до окончания middleware/cleanup.
Timeout/ошибка после возможного commit возвращают unavailable без повтора.
Все ответы этой ветви private/no-store; auth/CSRF статусы сохраняются.

Синхронные части не прерываются asyncio timer: явная проверка срока после
body/JSON/ASGI возврата обязательна. Неограниченный materialization общего
review/digest сюда не добавлять; его отдельный SQL cardinality/size guard
и проверки остаются обязательными до подключения полного HTTP пути.

## Причинная проверка границы

- RED: реальный `session_renewal_middleware` задерживается после handler;
  одна route-only граница не ограничивает ответ.
- GREEN: внешний guard отменяет работу, ждёт завершения cleanup и выдаёт
  только unavailable, без отложенного второго ответа/живых request tasks.
- Штатный быстрый renewal сохраняет cookie/срок; не подменять его заглушкой
  в единственном положительном случае.
- Slow/chunked/disconnected body; ложная/отсутствующая длина;2048/2049 bytes;
  duplicate keys/не-ASCII/1536/1537 bytes; urlencoded/multipart отвергаются
  до ловушки form/auth; допустимый JSON не освобождается от CSRF.
- Реальное ожидание небольшого DB pool и отмена SQL/rollback/close должны
  быть приняты отдельными испытаниями; успешный чистый ASGI пример не
  объявляется доказательством очистки соединения при всех DB отказах.
- Остальные маршруты и три прежних analytics ingress сохраняют поведение.

## RED настоящей БД: точное владение cleanup

Первый запуск:56PASS/1FAIL. Отмена `pg_sleep(10)` в auth вернула ответ за
~1,55s, но оставила `AsyncAdapt_asyncpg_connection._terminate_graceful_close`
task. Это настоящий недостаток границы, не отказ рабочей БД. Тест сохраняется.

Минимальное исправление без новой session factory: ContextVar уникального
владельца запроса и публичные SQLAlchemy Pool events checkout/checkin/invalidate.
Checkout связывает точный pool entry с владельцем и его driver connection;
checkin снимает связь до возможного повторного использования. Остальные
запросы без этого ContextVar проходят без изменения. На invalidate только
своего соединения asyncpg `driver_connection.terminate()` завершает его
без штатного двухсекундного graceful ожидания. Проверяются одновременно
identity владельца, pool entry и driver; чужой или уже возвращённый ресурс
не затрагивается. Не использовать private adapter API или engine.dispose.

Внутренний ASGI вызов выполняется одной явно принадлежащей запросу task.
При рабочем timeout сначала отменяются tasks, владеющие ещё выданными
соединениями; при их отсутствии — корневая ASGI task. Одновременная отмена
всех дочерних tasks прерывала SQLAlchemy bookkeeping и возвращала закрытый
driver в pool; выбранный порядок сохраняет штатное освобождение. По публичному
Task.get_context() Python>=3.13 выявляются также дочерние tasks этого же
ContextVar (включая shielded close), они тоже должны закончиться до ответа.
Сам ответ accepted отдаётся только при завершённом владельце и успешном
сроке. На отмене/неизвестном commit всегда unavailable и0 автоматических
повторов. Реальный малый pool, другой одновременный запрос и возврат/reuse
соединения проверяют отсутствие воздействия на чужой ресурс. Отдельная
проверка медленного close обязательна перед объявлением общего HTTP PASS.

Текущая регистрация Pool events действует в процессе, но ветвь terminate
ограничена точным owner/entry/DBAPI/driver. Стадии connect и включённый в
рабочем engine pre-ping выполняются до checkout; владение на этих стадиях
данным registry не доказано. Ни успешные checked-out тесты, ни присоединение
tasks не заменяют отдельную проверку этих стадий и общего предела очистки.
