## N1 — P2: метаданные Numeric занижают исходный размер выражения

Место: `cabinet/result_projection_budget.py:60–64`; допуск выражений —
`_bounded_projection:78–93`. Для всякого `Numeric(p,s)` без Float берётся
константа `32 + 2 * (p + abs(s))`. Проверяется тип выбранной expression, но
не доказано, что PostgreSQL применяет к её результату соответствующий typmod.
Арифметические BinaryExpression проходят нынешний проверяющий обход.

У SQLAlchemy 2.0.51 обычное умножение двух Numeric сохраняет один из типов
операндов: `sql/sqltypes.py:106–123` и `579–594` устанавливают результату
тип через `other_comparator.type`/`self.type`, без вычисления увеличенной
точности и без добавления SQL CAST к результату арифметики. PostgreSQL
ограничивает `NUMERIC(1000,0)` при сохранении в такой столбец или явном
приведении, но промежуточное `numeric * numeric` может иметь намного больше
цифр. Ограничение исходного столбца не ограничивает результат умножения.

Конкретный допустимый исходный случай: столбец `NUMERIC(1000,0)` содержит
положительное число из 1000 девяток. Семь последовательных возведений в
квадрат дают 128000 цифр; результат остаётся в диапазоне PostgreSQL numeric
(до 131072 цифр перед точкой), заканчивается на 1 и не теряет крайние группы
нулей при двоичном кодировании. Тип SQLAlchemy при этом остаётся
`Numeric(1000,0)`. Можно построить последовательность через подзапросы с
выбором `c * c`, без raw SQL, неизвестных функций, TypeCoerce или literal
column. Девять выбранных aliases такого результата имеют около
`9 * (8 + 2 * 32000) = 576072` двоичных байт в одной строке. Нынешняя
оценка — только `9 * 2032 = 18288` байт. Она пропускает строку сверх
512 KiB и так же занижает накопленный расход. JSON-фаза к Numeric не
применяется и этот недочёт не исправляет.

Это статический вывод из проверенного кода и правил типов; reviewer не
запускал новый PostgreSQL пример и не заявляет измеренное время его
исполнения либо достижимость такого Numeric в нынешнем общем reader.
Наличие будущего тайм-аута не делает константу доказанной верхней границей.
Речь об уже принимаемом компонентом классе выражений, а не о требовании
поддержать неизвестный новый тип или будущую функцию.

Обязательное исправление: либо считать фактический числовой транспортный
размер на стороне PostgreSQL (например, длину его двоичного numeric encoding),
либо закрывать такие Numeric выражения, пока не доказано принудительное
ограничение результата на самой выбранной expression. Одного `column.type`
или точности исходного столбца недостаточно. Пределы не увеличивать.
Добавить причинную проверку результата арифметики с сохранёнными p/s и
превышением настоящего row/cumulative размера, отдельно от проверки прямого
ограниченного столбца или явно приведённого результата. В нынешних 31 тесте
Numeric отсутствует, поэтому их PASS этому замечанию не противоречит.

## Что подтверждено в остальных числовых фазах

- SQL JSON измеряется как исходный `::text` в UTF-8, без предварительного
  преобразования в JSONB. Для SQL JSONB прибавляется двоичный version byte.
  String/Text и bytea измеряются на стороне БД; SQL NULL даёт ноль, JSON null
  остаётся четырьмя байтами и одним узлом. Каждая выбранная alias/expression
  участвует в расходе, включая повтор одного поля.
- Public Select/subquery/column API сохраняет Q и его binds, добавляя только
  внешний cap+1 prefix для подсчёта. Исходный reader не вызывается компонентом
  и ORM result-map не переписывается. Для scalar без SQL LIMIT считается
  фактическое множество SQL строк, а не единственная возвращаемая scalar.
  Пустой Q даёт нулевые показатели.
- Raw-byte approval предшествует отдельному запросу структуры. Рекурсивный
  обход использует `json_each/json_array_elements/json_typeof`, сохраняет
  ранние значения повторных ключей и не подменяет их JSONB-нормализацией.
  Неподходящие типы получают пустой object/array до вызова соответствующей
  функции. Корень имеет depth0; предел depth32 проверяется через depth33,
  nodes65536 — через nodes65537. Если ограниченный обход не исчерпал дерево,
  превышение числа узлов само закрывает бюджет.
- Состояние Python накапливает rows/raw_bytes/json_nodes до исходного Q;
  неизвестный исход заранее оставляет `failed=True`. Отказ не возвращает
  резерв и не позволяет повторить чтение тем же состоянием. SQLAlchemyError
  превращается в общий `ProjectionBudgetExceeded` с подавленным выводом
  исходного контекста; само приложение здесь ничего не журналирует.
- Неизвестные типы, TextClause, TypeCoerce, literal columns, неизвестные или
  квалифицированные функции, mapped entities с relationships и явное
  streaming отвергаются. Эти проверки не доказывают весь будущий перехват
  Session и не рассматриваются как такое доказательство.
- Два собственных CTE имеют явные имена; LATERAL children реально присоединён
  через JOIN true. Текущий тест отдельно компилирует 50 свежих построений.
  Нет GUC counters, новой таблицы продукта, зависимости или изменения схемы.

Пределы в текущем коде сохранены: 4096 rows/Q, 16384 cumulative rows,
8 MiB raw logical bytes, 512 KiB/row, 256 KiB/field, depth32, nodes65536.
Код не выдаёт счёт logical reads за отсутствующий предел 128 фактических SQL.
