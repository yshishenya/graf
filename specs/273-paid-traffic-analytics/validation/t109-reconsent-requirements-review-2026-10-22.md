## Первый P1 — учебное доказательство smoke

`run-product-analytics-provider-smoke.sh` создаёт version=1 retention receipt
без `recorded_at_epoch`. После обязательной проверки свежести такое состояние
правильно блокирует готовность; исправлять freshness gate ради smoke нельзя.
Минимально допустимо обновить только учебный receipt до version=2 и текущего
целого epoch, сохранив `until_decision`, категории и остальные проверки.

Обязательная проверка — исполнение реального smoke пути с заглушенным внешним
транспортом и его ожидаемыми статусами, а не только наличие строки version=2.
Отсутствующий/старый receipt в отрицательных тестах должен по-прежнему
блокировать readiness. Учебные basis/approval/key не являются рабочим согласием
или принятием инфраструктуры. Рабочие flags, архивы и state files не менять;
откат остаётся metadata-only, без вызова рабочего executor.

## Второй P1 — новый выбор после смены редакции

Текущий `handleConsent` сначала вызывает `consentStateFor`, который отклоняет
старые custom metadata, и только затем мог бы вызвать `persistConsentMetadata`.
CookieConsent при revision bump пишет новую библиотечную revision, сохраняя
старую custom data. Поэтому действительный новый выбор может остаться
заблокирован. Исправление должно восстановить новый явный выбор, сохранив
запрет автоматического обновления прежнего разрешения.

Предложенное разделение допустимо:

- `onFirstConsent` и `onChange` представляют новый явный выбор; новый режим
  разрешено вычислить из его действительных categories и текущей библиотечной
  revision, затем сохранить текущие custom metadata и повторно прочитать запись;
- `onConsent` включает автоматическое чтение при загрузке. Для него остаётся
  строгая проверка сохранённой редакции: старая/неизвестная запись не обновляется
  в текущую автоматически и не включает необязательные провайдеры;
- до успешного сохранения и повторного чтения согласованного текущего выбора
  никакая необязательная передача/загрузка провайдера не разрешается.

Это применение FR-001/003/046/059, а не добавление нового правила. При проверке
реализации обязательны следующие границы:

| Граница | Что нужно сохранить/доказать |
| --- | --- |
| Источник нового решения | Текущая revision берётся из настоящего cookie библиотеки в callback/getCookie. Fallback, который сам присваивает `revision: consentRevision()` результату preferences, не может служить доказательством нового текущего cookie. |
| Categories | Только закрытый известный набор, без дублей, с necessary. Unknown/повреждённый набор закрывает необязательные цели, а не заменяется «разрешить всё». |
| Старая custom data при свежем выборе | Разрешено обновить metadata только нового явного решения с фактической текущей revision. Само наличие новой конфигурации страницы этого не разрешает. |
| Сохранение и повторное чтение | Запись недоступна/не сохранилась/повреждена или отличается по текущей revision/категориям/metadata — запрет до загрузки и следующей передачи. Проверка одной только попытки `setCookieData` недостаточна. |
| Автоматическое чтение | Старая, отсутствующая или неверная revision остаётся запрещённой; callback не повышает её до текущей. Уже сохранённое действительное текущее решение может применяться на повторном визите. |
| Отказ и отзыв | Новый necessary-only и последующий отзыв не требуют разрешить аналитику для сохранения решения. Перед следующей соответствующей передачей провайдеры блокируются; FR-004 сохраняет равное число действий. |
| Раздельность целей | Analytics, advertising attribution и behavior replay не разрешают друг друга. Нормализация metadata не расширяет выбранные категории. |
| Порядок callbacks | Реальная последовательность first/change и последующего consent не должна повторно запускать провайдера, удваивать событие или возвращать прежнее разрешение. |

Для regression требуются оба уровня: синтетический harness для отказов/ошибок
хранения и настоящий браузер с vendored CookieConsent 3.1.0. В реальном сценарии
нужно сначала сохранить старое разрешение с его custom data, сменить редакцию,
доказать отсутствие автоматической активации, сделать новый выбор, затем
проверить сохранённую текущую metadata и поведение повторного визита.
Отдельно сохранить новый отказ и отзыв после разрешения. Сеть провайдера в
этих проверках заменяется заглушкой; реальные идентификаторы не нужны.

Это исправление не обещает остановить уже загруженный сторонний скрипт старой
вкладки и не закрывает offline/advertising revision или все writer gates T106.
Серверные ограничения двух first-party relay и текущая revision запроса
сохраняются. Успешное повторное согласие не принимает новое основание IP.
