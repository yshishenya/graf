## Найденный существующий образец

`cabinet/web_routes/notifications.py:35–44`, `notification_snapshot_db()`:
на свежей сессии вызывается
`db.connection(execution_options={"isolation_level": "REPEATABLE READ"})`,
затем устанавливается tenant scope и только затем начинается чтение.
Это подтверждённый исходниками образец выбора изоляции до первого запроса,
а не наблюдение рабочего PostgreSQL и не готовый T113 verifier.

Применение к аналитике требует отдельной проверки: legal/readiness и
действующие session/membership/source fences должны сохранять свежесть.
`FOR UPDATE` в REPEATABLE READ может закончиться конфликтом сериализации;
такой исход должен закрывать аналитическое решение без автоматического повтора.
Один устойчивый снимок сам по себе не доказывает свежесть допуска перед INSERT.

## Возврат одного Python-значения не равен одному SQL-результату

Перечитаны полные функции. Следующие запросы используют `db.scalar()`
с сортировкой, но без явного SQL LIMIT:

| Функция | Область фактической выборки |
| --- | --- |
| `queries._latest_media_revision` | Все принятые immutable ревизии данной встречи |
| `queries._latest_result` | Все результаты effective query текущей ревизии; сама query также требует учёта |
| `queries._latest_workflow` | Все workflows встречи и выбранной ревизии |
| `outcomes.progress.latest_summary_attempt` | Все попытки выбранного template/result/revision |

Основной текущий review часто переиспользует prefetch с lateral LIMIT1.
Однако предыдущая встреча серии имеет другой meeting_id и обращается
к `_latest_media_revision` и `_latest_result` без такого prefetch.
Исторический выбранный source_result_id также может дать cache miss
у summary attempt. Нельзя добавлять LIMIT1 только в аналитической копии
запроса и считать это эквивалентом общего reader.

Здесь подтверждена форма SQL в исходниках. Число реально переданных
драйвером строк ещё не измерялось; это обязательная причинная проверка
будущего ограничения, а не новый установленный рабочий отказ.

## Ранние чтения и допустимая область ограничения

`load_fresh_result_view_bindings()` сначала вызывает `lock_meeting_fence()`.
Последний возвращает полный `Meeting` через `select(Meeting) FOR UPDATE`,
а не только числовой ключ. Поля этой модели ограничены SQL String(N),
числовыми значениями, UUID и датами; больших Text/JSON полей в текущей модели
нет. Поэтому этот факт не доказывает неограниченную текущую Meeting-строку.
При любом будущем guard порядок этой операции должен быть явным;
нельзя заявлять, что до неё вообще не материализуется ORM.

Текущая `_account_transaction(require_period=True)` до callback читает
auth session, membership, workspace, device bindings и devices. Это
отдельная область допуска, которую нельзя потерять при guard проекции.
Повторно проверенный настоящий `_result_period_context()` всё ещё
возвращает отсутствие контекста (`yield None`). Рабочего открытия нет.

## Следующее проверяемое решение

Независимый проверяющий первоначально сообщил промежуточный
проект: ограничивать каждый фактический SELECT общей свежей Session до
материализации числовым агрегатом точного SQL subquery и использовать
снимок, выбранный владельцем до первого SQL. Так можно сохранить общий
reader без второй реализации его selectors. Это историческое предложение;
окончательный HOLD ниже отменяет допуск к этому варианту.

До реализации необходимо доказать охват `execute/scalar/scalars/get`,
отсутствие обхода через Core/connection, сохранение фактических locks,
запрет неучтённых форм и соответствие строк/байтов/JSON последующему чтению.
Одной суммы `pg_column_size` недостаточно для размера распакованного текста
или глубины JSON. Общий срок, cleanup, отсутствие повторов и закрытый T113
сохраняются. Никакой публичный запрос не выбирает новый режим сессии.

## Последующее уточнение: два запроса не равны одному выбору

Проверяющий позднее сообщил H1 и изменил проектный вывод на HOLD/P2=1.
Промежуточное SCOPED DESIGN PASS не является текущим допуском. Окончательный
отчёт получен, завершение проверяющего подтверждено. SHA-256 отчёта
`t112-projection-budget-preflight-20261116.md`:
`b3f5344650831ed104af19a108bbc870de0813659723f3ca44f644b5302f2356`.
Итог: HOLD, P1=0/P2=1, H1. Основной исполнитель не меняет его отчёт.

RR сохраняет набор видимых строк, но не выбирает единственную строку среди
равных ключей сортировки. Поэтому numeric aggregate точного LIMIT-запроса
и последующий исходный запрос могут охватить разные строки даже без writer.
Это применимо и к вложенному LATERAL. Доказательство одинаковых parameters
и snapshot не закрывает этот пробел.

При этом нельзя объявлять все LIMIT1 неоднозначными. В исходной модели
MediaRevision есть `uq_media_revisions_workspace_meeting_revision` по
workspace/meeting/revision_number. Для фиксированной встречи сортировка по
revision_number уже имеет такой уникальный ключ. Это свойство исходников
модели, а не новое чтение рабочего ограничения. Prefetch workflow сортируется
по attempt_ordinal/created_at, dependency — по updated_at. Egress activity
срез50 сортируется только по created_at, а calendar audit срез50 дополнен id.
Одна схема проверки уникальности не подменяет разбор каждого selector.

Текущий независимый проект предлагает проверить супермножество всех возможных
выборов с числовыми envelopes, либо отдельно спроектировать проверку и выдачу
строго одного server-materialized результата. До нового полного допуска
основной код, RED и рабочие проверки этого варианта не начинаются.

## Дополнительная граница размера JSON

`ProcessingResult.provenance_json` объявлен SQLAlchemy JSON; миграция0078
также добавляет `sa.JSON()`. Установленный PostgreSQL asyncpg dialect
в `setup_asyncpg_json_codec` передаёт исходные bytes после decode в json.loads.
Это отдельный источник расхода до построения ORM, не только размер
нормализованного дерева JSON.

Следовательно, измерение только `octet_length(to_jsonb(q)::text)` нельзя
объявлять достаточным верхним пределом исходного JSON-транспорта без
отдельного доказательства: преобразование json → jsonb нормализует
представление, включая незначащие пробелы. Будущий DB preflight должен
ограничивать также исходный JSON/text byte envelope до такого преобразования;
глубина и число узлов остаются отдельными проверками. Тип JSONB и JSON
нельзя смешивать в этом доказательстве. Это исходниковая находка и требование
к причинному PG примеру с большим raw JSON при маленьком нормализованном
дереве; такой пример и рабочая схема в этом проходе не исполнялись.
