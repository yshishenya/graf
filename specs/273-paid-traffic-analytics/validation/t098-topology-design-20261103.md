## Clarify и границы

прежними. Сохранение всех настоящих соседей уже входит в T098. Новое наблюдение

scenario8, законный выпускной путь, рабочие baseline и возврат.

## Минимальный кандидат

1. I1: сохранить действующие map `$kvn_443_backend`, все его строки и upstream
   побайтово, включая пять mail SNI, default10444, special443 и mail10445.
   Исходный public bind и stream log format сохраняются. Ни один старый
   upstream не получает envelope PROXY protocol.
2. I2: новый public map направляет только точный rec SNI на dedicated
   loopback10446, всё остальное — на один loopback strip relay10447.
   На public исходящий PROXY on; входящий public PROXY запрещён.
   У dedicated точные IPv4/IPv6 `ssl proxy_protocol`, прежние guards400/421,
   XFF/X-Real-IP из envelope, XFP=https, HTTP realip отсутствует.
   На обоих новых PP-входах отдельный effective `error_log /dev/null;`
   исключает сохранение malformed header nginx-парсером до HTTP guard.
   На dedicated это заменяет прежний server-level error destination;
   точные новые сокеты не делятся с чужими/default серверами.
3. I3: relay принимает PROXY, повторно читает неизменный ClientHello через
   `ssl_preread on` и выбирает upstream прежним `$kvn_443_backend`.
   Исходящий `proxy_protocol off`, `access_log off` и `error_log /dev/null;`
   заданы явно, без наследования чужого error log.
   Это сохраняет прежний map как единственный источник трёх старых маршрутов,
   без дублирования пяти mail SNI и без нового upstream/процесса/зависимости.
   Неизвестный/пустой SNI по-прежнему следует прежнему default.
4. I4:10446/10447 — выбранные значения только по текущей описи. Перед каждой
   стадией повторяются проверка полного graph/listeners и согласованная
   блокировка; новый конфликт означает HOLD без автоматического выбора порта.
   Закрытая операторская конфигурация использует фактический map и public bind.
5. I5: A добавляет dedicated/relay при прежнем public режиме, не меняя старые
   направления. B переключает public map/PROXY, держит обе стороны до полного
   дренирования. C снимает rec10444 и дренирует последнее старое поколение;
   noSNI/wrong-SNI с Host rec не должны достигать API. D принимает точный
   Docker peer тем же установленным образом без смены прочих настроек.
   Возврат — прежняя последовательность в обратном безопасном порядке;
   relay/dedicated не удаляются до завершения использующих их workers.
6. I6: изолированный стенд использует исходные rec/routing и сохранённый map
   с тремя учебными TLS upstream. Проверить все пять mail SNI, default,
   special, noSNI, обе IP-семьи, поддельные заголовки,
   ранний/поздний ClientHello, A/B/C и возврат, устойчивую очистку.
   Для обоих PP-входов отдельно заданы PP+ClientHello в одной записи,
   раздельные записи и фрагментация PP/ClientHello. Malformed/truncated PP
   даёт закрытие транспорта/internal400 stream без требования HTTP-ответа;
   dedicated с валидным PROXY UNKNOWN и законченным TLS даёт HTTP400 до API.
   Strip relay с валидным PROXY UNKNOWN выбирает прежний upstream по SNI,
   не используя пустой адрес как основание доверия и не передавая envelope.
   В stream/internal400 нельзя объявлять полученный клиентом HTTP400.
   Поздний ClientHello проверяется на каждой стадии применения и возврата
   отдельно для всех трёх прежних направлений, не только для rec.
   Raw fixture отдельно сравнивает каждый байт исходного TLS ClientHello с
   полученным на каждом из трёх старых upstream; PP envelope отсутствует.
   Негативный лог-тест посылает уникальный учебный malformed marker на оба
   новых входа и проверяет отсутствие marker/envelope в собственных всех
   наследуемых/серверных access/error/CLI логах; одного access_log off мало.
   HTTPS special fixture явно не является настоящим VLESS/REALITY.
7. I7: исходный ресурсный профиль расширяется на все три направления:
   после10 прогревов на каждое держать120 TLS соединений (40 на направление)
   не менее30с; каждую секунду измерять каждый worker, включая дренирующие.
   FD/soft FD и socket FD/worker_connections строго ниже0,70.
   Baseline/candidate по600 новых соединений (200 на направление),8 запросов/с,
   окно не менее75с; p95 nearest-rank отдельно на направление, прирост<10мс.
   Все запросы200 с ожидаемым учебным телом; неполнота/ошибка — FAIL.
   Это усиление существующей проверки за счёт нового реального маршрута,
   остальные требования к upload/WebSocket/half-close/keepalive сохраняются.
8. I8: до рабочего изменения нужны успешные исходные проверки всех настоящих
   соседей, в том числе действующий VLESS/REALITY своим разрешённым клиентом
   и настоящий Stalwart. Нынешний отказ loopback443/10445 — исходный блокер,
   его нельзя принять как «сохранённую доступность» или обойти HTTPS-заглушкой.
   Все рабочие IP/URI/секреты остаются вне evidence. Сбор IP/provider выключен;
   writer→DB→report — только при его собственном допуске.
