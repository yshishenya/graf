## Найденные дефекты и исправления

При первом чтении реализации найдены три существенные границы, сообщённые
исполнителю до итогового прогона. Все три исправлены в проверенных байтах.

1. SQL-проверка владельца в очистке могла ждать без ограничения. Теперь
   `asyncio.timeout_at(until)` охватывает весь `identity`, включая SQL и Docker.
   Native `cleanup_identity_timeout` задерживает действующий owner SQL и сжимает
   прежнее окно очистки до 100 мс. Тест требует ответ раньше 1,5 с, отсутствие
   DROP и сохранение обеих БД и staging при недоказанной identity.
2. Завершение процесса `docker exec` на хосте не доказывало завершения
   `pg_restore`/`psql` внутри контейнера. Теперь отдельная detached-обёртка
   ожидает native child и атомарно публикует код выхода с SHA256 команды
   в UUID-файл. Проверка требует обычный файл без ссылки, owner root,
   mode0600, nlink1, ограниченный размер и точное содержимое. Проверка очистки
   ожидает все зарегистрированные команды до DROP и удаления PG staging.
   Неизвестный spawn, незавершённая загрузка или недоказанный marker сохраняют
   PG-ресурсы и запрещают успешную готовность. `cancel_native`, `unknown_native`
   держат настоящий child перед подключением: даже при отсутствии PID в БД
   DROP не происходит; после разрешения child очистка завершается.
   `native_unresolved` подтверждает сохранение ресурсов при неизвестном исходе.
3. Потерянный ответ `docker start --attach` мог оставить известный контейнер
   `mc` живым во время удаления bucket. Теперь все подтверждённо принадлежащие
   процедуре контейнеры удаляются, их отсутствие проверяется, и лишь затем
   SDK удаляет объекты и bucket. При неизвестном контейнере bucket сохраняется.
   `unknown_mirror` запускает настоящий задержанный `mc`, теряет ответ attach
   и в SDK-проверке требует отсутствие всех собственных `mc` до remove_bucket.

## Проверенная корректность

Файловый manifest читает все байты через удерживаемые directory FD с
`O_NOFOLLOW`, проверяет права0700/0600, владельца, тип и отсутствие hardlinks.
Повторные снимки inode/размера/mtime/ctime дерева обнаруживают замену и
изменение; SHA256 связывает точное содержимое с размером и ключом.
UTF8/NFC-ключи допускают вложенные `audio/file`, но запрещают неоднозначные
компоненты, дубли и file/prefix collisions. Пустые файлы допустимы.

SDK manifest читает каждый объект полностью, сверяет размер и SHA256,
повторяет list/stat/config и закрывает с освобождением каждый response даже
при ошибке. Versioning, lifecycle и object-lock отклоняются. Разница точности
Last-Modified между S3 list и HEAD учтена: key/size/etag сравниваются между
методами, полный набор полей сравнивается до/после внутри того же метода.
Пустой bucket допустим. Worker thread удерживается до завершения при отмене.

Подготовка использует настоящий `rec-db-verify --inventory`, native
`pg_restore`, отдельный native разбор схемы, прежний полный verifier и
`mc mirror` из read-only копии. Две UUID БД имеют CONNECTION LIMIT0;
обычное подключение maintenance-роли отклоняется. Два независимых пути
подтверждают один PostgreSQL cluster. Известное создание получает OID до
передачи отмены; неизвестный CREATE не разрешает удаление по имени.
DROP сверяет name/OID, не использует FORCE и проверяет отсутствие цели.

Native успешный сценарий восстанавливает полный migrated dump с девятью
delivery states и двумя объектами, включая Unicode и пустой объект. Внутри
сохранённого контекста выполняются пониженные replay/карантин/удаление,
COMMIT и новое физическое чтение через NullPool: восемь строк остаются после
удаления одной. Лишь затем удаляются цели. Тест действительно понижает
session authorization и включает row_security; отдельную рабочую границу
выдачи однократных полномочий верхнего оператора он не доказывает.

Дополнительные отказы охватывают ошибку тела, двойную отмену CREATE/cleanup,
потерянный ответ CREATE, ошибку DROP, native schema mismatch после создания
обеих БД и порчу объекта без изменения размера. Последний schema-тест явно
проверяет создание двух БД, поэтому ранний отказ до сравнения не выдаётся
за проверку native schema verifier. Сохранённые при отказах ресурсы удаляет
владеющий учебным стендом тест, а не неподтверждённый поиск по похожим именам.

## Границы решения

Доверенный caller по-прежнему обязан удерживать deployment lock, привязку
установки и неизменной копии, доказательство остановленного источника и
согласованного export, передавать SDK с конечными HTTP timeout без retries,
завершить все собственные SQL/CLI children и закрыть target-соединения до
выхода из контекста. Эти обязанности явно заданы внутренним интерфейсом;
данная стадия не превращается в публичный callback/pass-file/SQL интерфейс.

Остаются в том же кандидате T113: полный initial/backup/verify/actual-restore/
resume, durable attempts, полные immutable комплекты, полное сравнение
рабочих данных и объектов при actual cutover, retention/access/resource
проверки, делегирование shell в конечный trusted entrypoint и выпускные
проверки. Это не основания отклонять проверенную внутреннюю стадию, но
они не могут считаться выполненными по её результатам.

Рабочая T0 не установлена, `activation_recovery_unverified` сохранён.
T113/T112 и коммерческие AC01–AC06 остаются открыты. Локальные учебные
проверки не подтверждают GitHub CI точного SHA, Full/CD, рабочее включение
аналитики/IP, посещения, новых внешних клиентов или продажи.

Ревьюер создал только этот отчёт. Исходники, spec/plan/tasks/checklist,
Git/GitHub и рабочую среду не менял; тесты, сборки, SQL и серверные команды
не запускал. Чужие изменения сохранены.
