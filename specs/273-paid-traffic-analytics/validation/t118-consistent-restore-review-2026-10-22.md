## Конкретные недостающие проектные решения

### R1 — как создаётся согласованная точка полного набора

Текущий backup writer последовательно tar-копирует работающие volumes.
Указание остановить provider delivery в procedure само по себе не
останавливает записи PostgreSQL/ClickHouse, фоновые workers, очереди и
объектное хранилище. Полный inventory и совпадение hashes подтверждают
прочитанные байты, но не одну согласованную точку состояния этих систем.
Ни plan, ни research/operations не выбирают способ, позволяющий проверить
именно такую копию. Документ обещает полноту восстановления данных,
зафиксированных на момент backup; произвольное сочетание моментов не
является доказательством этого обещания.

**Что должно быть решено до кода:** один поддержанный путь согласованного
создания/выбора набора, его граница с текущим writer, условия начала/окончания
и поведение при неполном завершении. Инженерные варианты для выбора —
контролируемая остановка только PostHog и холодный полный набор либо
поддержанный согласованный online backup; здесь ни один не принят за
владельца. Требование остановить GRAF, новый узел или разрешение рабочих
остановок из этого не следует. Если допускается временная остановка
аналитики, план должен описать управляемое окно/закрытую доставку и отдельное
разрешённое возобновление по существующим защитным правилам.

### R2 — какой именно runtime может прочитать этот набор

Основной runbook требует официальный generated PostHog Compose и
прикреплённые digest образов. Репозиторный
`infra/posthog/docker-compose.posthog.yml` прямо назван metadata-only
handoff contract, содержит сокращённый набор services и placeholder image;
его нельзя без дополнительного решения объявить полным restore runtime.
Копия T117 связывает inventory и данные, но не определяет совместимый
generated compose/configuration/image set для rehearsal.

**Что должно быть решено:** источник проверенного generated runtime,
привязка его версии/config и pinned images к выбранному набору, правила
получения восстановимых конфигурационных bind mounts и секретов без
вывода значений, проверка совместимости/доступности до запуска. Недоступная
версия/config должна давать blocker, а не тихо заменяться latest или текущим
произвольным runtime. Не требуется автоматически архивировать все образы
или добавлять новый хранилищный сервис; нужен один принятый воспроизводимый
вариант в существующем плане.

### R3 — техническая граница изолированной репетиции и очистки

Procedure описывает target как isolated from production users и
предлагает provider smoke в dry-run **или live-safe**. Этого недостаточно
для определения безопасного запуска клона с конфигурацией восстановленного
PostHog: не выбраны network/ports, доступ к рабочим volumes и внешним
получателям, допустимый набор запущенных workers/plugins и схема
идентификации временных ресурсов. Existing script создаёт фиксированные
rehearsal volume names, не запускает полный стек и убирает volumes только
в успешном пути; это разрыв реализации, а не принятый план изоляции.

**Что должно быть решено:** один конкретный профиль клона с отдельными
project/network/volumes, без доступа к рабочим данным на запись и без
внешних отправок из репетиции; идентификация принадлежащих ей ресурсов,
уборка после success/failure/timeout и трактовка неуспешной уборки.
Требования приватности/сохранности и очистка уже существуют; это их
техническое выражение в T118. Внешние smoke/учебная тревога не должны
неявно входить в изолированное чтение и остаются отдельными действиями.
Безопасный read-only/metadata вывод должен быть тем же при любом исходе.

### R4 — что конкретно считается чтением восстановленных данных

FR-053/quickstart7 требуют согласованное чтение полного PostHog, но
procedure после restore перечисляет health и provider smoke. Health200
может быть получен пустым, неверным или частично восстановленным runtime;
provider smoke может создать новые данные и не доказать наличие старых.
Existing script проверяет archive hash, tar extraction и число файлов;
не проверяет чтение PostHog-проекта/истории или связь restored components.
Июльский receipt с health200 сохраняется как история и не задаёт такой
нормативный критерий.

**Что должно быть решено:** конечный набор чтений/сверок для присутствующих
классов данных и ожидаемые признаки выбранного backup, позволяющие
отличить полное восстановление от пустого/несовместимого. Например,
восстановленная relational configuration и event store должны читаться
тем runtime и относиться к выбранному комплекту; способ сверки и
обработка legitimately empty class должны быть явно выбраны. Это пример
для проектирования, не самостоятельно введённые поля/SQL/численные пороги.
Нужен отказ при missing/incompatible/unknown, metadata-only доказательство
привязанное к комплекту и принятому критерию, с согласованным обновлением
restore-state/readiness/alerts. Исторический file-count receipt не должен
продолжать открывать новую проверку FR-053 как будто критерий не менялся.
