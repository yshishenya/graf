## Остаток P2-01: collector маскирует повторный checkin

В integration:1076–1079 `checkin(dbapi, entry)` добавляет marker только при `entered.is_set()`, exact entry **и `"checkin" not in markers`**. После первого checkin это последнее условие всегда ложно. Таким образом два реальных события того же target entry до ранней точки оставят в markers ровно один checkin; новый count==1 пройдёт в обоих случаях. Это следует непосредственно из callback, без запуска искусственного опыта. Invalidate callback такого подавления не имеет.

Порядок, None и identity принимаются как устранённая часть прежней находки. Для оставшейся точности достаточно минимального test-only изменения наблюдения: учитывать все целевые fault checkin до ранней точки/до первого borrow B, сохраняя exact entry и границу поколения/операции; count должен считаться по несжатому наблюдению. Например отдельный raw counter перед существующим first-marker фильтром либо снятие подавления в этом ограниченном окне. Не включать в этот счёт последующие законные возвраты B/F или следующего POST. Проверка остаётся до gate.set и вне callbacks; callback лишь снимает metadata. Нет основания менять pool/native/сроки/runtime, заново проектировать COMMIT или повторять весь исторический87/312 профиль.

Изменений и запусков по этому предложению здесь нет. Законченный2PASS относится именно к текущему64b6abed; его нельзя считать проверкой будущего raw counter.

## Минимальный проект следующего причинного наблюдения repeated

**Проект допустим только как следующее ограниченное диагностическое наблюдение, не как доказательство уже найденной причины и не как разрешение править runtime.** Цель — увидеть первоначальное исключение именно следующего POST до его преобразования в `_result_session_context:382` и первого refusing caller, не меняя class dispatch.

1. Оставить текущий настоящий сценарий, его исходные budgets/caps/proof/SQL/native операции и expected accepted неизменными. Наблюдать только явный repeated POST fault-случая; его попытку пометить test-only ContextVar, чтобы отделить дочерние задачи этого запроса от ожидаемой отмены первого COMMIT. Никаких дополнительных POST/retry ради PASS.
2. Использовать ограниченный Python exception/call trace для заранее выбранных проектных code objects: `_refuse`, `_result_session_context`, `_account_transaction`, `admit_result_view`, closure verify маршрута и внешний guard. **Не присваивать `_refuse` ни базовому, ни дочернему классу**, не оборачивать их методами и не сохранять до чужого monkeypatch bound original. Это устраняет доказанную subclass/base коллизию прежнего plugin.
3. При первом вызове `_refuse` каждого owner записать только caller name/line, expired/deadline_remaining, failed/budget_failed, same_task, sql_count и числовую фазу; не применять фильтр `not owner.failed`, скрывающий первый вызов после иной причины. При exception event до blanket catch записать только тип исключения и module/function/line; нормальные StopIteration/StopAsyncIteration от await не считать отказом. Не сохранять exception/frame/traceback/locals целиком, строки ошибок, SQL parameters, proof, auth, payload или текст встреч.
4. Trace ограничить повторным запросом и меткой его Context. В выбранных frames отключить line/opcode tracing; максимум фиксированных metadata-записей в памяти, печать после завершения HTTP. Сохранить/восстановить прежний tracing в finally; если сторонний tracer уже активен и безопасное сосуществование не доказано, не подменять его. Native методы, Pool/Session listeners и существующие тестовые callbacks сохраняются.
5. Полный исходный контекст87 может понадобиться для единственного следующего причинного запуска, поскольку исходный отказ возник именно в общем профиле, а адресный повтор его уже не воспроизвёл. Само наблюдение всё равно включается только на repeated fault POST, остальные случаи не получают новый plugin override. Не запускать серию повторов без нового вопроса. Влияние самого trace на время учитывать; исходные2s/1.5s/0.5s не расширять, traced timeout без дополнительного доказательства не объявлять причиной старого untraced отказа.
6. При отказе сопоставить первичное исключение/первый refuse с текущей проверкой источника и числовыми owner/connection/transaction фактами; guard unavailable и позднее ProjectionBudgetExceeded сами по себе недостаточны. Если отказ снова не возник, сохранить результат «не воспроизведён, причина неизвестна», снять observer и оставить HOLD. Сам удачный диагностический запуск не закрывает старый отказ.

Этот проект не требует немедленного запуска; здесь только документальный допуск подхода. Любой иной runtime-fix потребует отдельного независимого проекта по установленной причине.
