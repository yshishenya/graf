# T113: APT callers и условная ветвь прямого dpkg — 01.11.2026

Полоса: read-only investigation; запись результата — docs-only.
Рабочий код, конфигурация сервера, timers, packages, данные и T0 не менялись.
Наблюдения выполнены 31.10.2026 22:59–23:05 UTC (01.11 по Стамбулу).
Основание локальной ветки перед записью: `696d2eaa7`.
Remote master проверен отдельно: `ca02e2cf9bb4d761cc1d24bde230a8071c078361`.

**Вывод:** стандартный путь `apt-get install/upgrade` можно ограниченно
проследить через frontend lock. Но он не описывает автоматическую установку:
`apt.systemd.daily install` вызывает `unattended-upgrade`, в котором есть
прямой `dpkg --configure -a` до `cache.commit`. Поэтому одним `DPkg::Pre-Invoke` нельзя считать охват доказанным: для
этой ветви нужны доказанная недостижимость в принятой policy либо защита
всего entry до ранних эффектов. Исполнение direct dpkg не наблюдалось. Полный J1/L6 и
реализация оператора остаются HOLD. Это уточняет незакрытый охват прежнего
[архитектурного договора](t113-platform-invalidation-design-20261031.md),
не отменяя его принятые I1/I2.

## L1/L3: ограниченная трасса синхронного apt-get

Это исходниковая трасса выбранной нормальной ветви, не новый native runtime
experiment и не гарантия для любых flags/config/delegates.

1. `private-cachefile.h:31–36`: OpenForInstall вызывает Open(true), кроме
   Print-URIs. `cachefile.cc:85–149` получает system lock при WithLock,
   **но** ранние ветви existing Cache / pkgCacheFile::Generate=false
   обходят этот acquisition. Их нельзя пропустить в effective policy.
2. `debsystem.cc:120–187`: нормальный первый Lock получает frontend и inner
   по effective Dir::State::status. Debug::NoLocking и прежний LockCount
   не доказывают новое получение lock. `UnLockInner:208–212` закрывает
   inner FD; frontend остаётся до полного UnLock при LockCount→0:192–206.
3. `DoInstall:906–1048` создаёт локальный CacheFile до OpenForInstall и
   сохраняет объект через InstallPackages и post/fail JSON hooks.
   `UpgradeHelper:22–47` имеет такой же внешний CacheFile lifetime.
   `cachefile.cc:61–76` освобождает system lock в destructor; Close:357–380
   также освобождает его, поэтому изменённый caller требует новой трассы.
4. `private-install.cc:142–169`: APT::Install::Pre-Invoke расположен до
   archives lock, но в указанной нормальной ветви после frontend acquisition.
   Это исправляет неполноту прежнего excerpt: «до archives» не означает
   автоматически «до всех native locks». Для реально configured раннего
   hook всё ещё нужна его собственная классификация воздействия/делегирования.
5. `private-install.cc:382–420`: Download-Only явно делает полный UnLock
   до загрузки; обычная установка перед PM::DoInstall отпускает **inner**.
   Значит нельзя обещать непрерывное удержание backend lock. Нормальный
   frontend остаётся конфликтующим domain через PM/Post-Invoke и внешние
   JSON hooks до выхода CacheFile. Download-Only и early/no-op hooks
   требуют отдельного результата, даже если DPkg::Pre-Invoke не вызван.
6. `private-install.cc:255–258` вызывает APT::Install::Post-Invoke-Success
   и при отсутствии package changes. `:464–467` вызывает его после установки.
   Поэтому DPkg hook не предшествует вообще каждому configured post effect.

Вывод этой трассы нельзя переносить на python-apt API, прямой dpkg,
PackageKit или произвольный subclass по совпадению имени apt.

## L1/L3/L6: фактический daily entry

`apt.systemd.daily:320–335` в обычном входе открывает daily_lock на FD3,
получает flock, запускает собственный child `lock_is_held`, **закрывая FD3
у child**, затем ждёт его и возвращает его код. Lock удерживается родителем,
а не передаётся в apt Python процесс. Прямой вызов `lock_is_held` сам
acquisition не делает; actual argv и доступы к caller остаются частью policy.

Содержимое двух выбранных установленных штатных unit files совпало с ранее
проверенными хешами: apt-daily SHA
`90f87047f4ea2f261f9117d02870de8719f808b911bb1808bf039ff3c162e5e9`,
apt-daily-upgrade SHA
`da0651537cad0ed384291bd50c0bbc3268e6c625626ec9344150de4e8db3925e`.
В них вызовы `apt.systemd.daily update/install`; upgrade содержит
`KillMode=process`. Это чтение **файлов**, не полный loaded/effective unit
с drop-ins/environment или доказательство reap потомков при смерти parent.

`daily:494–502` вызывает `unattended-upgrade`. В точном аутентифицированном
script `run:2101–2108` получает apt system lock; **до открытия cache** есть
ветвь AutoFixInterruptedDpkg (`:2110–2130`): при dirty journal вызывает
`dpkg --force-confold --configure -a` через check_output с
`DPKG_FRONTEND_LOCKED=1` внутри Unlocked. `Unlocked:575–591` отпускает
inner и затем получает его снова. Это прямой dpkg, а не PM/cache.commit;
обработчик `DPkg::Pre-Invoke` из libapt этим вызовом не гарантирован.

Предел вывода: наличие ветви не доказывает её исполнение или полную
достижимость из daily. До неё daily запускает apt-get check, а debSystem::Lock
проверяет CheckUpdates и отклоняет all-digit записи journal. Python-функция
is_dpkg_journal_dirty:635–648 использует re.match("[0-9]+", f), то есть
числовой префикс; C++ CheckUpdates:224–257 требует полностью цифровое имя.
Соответствие actual файлов/входов и native binding ещё не принято. Нужно
доказать недостижимость ветви в конечной policy или защитить весь entry
до ранних эффектов. Нельзя объявить полный охват по одному наличию DPkg hook
либо назвать наблюдение исходника выполненным рабочим обходом.

Далее `cache_commit:857–877` вызывает cache.commit, затем cache.open;
LogInstallProgress.fork:563–572 создаёт child с перенастройкой FD.
Прочитанный installed `apt/cache.py:575–668` описывает SystemLock,
archives lock и временный unlock_inner; native bindings/progress wait и
происхождение этой старой библиотеки ещё не доказаны. Это отдельный entry,
а не подтверждённый C++ CLI trace выше.

`main:1992–2014` после run делает отчётность, stamp и возможный reboot;
`reboot_if_requested_and_needed:1654–1685` может вызвать shutdown с временем
из конфигурации. Deferred reboot и фактические флаги требуют отдельного
охвата; нельзя считать их законченными по одному return cache.commit.

## Ошибки и следующий конечный шаг

`daily:362–386` при Verbose≤1 подавляет stderr apt-get и даже неудачу check
завершает exit0. Ветка unattended failure:495–500 вызывает debug_echo,
который при Verbose=0 ничего не выводит. Указанный результат script и
systemd success сами по себе не доказывают видимое оповещение GRAF.
У unattended собственный file logging (`:1554–1642`), но доставка сообщения
оператору/guard этим наблюдением не проверена.

- [x] Установить точные outer CLI lock lifetime, daily parent FD и отличающийся
  unattended entry по выбранным источникам с явно ограниченными выводами.
- [x] Сохранить прямой dpkg/early/no-op эффекты как незакрытый охват, без
  рабочего изменения и без ложного PASS общего package probe.
- [ ] Выбрать и независимо принять конечное решение для daily caller:
  доказанную недостижимость условной direct-dpkg ветви в принятой policy
  либо **whole-entry** предварительный отзыв до AutoFix/ранних эффектов.
  Для whole-entry связать его
  непрерывный native domain с каждым ready writer, error visibility,
  parent death/descendants и deferred effects. Прежний DPkg hook сам этого
  не доказывает; конкретная обёртка ещё не утверждена/не установлена.
- [ ] Закончить конечный installed entry/config/delegate набор, включая
  реальные root-only scheduler roots и UID1003. Проба `sudo -n true`
  потребовала пароль; пригодный привилегированный путь чтения не подтверждён.
  Недоступность не считается пустым набором. Получение нового доступа
  не обходилось через Docker или чтение старых credentials.
- [ ] Завершить полный J1/checklist/analyze до следующего product кода T113.
