# Контракт: эксплуатация измерения

Покрывает FR-030 … FR-039 и SC-009 … SC-012. Инфраструктурная часть фичи.

## Оповещение о деградации

| Правило | Значение |
| --- | --- |
| Канал | Telegram; локальная деградация — отправитель `2brain.dev`, потеря доступности узла — независимый наблюдатель `astraglobal` напрямую в Telegram |
| Срок доставки | Не более 15 минут от начала деградации |
| Область `analytics` | Доступность узла, отставание доставки, рост очереди, абсолютный объём аналитики и защита запаса её файловой системы |
| Область `host` | Процессор, память, диск сервера |
| Порядок срабатывания | Аналитические правила раньше общехостовых |
| Поведение при деградации | Первой отключается аналитика; продукт продолжает работать |
| Общехостовые правила | Сами не отключают измерение; защита общего диска описана ниже |

### Независимый наблюдатель

Нормативное решение — `research.md` §5: существующий `astraglobal`, systemd timer
раз в 60 секунд, публичный GET `/api/v1/health/live`, timeout 10 секунд,
два последовательных неуспеха → `target_unreachable`, прямой Telegram-путь
без запроса/запуска кода на `2brain.dev`. Проверяются TLS, HTTP и JSON;
ошибка и неизвестный исход не становятся PASS. От первого непрерывного отказа
до принятой доставки ≤15 минут; timeout/ошибка отправки сохраняют недоставленное
состояние, повтор допустим без выдуманного receipt. Только безопасные метаданные;
секреты root 0600 вне Git, без доступа к БД/SSH GRAF. При полном отказе продукта
его доступность не обещается. T119 обязана проверить выключенный целевой стенд,
недоступность канала, неполный/неверный ответ, повторы и восстановление.

### Один физический диск продукта и аналитики

- `analytics_storage_bytes` — сумма занятых байтов непересекающихся классов
  аналитики из capacity baseline, включая локальные архивы; без двойного счёта
  тома/ссылок. `analytics_budget_bytes` — положительный абсолютный бюджет,
  принимаемый оператором в T097 вместе с измеренным ростом и датой расширения.
  Неизвестный объём или непринятый бюджет не означают ноль или готовность.
- `filesystem_free_bytes` и `filesystem_free_percent` — доступный запас одного
  файлового ресурса. Совпадение filesystem продукта и аналитики фиксируется по
  идентичности ресурса, а не по разным путям. При общем ресурсе это один замер,
  даже если прежние поля называются `analytics_disk_free_percent` и
  `disk_free_percent`. Он не доказывает, кто занял место.
- Достижение бюджета аналитики либо запас файловой системы аналитики `<20%`
  вызывает защитное отключение новых необязательных записей/доставки аналитики
  и внешнюю тревогу. `<10%` дополнительно вызывает критическую тревогу общего
  диска. При одновременном срабатывании сохраняются оба факта, отключение
  выполняется один раз; причина — защита общего запаса, виновник неизвестен,
  пока отдельно не проверены объём и рост классов. Историю не удаляют.
- Тревога CPU/памяти/общего диска сама не запускает второе отключение/откат
  продукта. Если файловые системы разные, порог общего диска не переносится
  на аналитику; бюджет и запас аналитики проверяются отдельно. Ошибка определения
  ресурса/замера блокирует заявление о готовности и требует оповещения.
- После защиты готовность остаётся закрытой до проверки запаса, бюджета,
  прогноза роста и управляемого восстановления оператором. Само исчезновение
  тревоги не включает запись заново. SC-012 проверяется при принятом запасе;
  истощение диска проверяется отдельно как срабатывание FR-032.

#### Состав расхода T116

Единый источник расчёта — существующий
`infra/scripts/measure-posthog-storage-growth.sh`; guard использует его полный
результат, а не повторяет формулу. Все присутствующие Docker volumes и bind
mounts аналитики сопоставляются с проверенным inventory
`infra/posthog/backup-volumes.txt` и фактическими mounts. Неучтённый том/bind,
неизвестное назначение или ошибка доступа дают INCOMPLETE.

| Расходный класс | Охват |
| --- | --- |
| `relational` | Весь выделенный том PostgreSQL PostHog, включая его WAL/служебные файлы; не складывать с размерами таблиц этой же БД. |
| `events` | Выделенные тома ClickHouse целиком; не прибавлять повторно `system.parts`. |
| `object_storage` | Присутствующие objectstorage, seaweedfs и posthog-media. |
| `queue_cache` | Все присутствующие варианты redis/redis7. |
| `broker` | Присутствующие kafka/redpanda. |
| `coordination` | Все присутствующие zookeeper data/datalog/logs. |
| `runtime_auxiliary` | Присутствующие caddy data/config и другие явно классифицированные служебные mounts аналитики. |
| `graf_analytics_tables` | Только аналитические relations БД GRAF, их индексы, TOAST, forks и segments: агрегаты, атрибуция, привлечение, служебные записи аналитики и сетевой журнал T110. Записи встреч и весь том GRAF DB сюда не входят. |
| `backup_artifacts` | Реально находящиеся на узле аналитические архивы, manifests и их staging/failed/incomplete файлы. Статус успешной копии не меняет занятого места. |

Для файловых классов учитываются выделенные блоки файлов (`st_blocks × 512`),
а не логическая ёмкость тома. Для `graf_analytics_tables` разрешён только
metadata-разбор каталога relations и выделенных блоков соответствующих файлов;
строки таблиц не читаются. Список relations задаётся явным inventory; новая
аналитическая таблица без классификации запрещает PASS. Отсутствующий до T110
сетевой журнал отмечается `not present in reviewed runtime`, а не выдуманным
нулевым измерением.

Общий WAL, системные каталоги и прочий совместный служебный расход БД GRAF
не входят в `analytics_storage_bytes`; их доля, вызванная аналитикой, неизвестна,
а не равна нулю. Полный физический разбор общей БД каждую минуту не требуется.
Риск расхода этих файлов и данных продукта учитывает один замер общего
filesystem и его защита `<20%`. При наличии отдельного безопасного замера
общий расход можно показать как диагностику, без прибавления к аналитическим
классам и без изменения 128 GiB. Бюджет сравнивается непосредственно с
`analytics_storage_bytes`.

Каждый объект учитывается один раз по файловой идентичности устройства/inode,
включая hardlinks. Повторные пути и bind aliases одного корня объединяются
только после подтверждения идентичности. Пересечение корней разных классов
либо непрослеживаемая ссылка даёт INCOMPLETE; вложенный mount нельзя считать
и частью родительского обхода, и отдельным томом. Отдельные физические копии
архивов считаются отдельно. Отсутствие optional-класса подтверждается текущим
inventory; ошибка команды не равна отсутствию класса. Проверка не читает
содержимое встреч/событий/архивов и не экспортирует имена пользовательских файлов.

`filesystem_total_bytes`, available bytes, точное отношение available/total
и идентичность ресурса составляют отдельную группу. Они никогда не входят
в расходную сумму. Для общего filesystem измеряется один запас; для разных —
каждый отдельно. Сравнения выполняются по байтам без округления `df`:
`100 × available < 20 × total` и `< 10 × total`. Ровно 20%/10% не пересекает
соответствующий нижний порог; другие причины по-прежнему могут требовать защиты.

#### Полнота входа и один защитный переход T116

- Guard работает раз в 60 секунд. Текущая выборка расхода/идентичности/запаса
  должна быть полной, с известным окончанием и возрастом `0 ≤ age <120 секунд`.
  Отсутствие, ошибка, будущее, возраст ≥120 секунд или неполный inventory дают
  `capacity_input_unverified`, внешнюю тревогу и закрытую готовность. Проверка
  текущего объёма не заменяет два замера роста с интервалом ≥24 часа в T097;
  промежуточные наблюдения не должны затирать исходную суточную выборку.
- Запись принятия бюджета содержит его версию/сумму, охват inventory,
  `infra_operator`, время принятия, срок пересмотра, основание T097 и ссылку
  на проверенную конфигурацию. Pending, missing, invalid, future или expired
  не дают готовности. Заданный начальный потолок 128 GiB не является такой
  записью. Сбор полных суточных замеров T097 разрешён при pending budget и
  закрытой готовности; полнота замера и принятие бюджета — отдельные статусы.
  Равенство `analytics_storage_bytes >= analytics_budget_bytes`
  запускает защиту; дата пересмотра 21.11.2026 и критерии роста не продлеваются.
- Оценка по средней величине события не является измеренным ростом. Падение
  общего расхода после ротации не обнуляется молча: живые классы
  и архивы имеют раздельные ряды. Без двух сопоставимых полных замеров нет
  PASS роста/90-дневного прогноза. Историю не удаляют ради числа или PASS.
- В состоянии сохраняются время/полнота выборки, версия inventory/бюджета,
  безопасная идентичность ресурса, расход/запас, все причины,
  требуемое действие и результат применения. Пути, IP, данные аккаунтов и
  записи встреч туда не попадают. State и его consumers обновляются вместе.
- `observed`, `protection_requested`, `blocked_dry_run`, `not_enabled`,
  `apply_failed` и `protected` различаются. `AUTO_ROLLBACK=0` и dry-run не
  подтверждают остановку записей. Неизвестный расход не отменяет достоверный
  низкий запас: известная причина защиты обрабатывается, готовность закрыта.
- Существующий guard сохраняет устойчивое закрытое состояние инцидента до
  изменения switches. Все одновременные причины приводят к одному применению.
  Только подтверждённая установка и чтение действующей конфигурации записывают
  `protected`; ошибка оставляет `apply_failed` и допускает повтор применения.
  После успешного перехода обычные повторы/перезапуск guard не вызывают новое
  переключение или перезапуск API. Ошибка записи state запрещает заявление
  об успехе. Параллельные запуски сериализуются существующей блокировкой.
- Область остановки — новая необязательная аналитика: доставка провайдерам,
  рекламная/offline отправка, replay/autocapture и отдельный IP writer, если
  он когда-либо будет разрешён. Provider-флаги сами по себе не доказывают
  остановку IP writer: он обязан учитывать защитное состояние до INSERT.
  Неидентифицирующий агрегат уровня 1 сохраняет отдельный контракт и не
  объявляется остановленным этим действием. Продукт, история и исполнение
  отдельных обязательных удалений не отключаются.
- Исчезновение тревоги не снимает закрытое состояние. Ручное восстановление
  проходит существующий раздел Restoration в
  `docs/analytics/product-analytics-provider-rollback.md`: полный свежий замер,
  действующий принятый бюджет/прогноз/срок расширения, проверка конфигурации,
  согласий/оснований, provider smoke и page validation, когда применима.
  Оператор фиксирует безопасное подтверждение для текущего инцидента и версии
  конфигурации; только после подтверждённого чтения применённой конфигурации
  закрывает инцидент. Обычный timer этот путь не вызывает, подстановка флага
  или старого receipt не заменяет одобрения и не разрешает IP writer.

| Сигнал при остальных здоровых проверках | Причины и действие |
| --- | --- |
| Только host CPU/память, достаточный запас/бюджет | Host-тревога; защита не запрашивается. |
| Общий filesystem 19,9% | Защита запаса; одно отключение необязательной аналитики. |
| Общий filesystem 9,9% | Та же защита + критическая host-тревога; один успешный переход. |
| Разные filesystem, низкий запас только у продукта | Host-тревога; нельзя приписывать низкий запас filesystem аналитики. |
| Бюджет и низкий запас одновременно | Все причины сохранены; один успешный переход. |
| Неизвестный вход/непринятый бюджет | Нет готовности; отдельная тревога; известная причина защиты не теряется. |
| Причины исчезли после защиты | Готовность закрыта до принятого ручного восстановления. |

Это целевой контракт; текущие runtime-поля и настройки ещё требуют сверки,
а T097 не принят. Число бюджета и реальный размер не выдумываются из порогов.

**Почему так**: сегодня пороги общехостовые, а в продуктиве включён
автоматический откат. Всплеск трафика на сайт может сам выключить измерение, не
сняв нагрузку. Это ровно та ситуация, ради которой фича и делается.

**Проверка**: SC-009 — учебная тревога, внешнее оповещение приходит не позднее
15 минут. SC-012 — пятикратный всплеск при принятой ёмкости и достаточном запасе
не отключает измерение и не влияет на доступность продукта.

## Нагрузка сайта

Это входной HTTP-профиль SC-012, не число людей, параллельных запросов,
событий PostHog, загрузок аудио или нагрузка CPU. Предварительно принимаются
ресурсный запас, абсолютный бюджет и срок расширения по T097; испытание
проводится на изолированном стенде после применимых гейтов, не на production.

- Набор адресов и доли: GET `/` — 40%, `/guides` — 20%, `/transcription` — 15%,
  `/meeting-minutes` — 15%, `/guides/rasshifrovka-zapisi-zoom` — 10%.
  Используются конечные canonical URL без query и автоматических повторов.
  Статика, health, robots, регистрация/вход, оплата и запись/обработка аудио
  исключены. Это проверка публичного сайта, а не всей нагрузки продукта.
- Baseline — 10 080 полных последовательных минут семи UTC-суток до дня
  проверки по тому же набору адресов. В каждой минуте считается число
  внешних HTML GET-запросов / 60. Известные боты, оператор, поддержка и
  автоматические проверки исключены принятым классификатором. Нет достоверной
  классификации/полного покрытия — baseline неизвестен; пропуск не заменяют
  нулём. Истинные наблюдаемые нули входят. R берётся по SC-012; источник,
  границы периода, N, R и пропуски указываются без IP/идентификаторов.
- Фазы: 5 минут разогрева при R → 20 минут при 5×R → 15 минут при R для
  восстановления. Частота задаёт открытый поток поступления запросов, а не
  ограниченное число постоянно занятых клиентов. Неотправленные плановые
  запросы учитываются как недостигнутая нагрузка; их нельзя скрыть снижением R.
  При R=0 либо неизвестном baseline допускается отдельная инженерная проба
  1 → 5 → 1 запрос/с с теми же фазами. Она маркируется как проба с нижним
  инженерным пределом и не закрывает SC-012 относительно измеренного p95.
- Для каждого запроса фиксируются длительность, итог/ошибка и достигнутая
  частота; итог — по минутам и каждой фазе. Раз в 15 секунд наблюдаются
  состояние продукта, аналитики, очередь, отставание и свободное место;
  на границах фаз — абсолютный объём классов. Только безопасные метаданные.
- PASS требует достигнутых входных 5×R полные 20 минут, HTTP 200 без 5xx,
  таймаутов/ошибок соединения и успешных проверок доступности продукта на
  всех пробах; нет защитного отключения измерения. Очередь после 15 минут
  восстановления не выше измеренного максимума разогрева, отставание не
  пересекает принятый порог guard. p50/p95/p99 времени ответа и фактические
  частоты публикуются по фазам; отсутствие задержек не выдумывается из HTTP 200.
- Любая потеря доступности, срабатывание защиты диска/аналитики или
  недостигнутая частота делает прогон FAIL, неизвестные обязательные метрики —
  INCOMPLETE. При защитной тревоге генератор останавливается, история не
  удаляется, продукт не откатывается автоматически. Принудительно выключать
  guard ради PASS нельзя. Весь поток теста исключён из клиентского отчёта.

Один такой прогон не подтверждает месяцы роста или доступность всего продукта.
T097 остаётся открытой до фактических измерений и приёмки; эти определения
не являются результатами испытания или новым одобрением владельца.

## Резервное копирование

| Правило | Значение |
| --- | --- |
| Расписание | Автоматическое |
| Целевое хранилище | `2brain.dev`, локальный `/var/backups/graf-posthog`; root 0700, архивы 0600 |
| Выгрузка за пределы сервера | В текущем этапе не требуется; принято владельцем 22.10.2026 |
| История точек восстановления | Последние 7 успешных полных наборов, минимум 2 перед готовностью; неполные не считаются и не вытесняют хорошие |
| Проверка восстановления | По расписанию, результат фиксируется |
| Блокировка готовности | Последний запуск неуспешен; нет полного проверенного набора/минимума; возраст неизвестен, отрицателен или ≥26 часов; часы проверены |

**Границы защиты**: решение владельца «сделай без него» отменяет обязательную
внешнюю копию. Потеря сервера/диска может уничтожить всю историю. Семь архивов
не ограничивают жизнь событий; каждый содержит всю сохраняемую историю.
Ротация допустима только после проверки нового полного набора и сохранения
минимума пригодных копий. Успешная распаковка не заменяет согласованное чтение
восстановленного PostHog. Восстановление из более старой точки означает пробел
после неё; потеря всех копий не обещает возврата истории. Для T113 исходный
T0 сохраняется; потеря его защищённого anchor запрещает новый старт.

**Проверка**: SC-010 — проверка восстановления выполнена не позднее 30 дней

## Хранение и удаление

| Категория | Целевой режим | Где применяется | Контроль |
| --- | --- | --- | --- |
| События уровней 2 и 3 | `until_decision` | ClickHouse | Нет удаления по возрасту; отдельное удаление |
| Обезличенный агрегат | `until_decision` | PostgreSQL | Нет возрастной очистки |
| История атрибуции визита | `until_decision` | PostgreSQL | Окно применения источника 90 дней отдельно |
| Атрибут привлечения клиента | `until_decision` | PostgreSQL | Нет возрастной очистки |
| `activation_milestone_decisions` | `until_decision` | GRAF PostgreSQL, `product_activation_milestones` | Уникальное принятие и два delivery states; отдельное удаление, свежая проверка restore до writer |
| IP / сетевые метаданные | `until_decision` | `rec-postgres/twobrain_rec/public.network_access_metadata`, storage=`graf_postgres` | INSERT-only приложение, операторский аудит до read/delete; writer закрыт до подтверждения основания/раскрытия/прав/копий по FR-061 |

Сессии, авторизационные данные и разрешения не получают бессрочную действительность.
Запись поведения не включается автоматически. Режим хранения не расширяет
перечень разрешённых полей и внешних получателей.

**Правила**: явный режим обязателен; отсутствующий/неизвестный режим — ошибка.
При отдельном удалении `client_acquisition_attribute` удаляется вся его строка,
включая связь с визитом; identity аккаунта сохраняется. Account finalizer и
повтор после restore используют один точный account helper и отдельный
purge-result. Учебный повтор охватывает все четыре локальные категории;
отзыв уровня требует case каждой его категории. Это не доказательство
исполнения provider-удаления или полной рабочей готовности.

`until_decision` — осознанный режим без автоматического удаления по возрасту.
Удаление по отдельному решению/обязательному требованию наблюдаемо: основание,
охват, ответственный, крайний срок и результат. Срок исполнения задаётся отдельно
от хранения; без него случай удаления не закрывается.
Формулировки об удалении остаются в пределах контролируемого хранилища
(принцип IV конституции).

**Проверка**: SC-011 — пересечение старых пределов не удаляет учебные данные,
90-дневное окно источника соблюдается, отдельное удаление подтверждено.
Оператор сверяет установленный TTL и задачи очистки перед изменением; сначала
проверяет на изолированном наборе. Конфигурация, восстановление из старой копии
и переполнение не должны возвращать старую возрастную очистку.
Нехватка места — оповещение и остановка новых необязательных записей по FR-032,
а не разрешение удалить историю. Рабочая настройка пока не подтверждена.
Проверка режима выполняется ежедневно в 03:15 UTC. Readiness принимает
`recorded_at_epoch` только при 0 ≤ age <26 часов; отсутствующее/неправильное
время, будущее и age ≥26 блокируют готовность. После восстановления прежняя
запись проверки удаляется из действующего состояния до повторного запуска
проверки; чтение старого receipt не принимает восстановленный TTL.

## T118 — согласованный локальный комплект и проверка чтения

Инженерное решение 22.10.2026, ещё не реализовано и не применено.
Выбран холодный комплект только PostHog на существующем узле. Онлайн-tar
работающих томов не признаётся согласованной точкой. GRAF не останавливается.

### Создание точки

1. Штатный writer и restore используют один существующий backup lock;
   ротация не удаляет выбранный restore-комплект во время проверки.
2. До действий проверяются запас места, полный runtime inventory (включая
   анонимные mounts), закреплённые локальные образы и закрытая конфигурация.
   Неучтённый ресурс/образ/bind или недостаточный запас закрывает запуск.
3. Фиксируются состав проекта, ранее работающие контейнеры, полный generated
   Compose через `docker compose config --format json`, image digests,
   необходимые конфигурационные bind/secret files и отображение mounts.
   Содержимое сохраняется только внутри root-only комплекта0700/0600;
   в Git/вывод допускаются лишь версия, хеши, числа и коды. Репозиторный
   сокращённый Compose источником полного runtime не является.
4. Перед остановкой записывается root-owned окно обслуживания только PostHog
   `purpose=cold_backup`, deadline не дальше10минут, fingerprint runtime.
   Guard продолжает проверять ёмкость и общую доступность продукта. Только
   ожидаемая недоступность перечисленных PostHog services внутри этого окна
   не становится аварией; неизвестное/просроченное окно ничего не подавляет.
   Окно не меняет provider switches, одобрения или постоянное защитное состояние.
5. Сначала останавливаются все производители и обработчики PostHog, затем
   на ещё работающих хранилищах снимается закрытый контроль чтения ниже.
   После этого штатно завершаются остальные ранее работающие контейнеры
   проекта. Состав/mounts перепроверяются; иной писатель в выбранный том,
   незавершённая остановка или drift закрывают копию. На всём протяжении
   tar ни один контейнер не должен писать в включённые volumes/binds.
6. Копируются все классы данных и конфигурация; после проверки целостности
   публикуется marker `consistency=cold_project_v1` с fingerprints, временем
   начала/окончания остановленной точки и контрольного чтения. Неполный набор
   или набор без этого marker не получает новую приёмку восстановления.
7. При успехе, ошибке или timeout предпринимается возобновление только
   ранее работавших контейнеров; ранее остановленные не запускаются.
   Проверяются их состав/health и GRAF. Окно закрывается только после этого;
   при превышении10минут/ошибке возобновления — неуспех и оповещение.
   Защита, включившаяся по другой причине, не снимается. Provider switches
   автоматически не включаются; существующий ручной restore-gate сохраняется.

### Изолированное восстановление

Каждая попытка получает уникальный префикс ресурсов, отдельный внутренний
Docker network без выхода наружу, только новые volumes и конфигурационные
копии внутри временного каталога0700. Все образы — по сохранённым digests,
без pull/build. Нет публичных ports, host network/PID/IPC, privileged/cap-add,
Docker socket/device mounts, внешних networks/volumes/binds, чужих container
names и средств подключения к рабочим службам. Read-only source архивов —
единственное обращение к исходному набору; рабочие volumes никогда не монтируются.
Конфигурация клона проверяется до `up`; неподдержанный параметр блокирует
попытку, а не исчезает молча. Используются сохранённые необходимые bind files
и закрытые значения; они не читаются из изменившегося рабочего runtime.

Сначала стартуют только восстановленные хранилища. После контрольного чтения
стартует соответствующий полный generated PostHog и проверяется чтение через
его приложение. Внешние SMTP/webhooks/провайдеры недостижимы из сети клона;
приложение и consumers не получают обхода этой изоляции. Health200 отдельно
не считается подтверждением данных. Время попытки ограничено30минутами.
Общий finally/trap после успеха, ошибки, SIGTERM и timeout удаляет только
ресурсы с собственным уникальным attempt label и временные файлы. Исходные
архивы и рабочий проект не удаляются. Неуспешная очистка — failed receipt
с оповещением; оставшиеся ресурсы перечисляются лишь безопасными счётчиками.

### Конечный контроль чтения

Контроль до холодной точки и после распаковки выполняется теми же закреплёнными
нативными клиентами; содержимое/имена/ключи остаются в памяти процесса или
root-only контрольном файле комплекта. Коммитится только итог по классам.
До старта обработчиков в клоне сверяются:

- PostgreSQL: все прикладные БД, схема и число строк каждой обычной таблицы;
  непустая база проекта обязательна, отсутствующая таблица/БД закрывает успех.
- ClickHouse: схемы и число строк всех локальных прикладных таблиц данных;
  distributed/views не заменяют базовые таблицы. Нулевой events допустим
  только при нуле в исходной контрольной точке, факт отсутствия событий отмечается.
- Объектные хранилища: через нативный API полный список объектов, размеры и
  потоковые SHA-256 содержимого; совпадение по каждому объекту без вывода ключей.
- Kafka/Redpanda: успешное восстановление брокера, topic/partition и сохранённые
  границы offsets; coordination storage загружается соответствующим сервисом.
- Redis: нативная загрузка сохранённого состояния без ошибок; сохранённые
  записи учтены как loaded+expired. Истёкшие ключи не считаются потерей,
  неизвестный/неподдержанный формат проверки закрывает успех.
- Elasticsearch и другие присутствующие хранилища: нативная загрузка, схемы
  индексов и counts. Неизвестный класс не пропускается автоматически.

После этого PostHog тем же образом и конфигурацией должен прочитать через
собственный ORM проекты/teams/dashboards и выполнить собственный запрос к
событиям. Результат сверяется с контрольными числами; чтение сырых событий
в доказательства не входит. Consumers стартуют только после начальной сверки;
их восстановление очередей может менять данные клона. Все ранее работавшие
services полного проекта должны восстановить ожидаемое состояние; заранее
остановленные init services не объявляются обязательными работающими.

Новые restore-state/evidence имеют версию2, `consistency=cold_project_v1`,
привязку к полному manifest/runtime digest и результаты каждого присутствующего
класса, собственного чтения PostHog и очистки. Отсутствующий/старый/v1 receipt,
несовместимый образ/конфигурация, отсутствие класса/контрольного файла, частичный
успех или cleanup failure закрывают readiness. После восстановления заново
проверяется `until_decision` и исполнение отдельных удалений; старый receipt
режима хранения не открывает измерение. При потере всех локальных копий
возвращается `history_unrecoverable`, а не успешная пустая новая установка.

Это план технической реализации, а не разрешение остановить рабочий PostHog
вне согласованного выпуска и не доказательство работающего восстановления.

### Формат краткого результата T118 v2

Краткое root-owned состояние допускает готовность только при всех полях:
`restore_state_version=2`, `consistency=cold_project_v1`, `last_verify_result=pass`,
`native_read=pass`, `posthog_read=pass`, `cleanup=pass`,
`retention_recheck=pass`, `deletion_recheck=pass`. `manifest_sha256` и
`runtime_sha256` — 64 строчные шестнадцатеричные цифры проверенных артефактов.
`storage_classes` и `verified_classes` — одинаковые непустые списки без
повторов из `postgres,clickhouse,objects,broker,coordination,redis,elasticsearch,proxy`;
`postgres` и `clickhouse` обязательны. Полный закрытый отчёт хранит нативный
результат каждой перечисленной категории, контроль до/после и привязки;
краткий файл его не заменяет. Writer публикует pass только после очистки.
Время — окончание проверки, строго 0≤age<30 суток; настройка не расширяет
предел. Будущее/неизвестное время, v1 и любое отсутствующее подтверждение
дают отказ и оповещение. На время миграции старый tar-only writer не создаёт
v2 доказательство; это ожидаемая блокировка, пока полный T118 не принят.


### Поправки PR #7727 — доступ и незавершённые копии, 23.10.2026

Продолжение T116/T117, без принятия T097/T118/T119 или установки на рабочем
узле. В текущем Compose уже есть read-only retention bind; права2750/0640
сохраняются. Перед включением трёх timers выбранный для API
`TWOBRAIN_RUNTIME_SECRET_GID` должен быть явно сохранён в существующих
`/etc/graf-posthog-{runtime-guard,backup,retention}.env`. Нельзя считать
переменную shell перед `systemctl start` окружением службы или подменять
нестандартный выбранный GID значением1001. Шаг установки требует числовой
принятый GID, сохраняет остальные поля root-owned0600 env-файлов и выполняется
до запуска служб; изменение выбранной группы требует повторить этот шаг.

Неуспех архивирования удаляет только собственный скрытый staging текущей
попытки, созданный после получения backup lock. Существовавший до попытки
incomplete/final, завершённые и повреждённые исторические наборы сохраняются.
После переименования staging в final путь final не удаляется обработчиком
отказа. Ошибка очистки не скрывается и не превращает отказ в успех.

При `GRAF_POSTHOG_PROJECT`, отличном от graf-posthog, префикс шаблонов
inventory преобразуется одинаково при discovery и verified_sets, как уже
делает posthog-storage.py. Сырые байты inventory в наборе и его SHA-256 не
переписываются. Тома другого старого проекта не могут дать полный набор
новому проекту. Нераспознанные labelled/mounted тома остаются отказом.

Приёмка: штатный установочный блок на временных файлах с нестандартным GID,
сохранность других параметров и отказ отсутствующего/неверного GID; backup
на новом проекте с сохранением сырого inventory, отказ только старых томов;
поздний отказ архива после записи, очистка своего staging и сохранность
чужих incomplete/final/history. Реальные службы/данные/отправки не затрагиваются.


## Lifecycle первой вехи T113 — 27.10.2026

`activation_milestone_decisions` — отдельная категория `graf_postgres`.
Она входит в отдельный полный GRAF DB комплект существующего контура T110
(не в cold PostHog комплект T118), реестр disposition и ежедневный контроль режима T109, а размер heap/index/TOAST — в непересекающийся inventory
T116. Режим until_decision без TTL; предел payload и число строк на аккаунт
не заменяют измерение роста/запаса. Переполнение останавливает новые
необязательные записи, не удаляет историю и не ломает продукт.

До рабочего включения T113: доказаны права аккаунта/maintenance, отсутствие
публичного чтения, отдельное удаление точного case с owner/deadline/result,
полное согласованное восстановление ledger+provider state и повторное
применение принятых удалений. Старая копия не возобновляет очередь: полный
карантин намерений и проверка пропуска после копии — по activation-milestones.
Старые runtime/retention/restore receipts недействительны после изменения
схемы или восстановления. Действующая readiness должна охватывать новую
relation/category и всю очередь; partial inventory не даёт PASS.

T110 переиспользует `infra/scripts/backup-rec-stack.sh` (полный custom-format
pg_dump) и `infra/scripts/rehearse-rec-restore.sh` (отдельная временная БД).
Существующее `count(*) >= 0` не доказывает ledger restore. В рамках T113
расширяется узкая проверка восстановленной relation: наличие схемы/unique/FK,
равенство безопасных количеств и состояний на согласованной точке копии,
карантин неподтверждённых намерений, отказ admission для непокрытого интервала,
повтор удаления точных account/category cases и проверка отсутствия остатков.
Receipt связывает backup checksum, schema/source/runtime fingerprint, точку
копии и сверки, результат удаления/карантина, время и результат очистки временной
БД. Без такого receipt общий backup_result=pass не разрешает writer. Копии
остаются в закрытом локальном контуре T110 с 0700/0600; на Mac не копируются.

В операционных отчётах только безопасные количества по состояниям и кодам,
период/версия/свежесть и неизвестная доля; account/event payload, URL встреч,
IP, секреты и тело provider ответа не копируются в Git или публичные отчёты.

### Закрытые файлы комплекта GRAF

Первый срез T110/T113: `backup-rec-stack.sh` создаёт новый выделенный каталог
0700; новые файлы имеют 0600, подкаталоги 0700. Маска 077 применяется также
в контейнерных `pg_dump` и `mc mirror`. Уже существующая цель (каталог,
файл или ссылка) отклоняется без изменения прежней копии. Уникальный закрытый
staging контейнера исключает общий dump между запусками и убирается при
успехе и отказе. Ошибка dump/copy/mirror/cleanup не даёт `backup_result=pass`;
неполная резервная копия остаётся закрытой для разбора. Другие временные
файлы и копии не затрагиваются.

Исправление прав прежних копий ограничено проверенным корнем: каталоги 0700,
обычные файлы 0600, без чтения содержимого, смены владельцев, следования ссылкам,
удаления или переноса. Необычный объект/ошибка доступа оставляют приёмку
открытой. Сводка содержит только количества и режимы. Это не доказывает
согласованность dump/объектов, восстановление ledger, пропуск после копии
или готовность локального writer.


### Приёмка первого локального периода T113

Локальная readiness определяется договором
[первого периода](activation-milestones.md#первый-локальный-период-t113--28102026).
Её нельзя получить общей PostHog готовностью или заменой render_only.
Решение владельца 30.10.2026: одна фиксированная T0, только новые аккаунты с
trusted created_at > T0 и новая запись после T0. Initial receipt создаётся
однократно по времени authoritative БД под общим product drain с полным
снимком и проверкой отсутствия уже подходящих аккаунтов. Обновление/restore
сохраняет started_at; потеря/неоднозначность закрывает допуск без нового T0.
Проверка маркетинговой истории до T0 не требуется для этой группы; неизвестные
удаления/основания/restore, затрагивающие текущее состояние, остаются блокерами.
Доказательства хранят только безопасные метаданные и digest, без списка клиентов.
Переиспользуются полный backup-rec-stack и rehearse-rec-restore; новый сервис,
хранилище решений или внешний узел не вводятся. Закрытые копии сохраняют
0700/0600; действующая последняя копия <26 часов, restore ≤30 дней.

Restore проверяет полную GRAF DB: schema/roles/RLS/unique/FK, безопасные точные
количества и состояния из согласованной точки, карантин неподтверждённой
доставки, повтор точных удалений и отсутствие остатков. Для пустого рабочего
ledger нужны отдельные непустые учебные случаи. При закрытом writer исходные
метаданные и dump связываются одной проверенной точкой; при открытом writer
требуется один согласованный snapshot. Частичные inventory/count>=0 не подходят.
Временная БД не получает provider secrets или возможность отправки; очистка БД,
объектов и staging проверяется до PASS. Рабочие копии на Mac не переносятся.

Поддерживаемый actual restore в rollback-runbook и schema/runtime rollback
CD обязаны filesystem EX → durable revoke → exclusive PostgreSQL advisory
lock (273, 3) в прежней DB до изменения данных. Все admission держат SH
xact-lock того же ключа до окончания COMMIT/ROLLBACK; timeout DB drain
запрещает restore даже после смерти клиента и освобождения flock. Дополнительно
поддерживаемая actual-restore процедура закрывает product ingress, останавливает
все пишущие службы и полной DB maintenance-ролью подтверждает drain всех
остальных writers/transactions, включая category purge и account_closure.
Late DELETE/identity COMMIT после смерти клиента не обходится admission-only
lock. Неизвестный охват/новые writers запрещают restore; службы остаются
остановленными до restore/reconciliation. Такой product drain пока не принят
в существующем CD и должен получить реализацию и проверку. Обычный analytics
HOLD не препятствует обязательным удалениям. Существующий helper, который
возвращает только решение, этой проверки не заменяет. Ошибка/потеря readiness
оставляет admission закрытым. При непокрытом gap локальный отчёт показывает
неизвестный интервал; повторное принятие утраченных решений запрещено.
Первое открытие, ежедневный контроль копии/ресурсов и восстановление — разные
проверки. Полные T110/T113/T118/T119 и платный запуск остаются отдельными.


### Ресурсная область local_only — T113/T116, 30.10.2026

Существующие collector/capacity/guard имеют ровно две области измерения:
`posthog` (по умолчанию) и `graf-local`. Collector/capacity получают `--scope`,
guard — `GRAF_ANALYTICS_GUARD_SCOPE`. Неверная область отвергается до проб и
изменений. API выбирает ожидаемую область из принятого режима Settings:
локальный оператор явно требует `graf-local`, provider readiness — `posthog`;
переменная guard не выбирает область разрешения API.

Обе области требуют полный успешный `docker ps -aq --no-trunc`, точные уникальные
64hex Id и полное равенство ответа inspect, правильные project/service labels,
оба volume lists и точный Name каждого volume inspect. Ошибка не означает
отсутствие. Оставшиеся mounts/labelled/prefix/detached volumes всегда входят
в inventory. Только graf-local допускает доказанное отсутствие обязательных
классов PostHog. GRAF relations обязательны; строки продукта не читаются.
Отсутствующий каталог выделенных аналитических архивов допустим local только
по ENOENT при существующем безопасном родителе; links/ошибки доступа запрещают
полноту. Выделенные архивы/staging/failed/incomplete считаются целиком.

Полные смешанные копии GRAF не прибавляются целиком к analytics sum: их доля
аналитики неизвестна, точный90дневный прогноз этой доли не заявляется. Их
настоящий filesystem защищается тем же резервом аналитики. Для этого среза
поддерживается только parent `/opt/projects/2brain-rec/backups`, независимо от
GRAF_APP_DIR. TWOBRAIN_BACKUP_DIR допускает лишь canonical прямой дочерний
destination на том же FS без links; unknown/другой путь — HOLD. Guard не создаёт
missing parent. Actual runtime overrides проверяет local operator. Host staging
только в этом parent; PostgreSQL staging — только на уже привязанном продуктовом
volume `/var/lib/postgresql/data`. tmpfs/overlay не поддерживаются этим путём. Неизвестные installed jobs/cron/shell
paths и staging остаются HOLD полного оператора. До stop верхний оператор
отдельно принимает место для двух новых полных копий, restore target и staging;
минутный резерв эту оценку не заменяет.

В graf-local FS anchors — actual roots, GRAF app и fixed backup parent;
отсутствующий PostHog analytics path не требуется. Provider-specific probes,
lag/queue/OOM/restarts/container caps пропускаются с `not_applicable`, без
выдуманного0/PASS. Product ready/host sensors/capacity/budget/reserve/latch
остаются. После24ч local не вызывает ClickHouse event count: count и per1000
неизвестны; метаданные роста классов сохраняются.

Sample и alert имеют version3 с обязательным measurement_scope; старый формат
не принимается. Scope входит в inventory digest, старый anchor несопоставим.
Budget schema version1 прежняя, но требует новый scope-bound inventory/config;
128GiB и пересмотр21.11.2026UTC не меняются. Известный свежий низкий запас
сохраняется даже при несовпадении scope или неполноте размеров.

Protection state version2 и manual restore receipt version2 имеют ту же область,
что исходный incident, sample и явный scope helper. Version1/missing/другая
область дают HOLD без перезаписи или автоматической миграции. Новый observed
создаётся только при доказанном отсутствии файла. Receipt сохраняет прежние
incident/time/growth/expansion/runtime/basis/readback proofs; posthog требует
provider_smoke/page_validation, graf-local — local_measurement_review.
Смена scope не заменяет provider proofs. Timer не восстанавливает запись.
Рабочий переход старого состояния требует отдельного trusted решения с
сохранением истории; этот срез его не исполняет. Общие HOLD полного оператора,
ready/T0 и отдельные удаления остаются.


### Временные файлы на защищённом диске T113 — 31.10.2026

Четыре создателя временного PG-комплекта (Python coherent backup/rehearsal и
shell backup/rehearse) используют только
`/var/lib/postgresql/data/twobrain-rec-backup.<alnum>`. Общий SQL-validator
отклоняет старый `/tmp`, произвольный и неканонический путь до запуска dump
и вывода inventory. Fallback отсутствует; логические dump/restore не копируют
PGDATA целиком. Очистка касается только уникального каталога данной попытки,
не PGDATA/base/global/pg_wal и не соседних каталогов.

Host metadata Python rehearsal создаются через удержанный FD уже существующего
canonical MIXED_BACKUP_PARENT, без ссылок,0700, с владельцем оператора (root в
рабочем входе). Reference — прямой canonical child. При коллизии чужой каталог
и исходный комплект сохраняются; подмена parent или собственной цели закрывает
успех. Удаление своей цели выполняется относительно удержанного FD parent.

До и после runtime DB read удерживаются host volume Source, backup parent и
PGDATA через единственный допустимый proc-root hop проверенного PG процесса.
PGDATA отсутствует в env либо строго `/var/lib/postgresql/data`; единственный
writable local volume mount не имеет submount. Реальный `SHOW data_directory`
проверяется до/после DB context. Source/proc PGDATA совпадают по dev/ino/uid/gid/mode,
UID/GID70,0700/0750,без ACL; parent root0700 на том же st_dev. Linux64 amd64/arm64
`fstatfs` удержанных FD допускает только ext/XFS/Btrfs. Ошибка syscall,
неизвестный ABI/magic,tmpfs/overlay дают HOLD. Обычные изменения времён,
размера и числа ссылок каталога не считаются подменой.

Это привязка ресурса, не принятие ёмкости двух копий/restore/staging. Shell host
TMPDIR ещё не получает полный local_only допуск. Старый `_runtime_policy` digest
полных метаданных volume root может измениться от own mkdir/cleanup: верхний
оператор не должен считать его неизменным после таких действий.
`full_preflight_not_implemented` и `activation_recovery_unverified` сохраняются;
рабочие T0,writer,выпуск и полная приёмка T113 остаются впереди.

### Весь PG-кластер локального периода — J2, 31.10.2026

`local_retention_database_catalog` одной GRAF DB не даёт полного доказательства
отсутствия планировщиков. Применяется конечный
[алгоритм J2](../validation/t113-cluster-inventory-20261031.md#конкретный-проект-j2-для-следующей-реализации)
для шести поддержанных DB PG17. Cluster/preload/role overrides, физическая
привязка каждой доступной DB, точные native extension/Temporal definitions,
closed template0 и background/prepared state проверяются фактически до/после.
Read-only probe не открывает закрытые базы. Неизвестное/лишнее/недоступное —
HOLD. Owned rehearsal targets ограничены доказанными UUID/OID текущего run
и исчезают после его cleanup. Отдельно допускаются сохранённые закрытые prior
DB только по trusted fsynced actual-run switch/complete state, точным
cluster/OID/binding, false/limit0/0PID/0prepared и полному lifecycle coverage.
Prefix не разрешает ни одну дополнительную DB. Prior сохраняются для отката,
не удаляются учебным cleanup; неизвестный switch/охват закрывает допуск.
Закрытая GRAF source использует уже удержанное reduced соединение.
Каталожный digest не выводится
из CLI pass-file или self-hash непрочитанной установки. J1 и весь верхний
цикл остаются отдельными воротами; проект J2 требует независимого review.
