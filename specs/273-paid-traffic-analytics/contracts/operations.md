# Контракт: эксплуатация измерения

Покрывает FR-030 … FR-039 и SC-009 … SC-012. Инфраструктурная часть фичи.

## Оповещение о деградации

| Правило | Значение |
| --- | --- |
| Канал | Telegram; локальная деградация — отправитель `2brain.dev`, потеря доступности узла — независимый наблюдатель `astraglobal` напрямую в Telegram |
| Срок доставки | Не более 15 минут от начала деградации |
| Область `analytics` | Доступность узла, отставание доставки, рост очереди, абсолютный объём аналитики и защита запаса её файловой системы |
| Область `host` | Процессор, память, диск сервера |
| Порядок срабатывания | Аналитические правила раньше общехостовых |
| Поведение при деградации | Первой отключается аналитика; продукт продолжает работать |
| Общехостовые правила | Сами не отключают измерение; защита общего диска описана ниже |

### Независимый наблюдатель

Нормативное решение — `research.md` §5: существующий `astraglobal`, systemd timer
раз в 60 секунд, публичный GET `/api/v1/health/live`, timeout 10 секунд,
два последовательных неуспеха → `target_unreachable`, прямой Telegram-путь
без запроса/запуска кода на `2brain.dev`. Проверяются TLS, HTTP и JSON;
ошибка и неизвестный исход не становятся PASS. От первого непрерывного отказа
до принятой доставки ≤15 минут; timeout/ошибка отправки сохраняют недоставленное
состояние, повтор допустим без выдуманного receipt. Только безопасные метаданные;
секреты root 0600 вне Git, без доступа к БД/SSH GRAF. При полном отказе продукта
его доступность не обещается. T119 обязана проверить выключенный целевой стенд,
недоступность канала, неполный/неверный ответ, повторы и восстановление.

### Один физический диск продукта и аналитики

- `analytics_storage_bytes` — сумма занятых байтов непересекающихся классов
  аналитики из capacity baseline, включая локальные архивы; без двойного счёта
  тома/ссылок. `analytics_budget_bytes` — положительный абсолютный бюджет,
  принимаемый оператором в T097 вместе с измеренным ростом и датой расширения.
  Неизвестный объём или непринятый бюджет не означают ноль или готовность.
- `filesystem_free_bytes` и `filesystem_free_percent` — доступный запас одного
  файлового ресурса. Совпадение filesystem продукта и аналитики фиксируется по
  идентичности ресурса, а не по разным путям. При общем ресурсе это один замер,
  даже если прежние поля называются `analytics_disk_free_percent` и
  `disk_free_percent`. Он не доказывает, кто занял место.
- Достижение бюджета аналитики либо запас файловой системы аналитики `<20%`
  вызывает защитное отключение новых необязательных записей/доставки аналитики
  и внешнюю тревогу. `<10%` дополнительно вызывает критическую тревогу общего
  диска. При одновременном срабатывании сохраняются оба факта, отключение
  выполняется один раз; причина — защита общего запаса, виновник неизвестен,
  пока отдельно не проверены объём и рост классов. Историю не удаляют.
- Тревога CPU/памяти/общего диска сама не запускает второе отключение/откат
  продукта. Если файловые системы разные, порог общего диска не переносится
  на аналитику; бюджет и запас аналитики проверяются отдельно. Ошибка определения
  ресурса/замера блокирует заявление о готовности и требует оповещения.
- После защиты готовность остаётся закрытой до проверки запаса, бюджета,
  прогноза роста и управляемого восстановления оператором. Само исчезновение
  тревоги не включает запись заново. SC-012 проверяется при принятом запасе;
  истощение диска проверяется отдельно как срабатывание FR-032.

#### Состав расхода T116

Единый источник расчёта — существующий
`infra/scripts/measure-posthog-storage-growth.sh`; guard использует его полный
результат, а не повторяет формулу. Все присутствующие Docker volumes и bind
mounts аналитики сопоставляются с проверенным inventory
`infra/posthog/backup-volumes.txt` и фактическими mounts. Неучтённый том/bind,
неизвестное назначение или ошибка доступа дают INCOMPLETE.

| Расходный класс | Охват |
| --- | --- |
| `relational` | Весь выделенный том PostgreSQL PostHog, включая его WAL/служебные файлы; не складывать с размерами таблиц этой же БД. |
| `events` | Выделенные тома ClickHouse целиком; не прибавлять повторно `system.parts`. |
| `object_storage` | Присутствующие objectstorage, seaweedfs и posthog-media. |
| `queue_cache` | Все присутствующие варианты redis/redis7. |
| `broker` | Присутствующие kafka/redpanda. |
| `coordination` | Все присутствующие zookeeper data/datalog/logs. |
| `runtime_auxiliary` | Присутствующие caddy data/config и другие явно классифицированные служебные mounts аналитики. |
| `graf_analytics_tables` | Только аналитические relations БД GRAF, их индексы, TOAST, forks и segments: агрегаты, атрибуция, привлечение, служебные записи аналитики и сетевой журнал T110. Записи встреч и весь том GRAF DB сюда не входят. |
| `backup_artifacts` | Реально находящиеся на узле аналитические архивы, manifests и их staging/failed/incomplete файлы. Статус успешной копии не меняет занятого места. |

Для файловых классов учитываются выделенные блоки файлов (`st_blocks × 512`),
а не логическая ёмкость тома. Для `graf_analytics_tables` разрешён только
metadata-разбор каталога relations и выделенных блоков соответствующих файлов;
строки таблиц не читаются. Список relations задаётся явным inventory; новая
аналитическая таблица без классификации запрещает PASS. Отсутствующий до T110
сетевой журнал отмечается `not present in reviewed runtime`, а не выдуманным
нулевым измерением.

Общий WAL, системные каталоги и прочий совместный служебный расход БД GRAF
не входят в `analytics_storage_bytes`; их доля, вызванная аналитикой, неизвестна,
а не равна нулю. Полный физический разбор общей БД каждую минуту не требуется.
Риск расхода этих файлов и данных продукта учитывает один замер общего
filesystem и его защита `<20%`. При наличии отдельного безопасного замера
общий расход можно показать как диагностику, без прибавления к аналитическим
классам и без изменения 128 GiB. Бюджет сравнивается непосредственно с
`analytics_storage_bytes`.

Каждый объект учитывается один раз по файловой идентичности устройства/inode,
включая hardlinks. Повторные пути и bind aliases одного корня объединяются
только после подтверждения идентичности. Пересечение корней разных классов
либо непрослеживаемая ссылка даёт INCOMPLETE; вложенный mount нельзя считать
и частью родительского обхода, и отдельным томом. Отдельные физические копии
архивов считаются отдельно. Отсутствие optional-класса подтверждается текущим
inventory; ошибка команды не равна отсутствию класса. Проверка не читает
содержимое встреч/событий/архивов и не экспортирует имена пользовательских файлов.

`filesystem_total_bytes`, available bytes, точное отношение available/total
и идентичность ресурса составляют отдельную группу. Они никогда не входят
в расходную сумму. Для общего filesystem измеряется один запас; для разных —
каждый отдельно. Сравнения выполняются по байтам без округления `df`:
`100 × available < 20 × total` и `< 10 × total`. Ровно 20%/10% не пересекает
соответствующий нижний порог; другие причины по-прежнему могут требовать защиты.

#### Полнота входа и один защитный переход T116

- Guard работает раз в 60 секунд. Текущая выборка расхода/идентичности/запаса
  должна быть полной, с известным окончанием и возрастом `0 ≤ age <120 секунд`.
  Отсутствие, ошибка, будущее, возраст ≥120 секунд или неполный inventory дают
  `capacity_input_unverified`, внешнюю тревогу и закрытую готовность. Проверка
  текущего объёма не заменяет два замера роста с интервалом ≥24 часа в T097;
  промежуточные наблюдения не должны затирать исходную суточную выборку.
- Запись принятия бюджета содержит его версию/сумму, охват inventory,
  `infra_operator`, время принятия, срок пересмотра, основание T097 и ссылку
  на проверенную конфигурацию. Pending, missing, invalid, future или expired
  не дают готовности. Заданный начальный потолок 128 GiB не является такой
  записью. Сбор полных суточных замеров T097 разрешён при pending budget и
  закрытой готовности; полнота замера и принятие бюджета — отдельные статусы.
  Равенство `analytics_storage_bytes >= analytics_budget_bytes`
  запускает защиту; дата пересмотра 21.11.2026 и критерии роста не продлеваются.
- Оценка по средней величине события не является измеренным ростом. Падение
  общего расхода после ротации не обнуляется молча: живые классы
  и архивы имеют раздельные ряды. Без двух сопоставимых полных замеров нет
  PASS роста/90-дневного прогноза. Историю не удаляют ради числа или PASS.
- В состоянии сохраняются время/полнота выборки, версия inventory/бюджета,
  безопасная идентичность ресурса, расход/запас, все причины,
  требуемое действие и результат применения. Пути, IP, данные аккаунтов и
  записи встреч туда не попадают. State и его consumers обновляются вместе.
- `observed`, `protection_requested`, `blocked_dry_run`, `not_enabled`,
  `apply_failed` и `protected` различаются. `AUTO_ROLLBACK=0` и dry-run не
  подтверждают остановку записей. Неизвестный расход не отменяет достоверный
  низкий запас: известная причина защиты обрабатывается, готовность закрыта.
- Существующий guard сохраняет устойчивое закрытое состояние инцидента до
  изменения switches. Все одновременные причины приводят к одному применению.
  Только подтверждённая установка и чтение действующей конфигурации записывают
  `protected`; ошибка оставляет `apply_failed` и допускает повтор применения.
  После успешного перехода обычные повторы/перезапуск guard не вызывают новое
  переключение или перезапуск API. Ошибка записи state запрещает заявление
  об успехе. Параллельные запуски сериализуются существующей блокировкой.
- Область остановки — новая необязательная аналитика: доставка провайдерам,
  рекламная/offline отправка, replay/autocapture и отдельный IP writer, если
  он когда-либо будет разрешён. Provider-флаги сами по себе не доказывают
  остановку IP writer: он обязан учитывать защитное состояние до INSERT.
  Неидентифицирующий агрегат уровня 1 сохраняет отдельный контракт и не
  объявляется остановленным этим действием. Продукт, история и исполнение
  отдельных обязательных удалений не отключаются.
- Исчезновение тревоги не снимает закрытое состояние. Ручное восстановление
  проходит существующий раздел Restoration в
  `docs/analytics/product-analytics-provider-rollback.md`: полный свежий замер,
  действующий принятый бюджет/прогноз/срок расширения, проверка конфигурации,
  согласий/оснований, provider smoke и page validation, когда применима.
  Оператор фиксирует безопасное подтверждение для текущего инцидента и версии
  конфигурации; только после подтверждённого чтения применённой конфигурации
  закрывает инцидент. Обычный timer этот путь не вызывает, подстановка флага
  или старого receipt не заменяет одобрения и не разрешает IP writer.

| Сигнал при остальных здоровых проверках | Причины и действие |
| --- | --- |
| Только host CPU/память, достаточный запас/бюджет | Host-тревога; защита не запрашивается. |
| Общий filesystem 19,9% | Защита запаса; одно отключение необязательной аналитики. |
| Общий filesystem 9,9% | Та же защита + критическая host-тревога; один успешный переход. |
| Разные filesystem, низкий запас только у продукта | Host-тревога; нельзя приписывать низкий запас filesystem аналитики. |
| Бюджет и низкий запас одновременно | Все причины сохранены; один успешный переход. |
| Неизвестный вход/непринятый бюджет | Нет готовности; отдельная тревога; известная причина защиты не теряется. |
| Причины исчезли после защиты | Готовность закрыта до принятого ручного восстановления. |

Это целевой контракт; текущие runtime-поля и настройки ещё требуют сверки,
а T097 не принят. Число бюджета и реальный размер не выдумываются из порогов.

**Почему так**: сегодня пороги общехостовые, а в продуктиве включён
автоматический откат. Всплеск трафика на сайт может сам выключить измерение, не
сняв нагрузку. Это ровно та ситуация, ради которой фича и делается.

**Проверка**: SC-009 — учебная тревога, внешнее оповещение приходит не позднее
15 минут. SC-012 — пятикратный всплеск при принятой ёмкости и достаточном запасе
не отключает измерение и не влияет на доступность продукта.

## Нагрузка сайта

Это входной HTTP-профиль SC-012, не число людей, параллельных запросов,
событий PostHog, загрузок аудио или нагрузка CPU. Предварительно принимаются
ресурсный запас, абсолютный бюджет и срок расширения по T097; испытание
проводится на изолированном стенде после применимых гейтов, не на production.

- Набор адресов и доли: GET `/` — 40%, `/guides` — 20%, `/transcription` — 15%,
  `/meeting-minutes` — 15%, `/guides/rasshifrovka-zapisi-zoom` — 10%.
  Используются конечные canonical URL без query и автоматических повторов.
  Статика, health, robots, регистрация/вход, оплата и запись/обработка аудио
  исключены. Это проверка публичного сайта, а не всей нагрузки продукта.
- Baseline — 10 080 полных последовательных минут семи UTC-суток до дня
  проверки по тому же набору адресов. В каждой минуте считается число
  внешних HTML GET-запросов / 60. Известные боты, оператор, поддержка и
  автоматические проверки исключены принятым классификатором. Нет достоверной
  классификации/полного покрытия — baseline неизвестен; пропуск не заменяют
  нулём. Истинные наблюдаемые нули входят. R берётся по SC-012; источник,
  границы периода, N, R и пропуски указываются без IP/идентификаторов.
- Фазы: 5 минут разогрева при R → 20 минут при 5×R → 15 минут при R для
  восстановления. Частота задаёт открытый поток поступления запросов, а не
  ограниченное число постоянно занятых клиентов. Неотправленные плановые
  запросы учитываются как недостигнутая нагрузка; их нельзя скрыть снижением R.
  При R=0 либо неизвестном baseline допускается отдельная инженерная проба
  1 → 5 → 1 запрос/с с теми же фазами. Она маркируется как проба с нижним
  инженерным пределом и не закрывает SC-012 относительно измеренного p95.
- Для каждого запроса фиксируются длительность, итог/ошибка и достигнутая
  частота; итог — по минутам и каждой фазе. Раз в 15 секунд наблюдаются
  состояние продукта, аналитики, очередь, отставание и свободное место;
  на границах фаз — абсолютный объём классов. Только безопасные метаданные.
- PASS требует достигнутых входных 5×R полные 20 минут, HTTP 200 без 5xx,
  таймаутов/ошибок соединения и успешных проверок доступности продукта на
  всех пробах; нет защитного отключения измерения. Очередь после 15 минут
  восстановления не выше измеренного максимума разогрева, отставание не
  пересекает принятый порог guard. p50/p95/p99 времени ответа и фактические
  частоты публикуются по фазам; отсутствие задержек не выдумывается из HTTP 200.
- Любая потеря доступности, срабатывание защиты диска/аналитики или
  недостигнутая частота делает прогон FAIL, неизвестные обязательные метрики —
  INCOMPLETE. При защитной тревоге генератор останавливается, история не
  удаляется, продукт не откатывается автоматически. Принудительно выключать
  guard ради PASS нельзя. Весь поток теста исключён из клиентского отчёта.

Один такой прогон не подтверждает месяцы роста или доступность всего продукта.
T097 остаётся открытой до фактических измерений и приёмки; эти определения
не являются результатами испытания или новым одобрением владельца.

## Резервное копирование

| Правило | Значение |
| --- | --- |
| Расписание | Автоматическое |
| Целевое хранилище | `2brain.dev`, локальный `/var/backups/graf-posthog`; root 0700, архивы 0600 |
| Выгрузка за пределы сервера | В текущем этапе не требуется; принято владельцем 22.10.2026 |
| История точек восстановления | Последние 7 успешных полных наборов, минимум 2 перед готовностью; неполные не считаются и не вытесняют хорошие |
| Проверка восстановления | По расписанию, результат фиксируется |
| Блокировка готовности | Последний запуск неуспешен; нет полного проверенного набора/минимума; возраст неизвестен, отрицателен или ≥26 часов; часы проверены |

**Границы защиты**: решение владельца «сделай без него» отменяет обязательную
внешнюю копию. Потеря сервера/диска может уничтожить всю историю. Семь архивов
не ограничивают жизнь событий; каждый содержит всю сохраняемую историю.
Ротация допустима только после проверки нового полного набора и сохранения
минимума пригодных копий. Успешная распаковка не заменяет согласованное чтение
восстановленного PostHog. Восстановление из более старой точки означает пробел
после неё; потеря всех копий — новое измерение без обещания вернуть историю.

**Проверка**: SC-010 — проверка восстановления выполнена не позднее 30 дней
назад и зафиксирована.

## Хранение и удаление

| Категория | Целевой режим | Где применяется | Контроль |
| --- | --- | --- | --- |
| События уровней 2 и 3 | `until_decision` | ClickHouse | Нет удаления по возрасту; отдельное удаление |
| Обезличенный агрегат | `until_decision` | PostgreSQL | Нет возрастной очистки |
| История атрибуции визита | `until_decision` | PostgreSQL | Окно применения источника 90 дней отдельно |
| Атрибут привлечения клиента | `until_decision` | PostgreSQL | Нет возрастной очистки |
| IP / сетевые метаданные | `until_decision` | `rec-postgres/twobrain_rec/public.network_access_metadata`, storage=`graf_postgres` | INSERT-only приложение, операторский аудит до read/delete; writer закрыт до подтверждения основания/раскрытия/прав/копий по FR-061 |

Сессии, авторизационные данные и разрешения не получают бессрочную действительность.
Запись поведения не включается автоматически. Режим хранения не расширяет
перечень разрешённых полей и внешних получателей.

**Правила**: явный режим обязателен; отсутствующий/неизвестный режим — ошибка.
`until_decision` — осознанный режим без автоматического удаления по возрасту.
Удаление по отдельному решению/обязательному требованию наблюдаемо: основание,
охват, ответственный, крайний срок и результат. Срок исполнения задаётся отдельно
от хранения; без него случай удаления не закрывается.
Формулировки об удалении остаются в пределах контролируемого хранилища
(принцип IV конституции).

**Проверка**: SC-011 — пересечение старых пределов не удаляет учебные данные,
90-дневное окно источника соблюдается, отдельное удаление подтверждено.
Оператор сверяет установленный TTL и задачи очистки перед изменением; сначала
проверяет на изолированном наборе. Конфигурация, восстановление из старой копии
и переполнение не должны возвращать старую возрастную очистку.
Нехватка места — оповещение и остановка новых необязательных записей по FR-032,
а не разрешение удалить историю. Рабочая настройка пока не подтверждена.
Проверка режима выполняется ежедневно в 03:15 UTC. Readiness принимает
`recorded_at_epoch` только при 0 ≤ age <26 часов; отсутствующее/неправильное
время, будущее и age ≥26 блокируют готовность. После восстановления прежняя
запись проверки удаляется из действующего состояния до повторного запуска
проверки; чтение старого receipt не принимает восстановленный TTL.

Отсутствующая, старая или неизвестная редакция запрещает передачу до вызова
провайдера; транспортное поле не добавляется в свойства провайдера. Это
закрывает отправку старой вкладкой через эти два маршрута. Уже загруженный
внешний скрипт не останавливается серверной проверкой; рекламные/offline
согласия и отдельная редакция продуктовой телеметрии остаются границей T106.

Внешние копии документов и настройка хранения в кабинете провайдера остаются
операторскими подтверждениями и не считаются проверенными этим репозиторием.

### Реестр сетевых метаданных

Закрытый набор семи полей, права, аудит и восстановление заданы в
`data-model.md` §Правило хранения. Категория регистрируется отдельно от трёх
уровней: неподдерживаемая category/state является ошибкой, а не игнорированием.
Запись основания и раскрытие проверяются до каждой новой вставки; pending,
revoked, unknown, недоступная запись или несовпавшая опубликованная редакция
запрещают вставку. Запрет не ломает публичную страницу и обезличенный счёт.
Журнал IP не передаётся в PostHog/Метрику/рекламу/отчёты; повторное использование
ограничено безопасностью, исключением своего/служебного трафика и качеством
измерения. Удаление и аудит — по точному контракту модели, без выдачи raw IP.
