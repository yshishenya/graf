# T112 — подтверждение показа готового результата

Проект от 16.11.2026 для FR-021/025 и SC-006. Дополняет
[общий контракт вех](activation-milestones.md), не заменяет T113.
До независимой проверки требований и analyze реализация не начинается.
Рабочий сбор и внешняя передача остаются выключенными.

## 1. Что доказывается

Один проверенный владелец действительно открыл непустой готовый результат
нового серверного приёма аудио после неизменного `started_at` первого периода
T113. Это наблюдение показа в штатном клиенте; оно не доказывает прочтение,
полезность, физический захват аудио на Mac или статус нового внешнего клиента.
Готовая загрузка старого разговора подходит. Время самого разговора для этой
ветви не является временем поступления в продукт.

События остаются прежними: `first_result_viewed` и
`first_value_session_completed`. Обычный GET, polling, результат обработки,
уведомление и произвольный JSON в `/events` или desktop-capture их не создают.
Публичный сайт, тексты, расположение и оформление элементов не меняются.

## 2. Серверная цепочка происхождения

Начало периода берётся только из проверенной общей готовности T113. Ни
настройка с произвольной датой, ни текущий час, ни пустая таблица не заменяют
её. Пока этот источник не реализован и не принят, результат проверки закрыт.
В тесте допустима явно подставленная граница; это не рабочая готовность.

Используются существующие продуктовые записи, без новой таблицы, записи
содержимого в аналитику или заполнения происхождения задним числом:

1. `Meeting.created_by_user_id` равен principal; серверный `created_at` не
   раньше `started_at`; присутствует корректный `create_request_fingerprint_sha256`.
2. Существует относящийся к этому созданию `IngestAuditEvent.meeting_created`
   с теми же workspace/meeting/actor/device и серверным временем после начала.
   Сам fingerprint подтверждает запрос, а не физическую запись.
3. Показанный результат связан с текущей принятой неизменной `MediaRevision`.
   `source_fingerprint_for_revision()` подтверждает manifest и обязательные
   контрольные суммы источника. `accepted_at` задан и не раньше начала периода.
4. Существует `UploadSession` того же владельца, workspace/meeting/revision,
   со статусом `finalized`, непустым допустимым источником и серверными
   `created_at`/`finalized_at` после начала периода. Есть совпадающие сохранённые
   `session_created` либо `media_revision_upload_session_created`, а также
   `finalized`; их session/actor/device согласованы с этой сессией.
5. Текущая обработка и разрешённая проекция результата относятся именно к
   этой ревизии. Действуют её workflow/source/deletion fences; готовность
   определяется продуктовым чтением, а не клиентским `ready=true`.

| Случай | Решение |
| --- | --- |
| Новый manual upload старого разговора, вся цепочка совпала | Допустим для result/value; локальная запись не приписывается |
| Новое desktop-поступление, вся цепочка совпала | Допустим для result/value; сам enum источника не аттестует физический захват |
| Повтор обработки новой записи этого периода | Может дать первый настоящий показ при всей текущей цепочке; не создаёт вторую account-веху |
| Новый приём ревизии новой встречи этого периода | Проверяется собственная завершённая upload session текущей ревизии; одного revision_number недостаточно |
| Старая встреча с новой обработкой, updated_at или миграцией | Не подходит: нет нового создания/приёма после начала периода |
| Restore без нового приёма, исторический dual-source `initial_recording`, неполная/противоречивая цепочка | Происхождение неизвестно либо историческое; нового решения нет |

`ProcessingResult.status="imported"` — штатный импорт ответа MediaScribe,
а не признак миграции. Исключать этот статус нельзя. Источник `restore` сам
по себе не доказывает новую загрузку; существующий результат не достраивается
по времени или названию файла. Непокрытый restore gap закрывает admission T113.

Точно настроенная smoke identity исключается по существующим
`smoke_identity_class`/`smoke_user_id` и связанным операторским ID. Известные
internal/test/support/automated запросы исключаются существующим доверенным
классификатором; его публичные query/header не становятся разрешением.
Отсутствие smoke-признака и эвристический класс `external` не доказывают
внешний статус аккаунта. Продуктовая веха и коммерческий внешний счёт разделены:
без отдельной проверенной сверки аккаунта его внешний статус остаётся unknown.
Роль admin/owner и IP не заменяют такую сверку; нового реестра личностей нет.

## 3. Разрешённая проекция и краткоживущее подтверждение

Оба detail-пути используют общий `get_cabinet_meeting_review()` и текущие
правила выбора transcript/outcome, включая последнюю пригодную закреплённую
версию. Проверка не зависит от права экспорта, наличия аудио или export form.
Приготовление подтверждения переиспользует именно эту проекцию. Отдельный
запрос «самого свежего результата» с иным порядком выбора запрещён.

Подтверждение выдаётся только для разрешённого непустого содержимого:
текстового turn/segment расшифровки либо тела принятых итогов/следующих действий.
Заголовок встречи, метаданные, имя формата, placeholder, whitespace и сообщение
об ошибке не подходят. Каждый блок связывается с собственным result/outcome:
закреплённые итоги могут относиться к другой версии, чем текущая расшифровка.
Тип берётся из существующего закрытого каталога, не из клиентского текста.

Digest вычисляется сервером из канонического JSON только соответствующего
разрешённого блока: type, result_id/result_version, outcome_set_id при наличии
и упорядоченный список показанных непустых текстовых значений. UTF-8,
sort_keys, separators `(',', ':')`; для проверки пустоты применяется strip,
сам исходный показанный текст не переписывается. Динамические кнопки, имена,
время/счётчики, ссылки и другие панели в digest не входят. Код получения
проекции общий для render и проверки, а не два похожих извлечения текста.
Сам JSON существует только в текущей серверной памяти, не сохраняется.

В серверном render context формируется подписанное HMAC-SHA256 подтверждение
с отдельным префиксом `f273-result-view-v1`, используя существующий серверный
CSRF secret; новый секрет и зависимость не добавляются. Не переиспользуется
подпись обычного CSRF token. Ограниченный payload содержит version, owner,
workspace, привязку к текущей auth session/device, meeting/revision,
source fingerprint, result/version, outcome-set при наличии, deletion_epoch,
тип блока, digest его разрешённой проекции и серверное время выдачи.
Текст, название, URL, IP и токены авторизации в payload не входят.

Срок — 10 минут, размер закодированного подтверждения — не более 1536 bytes
(тело собственного POST целиком — не более 2 KiB);
будущее время/неизвестная версия/неверная подпись/чужая сессия отвергаются.
Подтверждение передаётся только как невидимый data-атрибут соответствующего
готового блока и тело собственного POST, никогда в URL, журнал, внешнее событие
или durable ledger. Ответы private/no-store. Перехват тела диагностикой и
общим сбором поведения запрещён. Остаются существующие права detail-страницы.

При истечении срока endpoint может вернуть новое подтверждение **без принятия
вех**, только если свежая проекция, версия и все условия совпали. Клиент
повторно наблюдает тот же показанный блок и делает не более одного нового
подтверждения в рамках этого перехода видимости. Смена версии требует нового
штатного render; старый блок не получает разрешение на новый результат.
Это позволяет учесть поздний настоящий показ без срока чтения и вечной очереди.

## 4. Наблюдение показа

Один общий обработчик `cabinet.js` работает на готовой странице и после
HTMX replacement/processing→ready. Наблюдается сам непустой текстовый блок:
он подключён к текущему документу, не скрыт сам или предком, имеет ненулевой
прямоугольник и пересечение с viewport (`IntersectionObserver`). Одновременно
документ visible, не prerendering и имеет focus. Перед POST все условия
проверяются повторно после возможности отрисовки через animation frame.
Фоновое завершение polling само по себе ничего не отправляет.

Для встроенного кабинета дополнительно нужен ответ узкой native-проверки:
приложение активно, текущий WKWebView attached к разрешённой detail-странице,
окно visible, не miniaturized и имеет visible occlusion state. Используется
существующий проверяемый шаблон main-frame/origin/session-generation bridge;
новый узкий обработчик возвращает только готовность текущей поверхности и
ничего не отправляет. Deletion bridge `visibleRecordings` не переиспользуется.
После асинхронного ответа заново проверяются текущий документ и блок. Старый
клиент без этой проверки получает безопасное отсутствие измерения; запись и
просмотр продолжают работать. Совместимость и тесты обоих поколений обязательны.

Нет нового требования нажать кнопку, ждать N секунд или прочитать текст.
Браузерное наблюдение не является защитой от намеренной подделки собственного
клиента авторизованным владельцем и не даёт гарантии отсутствия перекрытия
чужим окном ОС. Оно подтверждает штатный наблюдаемый показ, не внимание человека.

Отправка асинхронна и не блокирует просмотр. Нет beacon при закрытии страницы,
localStorage/UserDefaults, повторов по таймеру и очереди после ухода. В памяти
документа хранятся только текущие proof/in-flight/успех для его блоков; HTMX
отключает наблюдение удалённых узлов. Ошибка допускает новую попытку только
при новом настоящем переходе видимости и повторной серверной проверке.

## 5. Защищённый серверный вход и согласованное решение

`POST /meetings/{meeting_id}/result-viewed` и встроенный alias
`POST /desktop/meetings/{meeting_id}/result-viewed` вызывают один обработчик.
Тело содержит только `proof`; неизвестные поля и тело свыше 2 KiB отклоняются.
Переиспользуются `PrincipalDependency`, `WebTenantDependency`,
`WebCSRFDependency` и существующие cookie/header правила. Не вводится
самостоятельное исключение из CSRF для этой операции. Субъект и поверхность
определяются сервером; account/pseudonym/source_kind из JSON не принимаются.

На свежей ограниченной сессии выполняются проверки:

1. Общая admission boundary T113 получает свои filesystem/DB fences; чужой
   или отсутствующий receipt, неизвестный started_at и закрытый gate прекращают
   измерение. `activation_recovery_unverified` в этом срезе не снимается.
2. В общем порядке T113 берётся shared identity lock активного аккаунта,
   затем действующие session/membership и meeting/source fences. Для этих
   аналитических чтений/locks используется NOWAIT либо ограниченный timeout;
   неизвестность и занятость дают отказ без влияния на продукт.
3. После locks заново читаются principal/session, действующее членство,
   точное владение `Meeting.created_by_user_id`, полный разрешённый доступ,
   source/result/digest/deletion_epoch и цепочка раздела 2. Colleague/admin/
   shared recipient другого владельца не подходит даже при полном чтении.
4. Свежие основание/отзыв, readiness, режим и resource guard проверяются
   непосредственно перед каждым INSERT общей границей. Сохранённый render
   context или paid approval не разрешает запись. При смене gate весь новый
   набор откатывается. Нет сетевой передачи провайдерам внутри запроса.
5. Только проверенный серверный факт создаёт payload двух прежних событий.
   Общий `admit_account_milestone()` сохраняет их одной транзакцией и одним
   commit, с прежними уникальными `(account_id,event_name)` и delivery states.

Весь аналитический запрос ограничен 2 секундами; lock timeout не более 250 ms,
statement timeout не более 500 ms, без SQL/application retry по timeout.
Лишний сетевой вызов не включается в путь render/обработки/записи. Ошибки
входа/auth/CSRF возвращают существующий безопасный отказ; ошибки аналитики —
закрытый ограниченный status без содержимого/exception text. Просмотр не зависит
от этого ответа. Нет фоновой сессии, переживающей свой бюджет.

Новые result/value не могут частично сохраниться. Уже принятое первое событие
не переписывается; допустимо добавить отсутствующее второе по новому полностью
проверенному показу. Этот текущий показ сам доказывает обработку и содержимое
одной записи для first value, независимо от записи первой result-вехи другой
встречи. В ledger ID частной встречи не сохраняется.
Два клиента, restart и replay получают прежние account-решения, без второго
счёта. Неопределённый commit не повторяется автоматически: следующая настоящая
видимость сначала разрешает существующие ключи через общий admission. Внешние
submitted/ambiguous не переотправляются. Restore/delete/regenerate не сбрасывают
первые ключи; account/category purge и recovery остаются T113.

Обычный `ingest_authenticated()` сохраняет `trigger_unverified` для обоих имён;
новый доверенный вызов не является флагом, который можно передать в клиентском
payload. До приёмки T113 проверяется настоящий закрытый путь и изолированный
trigger с подставленной admission boundary; второй не объявляется end-to-end
хранением, restore или разрешением `local_only`.

## 6. Свойство записи и отчёты

`first_recording_completed` как отдельное событие сохраняет смысл успешного
локального capture. Одноимённое свойство first-value является необязательным:

| Доказательство для той же показанной записи | Свойство first-value |
| --- | --- |
| Проверенная браузерная загрузка файла, без локального capture | `false` |
| Новый серверный приём с desktop, но нет привязанного к этой записи доверенного доказательства локального capture | Поле отсутствует: неизвестно |
| Собственное доверенное доказательство успешного локального capture именно этой записи | `true`; source_kind и account-веха другой записи таким доказательством не являются |
| Непроверенное происхождение | Нового result/value события нет |

Поверхность просмотра не определяет источник: открытие desktop-записи в
браузере не превращает её в manual upload. `false` выводится из полной
проверенной цепочки приёма файла с `manual_upload`, а не из route или client
boolean. Прочие неаттестованные способы capture сохраняют отсутствие поля.

Существующая серверная схема не связывает account-веху локальной записи с
частной встречей. Поэтому T112 не синтезирует `true` из неё. Построитель
`cabinet/web.py` принимает явное `bool | None`, без неявного `True`; `None`
не сериализуется. Каталог остаётся прежним, новых внешних полей нет.
Старые payload не переписываются и их семантика задним числом не исправляется.
Все callers/fixtures/tests и отчётные фильтры проверяются на отсутствие
обязательного `first_recording_completed=true` для browser first value.
Первая ценность обеих ветвей считается по имени account-вехи, не по установке,
локальному capture или отдельному свойству. Неизвестная кампания остаётся unknown.

## 7. Причинная проверка до приёмки

Матрица и команды находятся в [quickstart, T112](../quickstart.md#t112--профиль-подтверждения-показа).
До кода: независимый разбор D1–D7, четыре reviewer-owned checklist, analyze
без critical/high и проверка существующего issue mapping. После кода: RED на
исходном пути, DB/browser/Swift/failure GREEN, независимое ревью и converge;
обязательные exact-SHA GitHub gates сохраняются. Истёкшее исключение T098
не продлевается и классификация не меняется ради прохождения проверки.
