# T106: индивидуальный серверный выбор публичной аналитики

Статус: проект до независимой проверки, 01.11.2026. Та же T106/#7696,
FR-001/002/003/006/008/048/049/059. Это дополнение к прежним узким срезам,
которые явно не реализовывали индивидуальный серверный отзыв.

## Область и основание

Единственный получатель этого среза — существующий self-hosted PostHog через
public relay. Внешний браузерный SDK, Метрика, replay, формы, карты и offline
conversion остаются закрытыми. Никакого polling/SSE/TTL-разрешения вкладки.
Сохранение контроля отказа необходимо для соблюдения выбора, а не для измерения
отказавшегося посетителя. Оно отделено от всех трёх уровней событий.

Повторное согласие разрешено только новым явным действием. Восстановление
старого localStorage, повтор HTML, callback, payload или запроса grant не
являются новым действием. При неизвестном результате выбора необязательная
аналитика запрещена, страницы и обезличенный агрегат продолжают работать.

## Контрольная запись

Одна новая таблица `public_analytics_choices` в существующей GRAF PostgreSQL:

| Поле | Договор |
| --- | --- |
| `consent_digest` | SHA-256 уже существующего UUIDv4 `CookieConsent.consentId`, первичный ключ |
| `epoch` | Случайный серверный UUIDv4 при каждом изменении; не клиентское время |
| `categories` | Закрытый набор из существующего каталога, обязательно `necessary` |
| `copy_version` | Точная редакция положительного решения; NULL при отказе |
| `updated_at` | Серверное время изменения |

Исходный consentId используется как непредсказуемая ссылка владения выбором,
не как доказательство личности. Он передаётся только в ограниченном JSON-теле
первой стороне и никогда не включается в URL, журналы, свойства события,
distinct_id, агрегат, атрибуцию или аккаунт. Digest также не экспортируется.
Отправка сохраняет прежний сессионный `view_id` как distinct_id. Для будущего
удаления ранее переданных данных это само по себе не создаёт полной связи с
историей; такую связь и удаление у получателя данный срез не заявляет.

RLS обязателен и принудителен: приложение читает/меняет только digest из
проверенного сервером transaction-local контекста; без него — ни одной строки.
Maintenance-доступ — только существующая проверенная роль и названная операция
`public_consent_control`, без новых внешних ролей или BYPASSRLS. Миграция,
права, индекс, модель и фактические PostgreSQL проверки входят в реализацию.
Доступ через публичный API ограничен одним consentId, списков/поиска нет.

Категория хранения `public_consent_control`: `until_decision`, без возрастной
очистки. Не хранит IP, UA, кампанию, аккаунт, события или содержимое встреч.
Новая строка допускается под одной общей admission-блокировкой только пока
`pg_total_relation_size` таблицы с индексом меньше 16 MiB; повторно измеряется
перед INSERT. Превышение закрывает новые записи с 503 и видимым pending,
существующие отзывы обслуживаются. Это предел допуска новых ссылок, а не
обещание абсолютного размера при UPDATE/MVCC; общий ресурсный guard сохраняется.
Никакого удаления старых строк ради освобождения места.
Порядок блокировок един: digest → admission (только для отсутствующей строки).
Операция не берёт второй digest, admission-владелец не ждёт digest.

## API и порядок решений

Новый POST `/analytics/public-consent`: JSON не более 1024 байт, обязательный
точный same-origin Origin, `Cache-Control: no-store`, закрытые поля и типы.
UUID должны иметь каноническую форму UUIDv4. Никаких cookies/провайдерных ключей
в ответах. HTTP400 — неверное тело, 403 — чужой/отсутствующий Origin или
запрещённое разрешение, 409 — устаревший epoch, 503 — неизвестное состояние.
Каждый control request и каждая delivery attempt имеют общий конечный бюджет
6 секунд, включая получение соединения, контекст, обе блокировки, read/write,
transport и commit. Отдельный transport ограничен ещё и 5 секундами внутри
остатка общего бюджета; redirect запрещён. Бюджет истёк до доказанного commit —
503 `choice_unavailable`, без accepted/epoch и без автоматического grant.
Отмена не оставляет незавершённый transport за освобождённой защитой; bounded
drain завершается прежде освобождения DB lock. Бюджеты отрисовки страницы не
меняются: control выполняется отдельным запросом.

- `read`: `{action, consent_id}`. Не создаёт строку. Возвращает текущие
  `epoch/categories/copy_version`, либо `state=unknown`. Ничего не разрешает.
- `revoke`: `{action, consent_id}`. Сбрасывает все optional категории,
  очищает copy_version и создаёт новый epoch; при отсутствии строки сохраняет
  запрет прежде ответа. Не зависит от флага аналитики, текущей редакции,
  наличия положительного согласия, глобального register или состояния PostHog.
  Повтор безопасно оставляет запрет; epoch снова меняется, поэтому даже
  запоздалый grant после повторного revoke не становится действующим.
- `grant`: `{action, consent_id, expected_epoch, categories, copy_version}`.
  Только текущая редакция, нормализованный явный положительный выбор и
  существующий public/global basis guard. После блокировки expected_epoch
  обязан совпасть с текущим. Меняет epoch снова и сохраняет только выбранные
  категории. Нет автоматического rebase/retry grant после 409 или 503.

Точные success bodies после успешного commit, HTTP200:
`revoke → {accepted:true,state:"revoked",epoch:<uuid>,categories:["necessary"],copy_version:null}`;
`grant → {accepted:true,state:"granted",epoch:<uuid>,categories:<normalized>,copy_version:<current>}`.
Read возвращает HTTP200 `{state:"known",epoch,categories,copy_version}` либо
`{state:"unknown"}`, без accepted. Ошибки возвращают только
`{accepted:false,reason:<stable_code>}` и не возвращают epoch.
Для grant браузер берёт expected_epoch исключительно из принятого revoke
**этого явного выбора**, никогда из позднего read, 409 или повторного rebase.

Все операции одного digest и каждая отправка используют один PostgreSQL
transaction advisory lock с этим digest, включая случай отсутствующей строки.
Отзыв принят только после commit; ошибочный/неизвестный commit не означает
успеха. Последний успешно принятый сервером переход является действующим.
Новый отказ не ждёт включения необязательного измерения.

Relay дополнительно требует `consent_id` и `consent_epoch`, проверяет точную
редакцию, категории и прежний каталог. У самой границы transport повторяется
чтение состояния после той же блокировки. Lock и DB-сессия удерживаются до
завершения ограниченного transport. В том же порядке проверяются global basis
и существующий `resolve_provider_delivery_gate`; отказ не обходит wrapper.
После commit revoke старый epoch не начинает новый transport, включая
отложенный worker и повтор старого payload после нового grant.
Транспорт имеет общий предел 5 секунд, без redirect и фоновых retry/outbox.
Отключение HTTP-запроса не освобождает защиту раньше завершения transport;
поток/корутина должны быть завершены или дренированы. Неопределённая внешняя
доставка остаётся ambiguous и автоматически не повторяется. Уже начатая до
отзыва передача не объявляется ретроактивно отменённой.

## Браузер

Повторно используются CookieConsent и текущие локальные guards. Новый явный
выбор сначала блокирует sends и отправляет revoke; только после его принятия
и повторной сверки фактической записи библиотеки допускается CAS grant
выбранных категорий. После ответа epoch сохраняется в existing cookie data;
analytics запускается лишь если запись библиотеки по-прежнему совпадает.
Уменьшение набора целей сначала отзывает весь прежний набор, затем отдельным
grant разрешает оставшийся выбранный набор: промежуток всегда запрещён.

Загрузка страницы/onConsent не выдаёт grant: только read и сверка сохранённого
epoch, редакции и категорий. Старое положительное решение без серверного epoch
требует нового выбора. Storage/pageshow/focus не перезаписывают отказ и не
выдают grant; каждый relay передаёт принятый epoch. Cross-tab отзывает тот же
consentId. Потеря/порча записи — локальный запрет. Передача исходного consentId
в PostHog или установка его в качестве view_id запрещены.

При ошибке revoke локальный отказ сохраняется; доступный текст говорит
«На этом устройстве аналитика отключена. Серверное сохранение отказа пока не
подтверждено» и предлагает повторить. Успех не показывается до commit.
При ошибке grant измерение остаётся отключённым, выбор можно повторить.
Используются существующая панель настроек/статус `role=status`, без блокирования
сайта. Отказ остаётся столь же доступным, как согласие.
У статуса есть обычная доступная кнопка: «Повторить сохранение отказа» при
pending revoke или «Подтвердить выбранное разрешение» при положительной записи
без действующего server epoch/после ошибки grant. Её явная активация начинает
новую последовательность revoke→grant по текущему фактическому выбору.
Это необходимо и при неизменившихся категориях: CookieConsent не обязана
повторять onChange/onConsent. Никаких grant по одному восстановлению страницы.
На странице с выключенным измерением настройки отказа остаются доступны;
automatic banner и grant не включаются из-за одной доступности control API.

## Хранение, восстановление и границы приёмки

Таблица включается в полный GRAF dump, relation inventory, retention и
контролируемый lifecycle. Перед восстановлением действует существующий
глобальный запрет; до снятия карантина **все** записи таблицы, включая
necessary-only, сбрасываются с новыми случайными epoch. Поэтому старая копия не оживляет ни
отзыв, ни прежнее событие. Удаление контрольных строк разрешается только
отдельным случаем с основанием/охватом/сроком/ответственным/результатом и при
закрытой выдаче новых grant; последующий read отсутствующей записи запрещён.
Повторное применение случая после restore обязательно.

Публичные настройки и каталог не включаются этим PR. Рабочий запуск закрыт
до принятого включения таблицы в существующие backup/restore/lifecycle gates,
проверки фактических прав, опубликованных текстов, конфигурации и настоящего
browser/provider readback. Полный T106, T113/T0 и коммерческая цель открыты.
Перед реализацией: reviewer-owned checklist, analyze C/H0, связь с #7696.
