## Результат

T024 реализована и проверена локально. Сам валидатор получил внутренний режим
наблюдения установленного Dev, которым управляет существующий dev-harness.
Release direct-child режим и signing caller сохранены. Продуктовое приложение,
backend, данные, подпись, TCC и установленный bundle не изменялись.

Отдельные SHA инструмента и приложения, committed bytes, manifest/digest,
фактическая подпись и её параметры проверяются до и после операции. Новый
пустой журнал содержит только доказательства этого запуска; наблюдатель требует
точный единственный PID с временем старта, отсутствие zombie, жизнь ≥5s и
оба полных имени событий `app_launch_finished` / `app_main_window_presented`.
Завершение процесса связано с ожидаемой identity внутри native helper.

Работающий Dev без явного подтверждения idle отклоняется. HOME, Application
Support, cookies и defaults не подменяются: это обычная установленная приёмка
со штатными фоновыми действиями, а не изоляция пользовательских данных.

При обработанном успехе/ошибке harness возвращает исходное running/stopped
состояние, прежний running открывает без временного журнала. Неизвестный
заменивший процесс не завершается. При отказе восстановления результат FAIL;
каталог, используемый живым процессом, сохраняется. До первого изменения
долговечно записывается recovery receipt; при аварийном завершении контроллера
она остаётся. Общий state_lock блокирует все изменяющие операции, status
показывает блокировку. Автоматическая отдельная команда восстановления после
необработанного завершения контроллера не добавлена. При прежнем running
восстановление нельзя считать завершённым и нельзя снимать квитанцию, пока
состояние не подтверждено штатным путём; повторный idempotent promote сам по
себе не запускает остановленное приложение. Это явное ограничение отказа,
а не успешная приёмка прерывания.
