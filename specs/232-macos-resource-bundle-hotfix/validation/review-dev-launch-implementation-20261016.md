## Устранённое замечание к инструкции

### P2, устранено: описанный promote не возвращал остановленное приложение в running

Место: `infra/dev/README.md:73–78`, существующий idempotent путь
`scripts/dev-harness.py:2681–2693`.

После аварийного прерывания инструкция требует штатно выйти из Dev,
подтвердить остановку, очистить принадлежащие операции остатки и при исходном
running восстановить приложение обычным `promote --live` того же active
manifest. Но `operation_promote` возвращает idempotent success, если активны
backend/runtime и установлен bundle. Он не проверяет и не восстанавливает
работающий процесс приложения в этом пути.

Независимое воспроизведение на искусственном окружении существующего test
fixture: исходный app stopped, active manifest/live runtime и installed bundle
присутствуют; выполнен настоящий `operation_promote` с подменёнными только
внешними probes. Результат:

```text
idempotent= True app_running= False launches= []
```

Никакое настоящее приложение не запускалось. Первоначальное замечание требовало:
нужен конкретный поддержанный путь действительного восстановления
running либо честная остановка восстановления с сохранением незавершённого
состояния. Возврат idempotent нельзя описывать как восстановление процесса.
Не обходить singleDev/harness через прямой бинарник, копии или изменение
bundle/подписи. После изменения процедуры проверить её тем же stopped/runtime
сценарием. Это замечание к новой инструкции; оно не требует автоматически
расширять данный срез до изменения общего promote.

Повторная проверка после исправления: README больше не предлагает этот
неработающий путь. Если до аварийного завершения контроллера Dev был running,
восстановление честно остаётся незавершённым и receipt нельзя удалять до
подтверждённого штатного восстановления. Отдельной команды восстановления
в данном срезе нет; обход harness и снятие блокировки ради PASS запрещены.
Это допустимый минимальный отказ с сохранением доказательств, а не обещание
автоматического восстановления. `validation/dev-launch-20261016.md` содержит
то же ограничение. **Замечание устранено без изменения общего promote.**

Также перечитана окончательная поправка README: остановка подтверждается
существующим read-only `dev-app-lifecycle.swift status` и ответом `stopped`.
`dev-harness status --json` используется для наличия bundle/recovery;
несуществующее поле `app.running` больше не предлагается. Это соответствует
`_installed_app_state`, возвращающему только path/installed, и не меняет код
или четыре закреплённых хеша. Сам проверяющий helper на живом Dev не запускал.

## Устранённое замечание

### P1: после аварии остальные изменяющие операции могли обойти recovery receipt

В первой проверенной версии durable receipt учитывался только `status` и
новой проверкой. Независимый искусственный сценарий с существующей
`app-launch-validation-recovery.json` показал, что `operation_promote` достигает
adapter.promote:

```text
HarnessError REVIEW_SENTINEL lifecycle adapter reached
active_recovery_receipt_present= True
reached= ['adapter.promote']
```

Исполнитель перенёс отказ в общий `state_lock`, после захвата flock до yield.
Окончательный набор 39 проверок содержит отрицательные сценарии для всех
семи остальных изменяющих входов: build, promote, rollback, recover-schema,
rehydrate, prune, reset-data. Ни один не достигает adapter и квитанция не
изменяется. Новая проверка также отказывает до lifecycle. `status` остаётся
чтением и показывает blocked. **Замечание устранено.**

## Просмотренный поток

- Проверены все общие callers `_launch_dev_app` и `_terminate_dev_app`.
  Необязательные параметры оставляют прежний normal launch/quit без изменений;
  fresh-log launch отказывает при уже работающем приложении.
- До первого lifecycle изменения проверяются live pointer/manifest/recovery,
  clean tooling SHA, committed bytes четырёх управляющих файлов, точный bundle
  path/SHA/digest, codesign verify и signing identity/requirement/entitlements.
- Tooling SHA и installed source SHA различаются явно. Установка/пересборка
  продукта, backend или manifest не является частью новой операции.
- Native identity использует ровно один exact path/bundle ID и launchDate.
  Graceful terminate нового режима повторно связывается с ожидаемыми PID/date
  внутри native helper. Неоднозначный исходный процесс отклоняется до quit.
- Новый read-only shell observer не запускает и не завершает Dev. Он проверяет
  исходную/конечную identity, жизнь PID и отсутствие zombie на интервале 5s,
  затем оба полных имени маркеров в принадлежащем операции новом журнале.
- Recovery receipt долговечно записывается до первого quit/start, дополняется
  owned identity, остаётся при внезапном выходе или неудачном восстановлении.
  Неизвестный заменивший процесс не завершается; каталог живого процесса
  сохраняется. Успешное восстановление удаляет receipt даже при FAIL валидатора.
- Обычная обработанная ошибка пытается вернуть running/stopped в finally;
  прежний running запускается без временного log override. Ошибка восстановления
  блокирует PASS; forced termination установленного приложения отсутствует.
- Старый release CLI продолжает запускать собственный direct child с прежними
  временными каталогами, ≥5s, двумя маркерами и очисткой только своего процесса.
  Общая проверка маркеров стала точнее и отвергает суффикс `_fake`.
- Штатные фоновые действия обычного Dev и операторское idle-предусловие
  сохранены; изоляция данных/атомарный запрет будущей автозаписи не заявляются.
