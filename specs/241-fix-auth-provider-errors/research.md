# Research: Непрерывность способов входа при ошибках

## Decision 1: восстанавливать фактический provider snapshot в общем error path

**Decision**: Все восстановимые ошибки, для которых уже известны `db` и
`workspace_id`, получают список провайдеров через существующий
`_load_browser_login_providers()`. Общий error-response helper ловит
`ProblemDetail` и оставляет пустое fail-closed состояние.

**Rationale**: Обычные GET `/login` и `/sign-up` уже используют этот источник.
Ручные `providers=[]` в POST/error ветках стирают действующую политику и
оставляют только planned-заглушки из rendering layer. Повторное использование
загрузчика исправляет все соседние пути без параллельного registry.

**Alternatives considered**:

- Загружать провайдеров один раз в начале каждого POST — отвергнуто: добавляет
  лишний DB read в успешный email path.
- Передавать список из браузера скрытым полем — отвергнуто: это недоверенный
  клиентский ввод и может показать выключенный способ.
- Убрать planned-заглушки — отвергнуто: они не являются причиной; исходная
  продуктовая композиция остаётся вне этой фичи.

## Decision 2: сохранить fail-closed границы

**Decision**: Пустой provider state остаётся допустимым при неизвестном
workspace, отсутствии DB, недоступной политике и специальном recovery mode без
разрешённых провайдеров. Ошибка чтения политики не подменяется defaults в UI.

**Rationale**: Нельзя представлять непроверенный способ как включённый.
Существующий `ProblemDetail` — каноническая граница недоступности auth policy.

**Alternatives considered**:

- Показывать статический Яндекс ID/VK при сбое — отвергнуто: нарушает policy и
  вводит пользователя в заблуждение.
- Ослабить RLS/tenant context ради recovery UI — отвергнуто конституцией.

## Decision 3: различать pre-delivery отказ и реальный сбой доставки

**Decision**: `email_start_unavailable` говорит, что вход не удалось начать,
предлагает проверить адрес, другой включённый способ либо регистрацию и не
утверждает, что письмо отправлялось. `email_delivery_unavailable` остаётся
отдельным сообщением о фактическом сбое доставки.

**Rationale**: `_resolve_email_login_user()` может вернуть отсутствие
безопасно выбираемой identity до создания кода и вызова почтового сервиса.
Текущий текст «Не удалось отправить код» технически неверен и смешивает два
разных этапа.

**Alternatives considered**:

- Сообщить «аккаунт не найден» — отвергнуто: позволяет проверять наличие чужих
  аккаунтов по email.
- Автоматически перейти в регистрацию — отвергнуто: ordinary login не должен
  создавать аккаунт или менять identity policy.

## Decision 4: повторно показывать только проверенный нормализованный email

**Decision**: Rendering contract получает необязательный `email_value`.
Маршрут передаёт его только после успешной `_normalize_email()`; Jinja выводит
значение в `<input value>` с обычным autoescape. Неверное исходное значение не
отражается.

**Rationale**: Это устраняет повторный ввод после восстановимой ошибки, не
создаёт новый trust boundary и использует уже существующую валидацию.

**Alternatives considered**:

- Отражать сырой form input — отвергнуто из-за лишнего риска и несогласованной
  нормализации.
- Хранить email в cookie/session — отвергнуто: состояние нужно только в одном
  ответе и не требует хранения.

## Decision 5: удалить только связанное доказанное дублирование

**Decision**: Свести повторяющиеся try/catch загрузки provider snapshot и
многочисленные ручные error renders к минимальному общему пути, если это не
меняет status, headers, invitation mode, analytics и safe-next.

**Rationale**: Репозиторный поиск показал один owner-модуль auth rendering.
Глобальная чистка вне него не доказана и увеличила бы риск без пользы для
дефекта.

**Alternatives considered**:

- Массово реорганизовать auth routes — отвергнуто как несвязанная архитектурная
  работа.
- Исправить только screenshot branch — отвергнуто: rate-limit, delivery,
  sign-up и provider-start имеют тот же сброс состояния.

## Historical evidence

- Feature 175 уже сохранила provider actions в специальном ambiguous-email
  recovery path через `_ambiguous_email_recovery_response()`.
- Текущий дефект остался в обычных error branches, которые всё ещё передают
  `providers=[]` напрямую.
