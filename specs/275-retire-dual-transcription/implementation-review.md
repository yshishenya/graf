## Находки

### C2 — P2: старый workflow в not_submitted не получает заявленное конечное состояние

**Исправление исходного сценария видно в рабочем дереве; окончательное закрытие ожидает теста и финального SHA. Владелец T003.** Место новой логики: `apps/server/src/twobrain_rec_server/processing/store.py:1754`, `retire_unsupported_processing()`. Ниже описано состояние на момент обнаружения.

Сценарий: сохранённый workflow старой `initial_recording` имеет `status=not_submitted`, внешнего ID нет. Это допустимое сохранённое значение и значение по умолчанию `ProcessingWorkflow.status` в `db/models/processing.py:120`. `processing_source_is_retired()` возвращает True; helper вызывает `set_workflow_status(...FAILED_TERMINAL, terminal=True)` и без проверки результата возвращает True.

Однако `processing/lifecycle.py`, `ALLOWED_PROCESSING_TRANSITIONS[NOT_SUBMITTED]`, разрешает только STARTING/BLOCKED/CANCELED. В `set_workflow_status()` запрещённый переход возвращает прежний workflow до установки причины, времени завершения и освобождения квоты. Поэтому вызывающий worker может сообщить `failed_terminal`, хотя в БД осталось `not_submitted`; pickup повторно обнаруживает тот же незавершённый источник. Если существовало резервирование, этот вызов его также не освобождает. Новая dual-отправка не происходит, но FR-005 о конечном понятном состоянии нарушен.

Доказательство: независимо выполнены фактические enum, таблица переходов и `can_transition()`, выделенные через AST без импорта приложения и без записи файлов. Результат: `not_submitted -> failed_terminal: False`, контрольный `workflow_started -> failed_terminal: True`. Полный сценарий с БД пока не запускался. Прочитанная матрица `test_historical_pending_stops_without_quota_claim_or_egress` охватывает только workflow_started/waiting_retry/blocked_unknown.

Исправление: обеспечить допустимое и долговечное завершение старого pending workflow, проверять фактический результат перехода; сохранить ограничения удаления/tenant и терминальность завершённых записей. Добавить not_submitted в проверку с повторным чтением БД: failed_terminal, unsupported_recording_source, отсутствие следующего повтора, освобождённое существующее резервирование, ноль новых provider POST/claims/reservations. Не ослаблять общую таблицу состояний без необходимости.

При последнем чтении после сообщения находки в `ALLOWED_PROCESSING_TRANSITIONS[NOT_SUBMITTED]` добавлен FAILED_TERMINAL, а в матрицу теста — not_submitted. Это устраняет исходный запрещённый переход; существующая проверка терминальных состояний сохранена. Результат запуска расширенного теста и освобождение уже существующего резервирования рецензентом ещё не подтверждены. Первоначальный результат False выше относится к версии до исправления.

### C1 — P2: известный ID ошибочно разрешал новую попытку без источника

**Исправление видно в рабочем дереве; окончательное закрытие ожидает теста и финального SHA. Владелец T003.** Место: `processing/store.py`, `create_processing_attempt()`, первоначальное вычисление `known_provider_job` около строки 1275.

В первоначально прочитанной версии любой `previous_job.external_job_id` обходил обе проверки отсутствующего источника. При этом перенос старого job к новой попытке происходил только при `resumable_provider_job is not None`. Для завершённого/окончательно неуспешного старого dual job можно было пройти ручной retry/reprocess, зарезервировать квоту, создать workflow с этапом submit без переноса ID и получить немедленный отказ unsupported в worker. Это также расширяло допуск single-file повторов после удаления источника.

После сообщения находки код изменён: `known_provider_job` требует `_RESUMABLE_PROVIDER_JOB_REASONS` и исключает FAILED/BLOCKED/DELETING. Это закрывает первоначальный сценарий чтением кода. Проверить отдельно: завершённый/failed dual с известным ID и отсутствующим single source отклоняется до новой попытки/квоты; допустимое восстановление известного задания продолжает poll/import без POST и без зависимости от уже удалённого источника. Результаты этих тестов рецензент пока не подтверждает.
