# Research: Повторный ввод email-кода

## Decision: Использовать существующий state rate-limit bucket

- Текущий `email_code_verify_state` ограничивает проверки одного state и уже
  коммитит счётчик отдельно от auth-транзакции.
- Лимит меняется с 10 до 3; лимиты по email/IP и отправке не меняются.
- Это не требует новой колонки или миграции и сохраняет существующую защиту от
  brute force.

## Decision: Неверный код до лимита не завершает state

- HMAC mismatch фиксируется в auth audit, но state остаётся `pending`.
- `email_code_wrong` отделяется от повреждённого, истёкшего и replayed state.
- Для публичного login/signup существующий `expected_state` хранит два
  серверных HMAC-значения: отдельную привязку browser-cookie и проверку кода;
  это позволяет отличить опечатку от чужой или отсутствующей cookie без новой
  колонки, открытого кода или сохранённого nonce.
- Terminal state используется после expiry, success, replay или прочих
  fail-closed условий.
- После mismatch читается уже потреблённый state bucket; при счётчике 3 экран
  сразу показывает blocked/recovery state, не добавляя колонку или миграцию.

## Decision: Блокировка показывается через существующий 429 flow

- Три неудачные проверки допускаются.
- Третья неудача и последующая проверка получают текущий
  `auth_rate_limited` recovery state; форма кода скрывается, а resend остаётся
  доступным.
- Через действующий resend-flow пользователь получает новый state согласно
  существующим лимитам.

## Alternatives considered

- Новая `failed_attempts` колонка в `AuthCallbackState`: отклонено как лишняя
  схема и миграция; state bucket уже является durable counter для этого scope.
- Завершать state после первой ошибки: отклонено, это и есть текущий баг.
- Менять лимиты email/IP/resend или TTL: отклонено прямым решением пользователя.
