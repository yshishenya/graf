# Feature Specification: Повторный ввод email-кода с лимитом попыток

**Feature Branch**: `codex/200-email-code-retry`

**Created**: 2026-08-25

**Status**: Draft

**Input**: User description: "При неверном коде подтверждения email оставить возможность повторного ввода; разрешить 3 попытки на один код и заблокировать код после третьей неудачи. Остальные лимиты не менять."

## User Scenarios & Testing

### User Story 1 - Исправить опечатку в коде входа (Priority: P1)

Пользователь, который ошибся в одной или двух цифрах email-кода, может повторно
ввести код без обязательной повторной отправки письма.

**Why this priority**: Это основной дефект авторизации и прямой барьер входа.

**Independent Test**: Запросить код, отправить неправильный код один раз, затем
отправить правильный код в том же состоянии и получить успешный вход.

**Acceptance Scenarios**:

1. **Given** активный email-код, **When** пользователь вводит неверный код в
   первый или второй раз, **Then** код остаётся доступным, поля ввода остаются
   на экране и показывается понятная ошибка.
2. **Given** активный email-код, **When** пользователь вводит правильный код
   после одной или двух ошибок, **Then** вход завершается обычным успешным
   способом.
3. **Given** активный email-код, **When** пользователь вводит неверный код в
   третий раз, **Then** дальнейшая проверка этого кода блокируется и пользователю
   предлагается запросить новый код.

### User Story 2 - Безопасно запросить новый код после блокировки (Priority: P2)

Пользователь после блокировки кода может запросить новый код, оставаясь в том же
сценарии входа и не теряя выбранный email и return path.

**Why this priority**: Блокировка должна быть восстановимой и не превращаться в
тупик для пользователя.

**Independent Test**: Заблокировать код тремя ошибками, запросить новый код и
успешно войти новым кодом.

**Acceptance Scenarios**:

1. **Given** код заблокирован после трёх неудачных проверок, **When** пользователь
   запрашивает новый код, **Then** отправка и дальнейший вход работают по
   существующим лимитам resend.
2. **Given** новый код выпущен, **When** пользователь вводит его, **Then** вход
   завершается успешно без изменения остальных auth-ограничений.

### User Story 3 - Сохранить защитные ограничения других email-flow (Priority: P3)

Существующие signup-flow используют тот же безопасный лимит проверки и не
получают обхода rate limit; account-linking остаётся отдельным proof-flow.

**Why this priority**: Изменение общего кода не должно ослабить соседние
сценарии авторизации и объединения аккаунтов.

**Independent Test**: Проверить signup повторным вводом и убедиться, что
account-linking и существующие replay/expiry проверки сохраняют fail-closed
поведение.

**Acceptance Scenarios**:

1. **Given** signup email-код, **When** пользователь ошибается менее трёх раз,
   **Then** он может повторить ввод в том же состоянии.
2. **Given** истёкший, использованный или повреждённый state, **When** он
   отправлен повторно, **Then** вход не выполняется и предлагается новый код.
3. **Given** account-linking flow, **When** он обрабатывает proof-код,
   **Then** его существующие ограничения account merge не изменяются этим
   исправлением.

## Edge Cases

- Четвёртая проверка того же state не должна создать сессию даже при правильном
  коде после трёх неудач.
- Ошибка неверного кода не должна помечать state как terminal до достижения
  лимита; replay и expiry остаются terminal.
- Повторная отправка продолжает использовать действующие лимиты: 3 отправки на
  email за 15 минут, 20 на IP за 15 минут и 5 для invitation-flow.
- Лимиты проверки email и IP не меняются: 10 на email за 15 минут и 40 на IP за
  15 минут.
- Код, email, токены, state nonce и приватное содержимое не должны появляться в
  логах, аналитике или evidence.

## Requirements

### Functional Requirements

- **FR-001**: Система MUST разрешать до трёх неудачных проверок одного
  email-кода в рамках одного auth state.
- **FR-002**: После трёх неудачных проверок система MUST блокировать дальнейшую
  проверку этого state; правильный код после блокировки не должен создавать
  сессию.
- **FR-003**: После первой и второй неверной проверки система MUST сохранить
  state активным и вернуть экран с возможностью повторно ввести код.
- **FR-004**: Ошибка неверного кода MUST быть явно объяснена, а форма ввода MUST
  оставаться доступной только пока state не заблокирован, не истёк и не был
  использован.
- **FR-005**: После блокировки система MUST предложить запросить новый код и
  сохранить текущий email и безопасный return path.
- **FR-006**: Существующие лимиты отправки, лимиты по email/IP, срок действия,
  browser binding, HMAC-проверка, single-use и replay protection MUST remain
  unchanged.
- **FR-007**: Signup email-flow MUST использовать тот же лимит трёх проверок;
  account-linking proof-flow MUST сохранить отдельное fail-closed поведение.
- **FR-008**: Auth audit MUST фиксировать каждую неудачную проверку без записи
  самого кода или чувствительных значений.

### Key Entities

- **Auth state**: Одноразовое состояние email-аутентификации с TTL, browser
  binding, результатом и защитой от повторного использования.
- **Rate-limit bucket**: Ограничитель попыток, привязанный к state, email и IP;
  в этой задаче меняется только state-лимит с 10 до 3.

## Success Criteria

### Measurable Outcomes

- **SC-001**: В 100% проверенных сценариев одна или две ошибки не препятствуют
  успешному входу по правильному коду в том же state.
- **SC-002**: В 100% проверенных сценариев четвёртая проверка после трёх ошибок
  не создаёт auth-сессию.
- **SC-003**: Все существующие focused auth, RLS и frontend contract tests
  проходят без обхода browser binding, expiry или replay protection.
- **SC-004**: В пользовательском сценарии после блокировки новый код можно
  запросить без повторного ввода email и без потери безопасного return path.

## Assumptions

- Текущий TTL email-кода 15 минут, лимиты отправки и лимиты email/IP остаются
  без изменений.
- Изменение распространяется на browser login и signup, которые используют
  общий email-code consumer; account-linking не расширяется в эту задачу.
- Новая миграция не требуется: state-specific rate-limit bucket уже существует
  и является источником числа попыток.
- Web и macOS WebView используют общий server-rendered email-code экран.
