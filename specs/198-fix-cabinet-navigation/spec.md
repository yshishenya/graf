# Feature Specification: Надёжная навигация кабинета

**Feature Branch**: `198-fix-cabinet-navigation`

**Created**: 2026-08-23

**Status**: Draft

**Input**: User description: «Не работает кнопка назад в верхней части экрана после перехода в настройки календаря. В других местах возможно тоже. Кнопка вперёд никогда не активна. Нужно перепроверить все элементы.»

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Вернуться на предыдущий экран (Priority: P1)

Пользователь открывает любой разрешённый раздел кабинета, включая настройки
календаря, и нажимает «Назад». Кабинет возвращает его на ближайший предыдущий
отличающийся безопасный экран, а не оставляет на том же URL.

**Why this priority**: Сейчас пользователь может застрять в настройках и не
понимать, сработала ли кнопка.

**Independent Test**: Открыть «Запись» → «Календари», а также «Настройки» →
«Тариф и оплата», нажать «Назад» и убедиться, что URL и содержимое меняются на
предыдущий экран.

**Acceptance Scenarios**:

1. **Given** пользователь перешёл из «Запись» в «Календари», **When** он
   нажимает «Назад», **Then** открывается «Запись».
2. **Given** в истории есть несколько одинаковых записей текущего URL,
   **When** пользователь нажимает «Назад», **Then** одинаковые записи
   пропускаются и выбирается ближайший предыдущий отличный безопасный экран.
3. **Given** предыдущая запись истории относится к авторизации, внешнему
   адресу, POST-действию или запрещённому маршруту, **When** пользователь
   нажимает «Назад», **Then** такая запись не открывается, а применяется
   существующий безопасный fallback кабинета.

---

### User Story 2 - Вернуться вперёд после возврата (Priority: P1)

После перехода назад пользователь может нажать «Вперёд» и вернуться на
следующий отличающийся безопасный экран. Кнопка активна только при наличии
такого экрана и не выглядит рабочей, если действие невозможно.

**Why this priority**: Верхняя кнопка «Вперёд» сейчас практически недоступна,
поэтому пользователь не может отменить возврат назад.

**Independent Test**: Перейти из календарей в другой раздел, нажать «Назад»,
дождаться завершения загрузки и нажать «Вперёд»; проверить возврат на исходный
раздел и корректное обновление состояния кнопки.

**Acceptance Scenarios**:

1. **Given** пользователь вернулся назад и в истории есть безопасный следующий
   экран, **When** загрузка завершилась, **Then** «Вперёд» активна.
2. **Given** ближайшая forward-запись совпадает с текущим URL, **When**
   контроллер вычисляет доступное действие, **Then** дубликат пропускается и
   выбирается следующий отличный безопасный экран.
3. **Given** безопасного следующего экрана нет, **When** пользователь смотрит
   на панель, **Then** «Вперёд» отключена и не запускает пустую навигацию.

---

### User Story 3 - Предсказуемо использовать остальные кнопки (Priority: P2)

Пользователь видит одинаковую панель «Домой», «Назад», «Вперёд» и
«Обновить» в разделах кабинета: встречи, обзор, запись, итоги, календари,
пространства, аккаунт, уведомления и тарифы. Состояния кнопок отражают
доступность действия и загрузку.

**Why this priority**: Общий контроллер должен быть проверен по всей общей
поверхности, а не только на календарях.

**Independent Test**: Последовательно открыть все перечисленные разделы,
зафиксировать URL и состояния четырёх кнопок, затем отдельно проверить
«Домой» и «Обновить» на безопасном маршруте.

**Acceptance Scenarios**:

1. **Given** пользователь находится не на списке встреч, **When** он нажимает
   «Домой», **Then** открывается канонический список встреч.
2. **Given** текущий экран — безопасный документ и загрузка завершена, **When**
   пользователь нажимает «Обновить», **Then** текущий экран перезагружается,
   а панель временно показывает состояние загрузки.
3. **Given** выполняется переход, **When** пользователь смотрит на панель,
   **Then** все четыре кнопки недоступны до завершения или обработки ошибки.
4. **Given** любой из перечисленных разделов открыт, **When** пользователь
   использует VoiceOver или клавиатурный shortcut, **Then** кнопка имеет
   устойчивую подпись, подсказку и accessibility identifier.

### Edge Cases

- История содержит подряд несколько одинаковых URL текущего документа.
- Между двумя безопасными документами есть небезопасные или не-документные
  записи.
- После истечения сессии история содержит защищённый кабинетный экран.
- Навигация не вернула объект операции, была отменена или завершилась ошибкой.
- Текущий экран уже является каноническим списком встреч либо fallback
  загружается синтетически.
- На маршруте отсутствует разрешённый forward/back элемент.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Общий контроллер навигации MUST выбирать для «Назад» ближайший
  безопасный элемент истории, URL которого отличается от текущего.
- **FR-002**: Общий контроллер MUST выбирать для «Вперёд» ближайший безопасный
  элемент истории, URL которого отличается от текущего, и переходить именно к
  выбранному элементу.
- **FR-003**: Контроллер MUST пропускать auth, external, artifact-download,
  POST и другие запрещённые записи в обоих направлениях, сохраняя существующие
  session-boundary и fallback ограничения.
- **FR-004**: `canGoBack` и `canGoForward` MUST быть `true` только если
  соответствующее действие действительно приведёт к разрешённому отличающемуся
  экрану; во время загрузки оба действия MUST быть недоступны.
- **FR-005**: «Домой» MUST открывать канонический список встреч только с
  разрешённым fallback-запросом, а «Обновить» MUST быть доступна только для
  текущего безопасного документа.
- **FR-006**: Панель навигации MUST сохранять единые подписи, подсказки,
  shortcuts и accessibility identifiers во всех разделах кабинета.
- **FR-007**: Проверки MUST покрывать календарь и остальные маршруты общей
  панели, включая встречи, настройки, запись, итоги, пространства, аккаунт,
  уведомления и тарифы.

### Key Entities *(include if data involved)*

- **History item**: Разрешённый элемент истории WebKit с URL и направлением
  относительно текущего документа.
- **Navigation state**: Публичное состояние контроллера (`canGoBack`,
  `canGoForward`, `canReload`, `canGoHome`, `isLoading`), отображаемое верхней
  панелью.
- **Cabinet route**: Экран кабинета, классифицированный существующей политикой
  маршрутов как безопасный, защищённый, внешний или запрещённый.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Целевые тесты на дубликаты, безопасные back/forward-переходы,
  fallback и loading state проходят без регрессий.
- **SC-002**: В ручном smoke-прогоне 100% перечисленных разделов показывают
  общую панель, а каждое доступное действие меняет экран или перезагружает его
  в течение одного пользовательского действия.
- **SC-003**: После сценария «раздел A → раздел B → Назад → Вперёд» URL и
  содержимое возвращаются из B в A без зацикливания на дубликате.
- **SC-004**: Запрещённые и истёкшие session-boundary маршруты не открываются
  через верхнюю панель.
- **SC-005**: Панель сохраняет доступные подписи и identifiers для всех четырёх
  кнопок во всех поддержанных разделах.

## Assumptions

- Существующая WebKit history policy, route policy и fallback списка встреч
  остаются источниками истины; новые маршруты и зависимости не требуются.
- «Вперёд» сохраняется как функция браузерной истории и отключается только
  при отсутствии безопасного отличающегося forward-элемента.
- Проверка UI выполняется на установленном GRAF и на целевом macOS SwiftPM
  тестовом наборе; production deploy и выпуск не входят в эту задачу.
- Изменение не затрагивает захват аудио, авторизацию, хранение встреч или
  серверные API.
